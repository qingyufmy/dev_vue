# 自动推理、挂单管理、持仓退出与趋势反转最终方案

> 状态：最终实施基准 v1.1（二次风险复审合并稿）
> 本文整合并取代《反向持仓与趋势翻转执行方案》和《自动推理融合持仓管理完整方案》作为后续开发主规格；原文仅保留问题追溯价值。v1.1 已合并管理对象分组、撤单成交竞态、账户归属代际、可恢复状态机、分段校验和无保护持仓处置等复审结论。

## 1. 最终结论

将新信号判断、挂单管理和持仓管理融合进同一次自动推理，但不直接恢复旧智能平仓。服务端先根据不可变原交易论点建立匿名管理组，模型只对管理组提出结构化候选，服务端再验证行情证据、策略归属、账户状态和执行条件，MT5 止损继续承担即时保护。

目标不是让 AI 高频决定平仓，而是让每次策略推理回答三个独立问题：

1. 当前是否存在新的交易机会；
2. 当前策略挂单是否仍然有效；
3. 当前策略持仓的原始交易逻辑是否已经失效。

只有第三项得到可靠证据确认后，才允许退出；只有原仓全部退出并完成 MT5 对账后，才允许重新风控反向开仓。

模型不直接输出可执行的“替换挂单”或“反手”命令。替换挂单由“旧挂单取消结论 + 独立的新挂单建议”派生；反手由“旧仓退出结论 + 独立的反向开仓建议 + 用户授权 + 完整开仓风控”派生。任一后续条件不成立时，已经独立验证通过的风险降低型退出不得被错误撤销。

## 2. 当前问题与改造边界

当前执行器遇到任意同品种反向持仓，会在订单意图和正式风控前以 `opposite_position_exists` 直接跳过。这能避免对锁，却无法处理可靠趋势翻转。旧智能平仓链又存在以下问题，因此不得直接启用：

- 使用独立高频调度和独立模型调用，可能与自动推理结论冲突；
- 面向账户全部持仓，缺少严格的策略归属边界；
- 使用金额、持仓时长等简单规则即可直接平仓；
- 会额外写入普通 `ai_signals`，可能污染推理、复盘与记忆链路；
- 缺少完整的退出意图、幂等状态机和反手前确认。

本次范围只包含：继续持有、取消或替换策略挂单、完整退出当前策略持仓、退出后可选反手。暂不包含部分减仓、移动止损、自动修改止盈、利润保护和净持仓混合仓位拆分。

## 3. 当前数据现状与必须修正项

### 3.1 止盈止损已经传入，但语义需拆分

| 场景 | 持仓数据 | 止盈止损 |
| --- | --- | --- |
| 平台策略 | 观摩源中归属于该平台策略的参考持仓 | 已传，但当前会把 MT5 实际值和原信号建议值混合回退 |
| 私有策略且开启账户上下文 | 用户账户实时持仓 | 传实际 `sl`、`tp` |
| 私有策略且关闭账户上下文 | 不传 | 不传，不允许产生持仓动作 |

启用持仓管理前必须改为：

- `actual_stop_loss`、`actual_take_profit`：MT5 当前真实设置，未设置必须明确为 `null`；
- `original_stop_loss`、`original_take_profits`：原始信号建议；
- `take_profit_tier`：实际采用档位；
- `protection_status`：实际是否具有止损、止盈保护；
- `protection_modified`：是否发生人工或后续流程修改；
- `position_ticket`、`position_id`、`origin_signal_id`、`delivery_id`、`outcome_id`、策略 ID：可追溯归属；
- `broker_server_key`、`login_account`、`ownership_history_id`、原始 broker symbol：可追溯账户归属代际。

严禁以原信号建议值冒充 MT5 当前保护值。

系统持仓的实际止损为空、为零、方向错误或无法从 MT5 确认时，必须进入“保护异常”状态：停止该账户新增风险、实时告警并要求人工处理。除非管理员另行启用确定性的应急退出权限，否则不得把原始建议止损冒充真实保护，也不得让模型自行决定如何补救。

### 3.2 平台参考持仓查询不能依赖最近 200 条交付

长时间持有或交易频繁时，原持仓交付可能超出最近 200 条，导致参考持仓被错误遗漏。应先从 MT5 获取当前活跃 ticket、position identifier 和历史关联，再以 `signal_outcomes` 为持仓归属主账，按 position、order、deal、交付和原信号关系精确查询；不得通过固定条数窗口推断归属。

挂单成交后，订单 ticket、deal ticket 和 position ticket 可能不同。Bridge 对账必须把三者关联到同一交付，不能假设挂单 ticket 永远等于持仓 ticket。

### 3.3 品种匹配分两层

行情分析可以使用去后缀后的标准品种名；真实订单归属和执行必须同时保存原始 broker symbol。不同后缀可能对应不同合约规格，不能仅凭 `XAUUSD` 标准名关闭 `XAUUSD.s`、`XAUUSDm` 等账户订单。

### 3.4 管理对象与账户归属必须版本化

服务端按以下稳定信息生成不可变管理组，模型只能引用服务端给出的组 ID：

```text
策略 ID + 策略版本 + 标准品种 + 原始信号/交易论点 + 方向
```

管理组只表达“哪一批原交易论点需要评估”，不直接等于某个用户 ticket。用户执行阶段再用当前 `ownership_history_id`、原始 broker symbol、`signal_outcomes.position_id` 和实时 MT5 ticket 映射目标集合。

账户执行身份以“经纪商服务器 + 登录账号”为稳定主键，并额外绑定当前归属历史 ID 与 Bridge 连接代际。用户 ID 或 `trading_account_id` 不能单独证明当前仍有执行权。

## 4. 统一模型输出合同

新信号、挂单评估和持仓评估必须相互独立，并按服务端管理组返回，避免 `signal_type=hold` 被误解成不能退出持仓，也避免单个方向字段误管多批不同来源的持仓：

```json
{
  "contract_version": "position-management-v1.1",
  "as_of": {
    "decision_timeframe": "M15",
    "closed_bar_time_utc_ms": 1784736900000,
    "market_snapshot_hash": "sha256:..."
  },
  "market_regime": "bearish",
  "trade_thesis": "reversal",
  "market_plan": {
    "signal_type": "sell",
    "confidence": 0.78,
    "entry_method": "market",
    "limit_price": null,
    "stop_limit_price": null,
    "stop_loss_price": 4135,
    "take_profit_1_price": 4070,
    "take_profit_2_price": 4050,
    "take_profit_3_price": 4020,
    "recommended_take_profit_tier": 1,
    "position_size_tier": "probe",
    "position_size_reason": "反转初次确认，仅建议试探仓"
  },
  "pending_evaluations": [
    {
      "management_group_id": "pending_group_01",
      "action": "cancel",
      "reason": "中文具体依据",
      "evidence_refs": ["bar:M15:1784736900000", "condition:pending_invalid_01"]
    }
  ],
  "position_evaluations": [
    {
      "management_group_id": "position_group_01",
      "thesis_id": "thesis_01",
      "action": "exit",
      "matched_condition_id": "invalidation_01",
      "reversal_candidate": true,
      "reason": "原交易逻辑是否失效的中文结论",
      "evidence_refs": ["bar:M15:1784736900000", "condition:invalidation_01"]
    }
  ]
}
```

约束：

- `market_regime` 仅允许 `bullish/bearish/range/uncertain`，`trade_thesis` 仅允许 `continuation/reversal/mean_reversion/breakout`；
- `market_plan` 继续执行现有新订单严格合同：`signal_type` 沿用买、卖、观望及六种挂单枚举，入场方式、触发价、Stop Limit 价格、止损、三档止盈和推荐止盈档位必须完整且方向正确；
- `position_size_tier` 仅允许 `none/probe/light/standard`，模型不得补充绝对手数；
- 挂单评估仅允许 `keep/cancel`，持仓评估仅允许 `hold/exit`；未命中冻结条件时 `matched_condition_id` 必须为 `null`；
- 顶层 `market_plan=hold` 与某个管理组 `action=exit` 是合法组合，表示不建立新仓但退出旧仓；
- `management_group_id`、`thesis_id`、`matched_condition_id` 和 `evidence_refs` 必须来自服务端输入，模型不得编造或改写；
- 共享模型不得看到或输出订阅用户 ticket；用户 ticket 只在服务端执行适配阶段解析；
- 模型不得直接输出 `replace` 或 `reverse`。`cancel + 新挂单建议` 才可能派生替换，`exit + 反向新仓建议 + trade_thesis=reversal` 才可能派生反手；均值回归默认不得派生反手；
- `reversal_candidate` 只是解释性判断，不是执行命令；无相关管理组时对应评估数组必须为空，不得输出虚构的 `none` 目标；
- `exit` 必须引用冻结条件、周期、已收盘 K 线和结构化证据；中文 `reason` 只用于解释，不作为执行依据；
- 各部分独立失败关闭：`market_plan` 无效只禁止新订单，挂单评估无效只禁止撤单，持仓评估无效只降级为该管理组继续持有；
- 跨计划冲突时禁止增加风险，但不得用无效的新仓建议覆盖已经独立验证通过的退出结论；
- 合同版本、快照哈希、决策周期或已收盘 K 线时间不匹配时，整份响应过期，不得执行；
- 用户可见分析、推理正文和多空解释可以继续返回，但不属于执行字段；服务端不得从分析正文猜测动作。

## 5. 原交易论点与失效判断

每个可执行开仓信号必须冻结一份带唯一 `thesis_id` 的结构化交易论点：

- 策略 ID、策略修订号、模型配置和输出协议版本；
- 主分析周期、决策周期和生成时最后一根已收盘 K 线时间；
- 方向、入场方式、核心入场依据；
- 关键支撑、阻力和失效价格；
- 不可变失效条件 ID、条件类型、方向、比较符、周期及需要的已收盘 K 线数量；
- 缠论笔、线段、中枢、背驰证据及可靠性；
- 原始止损、止盈候选和实际采用档位；
- 来源信号、订单意图、成交归因、交付记录和 MT5 ticket/position 关联；
- 生成时行情快照哈希、模型合同版本和最后一根已收盘 K 线时间。

持仓管理不是重新询问“现在涨还是跌”，而是比较原论点和当前证据。模型只能声明某个冻结条件是否满足，不得在持仓期间重新选择失效价格或把软条件改成硬条件。

既有持仓始终绑定开仓时的策略版本和原交易论点。策略、提示词、模型、输出合同或证据算法在两次软确认之间发生实质变化时，已有软确认计数必须清零，避免把不同规则下的结论拼成两次确认；但版本变化不得反向改写已冻结论点。

## 6. 防止震荡误平仓的六道闸门

### 6.1 候选闸门

模型默认 `hold`，不得仅因浮亏、接近止损、单根未收盘 K 线、影线刺破、单一指标、短周期反向、多空概率轻微变化或“不适合新开仓”而提出退出。

### 6.2 行情证据闸门

服务端使用已收盘 K 线独立验证冻结条件中的失效价格、方向和周期。K 线缓存存在缺口、末端不新鲜、MT5 市场时钟未确认或缠论可靠性不足时，不得自动平仓。

硬失效由服务端按预先冻结的确定性条件判断，可在一根已收盘 K 线确认后进入退出流程，不依赖模型把它分类为“硬失效”。软反转至少跨越一根新的已收盘决策周期 K 线并连续两次结论一致。

### 6.3 持续性与防抖闸门

- 同一根 K 线重复推理不得累计确认次数；
- 候选超过有效期、证据撤回或行情状态变化时自动失效；
- 自动平仓不设置每日次数上限或账户级冷却，避免延迟风险收缩；
- 冷静期内允许 MT5 止损和管理员应急操作，但不允许新的 AI 反手。

### 6.4 归属闸门

自动处理必须同时匹配：当前 MT5 账户身份、用户、策略、原信号、交付记录、原始 broker symbol、系统 Magic 和 position ticket。仅匹配 Magic 或标准化品种名均不够。

人工仓、其他策略仓、归属不明仓禁止自动修改。套期保值账户首期只按精确 ticket 完整平仓；净持仓账户若可能混合人工与系统成交量，一律转人工复核。

### 6.5 执行闸门

发送任何命令前重新获取持仓、挂单、报价、市场状态、账户归属和 Bridge 会话代际。候选生成后若用户已平仓、修改手数、修改止盈止损、切换账户、账户被其他用户接管或 Bridge 重连，必须使旧前置条件失效并重新对账，不得沿用旧快照执行。

### 6.6 合同隔离与保护异常闸门

- 新订单、挂单和持仓三个部分分别校验、分别失败关闭；
- 服务端只接受输入中已声明的管理组、条件和证据引用；
- 当前实际止损缺失或方向错误时，禁止新增风险并进入保护异常告警；
- 保护异常不得使用原始建议止损回填，也不得等待下一次普通 AI 推理后才暴露；
- 执行异常或短时集中爆发时触发平台冻结和人工复核，不得静默继续批量平仓。

## 7. 平台策略与私有策略

### 7.1 平台策略

观摩源当前策略参考组合只是一种市场参考，不是平台策略持仓管理范围的唯一来源。若观摩源已经止盈、止损或人工平仓，但订阅用户仍保留由该策略产生的持仓，仅依赖观摩源当前组合会使用户持仓成为无法继续评估的“孤儿仓”。

平台策略的管理范围必须由服务端根据仍处于 `open/closing` 的 `signal_outcomes`、当前活跃 position、原信号和冻结交易论点建立匿名管理组。共享模型只读取这些管理组的市场论点与参考组合，不读取余额、净值、盈亏、绝对手数、人工订单或订阅用户私有持仓。各用户执行阶段再读取真实账户：

- 存在当前策略对应持仓：进入退出验证；
- 没有对应持仓：忽略持仓动作；
- 只有人工或其他策略持仓：不处理并提示；
- 观摩源已无持仓但仍有订阅用户管理组：继续评估冻结论点，不得静默遗漏；
- 同一策略、品种存在多批原始信号：分别按 `thesis_id` 评估，不得用最新结论覆盖全部历史仓；
- 用户仓位、止盈止损与观摩源不同：以用户真实 MT5 状态为准；
- 用户实际状态不适合反手：可以只退出，或完全不执行。

平台参考组合不能保证每个用户都处于相同状态，所以模型不得指定用户 ticket、用户最终手数或订阅用户实际保护状态。

### 7.2 私有策略

只有开启“传入持仓与挂单”时，模型才可产生挂单和持仓评估。关闭后仍可分析行情，但 `pending_evaluations` 和 `position_evaluations` 必须为空数组。账户上下文开关与自动执行权限是两个独立权限，传入数据不代表允许自动平仓。若推理期间账户上下文关闭、账户切换或归属变化，旧响应立即过期。

## 8. 多持仓、订阅生命周期与并发控制

当前 V1 仍保持“每个用户同时只能启用一个自动推理订阅”，本方案不暗中放开多订阅并行执行。但以下情况仍会形成多来源持仓：用户替换订阅前已有未平仓订单、挂单成交晚到、历史策略被下线、人工介入，或未来明确开放多策略。

启用新订阅、停用自动推理、删除/下线策略或切换账户前，必须查询归属明确的未平持仓、挂单和未完成管理任务，不得静默遗留。存在敞口时由用户明确选择：

1. 暂不切换，等待原持仓退出；
2. 人工处理后再切换；
3. 显式启用“仅管理旧仓、不再开新仓”的看护模式。

关闭自动推理或交易发送后，系统不得偷偷继续 AI 管理；看护模式也必须单独授权。未授权时只保留 MT5 已设置止损、状态展示和人工处理入口。

同一账户、同一原始 broker symbol 的撤单、平仓和反手必须使用跨进程管理租约：

```text
broker_server_key + login_account + ownership_history_id + 原始 broker symbol
```

管理租约使用数据库条件更新、过期时间和单调递增 fencing token；不得持有数据库事务或行锁等待 MT5 网络调用。每个状态迁移使用短事务与版本号比较，旧 worker 即使恢复也不能覆盖新 worker。

租约应覆盖读取实时组合、取消挂单、平仓、MT5 对账和可能的反向开仓，不能只锁单个调度器进程。获得租约后必须重新读取状态，并确认当前账户归属和 Bridge generation 与任务创建时一致。

多笔同策略同方向持仓按 ticket/position 建立子任务，但退出后反手是管理组级动作：只有本次目标组全部关闭，才允许创建一笔新的反向订单。部分成功时保持任务待对账，禁止按已关闭手数比例提前反手。

不同策略意见冲突时不得互相关闭持仓；系统只管理各自可追溯持仓。若账户类型无法隔离，自动持仓管理不可用。

## 9. 挂单、退出和反手的固定顺序

处理顺序必须固定：

1. 创建或认领持久化管理任务，取得账户品种租约和 fencing token；
2. 验证经纪商服务器、登录账号、当前归属历史、Bridge generation 和交易权限；
3. 获取账户实时持仓、挂单、报价和市场状态，锁定当前策略、交易论点、方向及归属明确的目标集合；
4. 持久化撤单命令及稳定 `operation_id`，再取消会恢复原方向风险或与反手冲突的策略挂单；
5. 查询当前挂单、历史订单、成交和持仓，明确区分“已取消”“撤单期间已成交”和“状态未知”；
6. 撤单期间成交时重新建立目标集合并停止本次反手；首期转人工复核，不得把“挂单消失”当作撤单成功；
7. 持久化退出意图和命令前置条件，完整关闭目标持仓；
8. 按 position、deal 和实时持仓二次确认目标持仓全部消失；部分成功或状态未知时只进入对账，不得反手；
9. 重新读取账户归属、Bridge generation、报价、点差、市场状态和新信号有效期；
10. 对反向新仓执行完整的开仓风控和手数计算；
11. 使用现有 `order_intents` 创建新的反向订单意图，发送后再次对账。

任一步失败立即停止后续增加风险的动作。宁可保持空仓，也不得为了同时完成而形成短暂对锁。已确认部分平仓时，可以在同一任务中对剩余仓位重新读取并进行有限次数重试；未知结果未完成对账前不得重发。

## 10. 持久化状态机与幂等

必须新增 `ai_position_management_tasks`、`ai_position_management_events` 和 `ai_position_management_commands`，不要把退出过程伪装成新的普通信号。`signal_outcomes` 继续作为开仓、position 和成交归属主账，管理任务只引用它，不复制出第二套互相竞争的归属账本。

最小数据合同：

| 表 | 必须保存的字段与约束 |
| --- | --- |
| `ai_position_management_tasks` | 任务类型、执行能力、用户与交易账户、`ownership_history_id`、账户稳定身份、原始/标准品种、策略及版本、`management_group_id`、`thesis_id`、原信号、`outcome_id`、决策 K 线、快照哈希、候选动作、状态与版本、租约、`fencing_token`、前置条件哈希、候选过期时间和完成时间 |
| `ai_position_management_commands` | `task_id`、命令序号、全局唯一 `operation_id`、撤单/平仓命令类型、预期账户与持仓条件、发送参数、发送状态、MT5 原始结果、对账状态和对账时间 |
| `ai_position_management_events` | `task_id`、前后状态、事件类型、中文审计摘要、结构化详情、操作者与时间；只追加，不覆盖历史 |

真实持仓动作的 `outcome_id`、`ownership_history_id`、`management_group_id` 和 `thesis_id` 不得为空。全局唯一 `operation_id` 防止业务命令重复；同一账户归属、原始品种、管理组、决策 K 线和动作只能存在一个有效任务。所有状态变更必须比较 `state_version` 和 `fencing_token`。

```text
CANDIDATE
  → EVIDENCE_CONFIRMED
  → PRECONDITIONS_LOCKED
      ├─ 无目标挂单 ───────────────────────┐
      └─ PENDING_CANCEL_INTENT             │
           → PENDING_CANCEL_SENT           │
           → PENDING_RECONCILING           │
               ├─ PENDING_CANCEL_CONFIRMED ┘
               ├─ PENDING_FILLED_DURING_CANCEL → MANUAL_REVIEW
               └─ PENDING_UNCERTAIN → 等待对账
  → CLOSE_INTENT_CREATED
      → CLOSE_SENT
      → CLOSE_RECONCILING
          ├─ CLOSE_CONFIRMED
          │    ├─ 无有效反向新仓 → EXIT_ONLY_COMPLETED
          │    └─ REENTRY_RISK_CHECKED
          │         → REENTRY_INTENT_CREATED
          │         → REENTRY_SENT
          │         → REENTRY_RECONCILING
          │         → COMPLETED
          ├─ CLOSE_PARTIAL → 等待对账/有限重试
          └─ CLOSE_UNCERTAIN → 等待对账
```

纯挂单管理任务可以在 `PENDING_CANCEL_CONFIRMED` 后完成，不强制进入平仓分支；没有挂单的持仓任务可跳过挂单分支。状态分支必须由服务端工作流决定，不能依赖模型文字。

`HELD`、`EXPIRED`、`REJECTED`、`COMPLETED` 和 `EXIT_ONLY_COMPLETED` 可以作为明确终止状态。`PENDING_FILLED_DURING_CANCEL`、`PENDING_UNCERTAIN`、`CLOSE_PARTIAL`、`CLOSE_UNCERTAIN`、`REENTRY_RECONCILING` 和 `MANUAL_REVIEW` 都是待对账或待处理状态，不得伪装成终止失败；只有确认没有外部副作用后，`FAILED` 才能终止。

幂等分三层：

1. 管理任务键：账户归属历史、策略、交易论点、管理组、决策 K 线和请求动作；
2. Bridge 命令键：`task_id + command_type + command_sequence`，发送前持久化稳定 `operation_id`、参数和前置条件；
3. 反向新仓键：继续复用 `order_intents` 的订单幂等与风险预留。

WebSocket `command_id` 只用于单次连接的请求响应关联，不得充当业务幂等键。Bridge 必须从命令参数读取并原样回传稳定 `operation_id`。若 Bridge 支持持久化去重，应对重复命令返回原结果；若暂不支持，服务端必须通过历史订单、成交和 position 对账，结果未知时不得自动重发平仓或开仓命令。服务重启或 Bridge 断线后，先对账再恢复。

服务端在真正写入 WebSocket 前必须再次以条件更新确认任务版本、租约 token 和 fencing token 仍有效；Bridge 端再比较预期账户、原始品种、ticket/position、方向、Magic 和预期手数，形成服务端与 MT5 端双重前置条件。

## 11. 开关与风控语义

管理员分别控制三项独立平台能力：自动平仓、AI 挂单、AI 取消挂单。用户只保存自己的自动平仓偏好：

1. `关闭`：仅关闭该用户的自动平仓，不影响证据充分的策略挂单取消；
2. `自动平仓`：用户默认值，只允许平掉已有策略持仓；
3. `退出后允许反手`：退出确认后允许重新风控入场。

权限关系：

- 自动推理关闭：不产生新的 AI 持仓判断；
- 交易发送关闭：不得取消、平仓或开仓；
- 用户未开启自动平仓：不生成新的平仓任务，但挂单取消仍按独立证据链执行；
- 用户没有保存过个人设置时默认开启自动平仓；用户手动关闭后，平台总闸关闭再开启也不得替用户重新开启；
- 自动平仓平台开关只限制平仓，不修改用户保存的个人开关；
- AI 挂单平台开关只限制新增 AI 限价、止损和止损限价挂单，不影响市价单、已有挂单取消或自动平仓；
- AI 取消挂单平台开关只限制 AI 自动撤销策略挂单，不影响新增挂单、自动平仓或人工撤单；
- 全局“禁止新增风险”阻止新开仓、加仓和反手入场，但不阻止已授权的策略撤单和风险降低型退出；
- 管理员“应急平仓”是第三种独立人工权限，不能由模型触发，也不等同于恢复全部自动交易。

三项 AI 执行能力必须使用不同的配置项和中文说明，禁止继续使用含义模糊的单一“禁止全部交易”开关。

自动平仓属于风险收缩操作，不使用每日次数或账户冷却阻断；反手属于新增风险，仍必须走独立的新单风控。执行异常或短时集中爆发由平台冻结和人工复核处理。

退出使用独立安全检查，不复用最低盈亏比、入场价格偏差、最大新仓手数等开仓规则。反手新仓必须重新通过全部现有开仓风控。退出遇到极端点差或报价异常时短暂重试并保留原 MT5 止损保护；不得无限重试或改成无保护等待。若实际止损本身缺失，则不能套用“等待止损保护”的普通重试逻辑，必须立即进入保护异常和人工/应急处置流程。

## 12. 前端与中文审计

推理结果仅在存在相关持仓或挂单时展示“挂单处理”和“持仓处理”：

- 当前实际持仓、实际止盈止损及原始建议；
- 当前保护是否有效；保护异常必须高优先级展示；
- 继续持有、退出建议，以及服务端是否具备派生反手条件；
- 原交易论点、管理批次、冻结失效条件和已确认依据；
- 当前阶段、等待条件和下一步；
- 撤单已确认、撤单期间成交、部分平仓、正在对账或人工复核；
- 未执行、被拒绝、执行失败或状态未知的具体中文原因。

风控与审计至少区分：持仓对齐跳过、证据不足、持仓归属不明、保护异常、账户归属变化、Bridge 会话变化、挂单取消失败、撤单期间成交、挂单状态未知、退出风控拒绝、平仓发送失败、平仓状态未知、部分平仓、退出成功但新仓风控拒绝、翻转完成。

内部规则码可保存用于诊断，但不得直接显示给用户。执行记录必须关联原信号、交易论点、管理组、成交归因、交付、ticket/position、账户归属历史、快照、模型结论、证据验证、`operation_id`、MT5 原始返回和最终状态。

任务状态变化必须通过现有 WSS 实时推送到用户界面和管理后台；断线重连后再从数据库读取任务主状态补齐，不得只依赖前端轮询或一次性消息。

## 13. 复盘、记忆与结果归因

AI 退出不能生成一条虚假的普通开仓信号，否则会导致日复盘重复、交易笔数异常和记忆归因错误。退出结果应通过 `outcome_id`、`thesis_id` 和管理任务归属于原始持仓、原始信号和原始策略。

- 平台策略的退出经验进入平台策略复盘，不注入订阅用户个人记忆；
- 私有策略的退出经验只归属于该用户策略；
- 复盘比较原止损结果、假设继续持有结果和实际 AI 退出结果；
- 撤单期间成交必须先补齐该成交的 outcome/position 归属，再记录管理任务如何处理；
- 只有已确认且通过复盘的结论才能进入对应策略记忆；
- 只按已确认的真实执行结果归因收益；候选建议不得混入真实收益统计。

## 14. 性能与行情完整性

- 复用自动推理现有行情快照，不启动第二套智能平仓模型循环；
- 仅在服务端存在活跃管理组时附加交易论点和参考组合上下文，不以观摩源当前是否持仓作为唯一判断；
- 同一根已收盘决策周期 K 线只评估一次；
- 平台策略保持一次共享推理，不按订阅用户重复调用模型；
- 同一策略品种存在多个交易论点时按管理组数组返回；超过单次合同上限时按组分批，不得截断、合并不同论点或改成逐用户模型调用；
- 硬失效条件由服务端确定性计算，不为它额外启动模型调用；
- 执行前只读取必要的实时持仓、挂单和报价；
- K 线缓存必须检查末端时间、连续性、市场开闭状态和 MT5 时区；
- 缓存断档或市场时钟不可信时，只展示建议，不执行持仓动作；
- 每次外部命令前保存账户、组合、报价、Bridge generation 和管理组状态的前置条件哈希；状态一旦变化，立即使旧候选失效。

## 15. 分阶段实施

### 阶段一：数据与协议

- 拆分实际止盈止损和原始建议；
- 以 `signal_outcomes` 为主账修复活跃 ticket/position 精确归属及挂单成交关联；
- 冻结结构化原交易论点、条件 ID 和匿名管理组；
- 引入 `position-management-v1.1` 输出合同、分段校验和服务端派生动作；
- Bridge 增加稳定 `operation_id` 回传、账户/持仓前置条件校验及订单、成交、position 对账能力；
- 任务和命令绑定账户归属历史、Bridge generation 与原始 broker symbol；
- 增加无真实止损的保护异常、停止新增风险和实时告警；
- 保持旧智能平仓总开关关闭。

### 阶段二：证据验证与界面

- 自动推理按管理组生成挂单和持仓评估；
- 建立持久化管理任务、命令、事件和中文审计；
- 在测试环境覆盖撤单期间成交、账户换绑、Bridge 重连和部分平仓；
- 正式环境只保留真实候选、证据、命令和最终态，不提供影子模拟运行。

### 阶段三：自动平仓

- 实现带 fencing token 的数据库租约、归属闸门、退出专用检查和 MT5 对账；
- 首期只支持套期保值账户中归属明确的完整持仓；
- 撤单期间成交、状态未知和部分平仓一律不进入反手；
- 只平仓，不反手；
- 小范围按策略、观摩源和用户灰度。

### 阶段四：退出后反手

- 由“已验证退出 + 独立反向新仓建议”派生反手，不接受模型直接 `reverse`；
- 先确认冲突挂单真正取消且未成交，再平仓并确认；
- 重新进行完整开仓风控；
- 反向订单继续复用 `order_intents` 幂等和风险预留；
- 首期反手最高为试探仓；
- 设置冷静期和次数上限；
- 稳定后再评估是否开放轻仓。

### 阶段五：高级能力再评估

根据真实数据决定是否支持净持仓账户、部分减仓、移动止损、动态止盈和完整智能平仓。不得与前四阶段同时上线。

## 16. 真实运行指标

按策略、交易论点、品种、周期和行情状态统计真实候选与真实执行：候选数、证据确认数、撤回数、实际执行数、数据缺失、归属不明、部分执行、MT5 状态未知、撤单期间成交、账户归属变化、Bridge 重连失效、平仓滑点、耗时和失败率。未向 MT5 发送命令的候选不得伪装成模拟收益或真实交易结果。

每次灰度升级前必须在发布记录中固定样本门槛、最大误退出率、数据完整率和状态未知处理时限，并使用置信区间审查，而不是运行后挑选有利口径。无论收益指标如何，以下事件均为硬阻断：误伤人工/其他策略仓、重复命令、账户归属错误、未确认平仓即反手、未解决的超时未知状态。

没有足够且口径一致的真实样本时不能仅凭少量成功案例开放自动执行。

## 17. 最终风险审查

以下异常在实施中最容易被遗漏，均应设为发布阻断项：

| 风险 | 可能后果 | 强制措施 |
| --- | --- | --- |
| 旧智能平仓与新链路并存 | 同一持仓被重复处理 | 旧调度器继续硬关闭，新能力使用独立模块和任务表 |
| 单个方向计划管理多批不同论点 | 错误关闭历史仓或遗漏目标仓 | 按 `thesis_id` 建立管理组并返回评估数组 |
| 观摩源已平仓但订阅用户仍持仓 | 用户仓成为孤儿，永远不再评估 | 以开放 `signal_outcomes` 和实时 position 建立平台管理范围 |
| 模型重写失效价格或条件类型 | 为了当前结论移动退出标准 | 条件在开仓时冻结，模型只能引用条件 ID |
| 两个策略同时操作同一品种 | 平仓、撤单、反手相互覆盖 | 按稳定账户身份、归属历史与原始 broker symbol 使用租约和 fencing token |
| 参考组合与用户实际组合不同 | 关闭错误持仓或错误反手 | 模型只给通用意图，用户执行前重新读取和适配 |
| 最近 200 条交付漏掉长持仓 | 模型看不到真实策略仓 | 以开放 `signal_outcomes` 和当前活跃 ticket/position 精确查询 |
| 挂单 ticket 与持仓 ticket 不同 | 归属断裂 | 建立 order、deal、position ticket 对账关联 |
| 撤单时挂单恰好成交 | 把成交误认为撤单成功，随后错误反手 | 查询历史订单、成交和持仓，成交时重建目标并停止反手 |
| 实际 SL/TP 与原建议混合 | 模型误认为已有保护 | 分字段保存，缺失必须为 `null` |
| 系统持仓没有真实止损 | 等待 AI 期间暴露无限风险 | 停止新增风险、实时告警并进入独立保护异常流程 |
| 未收盘 K 线或缓存断档 | 震荡中异常退出 | 已收盘验证、连续性与新鲜度检查 |
| 用户在确认期间手动操作 | 使用过期快照平错仓 | 执行前重新读取，状态变化即取消候选 |
| 平仓部分成功 | 提前反手造成双向风险 | 全部目标 ticket 确认消失后才允许反手 |
| 账户换绑或被其他用户接管 | 在错误账户或错误归属期执行 | 任务绑定账户归属历史并在 Bridge 内再次比较账户身份 |
| Bridge 重连后旧 worker 恢复 | 旧快照覆盖新状态或重复发送 | 绑定 Bridge generation，状态迁移使用 fencing token |
| 服务重启或 Bridge 超时 | 重复平仓或重复开仓 | 持久化任务/命令、稳定 operation ID、先对账后恢复 |
| 把 `UNCERTAIN` 当终止失败 | 未知副作用被遗忘或被重新发送 | 未知、部分和人工复核均保持可恢复状态 |
| 净持仓混合人工成交 | 误关人工仓位 | 首期禁用，无法证明纯归属即人工复核 |
| 去后缀品种误匹配 | 操作不同合约 | 执行归属必须匹配原始 broker symbol |
| 开仓风控用于退出 | 风险已失效却无法减仓 | 退出使用独立安全检查，反手才走开仓风控 |
| 新仓字段无效导致整份响应归零 | 已验证退出被错误撤销 | 三个计划分段校验，禁止新增风险但保留独立有效退出 |
| 订阅切换时仍有敞口 | 历史策略仓失去管理或被新策略误管 | 切换前检查并要求等待、人工处理或显式旧仓看护 |
| AI 退出写成普通信号 | 复盘重复、记忆污染 | 使用独立管理任务并归因原始持仓 |
| 模型或策略在两次确认间变化 | 拼接不同规则得出假确认 | 策略修订变化时清零确认计数 |
| 交易开关语义不清 | 一个开关误伤平仓、挂单或撤单中的其他能力 | 分离自动平仓、AI 挂单、AI 取消挂单和用户个人平仓偏好 |

## 18. 必测验收场景

- 接近止损但原逻辑未失效时继续持有；
- 影线刺破后收回、未收盘突破和单指标反转均不退出；
- 硬失效和软反转确认规则正确区分；
- 模型无法修改冻结失效价、条件类型和所需确认 K 线数；
- 同一根 K 线重复推理不累计确认；
- 无效的新仓建议不会覆盖另一个管理组已经验证通过的退出；
- 顶层 `market_plan=hold` 与某个管理组 `exit` 能退出旧仓但不创建新仓；
- 同策略品种的多个 `thesis_id` 分别管理，不互相覆盖；
- 观摩源已平仓但订阅用户仍持仓时，该管理组仍会进入评估；
- 派生反手必须先确认冲突挂单真正取消、再平仓、确认后重新风控；
- 挂单在撤单期间成交时能够识别新 position，并停止本次反手；
- 人工仓、其他策略仓、归属不明仓和混合净持仓不被处理；
- 多策略并发、重复消息、服务重启和 Bridge 重连不会重复执行；
- 用户手动平仓、修改 SL/TP、切换账户、账户被接管或 Bridge 重连后候选自动失效；
- Bridge 收到不匹配的账户、ticket、方向、Magic、手数或 operation ID 时拒绝执行；
- 平仓失败、超时、部分成功和状态未知时绝不反手；
- 未知和部分状态保持可恢复，重启后先对账且不会盲目重发；
- 实际止损缺失时停止新增风险、产生实时告警且不使用原建议回填；
- 带未平仓敞口切换订阅时必须显式选择处理方式；
- 自动平仓、AI 挂单、AI 取消挂单和用户个人平仓偏好行为互不混淆；关闭任一平台能力不得误伤另外两项；
- 平台共享信号在不同用户组合下得到正确个性化结果；
- 未执行候选不计入真实收益和真实交易数；
- 所有前端状态、拒绝原因和审计说明使用自然中文。

## 19. 最终实施裁决

本方案能够解决 `opposite_position_exists` 无条件阻断趋势翻转的问题，但实现重点不是删除该保护，也不是允许模型直接 `reverse`，而是把它改为按账户归属和原交易论点安全分流：

```text
反向持仓存在
  → 账户归属或管理组不清：保持并提示
  → 冻结原论点未失效：保持并跳过新仓
  → 冻结原论点确认失效：只退出
  → 独立反向新仓建议仍有效且用户授权：退出确认后再进入订单意图与完整风控
```

推荐发布顺序严格保持为：数据修正与协议加固 → 自动平仓 → 派生反手。任何阶段都不得依赖提示词直接操作持仓，也不得为了让反向信号成交而绕过管理组、账户归属、对账和风控。

本 v1.1 方案只有在管理组、冻结论点、撤单成交识别、账户归属代际、稳定 operation ID、可恢复状态机和保护异常七项基础能力全部完成后，才可开启自动平仓；其中任一项缺失时必须保持关闭。
