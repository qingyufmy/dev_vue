# 自动推理、挂单管理、持仓退出与趋势反转最终方案

> 状态：最终实施基准
> 本文整合并取代《反向持仓与趋势翻转执行方案》和《自动推理融合持仓管理完整方案》作为后续开发主规格；原文仅保留问题追溯价值。

## 1. 最终结论

将新信号判断、挂单管理和持仓管理融合进同一次自动推理，但不直接恢复旧智能平仓。模型负责提出结构化候选，服务端负责验证行情证据、策略归属、账户状态和执行条件，MT5 止损继续承担即时保护。

目标不是让 AI 高频决定平仓，而是让每次策略推理回答三个独立问题：

1. 当前是否存在新的交易机会；
2. 当前策略挂单是否仍然有效；
3. 当前策略持仓的原始交易逻辑是否已经失效。

只有第三项得到可靠证据确认后，才允许退出；只有原仓全部退出并完成 MT5 对账后，才允许重新风控反向开仓。

## 2. 当前问题与改造边界

当前执行器遇到任意同品种反向持仓，会在订单意图和正式风控前以 `opposite_position_exists` 直接跳过。这能避免对锁，却无法处理可靠趋势翻转。旧智能平仓链又存在以下问题，因此不得直接启用：

- 使用独立高频调度和独立模型调用，可能与自动推理结论冲突；
- 面向账户全部持仓，缺少严格的策略归属边界；
- 使用金额、持仓时长等简单规则即可直接平仓；
- 会额外写入普通 `ai_signals`，可能污染推理、复盘与记忆链路；
- 缺少完整的退出意图、幂等状态机和反手前确认。

本次范围只包含：继续持有、取消或替换策略挂单、完整退出当前策略持仓、退出后可选反手。暂不包含部分减仓、移动止损、自动修改止盈、利润保护和净持仓混合仓位拆分。

## 3. 当前数据现状与必须修正项

### 3.1 止盈止损已经传入，但语义需拆分

| 场景 | 持仓数据 | 止盈止损 |
| --- | --- | --- |
| 平台策略 | 观摩源中归属于该平台策略的参考持仓 | 已传，但当前会把 MT5 实际值和原信号建议值混合回退 |
| 私有策略且开启账户上下文 | 用户账户实时持仓 | 传实际 `sl`、`tp` |
| 私有策略且关闭账户上下文 | 不传 | 不传，不允许产生持仓动作 |

启用持仓管理前必须改为：

- `actual_stop_loss`、`actual_take_profit`：MT5 当前真实设置，未设置必须明确为 `null`；
- `original_stop_loss`、`original_take_profits`：原始信号建议；
- `take_profit_tier`：实际采用档位；
- `protection_status`：实际是否具有止损、止盈保护；
- `protection_modified`：是否发生人工或后续流程修改；
- `position_ticket`、`origin_signal_id`、`delivery_id`、策略 ID：可追溯归属。

严禁以原信号建议值冒充 MT5 当前保护值。

### 3.2 平台参考持仓查询不能依赖最近 200 条交付

长时间持有或交易频繁时，原持仓交付可能超出最近 200 条，导致参考持仓被错误遗漏。应先从 MT5 获取当前活跃 ticket，再按 ticket 精确查询交付记录；不得通过固定条数窗口推断归属。

挂单成交后，订单 ticket、deal ticket 和 position ticket 可能不同。Bridge 对账必须把三者关联到同一交付，不能假设挂单 ticket 永远等于持仓 ticket。

### 3.3 品种匹配分两层

行情分析可以使用去后缀后的标准品种名；真实订单归属和执行必须同时保存原始 broker symbol。不同后缀可能对应不同合约规格，不能仅凭 `XAUUSD` 标准名关闭 `XAUUSD.s`、`XAUUSDm` 等账户订单。

## 4. 统一模型输出合同

新信号、挂单计划和持仓计划必须相互独立，避免 `signal_type=hold` 被误解成不能退出持仓：

```json
{
  "market_regime": "bullish | bearish | range | uncertain",
  "trade_thesis": "continuation | reversal | mean_reversion | breakout",
  "market_plan": {
    "signal_type": "buy | sell | hold | buy_limit | sell_limit | buy_stop | sell_stop | buy_stop_limit | sell_stop_limit",
    "position_size_tier": "none | probe | light | standard"
  },
  "pending_plan": {
    "action": "none | keep | cancel | replace",
    "managed_direction": "buy | sell | none",
    "reason": "中文具体依据"
  },
  "position_plan": {
    "action": "none | hold | exit | reverse",
    "managed_direction": "buy | sell | none",
    "reason": "原交易逻辑是否失效的中文结论",
    "evidence": ["M15 已收盘K线跌破 4120"],
    "invalidation": {
      "kind": "hard | soft",
      "timeframe": "M15",
      "price": 4120,
      "confirmation": "closed_below | closed_above",
      "required_closed_bars": 2
    }
  }
}
```

约束：

- `hold + exit` 是合法组合，表示不建立新仓但退出旧仓；
- `reverse` 必须伴随明确的 `reversal` 交易论点，均值回归默认不得反手；
- `exit/reverse` 必须包含价格、周期、已收盘确认方式和中文证据；
- 模型不得输出最终绝对手数，只能选择仓位档位；
- 字段缺失、枚举无效、证据冲突、价格异常时统一降级为 `hold`；
- 服务端不得从分析正文猜测动作。

## 5. 原交易论点与失效判断

每个可执行开仓信号必须冻结一份结构化交易论点：

- 策略 ID、策略修订号、模型配置和输出协议版本；
- 主分析周期、决策周期和生成时最后一根已收盘 K 线时间；
- 方向、入场方式、核心入场依据；
- 关键支撑、阻力和失效价格；
- 失效方向、确认方式及需要的已收盘 K 线数量；
- 缠论笔、线段、中枢、背驰证据及可靠性；
- 原始止损、止盈候选和实际采用档位；
- 来源信号、交付记录和 MT5 ticket 关联。

持仓管理不是重新询问“现在涨还是跌”，而是比较原论点和当前证据。策略、提示词或模型在两次确认之间发生实质变化时，已有软确认计数必须清零，避免把不同规则下的结论拼成两次确认。

## 6. 防止震荡误平仓的五道闸门

### 6.1 候选闸门

模型默认 `hold`，不得仅因浮亏、接近止损、单根未收盘 K 线、影线刺破、单一指标、短周期反向、多空概率轻微变化或“不适合新开仓”而提出退出。

### 6.2 行情证据闸门

服务端使用已收盘 K 线独立验证失效价格、方向和周期。K 线缓存存在缺口、末端不新鲜、MT5 市场时钟未确认或缠论可靠性不足时，不得自动退出。

硬失效可在服务器定义的一根已收盘 K 线确认后退出；软反转至少跨越一根新的已收盘决策周期 K 线并连续两次结论一致。“硬失效”分类不能完全由模型自行决定，必须符合策略预先保存的确定性条件。

### 6.3 持续性与防抖闸门

- 同一根 K 线重复推理不得累计确认次数；
- 候选超过有效期、证据撤回或行情状态变化时自动失效；
- 自动退出或反手后进入冷静期；
- 设置每个持仓、账户和策略的每日自动退出与反手次数上限；
- 冷静期内允许 MT5 止损和管理员应急操作，但不允许新的 AI 反手。

### 6.4 归属闸门

自动处理必须同时匹配：当前 MT5 账户身份、用户、策略、原信号、交付记录、原始 broker symbol、系统 Magic 和 position ticket。仅匹配 Magic 或标准化品种名均不够。

人工仓、其他策略仓、归属不明仓禁止自动修改。套期保值账户首期只按精确 ticket 完整平仓；净持仓账户若可能混合人工与系统成交量，一律转人工复核。

### 6.5 执行闸门

发送任何命令前重新获取持仓、挂单、报价、市场状态和 Bridge 会话。候选生成后若用户已平仓、修改手数、修改止盈止损、切换账户或 Bridge 重连，必须重新对账，不得沿用旧快照执行。

## 7. 平台策略与私有策略

### 7.1 平台策略

共享模型只读取观摩源当前策略的参考组合，不读取余额、净值、盈亏、绝对手数、人工订单或订阅用户私有持仓。模型输出通用市场结论和策略级持仓意图，各用户执行阶段再读取真实账户：

- 存在当前策略对应持仓：进入退出验证；
- 没有对应持仓：忽略持仓动作；
- 只有人工或其他策略持仓：不处理并提示；
- 用户仓位、止盈止损与观摩源不同：以用户真实 MT5 状态为准；
- 用户实际状态不适合反手：可以只退出，或完全不执行。

平台参考组合不能保证每个用户都处于相同状态，所以模型不得指定用户 ticket 或用户最终手数。

### 7.2 私有策略

只有开启“传入持仓与挂单”时，模型才可产生挂单和持仓计划。关闭后仍可分析行情，但 `pending_plan` 和 `position_plan` 必须强制为 `none`。账户上下文开关与自动执行权限是两个独立权限，传入数据不代表允许自动平仓。

## 8. 多策略、多持仓与并发控制

同一账户可能同时订阅多个策略，甚至在相同品种上产生不同计划。必须使用数据库级互斥锁：

```text
交易账户身份 + 原始 broker symbol
```

锁应覆盖读取实时组合、取消挂单、平仓、MT5 对账和可能的反向开仓，不能只锁单个调度器进程。获得锁后必须重新读取状态。

多笔同策略同方向持仓按 ticket 建立子任务，但退出后反手是组级动作：只有本次目标组全部关闭，才允许创建一笔新的反向订单。部分成功时保持任务待对账，禁止按已关闭手数比例提前反手。

不同策略意见冲突时不得互相关闭持仓；系统只管理各自可追溯持仓。若账户类型无法隔离，自动持仓管理不可用。

## 9. 挂单、退出和反手的固定顺序

处理顺序必须固定：

1. 获取账户实时持仓与挂单；
2. 锁定当前策略、当前方向、归属明确的目标集合；
3. 取消会恢复原方向风险或与反手冲突的策略挂单；
4. MT5 二次确认目标挂单已经消失；
5. 创建持久化退出意图；
6. 完整关闭目标持仓；
7. MT5 二次确认目标持仓全部消失；
8. 重新读取账户、报价、点差、市场状态和信号有效期；
9. 对反向新仓执行完整的开仓风控和手数计算；
10. 发送反向订单并再次对账。

任一步失败立即停止后续动作。宁可保持空仓，也不得为了同时完成而形成短暂对锁。

## 10. 持久化状态机与幂等

建议新增 `ai_position_management_tasks` 和 `ai_position_management_events`，不要把退出过程伪装成新的普通信号。

```text
CANDIDATE
  → EVIDENCE_CONFIRMED
  → PENDING_CANCEL_INTENT
  → PENDING_CANCEL_CONFIRMED
  → CLOSE_INTENT_CREATED
  → CLOSE_SENT
  → CLOSE_CONFIRMED
  → REENTRY_RISK_CHECKED
  → REENTRY_SENT
  → COMPLETED
```

终止状态包括 `HELD`、`EXPIRED`、`REJECTED`、`FAILED`、`UNCERTAIN` 和 `MANUAL_REVIEW`。状态迁移必须使用条件更新，禁止并发覆盖。

幂等键至少包含：账户身份、策略 ID、来源信号、position ticket、动作和阶段。服务重启或 Bridge 断线后，先向 MT5 对账再恢复；结果未知时不得自动重发平仓或开仓命令。

## 11. 开关与风控语义

管理员设置平台最大能力，用户只能在范围内选择：

1. `仅展示建议`：默认；
2. `影子评估`：记录假设结果，不发送 MT5 指令；
3. `自动退出策略持仓`：只允许退出；
4. `退出后允许反手`：退出确认后允许重新风控入场。

权限关系：

- 自动推理关闭：不产生新的 AI 持仓判断；
- 交易发送关闭：可以展示和影子评估，但不得取消、平仓或开仓；
- 持仓管理未授权：即使交易发送开启，也不得自动平仓；
- 全局“禁止新开仓”应阻止反手入场，但不应错误套用开仓规则阻止已授权的风险降低型退出；
- 全局“禁止全部交易操作”则同时阻止 AI 撤单和平仓，MT5 已设置的止损仍独立有效；
- 管理员应急平仓属于独立人工权限，不得由模型自动触发。

退出使用独立安全检查，不复用最低盈亏比、入场价格偏差、最大新仓手数等开仓规则。反手新仓必须重新通过全部现有开仓风控。退出遇到极端点差或报价异常时短暂重试并保留原 MT5 止损保护；不得无限重试或改成无保护等待。

## 12. 前端与中文审计

推理结果仅在存在相关持仓或挂单时展示“挂单处理”和“持仓处理”：

- 当前实际持仓、实际止盈止损及原始建议；
- 继续持有、退出或退出后反手；
- 原交易论点、失效条件和已确认依据；
- 当前阶段、等待条件和下一步；
- 未执行、被拒绝、执行失败或状态未知的具体中文原因。

风控与审计至少区分：持仓对齐跳过、证据不足、持仓归属不明、挂单取消失败、退出风控拒绝、平仓发送失败、平仓状态未知、部分平仓、退出成功但新仓风控拒绝、翻转完成。

内部规则码可保存用于诊断，但不得直接显示给用户。执行记录必须关联原信号、交付、ticket、快照、模型结论、证据验证、MT5 原始返回和最终状态。

## 13. 复盘、记忆与结果归因

AI 退出不能生成一条虚假的普通开仓信号，否则会导致日复盘重复、交易笔数异常和记忆归因错误。退出结果应归属于原始持仓和原始策略，通过管理任务记录退出原因。

- 平台策略的退出经验进入平台策略复盘，不注入订阅用户个人记忆；
- 私有策略的退出经验只归属于该用户策略；
- 复盘比较原止损结果、假设继续持有结果和实际 AI 退出结果；
- 只有已确认且通过复盘的结论才能进入对应策略记忆；
- 影子任务与真实任务必须明确区分，不得混入真实收益统计。

## 14. 性能与行情完整性

- 复用自动推理现有行情快照，不启动第二套智能平仓模型循环；
- 仅在策略存在持仓或挂单时附加组合上下文；
- 同一根已收盘决策周期 K 线只评估一次；
- 平台策略保持一次共享推理，不按订阅用户重复调用模型；
- 执行前只读取必要的实时持仓、挂单和报价；
- K 线缓存必须检查末端时间、连续性、市场开闭状态和 MT5 时区；
- 缓存断档或市场时钟不可信时，只展示建议，不执行持仓动作。

## 15. 分阶段实施

### 阶段一：数据与协议

- 拆分实际止盈止损和原始建议；
- 修复活跃 ticket 精确归属及挂单成交关联；
- 冻结结构化原交易论点；
- 引入统一模型输出和严格校验；
- 保持旧智能平仓总开关关闭。

### 阶段二：影子评估与界面

- 自动推理生成挂单和持仓计划；
- 建立持久化管理任务、事件和中文审计；
- 展示建议与验证阶段，不发送交易命令；
- 收集误退出、撤回、震荡反复和数据完整率。

### 阶段三：自动退出

- 实现数据库互斥锁、归属闸门、退出专用检查和 MT5 对账；
- 首期只支持套期保值账户中归属明确的完整持仓；
- 只平仓，不反手；
- 小范围按策略、观摩源和用户灰度。

### 阶段四：退出后反手

- 先取消冲突挂单并确认，再平仓并确认；
- 重新进行完整开仓风控；
- 首期反手最高为试探仓；
- 设置冷静期和次数上限；
- 稳定后再评估是否开放轻仓。

### 阶段五：高级能力再评估

根据真实数据决定是否支持净持仓账户、部分减仓、移动止损、动态止盈和完整智能平仓。不得与前四阶段同时上线。

## 16. 影子评估指标

按策略、品种、周期和行情状态统计：

- 候选退出数、确认数、撤回数和实际可执行数；
- 假设退出后先到原止盈还是先到原止损；
- 避免的进一步亏损和错失的后续盈利；
- 自动退出与原止损退出的平均 R 倍数差异；
- 若干根 K 线内重新回到原方向的误退出率；
- 多空反复、冷静期拦截和每日上限命中次数；
- 数据缺失、归属不明、部分执行和 MT5 状态未知比例；
- 平仓滑点、耗时、失败率及反手后结果。

没有足够真实样本时不能仅凭少量成功案例开放自动执行。

## 17. 最终风险审查

以下异常在实施中最容易被遗漏，均应设为发布阻断项：

| 风险 | 可能后果 | 强制措施 |
| --- | --- | --- |
| 旧智能平仓与新链路并存 | 同一持仓被重复处理 | 旧调度器继续硬关闭，新能力使用独立模块和任务表 |
| 两个策略同时操作同一品种 | 平仓、撤单、反手相互覆盖 | 按账户身份与原始 broker symbol 加数据库锁 |
| 参考组合与用户实际组合不同 | 关闭错误持仓或错误反手 | 模型只给通用意图，用户执行前重新读取和适配 |
| 最近 200 条交付漏掉长持仓 | 模型看不到真实策略仓 | 按当前活跃 ticket 精确查询 |
| 挂单 ticket 与持仓 ticket 不同 | 归属断裂 | 建立 order、deal、position ticket 对账关联 |
| 实际 SL/TP 与原建议混合 | 模型误认为已有保护 | 分字段保存，缺失必须为 `null` |
| 未收盘 K 线或缓存断档 | 震荡中异常退出 | 已收盘验证、连续性与新鲜度检查 |
| 用户在确认期间手动操作 | 使用过期快照平错仓 | 执行前重新读取，状态变化即取消候选 |
| 平仓部分成功 | 提前反手造成双向风险 | 全部目标 ticket 确认消失后才允许反手 |
| 服务重启或 Bridge 超时 | 重复平仓或重复开仓 | 持久化状态机、幂等键、先对账后恢复 |
| 净持仓混合人工成交 | 误关人工仓位 | 首期禁用，无法证明纯归属即人工复核 |
| 去后缀品种误匹配 | 操作不同合约 | 执行归属必须匹配原始 broker symbol |
| 开仓风控用于退出 | 风险已失效却无法减仓 | 退出使用独立安全检查，反手才走开仓风控 |
| AI 退出写成普通信号 | 复盘重复、记忆污染 | 使用独立管理任务并归因原始持仓 |
| 模型或策略在两次确认间变化 | 拼接不同规则得出假确认 | 策略修订变化时清零确认计数 |
| 交易开关语义不清 | 用户关闭交易后仍被平仓 | 数据权限、持仓管理权限和交易发送权限分别校验 |

## 18. 必测验收场景

- 接近止损但原逻辑未失效时继续持有；
- 影线刺破后收回、未收盘突破和单指标反转均不退出；
- 硬失效和软反转确认规则正确区分；
- 同一根 K 线重复推理不累计确认；
- `hold + exit` 能退出旧仓但不创建新仓；
- `reverse` 必须先撤冲突挂单、再平仓、确认后重新风控；
- 人工仓、其他策略仓、归属不明仓和混合净持仓不被处理；
- 多策略并发、重复消息、服务重启和 Bridge 重连不会重复执行；
- 用户手动平仓、修改 SL/TP 或切换账户后候选自动失效；
- 平仓失败、超时、部分成功和状态未知时绝不反手；
- 平台共享信号在不同用户组合下得到正确个性化结果；
- 影子记录不计入真实收益和真实交易数；
- 所有前端状态、拒绝原因和审计说明使用自然中文。

## 19. 最终实施裁决

本方案能够解决 `opposite_position_exists` 无条件阻断趋势翻转的问题，但实现重点不是删除该保护，而是把它改为安全分流：

```text
反向持仓存在
  → 归属不清：保持并提示
  → 原逻辑未失效：保持并跳过新仓
  → 原逻辑确认失效：只退出
  → 确认趋势翻转且用户授权：退出确认后再独立风控反手
```

推荐发布顺序严格保持为：数据修正 → 影子评估 → 自动退出 → 自动反手。任何阶段都不得依赖提示词直接操作持仓，也不得为了让反向信号成交而绕过归属、对账和风控。
