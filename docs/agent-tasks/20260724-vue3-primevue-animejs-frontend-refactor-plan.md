# AURUM 全前端 Vue 3 重构方案

日期：2026-07-24

状态：已确认方向，供后续分阶段实施

适用范围：主站、AI 交易实验室、统一账户中心、统一管理后台、主站登录注册、AI 登录注册

## 1. 方案摘要

本方案将当前以大型原生 JavaScript、`innerHTML`、手动事件绑定和全局状态为主的前端，渐进迁移到 Vue 3 组件化架构。在迁移期间保留现有 Express 后端、API 合同、数据库、业务规则、路由入口和旧前端，按应用入口和路由逐步切换，不采用停站式或一次性替换。

确定采用的核心技术栈：

- Vue 3：页面与组件框架；
- Vite：开发、构建、按路由拆包和资源指纹；
- TypeScript：组件、Store、API 和业务数据类型；
- Vue Router：各独立前端内部路由；
- Pinia：会话投影、导航、界面偏好和跨组件客户端状态；
- PrimeVue：表格、表单、弹窗、抽屉、菜单、提示、分页等成熟组件；
- AURUM PrimeVue 自定义主题：映射现有 `DESIGN.md` 令牌，不使用默认 Material 风格；
- Anime.js 4：仅承担复杂状态流、局部布局变化和关键反馈动效；
- Lightweight Charts：继续承担行情与 K 线；
- Quill：第一阶段继续承担富文本编辑，避免同时更换编辑器；
- Lucide：继续作为统一图标体系；
- Vitest、Vue Test Utils、Testing Library、Playwright：单元、组件、集成和端到端测试。

不选择 Vuetify 作为主组件库。原因是 Vuetify 的 Material 视觉约束较强，完整保持 AURUM 深色交易工作台风格需要较多覆盖；PrimeVue 的设计令牌和无样式能力更适合现有品牌体系。

## 2. 重构目标

### 2.1 核心目标

1. 保留全部现有业务功能、权限、接口行为和安全边界。
2. 将页面拆分为可测试、可复用、生命周期明确的组件和领域模块。
3. 统一主站、AI、账户中心和后台的基础组件与设计令牌，但不共享页面组件或路由状态。
4. 清楚区分 AI 建议、服务器风控裁决和 MT5 实际结果。
5. 减少整块 DOM 重绘、重复事件绑定、全局状态和 CSS 覆盖。
6. 通过路由懒加载、Tree-shaking、虚拟列表和边界化响应式状态改善性能。
7. 达到 WCAG 2.1 AA，补齐键盘、焦点、非颜色状态表达和减少动态效果。
8. 建立可灰度、可观测、可回滚的上线机制。

### 2.2 非目标

本轮不做以下工作：

- 不重写 Express 后端或数据库；
- 不修改 AI 推理合同、风控计算和 MT5 执行规则；
- 不修改固定 TRC-20 共享地址、金额差和时间匹配逻辑；
- 不把主站、AI、账户中心和后台合并成单个巨型 SPA；
- 不同时替换 Lightweight Charts、Quill 和所有第三方工具；
- 不追求炫技式动效、游戏化霓虹或全站页面入场动画；
- 不为了组件复用破坏不同应用的权限、会话和路由隔离；
- 不在缺少真实基准测试时承诺 Vue 会自动提升性能。

## 3. 当前基线与主要问题

截至方案制定时，当前前端大致规模如下：

| 区域 | 主要文件 | 规模与特征 |
|---|---|---|
| 主站 | `public/src/main.js`、`style.css` | 约 7.4k 行 JS、7.8k 行 CSS，大量模板字符串和手动事件 |
| AI 实验室 | `public/ai/app.js`、`index.html`、`styles.css` | 约 7.2k 行 JS、942 行 HTML、8.1k 行主 CSS，实时轮询与复杂全局状态密集 |
| 管理后台 | `public/admin/app.js`、`styles.css` | 约 1.5k 行 JS、2k 行以上 CSS，大量长模板、表格、表单和查询 |

主要结构问题：

- 页面状态、DOM 查询、接口调用和渲染函数集中在大型文件；
- `innerHTML` 更新后需要重新绑定事件；
- 定时器、轮询、WebSocket 和弹窗清理依赖人工维护；
- 相同控件在不同应用中有不同实现和状态表现；
- CSS 体量大，存在大量 `transition: all`、重复 keyframes 和覆盖规则；
- 路由级代码拆分不足，功能常随入口整体加载；
- 业务状态缺少严格类型，回归依赖整页测试；
- 基础组件的 loading、disabled、error、focus 和 reduced-motion 不完全一致。

可保留的基础：

- 现有后端 API 可以继续使用；
- `public/src/lib/api.js` 已集中封装主要 fetch 和认证头；
- `/shared/session.js` 已承担同源会话兼容；
- `PRODUCT.md`、`DESIGN.md` 和 `.impeccable/design.json` 已定义产品与视觉边界；
- Lightweight Charts、Quill、Lucide 可以在第一阶段复用；
- 现有 Vitest 合同测试可作为迁移防线。

## 4. 产品与设计方向

### 4.1 产品场景

用户通常在桌面端长时间观察市场，需要快速理解 AI 看到了什么、建议做什么、风控如何裁决以及 MT5 实际做了什么。界面应专业、可信、克制，允许较高信息密度，但每个页面只能有一个首要结论。

### 4.2 视觉策略

采用 Restrained 克制策略：

- 深夜蓝黑作为工作背景；
- 金色只用于当前任务、关键操作和焦点；
- 红、绿、橙、蓝只表达明确语义；
- 静态层级优先使用背景和边界，不批量使用阴影；
- 常规圆角 6、10、14px，禁止卡片过度圆润；
- 中文自然文案优先，不直接暴露内部英文错误和规则码；
- 同一应用内保持一致按钮、输入框、表格、弹窗和空状态。

### 4.3 信息层级

AI 交易相关页面固定遵循：

1. 当前结论；
2. 是否执行；
3. 风控结论；
4. MT5 实际状态；
5. 市场证据与技术细节；
6. 审计与内部字段。

技术详情使用渐进披露，不得让指标和内部字段淹没当前结论。

## 5. 应用边界与路由保持

重构后继续保持多个独立前端：

| 应用 | 固定入口 | 职责 |
|---|---|---|
| 主站 | `/` | 课程、社区、内容、会员入口和普通导航 |
| 主站认证 | `/auth/` | 主站登录与注册 |
| AI 实验室 | `/ai/` | AI 分析、交易、风控、策略、复盘和个人配置 |
| AI 认证 | `/ai/auth/` | AI 登录与注册 |
| 账户中心 | `/account/` | 账号、会员、账单、绑定和统一个人设置 |
| 管理后台 | `/admin/` | 用户、内容、商业运营、平台 AI、风控、审计和系统配置 |

边界规则：

- 各应用不得互相导入页面组件或路由 Store；
- 允许共享设计令牌、基础 UI 组件、API 类型、会话和通用工具；
- 主站只使用普通链接进入 `/ai/`；
- 主站和 AI 分别通过嵌入模式打开 `/account/?embed=main` 和 `/account/?embed=ai`；
- 主站嵌入账户中心时实时同步主站深浅主题；
- 任一应用退出必须通过统一会话层清除兼容令牌并广播；
- AI 退出固定返回 `/ai/auth/`；
- `/api` 与 `/aurum-api` 保持兼容。

## 6. 推荐工程结构

建议新增独立 `frontend/` 工作区，使用 npm workspaces 与现有 npm 工具链保持一致：

```text
frontend/
  apps/
    main/
      src/
    main-auth/
      src/
    ai/
      src/
    ai-auth/
      src/
    account/
      src/
    admin/
      src/
  packages/
    api-client/
    contracts/
    session/
    ui/
    theme/
    motion/
    testing/
  vite/
    shared-config.ts
```

共享包职责：

| 包 | 职责 | 禁止内容 |
|---|---|---|
| `api-client` | fetch、错误归一化、请求取消、上传下载 | 页面状态、路由跳转 |
| `contracts` | API DTO、枚举、展示模型类型 | 服务端密钥、数据库模型直出 |
| `session` | Token 兼容、Cookie、跨应用退出广播 | 页面权限判断和业务组件 |
| `ui` | 按钮、输入、表格外壳、状态、空状态 | 主站或 AI 专属页面 |
| `theme` | AURUM 令牌、PrimeVue preset、主题桥 | 路由和接口调用 |
| `motion` | 动效令牌、Anime.js composable | 无限装饰动画和业务状态 |
| `testing` | Mock、fixture、render helper | 生产运行逻辑 |

每个应用内部建议使用领域结构：

```text
src/
  app/
  router/
  stores/
  features/
  pages/
  components/
  composables/
  services/
  styles/
  main.ts
```

不得按 `components/`、`utils/` 无限堆放所有代码；复杂业务按 feature 划分，例如 `signals`、`risk-center`、`membership`、`payments`、`courses`。

## 7. 状态与数据架构

### 7.1 Pinia 使用边界

Pinia 仅保存确实需要跨组件或跨路由的客户端状态：

- 当前用户的前端投影；
- 当前应用授权状态；
- 导航与界面偏好；
- 当前选中频道、品种和策略；
- 需要跨路由保留的筛选条件；
- WebSocket 连接摘要。

不得把所有 API 响应复制到一个巨型 Store。页面级数据优先由 feature service/composable 管理，并在路由卸载时取消请求和轮询。

### 7.2 服务端状态

- 为每类请求定义稳定 query key；
- 支持 `AbortController`；
- 轮询只在页面可见且功能处于活动状态时运行；
- 同一资源只保留一个轮询所有者；
- WebSocket 数据通过单一适配器归一化；
- 支付、交易和权限变更不得使用会造成事实误导的乐观更新；
- 用户生成 HTML 继续走服务端清洗，前端默认禁止 `v-html`。

### 7.3 类型边界

- API 原始 DTO 与页面展示模型分离；
- 所有金额、手数、时间和状态枚举显式类型化；
- 内部错误码保持稳定，在展示层统一映射为中文；
- `unknown` 响应先校验再进入 Store；
- 不将数据库字段名直接扩散到组件层。

## 8. PrimeVue 使用方案

### 8.1 使用范围

PrimeVue 优先承担：

- DataTable、VirtualScroller、Paginator；
- InputText、InputNumber、Select、MultiSelect、DatePicker；
- Dialog、Drawer、Popover、Tooltip；
- Tabs、Accordion、Tree、Menu；
- Toast、Message、ConfirmDialog；
- Skeleton、ProgressBar、Tag、Badge；
- FileUpload 和基础表单反馈。

### 8.2 主题策略

- 从 Aura 等中性 preset 派生 AURUM preset；
- 将 `DESIGN.md` 的 primitive、semantic、component 令牌映射到 PrimeVue；
- 深色为 AI、账户中心和后台主工作主题；
- 主站支持现有深浅主题；
- 不通过大量 `:deep()` 和高优先级选择器强行覆盖；
- 组件局部例外优先使用 PrimeVue design token 或 Pass Through API；
- 只有品牌要求超出 styled mode 时，才对特定组件采用 unstyled 模式。

### 8.3 导入和包体

- 按组件导入，不全量注册全部 PrimeVue 组件；
- 图标、编辑器和图表独立 chunk；
- 后台组件不得进入主站初始包；
- AI 复盘、模型配置和复杂图表按路由懒加载；
- 使用 bundle analyzer 检查每次依赖变化。

## 9. Anime.js 动效方案

### 9.1 定位

Anime.js 不替代 PrimeVue，也不负责普通按钮、输入框和 Toggle。其职责是表达复杂状态关系、局部布局变化和关键反馈。预计只有 10%～20% 的交互需要 Anime.js，其余继续使用 CSS Transition 或 PrimeVue 内置过渡。

### 9.2 高价值场景

1. AI 推理阶段：读取行情 → 模型分析 → 建议 → 风控 → MT5 执行；
2. AI 建议、风控调整和实际订单之间的视觉接续；
3. 新信号、新订单和复盘结果的局部进入或状态变化；
4. 风控详情、证据面板和列表重排；
5. 支付订单创建、链上等待、确认和会员激活的真实状态切换；
6. 账户中心和后台的复杂布局展开。

### 9.3 禁止场景

- 不给所有卡片播放入场动画；
- 不为每次页面加载编排长序列；
- 不持续动画 K 线、实时价格、盈亏或手数；
- 不使用字符乱序、文字拆分和随机跳动；
- 不使用 bounce、elastic 或游戏化粒子；
- 不使用动画暗示支付已确认、订单已成交或风控已通过；
- 不在大面积面板上持续运行 blur、filter 或 glow；
- 不阻塞用户交互等待动画结束。

### 9.4 Vue 集成

在 `packages/motion` 中统一封装：

```ts
useAnimeScope(root, setup)
useMotionPreference()
useStateTransition()
useLayoutTransition()
```

`useAnimeScope()` 必须：

- 在 `onMounted` 后创建 `createScope()`；
- 将 root 限定到当前组件；
- 在 `onBeforeUnmount` 调用 `scope.revert()`；
- 监听 `prefers-reduced-motion`；
- 不在 SSR 或 DOM 未就绪时访问元素；
- 避免同一元素同时被 PrimeVue transition 和 Anime.js 控制。

普通 transform/opacity 优先导入 `animejs/waapi`。只有需要编排时才懒加载 timeline，只有布局关系变化时才加载 layout。

### 9.5 动效令牌

```ts
export const motionTokens = {
  instant: 100,
  fast: 140,
  standard: 180,
  panel: 240,
  layout: 320,
  easeOut: 'out(4)',
  easeStrong: 'out(5)',
}
```

规则：

- 普通反馈 100～150ms；
- 状态切换 150～220ms；
- 面板和抽屉 220～300ms；
- 布局重排不超过 350ms；
- 退出约为进入时长的 75%；
- 列表 stagger 总时长不超过 400ms，并限制参与条目数量；
- reduced motion 下取消位移、缩放和连续脉冲，仅保留瞬时切换或极短淡入。

## 10. 关键页面迁移策略

### 10.1 管理后台

作为第一个完整试点，原因是表格、表单、筛选和弹窗最能验证 PrimeVue，同时不会影响公开内容 SEO。

迁移顺序：

1. 后台壳、导航和权限；
2. 用户管理；
3. 内容和课程；
4. 商业运营与会员；
5. 平台模型与策略；
6. 风控、审计和系统配置；
7. 观摩频道与 Bridge 运维。

必须保留最后一个管理员保护、观摩源账号锁定、桥接会话撤销和所有审计行为。

### 10.2 主站

迁移顺序：

1. 应用壳、导航和主题；
2. 首页和课程列表；
3. 文章、视频、测验、知识点和思维导图；
4. 社区、帖子、回复和图片；
5. 个人入口和通知；
6. 会员入口和账单展示。

公开内容若需要搜索引擎抓取，应保留服务端可见 HTML 或单独使用预渲染；不得简单把全部公开内容改成空壳纯 SPA。

### 10.3 账户中心与认证

账户中心必须作为独立应用：

- 兼容完整页面和 main/ai 嵌入模式；
- 复用统一会话；
- 支持主站主题同步；
- 保留邮箱、手机、密码、会员、账单和通知；
- 支付状态必须来自服务端事实；
- 登录、注册、验证码和退出行为保持原合同。

认证和支付安排在主站常规页面稳定后迁移，并设置独立回归门槛。

### 10.4 AI 交易实验室

按照用户任务迁移：

1. AI 分析师：行情、信号、推理详情；
2. AI 交易员：订单、持仓和执行状态；
3. AI 风控师：规则、裁决和账户风险；
4. AI 策略师：策略、模型和个人配置；
5. AI 复盘师：复盘、经验和记忆；
6. 观摩频道和来源状态。

`signals` 仅保留兼容跳转，不恢复为独立重复页面。共享信号、用户账户状态和实际执行必须在类型、Store 和组件层明确隔离。

## 11. 实施阶段与工期

以下为基于当前规模的工程估算，必须在基础阶段完成真实基准后重新校准。

| 阶段 | 主要交付物 | 预计时间 |
|---|---|---:|
| 0. 基线与迁移护栏 | 路由清单、截图、性能基线、功能矩阵、开关和回滚设计 | 2～3 天 |
| 1. 工程基础 | Vue/Vite/TS、workspace、Router、Pinia、API、Session、CI | 3～5 天 |
| 2. 设计系统与后台试点 | AURUM preset、基础组件、后台首批页面 | 6～9 天 |
| 3. 主站非关键页面 | 首页、课程、内容、社区、主题 | 6～9 天 |
| 4. 账户与认证 | account、auth、会话同步、通知 | 4～6 天 |
| 5. AI 实验室 | 五个任务域、图表、实时状态、策略与风控 | 10～15 天 |
| 6. Anime.js 与 UI 完善 | 状态流、布局变化、动效清理、reduced motion | 4～7 天 |

## 12. 新旧并行与切换

### 12.1 切换原则

- 旧前端在对应新应用完成验收前继续运行；
- 每个应用拥有独立 `legacy | vue` 服务开关；
- 必要时细化为 route-level allowlist；
- 新旧版本使用同一后端 API，不双写业务数据；
- 线上错误率、支付状态和交易执行异常可触发立即回退；
- 回退只切换静态入口，不回滚已经成功产生的业务事实。

### 12.2 构建与发布

- Vue 构建产物不覆盖旧源文件；
- 输出到版本化目录并生成 manifest；
- Express 根据配置选择对应入口；
- 静态资源使用内容 hash 和长期缓存；
- HTML 不使用长期缓存；
- 发布前验证 chunk 完整性和 source map 策略；
- 不提交构建产物，除非后续部署体系明确要求。

### 12.3 灰度顺序

## 14. 性能预算

阶段 0 必须记录当前真实基线，后续验收采用相对基线和绝对上限双重判断。

目标：

- 生产环境启用 Tree-shaking、压缩和路由懒加载；
- 每个入口首屏 JS 相比自身旧版传输体积至少不增加，目标降低 20%～30%；
- 图表、编辑器、Anime timeline/layout 和后台专属组件独立加载；
- LCP 不高于 2.5s；
- INP 不高于 200ms；
- CLS 不高于 0.1；
- 关键交互主线程长任务不超过 50ms；
- 列表超过约 200 条时评估虚拟滚动；
- 动画目标 60 FPS，低性能设备自动降级；
- `will-change` 只在正在动画的局部元素短期使用；
- 不对大型深层对象默认启用全量深响应式。

性能改善必须通过构建报告、浏览器 Performance、Lighthouse/WebPageTest 和真实路由测试确认，禁止只以“使用 Vue”作为完成依据。

## 15. 安全与业务一致性

- 不新增浏览器端密钥；
- 会话继续使用统一兼容层；
- 不将 Token 写入 URL；
- 所有用户生成 HTML 必须经过清洗；
- 文件上传保持服务端类型、大小和权限校验；
- 前端权限只用于展示，服务器仍是最终授权方；
- 支付、风控、MT5、会员和管理员操作不做事实型乐观更新；
- 支付页面不得从前端推断已付款；
- AI 页面不得把建议展示成已执行；
- 内部错误码不得直接暴露给普通用户；
- CSP、CSRF、同源和 iframe 嵌入策略在阶段 1 明确测试。

## 16. 风险与缓解

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 一次性重写导致长期不可用 | 高 | 按应用和路由渐进切换，旧版保留 |
| 新旧会话不一致 | 高 | 统一 session 包、跨应用 E2E 和退出广播 |
| 支付状态误展示 | 高 | 服务端事实唯一来源，真实低金额付款验收 |
| AI 建议与执行状态混淆 | 高 | 三层展示模型和强类型状态机 |
| 重复轮询和 WebSocket | 高 | 单一所有者、可见性暂停和卸载清理 |
| PrimeVue 默认风格稀释品牌 | 中 | AURUM preset、令牌审查和视觉回归 |
| 组件库增大包体 | 中 | 按需导入、懒加载和 bundle budget |
| Anime.js 造成疲劳或耗电 | 中 | WAAPI 优先、禁止无限装饰、reduced motion |
| CSS 新旧冲突 | 中 | 应用根节点隔离、CSS layer、分阶段删除旧样式 |
| 移动端功能退化 | 中 | 固定视口矩阵和触屏 E2E |
| 重构期间旧功能继续变化 | 高 | 功能冻结窗口、变更日志和双实现同步清单 |

## 20. 最终决策

后续全面重构按以下方案执行：

> Vue 3 + Vite + TypeScript + Vue Router + Pinia + PrimeVue 自定义 AURUM 主题，保留 Lightweight Charts、Quill 和 Lucide；Anime.js 作为有限的复杂状态动效层。使用多个独立前端、共享基础包、新旧并行、逐入口灰度和可即时回滚的迁移方式。后端 API、TRC-20 支付、AI 风控与 MT5 执行合同保持不变。

本文件作为后续重构任务拆分、实施和验收的上位方案。具体编码前应将每个阶段拆成独立任务文件，并以本方案的边界、测试门槛和完成定义为准。
