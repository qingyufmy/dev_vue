# AURUM 前后端规范化重构方案

初版日期：2026-07-24

审查修订：2026-08-18

状态：完成代码静态对照与两轮方案复审，可作为后续分阶段实施的上位方案

适用范围：主站、AI 交易实验室、统一管理后台、统一账户中心、三套独立登录入口、浏览器 API 与实时通道

## 1. 审查结论

原方案的基础技术方向仍然成立：继续采用 Vue 3、Vite、TypeScript、PrimeVue、Pinia，并将 Anime.js 限制在少量复杂状态动效中；采用新旧并行、按入口灰度和可即时回滚的迁移方式。

但原方案不能直接实施，必须先纳入本次审查发现的四项实质调整：

1. 主站、AI 交易实验室、管理后台必须是三套独立构建、独立路由、独立页面壳和独立登录体验；管理后台新增 `/admin/auth/`，不再借用主站登录页。
2. 账户体系、会话、订阅、支付和通知仍然统一；“独立登录页面”不等于创建三套用户表或三套认证服务。
3. 当前 AI 浏览器端把 WebSocket 同时用于实时推送、精确查询和交易命令，必须拆分为“实时事件走 WebSocket，精确快照、分页查询和业务命令走 HTTP API”。
4. 重构范围从单纯前端迁移扩大为前端组件化、后端接口规范化、浏览器实时协议拆分和带宽治理，原 30～45 个工作日估算已不适用。

审查状态为：**方案审查完成，运行时性能和线上带宽基线仍待阶段 0 实测**。本次没有通过浏览器 Network、真实生产流量、真实 MySQL、真实链上支付或真实 MT5 交易证明性能收益，因此所有绝对性能目标都必须在阶段 0 校准。

### 2.4 当前数据传输现状

HTTP 层已有较多独立路由文件，但统一挂载在无版本的 `/api` 下；AI 路由还同时挂载到 `/api` 与 `/aurum-api`。证据位于 `server/index.js:228-252`。

浏览器实时与查询当前共用 `/aurum-api/bridge/ws`：

- AI 浏览器连接 `type=browser`，见 `public/ai/app.js:3592-3594`；
- 管理后台连接 `type=admin`，见 `public/admin/app.js:321-326`；
- Bridge 终端和浏览器共享 `server/bridge-ws.js:829-884` 的升级入口；
- Bridge V3 使用独立 `/aurum-api/bridge/v3/ws`，见 `server/bridge-v3/gateway.js:22`。

AI 前端在 `public/ai/app.js:2601` 明确把 WebSocket 称为“所有 MT5/AI 数据的主通道”，并用 `wsApi()` 请求以下非实时或大数据能力：

- `account`、`positions`、`pending_list`；
- `rates`、`history`、`history_chart_data`、`export_history`；
- `signals`、`signal_detail`、`audit_logs`；
- `analyze`、`compare`、`execute`、`open`、`close`、`cancel_pending`；
- 健康检查、自动运行状态、品种目录和历史范围偏好。

这与本次确认的目标不一致，也是后续带宽、超时、重连、请求取消和精确缓存难以统一治理的核心原因。

## 3. 目标总体架构

目标不是一个巨型 SPA，而是：

> 三套独立业务前端、三套独立登录页面、一个共享账户中心、一个统一账号体系、一个统一管理后台、一套版本化 HTTP API、一个浏览器实时事件通道，以及独立的 Bridge 终端通道。

```text
主站 /                 ─┐
主站登录 /auth/         │
AI /ai/                 ├─ 浏览器 API /api/v1/* ─ 领域服务 ─ 数据库/外部服务
AI 登录 /ai/auth/       │
后台 /admin/            ├─ 浏览器实时 /api/v1/realtime/ws ─ 事件投影
后台登录 /admin/auth/   │
账户中心 /account/      ┘

Bridge 2.x /aurum-api/bridge/ws    ─┐
Bridge 3.x /aurum-api/bridge/v3/ws  ├─ Bridge 网关 ─ MT4/MT5
                                    ┘
```

### 3.1 “独立页面”的定义

主站、AI 和后台分别具备：

- 独立 Vite 入口和构建产物；
- 独立 Vue Router、页面壳、导航和错误边界；
- 独立登录页面和登录后返回规则；
- 独立灰度开关、性能预算和回滚开关；
- 独立主题组合和页面级 Store；
- 任一应用构建失败时不阻断其他应用发布。

独立不代表复制：三套应用继续共享接口合同、认证客户端、基础组件、设计令牌、实时客户端和测试工具。

### 3.2 固定入口与职责

| 应用 | 固定入口 | 职责 | 登录后默认目标 |
|---|---|---|---|
| 主站 | `/` | 内容、课程、社区、公开工具、会员入口 | 原 `next` 或 `/` |
| 主站登录 | `/auth/` | 普通用户登录、注册、找回密码 | 安全校验后的主站路径 |
| AI 实验室 | `/ai/` | 用户 AI 分析、交易、风控、策略和复盘 | `/ai/` |
| AI 登录 | `/ai/auth/` | 普通用户登录、注册、找回密码 | 安全校验后的 `/ai/` 内路径 |
| 管理后台 | `/admin/` | 唯一的平台管理界面 | `/admin/` |
| 后台登录 | `/admin/auth/` | 仅管理员登录，不提供注册 | 安全校验后的 `/admin/` 内路径 |
| 账户中心 | `/account/` | 唯一的资料、安全、订阅、支付、通知和邀请中心 | 来源应用或账户概览 |

管理后台登录必须在服务端认证后再次校验 `role=admin`。前端页面隐藏、独立 URL 或不同视觉都不能代替服务端权限校验。

### 3.3 会话边界

- 三套登录页调用同一认证服务、同一用户表和同一会话吊销机制；
- 任一前端退出后，主站、AI、后台和账户中心同时失效；
- 后台登录成功但角色不是管理员时，返回明确中文提示，不进入后台；
- `next` 只能接受同源白名单路径，分别限制在对应应用前缀内；
- 账户中心继续支持 `/account/?embed=main` 和 `/account/?embed=ai`；
- 后台账户入口使用完整页面或后台内安全嵌入模式，但不得复制账户设置；
- 迁移期间保留现有 Bearer/Cookie 兼容，目标浏览器会话优先使用安全、HttpOnly、SameSite Cookie，并独立评估 CSRF；
- Bridge 刷新凭据、网页会话和 Bridge WebSocket ticket 继续分开，不能因为浏览器认证重构破坏 Bridge 授权。

## 4. 前端工程规范

### 4.1 技术栈

- Vue 3：组件和 Composition API；
- Vite：独立入口、按路由拆包、内容哈希和构建分析；
- TypeScript：前端代码和接口展示模型；
- Vue Router：各应用内部路由；
- Pinia：仅保存跨页面客户端状态；
- TanStack Vue Query：服务端状态、缓存、请求合并、失效和取消；
- PrimeVue：成熟交互组件；
- Zod：运行时响应与表单边界校验；
- Lightweight Charts：K 线和行情图表；
- Quill：第一阶段保留富文本编辑；
- Lucide：统一图标；
- Anime.js 4：少量复杂状态与布局动效；
- Vitest、Vue Test Utils、Testing Library、Playwright：测试体系。

Pinia 与 Vue Query 必须分工：Pinia 不缓存服务器列表和详情；Vue Query 不保存导航、主题、未提交草稿和本地 UI 状态。

### 4.3 模块独立规则

1. 每个 feature 只通过自己的 `index.ts` 暴露公共能力；禁止跨 feature 导入内部文件。
2. 页面只负责组合模块、路由参数和页面级错误边界，不直接拼接请求 URL。
3. 组件不直接访问 `localStorage`、Cookie、全局 WebSocket 或裸 `fetch`。
4. API 调用只能位于 feature 的 `api/` 或共享 `api-client`。
5. 实时订阅只能位于 feature composable 或 `realtime-client`，卸载时自动取消。
6. 领域规则不得藏在 PrimeVue 事件回调或模板表达式中。
7. 共享 `ui` 不依赖主站、AI、后台或账户中心的业务类型。
8. ESLint 使用 import boundary 规则阻止反向依赖和循环依赖。
9. 每个模块必须同时拥有加载、空数据、错误、无权限、断线和恢复状态。
10. 单文件组件超过约 400 行、composable 超过约 250 行时必须审查是否职责过多；这不是机械拆分阈值，但不得重新形成新的大文件。

### 4.4 组件策略

“能使用 Vue 组件就使用组件”落实为三层：

| 层级 | 来源 | 示例 | 复用范围 |
|---|---|---|---|
| 基础交互 | PrimeVue | Button、Input、Select、Dialog、DataTable、Tabs、Toast | 全应用 |
| AURUM 语义组件 | `packages/ui` | 状态标签、错误面板、空状态、金额、时间、确认流程 | 全应用 |
| 领域组件 | 各 feature | 信号结论、风控裁决、支付状态、策略编辑器 | 仅本领域或明确导出 |

不为单个普通 `<div>` 创建无意义包装组件，也不制作接受几十个 props 的“万能业务组件”。组件化目标是稳定职责、可测试和可替换，不是追求组件数量。

PrimeVue 使用规则：

- 按组件导入，不全量注册；
- 使用 AURUM preset 映射 `DESIGN.md`，不直接使用默认 Material 外观；
- 组件状态统一覆盖 default、hover、focus、active、disabled、loading 和 error；
- 通过 design token 和 Pass Through API 定制，避免大量 `:deep()`；
- 表格、编辑器、图表和后台专属组件按路由懒加载；
- 同一种操作在三套应用中保持相同交互语义，但允许布局不同。

### 4.5 前端可解决问题的边界

| 统一放在前端 | 必须留在后端 |
|---|---|
| 展示模型转换、中文文案、本地格式化 | 身份认证、权限与数据范围 |
| 表格本页排序、筛选和展开状态 | 跨页、全量或安全敏感查询 |
| 已获取数据的派生统计和图表映射 | 支付金额匹配、到账确认和会员激活 |
| 表单即时提示和草稿 | 最终校验、幂等、事务和持久化 |
| 请求合并、缓存、取消、防抖 | AI 推理合同、服务器风控和手数计算 |
| 组件状态、主题、导航和响应式布局 | 订单意图、MT4/MT5 命令与实际结果 |
| 图片预览、压缩前检查 | 文件类型、大小、病毒和权限校验 |
| 当前页面已有数据的导出 | 大数据集、审计和受控导出 |

禁止把安全、支付、会员、交易、风控或权限规则搬到前端来减少接口调用。前端可以减少重复请求，但不能成为业务事实来源。

## 5. 后端接口规范化

### 5.1 原则

后端不重写核心业务算法和数据库事实，而是逐模块把路由、输入校验、应用服务、领域规则、存储和事件发布分层。现有支付、AI、风控、Bridge 和 MT5 合同必须保持。

目标模块：

```text
server/
  modules/
    auth/
    accounts/
    content/
    community/
    commerce/
    notifications/
    ai-analysis/
    ai-trading/
    ai-risk/
    ai-strategy/
    ai-review/
    admin/
    bridge/
  platform/
    http/
    realtime/
    database/
    cache/
    observability/
```

每个模块内部按需包含：

```text
domain/         纯规则和状态机
application/    用例、事务边界和权限后的业务编排
infrastructure/ 数据库、Redis、外部服务和 Bridge 适配
http/           路由、参数、状态码和响应
realtime/       领域事件到浏览器事件的投影
schemas/        Zod 合同与 OpenAPI 描述
tests/          单元、合同和集成测试
```

不得为了目录整齐复制业务逻辑。迁移初期新路由调用现有已验证 service；确认新旧合同一致后，才把路由中的业务逐步下沉。


兼容规则：

- 现有 `/api/*` 与 `/aurum-api/*` 在旧前端退役前保留；
- 新 `/api/v1` 路由优先复用原 service，禁止双写数据库；
- `/api/v1` 必须在旧 `/api` 全局 `no-store` 兼容中间件之前挂载，避免新接口的 ETag 和资源级缓存策略被旧策略覆盖；
- `/api/ai/admin/*` 只作为兼容入口，新管理接口统一迁往 `/api/v1/admin/*`；
- Bridge 2.x 与 3.x WebSocket 路径不随浏览器 API 改名；
- 每个兼容端点记录调用量，连续稳定无调用且通过回滚窗口后才能删除。

### 5.3 请求与响应合同

成功响应：

```json
{
  "data": {},
  "meta": {
    "request_id": "req_...",
    "version": 12,
    "generated_at": "2026-08-18T08:00:00.000Z"
  }
}
```

失败响应：

```json
{
  "error": {
    "code": "strategy_version_conflict",
    "message": "策略已被更新，请刷新后重试",
    "fields": {},
    "retryable": false
  },
  "meta": {
    "request_id": "req_..."
  }
}
```

规范：

- 使用正确 HTTP 状态码，不再所有错误都返回 200；
- 错误码稳定，中文文案可演进；
- 所有输入使用 schema 校验，未知字段按接口策略拒绝或显式忽略；
- 列表统一游标分页；管理后台必要时保留页码并在适配层转换；
- 默认页大小 20～50，普通接口最大 100；大于上限必须使用导出任务；
- 金额、价格和手数在传输层使用十进制字符串，避免 JSON 浮点误差；
- UTC 时间使用 ISO 8601；终端服务器时间额外带 `timezone_offset_minutes`、校准状态和来源；
- 写操作返回更新后的资源版本或任务 ID；
- 危险或可重试写操作支持 `Idempotency-Key`；
- 并发编辑使用 `expected_version` 或 `If-Match`，冲突返回 409；
- 每个请求带 `request_id`，贯穿日志、审计和异步任务；
- Zod 合同生成 OpenAPI，前端客户端和类型从合同生成或校验，禁止手写多份不一致 DTO。

### 5.4 查询模型

为减少无用数据，不提供任意 `fields=*`。每个复杂资源定义明确的查询模型：

- `summary`：列表所需字段；
- `detail`：详情所需字段；
- `export`：后台异步导出；
- `snapshot`：账户、持仓、挂单等某一版本的精确状态。

前端不得为了显示一行列表请求完整详情。详情在用户展开或进入页面时按需加载。

### 5.5 缓存与敏感数据

- 公开、稳定内容可使用 `public` 缓存与 ETag；
- 登录用户的可缓存读取使用 `private, no-cache` 配合 ETag，允许浏览器条件请求但禁止共享代理缓存；
- 支付、权限、交易、风控、密钥配置和一次性凭据使用 `no-store`；
- 认证相关响应设置正确的 `Vary`，不得让不同用户共享缓存；
- 304 只能复用同一身份、同一资源版本和同一查询条件的本地响应；
- 旧兼容接口继续保留原缓存语义，不能为了新 API 调整而改变旧前端事实。

## 6. HTTP 与 WebSocket 分工

### 6.1 三条通道

| 通道 | 用途 | 权威性 |
|---|---|---|
| 浏览器 HTTP `/api/v1/*` | 精确快照、分页、详情、配置、命令和导出任务 | 浏览器业务数据的权威读取入口 |
| 浏览器 WebSocket `/api/v1/realtime/ws` | 行情、连接、任务进度、资源变化和通知唤醒 | 实时提示或短生命周期流，不代替持久化事实 |
| Bridge WebSocket | 终端发现、采集、命令、结果和 Bridge 协议 | MT4/MT5 与服务器专用传输 |

浏览器实时通道必须从 `/aurum-api/bridge/ws` 拆出，避免浏览器协议与 Bridge 协议继续耦合。Bridge 旧路径和 V3 路径保持兼容。

### 6.2 数据分类

| 数据/操作 | 目标通道 | 说明 |
|---|---|---|
| 实时报价、点差、市场状态 | WebSocket | 高频小消息，带品种、时间和序号 |
| Bridge 在线、账户切换、连接代次 | WebSocket 事件 + HTTP 快照 | 事件触发精确重新读取 |
| 账户、持仓、挂单当前状态 | HTTP snapshot + WebSocket changed | 初次和断线恢复取快照，变化事件按版本失效 |
| K 线历史 | HTTP | 分页/范围/缓存；当前 K 线可用 WS tick 增量更新 |
| 交易历史、图表历史、审计 | HTTP | 游标分页，禁止通过 WS 传大包 |
| 信号列表和详情 | HTTP | WebSocket 只发 `signal.created/updated` |
| 模型、策略、风控、复盘、记忆 | HTTP | 异步任务进度可走 WS |
| 分析、对比、开单、平仓、撤单 | HTTP 命令/任务 | 返回任务或订单意图 ID，进度走 WS，最终再 GET |
| 通知 | HTTP summary/list + WS created | WS 唤醒后按需刷新摘要 |
| 支付 | HTTP 创建/状态 | 可选 WS 到账事件，但页面最终必须 GET 状态确认 |
| 后台表格和配置 | HTTP | WS 只发资源变化与任务状态 |

### 6.3 浏览器实时协议

事件格式：

```json
{
  "type": "resource.changed",
  "event_id": "evt_...",
  "sequence": 10241,
  "occurred_at": "2026-08-18T08:00:00.000Z",
  "topic": "ai.positions",
  "resource_id": "account:server:login",
  "version": 37,
  "payload": {
    "reason": "position_closed"
  }
}
```

规则：

- 按用户、角色、账户和观摩频道授权订阅；
- 握手必须校验允许的同源 `Origin`，使用安全 Cookie 或一次性票据认证，禁止把长期 Token 放在 WebSocket URL；
- 服务端对每个订阅 topic 和每条客户端命令再次做权限校验，不能只信任连接建立时的前端声明；
- 每个事件有递增序号或可恢复游标；
- 重连携带最后确认序号；服务端无法补齐时返回 `resync_required`；
- 收到版本跳跃、未知事件或 `resync_required` 时，前端失效对应 query 并重新 GET；
- 事件 payload 只包含完成即时渲染或精确失效所需的最小字段；
- 不在 WebSocket 里返回交易历史、完整信号详情、审计列表或大对象；
- 前端按 topic 合并短时间内重复失效，避免一个成交触发多次相同 GET；
- 心跳、重连和订阅由共享客户端管理，业务模块不得各自创建 socket；
- 页面隐藏时保留必要连接，但暂停非关键视觉更新和后台刷新；
- WebSocket 断开不清空已确认数据，界面显示“实时连接中断”和数据时间；
- 所有交易与支付最终状态都通过权威 API 再确认。

### 6.4 交易命令规则

浏览器不再通过 `wsApi('open'|'close'|'execute')` 直接等待终端结果。目标流程：

1. 浏览器 `POST /api/v1/ai/trading/order-intents`；
2. 服务端完成权限、幂等、策略、风控、账户和合约机械校验；
3. 返回 `202 Accepted`、`intent_id` 和当前状态；
4. 服务端通过 Bridge 通道发送命令；
5. WebSocket 推送 `order-intent.updated`；
6. 浏览器 `GET /api/v1/ai/trading/order-intents/:id` 获取最终权威详情；
7. 超时或未知结果进入对账，不允许前端猜测成交。

该改造只改变浏览器传输合同，不改变 AI 只能给仓位档位、服务器精算手数、风控最终裁决和 Bridge 执行的现有规则。

## 7. 性能与带宽最小化

### 7.1 总原则

1. 不请求当前界面不需要的数据；
2. 不重复请求相同数据；
3. 不通过 WebSocket 发送可分页的大对象；
4. 不在前后端重复计算纯展示结果；
5. 不把服务端权威规则下放前端；
6. 首屏只加载当前应用壳和首个路由；
7. 先建立基线，再以 CI 预算阻止回退。

### 7.2 HTTP 带宽规则

- Vue Query 合并同一 query key 的并发请求；
- 合理设置 `staleTime`，路由往返不重复拉取未变化数据；
- GET 支持 ETag/`If-None-Match`，未变化返回 304；
- 静态资源使用内容 hash、长期 immutable 缓存；HTML 使用 no-cache；
- API 与文本资源启用 Brotli，兼容 gzip；
- 列表使用 summary 模型和游标分页；
- 详情按展开或路由进入时懒加载；
- 搜索输入防抖 250～400ms，并取消旧请求；
- 切换账户、频道、策略时取消旧上下文请求并验证响应上下文；
- 页面隐藏后停止非必要轮询；恢复时先检查版本再刷新；
- 导出使用异步任务和流式下载，不把大文件装进 JSON；
- 图片使用尺寸变体、WebP/AVIF、懒加载和正确宽高；
- 字体优先系统中文字体，只自托管实际使用的等宽字体与必要字重，禁止首屏下载整套未用字体。

### 7.3 前端计算规则

以下在前端基于已获取数据完成，不再请求后端：

- 当前页排序、筛选、分组和展开；
- 文案、状态标签、时间与数字格式化；
- 当前页合计和图表坐标转换；
- 表单草稿、即时格式校验和可操作状态；
- 主题、导航、列显示、密度和用户界面偏好；
- 已取得行情 tick 对当前 K 线的局部更新；
- 不涉及权限和业务事实的派生展示。

跨页聚合、大时间范围统计、资金、风控、手数、支付和交易结果仍由后端提供。

### 7.4 构建与运行预算

阶段 0 实测后可调整，调整必须记录原因。初始目标：

| 指标 | 目标 |
|---|---:|
| 主站首屏 JS | 不超过 200 KiB gzip |
| 认证页首屏 JS | 不超过 120 KiB gzip |
| 账户/后台首屏 JS | 不超过 250 KiB gzip |
| AI 首屏 JS | 不超过 300 KiB gzip，不含按需图表 |
| 单个懒加载业务 chunk | 原则上不超过 150 KiB gzip |
| 普通列表响应 | 原则上不超过 100 KiB 压缩前 |
| 非分页业务响应 | 超过 200 KiB 必须审查 |
| 普通 WS 事件 | 原则上不超过 4 KiB |
| 行情 tick | 原则上不超过 1 KiB |
| LCP | ≤ 2.5s |
| INP | ≤ 200ms |
| CLS | ≤ 0.1 |
| 主线程长任务 | 单次 ≤ 50ms |

还必须满足：

- PrimeVue、图表、Quill、Anime.js 不得全部进入所有应用首包；
- Anime timeline/layout 按需加载；
- DataTable 大于约 200 行时评估虚拟滚动，但优先服务端分页；
- 避免深层全量响应式对象，冻结不变合同数据；
- 不使用全局 `transition: all`；
- 动画只使用 transform、opacity 或已验证不会持续触发布局的属性；
- Service Worker 仅在明确缓存失效策略后引入，第一阶段不为了“看起来先进”添加离线缓存。

### 7.5 流量可观测性

每个 API 和 WS topic 记录：

- 请求/消息数量；
- 压缩前后字节；
- p50、p95、p99 延迟；
- 304 命中率；
- 客户端取消率；
- 重试和重复请求率；
- WS 重连、补发和 `resync_required` 次数；
- 各入口首屏资源字节和路由 chunk 字节。

不得记录 Token、模型密钥、支付私钥、用户密码、完整模型敏感输入或客户交易隐私。

## 8. 状态管理与一致性

### 8.1 Pinia

只保存：

- 当前会话投影与应用授权摘要；
- 主题、导航和界面偏好；
- 当前账户、观摩频道、品种和策略选择；
- 未提交且需要跨组件保留的草稿；
- WebSocket 连接摘要，不保存 socket 实例到业务 Store。

### 8.2 Vue Query

负责：

- 服务端列表、详情、快照和任务状态；
- query key、缓存、失效、请求合并和取消；
- 乐观更新回滚机制。

支付、权限、交易、会员、风控和 MT5 实际状态禁止事实型乐观更新。允许乐观更新的仅限无安全影响的本地偏好，并且服务端失败时必须回滚。

### 8.3 版本与上下文

- 账户数据 query key 必须包含 `terminal_instance_id + broker_server + login` 或服务端稳定账户 ID；
- 观摩数据 query key 必须包含频道和来源版本；
- 策略、记忆和复盘编辑使用版本号；
- 切换账户/频道后，旧响应即使晚到也不能写入新上下文；
- WS 事件版本低于当前缓存时忽略，高于一个版本时触发重新同步；
- 时间比较遵守项目既有 UTC 与终端服务器时间边界，前端不得以本机时区推断交易时间。

## 9. UI 与动效规范

### 9.1 设计系统

- 继续以 `PRODUCT.md`、`DESIGN.md` 和 `.impeccable/design.json` 为唯一设计来源；
- 深蓝黑工作面、稀缺金色焦点、中文结论优先；
- 同一个页面只有一个首要结论和一个主要操作；
- AI 建议、风控裁决、订单意图和 MT5 实际结果必须分别显示；
- 状态使用图标、中文文本和颜色共同表达；
- WCAG 2.1 AA、键盘操作、清晰焦点和 200% 缩放作为验收门槛；
- 卡片最多两层，避免表格、卡片和弹窗重复套壳；
- 产品页不使用编排式全页入场动画。

### 9.2 Anime.js

Anime.js 只用于约 10%～20% 的复杂交互：

- AI 推理阶段之间的短促状态接续；
- 局部布局重排和证据面板展开；
- 新信号、任务完成或风险状态变化的局部反馈；
- 不暗示事实完成的支付等待和订单状态过渡。

禁止：

- 所有卡片统一入场；
- 高频价格、K 线、盈亏和手数持续动画；
- bounce、elastic、粒子、字符乱序和无意义 glow；
- 动画暗示支付确认、风控通过或订单成交；
- 同一元素同时由 PrimeVue transition 和 Anime.js 控制。

使用 `createScope()` 并在组件卸载时 `revert()`；完整支持 `prefers-reduced-motion`。普通状态过渡 150～250ms，布局动效不超过 350ms。

## 10. 业务功能保护边界

### 10.1 支付与会员

- 继续只要求 TRC-20 USDT；
- 所有用户使用同一固定地址；
- 通过唯一金额差、订单创建时间和 USDT 支付时间匹配；
- 前端只展示服务端返回的地址、金额、到期时间、确认数和状态；
- 订单创建、重复确认、取消竞态、过期、会员激活、返佣和清理都留在后端；
- 支付页面不得根据倒计时、WS 消息或本地状态自行判定已付款；
- 正式验收必须使用真实 MySQL 结果形状并进行一次受控低金额链上付款。

### 10.2 AI、风控与手数

- AI 只选择不建仓、试探仓、轻仓、标准仓；
- 服务器根据用户净值、真实止损亏损、仓位档位、合约规格、用户最大手数和平台风控精算；
- 低于 `volume_min` 时拒绝，不向上取整到 0.01；
- 加仓最多试探仓；
- 前端只负责解释档位、预算、限制和最终结果，不参与权威手数计算；
- 模型原始结论、风控裁决和执行事实不能相互覆盖。

### 10.3 管理后台

- `/admin/` 是唯一统一管理后台；
- 主站和 AI 不再复制用户管理、平台策略、平台模型、全局风控、复盘管理、观摩源、运营和系统设置；
- 管理员登录页只做登录，不做管理员注册；
- 保留最后一个管理员保护、观摩源账号锁定、Bridge 会话撤销、审计和版本冲突保护；
- 破坏性操作必须有影响预览、明确确认、幂等和审计。

### 10.4 Bridge 与 MT4/MT5

- 浏览器协议拆分不得改变 Bridge 2.x/V3 协议和客户端更新边界；
- Bridge 只连接用户已启动的终端，不自动启动或关闭 MT4/MT5；
- 网站授权失效不得阻止本地终端识别与本地采集；
- 账户归属、观摩隔离、时间校准和历史游标规则保持；
- 浏览器 REST 命令最终仍通过服务端安全队列与 Bridge 执行，不能绕过订单意图、风控和对账。

## 11. 分阶段实施

### 阶段 0：功能、流量与回归基线

交付：

- 三套业务前端、三套认证和账户中心的完整功能矩阵；

- Playwright 截图与关键流程录像；
- 各入口 bundle、请求数、传输字节、LCP、INP、CLS；
- 典型 AI 会话 10 分钟的 HTTP/WS 流量；
- 支付、通知、复盘、后台和 MT5 的受保护合同测试；
- 新旧入口开关和回滚设计。

验收：任何未进入功能矩阵的页面不得开始迁移。

### 阶段 1：工程底座

- 建立 npm workspace、Vue 3、Vite、TypeScript；

### 阶段 3：浏览器 API 与实时底座

- 新建 `/api/v1` 合同与兼容适配；
- 新建 `/api/v1/realtime/ws`；
- 先迁移通知、后台刷新和任务进度等低风险事件；
- 建立事件序号、重连、失效、重取快照和带宽指标；
- Bridge WebSocket 保持原路径。

### 阶段 4：管理后台试点

按模块迁移：运营总览 → 用户会员 → 通知 → 商业运营 → 内容 → AI 运营 → 风控审计 → 系统设置。

每个模块同时完成 Vue 页面、`/api/v1/admin` 合同、权限、审计、缓存和实时失效，不允许只换 UI 后继续堆旧接口。

### 阶段 5：主站

按模块迁移：应用壳 → 首页 → 课程 → 知识/测验/思维导图/工具 → 社区 → 会员入口。

账户、支付订单和安全设置统一跳转或嵌入 `/account/`，停止维护主站内重复实现。公开内容需要 SEO 时采用预渲染或服务端可见 HTML，不把全部公开内容变为空壳 SPA。

### 阶段 6：AI 交易实验室只读域

顺序：

1. 首页与连接状态；
2. AI 分析师的行情和信号；
3. 交易记录和审计；
4. AI 复盘师的查看与筛选。

先把 `rates`、`history`、`signals`、`signal_detail` 和 `audit_logs` 从 `wsApi()` 迁到分页 API，WebSocket 仅做 tick 和资源变化。

### 阶段 7：AI 写入与交易域

顺序：

1. AI 策略师；
2. AI 风控师；
3. AI 复盘编辑与记忆；
4. AI 交易员；
5. 手动分析、下单、平仓、撤单和持仓管理。

交易命令最后迁移，必须在订单意图 API、幂等、任务状态、未知结果对账和受控 MT5 测试齐全后切换。

### 阶段 8：性能、动效和旧代码退役

- 根据真实指标调整 chunk、查询和 WS payload；
- 加入有限 Anime.js 动效和 reduced-motion；
- 完成多视口视觉回归与无障碍；
- 每个旧入口经过观察期和回滚演练后独立删除；
- 最后才移除 `/api`、`/aurum-api` 中没有 Bridge 依赖的浏览器兼容端点。

## 13. 灰度与回滚

- 每个应用有独立 `legacy | vue` 开关；
- 必要时增加 route/feature allowlist；
- API v1 与兼容 API 读取同一事实，不双写；
- 新浏览器 WS 与旧浏览器 WS 在迁移期并存，但同一页面只建立一条业务实时连接；
- 静态产物输出到版本目录，HTML 指向 manifest，资源使用内容 hash；
- 回滚只切入口和客户端版本，不回滚已经产生的支付、会员、交易和审计事实；
- 触发回滚：登录失败、支付状态错误、权限越界、交易事实不一致、WS 重连风暴、请求/字节显著超预算或关键页面错误率上升；
- 旧端点必须保留到对应入口观察期结束且日志证明无调用。

## 14. 风险与缓解

| 风险 | 等级 | 缓解 |
|---|---|---|
| 三套登录复制认证规则 | 高 | 共享 auth-domain、schema 和 session；页面只独立体验 |
| 浏览器 WS 拆分影响 Bridge | 高 | 新建浏览器路径，Bridge 旧/V3 路径不改 |
| WS 事件丢失导致页面陈旧 | 高 | 序号、版本、resume、resync_required 和 HTTP 快照 |
| 交易命令迁移产生重复下单 | 高 | Idempotency-Key、订单意图、唯一约束和对账 |
| 新旧 API 双写或状态分叉 | 高 | 只复用同一 service，不允许双写 |
| 账户或观摩数据串线 | 高 | query key、服务端授权和上下文代次三重隔离 |
| 为节省请求把业务规则搬前端 | 高 | 使用第 4.5 节边界作为代码审查门槛 |
| 组件抽象过度 | 中 | 三层组件策略，领域组件默认不跨模块 |
| PrimeVue 增大首包 | 中 | 按需导入、route chunk 和 CI budget |
| Vue Query 缓存陈旧 | 中 | 服务端版本、事件失效和关键操作强制确认 |
| Anime.js 影响性能 | 低 | 延后到阶段 8、按需加载、reduced motion |
| 迁移期业务持续变化 | 高 | 功能矩阵、变更登记和旧新同步责任人 |
| 工期被低估 | 高 | 阶段 0 重新估算，按垂直模块验收 |

## 17. 实施前两轮复审

### 17.1 第一轮：需求覆盖、边界、复用和设计克制

检查内容：

- 是否覆盖主站、AI、后台三套独立页面；
- 是否提供三套独立登录页面；
- 是否保留统一账号、账户中心和唯一管理后台；
- 是否规定优先使用 Vue/PrimeVue 组件；
- 是否落实功能模块独立、易修改；
- 是否统一后端 API，并明确实时与精确查询分工；
- 是否把性能和带宽最小化作为硬指标；
- 是否复用现有支付、风控、Bridge、设计和会话能力；
- 是否为了“规范”引入不必要的大重写。

第一轮发现与调整：

1. 原方案遗漏后台独立登录，已增加 `admin-auth` 和 `/admin/auth/`；
2. 原方案把六个入口都称为应用，边界容易误解，已改成三套业务前端、三套认证、一个账户中心；
3. 原方案只写“WebSocket 单一适配器”，没有纠正当前查询走 WS，已增加三通道与数据分类表；
4. 原方案只有通用 `features/` 目录，约束不足，已增加 feature 公共入口、依赖边界和代码所有权规则；
5. 原方案只使用 Pinia，容易重新形成服务端数据大 Store，已增加 Vue Query；
6. 原方案保留全部后端接口不动，与本次接口规范化需求冲突，已改为保留业务规则、渐进建立 API v1；
7. 原性能预算没有请求数、响应大小和 WS 消息预算，已补充带宽规则与可观测性；
8. 为避免设计过度，没有要求一次性把全部后端转换 TypeScript，也没有引入微服务、GraphQL、事件总线平台或 Service Worker。
9. 初稿要求共享认证领域逻辑，但 workspace 漏列对应包，已补充 `packages/auth-domain`，三套登录只保留独立页面壳和返回规则。

第一轮结论：需求覆盖完整，应用边界清楚，复用现有能力，未要求一次性后端重写。剩余风险是阶段 0 尚未取得生产流量、浏览器网络和真实设备基线。

### 17.2 第二轮：兼容、数据、并发、恢复、安全、测试和回滚

检查内容与结论：

| 检查域 | 结论 | 方案中的处理 |
|---|---|---|
| URL 与入口兼容 | 通过 | 保留现有 URL，新增 `/admin/auth/`，旧入口按开关回滚 |
| 数据与数据库 | 通过 | 新旧 API 调同一 service，不双写，不要求先改 schema |
| 并发与幂等 | 通过 | Idempotency-Key、expected_version/If-Match、409 冲突 |
| WS 丢失与乱序 | 通过 | sequence、version、resume、resync_required、HTTP 快照 |
| 交易未知结果 | 通过 | 订单意图、最终 GET 和服务端对账，前端不猜测 |
| 异常恢复 | 通过 | 断线保留已确认数据、显示时间、重连后精确同步 |
| 时间语义 | 通过 | UTC 与终端时间分开，保留校准状态和来源 |
| 会话与权限 | 通过 | 共享认证、服务端角色校验、next 白名单、跨应用退出 |
| 支付安全 | 通过 | 服务端事实、固定地址、唯一金额、真实链上验收 |
| 前端缓存 | 通过 | query key 含账户/频道/策略上下文，版本失效 |
| 性能与带宽 | 有条件通过 | 已设预算，但必须由阶段 0 实测校准 |
| 测试 | 通过 | 合同、组件、E2E、WS 恢复、流量和真实关键链路 |
| 灰度与回滚 | 通过 | 入口级开关、兼容端点、版本静态目录、无业务双写 |
| 连带 Bug | 有条件通过 | 重点防账户串线、重复交易、重复登录逻辑和 Bridge 协议受影响 |

第二轮发现的实质问题与最终调整：

1. “所有实时数据都直接用 WS payload 更新”会在丢事件后产生静默错误，已改为关键资源事件失效 + HTTP 快照，只有报价等短生命周期流直接消费；
2. “能在前端解决的都放前端”可能被误解为下放业务规则，已新增前后端职责表并明确支付、权限、风控和交易不得下放；
3. 三套登录可能复制验证码、密码和 `next` 校验，已要求共享 auth-domain 与 schema，仅页面壳独立；
4. 任意 `fields` 查询会增加合同与权限复杂度，已改为明确 summary/detail/export/snapshot 模型；
5. 直接删除旧 `/aurum-api` 会影响 Bridge，已明确浏览器兼容端点与 Bridge 路径分别退役；
6. 原工期未覆盖接口和实时改造，已调整为 55～80 个有效工程日。
7. 当前旧 `/api` 会经过全局 `no-store` 兼容策略，可能让新 ETag 失效，已要求 `/api/v1` 先挂载并按公开、私有和敏感资源分别设置缓存。
8. 浏览器 WS 若只依赖 Cookie 而不校验来源会扩大跨站连接风险，已增加同源 `Origin`、一次性票据和 topic 级权限校验。

第二轮结论：最终方案在兼容、数据一致性、幂等、异常恢复、时间、安全、测试和回滚方面具备实施条件。实施前仍必须完成阶段 0；若真实基线显示首包或流量预算不现实，可调整数值，但不得取消按入口预算、HTTP/WS 分工和关键业务服务端权威这三项原则。

## 18. 最终决策

后续重构统一按以下决策执行：

> 使用 Vue 3 + Vite + TypeScript + PrimeVue 建设主站、AI 交易实验室和管理后台三套独立业务前端；分别提供 `/auth/`、`/ai/auth/`、`/admin/auth/` 三套独立登录页面，共用账号、会话、账户中心和后端认证。前端按垂直 feature 模块拆分，优先使用成熟 Vue 组件；服务端状态由 Vue Query 管理，本地状态由 Pinia 管理。后端渐进建立 `/api/v1` 领域合同，精确快照、分页查询和业务命令走 HTTP，实时行情、资源变化和任务进度走独立浏览器 WebSocket；Bridge WebSocket 保持独立兼容。性能、请求数和传输字节纳入 CI 与上线验收，前端承担展示与派生计算，支付、权限、风控、手数和交易事实继续由服务端权威处理。

本文件是后续任务拆分、实施、审查和验收的上位方案。每个阶段必须再拆成独立任务文档，列出功能清单、API/WS 合同、模块边界、性能预算、测试、灰度和回滚，完成后才能进入下一阶段。
