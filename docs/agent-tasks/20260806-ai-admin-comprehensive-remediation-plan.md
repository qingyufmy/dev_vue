## 1. 最终结论

本次整改不采用“一次性重写”，先修复会误导管理员或破坏兼容合同的问题，再统一可访问性和移动端基础，随后补齐管理员决策视图，最后进入已有 Vue 3 渐进迁移方案。

实施顺序固定为：

1. 恢复完全可信的测试基线；
2. 修复 AI 运营健康状态的“假绿色”；
3. 修复 `/api` 与 `/aurum-api` 观摩权限兼容，以及发布说明输入和 HTML 边界；
4. 统一桌面、手机和平板的字号、对比度、触控和表格行为；
5. 按普通用户任务重整 AI 实验室的信息层级；
6. 按管理员决策任务补齐中文审计、待办与可视化；
7. 完成性能、模块化、定时任务和依赖安全收尾；
8. 再进入 `20260724-vue3-primevue-animejs-frontend-refactor-plan.md`，不得同时维护两套互相竞争的重构路线。

前四个阶段继续使用现有 Express、静态页面和 API，不要求数据库迁移，不改变交易、风控、支付、会员、Bridge 或 AI 输出合同。

### 1.1 v1.1 复审修订摘要

- 健康状态改为按自动推理、人工推理、复盘、记忆和模型评测分别判断，禁止用某一类请求掩盖另一类任务停摆。
- 双 API 前缀规范化同时覆盖 Express 默认接受的尾部斜杠，不解码或放宽未知路径。
- 发布说明增加现有内容兼容盘点、服务端只读预览、50,000 字符上限、并发版本锁和确定的安全样式白名单。
- 把 `DESIGN.md`、`.impeccable/design.json` 纳入令牌整改范围，并分离交易涨跌色与系统成功/故障色。
- 管理审计词典必须同时盘点代码写入点、当前数据库和生产只读 distinct 值，不能只依赖本地样本。
- 时间序列接口增加 MySQL 版本、查询计划、返回点数、无 N+1 和并发请求上限。
- single-flight 增加停止函数、fake timer 重入测试和多实例边界说明。

## 2. 目标与成功标准

### 2.1 普通用户目标

- 进入任一 AI 页面后，第一屏能回答“现在发生了什么、是否安全、下一步做什么”。
- AI 建议、服务器风控裁决和 MT4/MT5 实际执行继续严格分离。
- 手机端单手可完成查看、筛选和展开详情；危险操作仍需明确确认。
- 平板端不依赖反复横向滚动才能看到交易结果和关键操作。
- 观摩、会员失效、桥接离线和完整交易模式的权限与提示一致。

### 2.2 管理员目标

- 运营总览和 AI 运营首页不得在无样本、样本过期或关键链路不可用时显示“稳定”。
- 异常、积压、风险账户和待办按紧急程度排序，并可下钻到现有管理页面。
- 审计记录首先显示自然中文动作和变更摘要，内部代码只作为次级证据。
- 用户、商业、AI、风控和内容页提供支持决策的数据，不添加装饰性图表。
- 配置页面明确说明字段语义、影响范围、生效时间、安全限制和回滚方式。

### 2.3 工程目标

- `/api` 与 `/aurum-api` 在认证和观摩权限上行为一致。
- 每个修复都有定向回归测试；全量测试恢复为零失败。
- 首批整改不修改既有迁移；如后续图表查询确需索引，只能新增迁移。
- 高风险状态由服务端生成权威展示模型，前端不重新推导另一套业务结论。
- 前端初始资源不得因整改增加超过 5%；进入模块化阶段后再设减重目标。

## 3. 不在本轮改变的合同

以下内容是硬边界，不得借整改顺带改变：

- 不修改 AI 结构化输出、仓位档位、风控计算、订单意图、MT4/MT5 指令或对账语义。
- 不恢复旧 `signals` 顶级导航，不在 AI 实验室或主站重复建设管理后台。
- 不改变 Plus、Pro、观摩源、会员失效及桥接离线时的既有套餐能力，只修复路径兼容和展示一致性。
- 不把观摩用户的只读操作错误绑定为本人交易操作。
- 不重写或批量更新管理员已保存的策略提示词。
- 不调整支付地址、金额匹配、会员激活、返佣、短信或邮件业务规则。
- 不自动启停 MT4/MT5，不修改 Bridge 发布、安装和更新边界。
- 不为了图表而复制业务事实或建立第二套统计主账。
- 不在本轮同时推进全站 Vue 重构；已有迁移方案仍是后续架构基准。

## 7. WP-01：重建 AI 运营健康状态

### 7.1 设计原则

健康状态必须由“样本、异常、依赖、积压和新鲜度”共同决定，禁止把“没有失败记录”直接等同于“健康”。

时间语义必须拆开：运行健康使用滚动 24 小时窗口和绝对时间戳判断新鲜度；“今日请求/今日信号”等运营指标继续使用北京时间自然日。两者在 API 和界面上分别标注，禁止用 `CURDATE()` 的自然日统计冒充滚动 24 小时健康样本，也不得使用 MT4/MT5 终端时间判断平台服务健康。

推荐服务端权威状态：

| 状态 | 含义 | 允许绿色 |
| --- | --- | --- |
| `healthy` | 有新鲜样本，关键链路均满足条件 | 是 |
| `attention` | 可运行但存在积压、降级或接近阈值 | 否，使用橙色 |
| `critical` | 已出现阻断、持续失败或必要依赖不可用 | 否，使用红色 |
| `insufficient_data` | 无样本、样本过期或无法完成判断 | 否，使用中性蓝灰 |

### 7.2 后端修改

主要文件：

- `server/admin/ai-operations.js`
- `server/routes/admin-console.js`
- `tests/ai/admin-scheduler-runtime.test.js`，或新建 `tests/ai/admin-ai-health.test.js`

新增纯函数 `deriveAdminAiHealth(input)`，输入只包含已查询的统计和依赖状态，输出稳定展示模型：

```json
{
  "state": "attention",
  "headline_code": "review_backlog_aging",
  "evaluated_at": "ISO-8601",
  "window": "24h",
  "sample_count": 42,
  "components": {
    "auto_inference": { "state": "healthy", "expected": true, "sample_count": 12 },
    "review": { "state": "attention", "expected": true, "sample_count": 8 },
    "model_compare": { "state": "insufficient_data", "expected": false, "sample_count": 0 }
  },
  "freshness": {
    "last_model_request_at": "ISO-8601|null",
    "last_signal_at": "ISO-8601|null",
    "last_scheduler_state_at": "ISO-8601|null"
  },
  "reasons": [
    { "code": "review_backlog_aging", "severity": "attention", "value": 8 }
  ]
}
```

必须满足：

- 保留现有 `summary.*_today` 供北京时间自然日运营展示；另增 `health_metrics` 作为滚动 24 小时健康输入，二者不得混算。
- `health_metrics.model_requests_24h = 0` 时成功率为 `null`，不得为 100%。
- `health_metrics` 必须按 `usage` 分组；模型评测或人工推理有成功请求，不能证明自动推理、复盘或记忆任务健康。
- 组件与现有稳定 usage 值固定映射：`manual`→人工推理、`model_compare`→模型评测、`auto_private|auto_platform`→自动推理、`review`→复盘、`memory_compression`→记忆压缩；不得另造无法与日志对齐的 usage。
- `expected` 不能由“最近是否有日志”反推：自动推理由已启用部署/订阅与调度运行态决定；模型评测由 queued/running job 决定；复盘和记忆由功能开关、到期/排队/运行/重试任务决定；人工推理属于按需能力，无活动请求时不作为后台持续运行预期。
- `health_metrics.signal_errors_24h > 0` 必须进入运行健康状态推导；`summary.signal_errors_today` 只用于北京时间自然日运营卡片。
- Redis 调度运行态不可用必须至少为 `attention`。
- 桥接数量不能孤立判断：只有存在启用订阅、活跃观摩源或其他明确运行预期时，必要桥接离线才为 `critical`；没有运行预期时显示“当前无运行任务”。
- 待处理复盘本身是工作队列；超过 SLA 或出现失败才降低健康状态。
- 复盘积压年龄直接复用 `getReviewAdminHealth()` 已返回的 `oldest_updated_at`，SLA 由现有复盘生成周期和重试规则推导；首批不增加一个无法解释的后台阈值开关。
- 每个状态都返回机器码和自然中文所需参数，不返回拼接好的危险 HTML。
- API 新字段采用增量兼容；旧前端忽略，新前端遇到旧服务端必须显示“状态未评估”，不得本地回退为绿色。

聚合优先级固定为：

1. 现有治理告警为 critical、存在运行预期但调度运行态不可用、或已启用观摩频道的唯一权威来源离线：对应组件为 `critical`；
2. 任一模型/信号错误、复盘失败或超过现有 SLA、数据接近过期：对应组件为 `attention`；
3. 没有运行预期且没有样本：对应组件为 `insufficient_data`；
4. 只有存在运行预期的组件均有新鲜成功证据，且没有上述异常时，整体才允许为 `healthy`；
5. 整体状态取所有“存在运行预期”组件的最差状态；没有任何运行预期时整体为 `insufficient_data`，不得显示绿色。

### 9.2 版本语义

后台字段改名为“通知序号”，明确说明：

- 必须是 `1` 到 `2147483647` 的安全整数；
- 与当前序号相同：允许修正文案，但已读用户不会再次弹出；
- 大于当前序号：视为新通知，用户会再次看到；
- 小于当前序号：拒绝，避免已读状态倒退；
- 软件产品版本 `3.0.0` 应写入内容标题，不应填写在通知序号字段。

### 9.3 服务端处理

- 在路由中严格校验原始字符串，禁止 `parseInt('1abc')`、`NaN`、负数和小数。
- 在一个数据库事务中通过按固定 key 顺序的单次 `SELECT ... FOR UPDATE` 读取当前值并原子更新序号与内容，降低并发死锁风险并保护递增语义。
- 管理端读取接口增量返回由“当前序号 + 已净化内容”计算的 `revision`；新前端保存时回传 `expected_revision`，事务内锁定两行并比对，不一致返回 409，避免同序号修正文案时后保存者静默覆盖先保存者。混部期允许旧前端不传该字段，但响应和日志需标识 legacy write，完成前端覆盖后再评估是否强制。
- 事务回调只使用 `withTransaction()` 提供的连接级 runner，并按 MySQL2 的 `[rows, fields]` 返回形态解构；事务内不得调用连接外的 `queryOne/queryRun`。缺失配置行通过现有 `(category, key)` 唯一键约束下的幂等插入补齐，再进入锁定与更新。
- 内容最大 50,000 个 JavaScript 字符；超限返回稳定错误码，不依赖全局请求体上限代替字段校验。
- 在 `server/html-sanitizer.js` 新增发布说明专用净化函数。
- 允许语义标签：标题、段落、列表、强调、链接、代码和安全容器。
- 禁止脚本、表单、iframe、SVG、事件属性、任意定位、z-index、外部交互控件。
- 为兼容现有发布说明，只允许 `color`、`background-color`、`font-weight`、`font-style`、`text-decoration`、`text-align`、`line-height`、非负且有上限的 `margin*`、`padding*`、`border*` 和 `border-radius`；禁止 `display`、`position`、`inset`、`z-index`、`width/height`、`transform`、`behavior`、`url()`、`expression()` 和自定义 CSS 变量。
- 写入时净化，公开读取时再次净化历史值，形成纵深防御。
- 保持响应中的 `content` 字段，避免破坏现有客户端。
- 新增管理员只读预览接口，接收待预览内容并返回同一服务端净化器的结果、是否发生移除及移除类别；预览接口不写数据库。
- 参数错误返回 HTTP 400，低于当前序号的并发/语义冲突返回 HTTP 409，同时保持 `{ ok:false, code, error }` JSON 结构；前端兼容处理现有 200 + `ok:false` 和新状态码。
- 同一事务写入 `release_notes_updated` 审计，detail 只记录旧/新通知序号、旧/新内容 SHA-256、净化移除类别和是否 legacy write，不记录发布说明正文；事务失败时配置和审计一并回滚。

### 9.4 管理员界面

- 编辑区旁增加实时安全预览，不直接运行原始 HTML。
- 显示“支持的标签”和“被移除内容”提示。
- 保存前显示“本次是否会重新通知用户”。
- 预览、保存成功、校验失败和服务端净化后内容不一致均有明确反馈。

### 9.5 测试

- `1`、当前值、递增值成功。
- `0`、负数、小数、空白、`NaN`、`1abc`、超 INT 范围失败。
- 低于当前值失败且无数据库写入。
- 第二次数据库写入失败时整体回滚。
- 审计写入失败时序号和内容也回滚，成功审计不包含原始 HTML。

- WP-00 至 WP-07 的入口 JS+CSS 压缩传输总量不得增加超过 5%。
- 新图表不得让未访问页面提前加载图表资源。
- 模块化或 Vue 迁移完成后，AI 初始路由 JS 解码体积至少降低 30%，管理后台至少降低 25%。
- XLSX 继续仅在导出时加载。
- 字体 CSS、Lucide 和 Chart.js 分别测量，禁止只看浏览器缓存后的 0 transfer。

## 15. WP-09：并发、依赖和安全硬化

### 15.1 定时任务 single-flight

目标文件：

- `server/routes/ai/scheduler.js`
- `server/routes/ai/order-intents.js`
- `server/index.js`
- 相关 scheduler/reconciler 测试

处理方式：

- 每类周期协调器增加进程内运行标记或 Promise single-flight。
- 新周期到达而上一轮未结束时记录 skipped-overlap 指标，不排队无限补跑。
- 保留数据库条件更新、Redis 锁和现有幂等逻辑；进程内锁不是分布式执行权。
- 为自动调度补齐与现有 `stopPendingReconciler()`、`stopOrderIntentReconciler()` 对称的停止函数，并由 `server/index.js` 的显式 graceful-shutdown 生命周期统一调用；不得只依赖清除 interval 或进程强退。
- 停止顺序固定为：拒绝新轮次、清除 timer、等待当前 Promise 在有界超时内完成、关闭 HTTP/Redis/数据库资源；超时后记录未完成任务类型再退出。
- fake timer 测试必须证明：第一轮 Promise 未结束时第二个 tick 只记 skipped-overlap；第一轮结束后下一 tick 可以执行；调用 stop 后不再启动新轮。
- 多实例部署时，进程内 single-flight 只约束单实例；跨实例仍以现有 Redis 锁、数据库条件更新和业务幂等键为准。实施验收必须分别覆盖单实例重入和双实例竞争，不能把单进程测试当作集群证明。

### 15.2 依赖

- 单独调查 `@solana/web3.js -> jayson -> uuid` 的安全升级路径。
- 禁止执行 npm 建议的 `@solana/web3.js 0.0.3` 自动修复。
- 如升级，必须覆盖 Solana 地址、支付监听和交易解析回归。
- 无安全版本时记录风险接受、输入边界和替换计划。

### 15.3 日志和 CSP

- 生产配置显式禁止 `DEBUG_LLM_PAYLOAD=1`。
- 即使开发开启，也应对账号、提示词、密钥和用户数据执行字段级脱敏。
- 逐步移除内联脚本/样式，再收紧 CSP；不得直接删除 `unsafe-inline` 导致当前页面不可用。
- 发布说明预览使用服务端净化结果，不另造一套不同的浏览器净化规则。
