## 1. 最终结论

本次整改不采用“一次性重写”，先修复会误导管理员或破坏兼容合同的问题，再统一可访问性和移动端基础，随后补齐管理员决策视图，最后进入已有 Vue 3 渐进迁移方案。

实施顺序固定为：

1. 恢复完全可信的测试基线；
2. 修复 AI 运营健康状态的“假绿色”；
3. 修复 `/api` 与 `/aurum-api` 观摩权限兼容，以及发布说明输入和 HTML 边界；
4. 统一桌面、手机和平板的字号、对比度、触控和表格行为；
5. 按普通用户任务重整 AI 实验室的信息层级；
6. 按管理员决策任务补齐中文审计、待办与可视化；
7. 完成性能、模块化、定时任务和依赖安全收尾；
8. 再进入 `20260724-vue3-primevue-animejs-frontend-refactor-plan.md`，不得同时维护两套互相竞争的重构路线。

前四个阶段继续使用现有 Express、静态页面和 API，不要求数据库迁移，不改变交易、风控、支付、会员、Bridge 或 AI 输出合同。

## 2. 目标与成功标准

### 2.1 普通用户目标

- 进入任一 AI 页面后，第一屏能回答“现在发生了什么、是否安全、下一步做什么”。
- AI 建议、服务器风控裁决和 MT4/MT5 实际执行继续严格分离。
- 手机端单手可完成查看、筛选和展开详情；危险操作仍需明确确认。
- 平板端不依赖反复横向滚动才能看到交易结果和关键操作。
- 观摩、会员失效、桥接离线和完整交易模式的权限与提示一致。

### 2.2 管理员目标

- 运营总览和 AI 运营首页不得在无样本、样本过期或关键链路不可用时显示“稳定”。
- 异常、积压、风险账户和待办按紧急程度排序，并可下钻到现有管理页面。
- 审计记录首先显示自然中文动作和变更摘要，内部代码只作为次级证据。
- 用户、商业、AI、风控和内容页提供支持决策的数据，不添加装饰性图表。
- 配置页面明确说明字段语义、影响范围、生效时间、安全限制和回滚方式。

### 2.3 工程目标

- `/api` 与 `/aurum-api` 在认证和观摩权限上行为一致。
- 每个修复都有定向回归测试；全量测试恢复为零失败。
- 首批整改不修改既有迁移；如后续图表查询确需索引，只能新增迁移。
- 高风险状态由服务端生成权威展示模型，前端不重新推导另一套业务结论。
- 前端初始资源不得因整改增加超过 5%；进入模块化阶段后再设减重目标。

## 3. 不在本轮改变的合同

以下内容是硬边界，不得借整改顺带改变：

- 不修改 AI 结构化输出、仓位档位、风控计算、订单意图、MT4/MT5 指令或对账语义。
- 不恢复旧 `signals` 顶级导航，不在 AI 实验室或主站重复建设管理后台。
- 不改变 Plus、Pro、观摩源、会员失效及桥接离线时的既有套餐能力，只修复路径兼容和展示一致性。
- 不把观摩用户的只读操作错误绑定为本人交易操作。
- 不重写或批量更新管理员已保存的策略提示词。
- 不调整支付地址、金额匹配、会员激活、返佣、短信或邮件业务规则。
- 不自动启停 MT4/MT5，不修改 Bridge 发布、安装和更新边界。
- 不为了图表而复制业务事实或建立第二套统计主账。
- 不在本轮同时推进全站 Vue 重构；已有迁移方案仍是后续架构基准。

## 7. WP-01：重建 AI 运营健康状态

### 7.1 设计原则

健康状态必须由“样本、异常、依赖、积压和新鲜度”共同决定，禁止把“没有失败记录”直接等同于“健康”。

时间语义必须拆开：运行健康使用滚动 24 小时窗口和绝对时间戳判断新鲜度；“今日请求/今日信号”等运营指标继续使用北京时间自然日。两者在 API 和界面上分别标注，禁止用 `CURDATE()` 的自然日统计冒充滚动 24 小时健康样本，也不得使用 MT4/MT5 终端时间判断平台服务健康。

推荐服务端权威状态：

| 状态 | 含义 | 允许绿色 |
| --- | --- | --- |
| `healthy` | 有新鲜样本，关键链路均满足条件 | 是 |
| `attention` | 可运行但存在积压、降级或接近阈值 | 否，使用橙色 |
| `critical` | 已出现阻断、持续失败或必要依赖不可用 | 否，使用红色 |
| `insufficient_data` | 无样本、样本过期或无法完成判断 | 否，使用中性蓝灰 |

### 7.2 后端修改

主要文件：

- `server/admin/ai-operations.js`
- `server/routes/admin-console.js`
- `tests/ai/admin-scheduler-runtime.test.js`，或新建 `tests/ai/admin-ai-health.test.js`

新增纯函数 `deriveAdminAiHealth(input)`，输入只包含已查询的统计和依赖状态，输出稳定展示模型：

```json
{
  "state": "attention",
  "headline_code": "review_backlog_aging",
  "evaluated_at": "ISO-8601",
  "window": "24h",
  "sample_count": 42,
  "freshness": {
    "last_model_request_at": "ISO-8601|null",
    "last_signal_at": "ISO-8601|null",
    "last_scheduler_state_at": "ISO-8601|null"
  },
  "reasons": [
    { "code": "review_backlog_aging", "severity": "attention", "value": 8 }
  ]
}
```

必须满足：

- 保留现有 `summary.*_today` 供北京时间自然日运营展示；另增 `health_metrics` 作为滚动 24 小时健康输入，二者不得混算。
- `health_metrics.model_requests_24h = 0` 时成功率为 `null`，不得为 100%。
- `signal_errors_today > 0` 必须进入状态推导。
- Redis 调度运行态不可用必须至少为 `attention`。
- 桥接数量不能孤立判断：只有存在启用订阅、活跃观摩源或其他明确运行预期时，必要桥接离线才为 `critical`；没有运行预期时显示“当前无运行任务”。
- 待处理复盘本身是工作队列；超过 SLA 或出现失败才降低健康状态。
- 复盘积压年龄直接复用 `getReviewAdminHealth()` 已返回的 `oldest_updated_at`，SLA 由现有复盘生成周期和重试规则推导；首批不增加一个无法解释的后台阈值开关。
- 每个状态都返回机器码和自然中文所需参数，不返回拼接好的危险 HTML。
- API 新字段采用增量兼容；旧前端忽略，新前端遇到旧服务端必须显示“状态未评估”，不得本地回退为绿色。

### 7.3 前端修改

主要文件：

- `public/admin/app.js`
- `public/admin/styles.css`
- `tests/admin-console-frontend.test.js`

调整 AI 运营首页：

- 顶部首先显示权威状态、时间窗、最后数据时间和样本量。
- 0 健康样本显示“最近 24 小时暂无模型请求，无法判断成功率”；“今日请求”卡片仍按北京时间自然日显示。
- 运行结论下方列出不超过 3 个主要原因，其余放入“查看全部”。
- 复盘待办、治理告警和桥接异常分别呈现，不把业务队列混写成系统故障。
- “模型成功率”无分母时显示 `--`，并使用中性样式。

### 7.4 测试矩阵

- 0 请求、0 失败：`insufficient_data`。
- 有请求、0 失败、依赖新鲜：`healthy`。
- 有信号异常但模型无失败：至少 `attention`。
- 有运行预期且所有桥接离线：`critical`。
- 无运行预期且 0 桥接：`insufficient_data` 或明确 idle，不得 critical。
- Redis 不可用：`attention/critical`，取决于是否存在运行预期。
- 复盘待处理但未超 SLA：不判故障。
- 复盘失败或超 SLA：`attention/critical`。
- 新前端对缺少 `health` 字段的旧 API：显示“状态未评估”。

### 9.1 修改范围

### 9.2 版本语义

后台字段改名为“通知序号”，明确说明：

- 必须是 `1` 到 `2147483647` 的安全整数；
- 与当前序号相同：允许修正文案，但已读用户不会再次弹出；
- 大于当前序号：视为新通知，用户会再次看到；
- 小于当前序号：拒绝，避免已读状态倒退；
- 软件产品版本 `3.0.0` 应写入内容标题，不应填写在通知序号字段。

### 9.3 服务端处理

- 在路由中严格校验原始字符串，禁止 `parseInt('1abc')`、`NaN`、负数和小数。
- 在一个数据库事务中读取当前值并原子更新序号与内容。
- 内容设置最大长度；请求体过大沿用现有全局限制。
- 在 `server/html-sanitizer.js` 新增发布说明专用净化函数。
- 允许语义标签：标题、段落、列表、强调、链接、代码和安全容器。
- 禁止脚本、表单、iframe、SVG、事件属性、任意定位、z-index、外部交互控件。
- 如必须兼容现有内联样式，只允许经过明确白名单的颜色、字重、对齐、间距和边界属性；禁止 `position`、`behavior`、`url()`、`expression()` 和自定义 CSS 变量。
- 写入时净化，公开读取时再次净化历史值，形成纵深防御。
- 保持响应中的 `content` 字段，避免破坏现有客户端。

### 9.4 管理员界面

- 编辑区旁增加实时安全预览，不直接运行原始 HTML。
- 显示“支持的标签”和“被移除内容”提示。
- 保存前显示“本次是否会重新通知用户”。
- 预览、保存成功、校验失败和服务端净化后内容不一致均有明确反馈。

### 9.5 测试

- `1`、当前值、递增值成功。
- `0`、负数、小数、空白、`NaN`、`1abc`、超 INT 范围失败。
- 低于当前值失败且无数据库写入。
- 第二次数据库写入失败时整体回滚。
- script、事件属性、危险 URL、危险 style 被移除。
- 合法标题、列表、强调和安全链接保留。
- AI 弹窗只展示服务端净化后的内容。

## 10. WP-04：统一设计令牌、可访问性和响应式基础

### 10.1 令牌策略

以 `DESIGN.md` 和 `.impeccable/design.json` 为权威，不改变 AURUM“智能交易团队”的视觉主轴。

需统一：

- 正文：14px；连续说明不低于 13px。
- 标签和辅助信息：默认不低于 12px。
- 9–11px 仅允许装饰性、可省略元数据，并仍需满足对比度要求。
- 正常文字对比度不低于 4.5:1；大字和图形状态不低于 3:1。
- 桌面普通控件视觉高度建议 40px；触摸环境和核心操作不低于 44px。
- 所有图标按钮必须有可访问名称。
- 颜色状态必须同时有中文文本或图标。
- 焦点、hover、active、disabled、loading、error 状态统一。
- 动效 150–250ms，并支持 `prefers-reduced-motion`。
- 动态状态变化使用适当的 `aria-live`，但行情逐跳刷新不得持续打断屏幕阅读器。

### 10.2 提示与通知卫生

- 表单字段错误优先显示在字段附近，不同时再弹一条重复 toast。
- 成功 toast 只用于用户主动提交且结果不能从页面状态直接看出的操作。
- 保存后页面已经明确更新的，不再重复显示长篇“保存成功”说明。
- WebSocket 重连、报价波动和调度刷新按状态合并，禁止同一问题连续弹出。
- 风险拒绝、权限不足、桥接离线和服务异常使用不同级别与不同解决指引。
- 危险操作确认只保留在会改变交易、风控、账户、发布或删除数据的动作；普通查看、筛选和展开不得二次确认。
- 所有 toast 可由键盘关闭，不自动吞掉必须阅读的错误；高风险结果同时保留在页面内。

### 10.3 CSS 改造边界

- 优先替换硬编码的低对比文字和重复控件尺寸。
- 先建立语义令牌，再逐页迁移；不得用新的高优先级覆盖层继续叠加 CSS。
- 删除 `transition: all` 和宽度类布局动画，改为明确属性。
- 横向页签必须显示部分下一项、渐隐遮罩或滚动提示，并支持键盘左右键。
- `pointer: coarse` 下统一扩大命中区。

### 10.4 断点

| 宽度 | 目标 |
| --- | --- |
| 320–479 | 单列手机；底部导航；表格转卡片/摘要行 |
| 480–767 | 大屏手机；可保留双列轻量指标 |
| 768–1023 | 平板；压缩侧栏；关键表格固定主列或摘要模式 |
| 1024–1439 | 标准桌面工作台 |
| ≥1440 | 限制正文最大宽度，增加信息并列，不放大字号 |

### 10.5 验收工具

- 浏览器计算样式对比度扫描。
- 键盘 Tab/Shift+Tab/Enter/Space/方向键走查。
- 390×844、768×1024、1280×800、1440×900。
- 200% 浏览器缩放下无信息丢失。
- reduced-motion 模式下无依赖动画才能出现的内容。
- 屏幕阅读器不会因实时行情和倒计时每秒重复播报。

## 15. WP-09：并发、依赖和安全硬化

### 15.1 定时任务 single-flight

目标文件：

- `server/routes/ai/scheduler.js`
- `server/routes/ai/order-intents.js`
- 相关 scheduler/reconciler 测试

处理方式：

- 每类周期协调器增加进程内运行标记或 Promise single-flight。
- 新周期到达而上一轮未结束时记录 skipped-overlap 指标，不排队无限补跑。
- 保留数据库条件更新、Redis 锁和现有幂等逻辑；进程内锁不是分布式执行权。
- 进程退出时停止接收新轮次，允许当前轮在明确超时内结束。

### 15.2 依赖

- 单独调查 `@solana/web3.js -> jayson -> uuid` 的安全升级路径。
- 禁止执行 npm 建议的 `@solana/web3.js 0.0.3` 自动修复。
- 如升级，必须覆盖 Solana 地址、支付监听和交易解析回归。
- 无安全版本时记录风险接受、输入边界和替换计划。

### 15.3 日志和 CSP

- 生产配置显式禁止 `DEBUG_LLM_PAYLOAD=1`。
- 即使开发开启，也应对账号、提示词、密钥和用户数据执行字段级脱敏。
- 逐步移除内联脚本/样式，再收紧 CSP；不得直接删除 `unsafe-inline` 导致当前页面不可用。
- 发布说明预览使用服务端净化结果，不另造一套不同的浏览器净化规则。

静态前端可回滚到上一缓存版本；服务端新增字段保持向后兼容；索引迁移通常无需紧急删除，除非证实造成写入或空间事故。

## 20. 两轮正式复审记录

### 20.1 第一轮：需求覆盖、业务边界、复用和过度设计

检查结论：

- 已覆盖普通用户、管理员、手机、平板、桌面、可视化、提示精简和全部审计发现。
- 初稿曾把“前端全面模块化”放在首批，复审后调整为先修真相、权限和安全，再进入既有 Vue 迁移，避免重复重构。
- 初稿曾把“0 Bridge”直接判为故障，复审后改为结合启用订阅和观摩源等运行预期，避免无任务时误报。
- 初稿曾要求所有复盘待办降低系统健康，复审后改为仅在失败或超过 SLA 时降低，避免把正常工作队列误报成故障。
- 复用现有统一后台、现有数据主账、现有 `sanitize-html`、审计词典和 Vue 迁移方案，不新增重复页面或第二套统计事实。
- 图表限定为支持决策并可下钻，删除装饰性仪表盘和全页面卡片化建议。

第一轮调整后结论：方案满足范围，首批改动最小，不改变交易与业务合同，不存在为了“现代化”而一次性重写的问题。

### 20.2 第二轮：兼容、数据、并发、恢复、安全、测试和回滚

检查结论：

- 增加新旧服务端/前端混部规则：新增字段向后兼容，新前端缺少新字段时显示未知而非绿色。
- 将滚动 24 小时运行健康与北京时间自然日运营指标分开，避免跨日和浏览器时区造成假结论。
- 发布说明允许同序号修正文案但不重新通知，递增才触发新通知；避免强制递增导致管理员无法修正当前内容。
- 发布说明更新改为事务，并在读取边界二次净化；补充历史脏数据兼容。
- 双 API 前缀增加真实路由集成测试，不只验证纯函数。
- 定时任务进程内 single-flight 只防重入，不替代 Redis/数据库执行权。
- 数据可视化索引改为 `EXPLAIN ANALYZE` 后按需新增，避免预先过度建索引。
- 图表响应字段采用可选增量，部署顺序支持服务端先行和静态前端回滚。
- 增加 200% 缩放、Token 失效、旧 API、Redis 不可用、无运行预期和长时间停留状态测试。
- 增加提示去重、字段内错误、`aria-live` 和实时行情不打断屏幕阅读器的验收要求。
- 增加明确停止条件，任何权限扩大、合同测试失败或健康结论与原始指标矛盾均阻断发布。

第二轮最终结论：未发现需要再次改写方案的实质问题。方案可以进入实施，但真实 MySQL 查询计划、生产缓存、已安装 Bridge 状态和真实移动设备仍必须在相应批次后单独验证。
