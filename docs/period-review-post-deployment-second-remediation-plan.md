# 周期复盘部署后第二轮修复方案

> 文档状态：第二轮已实施；第三轮已本地实施、待提交与部署验证
> 目标分支：`dev_codex`
> 运行基线：虚拟机 `/www/wwwroot/aurum-ai` / `3dc03cb98cba436ee2084a40b38327dd4a8be23c`
> 编制日期：2026-08-19

## 1. 结论与修复目标

提交 `3dc03cb9` 已正确部署，服务、数据库、Redis、静态资源和新模块版本均正常加载，但真实复盘没有达到验收标准：

1. case 291 的旧配额终态能够自动恢复，也能复用前四个成功分片；第 4 分片连续三轮返回不符合日复盘 v3 合同的结果，最终以 `invalid_daily_review_daily_lessons` 失败，没有生成版本。
2. 单分片请求仍约 1.27 MB、约 47 万输入 token。`daily-market-digest-v1` 只压缩了周期行情，完整事前快照仍反复携带系统提示词、用户提示词、策略运行快照、市场快照和 K 线。
3. case 292 仍保留旧的 `period_market_source_unauthorized`；新 `shared-canonical-v1` 已加载，但维护查询没有立即选中旧案例。
4. case 291 的证据也没有 `source_policy_version`。配额恢复发生在证据升级之前，导致旧证据和旧检查点继续参与新一轮生成。

本轮目标是修复“发现旧证据—重建证据—生成模型输入—验证 v3 输出—断点恢复—生成唯一版本”的完整状态链，而不是再次增加无边界重试。

## 2. 不变边界

- 不修改或补造原始信号、订单、成交、持仓、挂单、交易结果和经纪商历史。
- 订单及交易事实继续严格绑定真实用户和交易账号；只有标准市场 K 线允许使用平台可信共享源。
- 已存在 `current_version_id` 的用户可见版本保持不可变，不因政策升级静默重写。
- 复盘确认前不写入策略记忆库。
- 不通过 SQL 强行把证据标记为完整，不直接插入模型结果或复盘版本。
- 本方案不授权部署、服务器重启、手工重试或生产数据操作。

## 3. 根因修正

### 3.1 旧证据升级入口实际上不可达

`shouldUpgradePeriodMarketEvidence()` 能识别缺少 `shared-canonical-v1` 的证据，但调用它之前，案例必须先被 `eligibleOutcomeRows()` 选中。当前维护查询存在两个缺口：

- 已关联且 `evidence_status = complete` 的旧政策案例不会进入维护通道；
- 已关联但不完整的案例通常要等待 `updated_at` 超过一小时，政策升级不能在部署后立即触发。

因此“识别旧政策”的函数存在，但真实旧案例无法及时走到它。

### 3.2 配额恢复早于证据升级

现有流程先执行 `recoverDailyQuotaFailure()`，成功后立即返回；旧行情政策、旧证据哈希和旧分片计划没有重建。恢复任务随后复用了旧证据检查点，违反“重试必须使用同一冻结输入；输入政策变化必须创建新 revision”的状态机边界。

### 3.3 v3 输出错误落入旧版验证器

日复盘请求明确要求 `daily-period-review-v3`，但 `validateDailyReviewContent()` 在模型遗漏或改写 `output_contract_version` 时会回退到旧合同，并要求 `daily_lessons`。因此实际错误显示为 `invalid_daily_review_daily_lessons`，既误导运维，也让定向修复继续围绕错误合同进行。

### 3.4 输入压缩只处理了周期行情

`compactPeriodTradeEvidence()` 仍保存并向每个模型分片展开：

- `snapshot.system_prompt`；
- `snapshot.user_prompt`；
- `snapshot.strategy_runtime`；
- `snapshot.market_snapshot`；
- `snapshot.klines`。

这些字段是单分片约 47 万 token 的主要来源。供应商报告的大量 cached token 只影响计费或延迟，不降低上下文占用，也不能视为输入预算合格。

## 4. 修复设计

### 4.1 增加独立、受限的旧政策维护通道

在 `eligibleOutcomeRows()` 中增加 `policy_upgrade` 通道，专门选择同时满足以下条件的案例：

1. `current_version_id IS NULL`；
2. 存在关联的 `period_review_sources`；
3. `evidence_json.period_market.source_policy_version` 缺失或不等于当前政策；
4. 案例未被 supersede，且原始 outcome 仍符合复盘资格；
5. 没有正在使用同一证据 revision 的不可中断模型请求。

该通道不受普通“不完整证据一小时重查”限制，但必须：

- 每轮限制案例数，默认不超过 5 个；
- 按 case ID/更新时间稳定排序；
- 使用当前政策版本作为一次性升级标识；
- 只处理无用户可见版本的案例；
- 不挤占新产生复盘的 live lane。

普通行情暂时缺失仍保留原有退避；只有明确的政策版本升级可以立即进入维护通道。

### 4.2 调整状态转换顺序

`upsertDailyGroup()` 对既有案例按以下顺序处理：

1. 读取案例、证据、业务 job、模型任务和当前检查点状态；
2. 判断是否需要政策升级；
3. 如需升级，先重建周期行情和模型证据摘要；
4. 比较新的语义证据哈希；
5. 哈希变化时创建新的 evidence revision/幂等任务身份，使旧模型检查点失效；
6. 只有证据已是当前政策且完整时，才执行配额终态恢复；
7. 再由正常 worker 领取任务。

禁止在证据升级前恢复旧 job，也禁止新 evidence hash 继续使用旧 chunk task/checkpoint。

### 4.3 幂等重建旧案例

重建只允许更新派生层：

- 保持原 `period_review_cases.id` 和 outcome/source 集合；
- 重新生成 `period_market`、紧凑事前证据、证据哈希和政策版本；
- 写入 `evidence_upgrade_started/succeeded/failed` job event；
- 旧模型 task 和检查点保留用于审计，但不得再被新 revision 复用；
- 复用现有 job 时轮换幂等键、清空当前模型任务引用并重置业务尝试；
- 重复维护轮询在哈希和政策版本未变化时必须为 no-op。

case 291、292 只作为验收样本，不得在代码中硬编码 ID、账号或策略。

### 4.4 建立真正的事前证据摘要

新增 `compactPreTradeReviewEvidence()`，原始快照继续保存在服务端完整证据层，但模型分片只接收判断原始信号所必需的结构化字段：

- 信号 ID、品种、周期、方向、置信度、推理时间；
- 原始分析、推理理由、入场方式、入场价、止损、止盈；
- 当时策略 ID、版本、范围、内容哈希及受预算约束的有效规则正文；
- 风控决定、原始订单、批准订单；
- 各相关周期在推理时刻的指标和结构摘要；
- 每周期有限且确定数量的最近闭合 K 线；
- 原始快照引用、行情哈希和证据引用。

模型输入中移除：

- 完整 system prompt 和 user prompt；
- 重复的完整 `market_snapshot`；
- 无界全量 K 线；
- 与当前交易无关的运行期调试字段。

这不会删除审计证据：完整快照仍保存在数据库，只是不再逐分片发送给模型。原始信号的 `analysis/reasoning`、当时策略规则、指标摘要和局部 K 线共同用于判断“当时为什么下单、技术分析是否成立”。

### 4.5 强制输入预算

发送模型前计算实际序列化字节和估算 token：

- 单分片正文硬上限 500 KB；
- 单分片预计输入目标不超过 120,000 token；
- 单条交易过大时先压缩局部 K 线和重复策略上下文，不能只依赖继续拆 chunk；
- 多条交易超预算时再减少每 chunk 的 outcome 数量；
- 无法在保留交易事实后满足硬上限时，进入明确的 `period_review_input_budget_exceeded`，禁止向供应商发送必然失败的请求。

job event 记录 `request_bytes`、`estimated_input_tokens`、交易数量、市场摘要版本和事前摘要版本，不记录提示词或账号秘密。

### 4.6 v3 合同专用验证入口

拆分旧版兼容验证和 v3 验证：

- 新生成任务直接调用 `validateDailyReviewV3Content()`，绝不回退旧版 `daily_lessons` 合同；
- 如果模型仅遗漏 `output_contract_version`，但所有 v3 必填字段存在且没有旧字段，由服务端补入请求时已知的 v3 版本，并记录 `contract_version_normalized`；
- 如果返回明显的旧版结构，直接报 `invalid_daily_v3_contract_version`；
- 不允许通过添加 `daily_lessons` 将旧结构伪装成 v3；
- 定向修复提示必须引用 v3 缺失字段，最多一次供应商修复调用。

`invalid_daily_review_daily_lessons` 不得再出现在 v3 job 中。

### 4.7 限制重试并保留断点

- 业务尝试、供应商尝试和结构修复尝试继续分开计数；
- 同一 chunk 的一次业务尝试最多包含“首次生成 + 一次定向修复”；
- 已成功并且 evidence revision、plan hash、contract version 均相同的 chunk 可以复用；
- 政策版本、紧凑证据版本或输入哈希变化时，旧 chunk 全部失效；
- 相同 v3 合同错误重复出现时，达到业务上限后终止，不扩大 provider task 的隐式尝试次数；
- UI 显示准确的“第几分片、生成/修复/等待/终止”，不展示旧合同错误名。

## 6. 测试矩阵

### 6.1 旧证据升级

1. 已关联、证据完整、无版本、缺少当前政策版本：部署后立即进入升级通道。
2. 已关联、证据不完整、错误为旧来源身份冲突：不等待一小时即可升级。
3. 已有 `current_version_id`：保持不可变，不自动重建。
4. 升级后 outcome/source 集合完全不变。
5. 新证据哈希只创建或唤醒一个 job，不产生重复 case/version。
6. 重复轮询当前政策证据为 no-op。
7. 旧 job 为 quota failure 时，必须先升级证据，再执行恢复。

### 6.2 输入完整性与预算

1. 使用带超大 system/user prompt、完整市场快照和 1200 根 K 线的 12 笔夹具。
2. 每个真实 provider 请求正文小于等于 500 KB，预计输入小于等于 120,000 token。
3. 请求中不存在完整 system/user prompt 和无界 K 线数组。
4. 请求仍包含信号分析、推理理由、策略版本、技术指标摘要、局部 K 线、风控和订单事实。
5. 单条交易超过预算时先本地压缩，不生成一个仍超限的单交易 chunk。
6. 压缩前后逐笔 outcome 覆盖、成交事实和统计结果一致。

### 6.3 v3 合同与重试

1. 合法 v3 输出正常通过。
2. 仅缺少版本字段、其余为完整 v3：本地归一化，不追加模型调用。
3. 明显旧版输出：返回 `invalid_daily_v3_contract_version`，不要求 `daily_lessons`。
4. 缺少 v3 必填字段：最多一次定向修复。
5. 连续结构失败后业务尝试正确终止，provider attempt 不无限增长。
6. 相同 revision 重试只续跑失败 chunk；新 revision 不复用旧 chunk。
7. 最终成功只生成一个 AI version，并正确设置 `current_version_id`。

### 6.4 回归范围

- 日复盘准备、生成、重试、检查点、确认和记忆派生；
- 月复盘来源和检查点，确保日复盘改造没有破坏月复盘；
- 共享行情单源质量门禁；
- 前端状态和静态缓存版本；
- 模型任务容量、429 和进程重启恢复。

## 8. 两轮方案复审

### 第一轮：数据安全与状态机复审

发现风险：直接重置失败 job 会让新政策复用旧证据和旧检查点，也可能产生重复版本。

调整：先建立证据 revision，以政策版本、语义哈希和 plan hash 隔离旧任务；只有新证据完整后才恢复 job。已有用户可见版本不自动升级。

### 第二轮：分析质量与输入预算复审

发现风险：简单删除全部事前快照虽然能降 token，但会失去“当时为什么下单、采用什么技术分析”的核心证据。

调整：完整快照继续服务端冻结；模型接收信号原始分析、当时策略、指标摘要、有限局部 K 线、风控和订单事实。压缩删除的是重复载荷，不是业务证据。

## 9. 剩余风险

- 旧证据批量升级会产生模型任务峰值，必须限制每轮升级数量并服从模型容量调度。
- 指标摘要和局部 K 线窗口需要以真实策略周期回归，过短会影响技术判断，过长会重新放大输入。
- 模型仍可能拒绝 v3 合同；系统能限制浪费并给出准确终态，但不能保证外部模型每次合规。
- 行情源共享只能用于市场分析，不能替代经纪商成交价、点差和订单事实。
- case 291、292 的最终恢复需要部署后运行时证据；本地测试通过不能替代真实任务验收。

## 11. 第三轮完善范围（2026-08-19）

本轮只处理部署验证后确认的三个缺口，不扩大到行情来源政策、交易事实、月复盘合同或策略记忆结构：

1. 可恢复的行情证据缺失必须持久化 `next_attempt_at`，按 5、15、60 分钟退避，并在行情恢复后允许提前唤醒。
2. 前端必须显示“等待行情恢复”和明确的预计重试时间，不能把可恢复状态显示成静态失败、`skipped` 或无期限等待。
3. 日复盘分片必须去除重复的策略与记忆上下文，按最终模型请求体而不是仅按单笔证据大小装箱，显著减少逐笔模型调用。

这三个改动共享同一个边界：证据等待不消耗模型业务尝试，不创建复盘版本；输入压缩不能删除逐笔信号、技术分析、行情路径、成交结果及策略规则的可追溯依据。

## 12. 行情证据的持久化退避状态机

### 12.1 状态语义

可恢复的行情缺失不再写成终态：

- `period_review_jobs.status = 'queued'`；
- `progress_stage = 'evidence_retry_wait'`；
- `next_attempt_at` 写入下一次证据检查时间；
- `completed_at` 保持 `NULL`；
- `attempt_count` 不增加，因为尚未发生 provider 请求；
- `period_review_cases.evidence_status` 继续保持真实的 `incomplete`，不伪造为完整。

任务领取 SQL 已要求 `cases.evidence_status = 'complete'`，因此等待行情的 queued job 不会误进入模型生成。需要修改的是证据准备入口：已关联的不完整案例应以 job 的 `next_attempt_at <= NOW()` 为维护条件，不再依赖 case `updated_at` 满一小时。

### 12.2 可恢复原因分类

在服务端建立唯一的证据原因分类函数，不允许各调用点自行猜测：

- 可恢复：Bridge 暂时断开、历史请求超时、终端时钟暂不可用、可信源暂未覆盖目标窗口、缓存仍在补齐；
- 不可恢复：权限或归属不合法、冻结交易证据损坏、合同字段永久缺失、明确禁止的来源；
- `period_market_incomplete` 只是汇总状态，必须检查各周期的结构化原因后才能决定是否重试；未知原因默认失败关闭，不进入高频重试。

原始英文错误归一化为稳定代码写入 `last_error_code`，普通用户只看中文解释，管理员仍能看到代码和证据明细。

### 12.3 退避数据与算法

对 `period_review_jobs` 做加法式迁移：

- `evidence_retry_count INT NOT NULL DEFAULT 0`；
- `evidence_last_checked_at DATETIME NULL`。

继续复用现有 `next_attempt_at` 和 `last_error_code`，不新增另一套调度表。退避规则固定为：

- 第 1 次可恢复缺失：5 分钟；
- 第 2 次：15 分钟；
- 第 3 次及以后：60 分钟封顶；
- 可按 job id 增加不超过 30 秒的稳定抖动，避免同分钟大量唤醒。

证据恢复完整后，清空 `next_attempt_at` 和证据错误，保留累计次数作为审计信息，随后才允许模型 worker 领取。模型失败的 `attempt_count/max_attempts` 与证据检查次数始终分离。

### 12.4 行情恢复提前唤醒

在已成功持久化闭合 K 线之后发出轻量的“行情覆盖已更新”通知；不要在 Bridge 消息处理函数内直接生成复盘：

1. 新增一个无业务依赖的进程内唤醒模块，由行情持久化路径发布 `symbol/timeframe/source` 更新，由周期复盘注册监听。
2. 监听器只更新符合以下条件的 job：无当前版本、无活动 lease、非 `status_unknown`、属于可恢复行情错误、`next_attempt_at` 尚未到期。
3. 先以 case 所需品种/周期做窄匹配，再将 `next_attempt_at` 提前到当前时间并调用现有 `requestPeriodReviewCycle()`；真正的完整性仍由证据构建器重新校验。
4. 按 `source + symbol + timeframe` 做进程内防抖，并限制单次唤醒数量；服务重启后仍由数据库中的 `next_attempt_at` 兜底，不依赖事件是否送达。

这样行情恢复可以提前续跑，但事件丢失、进程重启或多实例竞争都不会丢任务或重复生成版本。

### 12.5 旧 `skipped` 兼容恢复

部署启动后的受限维护轮次仅转换满足全部条件的旧数据：

- 日复盘无 `current_version_id`；
- case 的确是可恢复的行情不完整；
- job 为旧 `skipped` 且 `next_attempt_at IS NULL`；
- 没有活动 lease、未知 provider 结果或禁用生成功能的原因。

匹配项幂等改为 `queued/evidence_retry_wait`，首次 `next_attempt_at` 为当前时间加稳定抖动。不得转换 `review_generation_disabled`、永久证据错误或已有版本的 job，也不得重置模型业务尝试。

## 13. 前端等待行情状态

### 13.1 展示契约

API 列表、详情和状态接口返回：`next_attempt_at`、`evidence_retry_count`、`evidence_last_checked_at`、规范化的 `last_error_code`。前端把 `queued + evidence_retry_wait + next_attempt_at` 映射为独立的 `evidence_retry_wait`，优先级规则为：

1. 已存在 `current_version_id` 时，版本结果权威，不显示等待横幅；
2. 可恢复行情等待显示“等待行情恢复”；
3. 到点进入证据准备时显示“正在重新检查行情”；
4. 只有不可恢复错误才显示“证据缺失/生成失败”。

等待卡片显示绝对时间和相对倒计时，例如“预计 11:25 再次检查（约 4 分钟后）”。倒计时归零只代表即将进入调度，不虚假宣称已经开始生成。

普通用户看到可操作的中文说明；管理员额外看到重试次数、上次检查时间和内部代码。页面在等待期间继续低频轮询，临近 `next_attempt_at` 时恢复正常轮询；失败终态仍停止轮询。

### 13.2 交互与缓存

- 行情提前恢复后，下一次轮询应自动从“等待行情恢复”切换到“准备证据/AI 分析”，无需 F5。
- 列表徽标、详情空态、进度卡和事件记录使用同一状态映射函数，避免不同区域互相矛盾。
- 更新前端静态构建标识和缓存契约测试，保证部署后不会继续加载旧状态文案。

## 14. 日复盘共享上下文去重与自适应分片

### 14.1 当前问题

当前 `buildDailyReviewChunkPlan()` 只累计每条 source 的字节数；真正请求时还会为每个 chunk 重复附加：

- 完整系统消息和输出合同；
- `system_statistics` 与 `period_market`；
- `current_optimization_context.strategy`；
- `current_optimization_context.strategy_memory_library`。

因此 12 笔交易可能形成 12 个独立 chunk，再加一次 merge。单请求虽然经过预算门禁，但总输入量、耗时和模型任务数量仍被重复上下文放大。

### 14.2 共享上下文的正确边界

不同 provider 请求之间不能假设存在会话记忆，也不能用模型无法解析的哈希替代必要文本。去重采用服务端确定性压缩和更合理装箱，而不是依赖 provider 缓存：

1. 构建一次 `daily_review_shared_context`，包含版本号、内容哈希、日统计、紧凑市场摘要以及从当前策略和统一记忆库确定性提取的规则索引。
2. 规则索引保留原文片段、稳定 excerpt id、适用品种/周期和来源版本；不调用额外模型做摘要，避免增加成本和幻觉。
3. 每个交易 chunk 只携带与该批交易证据匹配的规则片段，以及共享上下文哈希；不得每次重发整份策略和整份记忆库。
4. 最终 merge 接收已校验的 chunk 结论、统计事实、规则引用和共享上下文哈希，不再重发完整策略/记忆正文。
5. `strategy_conflicts` 的逐字引用仍由服务端拿 excerpt id 回查冻结原文校验，模型不能编造或引用未下发文本。

### 14.3 按最终请求体装箱

分片规划器改为增量构建候选请求，并对最终序列化 messages 同时检查 500 KB 和 120,000 预计输入 token：

- 基础成本包含 system message、输出 schema、共享字段和规则片段；
- 每加入一笔交易，都重新计算完整候选请求预算；
- 超预算时封箱，下一笔进入新 chunk；
- 单笔仍超预算时走已有的确定性证据压缩，压缩后仍超限则在 provider 调用前准确失败；
- `plan_hash` 必须包含共享上下文哈希、规则 excerpt ids、预算策略版本和 chunk outcome 集合，任一输入变化都不得复用旧检查点。

目标不是硬编码 chunk 数，而是在双预算内尽量装入更多交易。以当前 12 笔真实规模夹具为验收样本，期望从 12 个分析 chunk 降至不超过 4 个，再加 1 个 merge；若真实证据体积无法满足该数量，测试必须记录限制原因，但不能退回“一笔一任务”的固定策略。

### 14.4 质量保护

- 每个 outcome 必须恰好出现在一个 chunk，最终 merge 不得缺失或重复。
- 保留原始信号逻辑、技术依据、风险执行、入场至平仓行情路径和真实成交结果。
- 统计仍由后端计算，模型不得重算。
- 经验规则仍要求明确的条件、动作、风控、失效和禁止行为。
- provider 的 `cached_tokens` 只作为观测指标，不参与正确性或幂等判断。

## 17. 第三轮方案复审

### 第一轮：状态机与数据安全

发现风险：直接复用 `attempt_count` 会把 Bridge 离线误算成模型失败；直接把 job 改为 queued 又可能被生成 worker 提前领取。

调整：证据重试使用独立计数，job 虽保持 queued，但生成领取继续强制 `evidence_status = complete`；证据准备入口单独按 `next_attempt_at` 到期选择。可恢复等待不设置 `completed_at`，也不创建 provider task。

### 第二轮：输入质量与过度设计

发现风险：把共享上下文完全移出独立请求会让模型看不到策略规则；新增“上下文摘要模型”又会增加调用并引入幻觉。

调整：采用服务端确定性规则索引和逐字 excerpt，按交易相关性选择必要片段；merge 只使用已经验证的引用。分片按最终请求预算自适应装箱，不引入 provider 会话依赖或新的模型预处理阶段。

## 18. 剩余风险与明确不做项

- 极长且结构松散的策略正文可能难以稳定提取相关规则；需要用真实策略夹具验证 excerpt 召回率，并在召回不确定时宁可增加片段，不得静默丢规则。
- 多进程部署下进程内行情事件只能提供提前唤醒，数据库 `next_attempt_at` 才是最终可靠机制。
- 60 分钟是重试间隔上限，不代表永久放弃；案例保留策略沿用现有周期复盘清理政策，不能无限高频重试。
- 本轮不修改共享行情来源身份政策、不重写历史证据、不改变月复盘输出合同，也不增加人工“强制证据完整”入口。
- 本方案本身不授权迁移执行、服务器数据修复、任务重试、提交、推送、部署或重启。
