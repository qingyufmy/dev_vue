## 1. 文档定位

本文件是本轮从零重构的需求基线。后续新增或调整要求，先更新本文件，再进入产品设计、技术方案或实现。

本轮按以下方式重置上下文：

- 之前讨论过的具体 UI 稿、页面布局、主题方案和前端实现路线全部作废，不再作为实现依据。
- 之前选择过的其它前端组件框架全部作废。
- 保留当前系统已经存在的业务功能作为迁移清单，重构不得漏功能。
- AI 交易实验室当前功能以 [AI 交易实验室前端功能盘点](./ai-trading-lab-frontend-function-inventory.md) 为盘点基准；该文档只说明“有什么”，不约束新版“怎么设计”。
- 三套 Vue 前端的工程、组件、交互、响应式、性能和验收要求以 [Vue 前端重构需求规范](./vue-frontend-requirements-standard.md) 为强制标准。
- 三个子域的身份、会话、退出、WebSocket 和 Bridge 授权边界以 [单点登录与统一认证架构方案](./single-sign-on-authentication-architecture.md) 为强制标准。
- 数据库结构、UTC、事务锁序、查询预算、迁移校验、逐用户对账、回滚和旧表删除门以 [数据库规范化与全量数据迁移方案](./database-normalization-and-data-migration-plan.md) 与 [数据库逐表迁移矩阵](./database-table-migration-matrix.md) 为强制标准；165 张源表不得遗漏、重复或静默复制。
- HTTP API、浏览器实时通道和 Bridge 设备通信统一执行 [API V4、浏览器实时协议 V4 与 Bridge 设备协议 V4](./api-v4-and-realtime-protocol.md)，不得恢复浏览器 WebSocket RPC 或以旧路由命名新接口。
- 后端框架、模块边界、进程拓扑、后台任务、缓存、日志、指标和错误治理统一执行[后端目标架构与异步任务隔离方案](./backend-target-architecture.md)。
- 全项目阶段顺序、进入条件、确认规则和切换门以 [全量重构主路线图](./refactor-master-roadmap.md) 为唯一执行顺序。
- 主站和管理后台在正式设计前，也必须分别完成同等粒度的现有功能盘点。

## 2. 产品与用户定位

### 2.1 目标用户

核心用户是普通外汇交易者，而不是开发者、量化工程师或后台运营人员。

界面必须遵守以下原则：

- 使用交易者熟悉的概念和中文表达，避免用系统内部字段名直接面向用户。
- 首屏优先展示当前账户、连接、行情、持仓、风险和待处理事项。
- 常用操作直接可见，高级参数按需展开。
- 买入、卖出、平仓、撤单、修改保护参数等高风险动作必须明确对象、方向、数量和影响范围。
- 状态、错误、空数据、加载中、失联、延迟和权限不足必须有不同且清晰的反馈。
- 桌面、平板和手机均可正常完成核心任务；响应式设计不是桌面页面的简单缩放。
- 视觉可以现代化，但不得以装饰、动画或信息密度妨碍交易判断。

### 2.2 功能迁移原则

- 新版不要求复刻旧版布局和交互。
- 旧版已存在的有效功能必须全部进入迁移矩阵，并逐项确认去向。
- 可以合并重复入口、简化流程、重新命名和重新组织导航，但不能静默删除能力。
- 开始建立新版 Vue 工程时，`dev_vue` 中旧手写前端实现全部删除，不保留兼容页面、旧组件副本或双路由；需要核对旧版功能时只读参考 `D:\dev_codex\wall-street-skill-local`。功能盘点和迁移矩阵负责防遗漏，旧源码本身不作为新工程依赖。
- 每个功能都必须有明确的所属应用、所属业务模块、数据来源、权限和验收用例。

## 3. 三套前端的物理与业务边界

三套前端是三个独立应用，不是一个应用中的三个皮肤或三套路由前缀。

| 应用 | 生产域名 | 定位 | 独立要求 |
| --- | --- | --- | --- |
| 主站 | `www.<domain>` | 企业展示、课程、会员与面向客户的官网能力 | 独立入口、路由、登录、构建、部署和错误页 |
| AI 交易实验室 | `trade.<domain>` | 外汇交易者连接 MT4/MT5 后进行分析、交易、风控和复盘 | 独立入口、路由、登录、构建、部署和错误页 |
| 管理后台 | `admin.<domain>` | 平台运营、内容、用户、订单、模型和系统管理 | 独立入口、路由、登录、构建、部署和错误页 |

主站现有页面、课程、会员、支付、社区、通知、内容与账户能力以[主站现有功能盘点与迁移边界](./main-site-function-inventory.md)为迁移输入。

强制依赖规则：

```text
apps/www   ─┐
apps/trade ├──> packages/*
apps/admin ┘

禁止：apps/www <-> apps/trade <-> apps/admin
```

- 任何前端应用不得导入另一个应用的页面、业务组件、状态、路由或 API 模块。
- 登录态、权限、环境变量、路由守卫和部署配置分别维护；身份中心只统一认证，不替代各应用授权。
- 子域之间不依赖前端内存共享状态；跨域身份使用 Authorization Code + PKCE，各应用建立独立 Host-only 服务端会话。
- 一个应用构建或部署失败，不得阻塞另外两个应用的已有线上版本。
- 一个业务模块的改动默认只运行该模块与所属应用的测试；只有修改共享包时才扩大验证范围。

### 3.1 用户中心与设置页面边界

- 不再建设一个通用“用户中心前端”供主站、AI 交易实验室和管理后台通过 iframe 嵌入。
- 三个应用分别拥有符合自身任务的账户与设置路由、页面、加载状态和错误状态，禁止共享整页业务组件。
- 主站负责个人资料、会员、TRC20 支付、订单、返佣、课程进度、社区与主站通知。
- AI 交易实验室负责交易账户、Bridge、策略订阅、模型、交易偏好、交易通知和观摩模式；只展示完成当前交易任务所需的会员状态。
- 管理后台的管理员个人资料、安全设置、MFA 与会话管理，必须和平台用户管理、会员管理等运营页面分离。
- 可共享的只有服务端权威身份、会话、联系方式、角色、OpenAPI 合同、验证 Schema、无业务语义的 shadcn-vue 基础组件和设计令牌。
- 跨应用业务入口使用顶层页面跳转并依靠 SSO 保持体验连续；禁止 iframe、`postMessage`、父域 Cookie 或在应用之间传递 Token。
- `auth.<domain>` 只负责凭据、注册、恢复、MFA、安全挑战与统一登录会话，不作为第四个通用业务用户中心。

### 3.2 管理后台的网站与域名配置

- 管理后台必须提供按主站公开页面或路由键维护 TDK 的能力，至少包含页面标题 `title`、页面描述 `description` 和关键词 `keywords`；主站服务端渲染或预渲染时读取已发布版本，不能只在浏览器加载后修改。
- TDK 配置必须有默认值、页面级覆盖、草稿预览、发布版本、修改审计和回退能力；动态课程、文章等内容仍以内容自身 SEO 字段为主，页面模板配置作为兜底。
- 管理后台必须能配置平台主域名，以及主站、AI 交易实验室、管理后台和统一认证中心使用的完整域名或子域名，并提供格式、重复、协议和允许来源校验。
- 后台域名配置负责应用生成的链接、导航目标、Canonical URL、回调候选和公开配置；DNS、TLS 证书、反向代理和可信回调白名单仍是基础设施安全边界，未经独立校验和发布流程不得被一次普通表单保存直接改写。
- 域名变更采用“草稿 → 影响预览 → 安全校验 → 发布 → 审计”的流程；实施阶段必须提供旧域名过渡、会话影响说明和回滚路径。
- 管理后台正式加入：后台角色与操作级权限、配置变更中心、受控后台任务中心、管理员 MFA/会话安全、审计增强、集成健康、简化工单、异步数据导出、法律文本与同意记录、功能开关与发布治理、只读备份与迁移状态。
- `sitemap`、`robots`、重定向和失效链接检查组成的站点运营扩展本轮暂缓；这不取消页面 TDK、Canonical URL、分享元信息和域名配置。

## 4. 前端技术基线

### 4.1 已锁定选择

- 框架：统一使用 Vue 3；主站使用 Nuxt 4，AI 交易实验室与管理后台使用 Vue 3 SPA。
- 语言：TypeScript 严格模式。
- 构建：主站使用 Nuxt 4 的 Vite 构建链和混合渲染；AI 交易实验室与管理后台直接使用 Vite。
- 组件组织：Composition API、`<script setup>`、单文件组件。
- UI 组件体系：`shadcn-vue`，三套前端统一使用。
- 样式基础：Tailwind CSS 与语义化设计令牌。
- 图标：统一选择一套由项目 `components.json` 声明的图标库，业务模块不得自行混用。
- 专业行情图表可以使用专门图表组件；通用 UI 不得因此引入第二套通用组件库。

Vue 官方说明 Composition API 有利于逻辑复用、复杂组件的关注点组织和 TypeScript 推断，适合作为模块化应用的统一写法。`shadcn-vue` 官方明确说明它不是传统的运行时组件包，而是把组件源码交给项目维护。因此本项目采用“集中组件源 + 业务应用消费”的方式，不能让三个应用分别生成和修改三份组件源码。

### 4.2 建议目录

```text
frontend/
  apps/
    www/
      app/features/
    trade/
      src/features/
    admin/
      src/features/
  packages/
    ui/               # 唯一的 shadcn-vue 组件源和 components.json
    design-tokens/    # 颜色、字号、间距、圆角、阴影和动效令牌
    contracts/        # API/WebSocket 数据合同与生成类型
    api-client/       # 无业务状态的 HTTP/实时传输封装
    test-utils/       # 测试辅助，不包含生产业务逻辑
```

### 4.3 shadcn-vue 强制规则

- 新增 UI 前先检查 shadcn-vue 官方组件和已配置 Registry，存在组件时禁止手写同类控件。
- 业务页面只组合组件，不直接修改 `packages/ui` 中的基础组件来满足单页需求。
- `packages/ui` 的基础组件只允许做全局、可复用且经过评审的修改。
- 所有 shadcn-vue 组件只能通过统一 CLI 和 Registry 加入；禁止从网页或 GitHub 手工复制不受控代码。
- 更新组件前必须先执行 dry-run/diff，保留项目内有意修改，不允许无审查覆盖。
- 表单统一使用 `FieldGroup`、`Field`、对应输入组件和可访问性属性。
- 状态提示使用 `Alert`、`Badge`、`Progress`、`Skeleton`、`Spinner`、`Empty` 和 `sonner`，禁止重复手写。
- 对话框、侧滑面板、移动抽屉分别使用 `Dialog`、`Sheet`、`Drawer`；删除等危险操作使用 `AlertDialog`。
- 选项较少时使用 `ToggleGroup`，不得用一组按钮手写选中状态。
- 颜色只使用语义令牌和组件变体，不在业务页面散落原始色值或独立深色模式覆盖。
- `class` 主要负责布局；组件颜色、字号和交互状态通过变体与设计令牌控制。
- 图标、焦点、键盘操作、标题、加载态和空状态必须遵守组件的可访问性结构。
- 允许必要的语义 HTML、页面栅格和业务图表代码；“尽量不写原生代码”指不重复手写已有组件能力，不是禁止正常的 Vue 模板和业务逻辑。

### 4.4 模块边界

每个业务模块必须有公开入口，其余目录按实际需要创建：

```text
features/<feature>/
  index.ts
  routes.ts
  views/
  components/
  api/
  composables/
  model/
  schemas/
  __tests__/
```

- 禁止为了统一外观生成没有实际内容的空目录或占位文件。
- 模块只能通过公开入口导出能力，禁止跨模块深层路径引用。
- 页面组件只负责组合和用户交互；请求、缓存、业务计算和数据转换不得堆在页面中。
- 模块状态默认属于模块自身；只有确实跨页面共享的稳定状态才进入应用级状态层。
- 服务端合同先于页面实现；前端不得猜测字段、补造业务默认值或通过 UI 修复后端数据错误。
- 共享包不得包含主站、交易实验室或后台的具体业务判断。
- 共享包修改属于跨应用变更，必须运行三套应用的合同、类型、测试和构建验证。

## 5. 量见智桥需求边界

### 5.1 产品职责

量见智桥是小型终端桥接客户端，不是桌面版交易系统。

只负责：

- 发现并连接用户已启动的 MT4/MT5。
- 完成网站账号与本地终端的授权绑定。
- 接收服务器的精确数据请求，并返回对应终端数据。
- 接收经过服务端权限、策略、风控、额度和交易参数决策后的确定性交易命令，按协议原样调用终端执行；Bridge 不二次计算或收紧业务参数。
- 返回命令接收、终端调用、成功或失败、原始终端错误码和执行后实际资源状态；可能已经送达终端但无法确认时返回 `uncertain`，不得伪装成确定失败。
- 提供连接状态、版本、诊断日志和更新状态等最小客户端界面。
- 每个用户默认拥有 1 条 MT4/MT5 共用账户 WebSocket 并发连接额度，可单独购买额外并发额度；额度只计算当前在线账户连接，不限制历史或离线账户数量。Bridge Core 可管理多个相互隔离的终端档案，每个档案和独立 WebSocket 只连接一个账户，并允许新增、断开、删除和更换。

不负责：

- 策略分析、AI 推理、风险策略、复盘、报表或运营业务。
- 在本地复制策略、风控、会员、额度、品种白名单、手数上限、止盈止损、交易时段或其它服务器业务规则。
- 无请求地持续上传所有历史、所有 K 线或所有账户数据。
- 因网络抖动自动重复执行不确定的交易命令。

### 5.2 请求/响应模型

桥接协议采用“精确请求 + 精确响应 + 少量状态事件”：

```text
server request
  request_id
  action
  parameters
  deadline_utc
  protocol_version
  idempotency_key      # 交易命令必填

bridge response
  request_id
  status
  data | error
  observed_at_utc
  terminal_identity
  data_revision
```

允许主动上报的事件只保留必要状态：心跳、终端身份或能力变化、账户切换、时区变化、数据修订变化、交易执行回执和更新状态。其它数据由服务器按品种、周期、时间范围、票号、游标和字段精确请求。

MT4 与 MT5 使用相同的服务器合同和独立适配器，不把平台差异泄漏到上层业务模块。

并发连接额度与策略订阅按 [Bridge 并发连接额度与账户级策略订阅模型](./bridge-connection-quota-and-account-subscription-model.md) 执行：额度按系统用户跨设备统计当前有效账户 WebSocket；断开后释放，更换账户复用额度，同一稳定账户重连接管不双计数。策略订阅必须绑定具体交易账户，不再限制一个用户只能有一个活动订阅。额度判断只在服务端执行，Bridge 只根据服务端授权结果建立或拒绝公网会话。

K 线、交易订单、成交和资金事件等大体量终端数据按终端档案写入独立 SQLite。首次按有界时间片增量同步，之后使用时间与稳定票号游标补齐；服务端精确请求优先读取已覆盖的本地投影，缺失范围才唤醒对应终端。分页、帧大小、队列和磁盘水位属于传输与可靠性保护，不得被用来增加业务限制、静默截断数据或伪装完整结果。

Bridge 本地数据执行分级保留：未获服务端确认的命令、回执、Outbox、`uncertain` 对账和历史事实禁止按时间删除；已确认历史按保留期清理；K 线只缓存实际访问范围，并按数据年龄与最后访问时间淘汰；报价、心跳和当前未收 K 线以内存为主。清理只能由低优先级小批任务执行，必须避开活动游标、当前订阅、同步区间和交易队列，并在删除后修正覆盖范围。默认保留周期及档案删除宽限期以 Bridge V4 技术冻结方案为准。

### 5.3 Windows 7 兼容性结论

Windows 7 SP1 是硬性兼容目标，不能用“在开发机可运行”代替验收。

当前仓库 Rust 客户端使用 `x86_64-pc-windows-msvc`。Rust 官方当前把普通 Windows MSVC 目标标为 Windows 10+；继续支持 Windows 7 的 `x86_64-win7-windows-msvc` 是 Tier 3，官方不提供预编译产物，需要自行构建标准库并承担依赖兼容验证。因此现有 Rust 目标不能直接作为 Win7 兼容证明。

技术候选结论：

| 方案 | Win7 结论 | 维护与风险 | 当前建议 |
| --- | --- | --- | --- |
| Electron | Electron 22 是最后支持 Win7 的大版本，且早已结束支持 | 固定旧 Chromium/Node 带来长期安全与依赖风险 | 排除 |
| WebView2/Tauri 类 Web UI | 依赖旧版系统 WebView/运行时，长期支持和升级受限 | Win7 上难以保持现代安全运行时 | 排除为主方案 |
| 当前普通 Rust MSVC 目标 | 官方目标为 Windows 10+ | 现有构建不能证明 Win7 兼容 | 不直接采用 |
| Rust 专用 Win7 Tier 3 目标 | 理论可行，无官方预编译产物 | 工具链、依赖、TLS、安装和回归成本高 | 仅作对照原型 |
| .NET Framework 4.8 + WinForms | Microsoft 列出 Windows 7 SP1 32/64 位可单独安装 4.8 | 系统本身已停止支持，仍需 TLS、根证书和实机验证 | 首选兼容性原型 |
| Qt/C++ | 可做原生客户端 | 工具链、授权、部署和维护成本更高 | 备选 |

正式定型前必须完成两份最小原型，详细设计和历史证据见 [Bridge V4 Windows 7 架构、安装与更新技术冻结方案](./bridge-v4-win7-architecture-and-packaging-plan.md)：

1. `.NET Framework 4.8 + WinForms`：授权、独立 RFC 6455/TLS 传输、托盘、MT4 精简 EA、MT5 官方 Python Worker、自动更新和 Win7 SP1 实机冒烟。Windows 7 上禁止把框架自带 `ClientWebSocket` 当作可用实现。
2. Rust Win7 专用目标：核心连接、TLS、SQLite、更新器和 Win7 SP1 实机冒烟。

以稳定性、安装成功率、包体、开发维护成本和真实 Win7 结果选择最终方案。当前首选 `.NET Framework 4.8 + WinForms + MT4 精简 EA + MT5 官方 Python Worker + 本机命名管道 + Inno Setup`：MT5 不安装 EA，每个明确的终端档案使用一个隔离 Worker；固定 Python 仅作为内部无界面运行模块，不使用系统 Python、Python GUI、Nuitka/PyInstaller 或联网装包，也不引入 WebView。完整 Win7 实机矩阵通过前不宣布最终定型或已经兼容。

### 5.4 自动更新

普通用户必须能从现有安装自动升级，不要求重新下载安装。

- 启动器/更新器与业务 Core 分离，避免正在运行的程序覆盖自身。
- 更新包先下载到暂存目录，校验版本、大小、SHA-256 和项目签名后再激活。
- 激活采用版本目录与原子指针切换，启动健康检查失败自动回滚上一版本。
- 用户配置、授权、日志和可重建缓存与程序版本目录分离，升级不得覆盖。
- 协议版本、最低可升级版本和更新路径由签名清单声明。
- 迁移允许跨技术栈：旧版更新器下载并启动一次性迁移安装器，迁移成功后再切换到新版更新链。
- 自动更新失败必须保留旧版本可运行，并向用户提供明确原因和重试入口。
- 更新完成暂存后默认自动重启生效。Bridge 不读取、复制或推算自动分析计划；服务端负责避开自动分析触发点，并在签名更新通知中下发 `restart_not_before_utc_msc`。到达该时间后，只要当前档案不存在执行中的命令、`uncertain` 对账或关键数据写入，Bridge 即可原子切换版本并通过固定 Launcher 自动重启；否则继续等待空闲，不强杀终端、不丢弃回执。

### 5.5 客户端运行时依赖交付

- 普通用户不得被要求先自行检查或安装 `.NET Framework 4.8`。Bridge Bootstrapper 必须用注册表 `Release >= 528040` 检测 4.8 或更高版本，已满足时不重复安装。
- Bridge 下载页同时提供推荐的在线安装包和离线完整安装包；在线包缺少依赖时从 Microsoft 官方 HTTPS 下载并校验签名与 SHA-256，离线包内含官方 x86/x64 Runtime，不包含 Developer Pack。
- Windows 7 缺少 SP1/必要系统前置、依赖安装失败或要求重启时必须明确提示并支持安全续装，禁止降级到旧 .NET、TLS 1.0 或第三方下载镜像。
- 下载页可提供独立 `.NET Framework 4.8 Runtime` 官方下载入口用于故障排查，但普通安装主按钮必须完成依赖检测和引导，不能把责任转给用户。
- 运行时只在首次安装、修复或明确升级时处理；普通 Bridge 自动更新不得重复携带或重装 `.NET Framework 4.8`。未来提高最低运行时版本必须通过完整安装器和新的 Win7 兼容审查。

## 6. 数据、接口与隔离要求

### 6.0 数据库重构原则

- 当前 `dev_vue` 数据库是由最新测试虚拟机备份导入的只读迁移基线；未经明确授权不得在该库直接试改结构、修数据或删除旧表。
- 数据库统一存储 UTC，服务端数据库会话使用 `+00:00`，时间字段优先使用 `DATETIME(3)`；主站和管理后台显示北京时间，AI 交易实验室按终端时区显示。
- 迁移必须保留全部现有用户及业务数据，并按表、按用户和关键业务链路做数量、金额、状态、关联与抽样哈希对账。
- 新迁移必须不可变并记录校验和；大数据回填使用可暂停、可续跑、可审计的独立迁移任务，不得塞入服务启动迁移。
- 公网当前仍是旧版数据库结构。V4 必须保留从每个已识别公网旧版本到目标结构的完整可执行迁移链，不能只提供空库 baseline、开发库快照或最终建表 SQL；旧迁移、legacy ID map、回填 checkpoint 和对账规则属于上线能力，重构完成后也不得随旧前端/旧接口一起删除。
- “删除旧版代码”不等于删除迁移来源。应用切换后不继续运行旧业务接口或旧前端，但 migration runner 必须能够识别公网 `schema_migrations` 历史、验证校验和、续跑分块回填并完成一次性升级。
- 事务必须采用固定锁序，外部 HTTP、模型、Bridge 和 MT 调用不得放在数据库事务中；仅对幂等的完整事务提供有上限并带抖动的死锁重试。
- 新查询禁止 `SELECT *`，列表、详情和大字段载荷分层获取；历史和审计列表优先使用游标分页，并用真实数据量下的 `EXPLAIN ANALYZE` 和查询预算验收。
- 旧表、旧列和旧索引只有在功能迁移完成、逐用户对账通过、代码引用归零、恢复演练成功、回滚窗口结束且用户明确确认后，才能由独立迁移删除。

### 6.1 API 升级的定义

本轮 API 升级的主要目标是统一、标准化和规范化，不是重新发明现有业务。

- 现有有效业务能力和业务语义必须完整保留；接口升级不得成为删除功能或改变规则的理由。
- 统一 API 根路径、版本、资源命名、HTTP 方法、参数位置、响应结构、错误结构、分页、筛选、排序、权限、时间和幂等规则。
- 同一能力只保留一个权威接口；重复路径、历史别名、双前缀和重复实现完成迁移后删除。
- 主站、AI 交易实验室、管理后台和 Bridge 只暴露各自需要的接口面，不得直接依赖其它应用的业务接口。
- Bridge 只保留新版配对、授权、精确数据请求、确定性交易命令、状态诊断和自动更新接口；不得带入网站业务接口。
- 自动更新所必需的旧版发现或下载入口只可作为有期限的迁移通道，不继续承载新版业务。
- 规范化优先采用简单、稳定、可测试的实现；不得借 API 升级强行拆分微服务或增加无明确收益的中间层。

### 6.2 统一数据与传输规则

- HTTP 与实时协议使用统一、版本化合同；前端与 Bridge 由合同生成或推导类型。
- 业务模块只能通过自己的 API 门面访问后端，禁止页面散落 URL 和响应字段转换。
- 前端需要持续变化、主动更新且低延迟的数据使用 WebSocket；不需要实时更新的数据统一使用 HTTP API 精确获取。
- HTTP 是查询和写操作的权威入口：首屏快照、详情、分页、筛选、搜索、历史、配置、表单保存、交易命令和后台操作均通过 HTTP 完成，并使用权限、幂等和审计合同。
- WebSocket 只承担服务端到前端的实时增量与状态事件，不承载普通列表、历史查询、任意请求/响应 RPC 或浏览器业务写命令。
- 典型实时数据包括报价 Tick、当前 K 线增量与成交量、账户权益变化、持仓/挂单变化、Bridge 与市场状态、自动分析运行状态、新信号、信号执行状态、交易回执、风控告警和重要通知提示。
- 页面先通过 HTTP 获取带 `revision` 的一致快照，再订阅对应实时频道；WebSocket 只发送变化字段。重连、修订缺口或作用域切换时，前端精确重拉受影响资源，禁止全应用刷新。
- 倒计时由服务端下发 `next_run_at` 或截止时间后在前端计算，不每秒广播；历史 K 线通过 HTTP 获取，只有正在形成的 K 线和成交量通过 WebSocket 增量更新。
- 实时消息带账户、终端、模块、修订号和时间语义，前端不得把不同账户的数据混合。
- 请求和命令必须有超时、取消、幂等和重复响应处理。
- 任一模块加载失败只影响该模块，应用壳层、其它路由和已缓存模块保持可用。

### 6.3 单点登录与应用会话

- 新增 `auth.<domain>` 作为统一身份中心，集中处理登录、注册、验证码、找回密码、MFA 和账号恢复。
- `www`、`trade`、`admin` 保留独立登录入口和回调地址，通过 OpenID Connect Authorization Code Flow + PKCE 获取身份，不在应用间传递 Token。
- 三个应用分别使用不设置 `Domain` 的 `Secure`、`HttpOnly`、`SameSite=Strict` Host-only Cookie；禁止父域共享认证 Cookie。
- 浏览器不得把访问令牌或刷新令牌写入 Local Storage、Session Storage、IndexedDB、URL 或 JavaScript 可读 Cookie。
- 浏览器只调用当前应用同源 API；后端逻辑 BFF 根据服务端会话完成身份注入和权限校验，不为三个应用强制拆分微服务。
- 单点登录只统一系统用户身份；管理员角色、会员、交易账户归属、观摩权限和资源权限仍由各接口独立校验。
- `trade` WebSocket 使用当前会话签发的短时单次连接票据；Bridge 继续使用独立设备配对和刷新会话，不复用浏览器 SSO。
- 退出分为当前应用、全部网站和全部设备三种范围，避免普通退出误断 Bridge。
- 当前客户端可读 JWT 只作为旧版迁移来源；新版切换时允许用户重新登录一次，不把旧 JWT 自动兑换成新会话。

具体接口、两张新增表、迁移顺序、回滚和验收见 [单点登录与统一认证架构方案](./single-sign-on-authentication-architecture.md)。

### 6.4 后端与后台任务隔离

- 后端采用同一代码库内的模块化单体，业务域通过公开应用端口协作；不得把跨域 SQL、路由处理器调用或内部 HTTP 自调用作为模块协作方式。
- HTTP API、浏览器实时网关、Bridge 设备网关、调度器和后台 Worker 必须是独立运行角色。HTTP API 与两个网关进程禁止启动业务定时器、轮询器或后台任务消费者。
- 所有后台任务必须异步提交并由独立 Worker 处理；接口只完成权限、参数、幂等、事务落库和任务登记，不等待 AI、通知、复盘、支付副作用、清理或批量导出完成。
- 不同风险等级的任务使用独立队列和独立 Worker 进程组。交易执行与对账、AI 分析与模型调用、复盘记忆、支付会员、通知集成和维护清理不得共享一个无限并发任务池。
- 队列采用至少一次投递语义；每个任务必须有确定性幂等键、可恢复状态、超时、有限重试、退避、死信或人工处理入口。禁止以“只会执行一次”为前提编写副作用。
- 交易、支付、会员等关键业务必须在同一 MySQL 事务中写入业务状态与 outbox；队列只负责唤醒，不得成为唯一业务真相。
- 自动信号、手动交易、策略订阅者分发、持仓/挂单管理和管理员交易命令必须进入同一个 execution 应用域；公共操作、执行意图、Bridge 命令和终端资源分别维护有限状态，具体以 [交易执行统一状态机](./trade-execution-state-machine.md) 为准。
- 一旦命令可能已经送达 MT，任何超时、断线、进程退出或数据库异常都必须进入 `uncertain` 并对账，禁止自动重发；批量父操作使用 `partially_succeeded` 明确表达部分成功。
- CPU 密集型任务必须使用受限的线程池或隔离子进程，禁止占用 API、浏览器实时网关或 Bridge 网关事件循环。
- 每个运行角色使用独立且有总量预算的数据库连接池和 Redis 连接；队列 Redis 与可淘汰缓存必须使用不同实例或具备等价的资源与淘汰策略隔离。
- 后台任务故障不得导致 API、浏览器实时通道、Bridge 通道或其它任务组退出；进程管理器只重启失败的运行角色。

## 7. 实施顺序

详细阶段、状态与完成门统一见 [全量重构主路线图](./refactor-master-roadmap.md)。每个阶段开始前必须先介绍范围、交付物、风险和验收条件，并等待用户明确确认；上一个阶段的确认不得自动延续。

管理后台当前能力、TDK/域名目标、候选新增功能和暂缓项见[管理后台现有功能盘点与目标能力建议](./admin-function-inventory.md)。候选新增功能在用户确认前不视为冻结需求。

三个前端、后端、数据库和 Bridge 的功能归属、HTTP/WebSocket 分工、时间、权限和验收边界统一见[全项目功能迁移总矩阵](./full-project-function-migration-matrix.md)。

1. 完成主站、交易实验室、管理后台三份现有功能盘点和迁移矩阵。
2. 在功能盘点和迁移矩阵冻结后，先删除 `dev_vue` 中旧手写前端，再从空目录建立 Nuxt 主站、两套 Vite SPA、包依赖边界、合同包和 CI 边界测试；旧界面只从独立参考仓库只读核对。
3. 建立唯一 shadcn-vue 组件源、设计令牌、组件 Registry 和示例页。
4. 建立统一身份中心、应用独立会话和迁移表；先以 `trade` 完成登录、HTTP、WebSocket 端到端竖切。
5. 先做真实数据合同与一条交易业务端到端竖切，再按业务模块逐一迁移。
6. 每个模块完成设计、实现、模块测试、所属应用构建和多终端验收后再进入下一模块。
7. 并行完成 Bridge 两个 Win7 原型和自动更新迁移验证，原型通过后冻结客户端技术栈。
8. 旧前端在新版前端骨架建立前删除；旧接口、旧客户端实现和旧数据库结构则必须等功能迁移、数据迁移、回归、灰度及回滚窗口完成，并经用户逐项确认后再清理。任何阶段都不得删除、改写或压缩已经发布或用于公网旧库升级的迁移文件。

## 8. 验收门

### 8.1 前端

- 三个子域可独立安装依赖、测试、构建和部署。
- 主站公开内容可预渲染或服务端渲染；交易实验室和管理后台保持纯客户端应用，不承担无收益的 SSR。
- 应用之间无源码级业务依赖。
- 所有交互控件优先来自统一 shadcn-vue 组件源。
- 组件状态覆盖默认、悬停、聚焦、禁用、加载、空、错误和成功。
- 普通交易者无需了解系统内部结构即可完成核心流程。
- 桌面、平板和手机没有横向溢出、遮挡或不可达操作。
- 模块级变更通过依赖边界测试，未修改应用的构建产物不发生非预期变化。
- 单点登录后跨应用无需再次输入密码，但三个应用 Cookie 和权限保持隔离，浏览器存储中不存在长期 Token。

### 8.2 Bridge

- Windows 7 SP1、Windows 10、Windows 11 的目标位数均完成实机矩阵。
- MT4 与 MT5 分别通过连接、读数据、账户切换、断线恢复和受控交易命令测试。
- 数据按请求范围返回，不出现无界全量同步。
- 交易命令重复投递不会重复成交，不确定结果不会自动重放。
- 自动更新可升级、失败回滚并保留用户配置。
- 桥接进程退出、更新或崩溃不得关闭 MT4/MT5。

## 9. 第一轮方案复审

复审范围：需求覆盖、业务边界、现有能力复用、最小实现和是否过度设计。

结论与调整：

- 已覆盖三前端独立、模块隔离、shadcn-vue 统一、普通交易者定位、Bridge 精确请求、Win7 和自动更新。
- 为避免把“统一组件”做成三套副本，补充了唯一 `packages/ui` 组件源和禁止应用互相引用的边界。
- 为避免组件框架和专业图表冲突，明确通用 UI 只使用 shadcn-vue，行情图表允许专用组件。
- 为避免从零重写时漏功能，保留功能盘点作为迁移输入，但不保留旧 UI 方案。
- Bridge 不在方案阶段继续扩展本地业务，只保留数据、执行、诊断和更新，符合最小职责。
- 三应用原统一直接使用 Vite 会忽略主站 SEO 与内容首屏需求，调整为 Nuxt 主站和两套 Vite SPA，仍保持单一 Vue 生态。
- 单点登录没有拆分认证微服务或增加动态客户端平台，只在现有后端中增加统一认证模块、两个数据表和三个逻辑会话边界。

剩余风险：主站和管理后台尚未形成同等粒度的功能盘点；Bridge 当前已有大量能力，最终是复用核心还是重写，需要原型和代码审计后决定。

## 10. 第二轮方案复审

复审范围：兼容性、数据与迁移、并发与幂等、异常恢复、时间语义、安全、测试、回滚和连带 Bug。

结论与调整：

- 发现当前普通 Rust Windows 目标不能作为 Win7 证明，已增加 Rust 专用目标与 .NET Framework 4.8 的双原型门，禁止凭假设定型。
- 自动更新补充签名校验、版本目录、原子切换、健康检查、回滚和跨技术栈迁移路径。
- Bridge 合同补充 `request_id`、截止时间、协议版本和交易幂等键，避免重连或重复投递导致重复操作。
- 前端补充合同包、账户/终端/修订隔离、取消和重复响应处理，降低实时数据串号风险。
- 删除旧实现被推迟到功能、数据、更新和回滚全部验收之后，避免迁移期间失去可恢复路径。
- 共享组件包仍可能成为跨应用影响面，因此共享包变更必须触发三应用验证，业务功能不得进入共享包。
- 子域共享 Cookie 会扩大管理后台风险，改为 OIDC Code + PKCE 和每应用 Host-only 会话；同时补充 CSRF、精确 Origin、WebSocket 单次票据与三种退出范围。
- 旧 JWT 不自动兑换新会话，切换时允许用户重新登录一次，避免把可读长期令牌风险带入新架构。

剩余风险：Windows 7 已停止系统支持，TLS、根证书、代理环境和第三方依赖可能成为实机阻塞；shadcn-vue 是源码分发模式，若缺少统一 Registry 和升级审查，仍可能产生组件分叉。

### 2026-09-02：前端 HTTP 与 WebSocket 分工

- 范围：www / trade / admin / backend / bridge
- 要求：前端需要实时更新的数据走 WebSocket，其它数据走 HTTP API；具体数据由功能迁移总矩阵逐项判定。
- 影响：HTTP 负责快照、查询、历史、配置和所有写操作；WebSocket 只推送实时增量、状态变化和结果通知。浏览器不通过 WebSocket 执行业务写命令。
- 是否改变既有基线：否，是对“高频增量走实时、精准查询走 HTTP”的进一步冻结。
- 待确认项：具体事件名称、负载 Schema、频道粒度、保留/重放窗口和带宽阈值在 API V4 与实时协议 V4 阶段冻结。

### 2026-09-02：后端框架与异步任务隔离

- 范围：backend / database / bridge / www / trade / admin
- 要求：所有后台任务异步执行，且不能影响主进程或其它任务。
- 影响：后端目标冻结为 Node.js 24 LTS + TypeScript + Fastify 的模块化单体；HTTP API、浏览器实时网关、Bridge 网关、scheduler 和后台 Worker 分进程运行，后台任务再按交易、AI、复盘、支付、通知和维护分组隔离。
- 是否改变既有基线：是，明确废止在 API/网关进程内用业务定时器直接运行后台任务的方式。
- 待确认项：具体并发、连接池、超时和告警阈值由后续压力测试与故障演练确定；交易任务的严格状态机在阶段 6 冻结。
- 部署补充：正式环境继续使用宝塔 Node 项目管理，注册一个 `aurum_ai` PM2 项目并以 `ecosystem.config.cjs` 管理所有独立运行角色；不把每个 Worker 建成一个宝塔项目。

### 2026-09-02：Bridge 并发连接额度与账户级策略订阅

- 范围：trade / bridge / backend / database / commerce / admin
- 要求：每个系统用户默认支持 1 条 MT4/MT5 账户 WebSocket 并发连接，可单独购买额外并发额度；额度只计算当前在线连接，交易账户可以自由新增、删除和更换，并能为不同账户配置不同策略订阅。
- 影响：原“普通用户一个客户端只连接一个本人账户”改为“每个终端档案、Worker 和 WebSocket 只连接一个账户，一个客户端可按额度同时运行多个隔离档案”；额度按用户跨设备统计当前有效账户 WebSocket，MT4/MT5 共用，断开即释放；订阅以 `user_id + trading_account_id + strategy_id` 为基本作用域。
- 是否改变既有基线：是，扩展普通用户 Bridge 多账户能力，但不放宽同一交易账户单一可交易 route、幂等、归属和隔离要求。
- 待确认项：额外并发额度的永久/期限产品、单用户并发上限、额度减少宽限期、价格和返佣规则在商业实施阶段冻结。
