# 策略记忆库 UI 重构方案

## 1. 目标

将现有策略记忆库从“横向堆叠的配置面板”重构为以 Markdown 文档为中心的专业工作台，同时保留现有统一记忆库、版本、冲突、一致性检查和整理压缩业务合同。

本次只调整用户端与统一管理后台的界面结构、视觉层级、文案和前端交互反馈，不修改 API、数据库、记忆沉淀、冲突证据阈值、压缩语义或一致性检查逻辑。

## 2. 设计依据

- 沿用 `DESIGN.md` 的深蓝黑工作面、稀缺协作金和中文优先原则，不采用技能库建议的紫色通用 AI 配色。
- 采用内容优先、克制密集的产品工作台风格，不使用装饰性玻璃、霓虹、渐变文字和多层嵌套卡片。
- 以 WCAG 2.1 AA 为基线：键盘焦点可见，状态不只依赖颜色，主要控件在窄屏不低于 44px，动画支持 `prefers-reduced-motion`。

## 3. 信息架构

### 3.1 工作台顶部

- 左侧保留唯一的策略选择器，明确显示平台或私有范围。
- 右侧不再横向塞入全部信息，只显示当前版本和总体健康结论。
- 达到提醒阈值的策略冲突使用独立告警区，说明“只提醒，不自动修改策略”。

### 3.2 桌面主区

采用双栏布局：

- 主工作面：默认显示安全 Markdown 预览；切换“编辑原文”后显示完整 Markdown 编辑器。
- 维护侧栏：集中展示容量、整理压缩、一致性检查、冲突计数和相应动作。

主工作面中的记忆块使用文档分节，而非重复卡片。只有冲突块才使用红、橙、灰语义背景，并同时显示图标和中文状态。

### 3.3 编辑模式

- 模式名称使用“阅读预览 / 编辑原文”，避免“查看原文”与可编辑能力不匹配。
- 明确显示当前编辑的是唯一完整记忆库，新保存会形成可恢复版本。
- 保存新版本是该模式唯一主操作；取消编辑返回已保存预览。
- 未保存草稿、整理任务进行中和版本冲突继续沿用现有保护逻辑。

### 3.4 冲突与历史

- “只看冲突”仅在预览模式展示，并作为标准筛选开关。
- 冲突详情保留人工处理、忽略和重新打开动作；达到阈值、观察中、定位失效必须有非颜色文字。
- 版本历史继续渐进披露，不抢占当前文档的阅读层级。

### 3.5 异步反馈

- 整理压缩和一致性检查显示运行状态、简短解释和下一步动作。
- 活跃任务使用轻量旋转状态图标或状态点，不让整个面板闪烁。
- 按钮在请求中禁用并显示处理中状态，终态刷新正文但继续保护未保存草稿。

## 4. 响应式

- `>= 1040px`：主文档与约 300px 维护侧栏并列。
- `< 1040px`：侧栏移到文档上方，状态卡变为自适应行。
- `< 720px`：策略选择、模式切换、筛选与动作改为单列或整行；控件高度至少 44px；正文不产生横向滚动。

## 5. 实现范围

- `public/ai/app.js`：重组用户端记忆库标记结构和中文文案，保留既有 data attributes、轮询与 API 行为。
- `public/ai/styles.css`：新增工作台布局、文档排版、状态侧栏、冲突语义、编辑模式与响应式样式。
- `public/admin/app.js`、`public/admin/styles.css`：保持平台策略记忆管理与用户端同一交互模型。
- `public/ai/index.html`、`public/admin/index.html`：更新静态资源缓存键。
- `tests/ai/frontend-governance.test.js`：补充新结构、无障碍、响应式与既有契约回归。

## 6. 受保护合同

- 每个策略始终只有一个完整、可编辑、可版本恢复的 Markdown 记忆库。
- 预览 HTML 继续只使用服务端安全渲染结果。
- 冲突仍由服务端绑定精确记忆块；前端不得自行推断或修改冲突。
- 系统不得自动修改策略；冲突达到服务端阈值后只提醒人工处理。
- 整理压缩、一致性检查、保存、恢复、草稿保护、轮询和错误映射不得改变。
- 不引入新的前端框架、远程字体或图标体系。

## 7. 第一轮复审：需求与设计边界

### 检查结论

- 覆盖默认预览、原文编辑、冲突高亮、压缩反馈、一致性检查、版本历史和管理端一致性。
- 复用现有服务端预览、冲突绑定、轮询和恢复机制，不新增后端或数据模型。
- 原设想将多个状态都塞进顶部工具栏，会继续造成视觉竞争，已调整为主文档加维护侧栏。
- 冲突块若只用红色背景不满足可访问性，已增加图标、状态文字和详情。
- 不采用通用紫色 AI 设计系统，优先遵守 AURUM 已提交的金色品牌系统。

### 调整

- 将“查看原文”改为“编辑原文”。
- 增加“取消编辑”入口，避免只能通过切换 tab 离开编辑模式。
- 将版本历史保持为折叠区，避免挤占阅读空间。

## 8. 第二轮复审：兼容性与异常恢复

### 检查结论

- 所有现有选择器、action、conflict、restore data attributes 必须保留，因此无需修改事件和 API 合同。
- 切换策略时继续执行未保存草稿确认；压缩完成时仍不得覆盖脏编辑器。
- 活跃任务按钮继续禁用；失败、过期、未知状态继续保留原记忆并给出可重试入口。
- 预览加载失败仍可进入编辑原文，不形成不可恢复死路。
- 管理端与用户端复用同名结构和视觉规则，但保持各自按钮组件类名，避免跨前端依赖。
- 静态缓存键必须同步更新，避免部署后仍加载旧 CSS 或 JS。

### 调整

- 侧栏不使用 `position: sticky` 作为关键可用性前提，窄屏和嵌套滚动环境仍可正常操作。
- 动画仅作用于运行状态图标和 150–220ms 状态过渡；减少动态偏好下全部关闭。
- 不新增自动保存，避免改变现有显式版本语义。

### 剩余风险

- 超长 Markdown 的整体渲染性能仍取决于现有服务端分块数量，本次不引入虚拟列表，以免破坏锚点和冲突定位。
- 管理端与用户端是两套静态前端，结构保持一致仍需要双份回归测试。

## 9. 验收标准

- 1440px、1024px、768px、375px 下无横向溢出，操作区不遮挡正文。
- 默认进入阅读预览；编辑原文可修改并保存，取消编辑不写入服务端。
- 冲突块在正文中具备红/橙/灰状态、图标和文字；只看冲突可用。
- 压缩与一致性检查进行中有可见动画和中文阶段反馈，减少动态模式下无动画。
- 键盘可操作所有 tab、按钮、选择器、筛选和折叠区，焦点清晰。
- 用户端与管理端定向前端测试、JavaScript 语法检查和浏览器实测通过。
