# Vue 前端重构需求规范

> 状态：强制执行
>
> 版本：1.1
>
> 建立日期：2026-09-01
>
> 最近更新：2026-09-02
>
> 适用应用：`www`、`trade`、`admin`

## 1. 目的

本规范把“全面模块化、统一使用 shadcn-vue、符合普通外汇交易者习惯”转换为可以检查、测试和验收的工程规则。

关键词含义：

- **必须**：不满足即不得合并或进入下一阶段。
- **应该**：默认遵守；偏离时必须在变更说明中给出理由和验证证据。
- **可以**：按模块需要选择，不得为了预留未来能力提前增加代码。

本规范只约束新版 Vue 前端。旧页面仅作为功能盘点和数据行为参考，不作为代码、布局或组件实现参考。

## 2. 锁定技术基线

| 范围 | 统一选择 | 约束 |
| --- | --- | --- |
| 前端框架 | Vue 3 | 禁止新增 Vue 2、React 或其它页面框架 |
| 语言 | TypeScript 严格模式 | 生产代码禁止用 `any`、双重断言或关闭类型检查逃避合同问题 |
| 应用框架 | `www` 使用 Nuxt 4；`trade`、`admin` 使用 Vue 3 SPA | 统一 Vue 生态，按内容站与高交互应用分别选择渲染方式 |
| 构建 | Nuxt 4 的 Vite 构建链 / 直接 Vite | 三个应用分别配置、构建和输出 |
| Vue 写法 | Composition API、`<script setup lang="ts">`、SFC | 不混用 Class API；Options API 仅限有证据的第三方兼容边界 |
| 路由 | Vue Router | 每个应用独立路由表和守卫 |
| 服务端状态 | TanStack Query for Vue | 请求、缓存、失效、取消和重试集中管理 |
| 客户端状态 | Pinia | 只存真正跨页面的客户端状态，不复制服务端响应 |
| UI 组件 | shadcn-vue | 通用控件不得再引入第二套组件库 |
| 组件基础 | Reka UI | 与当前 shadcn-vue 官方 CLI 基础保持一致 |
| 样式 | Tailwind CSS、CSS 变量、语义设计令牌 | 禁止业务页面散落原始品牌色和独立暗色覆盖 |
| 表单 | shadcn-vue 表单组件、VeeValidate、Zod | 表单结构、前端校验和 API 合同保持一致 |
| 图表 | 专业行情图表与 shadcn-vue Chart 按职责选择 | 专业图表库不得扩展为第二套通用 UI 系统 |
| 包管理 | pnpm workspace | 三应用和共享包使用单一锁文件、精确依赖版本 |

未冻结项：视觉 preset、字体、图标库、主色和专业行情图表库。它们必须在设计系统原型阶段统一选定；选定后写入唯一 `components.json` 和设计令牌，三个应用不得各自更换。

## 3. 应用和依赖边界

### 3.1 独立应用

```text
frontend/
  apps/
    www/                 # Nuxt 4，公开内容使用 SSR/SSG/Hybrid
    trade/
    admin/
  packages/
    ui/
    design-tokens/
    contracts/
    api-client/
    test-utils/
```

三个应用必须分别具备：

- 入口文件、路由、登录页、错误页和应用壳层。
- 环境配置、构建配置、测试配置和部署产物。
- 权限守卫、API 门面和业务功能模块。
- 独立失败边界；一个应用构建或运行失败不得影响另外两个已部署应用。

渲染边界：

- `www` 公开首页、课程、分类、企业展示和需要搜索引擎收录的页面使用 Nuxt 预渲染、SSR 或按路由缓存。
- `www` 登录后的高度动态区域可以按路由使用客户端渲染，不为了形式统一强制 SSR。
- `trade`、`admin` 使用 Vite SPA；行情、图表、WebSocket、表格和表单不得引入无收益的服务端渲染与水合复杂度。
- `packages/ui` 保持纯 Vue，不导入 Nuxt API；只有主站的应用适配层可以使用 `ClientOnly`、SSR 宽度或 Nuxt 专用能力。

禁止：

- `apps/www`、`apps/trade`、`apps/admin` 之间任何方向的源码导入。
- 通过全局变量、同页内存、DOM 或浏览器事件隐式共享跨子域业务状态。
- 把后台页面放进交易实验室路由，或把交易业务组件放进主站。

### 3.2 共享包

共享包只允许包含稳定基础能力：

- `ui`：唯一 shadcn-vue 基础组件源。
- `design-tokens`：语义颜色、字体、间距、圆角、阴影、层级和动效令牌。
- `contracts`：HTTP、WebSocket 和 Bridge 的版本化类型与校验合同。
- `api-client`：无页面状态、无业务判断的传输封装。
- `test-utils`：测试工厂和测试辅助。

共享包禁止包含：

- 主站、交易实验室或后台的业务规则。
- 某个页面的查询组合、权限判断或显示文案。
- 交易方向、风控结果、策略结论等业务推导。
- 只被单个功能使用、却为了“以后可能复用”提前抽取的代码。

修改共享包属于跨应用变更，必须验证三个应用；修改应用内功能模块不应改变其它应用的构建产物。

## 4. 功能模块规范

### 4.1 最小模块结构

```text
features/<feature>/
  index.ts
  routes.ts              # 有独立路由时创建
  views/                 # 有页面时创建
  components/            # 有模块私有组件时创建
  api/                   # 有后端交互时创建
  composables/           # 有可复用状态逻辑时创建
  model/                 # 有非平凡业务状态或转换时创建
  schemas/               # 有模块输入或合同扩展时创建
  __tests__/             # 与真实模块结构就近组织
```

- `index.ts` 是模块唯一公开入口。
- 除 `index.ts` 外，其它目录按实际需要创建，禁止生成空目录和占位文件。
- 模块之间只能从公开入口导入，禁止深层路径穿透。
- 一个模块不能直接写入另一个模块的 Store、Query Cache 或浏览器存储。
- 跨模块协作通过明确的应用编排层、合同或公开服务完成，禁止无类型全局事件总线。

### 4.2 页面职责

页面 View 只负责：

- 读取路由参数。
- 组合模块组件。
- 触发公开用例。
- 呈现加载、空、错误、权限和正常状态。

页面 View 不负责：

- 直接拼接 URL 或解析不稳定响应。
- 直接创建 WebSocket。
- 编写大段业务计算、订单计算或数据清洗。
- 在组件挂载时复制整份服务端数据到 Pinia。
- 通过大量 watcher 互相同步相同状态。

## 5. shadcn-vue 组件规范

### 5.1 唯一组件源

- 全项目只保留一个权威 `components.json` 和一个 `packages/ui` 组件源码目录。
- 三个应用通过包入口使用相同基础组件，不复制组件文件。
- shadcn-vue 是源码分发体系；基础组件源码视为共享基础设施，不是业务页面的自由修改区。
- 业务差异优先通过属性、slot、variant 和组合实现，不为单页需求修改基础组件默认行为。

### 5.2 官方 CLI

必须使用项目包管理器调用官方 Vue CLI：

```text
pnpm dlx shadcn-vue@latest info
pnpm dlx shadcn-vue@latest search @shadcn-vue -q "<component>"
pnpm dlx shadcn-vue@latest docs <component>
pnpm dlx shadcn-vue@latest view <component>
pnpm dlx shadcn-vue@latest add <component>
```

- 添加组件前必须先查看项目 `info`、已安装目录和官方文档。
- 禁止用 React 版 CLI 代替 `shadcn-vue` CLI。
- 禁止从博客、截图或 GitHub raw 地址手工复制组件。
- 社区 Registry 必须明确来源、版本或提交、许可证和依赖；引入前先审查源码。
- 更新已有组件必须先比较差异；未经明确审查不得 `--overwrite`。
- 组件批量升级必须作为独立变更，不和业务功能修改混在同一批次。

### 5.3 组件优先级

业务实现按以下顺序选择：

1. 已安装的 shadcn-vue 组件。
2. shadcn-vue 官方 Registry 组件。
3. 已批准并固定版本的社区 Registry 组件。
4. 组合现有组件形成模块私有组件。
5. 只有前四项无法满足时，才允许编写新的交互控件。

允许使用原生语义 HTML 完成文档结构、布局容器和图表承载；禁止在已有组件可满足时手写 Button、Input、Select、Dialog、Drawer、Tabs、Table、Toast、Skeleton、Empty、Badge 等交互或状态控件。

### 5.4 组合和样式

- 优先使用组件现有 variant 和 size，再使用语义令牌，最后才增加经过评审的全局 variant。
- 业务页面的 Tailwind class 主要用于布局、响应式和间距，不覆盖基础组件的颜色、字体和交互状态。
- 组件颜色使用 `background`、`foreground`、`primary`、`muted`、`destructive`、`success`、`warning` 等语义令牌。
- 涨跌、买卖、成功、失败和风险状态不能只依赖红绿颜色，必须同时有文字、符号或图标。
- 条件 class 使用统一 `cn()`；布局间距使用 `gap-*`，不使用 `space-x-*` 或 `space-y-*`。
- 遮罩组件不手写 z-index；Dialog、Sheet、Drawer、Popover 和 Tooltip 使用组件自身层级。
- 功能私有 CSS 必须限定作用域；禁止用全局选择器影响其它模块。
- 禁止无设计依据的渐变、玻璃、发光、动画和阴影堆叠。

### 5.5 结构要求

- 表单使用 Field、FieldGroup、FieldSet 和对应控件，不用一组裸 `div` 代替表单结构。
- 2 至 7 个互斥或多选项优先使用 ToggleGroup、RadioGroup 或 Checkbox 组件。
- Dialog、Sheet、Drawer 必须包含可访问标题；危险操作使用 AlertDialog。
- Card 使用 Header、Title、Description、Content、Footer 的实际语义组合，不把所有内容堆入 Content。
- TabsTrigger 必须位于 TabsList 内。
- SelectItem、DropdownMenuItem、CommandItem 等必须位于对应 Group 内。
- Avatar 必须提供 Fallback。
- 加载使用 Skeleton 或 Spinner；空数据使用 Empty；通知使用 Sonner；状态使用 Badge、Alert 或 Progress。

## 6. 面向普通外汇交易者的 UX 要求

### 6.1 信息表达

- 默认使用清晰中文，保留必要的 MT4/MT5、Bid、Ask、SL、TP 等交易术语，并提供中文含义。
- 交易账户显示平台、登录账号和经纪商服务器，避免只显示内部账户 ID。
- 买入、卖出、持仓、挂单、平仓、撤单和风控状态使用一致文案。
- 内部错误码不得直接作为唯一用户提示；界面显示可理解原因，并保留可复制诊断编号。
- 高级配置按需展开，核心任务不能隐藏在多层菜单中。

### 6.2 交易安全

- 下单、分发、平仓、撤单和修改保护参数必须明确目标账户、品种、方向、手数、价格、SL、TP 和影响范围。
- 危险操作确认不能只写“确定吗”，必须描述会发生什么。
- 提交中禁用重复操作；网络超时和未知结果不得显示为明确失败并允许立即重试。
- 操作完成后展示服务器接收、Bridge 执行和终端核对的真实阶段状态。
- 普通用户和观摩模式的写权限在 API 层拒绝，前端隐藏按钮不能作为权限证明。

### 6.3 状态完整性

每个数据区域必须设计并测试：

- 首次加载。
- 已有数据后台刷新。
- 空数据。
- 权限不足。
- Bridge 未连接。
- 终端离线或账户已切换。
- 数据陈旧或实时连接重连中。
- 请求失败和可恢复重试。

后台更新不得反复卸载整个组件或让页面闪烁；已有数据保持展示，仅用局部状态提示刷新。

## 7. 数据、状态与实时连接

### 7.1 API 合同

- 前端只消费版本化合同生成或推导的类型。
- API 响应在 `packages/api-client` 边界完成校验和错误归一化。
- View 和展示组件不得猜测字段、兼容多个旧响应形状或补造业务结论。
- 每个功能模块通过自己的 API 门面对外，不在组件中散落请求路径。

### 7.2 Query Cache

- 所有账户级查询键必须包含系统用户、交易账户或观摩频道等完整作用域。
- 切换账户时取消旧请求；迟到响应不得覆盖新账户界面。
- 写操作成功后只失效受影响资源，不全局清空缓存。
- 实时增量按 revision 合并；检测到缺口时精确重新拉取对应资源。
- Skeleton 只用于首次无数据加载，后台刷新保留现有内容。

### 7.3 Pinia

Pinia 可以保存：

- 当前应用会话摘要。
- 主题、侧栏和用户界面偏好。
- 当前选择但尚未形成 URL 的临时 UI 状态。

Pinia 不保存：

- 可由 Query Cache 管理的账户、持仓、订单、信号或历史列表副本。
- 未加密的令牌、模型密钥或 Bridge 凭据。
- 跨用户或跨账户未明确分区的数据。

### 7.4 实时连接

- 应用只能通过统一 realtime client 使用 WebSocket，组件不得直接创建连接。
- 订阅必须声明频道、账户作用域和资源类型；卸载时释放订阅。
- 重连采用有界退避，不允许多个模块各自建立重复连接。
- 每条消息校验版本、类型、作用域、revision 和时间。
- 高频报价和 K 线更新只更新必要节点和图表数据，不重建整个页面或图表实例。

## 8. 路由、登录与子域

- `www`、`trade`、`admin` 使用独立路由表和独立登录页。
- 独立登录页负责当前应用说明和发起登录；账号、密码、验证码、注册、找回和 MFA 的权威表单由 `auth.<domain>` 统一提供。
- 登录使用 OpenID Connect Authorization Code Flow + PKCE；禁止 Implicit Flow、父域共享 Cookie 和前端持久化访问令牌。
- 每个应用通过自己的 `/auth/callback` 建立 Host-only `Secure`、`HttpOnly`、`SameSite=Strict` 服务端会话，不设置 Cookie `Domain`。
- 登录成功后的返回地址只能是当前应用允许的内部路径，防止开放重定向。
- 路由级功能使用动态导入；导航不得预加载所有大型页面。
- 路由参数和查询参数进入模块前必须校验。
- 无权限、未登录、资源不存在和系统异常使用不同页面或状态。
- 前端 API 客户端只访问当前应用同源 API，不读取 Cookie、不添加长期 Bearer Token，也不得自行复制身份到其它子域。
- `/api/v4/session` 提供当前应用会话摘要和 CSRF Token；所有写操作发送 `X-CSRF-Token`，后端同时校验精确 Origin。
- `trade` 通过同源会话申请短时、单次 WebSocket 连接票据；组件不得把 Cookie、访问令牌或用户 ID 拼入 WebSocket 权限判断。
- 退出必须明确区分当前应用、全部网站和全部设备；普通退出不得误撤 Bridge 设备会话。
- 单点登录方案、接口、数据结构、迁移和验收统一见 [单点登录与统一认证架构方案](./single-sign-on-authentication-architecture.md)。

## 9. 响应式与触控

- 最低支持 320 CSS 像素宽度，并覆盖常见手机、平板、笔记本和宽屏桌面。
- 断点由内容可用性决定，不只按设备名称决定。
- 主要交互触控区域不小于 44 × 44 CSS 像素。
- 页面不得出现由布局错误导致的横向滚动。
- 顶栏、侧栏、抽屉和内容滚动区域必须有明确滚动所有权，禁止双重滚动失控。
- 宽表格在小屏使用横向滚动、关键列冻结、行详情 Sheet/Drawer 或响应式卡片；不得直接删除关键字段。
- 移动端危险操作必须保留完整确认和执行状态，不因空间不足简化安全信息。
- 软键盘弹出后，表单当前字段和提交操作仍可到达。

## 10. 可访问性与动效

- 目标为 WCAG 2.2 AA。
- 所有交互可使用键盘完成，并有清晰焦点状态。
- 图标按钮必须有可访问名称；表单错误与对应字段关联。
- 颜色对比、缩放至 200%、屏幕阅读器语义和焦点返回必须验证。
- 动效只用于状态转换和空间关系，默认短暂、可中断，不阻塞操作。
- 遵守 `prefers-reduced-motion`；关闭动效后功能和信息不能缺失。
- 实时报价变化可短暂提示方向，但不得持续闪烁或造成布局跳动。

## 11. 性能与带宽

- 路由和大型功能模块按需加载。
- 图表、富文本、编辑器和导出能力不得进入不需要它们的首屏包。
- API 精确请求字段、范围和分页；禁止为了一个摘要拉取完整历史。
- 实时通道只传递需要低延迟的增量，静态配置和历史使用 HTTP。
- 页面后台刷新不得重复下载不变资源；使用 revision、ETag 或合同支持的缓存机制。
- 图片和媒体必须声明尺寸、采用合适格式并延迟加载非首屏内容。
- 建立每个应用首屏和每条懒加载路由的 gzip 预算；首次骨架完成后冻结数值，超限必须解释和审查。
- 性能验收至少记录 LCP、INP、CLS、首屏请求数、传输字节和实时空闲带宽。

## 12. 错误、安全与隐私

- 错误边界限制在路由或功能模块，单个模块异常不得让整个应用白屏。
- 前端日志不得包含密码、令牌、模型密钥、支付敏感数据、完整终端凭据或原始模型私密内容。
- 用户输入默认不可信；富文本使用统一清洗组件，禁止业务模块自行设置未经清洗的 HTML。
- 权限和资源归属由服务端校验；前端只负责交互引导。
- 写操作携带幂等键、资源 revision 或服务端要求的并发条件。
- 页面卸载、账户切换和用户登出时取消敏感请求、订阅和临时状态。
- 第三方组件和 Registry 依赖必须通过许可证、依赖和供应链审查。

## 13. 测试与质量门

每个模块至少具备与风险相称的验证：

- TypeScript 类型检查。
- 业务纯函数和 schema 单元测试。
- 组件加载、空、错误、权限和正常状态测试。
- 请求取消、迟到响应、重复提交和账户切换测试。
- 路由与权限守卫测试。
- 键盘、焦点和可访问名称测试。
- 手机、平板、桌面关键断点的浏览器验收。
- 关键页面视觉回归截图。
- 危险交易操作端到端测试；模拟通过不等于真实 Bridge/MT 验收。

仓库必须增加自动边界检查：

- 禁止应用之间互相导入。
- 禁止业务模块深层导入其它模块。
- 禁止 View 直接使用 `fetch`、`WebSocket` 或敏感浏览器存储。
- 禁止引入未批准的第二套通用 UI 库。
- 禁止业务页面新增未登记原始色值和全局 CSS 泄漏。

共享包变更验证三个应用；应用内模块变更验证该模块和所属应用。高风险合同、登录、账户隔离和交易相关变更必须扩大到跨应用及端到端验证。

## 14. 完成定义

一个 Vue 功能模块只有满足以下条件才算完成：

1. 功能迁移矩阵中的能力全部有去向。
2. 数据合同、权限和账户作用域明确。
3. 优先使用已批准的 shadcn-vue 组件。
4. 加载、刷新、空、错误、权限、离线和重连状态齐全。
5. 桌面、平板和手机核心流程可完成。
6. 类型、单元、组件、边界和所属应用构建通过。
7. 无跨模块深层依赖、全局样式泄漏和重复基础组件。
8. 性能与带宽未超过已冻结预算。
9. 交易或敏感操作完成安全确认、幂等和未知结果处理。
10. 产品验收确认信息层级、文案和交互符合目标用户习惯。

## 15. 第一轮规范复核

复核范围：需求覆盖、模块边界、现有功能复用、组件优先和是否过度设计。

发现与调整：

- 原基线要求每个模块固定创建完整目录，会产生空目录和模板代码；已改为只有公开入口必需，其余按实际需求创建。
- 原基线虽要求共享 UI，但没有明确唯一 `components.json`、官方 Vue CLI 和组件更新批次；本规范已补齐。
- 补充了应用内功能组件与共享基础组件的边界，避免为了复用把业务判断放入 `packages/ui`。
- 明确专业行情图表是专项依赖，不构成第二套通用 UI 库。
- 将普通外汇交易者的理解成本、危险操作、错误状态和账户语义转化为验收项，不再只写“符合用户习惯”。
- 未提前冻结字体、图标和视觉 preset，避免在产品设计前过度决定视觉细节。

第一轮结论：覆盖充分，结构可实施；已消除明显的空壳模块和组件分叉风险。

## 16. 第二轮规范复核

复核范围：兼容性、数据隔离、并发、异常恢复、时间、安全、测试、回滚和连带 Bug。

发现与调整：

- 增加账户切换时取消请求、拒绝迟到响应和 Query Key 完整作用域，防止不同账户数据串页。
- 增加 realtime 单连接、订阅释放、revision 缺口恢复和局部更新，避免重连风暴、闪屏和带宽浪费。
- 增加写操作幂等、资源 revision、交易未知结果和阶段状态，避免用户重复提交造成重复交易。
- 增加模块错误边界、共享包跨应用验证和应用独立部署要求，限制修改影响面。
- 增加 Registry 来源、版本、许可证和更新审查，控制源码分发组件的供应链风险。
- 增加子域返回地址、会话和敏感数据规则；后续联动复核已冻结 Host-only Cookie、CSRF、OIDC Code + PKCE 和应用同源 BFF 边界。
- 增加移动端危险操作、软键盘、表格详情和 320 像素验收，避免“响应式通过但无法操作”。

第二轮结论：规范可以作为搭建和代码审查门；认证联动方案已冻结，后端业务合同和视觉系统冻结后仍需分别复核。

## 17. 当前待冻结项和剩余风险

- 主站和管理后台的完整功能盘点尚未完成，模块清单可能继续扩展。
- API OpenAPI 合同和实时业务消息合同尚未冻结；子域认证架构已冻结，但正式域名、密钥轮换、管理员 MFA 和会话有效期仍待实施阶段确认。
- shadcn-vue 的 preset、字体、图标、主题令牌和专业行情图表库尚未选定。
- shadcn-vue 组件会进入仓库源码；如果绕过统一组件源或把业务修改直接写入基础组件，仍会产生跨应用影响。
- 真实普通交易者的可用性需要原型测试，规范和自动测试不能替代用户验收。
