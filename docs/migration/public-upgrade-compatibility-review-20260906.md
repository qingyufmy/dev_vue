# 公网覆盖升级与数据库兼容核查

2026-09-06；源码基线 `a71b6fa4`，工作目录 `D:/dev_codex/dev_vue`。本次仅只读查询和文档记录，没有建库、DDL/DML、迁移或部署。

## 用户确定的交付要求

用户明确：公网数据库结构与 `dev_xin` 一致；本次重构完成后必须能在现有公网服务器完成覆盖升级，现有数据不能丢失。`dev_xin` 是用户指定的公网结构基线，不是本次直接查询公网所得的事实。

此要求约束最终发布物，包括代码、配置升级、结构/数据迁移、对账及恢复工具。空库安装成功或新建联调库不满足公网升级要求。不能要求线上用户重新注册、重新建立历史归属或丢弃既有数据来适配 V4。具体采用同库前向迁移还是旁路库迁移并切换，需在逐表映射和演练后确定；都必须保留原数据并提供可验证升级路径。不得把“直接覆盖”实现为未经预检、随应用启动自动执行 DDL。

## 当前核查结果：两库有效结构一致，升级验收尚未完成

用户授权 SSH 后，已通过配置别名 `aurum-vm` 进入主机 `debian`，经本机 MySQL socket 只读比较两个库；没有修改 grants。关联应用目录 `/www/wwwroot/aurum-ai`，分支 `dev_codex`、commit `61610c3c3dc055974d1da90700ecf5336f19434c`，这里只作目标定位，不代表应用已部署 V4或已核验公网。逐项计数、hash 和 DDL 文本差异见 [结构比较证据](dev-vue-dev-xin-schema-comparison-20260906.json)。

两库均为 **165 张表、2,598 个字段、570 个索引（1,072 个索引列条目）、292 个约束、5 组外键参照规则、1 个 check**；字符集、排序规则、默认值、可空性、类型/精度、字段顺序、索引及约束逐项无差异。均没有视图、触发器、存储过程/函数或事件。`schema_migrations` 均为 `id/applied_at`，214 条 ID 集合一致；执行时间不要求相同。

对全部 165 张表额外执行 `SHOW CREATE TABLE`，忽略随数据变化的表级 AUTO_INCREMENT 计数后，4 张表仍有文本差异：`ai_market_benchmark_cases`、`ai_market_benchmark_sets`、`ai_model_compare_jobs`、`period_review_derivation_jobs`。差异全部为 `dev_vue` 显式写出 `CHARACTER SET utf8mb4`，`dev_xin` 在同一 `COLLATE utf8mb4_general_ci` 前省略该文字；字段元数据已独立确认相同。仅归一化这条已核实规则后，全部建表定义一致。结论是有效结构一致，而非原始 SQL 字节相同。

初次权限错误已通过用户授权的 SSH 路径解决。数据库凭据仅在主机匿名内存文件描述符传递，没有输出或落盘；比较文件只保存结构差异、hash 和迁移 ID，不包含业务行或凭据。没有扫描或核对业务数据，结构一致不等于数据内容一致，也不是不丢数据验收证明。

## 已确认的交付缺口

**高：现有结构安装器不是公网旧数据升级器。** `server/db/migrations/bootstrap/v4-foundation-v1.sql` 开头明确空库前提，并创建 `users` 等同名表；runner 校验 `schema_migrations` 的 V4 形状。现有库不能通过这些校验，直接覆盖代码后也没有兼容旧结构的证明。应保留安装路径，同时实现和验收从受支持旧版本到 V4 的显式升级入口；不绕过校验、不清空旧表。

**高：全量迁移与不丢数据证明未完成。** `docs/database-normalization-and-data-migration-plan.md` §6–7 已要求 legacy ID map、持久化 checkpoint、逐项对账、停写/最终增量及回滚，并明确相关回填记录尚待实现。既有交易历史 rehearsal 接受输入进行专项对账，不代表用户、权益、支付、策略、信号、历史、内容和附件等全部域已迁移。全量升级不能以该工具或离线业务测试代替。

**已关闭：源结构等同性疑点。** SSH 实测与建表定义交叉核验已完成，`dev_vue` 可作为用户指定的公网结构基线进行后续迁移演练。正式发布仍需对当时公网结构指纹重新预检，避免演练后新增迁移导致漂移。

## 接续顺序与通过标准

1. 已完成两库结构与旧迁移 ID 比较。正式发布前再次检查公网结构指纹，若有变化先更新映射；不将表级自增计数、行数或迁移执行时间差异当成结构差异。
2. 以确认过的源结构逐表/逐字段生成可校验转换清单：保留、拆分、合并、归档及新旧 ID 对应；归档须可查询和恢复，不能用“源库还在”掩盖 V4 无法访问用户既有数据。旧表删除保持独立验收门。
3. 从获准的可恢复备份建立冻结源，在隔离目标实现有 checkpoint 的回填与失败恢复。当前库和公网库均不作为试错目标；新库只服务演练，不代表已交付。
4. 对全部用户/账户和业务域核对记录集合、关联、状态、金额精度、时间语义、资产文件与解密可用性；不能只比总行数。支付/会员权益、历史归属、交易结果和 `uncertain` 不得改义或触发重放。
5. 用同一冻结源完成独立重复迁移、幂等重跑、中断恢复、备份恢复和业务验收。形成可重现结果后，再演练现有公网目录的代码覆盖、配置转换、维护停写与最终增量、切换和回滚。
6. 发布门必须同时满足完整升级与数据对账；切换后出现新写入时不能直接回旧库而丢失这些数据。公网操作与删除仍另行授权。

两轮复审：第一轮确认用户要求覆盖整个旧系统数据，而非仅 Bridge 档案，空库联调不能替代升级。第二轮确认源/目标隔离、旧迁移历史保留、不同证据级别；通过 SHOW CREATE 发现并核实字符集文字差异，不用同表数替代逐项比较。未改写已发布迁移或创建新库。

当前两库有效结构比较已完成。下一步是以此基线完成全量转换映射、迁移/对账工具及覆盖升级演练。此报告不声明已具备公网覆盖升级能力，也不声明任何业务数据已迁移。
