# 阶段 117：支付收款地址与派生钱包关系核对

## 实际结果

当前 dev_vue 八条 crypto_watch_list 的 id/chain/address/wallet_index 四字段投影，与四条 wallet_keys 的完整来源进行关联：一条精确匹配钱包行 1；七条地址不在派生钱包登记中。八条 wallet_index 都记录为 0，不能以这个字段单独推断关联。

继续只读查询明确白名单的四个固定地址配置项，七条未匹配派生钱包的监控地址均与当前 fixed_tron_address 相同。该结果两次独立读取一致，见 [包含配置比对的最终回执](dev-vue-wallet-recipient-config-review-20260907.json)；[初始钱包关联回执](dev-vue-wallet-watch-links-review-20260907.json)保留为来源核查过程证据。公开报告仅保存来源散列、非地址摘要和匹配 ID，不保存配置地址原文。

旧 payment.js 使用 getFixedAddressForChain('TRON') 生成付款收款地址，fixed-address.js 从 system_config 读取固定地址；归集扫描则通过 HD 派生索引执行。这两个流程不是同一地址身份来源。

## 对新结构的约束

1. payment_matches.recipient_address 与订单的历史收款地址快照必须原样保留；不能用当前配置覆盖旧地址。
2. 不给全部支付监控添加指向派生钱包记录的 NOT NULL 外键，也不按 wallet_index=0 填 wallet_id=1。
3. 只有链和地址精确匹配，且已记录索引没有矛盾时，才能建立元数据关联；该关联不证明密钥控制权。NULL 索引继续保持未知，不补零。
4. 当前固定配置与七条历史记录相等，并不证明配置当年的生效时间、操作者或托管来源。历史配置版本不能反推生成。
5. 钱包行 2/3/4 没有被这八条监控精确引用，只表示本次投影未引用，不构成删除地址或其资金可访问性的证据。

这细化了阶段 116 合同的地址来源分类。payment_wallet_addresses 承接派生钱包元数据时须保留派生来源；若后续用同一地址实体承接固定收款配置，需要明确来源种类与可空派生索引，不能伪造派生事实。支付匹配可保留软关联或暂无钱包关联，历史 recipient 快照仍是付款核对事实。

## 验证范围

新增纯关联检查器，八项关联/钱包检查测试通过，覆盖共享地址多监控、跨链、大小写、仅索引匹配、矛盾索引、稀疏/负索引、重复 ID 和未引用地址保留。真实数据库读取限定结构、地址元数据和固定公开收款配置，没有读取密钥、余额或链上数据，没有数据库写入。

这不是八条监控全部字段的新验收，也不是资金或密钥控制证明。钱包创建时间及托管证据仍待解决；当前库保持 203 表/53 步，全库标准化和旧结构清理继续进行。
