# 阶段 113：返佣规则管理事务与幂等

新增 commerce 应用服务及 MySQL 事务仓储。应用服务严格验证并复制请求；事务仓储再次验证，设置 UTC 会话，锁定当前用户并核验 admin、active、未删除状态，然后检查已有审计回执或调用版本写入器。此次没有新增数据表，也没有改动数据库。

## 幂等合同

请求 ID 使用小写 UUID，请求包含完整非空规则修改集合（最多四行）。同一操作者的请求由用户行锁串行化；锁顺序为 actor，再按规则数值 ID 升序。审计查询显式限定 actor 和 request ID。

每次成功修改必定为每条输入规则产生一条审计，包含 rule ID、actor、request ID、目标比例、目标启用状态和新 revision。回执必须与完整请求集合一一对应；新 revision 必须等于 expectedRevision+1。顺序不同的同内容请求归一后等价；遗漏、增加或更改任何规则参数均冲突。重放返回已记录 revision，不按当前规则的新状态重新执行。

沿用 `(request_id, rule_id)` 唯一键：不同操作者复用 UUID 修改同一规则时保守失败并回滚，不复用他人回执。客户端应生成新 UUID；不能以人为重复 UUID 作为跨操作者协作协议。已有规则审计是持久幂等证据，不得按普通短期日志清除。若未来需要审计保留期限，须先提供独立持久回执和明确幂等窗口。

## 事务与异常

规则更新和审计由仓储统一提交。写入或审计错误触发 rollback；rollback 不确定时销毁连接。commit 抛错按结果不确定处理，销毁连接，不盲目 rollback 或重试；客户端携同一完整请求再次调用时，先检查持久审计。异常不能绕过认证、管理员状态或 CSRF 检查。

第一轮复核：复用现有审计事实承载这个固定形状请求的回执，避免新增通用管理平台或另一个请求表；应用服务不直接 SQL，仓储不信任调用方传入的角色。

第二轮复核：同 actor 并发、规则锁顺序、完整集合比较、大整数 revision、审计失败、提交不确定及审计保留依赖均明确。其它事务锁序可能产生死锁，当前实现回滚并返回错误，不自动重放。真实多连接测试尚待完成。
