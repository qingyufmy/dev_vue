仅新建恢复库 `dev_vue_m1_source_20260906_01`。本轮原库没有结构或业务数据写入；导出期间持有 `LOCK INSTANCE FOR BACKUP`，释放后才创建恢复库。该锁限制结构变更，普通 InnoDB DML 仍可继续；数据一致性由 mysqldump 自身的事务快照提供，不把前后观测冒充同一事务。未修改 A/B 库、应用服务或终端。

## 增量升级演练结果

新脚本 `scripts/rehearse-dev-vue-columns.mjs` 只接受成功备份回执中的隔离恢复库，并核对 server UUID、原始完整结构指纹。`scripts/run-dev-vue-column-rehearsal-host.py` 提供私有凭据入口。

1. 读取 165 张表全部原有列（含生成列和不可见列），按主键流式哈希，只输出计数及摘要。
2. 完整预检后创建独立升级日志，真实 MySQL 日志结构校验通过。
3. 第一个 ADD COLUMN 已提交后主动关闭连接，模拟完成回执尚未写入时的断线。新连接重新取得升级锁，首步返回 `reconciled`，其余八步正常执行。
4. 再执行同一批，九步全部为 `completed`，DDL 总执行数仍为九。
5. 再次扫描全部原有列，逐表计数和内容哈希全部保持一致，包括旧 `schema_migrations`。

正式回执见 [增量演练证据](./dev-vue-inplace-column-rehearsal-20260906.json)。它只证明九列增量的断线恢复和保留原数据能力，不证明所有网络故障、所有迁移或全部业务语义。命名锁竞争行为有离线测试，尚未做两个真实写入进程的竞争演练。

[演练工具清单](./dev-vue-inplace-rehearsal-tools-20260906.json) 保存实际执行的八个源码与 SQL 文件 SHA-256；回收证据时逐一与当前工作区核对一致。后续实际执行必须核对这些 SQL 与执行核心的身份，不能仅凭相同的步骤名称复用本次证明。
