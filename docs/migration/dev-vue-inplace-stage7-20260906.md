## 已实现的转换规则

`scripts/lib/v4-ownership-conversion.mjs` 接受源区间、独立核实的账户 ID 映射、用户集合及显式历史时区依据，只产出转换结果，不直接执行 SQL：

1. 每个来源区间输出一条目标区间，稳定键与 logicalSourceId/来源 ID 绑定；保留来源摘要、目标摘要、原始时间词法与时间依据摘要。
2. 历史 user_id 原样保留，不用账户当前设置用户覆盖。账户合并后在目标账户粒度重新检查所有区间的重叠和唯一开放所有者。
3. 零长度闭区间保留历史，不占用 `[start,end)`，不错误撤销现有开放区间。
4. 当前/最近授权按用户与目标账户投影，并精确引用目标 interval_id。开放区间优先；闭区间的 ended_at 转为 revoked_at，不复活旧权限。
5. 拒绝缺失父用户、账户身份不匹配、两个不同身份指向同一目标、重复来源 ID、反向区间、精度损失和开放区间携带关闭原因。全部检查在无写入的纯函数中完成。

UTC 转换必须提供指定源表的 offsetMinutes 和 evidenceId。没有 UTC+8 或 UTC+3 默认值；非零微秒不能悄悄截断到毫秒，越过 MySQL 日期范围直接拒绝。现有 epoch-ms 与 wall-clock 校验器继续复用。

6 项新增转换测试通过，覆盖时间基准、精度/边界、跨用户合并后的历史保留、顺序无关、跨旧 ID 重叠、零长度证据和身份映射冲突；已有账户候选/源审查 12 项回归也已通过。

## 待确认及后续

已向用户询问旧库历史 DATETIME 是否全部按 UTC+8 写入。当前源码支持该候选判断，但不能只靠当前配置或测试断言证明历史值；这与 MT5 终端时区不同。截至本报告，尚未收到答复。新增测试中的 UTC+8 仅是合成样例，不是对真实数据的确认。

后续继续完成账户实体及同库目标结构、稳定 ID 映射与设置转换；历史时区依据确认后，将真实区间接入转换器并做逐条对账，再通过已有迁移账本事务写入。新旧账户粒度不同，不能仅扩宽主键后就把旧表当成规范化实体。实际回填之前仍需完整账户映射和目标结构验收，不以没有报错代替这些条件。
