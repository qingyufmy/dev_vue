## 待执行的副本诊断范围

目的为恢复当前数据的可读性，随后回到数据库规范化主流程。该步骤不属于已执行迁移，也不把故障前验收当作故障后现状。

1. 重新检查原实例仍停止、源文件摘要未变。若用户已经修复或启动原实例，停止冷复制方案，改做当前实例只读验收。核实是否发生 VM 快照恢复或数据目录替换；此信息影响最新数据边界。
2. 核对配置包含、表空间和 keyring 依赖，确认现有备份覆盖范围。保留原始冷归档，只在新建副本目录操作。副本候选根目录为 /www/backup/aurum-v4/mysql-recovery-20260907-01；存在即停止，不覆盖。
3. 预检剩余空间足够保存一份工作副本与导出结果，保留空间余量。使用相同 MySQL 8.4.8 二进制；专用配置显式指向副本 datadir、socket、pid、日志、临时目录。禁止读取原 my.cnf 直接启动，逐项迁移必要兼容参数。禁用 TCP、MySQL X 网络入口、事件调度及复制自动启动；不接 API、Worker 或 Bridge。采用独立操作系统隔离，确保子进程不能写原 datadir。不能证明隔离时不得启动。
4. 首次只尝试副本正常启动（innodb_force_recovery=0），保存退出状态与日志。启动恢复本身可能写副本，不能称为只读文件操作。失败不循环重启，不删除 redo、undo、ibdata1 或修改原目录权限。
5. 若正常启动成功，只读枚举完整数据库对象及表空间依赖，逻辑导出到新文件，并在另一干净实例验证导入及逐表数据；不能仅凭 ready for connections 判断恢复成功。若正常启动失败，依据副本日志提出下一步；本方案不授权自动提高 innodb_force_recovery 或把旧 SQL 覆盖当前库。

MySQL 官方将 innodb_force_recovery 用于紧急导出，要求先保留副本并从最低级别开始；较高级别会跳过正常恢复步骤，4 及以上可能永久损坏文件。因此任何强制恢复产物仍需独立对账，不能直接作为迁移成功来源。[MySQL 8.4 恢复文档](https://dev.mysql.com/doc/refman/8.4/en/forcing-innodb-recovery.html)

## 两轮复核

第一轮（需求及范围）：当前恢复的是升级所需的数据库依赖，不把修好 MySQL 等同于完成重构。调整为原实例保全、副本诊断、导出验证、升级重新准入四个独立结果；不引入公网操作。
