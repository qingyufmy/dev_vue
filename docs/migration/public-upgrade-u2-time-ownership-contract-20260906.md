# U2 历史时间依据与账户承接合同

## 1. 已收敛的结论

旧写入代码支持UTC+8候选解释，不能继续只描述成完全没有依据。`server/db.js`的`beijingNow()`在UTC上加8小时后格式化；连接池配置和SQL会话也明确使用`+08:00`。本批登记的13个源文件与已观测运行提交`61610c3c3dc055974d1da90700ecf5336f19434c`内容一致；该对比在本地Git对象中执行，没有再次检查运行主机工作区是否有未提交改动。

Git历史：`645f4f7e`（2026-06-10）引入beijingNow，`29599418`（2026-07-08）引入SQL会话时区设置，`fa6bf23a`（2026-07-22）的归属历史写入已使用beijingNow。冻结镜像归属起始值范围为2026-07-25至2026-08-27，代码依据早于这些值。提交时间和字段相等只是支持证据，不能证明每条历史数据没有经过其它导入或修数。

## 2. 时间规则

[机器证据](public-upgrade-u2-time-ownership-evidence-20260906.json)逐项覆盖原U1的39个墙钟字段，保留源类型/NULL约束、当前目标、代码引用与文件hash。引用按写入族分组，是已找到路径的证据目录，不宣称每个字段的全部历史写入路径已穷尽。

| 字段范围 | 已找到的写入依据 | 转换约束 |
| --- | --- | --- |
| 用户会员到期 | 管理端日期输入转为当日23:59:59；注册、会员等其它路径仍需分别核对 | 保留实际到期时刻，不能仅截取日期或统一补午夜 |
| 用户创建/修改/活跃/注销 | SQL默认、NOW、beijingNow及注销更新 | 依据源字段和写入来源决定，不从当前OS时区推导 |
| users.bridge_heartbeat | 退役字段，当前完整写入路径未恢复 | 原值保留为历史；不得恢复在线状态 |
| 验证码、旧配对、旧refresh | 显式北京时间到期字符串或SQL NOW/DATE_ADD | 旧验证码/配对保留既有归档处置；不复活凭据。refresh仍依赖既有兼容/撤销合同 |
| 账户创建/验证/更新 | risk-state及手动账户入口显式beijingNow | 各源行时间保留；实体合并后的min/max另行检查，不覆盖用户设置时间 |
| 当前绑定、历史归属 | 运行时beijingNow；初始化迁移复制账户时间/COALESCE回填 | 区分当前事实和历史推导，不能把所有first_connected_at解释为首次真实连接 |
| 旧终端created/updated | SQL默认，与另3个epoch毫秒字段不同 | 不用last_seen epoch替代created/updated；更新事件不同不能拿时间差作时区证明 |
| 观摩源、频道、授权 | SQL NOW | 来源时间转UTC与授权有效性分开验收 |

NULL保留NULL，不做时区运算；NOT NULL出现空值拒绝。非NULL先保留完整墙钟值，确认该字段/记录来源后才应用候选UTC+8转换，输出DATETIME(3)且不丢非零精度。`23:59:59`仍是精确到秒的原边界，不擅自延长为`23:59:59.999`。新UTC日期跨日是正常现象，独立对账比较瞬间与旧业务日期语义，不只比较字符串日期。

39个字段仍未标为`readyForConversion`。特别是用户会员到期、首次连接回填和退役心跳不能因为账户历史支持UTC+8就一并解除阻断。上一批1353个非NULL墙钟值、74个NULL的统计是2026-09-06完整读取证据，本批没有重新遍历全部11表。

## 3. 归属区间现场检查

在已授权SSH路径连接同一冻结镜像、核对UUID后，以一个READ ONLY一致快照执行4组聚合SELECT；SQL和原始聚合结果保存在机器证据中。使用同源服务器ASCII大小写候选及原样login分组，对源墙钟区间做半开区间比较；相邻边界相等不算重叠。不把缺少历史platform的旧字段分组当作最终V4实体证明。

- 274条历史：3条未结束；271条`end_reason=account_transferred`。
- 倒置0、零长度0、正长度区间重叠对0。无匹配行时SUM返回NULL，机器证据保留NULL，不把NULL偷改成一次独立跨用户验证结果。
- 全部274条created_at等于started_at；271条已结束记录updated_at等于ended_at。
- `historical_backfill`结束原因0；仅凭该值不能排除曾有其它历史导入，不能将字段相等当作不可伪造的来源证明。
- 1个重复源账户组含2条记录、2个不同用户，与前一批候选结果一致。

这是源墙钟内部顺序检查，不是UTC时间转换验收。对账没有调整任何区间、改owner、删重复行或重放交易。

## 4. 三个实体、四份设置、全部历史的承接草案

目标结构已有003账户实体/当前授权以及019历史区间/用户设置，不需要为这组重复数据立刻加新表。

1. **账户实体候选3个。** 4条旧账户记录经同用户终端平台证据形成3组；每个旧ID分别保留映射，同组可指向同一未来目标实体。当前只有候选key，没有分配目标ID。服务器名称仅使用已审查ASCII规则，login原样保留。
2. **用户设置4份。** 用`(user_id, trading_account_id)`分别保存nickname、review/observe状态、异常、隐藏/暂停及验证时间。不同用户的设置不得最后写入覆盖。源is_deleted保留在legacy_is_deleted并按明确规则处理hidden；不能直接当作共享账户实体已删除。当前没有同用户重复槽位，后续出现必须拒绝覆盖。
3. **历史区间274条全部承接。** 每条保留自己的user_id、源account ID映射、start/end/end_reason和原始证据；origin_ref按逻辑源+表+旧PK稳定生成，不使用run/snapshot随机值。created/updated在019已有UTC目标列；U1的proposal去向需在下一版字段合同显式更新，不能静默改冻结版。
4. **当前owner候选3份。** 从当前binding与唯一未结束区间的精确用户/account引用产生候选。对已注销/删除用户、不可用来源、多个open或binding不一致继续拒绝授权；不得从4份设置推导4个owner，也不创建旧会话或设备授权。历史上曾拥有账户的用户只按已存在的历史区间访问相应数据。
5. **实体公共属性仍需核验。** margin_mode、币种及实体created/updated的归并规则须检查同组各来源；不同值不按最后写入选取。当前绑定币种可提供候选，不证明全部历史币种。共享实体是否删除不能由一个用户的隐藏/删除设置决定。

## 5. 两轮复审和接续条件

第一轮（需求/职责）：沿用现有003/019及ID map，不另建迁移服务；账户实体、用户设置、历史归属和当前授权各有明确目标。保留所有旧记录，不靠删除重复数据解决唯一键问题。归档凭据和活动业务时间的门分开，避免无关的退役字段阻塞已明确的活动字段设计。

第二轮（兼容/时间/权限）：现有代码版本和字段模式只提供候选来源，不能替代逐行历史证明；检查半开区间、当前owner唯一性、注销态及设置主键冲突；共享实体元数据冲突和源内容封印继续保留阻断。最终writer必须在短事务中同时写业务行、ID map、receipt和checkpoint，独立回读验证记录集合与字段；回填期间不调用正常业务创建接口。

本批只改文档/机器证据，没有修改运行代码或SQL；验证39字段无漏项重复、引用文件hash和运行提交源文件一致性、现场只读聚合以及U1静态检查。未重复运行与文档无关的全套测试。

下一批可直接细化003/019目标字段转换：先补实体公共属性冲突检查、四份用户设置映射和274条历史记录的完整目标字段合同，再实现纯转换与独立对账。非NULL时间的历史来源/采纳依据保持显式条件；真实业务写入仍需具体范围获准。当前成果不代表已可切换公网，也不必等待其余154表全部迁移后才接续身份相关页面联调。
