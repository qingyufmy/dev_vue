# 公网无损升级接续实施方案

状态：2026-09-06 方案已完成两轮复审，待进入首批实施。当前任务仅制定方案，不执行数据库写入或部署。依据 [结构核查](public-upgrade-compatibility-review-20260906.md)、[既有 B1–B4 方案](../stage-m1-data-backfill-and-reconciliation-plan.md) 和主路线图，不另起一套迁移体系。

## 1. 实施结论

推荐沿用既有旁路迁移方案：旧公网结构 → 冻结源镜像 → V4 目标库 → 对账 → 同一公网服务器升级程序并切换配置。旧库完整保留；最终交付包含显式升级命令和恢复手册。用户无需重新建立业务数据，不能只覆盖代码然后让新程序读取不兼容的旧表。

“覆盖公网服务器”理解为在现有服务器完成版本升级和业务接续，不强制所有物理表名、库名保持不变。如果后续明确要求数据库名/连接配置也完全不变，需另行评估同库兼容方案，不能把空库安装 SQL 直接套进旧库。现阶段不改 V4 既有迁移历史，不建立长期双写系统，也不承诺未经演练的零停机。

建议把升级数据链路作为当前优先工作；Bridge 已完成批次保留，P5B 与其它新功能按依赖接续。目标功能没有承接的旧数据，必须先补功能和结构，不能为了赶回填把活动数据全部归档。最终发布仍受主站、后台、Bridge 和非功能验收门共同约束。

## 4. 第一批具体做什么

下一批只进入 **U1：把既有映射变成可检查的实施合同**，不立即回填。

1. 从已经核实的源结构登记全部165表，逐项关联现有迁移矩阵和当前V4目标/责任域，列出阻断；不从表名推断目标业务语义。
2. 保留 `m1-b2-identity-field-manifest-20260905.json`，生成首批新版清单，复核11表148列与当前源快照是否一致。逐列确认目标存在、类型/NULL/默认值/精度/排序规则、关系、时间语义和活动/历史处置。
3. 按后续 P1–P5A 实施记录逐项复核旧 blocker，附源码/合同证据后关闭；目标缺失、旧 DATETIME 时区不明、账户重复或归属冲突保持阻断。不能由当前服务器时区反推全部历史 DATETIME。
4. 新增或复用离线校验器，覆盖遗漏/重复列、未知转换、不存在的目标、未关闭阻断却标记 executable 等行为。验证通过只说明清单合格，不代表真实迁移通过。
5. 交付首批差异报告：哪些可以进入 U2/U3、哪些需补功能/DDL、哪些需数据语义决策。记录后续迁移的精确范围，作为真实写入前的可审查输入。

重点保留：用户 ID、匿名化/删除态、密码哈希和 token 版本的语义、会员来源/到期及推荐余额、账户精确身份和历史 owner 区间、旧设备兼容证据。不得迁移后恢复旧验证码、重新激活撤销凭据或给无证据账户补 owner。历史数据归属不能只按当前 owner 重写。

## 5. 不丢数据的判定

不以“表数相等”“行数差不多”或“旧库还在”作为通过。需要记录集合、字段原值/转换值、ID关系、状态、十进制金额、时间与权限语义逐项对账；合并/拆分以映射证明，不能简单要求各表行数相同。密码/加密配置需验证兼容与可解密性，附件还需验证实际文件及引用。

回填必须是纯数据转换，不调用正常业务创建入口去重发通知、续会员、重跑模型、执行支付或投递交易。历史 accepted/uncertain 不能重放；旧 outbox/队列工作需按明确处置规则保留为历史或阻断，禁止恢复后自动消费。隔离演练期间业务 Worker 不连接迁移目标。

正式切换的恢复分两种：开放新写入前可以按已演练步骤回退程序/连接；开放后先冻结新增事实，再按已实现并验证的恢复/逆向对账流程处理。若尚无可靠方案，不得承诺可直接回旧库，也不能带着该缺口开放生产写入。

## 6. 两轮复审

第一轮（需求与职责）：采用原有旁路路线和工具，不重复建迁移平台；明确公网升级包含代码、配置、数据、文件及用户可用性。把全表覆盖登记与首批可执行字段合同分开，避免要求一次完成全系统才开始第一批，也避免将11表成功冒充全量完成。

第二轮（数据与异常）：保留旧214条迁移事实和冻结映射，不改共享迁移；补齐checkpoint与批事务原子性、快照和规则绑定、非法历史数据阻断、切换后写入恢复、密码/文件可用性与业务副作用隔离。既有备份/A/B状态待只读复核，不重复导出或清库。剩余风险是时间语义、冲突账户归属、全域目标功能缺口和停机耗时，分别在U1/U4/U5关闭。

本次方案验证仅为源码/文档交叉核对、内部链接与差异检查，没有重新执行业务测试、数据库查询、迁移、部署或终端操作。
