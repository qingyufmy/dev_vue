## 已实现

`server/src/modules/commerce/domain/referral-credit.ts` 使用 BigInt、固定 8 位小数和 DECIMAL(20,8) 边界。输入只接受十进制文本，拒绝浮点数、指数形式、超精度和溢出。

- `quoteReferralCredit` 计算可抵扣额、应付额及剩余余额。负期初余额保留，不能花费但不自动改成零；未请求抵扣则不使用余额。
- `projectReferralBalance` 计算正额入账/扣减前后值，拒绝透支和溢出。它只计算金额，不证明该请求有权执行，也不负责幂等。

14 项定向测试及服务端类型检查通过。未注册接口、未写数据库、未启动服务。

## 下一批账本与迁移合同

1. 新账本需保存 user_id、事件种类、稳定业务来源、带符号 delta、变更前后余额、账户 revision、记录 UTC 时间及来源证据。每用户 revision 唯一，事件业务来源唯一；余额与账本、订单/佣金状态必须同事务更新。API 幂等键不能代替业务事件唯一性。
2. 取消与过期必须竞争同一个 `order_release` 事件键，按订单 ID 去重，不能以两个不同 reason 各退款一次。支付完成后不再释放，佣金审核通过只允许一次入账。锁序由订单/佣金事实与余额共享调用协议统一，不允许各入口自行加锁。
3. 25 条已迁余额是新的期初事实。建立 opening 事件时绑定已有迁移 run/来源 hash，可以为零或负；不使用普通正额变动函数，不伪造历史佣金或旧事件发生时间。新发生时间和历史来源时间分开记录。
4. 旧 pending 订单可能已经扣除 referral_credit_applied。导入该订单只能登记原抵扣及未履行的返还义务，不能再从期初余额扣一次。后续释放应引用明确导入的义务；金额/状态/关联不清楚时阻断该订单转换，不能猜测已返还与否。
5. 币种/单位需要依据旧订单与产品合同确认，不能因为支付链为 USDT 就擅自给全部历史推荐余额补币种。佣金费率、归因与审核事实仍需按逐表矩阵迁移；当前 refs 为零行也不代表运行能力可删除。

两轮复核：先核对旧版扣减/返还事务触发条件，再检查迁移期初与待支付订单的重复扣款/重复返还风险。上述是下一批结构与事务要求，尚无对应账本 DDL 和运行 repository，不宣称已经实现。

下一步只读核对实际 orders/referrals/referral_rules 的金额字段与待支付抵扣，再冻结订单义务和账本结构。本阶段不满足旧 users 推荐字段删除门，全库自动升级与清理仍未完成。
