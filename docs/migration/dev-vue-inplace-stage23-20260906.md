# 同库升级第二十三批：同一表多步DDL恢复

回到全域结构承接，核实策略域原004迁移包含 strategies CREATE、strategy_versions CREATE、strategies ADD FOREIGN KEY。两张表通过当前版本和版本所属策略双向关联。现有同库建表执行器只核对每一步固定的最终表指纹，不能直接用于同一表随后追加外键：重跑时早期CREATE指纹已经被合法ALTER改变，误报漂移。

新增 `scripts/lib/inplace-ordered-schema-upgrade.mjs`，继续复用现有 journal 的 started/completed、checksum、连续前缀与时间校验，不建立第二套账本。每条DDL绑定前后两个SHOW CREATE结构摘要。按已完成前缀推导当前结构，未完成的最后一步仅允许其前态或后态；DDL成功但响应丢失后核对后态并补记完成，不重复执行。完整受管表集合先通过预检，再写第一条journal，避免后续表漂移导致部分执行。

范围限于CREATE和单条ADD FOREIGN KEY；拒绝混合ADD COLUMN、DROP、级联删除等操作。调用方必须持有现有独占升级锁，并实现assertPrerequisites，核实前序23步、原库结构和父表定义。执行器不关闭外键、不切表、不激活任务，也不能独自证明旧数据可以转换。

定向复核：第一轮检查职责，选择扩充现有迁移工具而非另建版本账本；第二轮检查恢复，使用DDL前后状态链解决旧指纹失效，保留全部预检、未知历史和checksum拒绝路径。此为已批准同库方案内的执行器补充。

验证：9项新增测试与3项账户建表回归通过。覆盖最终ALTER后的重复执行、三处DDL响应丢失恢复、started但DDL未执行、后续表未登记、已完成结构漂移、历史缺口、计划篡改、前置条件失败、只读计划及禁止的混合/破坏性语句。均为内存adapter测试，不是MySQL DDL演练。

本批未生成或执行006迁移，也没有建表、回填、重命名、删除或部署。下一步按真实目标结构生成策略/版本的具体状态链，绑定根迁移与SHOW CREATE证据，接入既有恢复副本执行器，完成真实DDL恢复后再承接源策略数据。历史时间依据与账户真实回填条件仍未关闭，全域升级目标继续进行。
