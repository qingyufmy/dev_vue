# 账户风控跨日回撤与自动恢复修复方案

## 1. 结论

2026-08-25 对公网正式服务器、当前发布提交 `9446636506741d261ba4c657439246ded53e27a0` 和账户 `839069` 的只读核查确认：

- 当前暂停不是“最近几天的单日亏损相加”。账户命中的是 `R3.3_MAX_DRAWDOWN`，系统按资金流校正后的账户净值历史高水位计算跨日回撤：`(历史高水位 - 当前净值) / 历史高水位`。
- `R3.1 当日亏损` 才按 MT5 `business_date` 切换并重置；`R3.3 最大回撤` 不在第二个 MT5 交易日归零。两条规则是独立指标。
- 公网账户当前持久化回撤为 `8.474657%`，有效上限为 `8%`，所以此刻继续停止新开仓符合现有规则；不能直接清空状态。
- 真正需要修复的是自动恢复链路：后台和风险中心只主动刷新“数据不完整”账户，没有刷新已经数据完整、但因 `R3.1/R3.2/R3.3` 暂停的账户。即使净值后来恢复至阈值内，也可能一直保留旧暂停状态，直到某条后续下单链路重新执行完整风控。
- 当前状态表没有可靠的“本次暂停开始时间/当前原因开始时间”，因此不能从现有数据精确证明该次暂停是哪一天触发；不得用 `updated_at` 或最后快照时间冒充触发时间。

本方案保持风控口径不变，补齐“可恢复状态的主动重算、精确账户路由、并发围栏、状态审计和页面解释”。本文件只给出实施方案，不授权改代码、迁移、部署、重启、修改阈值或操作公网数据。

## 2. 已验证根因

### 2.1 跨日回撤是历史高水位，不是多日单日亏损求和

`server/routes/ai/risk-state.js` 当前逻辑为：

1. MT5 `business_date` 变化时，重置 `day_start_equity` 和当日已实现净损益，用于计算 `daily_loss_pct`。
2. `equity_high_water` 延续上一快照的高水位，并按入金、出金和信用额变化校正。
3. `drawdown_pct = (equity_high_water - equity) / equity_high_water`，因此天然跨日。

所以“最近各交易日都没有单日回撤超过 8%”不能排除账户历史高水位回撤已经达到 `8.474657%`。交易记录图表若展示的是单日已实现收益，也不能直接与包含当前浮动盈亏的净值高水位回撤比较。

### 2.2 自动恢复选择器遗漏了数据完整的暂停账户

当前 `server/routes/ai/risk-snapshot-refresh.js` 只选择：

```sql
ras.data_complete = 0 OR ras.halt_reason = 'R3_RISK_DATA_INCOMPLETE'
```

它不会选择：

- `R3.1_DAILY_LOSS_LIMIT`
- `R3.2_CONSECUTIVE_LOSS_COOLDOWN`
- `R3.3_MAX_DRAWDOWN`

`server/bridge-ws.js` 也只在 Bridge 身份同步完成后做一次上述“不完整账户刷新”，不是持续恢复任务。`public/ai/app.js` 打开风险中心时同样只在 `data_complete=false` 时调用刷新接口。

结果是：

- MT5 交易日已切换，但 `R3.1` 旧状态未重新取快照，可能不解除。
- 连亏冷静期已到期，但 `R3.2` 未重新计算，可能不解除。
- 净值回升、入出金校正或阈值调整后，`R3.3` 未重新计算，可能不解除。
- 后续订单风控本身能够基于新快照恢复状态，但不能依赖“出现下一笔订单”作为恢复调度器；部分管理员分发路径还会在进入完整订单风控前先过滤已暂停账户。

### 2.3 页面文案混淆了两类 8% 指标

页面目前同时展示“回撤”和“将在下一次完整风险快照校验通过后解除”，但没有说明：

- 当日亏损按 MT5 交易日重置。
- 最大回撤为跨日净值高水位回撤，不会在零点重置。
- Bridge 离线或没有主动刷新时，“下一次完整快照”可能尚未发生。

因此用户会自然把 `8%` 理解为单日回撤，并认为第二天必然自动恢复。

## 3. 修复目标与非目标

### 3.1 修复目标

1. 保持 `R3.1` 按 MT5 交易日、`R3.3` 按资金流校正后历史高水位的现有业务口径。
2. Bridge 在线时，自动重算处于可自动恢复状态的账户，不需要等待新订单或用户打开页面。
3. 只允许完整、身份匹配的新快照解除暂停；失败、超时、过期或路由不明的快照继续 fail closed。
4. 策略阈值保存后立即重算目标账户，既能解除已恢复状态，也能识别新阈值下的超限状态。
5. 页面明确区分“当日亏损”和“历史高水位回撤”，显示快照新鲜度和等待原因。
6. 从修复上线后的状态转换开始，能够回答“何时暂停、因何暂停、何时恢复”。

### 3.2 明确不做

- 不把 `equity_high_water` 按天重置，不把最大回撤改成日内回撤。
- 不把最近几天的日亏损百分比相加。
- 不自动提高账户 `8%` 上限，不手工清空账户 `839069` 的暂停状态。
- 不用不完整快照、缓存页面数据或单纯时间到期直接解除风控。
- 不自动开仓、补单、重试交易或修改 Bridge 交易开关。
- 不自动回填现存暂停记录的历史触发时间；缺少可靠证据时必须显示“未知”。
- 不轮询所有正常账户，避免把风险恢复变成持续的全量 MT5 历史查询。

## 4. 详细设计

### 4.1 统一“可自动恢复状态”白名单

将 `refreshIncompleteRiskAccounts()` 重构为面向恢复的服务，例如：

```js
refreshRecoverableRiskAccounts(userId, {
  accountId = null,
  route = null,
  trigger = 'background',
  includeActive = false,
} = {})
```

默认只选择以下状态：

- `data_complete = 0`
- `R3_RISK_DATA_INCOMPLETE`
- `R3.1_DAILY_LOSS_LIMIT`
- `R3.2_CONSECUTIVE_LOSS_COOLDOWN`
- `R3.3_MAX_DRAWDOWN`

同时必须满足：

- 账户属于当前用户、未删除、`review_status=approved`、`observe_status=active`。
- `user_kill_switch=0`。
- 当前不是 `protection_incident`，不是 `R6_ACCOUNT_*`、账户转移、冻结、暂停等人工或权限状态。

`includeActive=true` 只允许策略保存后的单账户定向重算使用，禁止后台借此轮询所有活动账户。全局 kill switch、用户 kill switch、保护事件和 R6 状态继续由各自授权链路解除，风险快照不得替代它们。

### 4.2 用完整 MT5 快照重算，不直接改状态

每次恢复检查继续复用：

- Bridge `risk_snapshot`
- 增量成交游标 `last_deal_time_msc + last_deal_ticket`
- 必要的报价与币种换算
- 当前实时生效策略 `resolveEffectiveRiskPolicy()`
- 单一状态计算入口 `refreshRiskAccountState()`

解除规则保持为：

- `R3.1`：MT5 `business_date` 已变化，且新交易日的完整快照下 `daily_loss_pct < daily_loss_limit_pct`。
- `R3.2`：冷静期已到期，且新快照没有重新触发更高优先级风险。
- `R3.3`：资金流校正后的新快照下 `drawdown_pct < max_drawdown_pct`。
- 任一快照不完整、账户净值无效、历史不完整、币种换算缺失或 Bridge 返回失败，均保持暂停，不覆盖上一次可信状态。

不增加模糊的“宽限恢复值”。当前命中条件是 `>= 阈值`，恢复条件保持 `< 阈值`；若未来需要 0.1% 等防抖缓冲，应作为单独产品规则评审。

### 4.3 绑定准确账户和终端路由

当前刷新请求只按 `userId` 发送，在同一用户连接多个终端时可能路由歧义。修复后每个候选账户必须绑定：

- `trading_account_id`
- `broker_server + login_account`
- `terminal_instance_id`
- 当前 `connection_generation/connection_epoch`

`risk_snapshot`、`quote` 均携带账户身份和终端路由参数。结果返回后再次校验 `server/login` 与数据库账户一致，并确认连接代次仍然有效；账户切换、所有权转移或旧连接迟到结果不得更新新账户状态。

若找不到唯一在线路由，返回稳定的 `bridge_terminal_not_connected` 或 `bridge_terminal_ambiguous`，保持暂停并在页面显示等待 Bridge，不允许回退到另一个终端。

### 4.4 增加按需运行的自动恢复调度器

在 Bridge 运行层增加每用户一个恢复任务：

1. Bridge 身份验证完成后立即检查一次所有可恢复账户。
2. 只要仍存在可恢复的暂停/不完整账户且对应 Bridge 在线，就在前一轮完成后延迟 60 秒执行下一轮。
3. 没有候选账户、账户已恢复、Bridge 离线、账户切换或权限状态改变时停止定时器。
4. 临时失败采用 `60秒 -> 120秒 -> 300秒` 上限退避；Bridge 重连后立即恢复，不等待旧退避结束。
5. 每用户只允许一轮，每账户只允许一个 in-flight；定时器不能与页面手动刷新、策略保存刷新重叠发送同一账户快照。
6. 进程关闭和 Bridge 断开时清理定时器；迟到 Promise 仍必须通过连接代次围栏后才能写状态。

任务仅查询可恢复状态，不持续轮询正常账户。风险快照是低优先级只读命令；若该用户正在执行 Bridge 交易发送或处于 Bridge 更新维护围栏，跳过本轮并稍后重试，避免与下单关键路径争用。

### 4.5 页面刷新与策略保存联动

修改 `/api/ai/risk-center/refresh`：

- 接受可选 `account_id`，仅刷新当前用户拥有的账户。
- 调用新的可恢复刷新服务，不再只处理 `data_complete=false`。
- 返回每账户 `attempted/refreshed/recovered/still_halted/error/last_snapshot_at`，不把“命令发送成功”误报为“已恢复”。

修改策略保存接口：

1. 先按现有事务保存和审计策略版本。
2. 保存成功后对该账户触发一次 `includeActive=true` 的定向完整快照。
3. Bridge 离线时策略仍保存成功，但响应明确返回 `risk_refresh=pending_bridge`；页面显示“规则已保存，等待 Bridge 完整快照验证”，不能宣称状态已立即生效完成。

风险中心页面在遇到可自动恢复的暂停状态或数据不完整时可以发起一次去重刷新，用于快速反馈；真正的自动恢复仍由服务端调度器负责，不能依赖浏览器页面常开。

### 4.6 页面解释和指标展示

风险卡片拆分为两个明确指标：

- `当日亏损`：按 MT5 交易日，显示 `business_date`、当日起始净值、当日亏损率和上限。
- `历史高水位回撤`：跨日，显示资金流校正后高水位、当前净值、回撤率和上限。

`R3.3` 文案改为：

> 历史高水位回撤达到上限。该指标跨交易日累计，不会在 MT5 日期切换时归零；净值恢复至阈值以内并通过完整快照后自动解除。

`R3.1` 文案改为：

> 当日亏损达到上限。MT5 交易日切换后，将在下一次完整快照中按新交易日重新计算。

同时展示：

- 最后完整风险快照时间及“新鲜/过期”。
- 当前恢复状态：`监测中 / 等待 Bridge / 等待完整历史 / 仍高于阈值 / 已恢复`。
- 图表旁提示“交易记录日收益不等于账户净值高水位回撤”，避免继续用日柱图验证跨日指标。

### 4.7 增加状态转换时间与审计

通过幂等迁移为 `risk_account_state` 增加可空字段：

- `halt_started_at`：本轮从 active 进入 halted/protection 状态的时间。
- `halt_reason_changed_at`：当前暂停原因开始生效的时间。
- `last_recovered_at`：最近一次从可自动恢复暂停回到 active 的时间。

状态更新时间规则集中到同一辅助函数，并由 `refreshRiskAccountState()` 与订单风控重算路径共同调用：

- active -> halted：同时设置 `halt_started_at` 和 `halt_reason_changed_at`。
- halted 且原因变化：保留 `halt_started_at`，更新 `halt_reason_changed_at`。
- halted -> active：设置 `last_recovered_at`，保留最近一次 `halt_started_at` 作为历史展示依据。
- 状态和原因未变化：不得刷新上述时间。

每次真实状态/原因转换后写现有 `audit_logs`，只保存账户 ID、前后状态、规则代码、关键百分比、MT5 `business_date`、快照时间和触发来源，不保存完整账户快照、持仓明细或敏感凭据。

迁移不得用 `updated_at`、`last_risk_snapshot_at` 猜测现有暂停的触发时间。旧记录字段保持 `NULL`，页面显示“该状态产生于审计字段上线前，准确触发时间未知”。

## 6. 测试与验收

### 6.1 指标语义测试

- MT5 `business_date` 切换后 `day_start_equity` 和当日损益重置。
- 同一切换不会重置 `equity_high_water`。
- 连续三天每一天都小于 8%，但相对历史高水位累计回撤超过 8% 时，仍命中 `R3.3`。
- 入金、出金和信用额变化按现有资金流校正，不制造虚假回撤或虚假恢复。
- 当前回撤等于 8% 时仍暂停；低于 8% 时完整快照可恢复。
- 日亏损跨日恢复不会误清仍然命中的最大回撤。

### 6.2 恢复调度测试

- 数据完整的 `R3.1/R3.2/R3.3` 均进入候选；active 正常账户不进入后台候选。
- 用户 kill、保护事件、R6、账户 paused/switched/frozen/transferred 均不自动解除。
- Bridge 重连立即执行一轮；仍暂停时按 60 秒继续；恢复后停止。
- 快照失败、超时、不完整、路由歧义时保持原状态并退避。
- 页面刷新、策略保存和后台定时器并发时，同一账户只发送一次快照。
- 旧终端/旧连接代次迟到结果不能覆盖新身份。
- 正在下单或 Bridge 更新维护时跳过恢复快照，交易路径不被阻塞。

### 6.3 API 与页面测试

- `/risk-center/refresh` 不能刷新其他用户账户。
- 策略上限提高后，完整快照确认当前指标低于新阈值，可解除；上限降低后可进入暂停。
- Bridge 离线保存策略返回“等待验证”，不是“已恢复”。
- `R3.1` 与 `R3.3` 文案、单位、MT5 business date 和最后快照时间正确。
- 历史触发时间为空时显示未知，不回退使用 `updated_at`。

## 7. 发布与回滚

- 本地实现、提交推送、虚拟机部署和公网发布是四个独立授权步骤。
- 数据库变更只通过项目内幂等迁移执行，不运行直接 SQL 或手工修表。
- 先在虚拟机 Demo 验证，再申请公网发布；不发布 Bridge 安装器或模块更新包。
- 发布后重点监控：每分钟候选账户数、快照成功率/耗时、错误码分布、单账户并发数、恢复次数和 Bridge 命令延迟。
- 代码回滚时停止新恢复调度器并恢复旧服务；新增可空字段可以保留，不做破坏性回滚。旧字段不会改变现有风控计算。
- 若快照负载超出预期，先把后台间隔提高到 300 秒或临时关闭自动调度，但保留定向刷新和 fail-closed 状态；不得用批量清除暂停作为降载手段。

## 8. 两轮方案复审

### 8.1 第一轮：业务语义、根因与最小改动复审

检查项：是否把跨日高水位误当日内指标，是否真正解决“无人触发刷新”，是否扩大风控权限。

发现与调整：

1. 最初可以在 MT5 日切时把所有回撤归零，但这会把 `R3.3` 降级为第二条日亏损规则，并掩盖真实账户累计回撤。调整为保留高水位，只重置 `R3.1` 日内基线。
2. 只修改风险中心页面可以让用户打开页面时恢复，但浏览器关闭后仍不会自动运行。增加 Bridge 在线期间的服务端按需调度器，页面只承担快速反馈。
3. 轮询全部账户会增加 MT5 历史和报价负载。调整为只轮询明确的可恢复状态；活动账户只有策略保存后才允许单次定向重算。
4. 直接把 `halt_status` 改为 active 无法验证资金流、持仓和历史完整性。确定所有恢复继续通过现有 `refreshRiskAccountState()`，不得建立第二套解除公式。

第一轮结论：方案修复的是恢复调度缺口，不改变 8% 最大回撤的业务含义，也不绕过完整快照。

### 8.2 第二轮：身份、并发、审计、异常与发布复审

检查项：多终端路由、账户转移、迟到结果、任务重叠、Bridge 离线、历史审计、迁移和回滚。

发现与调整：

1. 只按 `userId` 发送快照在多终端用户下可能歧义。增加账户身份、终端实例和连接代次三重围栏，报价请求也必须走同一路由。
2. 固定间隔 `setInterval` 可能让慢请求叠加。调整为上一轮完成后再 `setTimeout`，并增加每用户/每账户 single-flight 与失败退避。
3. 自动恢复白名单若只按 `halt_status` 会误清用户紧急停止、保护事件或账户权限暂停。调整为显式 R3 原因白名单并同时检查账户和 kill-switch 状态。
4. 当前无法准确回答旧暂停的触发日期。增加状态转换时间和审计，但拒绝伪造历史回填；账户 `839069` 的现存暂停仍只能标记为“上线前触发时间未知”。
5. 用仍高于阈值的公网账户验证“恢复成功”会诱发改阈值或改数据。调整为先在受控 Demo 场景验证，公网账户只验证“超限不误恢复”，自然低于阈值后再观察真实恢复。

第二轮结论：方案具备 fail-closed、账户身份隔离、并发幂等、可观测和可回滚边界，可以进入实现评审；尚未获得实现或发布授权。

## 9. 剩余风险

- `risk_snapshot` 涉及历史增量、持仓、挂单、品种和必要报价；大量账户同时暂停时仍可能增加 Bridge 压力，需要以候选数和耗时决定是否把间隔从 60 秒调高。
- 在阈值附近波动可能出现暂停/恢复切换。本方案保持既有严格边界，不擅自增加滞回区；如实际出现抖动，应另行评审恢复缓冲和最短稳定时间。
- Bridge 长期离线时无法获得权威快照，账户会继续 fail closed；这是安全边界，不是可通过网站缓存规避的故障。
- 修复上线前已发生的暂停没有可靠触发时间，只能从上线后的转换开始完整审计。
- 当前交易记录图表未必保存每个历史时点的净值高水位；本次通过解释和当前指标消除误读，不扩建完整净值时间序列仓库。
- 策略保存后的同步快照可能超过普通 HTTP 交互时限；实施时应允许接口返回“已排队/等待结果”，不能为了即时 toast 延长到不受控等待。
