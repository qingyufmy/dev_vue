# 量见智桥会员变更、授权失效与可恢复退出最终修复方案

## 1. 文档状态

- 状态：方案完成，尚未实施。
- 目标版本：量见智桥公开版本仍为 `3.0.0`。
- 影响范围：网站管理员用户档案更新、网页会话、Bridge 长期授权、Bridge Core 生命周期、Bridge 本地控制与 UI、签名模块更新和同版本完整安装包。
- 不包含：数据库人工修复、生产数据修改、七牛云上传、下载接口切换、网站部署、Bridge 发布激活。上述动作均需在实现和验证完成后按各自授权边界执行。

## 2. 已确认的问题与根因

### 2.1 复现现象

管理员只修改用户会员有效期后，出现以下连锁反应：

1. 当前网页会话要求重新登录；
2. Bridge 的长期刷新凭据被撤销；
3. Bridge 日志出现 `bridge_refresh_revoked`；
4. Bridge Core 退出并被 Launcher 重启，形成约十秒一次的重启循环；
5. Core 重启期间本地控制管道反复消失，UI 的“退出账号”无法完成，只显示通用失败提示；
6. 用户退出网页并重新授权 Bridge 后恢复。

### 2.2 网站端根因

`server/admin/user-profile.js` 当前把以下任一变化都归为 `sensitiveChange`：

- 密码变化；
- 邮箱变化；
- 角色变化；
- 套餐变化；
- 会员有效期变化。

一旦命中，代码同时执行：

- `users.token_version = token_version + 1`；
- `revokeBridgeRefreshSessions()`；
- `disconnectUserSockets()`，关闭网页和 Bridge 连接。

这里混淆了两类语义：

- 密码、身份邮箱、角色、全端退出属于账号安全事件，撤销全部会话是正确的；
- 套餐和有效期属于会员权益事件，不应让用户退出网页，也不应销毁 Bridge 长期授权。

正常支付续费路径直接更新套餐和有效期，当前不会调用 Bridge 会话撤销；因此本次问题主要发生在管理员用户档案修改路径，而不是所有续费都会必然触发。

### 2.3 Bridge 端根因

Bridge 传输层能把 `bridge_refresh_invalid`、`bridge_refresh_revoked` 和 `bridge_session_revoked` 映射为“需要重新授权”，但 Core 生命周期仍将连接运行时返回的错误向上抛出。`run_connected_profile()` 随即取消：

- 本地控制服务；
- 更新检查任务；
- 观摩档案运行时；
- 状态监控和连接运行时。

Launcher 再启动 Core 后，同一无效凭据仍然存在，于是再次失败。UI 已有较明确的授权失效文案，但因为 Core 和本地控制服务没有稳定存活，用户无法正常执行退出或重新授权。

### 2.4 与产品硬边界的冲突

当前行为违反以下既定边界：

- 网站授权只负责服务器连接，不得阻止本地 MT4/MT5 发现和本地采集；
- 会员到期只应暂停服务器连接，续费后应自动恢复，不应要求重新授权；
- 长期授权真正失效时，客户端应稳定进入“需要重新授权”状态，而不是退出循环；
- 用户必须始终能够退出账号或重新授权，不能因远端授权失效而卡死本地 UI。

## 3. 最终目标

修复后必须同时满足：

1. 管理员延长或缩短会员有效期、调整会员套餐时，网页不被强制退出，Bridge 长期刷新凭据不被撤销。
2. 会员仍具备 Bridge 权限时，现有 Bridge 连接继续工作；无需重新授权。
3. 会员变为无权限或已过期时，只暂停 Bridge 的服务器连接，本地终端发现、采集、SQLite 和 UI 继续工作；恢复有效会员后自动重连。
4. 密码重置、身份邮箱变化、角色变化、全端退出、账号删除等安全事件仍然撤销网页令牌和 Bridge 长期凭据，不降低安全性。
5. Bridge 长期刷新凭据确实失效时，Core 不退出、不重启循环；停止远端连接后稳定显示“授权已失效，请重新登录”。
6. “退出账号”在已失效、未授权、服务器离线和连接重试状态下均幂等可用。
7. 对外版本保持 `3.0.0` 时，必须通过经过同版本修复演练的完整安装包覆盖交付；当前 3.0.0 客户端不会接受另一个 3.0.0 模块清单。

## 5. 网站端修复

### 5.1 拆分变更分类

在 `server/admin/user-profile.js` 将当前单一 `sensitiveChange` 拆为至少三类：

1. `securityCredentialChange`
   - 密码变化；
   - 身份邮箱变化；
   - 角色变化；
   - 未来明确列入安全域的账号状态变化。
2. `membershipChange`
   - 套餐变化；
   - 会员有效期变化。
3. `profileChange`
   - 昵称、手机、头像等普通资料变化。

只有 `securityCredentialChange` 执行 `token_version + 1`、撤销 Bridge 刷新会话和关闭全部用户 WebSocket。

### 5.2 会员变化的即时生效

会员变化不修改 `token_version`，不撤销 Bridge 刷新会话，不关闭浏览器会话。

- 新权益仍允许 Bridge：不强制断开现有连接；后续请求和页面刷新自然读取新权益。
- 新权益不允许 Bridge：只调用 `disconnectUserBridgeConnections()`，使用稳定原因 `bridge_membership_required`；不得调用会同时关闭浏览器的 `disconnectUserSockets()`。
- 权益恢复：不撤销、不重新配对。处于会员暂停状态的 Bridge 按既有退避机制重新刷新票据并自动连接。

权益判断必须复用服务器现有 Bridge 会员准入规则，禁止在管理员服务中复制一套容易漂移的判断。若当前准入函数不可复用，先抽取为无副作用公共 helper，再由 Bridge 刷新、Gateway 鉴权和管理员更新共同调用。

### 5.3 事务和失败语义

- 用户字段更新和安全事件的 `token_version` 递增、刷新会话撤销继续放在同一事务中。
- WebSocket 关闭属于事务提交后的进程内副作用。
- 会员变化的数据库更新成功后，再按最终权益决定是否关闭 Bridge 连接。
- 如果关闭连接失败，不回滚已经正确保存的会员数据；记录稳定错误和审计事件，由 Gateway 的周期资格复核兜底。
- 不新增数据库表或迁移。

### 5.4 管理后台请求约束

管理后台虽然继续允许提交完整表单，但后端必须以“标准化后的旧值与新值差异”判断事件类型，不能因字段被重复提交而误判。审计继续记录：

- 原套餐和新套餐；
- 原有效期和新有效期；
- 是否发生密码重置、邮箱变化、角色变化；
- 是否触发安全会话撤销；
- 是否只触发 Bridge 会员暂停。

## 6. Bridge 端修复

### 6.1 将授权错误从进程级失败降为连接级状态

Core 必须明确区分：

- `bridge_membership_required`：会员暂停，可重试，不清理长期凭据；
- `bridge_refresh_invalid`、`bridge_refresh_revoked`：长期凭据不可再使用，进入稳定未授权状态；
- `bridge_session_revoked`：先尝试使用长期凭据刷新；只有服务端进一步返回 refresh invalid/revoked 才清理长期凭据；
- 网络、HTTP 5xx、超时：保留凭据，按有界退避重试。

出现长期凭据不可用时：

1. 原子清理当前档案的无效凭据；
2. 停止远端 Transport、命令和服务器观察任务；
3. 保持本地 MT4/MT5 发现、Worker、数据采集、SQLite、状态文件、UI 和本地控制管道运行；
4. 将运行时发布为 `pairing_required`，携带可展示但不泄露敏感信息的稳定错误码；
5. 等待用户重新授权或主动退出，不让 `run_connected_profile()` 把该状态作为 Core 致命错误返回。

不得通过 Launcher 无限重启来恢复授权。

### 6.2 保证退出账号永远可用

`LocalControlAction::Logout` 必须满足：

- 凭据存在时删除；
- 凭据已经不存在时也返回成功；
- 服务器离线、会员失效、刷新令牌失效时不访问远端；
- 清理完成后触发本地生命周期切换到未授权态；
- 不删除 SQLite、平台选择、终端绑定、服务器自定义地址或历史数据；
- 不关闭 MT4/MT5。

UI 对本地控制失败需显示可行动的错误，不再统一显示“暂时无法完成操作”。如果 Core 尚未升级或管道确实不可用，完整安装包修复是兜底；本轮不让 UI 绕过 Core 直接操作加密凭据，以避免双写、锁冲突和权限漂移。

### 6.3 防止重启风暴

新增生命周期回归和运行时保护：

- 同一个无效 refresh token 只产生一次状态转换和一次脱敏警告；
- 状态稳定后不得每几秒重复启动/停止 observer runtime；
- `pairing_required` 等待期间更新检查、本地控制和 UI 保持存活；
- 新凭据写入后只启动一次新的远端连接；
- 停止、退出和更新 drain 均保持幂等。

### 6.4 发布包归属与更新限制

本次 Bridge 改动位于 `AURUMBridge.Core.exe`，如 UI 文案或错误映射需要调整则同时包含 `AURUMBridge.exe`。两者都属于发布脚本生成的签名 `core.zip` 模块，因此代码范围本身不要求修改 Launcher、Installer、安装路径、ACL、MT4 EA 或 MT5 Worker。

但是当前 Update Coordinator 以语义版本为升级门槛：检查、恢复 staging 和 activation 都拒绝 `target_version <= current_version`。所以“文件属于 core 模块”只说明它可以被更高版本模块更新替换，不代表 3.0.0 可以自动更新到另一个 3.0.0。此次保持公开版本不变，必须使用完整安装包的同版本 repair 路径覆盖安装。

## 7. 测试与验收

## 8. 发布方式判断

### 8.1 网站更新能解决什么

先部署网站端修复可以阻止新的错误撤销：以后管理员只修改套餐或有效期，不再让网页退出，也不再撤销 Bridge refresh token。

但网站更新不能恢复已经被标记为 revoked 的长期凭据，也不能替换本机旧 Core 的错误生命周期。因此已经出现重启循环的客户端仍需要：

1. 安装修复后的 Bridge 二进制；
2. 对已经被撤销的账号重新授权一次。

### 8.2 同版本模块更新能否修复

不能。虽然签名 `core.zip` 包含：

- `AURUMBridge.Core.exe`；
- `AURUMBridge.exe`；
- Launcher 的版本内副本；
- Core 所需运行时和配置。

但当前旧 3.0.0 客户端在 `check_and_stage`、staged restore 和 activation 三处都要求目标语义版本严格大于运行版本。新的 ReleaseId 不会绕过这一比较。向 current endpoint 发布另一个 `3.0.0` 清单，旧客户端会按设计忽略，不能完成覆盖。

如果把公开版本提升为 `3.0.1`，健康运行的旧 3.0.0 可以走模块更新；但这不符合本次“仍为 3.0.0”的明确要求，而且已经陷入快速重启的客户端仍不能把自动更新视为可靠恢复入口。

### 8.3 为什么必须重新生成完整安装包

本次必须生成新的完整 `3.0.0` 安装包，并使用安装器的同版本 repair/覆盖安装路径。原因有两个：

1. 旧 3.0.0 更新器不会接受同版本模块；
2. 当前受影响客户端会在 `bridge_refresh_revoked` 后很快结束 Core 生命周期，更新任务也会被取消。

安装包内部仍必须嵌入经过签名和哈希验证的 core、MT5 和 MT4 包；“必须使用完整安装包”不等于降低模块签名要求。

用户无需先卸载。只有在 `test-local-full-installer.ps1` 证明同版本 repair 能保留偏好、SQLite、终端绑定和服务器地址后，才允许告知用户直接覆盖安装。已被撤销的 refresh token 无法由安装包恢复，覆盖后仍需重新授权一次。

### 8.4 同版本 3.0.0 发布约束

- 对外版本仍显示 `3.0.0`，不得改成 3.0.1 或内部假版本。
- 安装包内嵌签名清单仍生成新的唯一 `ReleaseId`，用于完整性和审计，不用于绕过客户端的语义版本升级门槛。
- 模块和安装包使用新的内容寻址路径；七牛云已存在对象不得覆盖。
- 更新清单和模块包必须继续使用 P-256 签名，并校验大小、SHA-256、版本和签名。
- 完整安装包可以按项目既定授权使用未签名 Authenticode 构建，但这不豁免模块和清单密码学签名。
- 不向 current update endpoint 发布同版本清单并声称可以自动覆盖；旧客户端会忽略它。
- 不修改公钥，不修改协议兼容号，不修改 MT4 EA/MT5 Worker 版本，除非实现阶段实际触及它们。

### 8.5 发布前门槛

本次发布模式固定为 **Full installer**，不再以同版本模块更新演练决定模式。上传前必须完成：

1. 隔离首次安装演练；
2. 从旧 3.0.0 到新 3.0.0 的同版本 repair 演练；
3. 偏好、SQLite、终端绑定、服务器地址和安装根保留验证；
4. 安装后 Core 不再重启循环，未授权态本地控制可用；
5. 重新授权后远端连接恢复；
6. 安装包版本、大小、SHA-256、Authenticode 状态和内嵌签名包验证。

网站端修复必须先部署，避免修复中的客户端继续被错误撤销。

## 9. 发布与部署顺序

### 阶段 1：实现和本地验证

1. 修复网站管理员用户档案变更分类。
2. 修复 Bridge 授权失效状态机和幂等退出。
3. 完成定向、全量及真实进程测试。
4. 对最终 diff 做安全与兼容审查。

### 阶段 2：先部署网站修复

1. 提交并推送精确网站修复提交。
2. 通过正式网站部署流程部署虚拟机和公网服务器。
3. 验证健康检查、静态资源和管理修改接口。
4. 用隔离测试账号验证会员延长不退出、会员失效只暂停 Bridge、恢复后自动重连。

这一阶段不运行生产 SQL，不做手工数据库修改。

### 阶段 3：生成 Bridge 发布物

1. 运行发布 preflight 和完整测试。
2. 生成新的同版本 `3.0.0`、唯一 ReleaseId 的 release 目录。
3. 构建并签名模块清单与包，验证签名、大小和 SHA-256。
4. 构建完整离线安装包。
5. 完成隔离首次安装和同版本覆盖修复演练，确认用户偏好、SQLite、终端绑定和服务器地址按合同保留。
6. 用撤销 refresh token 的旧安装状态覆盖安装，确认修复后稳定进入重新授权态并可正常退出、配对。

### 阶段 4：上传与激活

1. 验证七牛云访问；上传到不可变内容寻址路径。
2. 对比远端字节、大小和 SHA-256。
3. 先更新网站安装包描述和下载接口，再部署精确提交。
4. 更新安装包 descriptor、前端 fallback 和经授权的新安装 bootstrap；不发布同版本 current manifest 作为自动更新。
5. 验证版本 API、下载 URL、安装包哈希、内嵌签名清单和网站健康。
6. 先安排少量受影响客户端覆盖安装，观察 Core 重启率和重新授权结果，再扩大下载提示范围。

## 10. 回滚方案

### 网站回滚

- 回滚到上一稳定应用提交，不执行数据库回滚，因为本方案不引入迁移。
- 如果会员变更副作用异常，先停止管理员用户档案相关写操作，再修复应用；禁止手工改生产会话表。

### Bridge 回滚

- 本次不激活同版本模块 current manifest；若实现期间另有更高版本模块发布，必须作为独立发布处理。
- 新安装包异常：恢复上一份 bootstrap/download 指针；不可变对象保留审计，不覆盖或删除。
- 已覆盖安装的客户端如果发现异常，使用上一份经过验证的完整安装包 repair；不得覆盖七牛云不可变对象。

## 11. 第一轮复审：需求覆盖与最小改动

### 11.1 检查结论

- 覆盖了用户提出的两个直接问题：修改会员导致网页和 Bridge 同时失效；Bridge 授权失效后无法退出。
- 复用了现有会员准入、Bridge refresh、Gateway 周期资格复核、CredentialStore、本地控制和签名更新体系，没有另建会话系统。
- 无数据库迁移，无清库，无 MT4/MT5 Worker、历史同步、安装路径或 ACL 变更。
- 区分了正常续费、管理员手工改会员、安全凭据变化和真正的 Bridge refresh 撤销。
- 初稿中“任何会员变化都主动断开 Bridge”会造成有效续费或延长时无意义重连，属于设计过度。

### 11.2 第一轮调整

- 改为只有最终权益不允许 Bridge 时才立即断开 Bridge；有效续费、延长或仍有效的缩短不主动断开。
- 明确浏览器会话与 Bridge 连接使用不同副作用函数，会员事件禁止调用 `disconnectUserSockets()`。
- 明确不让 UI 直接删除凭据，凭据写入仍由 Core 单写者负责。
- 初稿把完整安装包定位为兜底；第一轮尚未检查旧更新器是否支持相同公开版本的不同 ReleaseId，这一点留到发布兼容复审确认。

第一轮复审后，方案满足最小改动和业务边界要求。

## 12. 第二轮复审：兼容、安全、并发、恢复与发布

### 12.1 检查结论

- 安全性：密码、邮箱、角色和全端退出仍递增 `token_version` 并撤销 Bridge refresh，不因会员修复削弱安全会话撤销。
- 会员恢复：refresh 凭据保留，现有 `bridge_membership_required` 可有界重试，续费不需要重新配对。
- 并发与幂等：会员数据库事务先提交，连接关闭后执行；Gateway 周期资格检查提供跨进程兜底；Logout 对缺失凭据幂等。
- 异常恢复：Core 进入稳定未授权态而不是退出；远端连接失败不会停止本地终端能力。
- 数据与迁移：不修改数据库结构，不删除 SQLite、绑定、偏好或服务器配置。
- 时间语义：有效期继续沿用现有服务器会员判断，不在 Bridge 本地自行计算会员日期。
- 发布兼容：Core/UI 位于 `core.zip`，但旧 Update Coordinator 明确拒绝 `target_version <= current_version`；新的 3.0.0 ReleaseId 不能对旧 3.0.0 自动更新。
- 回滚：网站应用、current manifest 和 bootstrap/download 指针均可独立回滚。

### 12.2 第二轮发现与调整

第二轮发现，若把 `bridge_session_revoked` 与 refresh token 撤销完全等同，会在短期连接票据或会话被关闭时误删仍有效的长期凭据。方案已调整为：

- `bridge_session_revoked` 先走一次长期 refresh 恢复；
- 只有 refresh 接口明确返回 `bridge_refresh_invalid` 或 `bridge_refresh_revoked` 才清理本地长期凭据。

第二轮还发现初稿关于“同版本模块更新可以作为主路径”的判断不成立。方案已调整为：

- 公开版本保持 3.0.0 时，发布模式固定为完整安装包；
- 不激活同版本 current manifest 并声称可以自动更新；
- 必须完成旧 3.0.0 到新 3.0.0 的同版本 repair 演练；
- 覆盖安装后，对已被服务端撤销的账号仍需重新授权一次；
- 只有未来提升语义版本时，才把签名模块更新作为旧 3.0.0 的自动交付路径。

完成上述调整后再次核对安全、幂等、恢复和回滚，未发现需要新增迁移、协议破坏或扩大修改范围的问题。方案可进入实施。

## 13. 剩余风险

1. 当前 3.0.0 客户端不会接受另一个 3.0.0 模块更新；用户必须覆盖安装新的完整安装包。
2. 管理后台所在进程之外可能还存在同用户的其他 Gateway 实例；需要依赖既有跨实例连接管理或周期资格复核，部署验证时必须覆盖多实例环境。
3. 管理员把 Pro 改为 Plus/free 后，网页继续登录是预期行为，但 AI 页面权限应立即按新套餐重新读取，需做浏览器回归。
4. 自动清理无效 Bridge 凭据后，观摩档案的授权恢复语义必须与默认档案分别测试，禁止管理员凭据误清理观摩源凭据。
5. 同版本覆盖安装是否完全保留当前安装数据，必须以 `test-local-full-installer.ps1` 的同版本 repair 结果为准；演练失败即停止上传。
6. 本方案尚未实施、构建、上传或部署；任何发布结论都以实现后的测试、签名和远端字节验证为准。
