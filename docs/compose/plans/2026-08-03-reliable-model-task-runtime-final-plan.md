# AI 模型任务可靠运行时最终方案

> 状态：最终实施方案，已完成第二遍反向故障审查，尚未实施
>
> 审查基线：`dev_codex` @ `b648138ab5962eca732c5a01d4a637a688111c11`
>
> 日期：2026-08-03
>
> 适用范围：自动推理、手动分析、模型比较、日复盘、月复盘、记忆压缩及其模型调用、任务状态、终端时间证据、重启恢复和管理界面
>
> 本文是方案与验收合同，不代表功能已经上线。

## 1. 最终裁决

采用一套统一的、持久化的模型调用运行时，但不把所有业务任务强行改造成同一种执行方式。

最终规则如下：

1. 保留超时和最大输出 token，但改变其职责。
2. 超时只作为分层安全看门狗，不能再被解释成“模型已卡死”。
3. `max_tokens=30000` 作为管理员允许的硬上限，不再要求每次任务都固定申请 30000。
4. 系统根据任务类型、结构化输出规模、输入长度、模型能力和已验证历史数据自动选择本次输出预算。
5. 所有模型调用先进入持久化任务，保存任务、尝试、服务商请求标识、活动状态、结果和应用状态。
6. 自动推理使用同一运行时，但保持“本轮结束后再等待完整间隔”的调度方式；慢推理期间不并发，错过的周期不补跑，过期结果只能留档。
7. 日复盘、月复盘、模型比较和记忆压缩允许长时间后台运行，并通过续租、检查点和重启恢复保证稳定。
8. 月复盘允许分块，但必须完整覆盖全部来源并经过确定性汇总校验；自动交易最终决策不得拆成多个相互独立的模型结论。
9. 模型请求失败、连接中断和服务商状态未知必须分开记录；状态未知时不得盲目重发。
10. 不允许静默切换模型、策略版本、提示词、输出合同或行情快照。

这套设计的目标不是让单次请求永不失败，而是保证：失败可判断、状态可恢复、成本不重复、结果不误用、服务重启不丢任务、交易永不使用过期结论。

## 2. 当前代码基线与已证实缺口

### 2.1 已有可复用能力

当前系统并非从零开始，以下能力应保留并纳入统一运行时：

- `server/routes/ai/llm.js` 已按协议发送 `max_tokens` 或 `max_output_tokens`，并有结构化 JSON 校验和一次修复调用。
- 自动推理已使用 Redis 锁和 30 秒续租，并在写信号、交付和下单前检查锁所有权。
- 自动推理已经冻结推理快照，并限制过大的自动推理提示输入。
- `period_review_jobs`、`memory_compression_jobs` 和 `ai_model_compare_jobs` 已有各自的任务记录。
- 复盘任务已有幂等键、重试、事件和进度阶段。
- 模型比较已经锁定策略版本、快照、输出合同和取消信号。
- 模型调用已经记录请求字节、响应字节、总 token、持续时间和配额预留。
- 私有策略、平台策略、私有模型和平台模型已有授权边界；最终方案不得破坏这些边界。

### 2.2 已确认正确：自动推理成功后从完成时间重新冷却

`scheduler.js` 当前在成功完成后按“完成时间 + 完整间隔”计算下一轮，并用 `inFlight`、Redis 锁和续租阻止同一策略、品种并发。测试也明确要求不对齐墙上时钟固定点。

这个行为应保留：若模型运行 8 分钟、间隔为 5 分钟，应在第 8 分钟结束后再等 5 分钟，而不是立即补跑已经错过的周期。长期调度偏移是可接受的，防止慢推理演变成连续推理更重要。

当前剩余问题在失败路径：模型已经发起后若返回 `ai_failed`，首次只冷却 60 秒，之后为 120、240、300 秒。慢请求持续超时或失败时，可能形成“长时间推理—短暂等待—再次推理”的高占用循环。最终方案必须让所有已经发起服务商请求的终态都至少等待完整配置间隔。

### 2.3 P0：复盘任务租约不会在模型运行期间续期

日复盘初始租约为 300 秒，月复盘为 420 秒。`setPeriodReviewJobStage()` 只更新进度和时间，不延长 `lease_expires_at`。

后果是长请求仍在运行时，租约可能过期并被其他 worker 重新领取，造成重复请求、重复费用和最终写入竞争。

### 2.4 P0：日/月复盘没有使用模型配置的请求超时

自动推理会传入 `request_timeout_ms`，但日复盘和月复盘调用 `requestJsonObject()` 时没有传 `timeout`，实际回退到 120 秒。

同一会话此前对虚拟机使用日志的核查显示，正常复盘请求最长已经接近 107 秒，四次失败在约 120 秒处整齐中断。当前 120 秒不是可靠的异常识别线，而是误伤正常长推理的固定边界。

### 2.5 P1：同步非流式请求无法判断模型正在思考还是链路半开

`trackedModelRequest()` 当前等待 `fetch()` 和完整 `response.json()`。请求开始后，直到完整响应或异常前没有服务商状态、增量输出或请求 ID。

因此系统目前只能确认：请求已在本地发出、连接尚未返回或已经返回。它不能准确声称“模型仍在工作”，也不能准确声称“模型已经卡死”。

### 2.6 P1：一次业务任务可能连续消耗多个完整超时窗口

初次请求、空响应重试和格式修复各自使用同一个完整超时值。若配置为 300 秒，一次业务任务最坏可能等待接近 900 秒，而外层任务租约仍按另一套固定时间计算。

最终运行时必须使用一个任务总期限，每个后续阶段只能消费剩余时间，不能重新获得完整预算。

### 2.7 P1：没有检查输出截断的标准信号

当前解析路径未把 Chat Completions 的 `finish_reason=length` 或 Responses 的 `incomplete_details` 提升为独立失败类型。被截断内容可能先进入 JSON 修复，掩盖“输出预算不足”这个真实原因。

### 2.8 P1：token 日志不能支持可靠的自适应预算

当前主要记录总 token，无法稳定区分输入、输出、推理和缓存 token。总 token 很高不代表输出接近上限，不能直接用来学习下一次 `max_output_tokens`。

### 2.9 P1：模型比较和记忆压缩的重启恢复仍不完整

- 模型比较虽然持久化任务，但服务重启后会把未完成任务标记为 `history_compare_interrupted`，不会从检查点恢复。
- 记忆压缩使用 180 秒固定租约且没有续租，模型请求仍使用默认 120 秒。
- 无服务商请求 ID 时，进程退出后无法确认外部请求是否仍在执行或已经计费。

## 3. 必须长期成立的可靠性不变量

以下任一条不能满足，就不得开启自动执行：

1. 同一业务幂等键只能应用一次模型结果。
2. worker 失去租约或 fencing token 后，不能写最终结果或产生业务副作用。
3. 模型结果、业务应用和交易执行是三个不同阶段，模型成功不等于信号已发布，更不等于订单已执行。
4. 自动推理必须冻结策略 ID、策略版本、模型配置版本、提示词哈希、输出合同哈希、行情快照哈希、MT 时间依据和本轮周期身份。
5. 自动推理的结果在执行前必须重新验证周期身份、行情新鲜度、账户归属、Bridge generation、持仓、挂单、策略版本和平台开关。
6. 迟到、来源不完整、状态未知或结构化输出不完整的自动推理结果只能审计，不能执行。
7. 任何重试都必须说明前一次是明确失败、仍在运行还是状态未知。
8. 不支持幂等或查询状态的服务商，在请求结果未知时不得立即重复提交。
9. 不得把流连接仍然打开、收到心跳或服务商返回 `running` 之外的本地等待状态表述成“模型确定正在工作”。
10. 最大 token 和任务期限不足时必须显式失败或安全降级，不得静默截断必要证据、漏掉持仓管理组或伪造完整结果。
11. 自动推理不允许静默切换备用模型；复盘等非交易任务若未来允许切换，也必须创建新的明确尝试并显示模型变化。
12. 一轮自动推理结束后必须先进入完整冷却；冷却期间不得补跑错过的周期，也不得并发创建第二个模型请求。
13. 决策数据使用冻结的 MT4/MT5 服务器时间及其 UTC 映射；无法确认时间或行情状态时，自动新增风险必须失败关闭。
14. 凡界面标注为 MT4/MT5 时间，数据库统一以 UTC 毫秒作为时间基准；前端优先采用事件时区快照，没有快照时使用 Bridge 当前返回的可信终端时区进行显示换算。禁止回退到应用服务器北京时间；只有 UTC 或 Bridge 时区本身不可用时才显示“时间待终端校准”。

## 4. 总体架构

### 4.1 采用“通用调用信封 + 业务任务表”，不建立第二套业务主账

保留现有业务任务表：

- `period_review_jobs`
- `ai_model_compare_jobs`
- `memory_compression_jobs`
- 自动推理现有调度、快照和信号表

新增三张通用表，只负责模型调用，不复制复盘、信号、记忆或比较结果的业务状态：

| 表 | 职责 |
| --- | --- |
| `ai_model_tasks` | 一次可恢复模型任务的身份、冻结输入引用、期限、预算、总体状态和最终结果摘要 |
| `ai_model_task_attempts` | 每次初始请求、扩容重试、格式修复、异步轮询对应的服务商请求和计量 |
| `ai_model_task_events` | 只追加的阶段、活动、错误、恢复、取消和业务应用审计 |

各业务任务通过 `model_task_id` 引用通用任务。自动推理通过 `inference_task_id` 关联快照和信号。不得把复盘内容、交易信号或记忆正文复制为另一套相互竞争的主账。

### 4.2 `ai_model_tasks` 最小字段

任务至少保存：

- `id`：UUID。
- `task_kind`：`auto_inference`、`manual_analysis`、`model_compare_unit`、`daily_review`、`monthly_review_chunk`、`monthly_review_merge`、`memory_compression`。
- `owner_user_id`、`strategy_id`、`strategy_version` 和授权作用域。
- `domain_type`、`domain_id` 和全局唯一 `idempotency_key`。
- `source_snapshot_id`、`input_hash`、`prompt_hash`、`output_contract_hash`。
- 冻结的 `model_profile_id`、provider、model、protocol、credential source；不得保存明文密钥。
- `status`、`priority_class`、`attempt_count`、`max_attempts`。
- `scheduled_at_utc_msc`、`task_deadline_at_utc_msc`、`result_valid_until_utc_msc`。
- `lease_token`、`fencing_token`、`lease_expires_at`、`last_activity_at`。
- `input_tokens_estimated`、`output_tokens_selected`、`context_window_tokens`、`provider_output_cap`。
- `result_hash`、`result_ref`、`finish_reason`、`incomplete_reason`、`last_error_code`。
- `created_at`、`submitted_at`、`completed_at`、`applied_at`。

大体积提示和行情证据继续保存在推理快照或业务证据表。通用任务只保存引用和哈希，避免敏感行情、账户信息和提示词被无期限重复保存。

跨进程排序、租约、期限和冷却截止时间一律使用 UTC 毫秒或数据库 UTC 时间；MT4/MT5 服务器时间、偏移和来源作为独立决策证据保存。worker 使用本地单调时钟计算单次进程内耗时，不能用应用服务器的北京时间字符串决定跨进程租约是否过期。数据库时间是领取、续租和冷却的最终权威，并监控应用服务器、数据库和 Bridge 的时钟偏差。

### 4.2.1 统一终端时间证据合同

模型任务、信号、交易审计和复盘事件只保存一个可排序的绝对时刻，并把终端时间作为证据视图：

- `event_at_utc_msc`：事件绝对时刻，是排序、租约、去重和列表分页的唯一时间依据。
- `trading_account_id`、`terminal_instance_id`：事件所属交易账户和终端；多账户记录不得借用页面当前账户。
- `terminal_timezone_offset_minutes`：可选的事件时区快照，用于跨夏令时边界时保持历史显示精确；旧记录没有快照时允许使用当前 Bridge 可信时区作为纯显示兜底。
- `terminal_clock_status`、`terminal_clock_source`、`terminal_clock_sample_id`：记录偏移为何可信以及来自哪个终端样本。
- `terminal_time_text` 由 UTC 时刻与“事件快照优先、当前 Bridge 时区兜底”的显示偏移派生，不作为排序或交易业务判断字段。

偏移不得写死为 UTC+2、UTC+3 或其他固定值。MT5 优先使用连续终端时钟样本；MT4 使用可验证的当前终端偏移；首次安装且没有可信记录时，只能在经纪商身份一致且观摩源证据未过期时采用默认观摩源。休市期间不通过停滞 tick 猜测新偏移，而是继续使用最后一条未过期的可信记录；超过可信期限后显示“时间待终端校准”。

历史兼容采用统一 UTC 显示链路：旧记录若在冻结行情中同时保存了至少两组一致的 `time_server_msc` / `time_utc_msc`，可以回填事件偏移；没有事件偏移但已有 UTC 时刻时，由前端使用 Bridge 当前可信时区换算。若旧表只保存了应用服务器 `created_at`，迁移时先按既有 Asia/Shanghai 存储约定一次性转换为 UTC，前端不直接使用北京时间字符串。列表和详情调用同一个前端解析器，因此打开详情不会改变同一条记录的显示时间。当前 Bridge 时区兜底只用于界面显示，不得用于交易窗口、风控或自动执行判断。

### 4.3 `ai_model_task_attempts` 最小字段

每次服务商调用至少保存：

- `task_id`、`attempt_no`、`phase`。
- `provider_request_id` 和经能力验证后才发送的 `provider_idempotency_key`。
- `status`：提交前、已提交、运行中、状态未知、已完成、明确失败、已取消。
- `request_started_at`、`provider_accepted_at`、`last_activity_at`、`response_received_at`。
- `request_bytes`、`response_bytes`。
- `input_tokens`、`output_tokens`、`reasoning_tokens`、`cached_tokens`、`total_tokens`。
- `finish_reason`、`incomplete_details`、HTTP 状态和标准化错误。
- 连接、首字节、活动间隔和总持续时间。

### 4.4 状态机

```text
queued
  -> leased
  -> preparing
  -> submitted
      -> provider_running
      -> provider_quiet
      -> status_unknown -> reconciling
  -> response_received
  -> validating
      -> repairing
      -> retry_wait
  -> result_ready
  -> applying
      -> succeeded
      -> completed_stale
      -> completed_rejected

明确终止：cancelled、failed_terminal、succeeded、completed_stale、completed_rejected
可恢复状态：queued、leased、submitted、provider_running、provider_quiet、status_unknown、reconciling、retry_wait、result_ready、applying
```

`status_unknown` 不是失败终态。它表示请求可能已被服务商接受，但本系统暂时无法证明完成或失败。

## 5. 服务商能力适配

### 5.1 不再把“OpenAI 兼容”当成能力保证

每个 provider/model profile 使用能力注册表：

```text
supports_stream
supports_async_submit
supports_request_status
supports_idempotency
supports_cancel
supports_structured_output
supports_usage_split
context_window_tokens
max_output_tokens
```

能力来自服务端白名单和管理员测试结果，不能根据接口路径或模型名称猜测。未经验证的能力默认关闭。

### 5.2 统一适配器合同

适配器只提供通用动作：

- `submit()`：提交请求并提取服务商请求 ID。
- `stream()`：读取增量事件并更新活动时间。
- `poll()`：查询已提交请求状态。
- `cancel()`：请求服务商取消。
- `parseUsage()`：拆分输入、输出、推理和缓存 token。
- `classifyError()`：区分提交前失败、服务商明确拒绝、可重试、配额耗尽和状态未知。

不支持某项能力时返回明确的 `unsupported`，不得假装已实现。

### 5.3 “模型是否在工作”的准确口径

界面和日志只使用以下事实状态：

| 状态 | 可以确认的事实 |
| --- | --- |
| 已提交 | 本地已发送；若有请求 ID，则服务商已接收 |
| 服务商处理中 | 服务商状态接口明确返回运行中 |
| 持续接收 | 流式响应仍有增量事件 |
| 等待响应 | 连接未结束，但没有足够证据证明模型仍在计算 |
| 疑似停滞 | 超过活动告警阈值，需要查询或继续观察，不等于已卡死 |
| 状态未知 | 连接丢失且无法确认服务商最终状态 |

心跳只能证明连接或状态查询通道仍活跃，不能证明模型正在产生新的语义进展。

## 6. 分层期限与看门狗

### 6.1 四层时间控制

| 层级 | 作用 | 是否可因活动续期 |
| --- | --- | --- |
| 连接期限 | DNS、TCP、TLS、发送前故障，建议初始 15 秒 | 否 |
| 活动告警 | 流或状态查询长时间无活动，触发查询和告警 | 可以，但不直接判失败 |
| 单次尝试安全上限 | 防止半开连接、SDK 或服务商无限挂起 | 仅在能力明确且有活动证据时按策略延长 |
| 业务任务期限 | 决定结果是否仍有业务价值 | 不得突破 |

数据库租约是第五个独立机制，只表示哪个 worker 有权推进任务。租约必须由 worker 定期续期，不能依赖模型进度回调。

### 6.2 总预算约束

一次业务任务只有一个总期限：

```text
remaining = task_deadline_at - now
phase_deadline = min(attempt_safety_deadline, remaining)
```

初始请求、扩容重试和格式修复都消耗同一份 `remaining`。任何阶段不得重新获得完整超时窗口。

### 6.3 初始安全上限

以下是第一版保守上界，不是每次都等待到上界：

| 任务 | 单次尝试硬上限 | 整体任务上限 |
| --- | ---: | ---: |
| 自动推理 | 系统上界 10 分钟，且不得超过冻结行情有效期 | 行情、决策 K 线和任务安全期限中的较早者 |
| 手动分析 | 系统上界 15 分钟 | 30 分钟 |
| 日复盘 | 系统上界 20 分钟 | 60 分钟 |
| 月复盘单个分块/汇总 | 系统上界 20 分钟 | 6 小时 |
| 模型比较单个模型/样本单元 | 系统上界 15 分钟 | 24 小时 |
| 记忆压缩单个分块 | 系统上界 15 分钟 | 60 分钟 |

这些值通过按 provider、model、task kind 和复杂度统计的 p95/p99 调整，但永远受系统上界、管理员手动安全上限、模型能力和业务期限约束。`timeout_mode=auto` 时，系统按任务选择单次尝试期限；`timeout_mode=manual` 时，管理员值只允许进一步收紧该期限，不能突破系统或业务上界。现有 `request_timeout_ms` 在迁移前作为手动值兼容保留，不能继续无条件覆盖所有任务。

自动推理可能被行情或决策 K 线有效期提前终止。即使管理员把模型请求上限设置得很大，也不能突破交易结果有效期；终止后仍要执行完整冷却，不能立即启动下一轮。

## 7. 自适应最大输出 token

### 7.1 30000 的最终语义

管理员设置的 `30000` 表示该模型配置允许系统申请的最大输出上限，不表示每次任务都必须传 30000，也不表示模型必须生成 30000。

简单任务可以选择 2000，复杂策略和大覆盖复盘可以逐步提高到 30000。系统不得超过：

1. 管理员硬上限；
2. 已验证的服务商输出上限；
3. 模型上下文窗口减去输入估算和安全预留后的剩余空间；
4. 当前任务类型允许的上限。

### 7.2 选择公式

```text
schema_need   = 根据必填字段、数组项数、持仓管理组数和文本上限估算
history_need  = 同 provider/model/task/complexity 桶的可靠输出 p95 * 1.35
task_need     = max(task_floor, schema_need, history_need)
context_room  = context_window - estimated_input - safety_reserve
selected      = min(profile_hard_cap, provider_output_cap, task_cap, context_room, task_need)
```

输入 token 优先使用 provider/model 对应 tokenizer；没有可靠 tokenizer 时采用经过校准的保守估算并保留至少 15% 上下文安全空间。若 `selected < schema_need`，系统不得直接发出明知装不下的请求，必须先执行该任务允许的分块或安全失败。

历史学习只使用能可靠拆分 `output_tokens` 且完整完成的请求。现有只有总 token 的旧日志只用于耗时和成本观察，不能用于输出预算学习。

### 7.3 预算不足时的处理

- 自动推理先执行无损压缩和确定性去重，不删除策略要求的周期、持仓管理组、挂单管理组或必要风险证据。
- 若完整的自动交易输出合同仍放不下，返回 `output_budget_insufficient` 并 HOLD，不拆分最终交易决策。
- 日/月复盘按交易或日期分块，再执行完整覆盖汇总。
- 模型比较按模型和样本单元拆分。
- 记忆压缩按相同作用域和适用条件分组，不合并互相矛盾的经验。

### 7.4 截断处理

检测到 `finish_reason=length`、`incomplete_details` 或等价服务商信号时：

1. 不把响应送入普通 JSON 修复。
2. 标记 `output_truncated` 并记录已使用输出 token。
3. 非交易后台任务若仍有时间、服务商已明确完成前一次请求且上限仍可提高，可以创建一次扩容重试。
4. 自动推理本轮不立即扩容重试：记录实际用量，在完整冷却后的下一轮使用新行情和提高后的预算。
5. 任何不完整的自动推理都失败关闭；部分交易计划不得执行。

格式修复只用于允许多次调用的非自动交易任务，并且只能处理字段名、类型、枚举和缺失字段，不能根据截断片段重新推导交易语义。自动推理不发起第二次格式修复请求。

## 8. 各任务的执行政策

| 任务 | 时效 | 可分块 | 重启后 | 迟到结果 | 重试规则 |
| --- | --- | --- | --- | --- | --- |
| 自动推理 | 严格行情和账户新鲜度；完成后完整冷却 | 最终决策不可分块 | 恢复状态；不补跑错过周期 | 留档，不发布、不交易 | 服务商请求一旦发起，本轮不立即重试；下一轮使用新快照 |
| 手动分析 | 用户可见期限 | 原则上单次 | 返回任务页继续查看 | 可展示并标明耗时 | 用户可重试或取消 |
| 日复盘 | 无交易执行时效 | 交易过多时可分块 | 续租、检查点恢复 | 正常保存 | 明确失败自动退避重试 |
| 月复盘 | 长后台任务 | 必须支持按日分块 | 续租、检查点恢复 | 正常保存 | 分块级重试，不重跑已验证分块 |
| 模型比较 | 无交易执行时效 | 按模型/样本 | 从完成单元恢复 | 正常保存 | 只重跑失败单元 |
| 记忆压缩 | 低优先级 | 按作用域/条件 | 续租、来源哈希复核 | 来源变化则废弃 | 来源未变且明确失败才重试 |

## 9. 自动推理专用流程

### 9.1 完成后冷却，不对齐固定时槽

为每个策略、品种和实际启动周期生成稳定周期键：

```text
strategy_id + strategy_version + symbol + cycle_started_at_utc_msc + cycle_sequence
```

任务开始时同时冻结 MT4/MT5 服务器时间、可信时区映射、目标 K 线身份和实际采用的时区来源。休市或首次安装场景继续使用系统已经确定的默认观摩源时区规则，但不得为了对齐墙上时钟创建额外推理。

下一次允许发起模型请求的时间为：

```text
next_model_request_not_before = attempt_terminal_at + max(configured_interval, failure_backoff)
```

若本轮模型调用 8 分钟、配置间隔 5 分钟，则完成后再冷却 5 分钟。8 分钟内错过的计划周期全部丢弃，不补跑、不排队、不并发。失败退避大于配置间隔时使用更长值。

只有尚未发起模型请求的前置条件等待，例如 Bridge 离线、市场休市或行情尚未同步，才允许使用短周期状态检查；这些检查不能调用模型。

### 9.2 冻结输入

创建任务时冻结：

- 策略及版本；
- 模型配置及版本；
- 系统提示、用户提示和输出合同哈希；
- 决策 K 线和所有行情证据；
- MT 服务器时间、时区偏移、UTC 映射和数据采集时间；
- 账户归属历史、Bridge generation、持仓和挂单管理组；
- 平台开关与用户自动交易授权快照。

同一周期不进行第二次自动模型请求。下一周期重新读取并冻结最新行情，但不得悄悄更换本轮已经记录的策略、模型或提示合同。

### 9.3 结果有效期

```text
result_valid_until = min(
  market_snapshot_valid_until,
  decision_bar_valid_until,
  account_state_valid_until,
  task_safety_deadline
)
```

结果返回后执行两次门禁：

1. 写信号前验证周期身份、策略版本、行情、账户归属、Bridge generation、持仓和挂单。
2. 向 Bridge 发送命令前再次读取实时状态和报价并重新验证。

任一门禁失败，任务转为 `completed_stale` 或 `completed_rejected`。结果可以用于复盘模型质量，但不得形成可执行交付。

### 9.4 重试和状态未知

- DNS、TLS、参数校验等明确发生在服务商接收前的失败可以安全重试。
- 有服务商请求 ID时优先轮询和恢复，不创建重复请求。
- 无请求 ID且连接在提交后中断时进入 `status_unknown`。
- `status_unknown` 未解决前不自动重发同一交易任务。
- 状态确认完成、失败或过期后，从该终态时间开始执行完整配置间隔冷却；不能立刻新建请求。
- 已经发起过服务商请求的自动推理，无论成功、超时、截断、校验失败还是普通模型失败，本轮都不立即请求第二次。
- 自动推理不切换备用模型。模型不可用时本轮 HOLD。

### 9.5 业务应用幂等

`ai_signals` 增加唯一 `inference_task_id`。从 `result_ready` 应用到信号时使用事务和 fencing token：

1. 锁定模型任务和目标周期。
2. 验证任务仍由当前 worker 持有且未应用。
3. 重新执行结果有效性门禁。
4. 插入一次信号或写入明确的拒绝终态。
5. 使用 outbox 推送界面事件。

订单执行继续使用现有订单意图、库存锁、Bridge operation ID 和执行前风控，不由模型任务表替代。

## 10. 日复盘与月复盘

### 10.1 立即修正的共同问题

- 复盘调用读取冻结模型配置的 `request_timeout_ms`，但最终由任务剩余期限约束。
- worker 每 30 秒续租，租约建议保持 120 秒滚动窗口。
- 续租失败立即设置 fencing token 失效；当前请求可以被取消，但不能写最终版本。
- 每次进度、服务商活动和轮询只追加事件；租约续期由独立定时器完成。
- 复盘版本增加唯一 `source_model_task_id`，防止两个 worker 重复写版本。

### 10.2 日复盘

交易数量和输出合同在单次模型能力内时保持单次调用。超出预算时按 `outcome_id` 稳定分块，每块返回逐交易评估和局部总结，最终汇总必须验证所有 outcome 恰好出现一次。

### 10.3 月复盘

月复盘采用两级流程：

1. `monthly_review_chunk`：按日期范围处理已冻结的日复盘和行情摘要。
2. `monthly_review_merge`：读取全部已验证分块，生成跨日模式、优势、风险和下月行动。

必须保存：

- 预期日复盘 ID 集合及来源哈希；
- 每个分块覆盖的日复盘 ID；
- 汇总实际引用的日复盘 ID；
- 已确认和未确认来源的边界；
- 互相矛盾经验的冲突分组。

汇总前后执行确定性覆盖校验：不得遗漏、重复、合并或虚构日期。任何分块来源变化时，只废弃受影响分块和汇总，不重跑仍有效的分块。

月复盘可以运行很久，但不会让单个 HTTP 请求无限运行，也不会因服务重启从头重算整月。

## 11. 模型比较、手动分析和记忆压缩

### 11.1 模型比较

现有任务拆成持久化单元：

```text
job -> model -> snapshot/sample -> provider attempt -> evaluation
```

每个完成单元保存输入哈希、模型配置、原始结果哈希和评分结果。重启后从首个未完成单元继续；策略版本、快照指纹或输出合同不一致时整个任务明确失效，不拼接新旧结果。

### 11.2 手动分析

短请求可以继续等待并返回；超过前端同步等待阈值后返回 `202 + task_id`，用户通过任务状态查看、取消或稍后取结果。断开浏览器不自动取消已提交任务，除非用户明确取消。

### 11.3 记忆压缩

保留当前来源集合哈希和写入前二次验证。增加续租、分块、服务商状态和重启恢复。来源集合在运行期间变化时任务终止为 `source_stale`，不得把旧摘要应用到新集合。

记忆压缩属于低优先级队列，不能占满自动推理或交互任务的服务商并发额度。

## 12. 并发、配额和重复计费控制

### 12.1 三类队列

- `execution_critical`：自动推理，只服务当前有效周期。
- `interactive`：手动分析和用户主动模型测试。
- `background`：复盘、比较和记忆压缩。

按 provider/model profile 设置并发和速率限制，并使用加权公平调度。对存在自动推理计划的 provider/model 保留执行关键容量，并在自动推理冷却即将结束时停止领取会占满容量的后台分块。后台任务不得堵塞自动推理，但自动推理也不得通过无限并发触发服务商限流。

### 12.2 配额账本

使用日志增加 `input_tokens`、`output_tokens`、`reasoning_tokens`、`cached_tokens`、`provider_request_id` 和 `accounting_status`。

状态未知时：

- 不把 token 记为 0 并视为无成本；
- 保留最初的保守预留，标记 `usage_unknown`；
- 能查询服务商用量时对账后结算；
- 无法查询时按策略在观察期后结算为保守估计，并单独统计不确定成本。

### 12.3 幂等边界

只有能力注册表明确支持时才发送服务商幂等键。通用代码不得向所有兼容接口盲发未知 header。

本系统仍必须通过数据库唯一键和业务应用幂等防止本地重复，即使服务商不支持请求幂等。

## 13. 重启、发布与恢复

### 13.1 优雅停止

收到停止信号后：

1. 停止领取新任务。
2. 标记 worker 为 draining。
3. 持续保存已获得的服务商请求 ID和最后活动时间。
4. 在有限退出窗口内完成可快速结束的验证和事务。
5. 不能完成的任务保留为可恢复状态，不改成普通失败。

### 13.2 启动恢复

- 有请求 ID和状态查询能力：继续轮询原请求。
- 有流恢复能力：从保存的 cursor 恢复。
- 无恢复能力且请求已提交：进入 `status_unknown`，不盲目重发。
- 只在明确失败或服务商确认不存在原请求时进入 `retry_wait`。
- `result_ready` 或 `applying` 任务重新执行幂等业务应用，而不是重新请求模型。

### 13.3 数据保留

- 事件和尝试保留满足审计的必要期限。
- 大体积原始响应按引用和压缩存储，并对账户敏感字段应用现有授权边界。
- 定期归档终态任务；不得删除仍处于 `status_unknown` 或待对账状态的记录。

## 14. 管理界面和用户状态

### 14.1 模型配置

模型编辑界面调整为：

- `最大输出令牌` 改名为 `模型输出硬上限`，说明 30000 是上限而非固定用量。
- 新增 `任务预算：自动管理`，默认开启。
- 现有 `请求超时` 移到高级设置，改名为 `单次请求安全上限`。
- 手动模式允许在 30 秒到 30 分钟之间进一步收紧单次请求；超过范围的长任务通过分块和任务总期限解决，不靠无限放大单次 HTTP 超时。
- 显示已验证的上下文窗口、输出上限、流式、状态查询、取消和幂等能力。

### 14.2 任务状态

用户可见状态使用自然中文：

- 排队中
- 正在准备
- 已提交给模型
- 服务商处理中
- 正在等待响应
- 正在校验
- 正在修复格式
- 状态暂时无法确认
- 正在恢复
- 已完成
- 已完成但结果已过期
- 已完成但未通过执行门禁
- 将自动重试
- 已失败
- 已取消

“疑似停滞”必须附带事实依据，例如最后活动时间、是否有服务商请求 ID和下一次状态查询时间，不能直接显示“模型卡死”。

## 15. 实施顺序

### 阶段 0：紧急可靠性收口

- 日/月复盘立即读取当前模型的 `request_timeout_ms`，并让 worker 在模型调用期间独立续租；这是完整运行时上线前的兼容修复。
- 保留自动推理成功后完整间隔冷却；把超时、截断、校验失败和 `ai_failed` 等所有已发起模型请求的终态改为至少冷却完整配置间隔。
- 自动推理关闭同一周期内的空响应重试、格式修复和扩容重试；下一轮使用新行情重新推理。
- 初始请求、空响应重试和格式修复先共享一个外层总期限，避免三个完整超时窗口叠加。
- 识别 `finish_reason=length`、`incomplete_details` 和等价截断信号，自动交易截断结果立即失败关闭。
- 为以上行为补充回归测试，并单独发布，不与完整运行时迁移混在一个提交。

### 阶段 1：补齐观测和能力基线，不改变业务结果

- 增加 token 拆分、finish reason、incomplete details、服务商请求 ID和尝试阶段日志。
- 建立 provider capability 注册表和管理员能力测试。
- 为当前各任务记录耗时 p50/p95/p99、截断率、修复率和状态未知率。
- shadow 记录不得增加一次额外服务商请求。

### 阶段 2：通用模型任务信封

- 新增三张通用表、claim/renew/fencing、事件和适配器接口。
- 先以 shadow 方式包裹现有调用，只记录任务，不改变结果路径。
- 验证新旧调用结果、费用和状态完全对齐。

### 阶段 3：复盘和记忆压缩

- 先迁移日复盘，再迁移月复盘和记忆压缩。
- 增加租约续期、任务总期限、分块、覆盖校验和重启恢复。
- 这是低交易风险且最能验证长任务稳定性的第一批 enforce 场景。

### 阶段 4：模型比较和手动分析

- 模型比较改为检查点恢复。
- 手动长分析改为异步任务。
- 验证取消、恢复、公平队列和配额结算。

### 阶段 5：自动推理 shadow

- 为自动推理创建冻结任务、周期键和 `next_model_request_not_before`。
- 新运行时计算有效期、重试和最终门禁，但仍由当前执行路径产生业务结果。
- 对比两套路径的任务身份、结果、迟到判定和信号资格；不得发送两次模型请求。

### 阶段 6：自动推理 enforce

- 切换为通用任务驱动信号应用。
- 先只生成建议，不自动交易。
- 再按策略、品种、观摩源和少量账户逐步开放自动交易。
- 保留按任务类型、provider/model 和策略的独立回退开关。

### 阶段 7：界面收口与旧字段退役

- 默认展示自动管理，保留高级硬上限。
- 观察至少一个完整月复盘周期后，才评估退役旧的直接调用和旧状态字段。
- 迁移期间只做增量字段和双读兼容，不自动重写用户模型配置。

## 16. 发布阻断验收

### 16.1 通用运行时

- 两个 worker 同时领取同一任务，只允许一个 fencing token 应用结果。
- 租约续期失败后旧 worker 即使收到模型结果也不能写业务状态。
- 初始请求、扩容和修复共享一个总期限。
- 服务重启后，有请求 ID的任务继续查询，无请求 ID的已提交任务进入状态未知。
- 状态未知不会触发立即重复请求，配额预留不会被错误结算为 0。
- `finish_reason=length` 和 `incomplete_details` 不进入普通格式修复。
- 输入、输出、推理、缓存和总 token 可分别记录。
- provider 不支持的 stream、poll、cancel 或幂等能力不会被调用。

### 16.2 自动推理

- 5 分钟配置在模型分别耗时 10 秒、4 分钟和 8 分钟时，都从本轮终态后再等待完整 5 分钟。
- 模型运行期间不会启动第二轮，错过的周期不会在结束后补跑。
- 同一策略、品种同时只有一个自动推理任务和一个可应用信号。
- 已发起模型请求后，无论成功、超时、截断、空响应、校验失败还是模型失败，本轮都不会立即发起第二次模型请求。
- 首次模型失败的实际冷却不少于配置间隔，而不是固定 60 秒；连续失败可在此基础上进一步指数退避。
- 模型在有效期后返回时，数据库可见结果但不会创建可执行信号或订单。
- 重试使用完全相同的策略版本、提示哈希、输出合同、行情快照和 MT 时间映射。
- 服务商状态未知、行情不新鲜、时区不可信、账户换绑、Bridge 重连、持仓变化、策略版本变化和平台开关变化均失败关闭。
- 管理员硬上限 30000 时，简单任务可选择更小预算；复杂但合法任务允许选择到 30000，并验证实际请求字段正确。
- 输出预算仍不足时返回 HOLD，不能漏掉部分持仓组后继续交易。
- 自动推理不会切换备用模型。

### 16.3 复盘和后台任务

- 构造超过 20 分钟的慢服务商，租约持续续期且不会被第二个 worker 重领。
- 在月复盘第 N 个分块后重启，恢复时只继续未完成分块。
- 31 个交易日来源必须全部且仅出现一次；删除、替换或重复任一来源都会阻断汇总。
- 日复盘交易数超出单次输出预算时，分块后仍完整覆盖全部 outcome。
- 模型比较重启后从完成单元继续，不再统一标记 `history_compare_interrupted`。
- 记忆压缩来源变化时不会应用旧摘要。

### 16.4 发布与生产验证

- migration 可重复执行，旧数据和旧模型配置无需回填即可继续读取。
- 关闭新开关后可回到旧路径，且不会丢失已完成任务或重复应用结果。
- 正式开启自动交易前，至少完成一次测试环境进程强杀、数据库短暂不可用、Redis 短暂不可用、服务商 429、5xx、半开连接和 Bridge 重连演练。
- 虚拟机发布后核对 commit、migration、worker、健康接口、任务队列、状态未知积压和实时日志。

## 17. 监控与告警

按 task kind、provider、model、策略和复杂度桶统计：

- 排队、首字节、模型持续和总耗时 p50/p95/p99；
- 自动推理占空比、完成后冷却合规率、连续模型请求间隔和有效期内完成率；
- 迟到丢弃率、状态未知率及最长未知时长；
- 输出截断率、结构校验失败率、格式修复率和扩容重试率；
- 请求重复率、业务重复应用率和 fencing 拒绝次数；
- 输入、输出、推理、缓存 token 和不确定费用；
- 复盘来源覆盖失败、租约丢失、重启恢复和积压年龄；
- 自动推理因行情、时间、账户、策略或 Bridge 变化而失败关闭的次数。

硬告警：

- 同一业务幂等键出现多个服务商请求且没有明确重试依据；
- 同一模型任务应用两次；
- 自动推理在完整冷却结束前发起下一次模型请求；
- 慢推理结束后补跑已经错过的周期；
- 迟到自动推理生成可执行信号；
- 租约过期任务仍写入结果；
- 状态未知自动交易任务被重新发送或执行；
- 月复盘来源覆盖不完整却生成版本；
- 输出被截断却通过交易校验。

## 18. 第二遍反向故障审查

### 18.1 P0：统一任务表可能错误地替代业务主账

初始方向若把所有任务、结果和业务状态都塞进一张通用表，会形成新的超大主账，复盘、信号和记忆的业务约束难以保证。

修正：最终方案只增加通用模型调用信封；现有业务表继续是主账，通过 `model_task_id` 关联。

### 18.2 P0：自动推理使用统一长任务规则会执行迟到结论

复盘可以等待数小时，但交易结论不能。若只实现统一重试和恢复，不加结果有效期，稳定运行反而会稳定地执行过期信号。

修正：自动推理有独立 `result_valid_until`、周期身份和两次执行门禁；迟到结果只有审计价值。迟到与否不改变完成后冷却规则。

### 18.3 P0：固定时槽补跑会让慢推理变成连续推理

如果为了消除调度偏移而对齐固定时间点，慢推理结束时下一个时间点可能已经到达，调度器会立即再发起请求；多次错过时还可能产生补跑积压。这比长期偏移更危险。

修正：保留当前成功路径的“终态后完整间隔”，错过周期直接丢弃。所有已经发起模型请求的失败路径也使用 `max(配置间隔, 失败退避)`，自动推理同一周期最多一次服务商请求。

### 18.4 P1：收到流式心跳不等于模型语义仍在前进

若把任意心跳都视为“模型正常工作”并无限续期，服务商也可能永久维持空连接。

修正：活动只推迟疑似停滞告警；绝不能突破单次尝试硬上限和业务任务期限。

### 18.5 P1：假设所有兼容服务商都有异步状态会导致不可恢复

不同服务商对 stream、请求 ID、poll、cancel、幂等和 usage 的支持不同。

修正：引入显式能力注册表；未验证能力默认关闭，状态未知保守处理。

### 18.6 P1：从总 token 学习输出预算会持续高估

复杂策略输入可能很大，但输出很短。使用总 token 计算 `max_output_tokens` 会放大费用预留并掩盖上下文不足。

修正：只有可靠拆分的 output token 才参与自适应；旧总 token 仅用于耗时和成本观察。

### 18.7 P1：月复盘分块可能丢失跨日矛盾

普通 map-reduce 容易把不同市场状态下互相矛盾的经验合并为一条错误规则。

修正：分块按来源 ID、行情状态和适用条件保存，汇总必须做完整覆盖和冲突分组，不能把矛盾经验强行统一。

### 18.8 P1：格式修复可能改写被截断的交易含义

截断不是普通 JSON 格式错误。让修复模型补齐未知尾部可能创造交易动作。

修正：非交易后台任务可以在总期限内按原证据扩容重试；自动推理不进行本轮扩容或格式修复，截断结果失败关闭，完整冷却后的下一轮使用新行情重新推理。

### 18.9 P1：服务重启后盲目恢复会重复计费

没有服务商请求 ID时，进程无法知道外部请求是否成功。立即重新请求可能重复付费，甚至产生两个不同结论。

修正：进入 `status_unknown` 并隔离；自动推理等待状态查明或任务安全期限到达，再从终态开始完整冷却。非交易任务由人工或明确政策处理，不能把未知当作普通失败。

### 18.10 P1：长任务可能耗尽服务商并发，阻塞自动推理

月复盘和模型比较若与自动推理共用无界 worker，稳定的后台吞吐会导致新一轮自动推理请求排队。

修正：三类优先级队列、按 provider/model 的并发限制和加权公平调度是 enforce 前置条件。

### 18.11 P2：自适应预算可能掩盖必要输入被删减

若系统为了适配 token 自动删除周期、持仓组或风险证据，会得到格式完整但业务不完整的交易结果。

修正：自动推理只允许无损压缩；必要合同放不下时 HOLD。复盘分块必须确定性验证完整覆盖。

### 18.12 P2：状态事件和原始响应可能造成存储膨胀或敏感数据重复

长任务的流事件很多，重复保存完整提示、行情和账户信息会迅速增大数据库并扩大授权面。

修正：任务保存引用和哈希；事件限频、原始响应压缩、终态归档，继续沿用策略和账户授权边界。

### 18.13 P2：管理员仍可能把硬上限理解成目标值

只改后端而不改界面，用户仍会认为 30000 没有被使用或必须每次用满。

修正：界面明确显示“系统本次选择 / 模型硬上限 / 选择依据”，默认自动管理。

### 18.14 P1：数据库、应用服务器和 MT 时间混用会错误判定租约、冷却与迟到

当前系统存在北京时间数据库字段、JavaScript UTC 时间和 MT4/MT5 服务器时间并行使用。若新运行时继续混合比较，时区或时钟漂移会让任务提前过期、重复领取、缩短冷却或错误执行迟到结果。

修正：租约、跨进程期限和冷却截止时间以数据库 UTC 时间为权威，任务保存 UTC 毫秒；MT 时间及其偏移只作为交易证据冻结，进程内耗时使用单调时钟，并对三方时钟偏差告警。

### 18.15 P1：后台任务先占满服务商容量会推迟冷却结束后的自动推理

自动推理冷却结束时如果所有 provider 并发都被长月复盘占用，新周期仍会在队列中迟到。

修正：执行关键队列预留 provider/model 容量，临近冷却结束时暂停领取长后台分块；无法获得容量的自动任务按时效失败关闭，不通过超额并发冲击服务商。

## 19. 审查结论与剩余不确定性

第二遍审查后，方案不存在已知的架构性自相矛盾，可以进入分阶段实施，但必须满足以下前置条件：

1. 先统一自动推理所有已发起请求终态的完整冷却，并修复复盘续租和任务总期限，再讨论扩大自动执行。
2. provider/model 的流式、异步状态、取消、幂等、上下文窗口和输出上限必须逐个做真实能力验证，不能只看兼容文档。
3. 自动推理 shadow 阶段不得多发一次服务商请求；只能在同一请求周围记录新任务状态。
4. 自动交易 enforce 前，迟到丢弃、状态未知、fencing、重启恢复和执行前二次门禁必须全部通过故障注入测试。
5. 月复盘分块必须先通过完整来源和矛盾经验测试，不能仅以“最终能生成一段文字”为验收。

仍然存在的外部不确定性是各服务商对请求状态、幂等和精细 usage 的真实支持程度。最终方案已经把这些差异隔离在能力适配器中：能力不足会降低恢复效率，但不会降低交易安全性。
