# 交易执行与周期复盘纠正优化方案

## 1. 方案状态与基线

- 方案性质：诊断后的实施方案；本文件不执行下单、撤单、复盘重跑、数据库修复、服务重启或部署。
- 本地基线：`D:\dev_codex\wall-street-skill-local`，分支 `dev_codex`，提交 `911759fa9018f8c4a037ab8202b5d119916e7e95`，方案编写前工作区干净。
- 虚拟机基线：`192.168.1.254:/www/wwwroot/aurum-ai`，分支 `dev_codex`，提交 `911759fa9018f8c4a037ab8202b5d119916e7e95`；`/health` 返回数据库、Redis 正常。
- 本轮纳入四项已确认问题：
  1. 同一账户、同一策略、同一品种和同一价格区域出现重复挂单；
  2. 订阅用户订单在风险校验通过后，被 Bridge 发送前的第二次终端时钟判断错误拒绝；
  3. 已生成但尚未确认的日/月复盘缺少安全、明确的“重新生成”能力；
  4. 日复盘 v3 结果被长驻旧前端按旧合同渲染，造成“当日经验为空”和结构化结论被泛化文案替代。

## 2. 已确认事实与影响

### 2.1 高风险：提示词限制不能阻止跨周期重复挂单

当前策略正文已经声明同位置重复挂单限制，模型也能看到现有挂单，但仍可能再次输出 `position_action=open`。服务端虽然定义了 `dedup_window_seconds` 和 `dedup_price_atr`，当前下单运行时没有在最终发送前执行实时库存去重。

已在虚拟机确认同一平台策略存在以下未闭合重复组：

- `buy_limit 4405.68`：2 条；
- `buy_limit 4406.50`：4 条。

影响：模型输出具有概率性，单靠提示词不能形成强制约束；重复挂单可能放大风险敞口，并在多个订阅账户上同步复制。

### 2.2 高风险：订阅用户终端时钟在执行阶段被重新判定

订阅用户的风险快照已携带账户级可信 MT4 时钟，但 `sendBridgeCommand()` 在真正发送前重新查询平台市场时钟并再次调用周末风险锁。该第二条路径没有复用刚刚通过风控的同一份时钟证据，因此订单在进入本地 Bridge 前即以“交易平台时间尚未校准”拒绝。

影响：管理员观摩源可正常下单，订阅用户却全部被系统拒绝；拒绝发生在服务器端，终端没有收到命令，也没有产生 MT 票号。

### 2.3 中风险：待确认复盘只能标记问题，不能重新生成

当前 `/api/ai/period-reviews/:id/retry` 只允许 `current_version_id` 为空的失败任务重试，前端也只在 `failed` 状态显示“重试生成”。`draft`、`edited`、`needs_revision`、`deferred` 已有版本，因此点击“标记有问题”只改变状态，不会重新调用模型。

影响：用户无法在保留冻结证据和旧版本的前提下主动生成一个新模型版本，只能继续人工编辑，操作语义与预期不一致。

### 2.4 中风险：新复盘合同被旧前端错误渲染

虚拟机案例 `period_review_case=289`、版本 `158` 已确认：9 个 `daily_review_chunk` 和 1 个 `daily_review_merge` 全部成功，最终 v3 内容包含 6 条完整 `experience_rules`；新版合同按设计不再生成 `daily_lessons`。数据库中的 `repeated_issues` 和 `strengths` 也是不同的中文结构化结论。

截图仍显示旧字段“当日经验”，并把结构化对象经旧字符串本地化路径转换成重复的“系统执行条件未满足，详细信息已记录”。虚拟机当前静态文件与目标提交哈希一致，因此当前案例的数据和模型合并没有丢失；问题发生在部署前已打开、部署后未重新加载的长驻旧 JavaScript 页面。

影响：用户看到的内容与 `current_version_id` 对应的真实版本不一致，可能误判模型结果；更严重的是旧编辑器可能用旧字段合同保存或确认新版内容，因此合同错配必须失败关闭，不能只依靠用户手动强制刷新。

## 3. 最终业务合同

### 3.1 模型与服务端责任边界

- 策略正文继续决定交易逻辑、方向、入场方法和策略特有约束。
- 模型输出属于建议，不能作为资金安全和唯一性约束的最终执行依据。
- 服务端必须机械执行权限、账户归属、风险、幂等、实时库存和同位置重复挂单门禁。
- 服务端门禁只能允许、阻止或解释执行状态，不得改写模型买卖结论。

### 3.2 重复挂单的判定范围

第一版只阻止明确相同的系统挂单，不引入网格、加仓或模糊语义推断：

- 同一交易账户；
- 同一平台策略；
- 规范化后的同一品种；
- 同一交易方向；
- 同一挂单类型；
- 入场价处于服务端配置的相同价格容差内；
- 现有订单仍在终端实时 `pending_list` 中；
- 现有订单能够通过系统 Magic、delivery/outcome/intent 链路证明属于该策略。

人工挂单、其他策略挂单、已成交/已取消/已过期挂单不得被当作本策略重复项，也不得被自动撤销。

### 3.3 复盘重新生成语义

- “标记有问题”：只把当前版本标记为 `needs_revision`，不调用模型。
- “重新生成”：用户显式触发；冻结来源和 `evidence_hash` 不变，生成一个新的模型版本。
- 生成期间保留当前版本可见且只读，不能把页面清空。
- 成功后以新版本原子替换 `current_version_id`，并以旧版本作为父版本；失败时仍保留旧版本和 `needs_revision` 状态。
- 已批准复盘禁止直接重新生成；需要先走明确的撤销/新修订治理流程，本批次不新增该能力。

### 3.4 日复盘展示与版本一致性

- `daily-period-review-v3` 的权威经验字段是 `experience_rules`，不得恢复 `daily_lessons` 或建立第二套经验正文。
- 页面把 `experience_rules` 显示为“当日经验（确认后沉淀）”，逐条展示条件、动作、风控、失效、禁止行为、来源交易和置信度。
- API 返回的 `output_contract_version`、服务端要求的前端合同版本与当前 JavaScript build 必须可比较。
- 当前前端不支持服务端合同、静态资源 build 过旧或结构化对象落入旧字符串渲染器时，必须停止编辑和确认，显示“页面版本已更新，请刷新后继续”。
- 页面长驻期间发现新 build 时，若没有未保存编辑和进行中写操作，可提示并安全刷新；存在未保存内容时只能提示用户确认刷新，不得静默丢失编辑。
- 刷新只重新加载页面和当前 case，不重跑模型、不新建版本、不改变确认状态。

## 4. 修复设计

### 4.1 服务端实时重复挂单硬门禁

在 `server/routes/ai/scheduler.js` 已有账户—品种库存锁内部、最终 `executeOrderCore()` 之前增加统一门禁：

1. 获取 `trading_account_id + normalized_symbol` 库存锁；
2. 在锁内重新拉取该执行账户最新 `positions` 和 `pending_list`；
3. 只保留能证明属于当前策略的系统挂单；
4. 用方向、挂单类型和价格容差匹配重复项；价格容差使用现有 `dedup_price_atr`，并设置不低于品种 tick size 的下界；
5. 命中时不发送 Bridge `open` 命令，订单意图以稳定原因 `duplicate_live_pending` 结束，并记录冲突挂单票号、来源 signal/delivery/outcome 和命中阈值；
6. 未命中才进入现有风控和发送链路；在发送前仍保留现有信号幂等校验。

取消后替换必须走独立的显式状态机：先根据原信号分发记录取消指定系统挂单，刷新终端确认旧票号消失，再允许创建新挂单。不得把“发现重复”解释为自动取消旧单或自动替换。

首版不增加策略例外开关。以后若产品明确支持网格或同区间分层挂单，再新增版本化结构策略字段和独立验收；禁止用自然语言提示词绕过硬门禁。

- `server/routes/ai/scheduler.js`
- `server/routes/ai/risk-policy.js`（仅复用/明确阈值语义，不扩大用户可编辑范围）
- 可新增纯函数模块 `server/routes/ai/live-pending-dedup.js`
- `tests/ai/scheduler-*.test.js` 及新的纯函数回归测试

### 4.2 订阅执行时钟证据单一化

在风险快照创建时形成不可变的 `execution_clock_context`，至少包含：

- `user_id`、`trading_account_id`；
- `terminal_instance_id`、`broker_server`、`login`；
- `timezone_offset_minutes`、`clock_status`、`clock_source`；
- 校准时间和允许的新鲜度上限；
- 风险快照/订单意图绑定标识。

`scheduler -> executeOrderCore -> sendBridgeCommand` 全链路传递该对象。Bridge 发送前只做以下机械校验：

1. 账户、终端、经纪商和登录身份必须与当前路由一致；
2. 状态必须属于现有可信状态集合；
3. 证据未超过允许新鲜度；
4. 周末/交易时段锁使用这份已验证上下文计算。

不得回退到管理员观摩源时钟、用户级共享时差、固定 UTC+3、北京时间或客户端任意参数。若身份不符或证据过期，可尝试一次账户级可信时钟刷新；仍不可信则明确失败关闭，并区分“风险快照无时钟”“路由身份变化”“时钟已过期”。

### 4.3 待确认复盘显式重新生成

新增与失败重试语义分离的服务方法和接口，例如：

- `POST /api/ai/period-reviews/:id/regenerate`
- `/aurum-api` 保持同路由兼容。

事务内执行：

1. 校验 actor scope、case 未批准、证据完整且存在当前版本；
2. 锁定 case、job 和当前版本，确认没有 unresolved model task；
3. 保留 `current_version_id`，记录 `parent_version_id` 和当前 `evidence_hash`；
4. 为本次显式生成创建新的业务幂等键，重置已终态 job 或安全建立新的 job attempt；
5. worker 继续使用同一冻结来源、策略和记忆快照规则；
6. 成功后创建 `version_no + 1`，CAS 更新 `current_version_id`；
7. 失败时保留旧版本、恢复 `needs_revision`，并显示可读错误。

前端仅在 `draft`、`edited`、`needs_revision`、`deferred` 且没有进行中任务时显示“重新生成”。点击前确认“会产生新模型调用并保留旧版本”；提交后禁用重复点击并轮询 job 状态。

### 4.4 日复盘 v3 合同握手与失败关闭

后端和前端增加轻量、通用的版本一致性机制，不针对案例 ID 或策略名称编写分支：

1. 服务端在周期复盘详情或统一 AI runtime capabilities 响应中返回稳定的 `frontend_contract_version`、支持的 `period_review_contracts` 和当前 `ai_frontend_build`；响应禁止缓存。
2. `public/ai/app.js` 声明自身 build 与支持的复盘合同集合。加载详情前先比较服务端合同；不支持时不进入旧版 editor。
3. 对未知合同、v3 结构化数组进入 legacy 路径、对象被传给 `userVisibleText()` 等情况增加显式保护，展示刷新提示并禁用保存、标记问题、确认和经验沉淀。
4. 页面在后台低频检查 no-cache build manifest。仅当无未保存编辑、无活动弹窗确认、无进行中 mutation 时允许用户一键刷新；否则保留当前页面并明确提示先保存或放弃编辑。
5. 保持全站共享 `?v=` 缓存键合同，只更新 AI `app.js` 的功能级 `build=` 标记；不得单独修改共享 `v=` 破坏其他入口的缓存测试。
6. 刷新后重新请求当前 case，并核对 `current_version_id`、`content_hash` 和 `output_contract_version` 后再开放编辑。

## 5. 实施顺序与验收门槛

### 批次 A：实时重复挂单门禁

- 先实现纯判定函数和审计字段，再接入库存锁内的发送前路径。
- 同时覆盖管理员平台账户和所有订阅账户，不为用户角色建立两套判断。
- 验收：同一实时挂单存在时 Bridge `open` 调用次数为 0；其他策略、人工挂单、不同方向、不同挂单类型和超出容差的价格不被误拦截。

### 批次 B：时钟证据贯穿

- 将同一风险快照的账户级可信时钟传递到最终发送。
- 验收：订阅用户使用其本人终端时钟完成周末锁校验；身份或新鲜度不满足时仍失败关闭；管理员和现有历史/查询命令不受影响。

### 批次 C：复盘重新生成

- 后端事务与幂等先行，再添加按钮、确认提示和状态展示。
- 验收：标记有问题不会调用模型；显式重新生成产生一个新版本；失败不丢旧版本；重复点击、并发 worker 和服务重启不产生多个有效新版本。

### 批次 D：v3 前端合同一致性

- 先实现未知合同失败关闭和对象渲染保护，再增加 build manifest/能力握手和刷新提示。
- 把“将沉淀到策略记忆库的经验”统一命名为“当日经验（确认后沉淀）”，继续使用 `experience_rules` 结构。
- 验收：旧 build 或未知合同不能保存/确认；刷新后案例 289 直接显示现有 6 条经验，无模型调用和版本变化；有未保存编辑时不会自动刷新。

### 批次 E：虚拟机验收

- 先部署代码并核对精确提交与 `/health`；不自动进行真实下单。
- 使用只读/模拟门禁验证已有重复挂单会被识别。
- 真实订阅账户验证需由用户明确授权一次受控测试订单；核对风险、intent、Bridge ledger 和 MT 票号全链路。
- 复盘重新生成测试使用非批准测试 case；案例 289 只验证现有版本的前端展示，不重跑、不编辑、不确认。

## 6. 测试矩阵

### 6.1 重复挂单

- 同账户、同策略、同品种、同方向、同类型、同价；
- 同价但不同策略或人工 Magic；
- 同价但不同方向/挂单类型；
- 价格距离刚好在阈值内、阈值外及 ATR 不可用；
- 旧 outcome 显示 open 但终端已无订单；
- 两个调度周期并发、Bridge 超时重试、服务重启恢复；
- 管理员和多个订阅账户分别只检查本账户库存。

### 6.2 终端时钟

- MT4 `mt4_current_offset` 和 MT5 `progressing_tick`；
- 订阅账户与观摩源 broker 相同但 login 不同；
- 风险后到发送前终端路由切换；
- 时钟刚好在新鲜度边界内/外；
- 周末锁允许、拒绝以及无可信时钟；
- 非交易命令和历史读取不错误复用下单时钟上下文。

### 6.3 复盘重新生成

- `draft/edited/needs_revision/deferred` 可显式生成；
- `approved/generating/superseded` 拒绝；
- 证据不完整、证据 hash 变化、当前版本 CAS 冲突；
- 日复盘多分块检查点、月复盘检查点和 provider status unknown；
- 成功版本父子关系、失败保留旧版本、刷新后状态一致；
- `/api` 与 `/aurum-api`、桌面端和移动端按钮一致。

### 6.4 前端合同与缓存

- v2、v3 和未知 `output_contract_version`；
- 当前 build、旧 build、服务端与静态资源发布短暂错位；
- v3 结构化 `repeated_issues/strengths/experience_rules` 不经过通用字符串本地化；
- build 更新时页面空闲、有未保存编辑、有进行中 API mutation；
- F5、强制刷新、长时间打开页面后重新进入同一 case；
- 案例 289 刷新前后 `current_version_id=158`、`content_hash` 和经验规则数量保持不变；
- 桌面端、移动端和键盘操作均能看到刷新提示，不出现无限刷新循环。

## 7. 数据、迁移、观测与回滚

### 7.1 数据与迁移

- 本方案优先复用已有 risk snapshot、order intent、delivery、outcome、model task、period review job/version 字段，预计不需要数据库迁移。
- 前端 build/合同能力使用代码常量或现有系统能力响应，不新增持久化表，不回写复盘内容。
- 不修改既有迁移正文，不自动清理重复挂单，不回写历史复盘版本。
- 若实现阶段发现必须新增字段，需追加新迁移并重新复审；不得把运行时回填塞进启动迁移。

### 7.2 观测

新增稳定指标/审计：

- `duplicate_live_pending` 命中次数，按策略、账户、品种和挂单类型聚合；
- 时钟上下文来源、年龄、身份匹配结果和最终 Bridge 是否收到命令；
- 复盘 regenerate 请求、成功版本、失败码、重复请求去重和旧版本保留状态。
- 前端合同不匹配次数、旧 build 命中次数、刷新提示结果和被保护的旧编辑器写操作次数；不得记录复盘正文。

日志和 API 不返回完整账号、登录凭据、模型提示词或其他用户订单数据。

### 7.3 回滚

- 重复门禁出现误杀：关闭新增门禁调用点，但保留审计记录；不得自动补下被拦截订单。
- 时钟证据链异常：回滚到上一版本并暂停自动交易发送；禁止恢复到固定时区或观摩源兜底。
- 复盘重新生成异常：隐藏新按钮并停止新 job 领取；已生成版本和旧版本全部保留。
- 合同握手异常：保留未知合同失败关闭，关闭自动刷新提示；不得退回把结构化对象强转字符串的旧渲染路径。
- 回滚代码不撤单、不平仓、不删除复盘或任务数据。

## 8. 案例 289 的修复边界与验收基准

虚拟机案例 `289`、版本 `158` 的只读证据表明：

- 9 个 `daily_review_chunk` 和 1 个 `daily_review_merge` 全部成功；
- v3 最终版本包含 6 条完整 `experience_rules`，不存在 `daily_lessons` 字段是新版合同的设计结果；
- 数据库中的 `repeated_issues` 和 `strengths` 是不同的中文结构化结论，并非截图中的两组相同泛化句；
- 虚拟机实际 `app.js` 与本地提交哈希一致，且当前前端会把 v3 经验显示为“将沉淀到策略记忆库的经验”。

截图仍显示旧字段“当日经验”，并把结构化对象经过旧版字符串本地化后显示为“系统执行条件未满足，详细信息已记录”。这说明截图页面运行的是旧渲染分支，最可能是部署后未重新加载的长驻旧 JavaScript；不是本次模型分块或最终合并丢失经验。

本方案现已纳入静态资源版本握手、前后端合同不一致失败关闭、安全刷新提示、v3 经验区命名优化及浏览器验收。实施仍不得重跑、编辑、确认或删除案例 289；它只作为既有数据的只读显示验收样本。

## 9. 第一轮复审：需求覆盖、边界与过度设计

### 9.1 复审发现

1. 仅加强策略提示词仍无法形成确定性执行保障；重复挂单必须由服务端实时库存门禁负责。
2. 若按订单价格全局去重，会误拦截其他策略和人工订单；必须限定账户、策略、品种、方向、类型和系统归属。
3. 若 Bridge 发送前完全取消时钟校验，会放大路由切换风险；正确做法是传递并重新验证同一份绑定时钟证据。
4. 把“标记有问题”直接等同重新生成会意外产生费用；必须保留两个显式动作。
5. 为未来网格策略预建复杂例外系统超出当前需求。
6. 只修改缓存键可以解决一次部署后的刷新，但不能阻止未来长驻页面再次运行旧合同；必须增加运行时合同检测。
7. 恢复 `daily_lessons` 会重新形成经验双轨并破坏 v3 统一记忆规则设计。

### 9.2 第一轮调整

- 重复挂单门禁放到最新终端库存刷新之后、Bridge 发送之前，并保留模型原始结论。
- 首版只处理能够证明归属当前策略的系统挂单，不引入网格例外。
- 时钟方案改为不可变上下文贯穿，并在发送前验证绑定与新鲜度，不重复选择另一来源。
- 复盘重试与重新生成拆分；生成失败时保留旧版本。
- 案例 289 的前端异常在用户确认后纳入方案，但修复限定为通用合同握手、失败关闭和正确展示，不修改复盘数据或模型合同。
- 保留 `experience_rules` 为唯一经验来源，只优化用户可见名称和结构化编辑体验。

### 9.3 第一轮结论与剩余风险

方案覆盖用户已确认的四项问题，复用现有库存锁、风险快照、版本、任务状态机和 v3 经验规则，没有引入第二套交易或复盘系统。剩余风险是价格容差的品种精度、时钟新鲜度边界、长耗时复盘的并发状态，以及版本检测造成刷新循环或丢失编辑，需要第二轮重点核对。

## 10. 第二轮复审：兼容性、幂等、恢复、时间与连带 Bug

### 10.1 复审发现

1. 只查数据库 open outcome 会重现历史残留误判；最终门禁必须以锁内最新终端 `pending_list` 为真相，数据库仅用于归属证明。
2. 两个调度周期可能在第一次刷新后同时下单；门禁必须与发送共享同一账户—品种库存锁，不能在锁外检查。
3. ATR 缺失或异常时若直接放行，仍可能同价重复；必须至少使用品种 tick size/点值下界做精确同价保护。
4. 复用风险时钟如果不绑定 terminal/login，会在账户接管后误用旧证据；身份和年龄必须同时验证。
5. 复盘重新生成若先清空 `current_version_id`，失败或重启会让用户失去可见旧结果；必须直到新版本事务提交前都保留旧指针。
6. 新接口若复用失败 retry 的幂等键，可能加载旧 checkpoint；每次显式 regenerate 必须有新业务键，同时冻结同一 evidence hash。
7. 前端更新后若缓存键不变，会再次出现合同错配；任何前端实施批次必须同步更新静态资源键并测试。
8. 仅靠自动刷新可能在用户编辑时丢失内容，也可能因反向代理短暂返回新旧 manifest 形成循环；必须以用户脏状态、mutation 状态和稳定 build 比较为门禁。
9. 旧前端可能忽略新增 API 字段；服务端不能假定一次部署即可约束已经运行的旧 JavaScript，因此当前存量页面仍需一次人工刷新，新增握手用于保护后续版本。

### 10.2 第二轮调整

- 明确终端实时库存是真相，delivery/outcome/intent 只证明系统归属。
- 把刷新、去重和发送固定在同一库存锁临界区。
- 增加 ATR 不可用时的最小精确价格保护，并要求审计记录实际阈值来源。
- 时钟上下文增加完整终端身份和新鲜度校验；不允许跨账户、跨登录继承。
- regenerate 保留旧版本、使用新幂等键和 CAS 原子切换；失败回到 `needs_revision`。
- 将静态缓存键回归测试列为前端批次阻断门槛。
- 合同不匹配时禁用所有复盘写操作；刷新提示尊重未保存编辑和进行中 mutation，且用稳定 build 值避免循环。
- 明确当前存量旧标签页需要一次 F5/强制刷新，新机制从加载新版前端后开始保护未来部署。

### 10.3 最终剩余风险与实施判定

- 部分经纪商品种后缀、tick size 或 ATR 数据异常可能影响价格容差；上线前必须用真实 XAUUSD 规格校验。
- 账户终端在风险通过后立即切换时，订单将被安全拒绝而不是自动迁移；这是预期失败关闭行为。
- 模型仍可能输出违反策略的其他非机械语义；本批次只强制同位置重复挂单，后续每条硬风险规则都应有独立、可测试的服务端门禁，不能把整个策略解释器复制到后端。
- 重新生成会产生新的模型费用，前端必须明确提示且防重复提交。
- 长驻旧页面在首次加载本修复前无法执行新握手，因此部署验收必须包含一次人工刷新和之后的跨版本模拟。
- 生产真实下单、撤单、复盘重跑以及案例 289 的编辑、确认和数据处理均不在本方案授权内。

第二轮结论：兼容性、归属、并发、幂等、异常恢复、时间证据、缓存、测试和回滚边界已补齐。方案可进入实施，但需等待用户明确授权。
