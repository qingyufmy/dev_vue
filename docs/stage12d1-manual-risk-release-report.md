# 阶段 12D.1：账户风控手动解锁验收记录

> 日期：2026-09-03
>
> 范围：账户级风险触发事件的人工确认、有限解锁、自动失效与审计
>
> 明确不包含：数据库迁移执行、平台全局停机解除、执行意图、Bridge 指令、MT4/MT5 交易

## 1. 阶段结论

账户所有者可以在账户因单日亏损、回撤、每日开仓次数、连续亏损或冷却期被限制后，确认风险并释放当前触发事件。该操作不修改实际指标、不删除原风险事件、不改变自动发送开关，也不允许跳过平台、权限、数据完整性、报价、合约、止损或终端限制。

解锁是独立资源，其策略身份、风险摘要 revision、被释放规则、触发基线、业务日期、失效时间、原因和幂等身份创建后不可改写；只有状态、失效时间和失效原因按有限状态规则迁移。后续风险决定明确关联实际使用的解锁记录。

## 2. 可解锁与不可解锁边界

允许释放的账户级规则：

- `RISK_DAILY_LOSS_LIMIT`
- `RISK_DRAWDOWN_LIMIT`
- `RISK_DAILY_OPEN_LIMIT`
- `RISK_CONSECUTIVE_LOSS_LIMIT`
- `RISK_COOLDOWN_ACTIVE`

以下边界不能通过手动解锁绕过：

- 平台全局 kill switch、账户 kill switch 和关闭的自动发送开关。
- 平台绝对亏损、回撤、开仓次数和连续亏损上限。
- 用户与账户归属、会员、订阅及终端交易权限。
- 账户风险摘要、报价、合约或终端时钟不完整、过期或不可验证。
- 品种、点差、手数网格、止损方向、单笔风险、价格偏移和目标 ticket 校验。

## 3. 生命周期与失效

创建解锁必须携带当前风险摘要 `If-Match`、`Idempotency-Key`、明确的风险确认布尔值和原因。相同幂等键与相同请求返回原结果；相同键但不同内容返回冲突。

解锁只在以下条件全部满足时生效：

1. 状态仍为 `active`。
2. 系统用户、交易账户及平台/账户策略版本均与创建时一致。
3. 当前业务日期仍相同且未超过下一终端本地日期边界。
4. 被释放的风险指标没有相对解锁基线进一步恶化。

风险摘要更新时若发现指标恶化、业务日变化或到期，原解锁转为 `superseded` 或 `expired`，并通过 Outbox 产生小型失效事件。评审落库前还会在同一短事务中再次检查解锁版本和当前风险摘要，迟到结果不能使用已经失效的解锁。

## 4. 数据库与旧数据

新增迁移 `server/db/migrations/20260903_008_manual_risk_release.sql`：

- 新增 `risk_manual_releases`，按账户保存不可变解锁证据和状态。
- `risk_decisions_v4.manual_release_id` 记录一次风险批准实际使用的解锁身份；旧版同名 `risk_decisions` 不做原地改列。
- 平台风险策略通过新增版本加入手动解锁开关和绝对上限，不改写原版本。
- 相同账户、相同触发指纹只能释放一次；相同请求幂等键不能生成第二条记录。
- 旧风险重置记录只有在用户、账户、操作者、时间和触发事件都能精确归属时才允许后续批量迁移，无法归属的记录进入异常清单，不猜测、不删除。

迁移未执行，公网旧表没有改变。

只读复核还确认旧库已有同名但异构的风险策略和决定表。阶段 12D/12D.1 的新表因此使用 `_v4` 旁路后缀，避免部署迁移时静默命中旧表；最终规范名称只会在旧数据完整回填、双读哈希一致且旧程序停用后切换。

## 5. HTTP 与 WebSocket

HTTP：

- `GET /risk-accounts/{account_id}/manual-release` 获取该账户最近一次解锁及其状态。
- `POST /risk-accounts/{account_id}/manual-release` 创建当前触发事件的有限解锁。
- 风险策略响应同时公开只读的手动解锁能力和平台绝对上限，前端可以解释为什么某次触发不能解锁。

WebSocket 只增加 `risk.manual_release.changed`，包含解锁 ID、账户、状态、失效原因和 revision。风险基线、用户原因及完整规则继续通过 HTTP 读取。

## 6. 第一轮复审：权限和产品语义

发现与调整：

- 直接清零亏损或回撤会破坏真实风险事实；调整为独立解锁记录，指标保持原值。
- 只设置一个“已解锁”布尔值会永久绕过限制；调整为绑定当前触发基线、业务日期和策略身份。
- 在全局停机或自动发送关闭时创建解锁会让用户误以为可以交易；调整为明确拒绝创建。
- 风险摘要每次刷新都会改变 revision，若解锁只绑定 revision 会立即失效；解锁改为冻结 revision 作为审计，同时按风险指标是否恶化决定持续有效性。
- 非法终端业务日期可能使到期时间计算抛出未受控错误；调整为创建前严格校验 `YYYY-MM-DD` 及真实日历日期。

第一轮结论：手动解锁是用户主动承担当前账户级风险的有限例外，不是平台风控后门。

## 7. 第二轮复审：并发、幂等和迟到结果

发现与调整：

- 重复请求若先重新评估当前状态，会在状态变化后错误返回失败；调整为先按用户、账户和幂等键恢复原结果，再处理新请求。
- 策略更新后继续使用旧解锁会绕过新边界；解锁必须匹配平台版本、账户版本和账户策略 revision。
- 风险决定开始时看到有效解锁，不代表落库时仍有效；落库前重新锁定并检查解锁、策略和风险摘要。
- 新风险摘要和手动解锁均先锁交易账户，再访问风险状态，避免同账户更新形成反向锁序。
- 账户策略更新或新解锁替代旧解锁时，旧状态也必须逐条产生 Outbox 事件，避免前端继续显示已失效授权。

第二轮结论：当前实现可在不修改 AI 结果、不触达执行域的情况下，提供有限、幂等、可解释和可审计的账户解锁。

## 8. 剩余风险与下一阶段

- 本阶段未在真实 MySQL/MariaDB 上执行迁移；旁路库演练仍需验证 JSON、生成策略版本、外键和历史异常清单。
- 同一业务日恢复后再次以完全相同指标触发，会被相同触发指纹保守识别为已释放事件；后续真实投影若需要精确区分，可增加风险触发 episode ID，但当前不为此引入额外状态机。
- 当前未实现独立的定时到期清理进程；风险评审和 HTTP 读取会实时把过期记录视为无效，持久状态的有界异步清理可在 Worker 运行角色接线阶段增加。
