## 1. 结论与当前优先级

将全量数据库规范化与当前dev_vue无损增量升级作为主线，不涉及公网。沿用现有 MySQL、模块化 Repository、迁移 runner、U1–U6 工作包及 A/B 演练库，不另建迁移框架，不重做已完成的结构安装。

实施顺序：**核实源/目标现状 → 冻结规范和全量字段合同 → 追加目标结构修正 → 逐域转换与独立对账 → 全量演练 → dev_vue同库升级验收**。性能优化贯穿其中，但必须由查询和执行计划证明收益，不能为了减少表数、统一名字或增加外键而搬动数据。

用户后续明确：只要当前dev_vue数据库能正常直接升级。实现必须保持该库的数据接续，不以清空/重建数据库、改连空库或手工搬数据为前提；必要的过渡表可以在同库内由版本化升级器管理。原旁路A/B仅为可选验证手段，不能替代同库升级交付。不涉及公网预检、发布、部署和切流。

本方案细化并承接 [原数据库基线](database-normalization-and-data-migration-plan.md)、[逐表矩阵](database-table-migration-matrix.md)、[M1 回填方案](stage-m1-data-backfill-and-reconciliation-plan.md)、[U1–U6 升级方案](migration/public-upgrade-execution-plan-20260906.md)。既有冻结合同和已执行迁移不得覆盖修改。

## 3. 全库统一规范

以下规则用于新设计及逐项整改。已建结构若不符合，先登记影响和兼容方案；不能全库自动重命名或批量转换类型。

| 维度 | 目标标准 | 必须检查的例外/验收 |
| --- | --- | --- |
| 权威事实 | 每个业务事实只有一个权威实体；当前态、不可变历史、可重建投影职责明确 | JSON副本/Redis缓存标记来源revision及重建方式，不成为第二个写入口 |
| 表与字段名 | 新名称采用业务含义清楚的 snake_case，沿用已冻结物理命名 | `_v4`等已有名称不为美观改名；跨域同名不同义单独整改 |
| 主键与外部ID | 同一引用链类型、长度、有无符号、排序规则一致；API大整数用字符串 | 保留外部ticket/order/deal原始精度和作用域，不把它们等同于内部ID；不强制全库改UUID |
| 账户与租户 | 交易账户实体与用户设置、当前归属、历史区间分开 | 唯一身份按平台/经纪商服务器/登录名的经证实规则定义；服务器大小写归一只作候选，跨平台不得合并 |
| NULL与默认值 | NULL、0、空串、未知状态具有不同语义；必填来自业务约束 | 不用0用户、假日期、默认金额填平迁移异常；先查脏数据，再加NOT NULL |
| 金额与数量 | 金额/价格/手数使用精度明确的DECIMAL或定点文本，币种和单位明确 | 逐字段基于源最大整数位、小数位和业务范围确定精度；禁止盲目统一DECIMAL(18,2)或经JS Number转换 |
| 时间 | 新事实使用UTC会话及DATETIME(3)，业务日期单独声明计算规则 | 旧墙钟保留原值、来源时区、转换版本；DATE不能当UTC瞬间；默认UTC+3仅展示，不是迁移依据 |
| 字符集与排序 | 人类文本使用已确定的utf8mb4规则；机器ID/哈希采用适合其语义的精确比较 | 改排序规则前比较唯一键碰撞、尾空格、大小写和中文排序，不批量ALTER全库 |
| 状态 | 每个实体有独立状态集合、允许转移和历史未知值处置 | 不以一个巨大通用状态表混合支付、执行、审核等语义；ENUM/字典/字符串按实际扩展频率决定 |
| 强关系 | 同事务、同生命周期的关键父子事实优先唯一约束/外键；加约束前查孤儿 | 审计、外部ID和历史快照可显式软引用，但要有对账；禁止对交易/支付历史使用级联删除 |
| JSON与大字段 | 参与过滤、排序、关系和约束的稳定字段列化；大正文与摘要拆分 | 冻结模型输入、原始终端证据可版本化JSON保存；不把每个嵌套字段拆表。载荷保存hash/大小/编码版本 |
| 幂等与并发 | 业务唯一键、幂等键、revision、短事务、固定锁顺序、同事务outbox | 提交结果未知先查回执，不能盲目重试；交易uncertain不能重发 |
| 删除与保留 | 用户生命周期、业务停用和物理清理分开；每域声明保留策略 | 注销用户不得复活；保留历史引用及必要证据，禁止用“表为空/无前端入口”作为删除理由 |
| 查询 | 显式列清单、摘要/详情分离、参数化、稳定游标和账户范围 | 记录每个查询的过滤/排序/返回量；LIMIT绑定按真实mysql2行为验证，不把一次修复扩展成未经验证的统一改写 |
| 迁移 | 只追加迁移；结构、数据转换和应用版本分别可追踪 | bootstrap及001–025冻结；后续版本号由实施时清单分配，不提前生成未审查DDL |

每个例外必须记录责任域、理由、约束替代方案、验证方式和是否有退出条件，不能用一个全局豁免绕过规范。

## 4. 按业务域完成结构与数据规范化

下表表示审查范围，不代表这些候选实体都已建表，也不表示必须新增表。

| 顺序/领域 | 结构工作 | 无损验收重点 |
| --- | --- | --- |
| 1 身份、认证、会员当前态 | 复核users资料/权益/认证职责、会话撤销和注销状态 | 旧用户ID与密码哈希、角色/到期时间精确承接；不把历史Bridge在线状态变成新授权 |
| 2 交易账户、Bridge、观摩 | 账户实体/用户设置/归属区间/设备档案拆清；唯一键与投影来源约束 | 4→3账户只是候选；全部旧ID可追溯，274区间无丢失、重叠或错误新增权限；私人数据不进入观摩投影 |
| 3 策略、订阅、模型与分析 | 版本、发布态、用户级分析与账户级执行分离；任务/尝试/事件及大载荷整理 | 订阅范围、冻结版本、模型配置和历史信号可用；平台user_id=0按专用规则承接，不伪造用户 |
| 4 执行、风控、成交历史 | operation/intent/risk/command/result精确关联；预留、幂等和历史时间审查 | 每账户资金、持仓/成交事实和状态一致；未知归因不猜测，历史导入不触发交易任务 |
| 5 复盘、记忆、审计 | 冻结证据与摘要拆分、版本引用、人工确认和追踪关系 | 全版本/确认人/证据hash保留；迁移不能自动生成记忆或修改策略 |
| 6 支付、权益、推荐 | 订单/链上交易/匹配/权益事件职责与唯一键审查 | 币种、金额、到账状态、权益效果精确对账；历史回填不重复到账或激活权益 |
| 7 课程、内容、社区、文件 | 购买/报名/进度、内容版本、资产引用及权限 | 购买后仍可访问、学习进度不丢、文件真实可读；数据库对账不能替代对象存储校验 |
| 8 通知、宏观数据、系统配置 | 通知事实与投递状态分离、来源/版本/配置类型明确 | 不重发旧通知；宏观记录来源时间不改写；配置/加密数据及外部密钥依赖可恢复 |

跨域依赖先登记成图。采用父事实先于子引用、ID map先于引用转换的顺序；同一事实不得被两个领域writer重复建档。不能承接的活动业务必须补结构与功能，不能全部塞进归档后称为完成。

## 5. 必须交付的全量清单

复用现有U1/U2登记与校验工具，扩充而非另起清单系统：

1. **源/目标结构目录**：每张实际表的列、主键、唯一键、索引、外键、CHECK、引擎、排序规则、触发器/视图/例程/事件，以及结构指纹和采集时间。没有相应对象也记录已核查为空。
2. **逐字段转换合同**：每个源字段只有一个主处置，填写目标实体/字段、类型、NULL/默认值、转换版本、时间/金额规则、映射基数、去重依据、错误处置、独立对账方式和阻断状态。拆分可有多个输出，但主处置不能重复计算。
3. **目标反向覆盖表**：每个目标必填字段、约束和初始化控制行都能追溯到源、确定生成规则或显式空值规则。仅覆盖源字段不足以证明目标可运行。
4. **关系与业务不变量清单**：强/软引用、所有权、唯一身份、金额平衡、区间、当前态与历史一致性逐项可执行检查。
5. **结构整改清单**：问题、实际表/列/查询、影响量、风险、依赖、追加迁移草案、前后兼容、数据预检、回滚和验收SQL。
6. **查询/索引登记表**：Repository入口、作用域、过滤/排序、预期返回列/行、现有索引、执行计划、优化前后证据与写入代价。

JSON/text类型、时间歧义、无父引用或未知状态不得悄悄转换为空。进入异常清单，保留原始行与原因；活动业务受影响的异常未解决则阻断该域上线。

## 6. 性能优化方法和预算

先按接口和任务登记查询，再按“高频 × 扫描量 × 大载荷 × 锁等待”排序。初始复核对象包括交易账户K线查询的外层SELECT *、复盘详情/锁查询和执行预留读取；目前只证明源码存在这些写法，不宣称它们已构成线上慢SQL。

索引候选从等值作用域列、过滤列、稳定排序列推导，依据实际EXPLAIN和数据分布决定；不得见到_id就加索引。主键前缀、复合索引重叠及写入放大一起评估。删除旧索引需要证明业务查询、唯一性、外键及后台任务均不依赖它。

首轮演练设以下**拟定预算**，在记录机器配置、数据规模和并发后冻结，可按证据调整；这些不是当前性能结果：

| 场景 | 初始预算/验收方式 |
| --- | --- |
| 账户/权限单条读取 | 数据库查询p95≤50ms，无非预期大表扫描 |
| 常规分页列表 | 100行以内、查询p95≤200ms；列表不读完整提示词、K线包或复盘证据 |
| 用户写事务 | SQL事务p95≤200ms，外部I/O不在事务内；锁等待/死锁单独记录 |
| 大历史扫描/回填 | 有界主键分页；批量从100–500行候选起步，按载荷字节与事务耗时缩小，不硬编码“全表一次提交” |
| 新索引 | 同等数据和负载比较查询时延、扫描行、写入时延和磁盘增量；只有读收益或完整性收益明确才保留 |

执行计划分析使用授权的镜像/演练库；EXPLAIN ANALYZE实际执行查询，不默认在生产跑。分区、归档分层、载荷外置和缓存只在现有规模/保留期证据支持后提出，不作为首批硬要求。

## 8. 无损迁移与回滚

无损要求是业务事实及原始证据不丢失，不要求拆分/合并前后总行数机械相等。每个来源主键必须经legacy ID map/receipt追溯到目标事实或明确归档；行数、状态分布、金额、归属区间、文件及规范化hash共同证明结果。

历史密码哈希和可恢复的加密数据原样承接，不打印或导出明文秘密。旧会话和凭据按安全版本/撤销规则处理，不能以“原样保留”为理由复活已撤销权限。恢复需要的外部密钥/对象存储依赖要纳入受控清单，而不是写进仓库。

推荐最终停写范围包含API写入、调度器、Worker、Bridge投影、支付回调和通知投递；分别制定暂停/排队/拒绝与恢复策略。最终快照须在所有写入口收敛后形成，并记录边界。未验证的CDC或长期双写不作为默认迁移捷径。

回滚分界：

- **开放V4写入之前**：保持旧库和旧版本可恢复，恢复配置/程序并验证旧系统；目标库留作失败证据。
- **开放V4写入之后**：禁止直接切回旧库，否则会丢失新写入。先停止新写入，保存V4增量，按已演练的反向转换/对账方案恢复，或选择向前修复；没有此能力时必须延后开放写入，而不能声称可随时一键回滚。

DDL与DML分开执行和记账。MySQL原子DDL不等于多语句事务DDL，不能靠ROLLBACK撤销一批ALTER；恢复依赖追加纠正迁移或备份恢复。[MySQL 8.4 原子DDL说明](https://dev.mysql.com/doc/refman/8.4/en/atomic-ddl.html)

## 9. 完成标准

全部通过才能称为“数据库结构优化与全面规范化完成”：

1. 全量源字段及目标必填字段覆盖率100%，所有业务阻断已处理或有明确验收范围；不以表数下降作为成绩。
2. 每个关键事实只有一个权威写入口；关系、唯一性、租户隔离、归属历史和状态转移有约束或可执行证据。
3. 金额和权益精确一致；每种拆分/合并有基数说明；没有未解释的丢行、截断、乱码、重复副作用或权限扩大。
4. 旧数据在新API和页面可实际使用；活跃业务不能仅留原始JSON归档。
5. 冻结输入在A/B得到相同业务事实；主键不同通过ID map比较。中断恢复、备份恢复和开放写入后的恢复边界均有演练证据。
6. 核心查询达到冻结的性能预算，新增索引写入代价可接受，锁序和幂等恢复经过并发验证。
7. 当前dev_vue版本/结构/备份/文件/停写边界核实，完整升级手册可执行；旧表清理仍走后续独立删除门。

## 10. 两轮复审记录

### 第一轮：需求覆盖、职责与实施规模

发现：旧阶段7逻辑表与当前物理表易混淆；单谈索引会遗漏身份、权益、文件和历史可用性；另起任务体系会重复U1/U2工作。

调整：明确旧方案是设计输入、实际结构目录才是DDL依据；增加目标反向覆盖、八类业务域及文件依赖；沿用U1–U6并把查询优化纳入每域验收；取消以减少表数、全库统一主键或JSON全部拆表为目标。

剩余事项：具体表级DDL、索引名单与收益必须等待U1-A实际目录和查询证据，当前不预先承诺优化百分比或工期。

### 第二轮：兼容、数据、并发、验证与恢复

发现：仅比较总行数无法证明合并/拆分无损；“保留旧库即可回滚”不覆盖V4新写入；把当前UTC+3用于历史转换会破坏证据；直接修改已安装SQL会破坏A/B升级链。

调整：引入逐来源追溯及语义对账；区分开放写入前后恢复策略；明确全部后台写入口的停写边界；冻结bootstrap及001–025；为DDL/DML分别记账，约束之前先检查脏数据和排序冲突；性能数字标记为待演练冻结的预算。

剩余风险：当前dev_vue结构漂移、旧历史时间来源、账户公共属性冲突、部分业务目标缺失、对象存储/密钥恢复及生产负载尚需核实。这些是工作包退出门，不通过写方案或提交代码自动关闭。
