# M1 空库基础结构与迁移执行器

> 2026-09-05；结构安装与中断恢复已通过真实双库演练，18 文件/102 表完全一致；全量旧数据迁移仍未完成。最新证据见 [中断恢复记录](./stage-m1-interrupted-schema-recovery.md)。

## 范围与步骤

1. 在 `server/db/migrations/bootstrap/` 增加显式的空库基础结构。它是 001 之前的安装前置阶段，不重排或修改既有 001～017，不调用旧 `initDB`。
2. 基础表只承接当前 V4 Repository 依赖的身份、Bridge refresh 与模型配置/用量结构。没有真实用户、凭据、默认平台配置或可执行任务种子；旧字段如何迁移和拆分仍需逐字段处置清单。
3. 实现独立 CLI 和纯迁移执行模块，默认只做计划/只读检查；仅显式 apply 才写入指定目标。连接配置不自动加载源 `.env`，目标必须不同于显式源库并通过显式目标确认。
4. 目标连接固定 UTC，执行连接持有命名锁，独立控制连接记录文件 SHA-256、执行 ID、状态、时间、语句检查点。两连接必须指向同一目标库。文件或日志不匹配、未知历史、顺序不连续、未完成 DDL 均失败关闭。
5. SQL 单语句执行，不启用 multiStatements，不执行源库查询。除 CREATE TABLE/ALTER TABLE 外，仅按文件身份与语句哈希放行既有 005/007/008 中经审查的转换和风控种子 DML/会话变量语句；不泛化开放 DML、系统 SET、库限定符、动态 SQL、数据库切换、外部读写或禁用约束。
6. 已完成文件可以安全跳过；只在文件完成边界暂停/续跑。DDL 已执行但检查点未确认的崩溃属于未知状态，禁止自动重放；本阶段不实现通用自动 DDL 回滚器。
7. 离线测试通过后，经 SSH 在 `dev_vue_m1_a`、`dev_vue_m1_b` 执行相同计划。比较 schema 指纹与迁移哈希，验证重复运行不写业务表及文件边界暂停恢复。

本阶段仅证明空库结构安装，不迁移用户数据、不启用模型/策略、不启动服务/Bridge/MT，不清空两个目标。全量数据迁移、源备份恢复、金额对账和正式切换仍独立验收。

既有 007/008 会初始化全局风险控制、平台默认风控规则及手动解除参数版本；它们不是交易策略、真实账户或可执行任务。本阶段不改动其产品含义，验收需核对两个库的风控种子内容及当前版本一致。

## 第一轮复审：需求与边界

- 不为了空库通过而复制 165 张旧表。只补明确的当前依赖，保持空库结构验证与业务数据转换分开。
- 前置基础结构使用显式计划身份与 checksum，不伪装成已执行的旧迁移，也不变更既有 SQL 顺序。
- 迁移器不集成进 PM2/应用启动，不读默认 `.env`，不把更新网站变成隐式执行迁移。

## 第二轮复审：数据、安全、异常与恢复

- MySQL DDL 隐式提交；语句检查点不代表 DDL 可回滚。任何 running/failed 日志必须拒绝普通续跑，避免 ADD COLUMN 重复和部分失败被掩盖。
- 命名锁覆盖预检、日志创建与执行；目标存在未知业务表而无合法迁移记录时拒绝接管。
- 008 依赖执行连接的 `ROW_COUNT()` 与 `LAST_INSERT_ID()`。日志 UPDATE 和元数据 SELECT 不能穿插在同一执行连接中，否则会污染风险版本激活结果；使用独立控制连接，并增加回归验收。
- 对文件 hash、路径、语句类型和目标名称在写入前校验；原始 SQL 错误和连接凭据不得写入可公开报告。
- 已在测试库执行的迁移同样冻结，错误必须保留记录并使用明确的纠正方案，不能静默改文件再重跑。
- 剩余风险：真实 MySQL 的生成列/FK/CHECK 兼容性、全量字段映射与旧时间语义尚未验证；本阶段不宣称运行时功能和数据升级完成。

## 操作入口

- `pnpm run migrate:v4-schema`：只读检查目标与待执行计划。
- `pnpm run migrate:v4-schema -- --apply --confirm-target=<目标库>`：显式写入已确认的隔离目标；以 CLI 实际帮助/参数验证为准。
- 配置只从显式 `V4_MIGRATION_SOURCE_DATABASE`、`V4_MIGRATION_TARGET_DATABASE/HOST/PORT/USER/PASSWORD` 读取，不加载 `server/.env`。源名称仅用于禁止误写，不建立源库连接。
- SSH 场景在独立临时工作目录运行经过本地验证的脚本与 SQL；只使用已安装的 MySQL 驱动，不导入网站入口，不改运行中的网站代码或配置。
- 数据库结构校验函数 `scripts/lib/v4-schema-fingerprint.mjs` 对排序后的 SHOW CREATE TABLE 内容及库字符集/排序规则计算 SHA-256；保留列、索引、约束、默认值与自增状态差异，不输出表内数据。

## 首次真实演练结果（保留故障历史）

环境：经 SSH 与 `server/.env` 指向的同一 MySQL 实例核对，MySQL 8.4.8。执行脚本和 SQL 单独复制到 SSH 临时目录，没有部署、覆盖或启动网站源码，没有修改应用配置、运行时开关和账号权限。

| 检查 | 结果 |
| --- | --- |
| 两空库只读计划 | 均通过，18 份文件、143 条语句；计划没有创建迁移日志 |
| A 库首次基础安装 | 第 3 条 CREATE 已成功，但返回警告后停止；日志 checkpoint=2/7、status=failed |
| 警告诊断 | 在同库会话内的临时类型探针确认 MySQL 1681：整数显示宽度弃用；会话关闭后临时表自动消失 |
| 警告处理修正 | 只在 DDL 后读取警告，仅放行 1681 且消息精确匹配整数显示宽度弃用；DML 间不插 SHOW WARNINGS；其它警告仍失败关闭 |
| A 库普通续跑保护 | 只读再次运行明确返回 `migration_incomplete`，没有重放 CREATE 或修改失败日志 |
| B 库基础安装/暂停 | 7/7 完成；在基础文件边界暂停成功 |
| B 库恢复 | 跳过完成的基础文件，001～010 全部完成 |
| 风控会话语义 | B 库平台当前风险版本 ID=2、version_number=1，`manualReleaseEnabled=true`，独立日志连接没有污染版本激活 |
| 011 | 第 1～2 条完成；第 3 条失败，MySQL errno=1826，日志 status=failed、checkpoint=2/7 |
| 最终目标状态 | A：4 表（含日志）；B：66 表（含日志），B users=0；不能供应用切流使用 |
| 源库 | 本轮仅做只读元数据查询；未对 `dev_vue` 执行 DDL/DML，可见源表仍为 165 |

A 库有 3 张已创建业务表而 checkpoint 只有 2，正是“DDL 完成但检查点未确认”的状态，不能从 checkpoint 数字盲目重放。即使本次已知是弃用警告，也必须通过单独的精确结构核对与审计恢复步骤处理；没有直接把失败改成成功。

### 011 缺陷定位

`20260904_011_user_execution_commands_and_distributions.sql` 第 3 条语句（`ALTER TABLE execution_intents`）在同一语句中 DROP 再 ADD `fk_execution_intent_risk` 和 `fk_execution_intent_trade`，真实执行返回 1826。只读复核发现原外键仍在，检查点停在此语句之前，后续分发相关表未继续创建。MySQL 官方缺陷记录也描述了同类问题：[Bug #113226](https://bugs.mysql.com/bug.php?id=113226)；ALTER 外键行为见 [MySQL 8.4 ALTER TABLE](https://dev.mysql.com/doc/refman/8.4/en/alter-table.html)。

没有修改、删除或重排已经执行的 SQL，也没有关闭外键检查、清空库或跳过失败日志。后续需要显式纠正产物与失败步骤对账方案，保留原文件 checksum 和执行事实，再恢复两库；不能把未到达的 012～017 声称为 MySQL 验收通过。
