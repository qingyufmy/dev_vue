# 服务端、API 与前后端模块化核查

日期：2026-09-08。源码基线：`dev_vue` / `6d567450caacd4f7bc710e55c3e2627d6dfdcbc0`，审查开始时工作区干净。

结论：服务端和 API 重构尚未完成。已形成模块化单体骨架并实现多条业务链路，但跨模块封装、完整 API 合同落地、旧业务覆盖和真实依赖读写切换尚未完成。本次是本地源码、类型与定向测试核查，不是全功能或运行环境验收。

## 尚未收口的发现

### 高：服务端目标读写所需的业务根迁移仍未完成

数据库验收文档的延期清单明确包含账户、行情、订阅、推理快照、模型任务、风控/观摩初始事实和旧业务数据消费。69 张目标缺表及同名表缺列与这些根合同有关。因此已有 repository 和 Worker 源码不能证明当前开发库可以承接全量 V4 功能。

处理：按业务流程确定 ID 映射、唯一写入口、权限、任务租约和恢复规则，再追加增量迁移及消费者切换。验收必须包括历史值/行数对账、真实 MySQL 读写、幂等和中断恢复。不能通过建空表或伪造初始状态消除差异。

### 中：跨模块依赖仍穿透内部目录

使用 TypeScript AST 遍历模块源码的静态 import/export moduleSpecifier，解析相对路径后发现 83 处跨模块依赖，其中 60 处指向另一模块的 domain/application/infrastructure/transport 内部目录。计数包含 type-only 依赖，不等于 60 个运行故障；未把动态加载或依赖环检测计入。

具体证据：

- `server/src/modules/bridge/application/bridge-gateway-session.ts:2` 依赖 execution 的内部应用服务，第 3 行导入内部领域校验函数；构造器直接接收该具体服务类型。
- `server/src/modules/trading/infrastructure/auth-trade-request-adapter.ts:1` 导入 auth 内部应用服务。
- `server/src/modules/audit/application/audit-service.ts:1` 导入 trading 内部领域文件。

影响：移动或改造一个域的内部实现会牵动其它域，与 AGENTS 的公开边界要求不一致。应定义公开业务端口/DTO，将具体实现留在模块内部或运行组装入口；不能仅把所有内部实现转导出到 index.ts 来通过检查。

验收：静态依赖图检查越界导入、层反向依赖和业务依赖环；针对代表性非法 import 做负例验证。现存例外若需过渡，必须逐条标明原因与消除条件，禁止新增债务。

### 中：API 声明与路由的统一校验尚未完整落地

`server/src/modules/trading/transport/http/trading-routes.ts:44` 起的 context 路由使用 TypeScript 泛型和局部解析；PUT 并未挂载请求 JSON Schema。`server/src/transport/api-v4-route-registrar.ts:47` 负责注册服务，但未加载 OpenAPI 形成统一运行时校验。Bridge 的部分 HTTP 路由已有 schema，说明不同模块采用了不同方式。

这不代表所有路由没有业务校验，也不据此判定权限漏洞；它意味着 TypeScript 类型、手写转换和合同文件仍可能漂移。抽查通过的合同测试不能替代全部 93 个操作与实际注册路径、请求/响应结构的双向覆盖。

处理：每个业务域拥有自己的 HTTP 合同及适配层，统一机械校验、错误响应和分页约定；比较 OpenAPI 与运行注册清单，保留显式认证协议例外。按操作校验正常输入、错误输入、权限、响应和消费者类型。支付、通知等旧业务的完整覆盖还需以功能矩阵逐域对账，不能从现有操作数推算完成率。

### 中：完整服务端类型检查失败

`pnpm run typecheck:server` 在 `server/tests/auth-sso-service.test.ts:275` 等位置报 7 个错误：测试辅助函数把 unknown payload 传给 Fastify inject，随后响应类型推断出现连锁错误。源代码构建范围的 `tsc -p server/tsconfig.build.json --noEmit` 通过，同一测试的运行测试也通过。故当前证据是测试代码类型门失败，不能表述成生产源码编译失败或全部验证通过。

处理：收窄测试输入类型并保持非法请求的测试意图，然后重新运行完整服务端类型检查及该认证测试。本次审查未修改业务或测试实现。

### 中：后续模块化尚缺完整自动门禁

根 package.json 有 `verify:frontend-boundaries`，未提供对应全后端模块依赖检查命令。现有持久化/权限边界测试检查业务行为，不能替代模块导入检查。

`frontend/scripts/verify-boundaries.mjs:31` 起主要扫描应用间路径标记、直接 fetch/WebSocket 及 UI 库；未解析同一应用的业务模块依赖图，也没有用 AST 解析所有相对路径。因此它通过只能证明现有检查项通过，不能证明前端完全模块化。

## 统一模块化标准与接续顺序

“完全模块化”采用同一套业务边界要求，继续使用既定模块化单体，不要求每个功能增加进程或微服务。

1. 先修复类型门，确定业务模块公开入口与依赖规则，补齐前后端边界检查及运行入口例外规则。通用基础设施只承载技术能力；不把业务逻辑转移到万能 shared/utils。
2. 按账户/交易上下文 → 行情 → 策略/订阅 → 推理/调度顺序收口根模块。每个模块同时完成数据所有权、端口、repository、API、前端功能模块和增量迁移，不等全部后端做完才开始前端。
3. 按功能矩阵逐域补齐其余业务，再完成 OpenAPI/实际路由/消费者双向验证。页面只组合功能模块；功能模块通过自己的服务层和公开合同交互；共享 UI 不承载业务状态。
4. 每条链路分别验收故障、权限、幂等、账户切换、时间显示和真实依赖，再推进全量切换。数据库保存 UTC，实验室显示终端时间，其它位置显示北京时间；休市不从停滞 tick 重新推断时区，默认 UTC+3。

所有未来新增功能同样必须说明模块职责、公开入口、依赖方向、数据所有权和测试入口。模块检查与合同验证通过才算模块化验收完成；当前 AGENTS 已补充这一要求，自动门禁本身尚待实现。

第一轮复核：目录分层、公共 barrel 或进程数不能单独证明模块化；不按文件行数机械拆分，不引入不必要的服务拆分。第二轮复核：保持旧数据、既有权限和幂等语义；跨域事务不能因拆文件被破坏；例外必须可追踪。实施时可回退单域代码组装，数据库继续遵守追加迁移和恢复对账规则，不修改历史迁移。
