## 2. 统一目标与模块交付标准

继续采用模块化单体和 www/trade/admin/auth 四应用。模块按稳定业务职责划分，不按页面数或文件大小机械拆分，也不为每个功能增加微服务。

每个模块必须具备以下可审查交付物：

1. 模块说明：职责、公开能力、允许依赖、数据所有权、事件与测试入口。
2. 服务端：`domain/application/infrastructure/transport` 各负其责；跨域只使用业务 `index.ts`，`composition.ts` 仅供运行组装。公开入口不得泄漏 repository、SQL 连接或 SDK。
3. 数据：每张表唯一写入所有者；跨域读模型明确权限、一致性和索引。强一致流程由一个用例拥有事务，公开事务能力共享同一事务，禁止各域分别提交导致部分成功。
4. API：域合同为唯一源，同步生成类型和运行 schema；覆盖 method/path、Host、权限、输入输出、错误、分页及幂等/revision。认证重定向等协议例外逐项登记。
5. 前端：页面负责组装，feature 拥有业务组件、API、状态与转换；跨 feature 经公开入口。查询缓存与实时订阅具有账户作用域，账户切换后旧响应不能覆盖新状态。
6. 验证：该域越界债务清零，合同与生产者/消费者一致，相关行为、真实依赖和浏览器流程分别有证据。目录整理、类型通过或健康检查均不能单独作为完成证明。

开发应用、Redis 和测试留在本地，虚拟机仅使用既有 MySQL。当前 `dev_vue` 继续增量升级，保留历史数据、旧 ID、映射和迁移账本；已执行迁移、proof 及其冻结工具不改写，只追加新版本。每次变更先核对冻结输入范围，避免修改共享配置使旧 proof 失效。

每个需要数据切换的域交付前后对账、唯一写入口、断点恢复和回退说明。回退必须处理切换后新增数据，不能简单恢复旧备份覆盖新记录。本方案不安排删除旧表、公网切换或终端交易；未来公网覆盖仍须单独验证实际服务器版本及数据升级链。

## 6. 后续新增功能的固定规则

新增功能先确定归属模块，再定义公开合同、数据写入者和权限/并发语义；同步实现服务端用例、API 与所属前端 feature。跨模块需求由流程拥有者编排，禁止直接改他域表或 Store。

验收运行现有 `verify:server-boundary-delta`、`verify:frontend-boundary-delta`、`verify:api-generated`、`verify:api-types`、`verify:api-runtime` 及受影响测试/类型/构建。合同变更同步生成；写操作验证权限、CSRF、幂等、revision、审计和未知结果恢复。仅运行已经存在且适用于该改动的命令，不把拟议汇总门禁当作已实现能力。

已覆盖的运行 schema 与未覆盖操作分别记录。模块 README、合同、迁移和行为证据缺任何必要项，该功能就不能标为模块化完成。

### 9.1 数据库规范化的交付方式

每个域先登记“表 → 唯一写入者 → 跨域读取能力 → 事务拥有者 → 历史映射 → 查询与索引”，并标出跨域 SQL 的具体调用位置。公开端口收口与物理数据所有权分别验收；index 不再导出 MySQL 类，不代表跨域 SQL 已消失。

确有结构差距时才追加迁移：先检查当前 dev_vue 和历史账本，再验证兼容结构、回填、逐账户计数/金额/时间对账、重复执行与中断恢复，最后切换唯一写入口。数据库保留现有实例和数据；已有 165 步、238 表仅引用归档回执，本轮方案未连接数据库确认。历史 UTC 原值不平移；冻结迁移、proof 和工具不改写。

跨域强一致用例必须有一个事务拥有者，各域能力使用同一事务上下文；不得为了模块隔离拆成多个独立提交。整表 DDL 摘要检查逐步改为所有者的版本化能力检查，保留必需字段、约束和迁移就绪验证。单次升级先完成可复现对账与恢复证明，不以命名统一为理由重建全库。

### 9.2 API 与前端统一完成定义

每个用户流程交付同一行证据：业务模块、表所有者、服务端用例、合同 operationId、运行 schema、前端 feature、行为测试、本地真实依赖、浏览器验收与缺口。API 合同登记 14 项运行操作不等于完整请求/响应与权限覆盖；全量路由数量需通过现有 inspect:api-contracts 重新核算，不延用历史 96/88 作为当前结果。

页面和路由只组装，feature 内管理业务状态、API 与展示转换；跨 feature 只通过公开入口，共享 UI 不承载账户、策略等业务状态。查询和实时订阅带账户作用域，切换取消/隔离旧请求，重连重取权威快照；写入结果未知时保留原 key/body 查询结果。实验室显示终端时区，其它页面显示北京时间。

### 12.4 数据库直接升级标准

沿用当前 dev_vue 和现有数据，本地运行应用、Redis 与测试，虚拟机仅承载现有 MySQL。逐域登记“表 → 唯一写入者 → 公开读取能力 → 事务拥有者 → 旧 ID 映射 → 查询/索引依据”。跨域强一致仍由一个事务拥有者协调，能力共享同一事务，不拆成多个独立提交。

迁移顺序固定为：现库与账本核查 → 恢复副本演练 → 兼容扩展 → 有界、幂等、可续跑回填 → 行数/关键金额/时间/ID 对账 → 切换唯一读写入口 → 验证恢复。已执行迁移及冻结输入不可修改，不重建空库替代升级，不用删数据解决约束问题。索引和类型优化依据实际查询及数据，避免纯命名重排。

数据库时间统一 UTC；旧历史时间原值当作 UTC 保留。实验室显示终端时区，其它页面北京时间。休市不得从停滞 tick 重新推断时区，UTC+3 仅作显示默认，交易校验仍要求可信时间。恢复方案必须保存切换后新增事实；不能把 MySQL DDL 当成可事务回滚，也不能直接覆盖旧备份丢掉新增数据。

### 12.5 API 和未来新增模块的固定标准

每个新增功能必须交付以下六项，适用项缺失不能标记完成：

1. 模块 README：职责、边界、公开入口、依赖、数据所有权与测试入口。
2. 服务端用例：domain/application/infrastructure/transport 分责；跨域业务仅访问 index.ts，composition.ts 只供运行组装，不导出具体 repository 绕过边界。
3. 数据与事务：唯一写入者、固定锁序、版本条件、幂等回执、审计、outbox 和未知结果恢复；外部 I/O 在事务外。
4. API 合同：域源、operationId、输入输出及消费者一致；新增操作接入运行校验，写操作包含认证、授权、CSRF、幂等和 revision。错误、分页、金额与时间格式遵循现有合同，认证协议例外明确登记。
5. 前端 feature：拥有本功能 API、状态、转换与组件；页面只组装，跨 feature 使用公开入口。缓存、订阅、请求、表单都带账户作用域，共享 UI 不保存业务状态。
6. 验收行：用户流程、所属域、数据、端口、合同、前端入口、验证证据、未完成项；不适用项说明原因。

边界检查需能识别合法和非法示例；存量精确消除，不重建基线、不新增豁免。先运行受影响行为测试、合同生成一致性、类型与边界检查，必要时构建；真实 MySQL/Redis、浏览器、终端分层验收。最后 P7 再做全局回归，不将每次小改动扩大为无关全仓测试。

第一轮复审（需求、职责、投入）：对照当前登记与第 69–80 节，移除已归档 Outbox、已完成会话/观摩退役和部分 Chrome 正向流程的重复待办；保留前后端同步交付，明确“登记债务为零”不等于模块化完成。调整夹具清理边界，禁止为清理另造通用删除平台；保留现有模块化单体，不新增框架。
