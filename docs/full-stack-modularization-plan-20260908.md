# 前后端全面模块化与 API 标准化实施方案

日期：2026-09-08。状态：方案及两轮复审完成，当前 P0 与 P1 账户前置工作部分完成，见[逐批进度](modularization-p0-progress-20260908.md)。本次修订补充第 11 节的当前基线与接续工作包；本文不表示代码、迁移或自动检查已经全部完成。

## 1. 目标与范围

服务端、API、前端以同一业务边界完成模块化；后续开发和新增功能遵守同一验收标准。模块必须能通过公开接口协作，内部实现变化不应要求其它模块同步修改。无需为了模块化改成微服务，也不按文件行数机械拆分。

继续使用既定 Fastify + TypeScript 模块化单体，以及 Vue/Nuxt 四应用架构。保留当前 11 个运行角色，新增角色必须有明确的故障隔离或资源预算理由。本地运行应用与测试，虚拟机仅提供现有开发 MySQL；本方案不安排公网操作。

现有开发库直接增量升级，保留历史数据。历史时间按用户决定视为 UTC 原值，不平移；数据库统一保存 UTC，实验室显示终端时间，其它页面显示北京时间。休市不根据停滞的终端 tick 重新估算时区，显示默认值采用 UTC+3；显示默认值不能自动成为执行、风控或时间有效性判断的可信证据。

实施依据：

- [本轮源码核查](backend-api-modularity-audit-20260908.md)：13 个业务模块；60 处跨域内部导入；完整 server 类型检查有 7 个测试类型错误。均为前一轮核查基线，实施前重测。
- [后端目标架构](backend-target-architecture.md)、[API 与实时协议](api-v4-and-realtime-protocol.md)、[前端要求](vue-frontend-requirements-standard.md)。
- [全项目功能矩阵](full-project-function-migration-matrix.md)、[数据库表矩阵](database-table-migration-matrix.md)、[独立数据库升级验收与延期清单](database-independent-upgrade-acceptance-20260908.md)。

本文细化模块封装和验收，不替换上述文件中的权限、交易、SSO、迁移合同。后端目标文档中的目录名是业务目标，当前目录名可以保留；不为统一名称进行无收益搬迁。各阶段验收后更新主路线图，历史阶段编号或测试总数不能代替当前状态。

## 2. 模块边界与公开入口

### 2.1 后端

```text
modules/<business-domain>/
  index.ts                  公开业务端口、必要 DTO/错误类型
  composition.ts            运行组装工厂；仅 bootstrap/entrypoints 可导入
  domain/                   业务规则与不变量
  application/              用例与端口、事务边界
  infrastructure/           本域 repository、外部适配器
  transport/                HTTP、实时与任务适配
```

只创建实际需要的文件。`index.ts` 保持唯一跨域业务入口；`composition.ts` 是受限组装入口，不是第二个业务入口。这是对旧设计中单一 index 同时导出基础设施的细化，实施时同步更新目标架构的入口说明。

允许依赖：transport → application → domain；infrastructure 实现 application 定义的端口；运行组装入口创建并注入具体实现。domain 不依赖框架或另一域的具体服务；application 不导入 infrastructure/transport。跨域调用依赖公开能力接口，由组装处注入。

禁止把 repository、连接池、SDK、内部服务全集重新导出到 index 来规避检查。type-only 导入同样遵守边界；公开业务契约也需要稳定。确有双向需求时，由流程拥有者编排、抽取消费方端口或使用 outbox 事件，不用万能 shared 模块消除表面依赖环。

每个模块记录以下信息，可在模块 README 中维护，无需另建复杂注册平台：职责与非职责、公开能力、允许依赖、拥有的表/写入口、事件、事务范围、测试及合同入口。

### 2.2 数据所有权与跨域事务

- 每张正式业务表明确唯一写入所有者。其它域通过公开查询端口或经声明的只读投影取数，不直接改表。
- 列表/统计所需跨域读取建立明确的 read-model 合同：记录源表所有者、查询范围、权限、索引与一致性要求；不能以报表名义任意跨库扫描。
- 强一致流程由一个应用用例拥有事务。涉及多个域时，通过事务范围内的公开能力/工作单元协作，适配层共享同一连接；不向业务层暴露 MySQL 类型或原始 SQL，也不让每个 repository 各自提交。
- 允许延后完成的副作用使用同事务 outbox，再由幂等消费者处理；外部 I/O 不放在数据库事务内。
- 学习完成、权益、支付、执行等既有原子性不得因拆分文件被削弱。先为实际跨域事务列清单，再选对应方式，不预建通用事务框架。

### 2.3 前端

沿用 `apps/<app>/.../features/<feature>` 及现有 index/views/components/api/composables/model 结构。Nuxt 按其实际源码目录配置扫描根，不强行套用 SPA 路径。

- 页面只读取路由、组合组件、触发用例与展示状态；业务转换和 API 调用归所属 feature。
- 每个 feature 只从另一 feature 的 index 导入公开能力；不能访问私有组件、Store、查询键或直接修改对方缓存。
- 页面级跨模块流程由应用编排层协调。四应用不导入彼此源码。
- api-client 只负责传输、认证错误处理等通用机制；contracts 只提供合同类型；realtime 包管理连接协议；ui 保持无业务状态。业务权限与交易判断不能搬到共享包。
- 服务端状态以查询缓存为准，Pinia 仅存客户端状态。缓存键和失效必须包含账户/观摩作用域，切换账户时取消旧请求并阻止迟到响应覆盖。
- 实际 UI 实施继续遵守已有设计系统与 UI 技能要求，本阶段不重新设计视觉风格。

## 3. API 标准化

### 3.1 合同唯一来源

将现有 OpenAPI 按业务域拆为可组合的合同源，公共部分仅含真正共享的标量、分页和错误结构。保留 `contracts/openapi-v4.json` 作为确定性聚合产物，现有工具和消费者继续使用这一稳定路径；不得同时手工维护聚合文件与域合同。

从同一域合同产生前端类型和服务端机械校验 schema。业务授权、不变量和幂等仍由用例执行。实施第一阶段先确定与现有 OpenAPI 方言兼容的编译方式，验证 $ref、nullable、oneOf 和额外字段规则后再迁移，避免采用仅能生成类型、无法保证运行时语义的方案。

按模块逐步替换，过渡期明确每个操作的合同来源，生成结果必须可重复。兼容性字段新增不得改变旧消费者意义；破坏性变化遵守现有版本协议。

### 3.2 每个操作的必填项

| 类别 | 必须明确的内容 |
| --- | --- |
| 身份与作用域 | 应用 host、认证、角色、账户/观摩范围；前端可见性不代替后端授权 |
| 输入 | path/query/body/header 的 schema、长度和分页上限；危险写操作拒绝未知输入字段 |
| 输出 | 成功结构、响应 schema、稳定机器错误码；不暴露 SQL、堆栈、凭据或内部对象 |
| 数值与时间 | ID 字符串、精确数值按既有合同序列化、UTC ISO 时间；展示时区由前端处理 |
| 读写语义 | GET 无副作用；分页稳定排序；按既有合同使用游标；写请求 CSRF、revision/幂等要求明确 |
| 异步操作 | 返回可查询的 operation 状态；受理不等于执行成功；提交结果未知时保留同一 key/body 查询确认 |
| 实时 | 首次 HTTP 快照，实时只推增量/状态；revision 缺口触发重新取快照，浏览器不通过 WS 发交易命令 |

不机械要求所有请求携幂等键或所有接口套业务 envelope；OIDC 回调、重定向、健康检查、文件流等按协议列入精确例外清单。业务 HTTP 默认沿用既有 data/meta 与 problem 错误约定，不另创一套。

### 3.3 完成判据

比较“全项目功能矩阵 → 域合同 → 实际 Fastify 注册 → 前端消费者”。对注册路由采用无需监听端口/真实依赖的应用工厂，以测试适配器注入，再按规范化 method/path 对账。允许的认证协议例外必须明确，不能用通配符隐藏未覆盖业务。

每个操作具备 schema 验证与代表性成功/失败响应；写操作另有权限、非法输入、revision/幂等行为测试。高风险流程验证重复、提交未知和恢复，普通只读接口不复制无收益测试。最终业务操作缺失、未声明注册和未解释合同漂移均为 0。

## 4. 自动检查与持续开发规则

以下命令为拟新增目标，不表示目前可运行：

- `verify:server-boundaries`：解析 TypeScript import/export、静态动态 import、路径别名及 re-export 链，检查内部穿透、反向依赖、公开入口泄漏和依赖环。
- 增强 `verify:frontend-boundaries`：解析 Vue script、TS/JS、别名、相对路径与 Nuxt 自动导入来源，检查应用内 feature 和共享包边界。保留现有 UI 库及直接 fetch/WebSocket 检查。
- `verify:api-contracts`：合同合法性、确定性生成、实际路由双向覆盖与消费者类型一致性。
- `verify:architecture`：汇总上述结构检查，用于本地验收及现有远端流水线；接入时先确认实际 Gitee 构建环境，不能因仓库没有 GitHub workflow 就声称不存在 CI。

边界检查要区分业务依赖图与组装依赖图；禁止运行代码循环，纯类型契约也不得任意循环。无法静态解析的动态加载必须限制在精确的组装位置，不能直接跳过。为检测器提供少量有效/非法导入、别名、barrel 泄漏和循环的正反例，证明检查有拦截作用。

过渡阶段将 60 处候选逐条复核后登记为精确 source/target/rule 例外，每条挂模块与消除阶段；禁止通配符、只比较总数或新增一条抵消删除一条。P0 起禁止新增越界；全量完成时业务越界例外清零，必要的组装入口属于正式规则而非技术债。

新增功能的完成定义：模块归属、公开合同、数据所有权、迁移兼容、前端状态归属明确；相关类型/边界/合同/行为检查通过；涉及真实依赖的验证分开记录。共享包改动验证所有受影响应用；纯文案等小变更不要求全仓测试。

## 6. 数据升级、切换与异常恢复

每个涉及数据库的模块先从延期清单重开对应项，核对实际 dev_vue 结构和历史迁移 checksum。沿用已有恢复副本/备份流程，先在恢复副本验证，再按现有库增量升级合同执行；不更换空库、不重写已执行 SQL。

操作顺序：旧数据映射与约束审计 → 追加兼容结构 → 可恢复回填 → 旧/新读结果逐项对账 → 切换应用读写 → 观察与复核。双读仅用于校验，不引入两个无协调的权威写入口。

每步保留迁移记录、旧 ID 对照、结构和业务行/关键字段摘要。BIGINT/UUID、用户 0、根表引用、风控初值必须按具体合同处理，不能用虚构用户、删除行或默认解除风控补齐约束。

回退条件包括对账差异、权限范围扩大、重复副作用或新消费者无法恢复。兼容阶段可回退已验证的模块组装；一旦新写入不能被旧代码正确解释，停止切换并以前向修复/对账处理，不能盲目退旧代码。MySQL DDL 不承诺事务回滚；灾难恢复需先保存切换后的新增事实并核定重放方式，不能直接覆盖旧备份导致新数据丢失。

数据库执行按届时已授权的具体模块范围推进，本次只编制方案，没有运行迁移或更改配置。

## 7. 验收证据与总完成定义

每模块记录五种独立状态：结构边界、源码/类型、离线行为与合同、真实依赖、用户流程。用“完成/部分/未验证/阻塞”并附证据，禁止从任一层推断另一层，避免使用无法核算的百分比。

总完成条件：

1. 全项目功能矩阵无未解释遗漏；所有模块的公开接口和表所有权明确，内部跨域导入及未批准反向依赖为 0。
2. 前端四应用和各 feature 边界检查通过，共享包没有业务状态；页面复杂逻辑归属清晰。
3. API 合同、实际注册、消费者可重复对账，统一校验/错误/分页落实；实时与 Bridge 协议独立验收。
4. 完整类型检查、相关构建、结构检查及关键用户流程测试通过；历史数据映射和当前库升级对账完成。
5. 本地应用连接实际开发 MySQL、本地 Redis 后，验证 API/Worker 独立启停、恢复、连接池总预算、队列延迟和慢请求；容量阈值在测量前按既有预算确定，不以“能启动”判完成。
6. 需要终端证据的链路独立完成验证。行情只读验证与测试账户交易分开；未完成真实终端或交易验证时明确保留缺口。
7. 新增功能模板和自动检查实际可执行；后续变更不能绕过相同规则。公网部署和旧代码/旧表删除不由本方案的通过自动授权。

## 8. 两轮复审记录

### 第一轮：需求覆盖、职责与复杂度

复核结果与调整：

- “前后端完全模块化”已展开为公开入口、数据所有权、前端状态归属和自动检查；补入应用内部 feature，避免只隔离四应用。
- 保持模块化单体与当前框架；允许保留目录名，不批量生成空模块，不按行数拆 repository。
- 增加受限 composition 入口，避免公开 index 暴露基础设施；明确业务入口仍只有一个。
- 把前端开始点提前到 P1；将 P6 的范围绑定全功能矩阵，避免只做交易实验室就称全项目完成。

剩余事项：P0 需要实查各域数据写入者和全量依赖图，60 处仅为当前静态候选基线，不直接等同所需修改数。

### 第二轮：兼容、数据、并发与验证

复核结果与调整：

- 补入跨域短事务的公开能力协作，禁止拆模块后各 repository 独立提交破坏原子性。
- OpenAPI 聚合路径保留，按域逐步迁移并验证方言语义；认证协议例外精确登记，不能强套业务 envelope。
- 例外按具体依赖登记，不能仅比较总数；扫描覆盖别名、re-export、Vue/Nuxt 自动导入，避免检查假通过。
- 区分显示 UTC+3 默认与执行可信时间；继续遵守用户历史 UTC 原值决定。
- 补入新写入后的回退兼容条件和增量事实保全，避免“恢复备份”等同无损回滚的错误承诺。
- 实际数据库、Redis、终端及交易证据分层验收；不因本地测试通过推断公网可覆盖。

剩余风险：旧业务覆盖量、根 ID 迁移影响、现有跨域 SQL 和真实终端时间需实施时验证。以各阶段退出条件控制，不用未经测量的工期承诺掩盖未确认项。

### 11.3 后续新增功能的固定交付规则

每次新增功能先确定所属域，确需新域时才新增模块。模块 README 至少登记职责、公开入口、依赖、拥有的表、查询投影、事务与测试入口。交付清单如下：

1. 服务端用例经公开端口协作，路由和 Worker 只组装调用；公开 index 不暴露数据库实现。
2. 数据库仅追加迁移，明确旧数据转换和恢复条件；所有正式业务表有唯一写入所有者。
3. API 先更新域合同，再生成生产者校验和消费者类型；登记操作的权限、错误、幂等与并发语义。
4. 前端业务状态归所属 feature，账户作用域贯穿请求、缓存和实时订阅，共享 UI 不承担业务状态。
5. 运行受影响的边界、合同、类型和行为检查；新增越界不得加入存量基线。真实依赖和用户流程结果单独记录。

P0 继续补齐汇总检查与流水线接入；尚未自动化的条目逐项人工核对，不能因规则已写入本文而声称自动门禁完成。
