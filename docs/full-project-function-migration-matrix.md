## 3. HTTP API 与 WebSocket 决策

### 3.1 判定规则

| 问题 | 结论 |
| --- | --- |
| 用户是否主动打开、搜索、筛选、分页或查看详情？ | 使用 HTTP API |
| 是否是表单保存、下单、改单、撤单、平仓、确认、发布或其它写操作？ | 使用 HTTP API，并带权限、幂等和审计 |
| 数据是否在页面停留期间持续变化，并要求秒级或事件发生后立即更新？ | 使用 WebSocket 增量 |
| 数据是否可从服务端下发的绝对时间在前端推导？ | HTTP/事件下发时间点，前端本地计算，不秒级广播 |
| WebSocket 是否断线、重连或出现 revision 缺口？ | 精确 HTTP 重拉受影响资源 |
| 数据是否是历史、报表、完整推理、导出或大列表？ | 使用 HTTP API，不通过 WebSocket 传大对象 |

### 3.2 浏览器统一模型

```text
进入页面
  -> HTTP 获取一致快照 + snapshot_revision
  -> WebSocket 订阅当前用户/账户/资源频道
  -> 按 revision 合并增量
  -> revision 缺口或重连
  -> HTTP 精确重拉对应资源
```

禁止：

- 浏览器通过 WebSocket 查询普通列表、历史、详情或导出。
- 浏览器通过 WebSocket 直接发送交易、风控、策略或后台管理写命令。
- 每个页面各建一条 WebSocket。
- WebSocket 高频发送完整账户、完整持仓或完整 K 线数组。
- 实时连接正常时继续用秒级 HTTP 轮询同一资源。
- 为倒计时每秒广播相同状态。

### 3.3 实时数据矩阵

| 数据 | 首次/恢复 | 实时通道 | 推送内容 | 不实时的部分 |
| --- | --- | --- | --- | --- |

### 3.4 Bridge 内部通道与浏览器通道

浏览器实时通道和 Bridge 设备通道是两种不同信任边界：

- 浏览器通过当前 `trade` 会话申请短时单次 WebSocket 票据，只订阅服务端已经授权的频道。
- Bridge 使用独立设备配对与刷新会话，通过设备 WebSocket 接收服务器的精确数据请求和确定性交易命令。
- 浏览器写操作先通过 HTTP 进入服务端状态机并持久化；服务端再把已授权、可审计的命令发送给 Bridge。
- Bridge 回执先写入服务端账本，再由浏览器 WebSocket 接收状态变化。
- Bridge 不是浏览器可访问的数据库、SQL 服务或远程脚本执行器。

execution 域的目标不是把所有业务塞入一个状态枚举，而是统一为公共 operation、账户级 execution intent、Bridge command、终端资源投影和来源/分发五类关联状态。自动单、手动单、策略分发、分发平仓、持仓保护、挂单修改和撤单共用同一个机械执行入口；完整转换与恢复规则见 [交易执行统一状态机](./trade-execution-state-machine.md)。

| MT4 连接 | EA/本地通信和精确调用 | 路由请求 | 重构 | 与 MT5 同等核心能力，差异显式 |
| 多账户终端档案 | 一个档案/Worker/账户 WebSocket 只连接一个账户，各档案数据和故障隔离；支持新增、断开、删除、更换 | 按用户并发额度授权、按账户精确路由 | 新增 | 默认同时 1 条；额度内可混合连接多个 MT4/MT5，离线档案不占额度 |
| 账户发现与切换 | 识别 login/server/platform | 校验绑定和唯一性 | 保留 | 切换不串数据，频繁切换可恢复 |
| 时区校准 | 比对终端时间与 UTC，上传时区/版本 | 缓存并发布给前端 | 保留重塑 | 不持续上传终端当前时间 |
| 账户事实 | 精确返回 balance/equity/margin 等 | 权限、缓存、投影 | 保留 | 字段定义和新鲜度明确 |
| 品种与规格 | 返回终端真实品种和合约规格 | 标准化和授权 | 保留 | 后缀品种、精度、交易量约束正确 |
| 实时报价 | 订阅/读取 Tick | 作用域路由和扇出 | 保留 | 低延迟、断线、陈旧状态明确 |
| K 线和成交量 | 返回历史窗口并推送当前增量 | 缓存、修订和前端事件 | 保留 | M1–D1、MT4/MT5 时间和成交量一致 |
| 持仓与挂单 | 精确快照和 delta | 授权、对账和扇出 | 保留 | ticket、Magic、symbol、ownership 完整 |
| 历史交易 | 受控查询、范围、游标和快照 | 统计、图表和业务组合 | Query V4 目标 | 大数据不阻塞交易命令 |
| 交易命令 | 确定性执行并持久化账本/回执 | 风控、意图、幂等、调度、对账 | 保留安全内核并 V4 化 | 重投不重复成交，未知结果可对账 |
| 诊断 | 本地版本、连接、延迟、同步和有限日志 | 健康聚合和后台展示 | 保留 | 不暴露凭据和客户敏感数据 |
| 暂停/退出 | 停止 Bridge 自身 | 更新会话状态 | 保留 | 不关闭 MT4/MT5 |
| 本地存储 | SQLite 保存事实、游标、命令安全层 | 不直接访问本地 DB | 保留并分层 | 查询层不能访问凭据/账本/更新表 |

Bridge 只提供客观数据事实和确定性终端操作。业务统计、策略判断、风控决策、图表组合和用户权限保留在服务器。

并发连接额度和账户级订阅的完整规则见 [Bridge 并发连接额度与账户级策略订阅模型](./bridge-connection-quota-and-account-subscription-model.md)。

## 12. 跨域规则

### 12.1 权限

- 所有资源由服务端按系统用户、管理员权限、交易账户、观摩频道和资源所有权判断。
- 观摩模式只读；普通用户无 Bridge 时可分析，但交易命令明确拒绝。
- 管理后台使用操作级 RBAC；超级管理员也必须通过高风险重新认证。
- 平台策略分发只能操作该策略授权范围内、状态合格的订阅者。

### 12.2 时间

- 数据库存 UTC。
- `www` 与 `admin` 显示北京时间。
- `trade` 显示 MT 终端时间，使用服务端缓存的时区偏移和校准版本。
- Bridge 只在时区变化或重新校准时更新时区，不持续推送当前终端时间。
- 自动分析和订阅时段使用带 IANA 时区或明确固定偏移的配置；不得依赖浏览器本地时区猜测。

### 12.3 错误与陈旧状态

- HTTP 错误统一包含稳定错误码、用户可读信息、关联 ID 和可否重试。
- WebSocket 数据带 `occurred_at`、`revision` 和作用域；过期数据不得伪装为实时。
- 单模块失败不清空其它模块；后台刷新保留旧数据并显示陈旧标记。
- Bridge 无法确认交易结果时显示“结果待对账”，不得自动当作失败重发。

### 12.4 性能与带宽

- 公共主站未登录页面不建立 WebSocket。
- 登录主站只有通知或活跃支付订单需要实时通道时才连接。
- `trade` 和 `admin` 各自只使用一个统一浏览器实时连接。
- 页面隐藏后取消 Tick/K 线等高频订阅，但保持必要的低频连接状态或按产品策略断开。
- 大列表、历史、推理正文、审计和导出不进入实时帧。
- 服务端按频道合并订阅，前端只更新变化节点，避免整页闪烁。

## 15. 第一轮复审

复审范围：功能覆盖、产品归属、用户习惯、最小实现和避免过度设计。

结论与调整：

- 三前端不共享业务页面，但共享身份、合同、基础组件和设计令牌。
- 首页、分析师、交易员、风控师、策略师、复盘师、交易记录、审计和宏观行情全部有明确目标；模型配置移到独立设置，不继续塞入策略师。
- 主站保持官网和课程定位；管理后台按运营任务组织，不复制交易工作台。
- 传输不按“已有 WebSocket 能做什么”迁移，而按用户是否需要实时更新决定。
- 不引入微服务、Kafka、GraphQL、通用工作流、通用 BI 或额外数据库作为默认方案。
- B1 按用户决定暂缓；TDK、Canonical、分享元信息和域名配置仍保留。

第一轮结论：当前已知功能均有去向，产品边界与传输选择符合普通外汇交易者的使用场景。

## 16. 第二轮复审

复审范围：权限、并发、幂等、断线、时间、数据迁移、交易安全、性能、回滚和连带 Bug。

结论与调整：

- 浏览器交易命令改走 HTTP，不表示交易是同步完成；HTTP 只确认服务端已持久化接受，真实执行结果通过 WebSocket 更新并可由 HTTP 查询恢复。
- HTTP 快照与 WebSocket 增量共享 revision，避免先订阅后快照或先快照后订阅产生丢事件窗口；具体握手在实时协议阶段冻结。
- 账户切换必须取消旧 HTTP、退订旧频道并拒绝迟到消息，解决跨账户数据污染。
- K 线只实时更新当前蜡烛和成交量，历史窗口使用 HTTP，降低带宽和图表重建成本。
- 完整推理、审计、交易历史和报表不进入 WebSocket，防止大帧阻塞交易回执。
- Bridge 数据查询和交易安全层隔离；大历史查询不得延迟命令账本和回执。
- 所有写命令使用幂等键；未知 MT 结果进入对账，不自动重放。
- 时区变化用版本事件通知，前端计算终端时钟；数据库 UTC 不被显示时间覆盖。
- 旧业务协议删除、数据库清理和客户端切换分别授权并保留回滚路径。

第二轮结论：迁移矩阵已覆盖传输、数据、权限、并发、时间和恢复边界，可作为下一阶段 API V4 与实时协议 V4 的输入。
