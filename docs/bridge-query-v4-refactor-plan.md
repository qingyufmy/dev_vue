## 2. 已确认需求与最终结论

### 2.1 已确认需求

1. SQLite 必须保留。
2. 精简目标是降低 Bridge 代码复杂度，而不是删除功能、缩小安装包或把可靠性状态移出本机。
3. 前端表达业务请求，后端完成鉴权和查询编排，再通过 WebSocket 向 Bridge 发送标准查询。
4. 对已经进入 SQLite 的数据，后续增加筛选、排序、字段组合、分页、统计和图表时，原则上只改服务器和前端，不再为每个页面新增一个 Bridge action。
5. 复杂业务统计和图表解释放在服务器；Bridge 只维护可复用的基础事实和物化汇总。
6. 查询默认使用 `refresh_if_stale` 新鲜度策略；是否刷新由请求显式表达，Bridge 不在普通读取中偷偷扩大同步范围。
7. 允许开发新的 Bridge Query V4 协议。
8. 新增 MT4/MT5 原始采集能力、终端 API 或新的规范化字段时，允许修改并发布 Bridge。
9. 完整历史在授权范围内逻辑上可查，但任何一次物理响应都必须有界、分页并受字节预算约束。

### 2.2 最终架构判断

Bridge 应收敛为“受控、类型化的本地数据服务与安全交易执行器”，而不是远程脚本执行器或开放 SQL 数据库。

- Query V4 负责：资源描述、只读查询、显式同步、新鲜度、分页、修订号和查询结果。
- V3 继续负责：现有交易命令、命令幂等、执行回执、未知结果对账、实时流和旧数据 action 的兼容期。
- SQLite 继续负责：可靠投递与交易安全证据、历史归档、同步游标、物化汇总和可重建读取模型。
- 服务器负责：用户与账户授权、业务查询组合、复杂统计公式、图表结构、缓存、前端兼容和跨资源业务解释。
- 前端负责：发出业务意图和展示结果，不直接构造 Bridge 查询，不接触 SQLite 表结构。

## 3. 当前实现基线

### 3.1 已具备的可复用能力

当前 V3 已具备以下基础，不应在 V4 中重写：

- WebSocket 鉴权、会话、心跳、终端路由和连接代际；
- `terminal_instance_id + broker_server + login + connection_epoch` 路由约束；
- `data_request` 与关联 `data_response`；
- 交易 `command`、全局 `command_id`、截止时间、执行回执和 `uncertain` 对账；
- SQLite WAL、独立只读历史连接、历史同步任务、覆盖范围、游标快照和每日汇总；
- 每页最多 200 条、单条历史记录上限、历史响应字节上限和 WebSocket 4 MiB 硬上限；
- 服务器每连接待处理数据请求上限和 Bridge 内部有界数据队列；
- 历史统计、图表和筛选目前已有静态测试，可作为 V3/V4 对照基线。

### 3.2 当前复杂度来源

当前读取能力按业务用途持续增加专用 action，例如：

- `history`
- `history_page`
- `history_evidence`
- `history_prepare_status_v1`
- `chart_data`
- `performance_daily`
- `pending_order_state`
- `diagnostics`

每个 action 可能在协议白名单、服务器适配器、Bridge Core、Worker 合同、SQLite 查询、前端调用和测试中重复增加分支。新页面往往演变成新的 Bridge 合同，导致客户端重发版成本和协议漂移风险上升。

### 3.3 当前必须保留的行为

- SQLite 是可重建的读取模型、离线缓存和对账证据，不是经纪商交易真相。
- 交易命令在执行前必须持久化，结果在服务器确认前必须保留。
- `uncertain` 不能当作失败重发；只能查询执行证据后结算。
- 历史必须按有界范围、游标和快照读取，禁止重新引入无边界全量响应。
- MT4/MT5、本地档案、观摩源和账户数据必须相互隔离。
- Bridge 暂停、退出、更新或授权失效不得关闭 MT4/MT5。

## 4. 目标与非目标

### 4.1 目标

1. 用一个稳定的 V4 查询合同覆盖已有数据的字段选择、过滤、排序和游标分页。
2. 用稳定资源名隔离服务器与 SQLite 内部表结构。
3. 新增页面统计和图表时，优先只修改服务器计算与前端展示。
4. 保留本地物化汇总，避免为了统计把数万笔交易明细传给服务器。
5. 把性能、安全、范围、字节数和并发限制写入协议并自动验证。
6. 允许 V3 与 V4 长期并存和逐资源迁移，旧 Bridge 不因服务器升级立即失效。
7. 保留可关闭、可回滚、可观测的迁移路径。

这里的“不再修改 Bridge”边界必须可验证：同一已注册资源中，对已经公开的规范化字段改变选择、组合、范围和现有操作符，只改服务器和前端；新增资源、尚未采集或尚未公开的字段、新的 MT 能力、新索引语义或新的查询操作符，仍可能需要 Bridge 更新。首版资源目录应一次性公开各资源中稳定、非敏感的规范化事实字段，不能只按当前某个页面挑选字段，否则会继续产生页面驱动的客户端发版。

### 4.2 非目标

- 不开放原始 SQL、SQLite 表名、列名、文件路径、Shell、PowerShell、Python 或动态脚本。
- 不在 V4 第一阶段实现任意 `JOIN`、子查询、表达式语言、用户自定义函数或数据库写操作。
- 不把策略、风控决策、复盘、图表 UI、报告或 AI 业务逻辑放入 Bridge。
- 不在本方案中迁移或重写交易命令协议；V3 交易幂等和对账合同继续作为安全基线。
- 不为了 V4 拆分 SQLite 文件、引入外部数据库或新增常驻服务。
- 不保证“任何未来未知 MT 数据都无需更新 Bridge”；只有已采集、已规范化的数据可由通用查询自由组合。

## 5. 总体架构

```text
前端业务请求
  -> 网站后端鉴权、账户路由、范围解析和查询编排
  -> Query V4 请求
  -> Bridge V4 校验、资源解析和新鲜度处理
  -> SQLite 数据资源 / 必要时有界唤醒 MT 同步
  -> Query V4 结果、修订号、完整性与游标
  -> 网站后端缓存、统计、图表和兼容组装
  -> 前端现有或新页面
```

Bridge 内部分为五个明确责任区：

1. 传输与路由：鉴权、会话、账户路由、限流、优先级和消息预算。
2. Query V4 合同：解析、字段白名单、操作符、资源目录和错误码。
3. 新鲜度与同步：判断缓存状态、合并刷新、创建或等待同步任务。
4. SQLite Store：只执行预定义、参数化、有界的查询计划。
5. 交易安全内核：命令账本、回执、Outbox 和对账；与通用查询隔离。

## 6. V4 兼容与能力协商

### 6.1 兼容策略

V4 先作为现有 WebSocket 会话中的新查询方言引入，不重写鉴权、心跳、交易命令或实时推送。

1. Bridge 仍使用现有 hello 建立会话。
2. 新 Bridge 在能力列表中声明 `bridge_query_v4` 和资源目录版本。
3. 服务器只有看到该能力后才发送 `v:4` 查询消息。
4. 未声明能力的旧 Bridge 继续走 V3 action。
5. 每个网站读取入口均有独立功能开关，可选择 V3、V4、影子比对或关闭。
6. 迁移完成前不得删除 V3 fallback。

### 6.2 V4 第一阶段消息类型

- `describe_request` / `describe_response`
- `query_request` / `query_response`
- `sync_request` / `sync_response`

V4 第一阶段不新增通用 `execute` 和 `subscribe`：

- 交易继续使用经过验证的 V3 `command`；
- 实时账户、持仓、订单、报价继续使用 V3 snapshot/delta/quote 能力；
- V4 只解决读取 action 膨胀和同步编排问题。


所有 V4 请求必须携带 `deadline_utc_msc`。Bridge 在进入查询队列前和获得查询槽后各检查一次；已经过期的请求不得执行 SQLite 查询或唤醒 MT。服务器断开、请求取消或截止时间到达后必须释放等待者和查询槽。SQLite 执行层应使用可中断的步骤预算或等价机制，不能只依赖外层 Promise/任务超时而让底层扫描继续占用连接。

历史快照必须包含账户路由、资源版本、归一化查询、冻结结束时间、`highwater_rowid`（或等价不可变高水位）、history revision、summary revision 和过期时间。游标页可以由两个只读连接中的任意一个执行，但只能查询该快照高水位以内的数据，不能依赖某个连接私有的长事务；账户路由、资源版本、查询哈希或快照证据不匹配时必须拒绝续页。

### 7.3 失败响应

失败必须区分：

- 协议错误：消息结构、版本、路由或身份无效，必要时关闭会话；
- 查询拒绝：未知资源、字段、操作符、排序、范围或成本超限；
- 数据状态：历史未覆盖、汇总未就绪、快照过期或刷新仍在进行；
- 传输状态：队列满、超时、断线或结果超出硬预算。

错误只返回稳定错误码和安全上下文，不返回 SQL、表名、路径或 SQLite 原始错误。

V4 `request_id` 在同一连接的 pending 集合内必须唯一，V3 和 V4 的待处理请求共同计入每连接上限，避免通过混合协议绕过容量控制。重复 query ID 直接拒绝；重复 sync 使用归一化同步键附着已有任务并返回同一 `sync_id`。

## 8. 资源目录

### 8.1 第一阶段资源

| 稳定资源名 | 数据性质 | 默认来源 | 允许能力 |
| --- | --- | --- | --- |
| `account.snapshot` | 当前账户快照 | SQLite 最新投影 | 字段选择 |
| `positions.current` | 当前持仓 | SQLite 最新投影 | 过滤、排序、游标 |
| `orders.current` | 当前挂单 | SQLite 最新投影 | 过滤、排序、游标 |
| `history.trades` | 规范化平仓交易 | SQLite 历史归档 | 范围、过滤、排序、游标 |
| `history.deals` | 成交与资金事件 | SQLite 历史归档 | 范围、类型过滤、游标 |
| `history.orders` | 历史订单 | SQLite 历史归档 | 范围、过滤、游标 |
| `history.performance_daily` | 按终端业务日物化的基础汇总 | SQLite summary v2 | 范围、方向、盈亏桶 |
| `symbols.catalog` | 品种目录 | SQLite 缓存/终端刷新 | 字段选择、品种过滤 |
| `rates.bars` | K 线 | SQLite 缓存/终端读取 | 品种、周期、范围、有界数量 |
| `diagnostics.summary` | 脱敏运行状态 | Bridge 状态投影 | 字段选择 |

### 8.2 资源注册规则

每个资源必须在 Bridge 内部注册：

- 资源版本；
- 公开字段及类型；
- 可选择、可过滤、可排序字段；
- 允许操作符；
- 默认排序和稳定次级排序；
- 必须携带的账户和时间范围；
- 最大页大小和结果字节预算；
- 对应索引或预定义查询计划；
- 新鲜度来源和可否唤醒 MT；
- 完整性、时间语义和修订号来源。

字段能力分为两级：

- `selectable`：稳定、非敏感的规范化事实字段原则上完整开放，避免以后只为增加列表列而更新 Bridge；
- `filterable/sortable`：只开放具备稳定语义和可接受查询计划的字段，新增高成本过滤或排序仍需先补索引和基准验证。

服务器只使用资源目录，不依赖 SQLite 表名、内部列名或 JSON 存储形式。

## 9. 受限查询语言

### 9.1 第一阶段允许项

- `select`：最多 32 个公开字段；
- `filters`：最多 16 个，第一阶段只支持隐式 AND；
- 操作符：`eq`、`ne`、`lt`、`lte`、`gt`、`gte`、`between`、有界 `in`；
- `order`：最多 2 个字段，必须包含或自动补齐稳定唯一次序；
- `page.limit`：1 到 200；
- `range`：历史资源必须使用服务器解析后的 UTC 半开区间；
- `include_total`：默认 false，只在首个快照需要时计算一次。

### 9.2 第一阶段禁止项

- 原始 SQL、表达式字符串和任意函数；
- 用户指定表、列、索引或排序规则；
- OFFSET 深分页；
- 不受限制的 contains/正则/模糊扫描；
- 任意 OR 树、JOIN、子查询和跨资源聚合；
- 查询安全层表、凭据、Outbox、命令账本、回执、更新签名或系统表；
- 通过查询执行 INSERT、UPDATE、DELETE、DDL 或 PRAGMA。

复杂 OR 和跨资源组合由服务器拆成多个有界查询并在业务层合并；若未来确有高频需求，再以新资源或新资源版本扩展，不能把任意 SQL 下放。

## 10. 新鲜度与同步

### 10.1 新鲜度模式

| 模式 | 行为 | 适用场景 |
| --- | --- | --- |
| `cache_only` | 只读 SQLite，不唤醒 MT | 后台统计、复用缓存、离线展示 |
| `refresh_if_stale` | 超过 `max_age_ms` 才有界刷新，默认模式 | 普通页面 |
| `force_refresh` | 用户明确操作才触发 | “立即刷新”按钮、诊断 |

### 10.2 同步去重

同一档案内按照以下键合并刷新：

```text
terminal + account + resource + normalized range + refresh reason
```

- 已存在等价或更宽的同步任务时，后续请求等待或附着该任务；
- 查询等待时间到达后返回 `refreshing` 和可轮询状态，不阻塞到完整历史回填结束；
- 强制刷新不得清库，不得绕过覆盖范围和游标；
- 历史回填、近期尾部刷新和页面读取使用独立优先级；
- 同步请求必须幂等，并返回稳定 `sync_id`。

### 10.3 同步请求边界

`sync_request` 只允许刷新已注册资源和授权范围，不允许服务器描述任意本机操作。历史同步必须携带精确 UTC 范围；超大范围进入后台分批任务，立即返回状态，不通过一个 WebSocket 请求长期占用连接。

## 11. 统计与图表

### 11.1 Bridge 返回基础事实

V4 不保留面向具体 UI 的 `chart_data` 资源。Bridge 通过 `history.performance_daily` 返回：

- `business_date`
- `trade_count`
- `win_count`
- `loss_count`
- `breakeven_count`
- `gross_profit`
- `gross_loss`
- `net_profit`
- `volume`
- `deposit`
- `withdrawal`
- `credit`
- `direction`
- `profit_bucket`

SQLite 继续维护每日物化汇总，因为它能把数万笔历史交易压缩为几十到几千条基础记录。该汇总属于数据库读取模型，不属于图表业务逻辑。

### 11.2 服务器计算展示指标

服务器基于同一账户、同一冻结范围、同一过滤条件和同一 summary revision 计算：

- 总交易：`sum(trade_count)`；
- 胜率：`sum(win_count) / sum(trade_count)`，保留当前是否将保本单计入分母的既有口径，变更需另行确认；
- 实现盈亏比 `payoff_ratio`：平均盈利金额除以平均亏损绝对值；
- 利润因子 `profit_factor`：总盈利除以总亏损绝对值；
- 每日盈亏：每日 `net_profit`；
- 累计收益：按终端业务日累计 `net_profit`；
- 金额回撤：累计收益曲线的峰谷差；
- 百分比回撤：只有区间起始资金和期间资金流证据完整时才计算，否则返回 null。

`history.performance_daily` 的普通整日范围读取 summary v2。若精确 UTC 范围切穿终端业务日边界，Bridge 必须复用现有安全语义：完整业务日使用物化汇总，最多两个边界片段从有界原始归档精确聚合，或明确返回该范围不支持；不得把整日汇总直接裁成边界结果。响应相应标记 `exact_close_utc` 或 `server_business_date`。

当前 UI 中名为 `profit_factor`、实际表示平均盈利/平均亏损的字段，在 V4 服务器适配层中明确映射为 `payoff_ratio`。兼容期不直接改变用户可见数值，避免把协议迁移变成统计口径变更。

### 11.3 前端兼容

第一阶段服务器把 V4 每日汇总组装成现有结构：

```json
{
  "daily": [],
  "cumulative": [],
  "drawdown": [],
  "stats": {
    "total_trades": 0,
    "win_rate": 0,
    "payoff_ratio": 0,
    "profit_factor": 0,
    "max_drawdown_amount": 0,
    "max_drawdown_pct": null
  }
}
```

现有交易历史页面先不改视觉和交互。服务器完成 V3/V4 影子比对后切换数据来源，避免前端、服务器和 Bridge 同时大改。

## 12. SQLite 分层与迁移原则

### 12.1 安全层：完全不向 Query V4 开放

- 命令账本；
- 执行回执；
- Outbox；
- 同步租约与恢复证据；
- 凭据和授权状态；
- 更新状态、签名和安装信息。

### 12.2 数据层：通过稳定资源只读开放

- 账户、持仓、挂单最新投影；
- 规范化历史交易、成交和历史订单；
- 品种、K 线和受控缓存；
- 每日物化汇总；
- 脱敏诊断投影。

### 12.3 本地迁移原则

- SQLite 迁移只能追加，不能修改已发布迁移的语义；
- 新查询字段优先复用现有规范化标量列；
- 只有经过查询计划和基准验证的高频过滤才增加索引；
- 新字段回填必须有界、可恢复，不阻塞交易命令；
- 汇总不可用时 fail closed，返回未就绪，不扫描全部 payload JSON 伪造零值；
- V4 禁用或回滚后，SQLite 数据仍可由 V3 使用；
- 本方案不涉及网站 MySQL 表或生产数据库迁移。

## 13. 性能设计

### 13.1 固定性能边界

| 项目 | V4 首版限制 |
| --- | --- |
| 单页最大记录 | 200 |
| 响应软上限 | 1 MiB |
| WebSocket 响应硬上限 | 4 MiB |
| 每档案并发 SQLite 查询 | 2 |
| 只读 SQLite 连接 | 固定 2 个，不引入通用连接池依赖 |
| 最大过滤条件 | 16 |
| 最大排序字段 | 2 |
| `include_total` | 默认 false，首个快照最多计算一次 |
| 深分页 | 只允许不透明 keyset cursor |
| 导出 | 后台分批，不占用交互查询槽 |
| 刷新 | 相同范围 in-flight 去重 |

写连接继续使用当前可靠性设置和串行事务。V4 首版不拆数据库；如果基准证明历史写入仍阻塞命令安全写入，再单独提出隔离方案，不能在本次为假设性性能问题增加双库复杂度。

### 13.2 优先级

从高到低：

1. 交易命令、结果回执和未知结果对账；
2. 当前账户、持仓、挂单和交易状态查询；
3. 用户可见历史页面与每日汇总；
4. 后台历史回填、导出和低优先级统计。

任何大型数据响应都必须受字节预算和队列约束，不能因为单个帧占用发送通道而延迟交易结果。

### 13.3 缓存

服务器缓存键至少包含：

```text
user/account route + resource/version + normalized query hash
+ history_revision + summary_revision + captured range
```

修订号未变时可直接复用服务器结果；修订号变化、账户接管、连接代际变化、筛选或范围变化必须失效。不得只用时间 TTL 混用不同账户或不同历史快照。

### 13.4 验收目标

以下是实现验收目标，不是当前实测结论：

- Bridge 内部缓存账户/持仓/订单查询 P95 不超过 20ms；
- 100,000 笔历史下，200 条 keyset 页面 P95 不超过 100ms；
- 十年每日汇总查询 P95 不超过 100ms；
- 服务器生成统计和图表数组 P95 不超过 20ms；
- 同时同步历史和查询时，交易命令调度额外延迟不超过 50ms；
- 32 个并发请求不得导致内存持续增长、队列失控或 WebSocket 断开；
- 任何响应不得突破 4 MiB；软预算超限时应缩页或明确返回 `result_too_large`；
- 超时或取消后必须释放查询槽，不得长期占用只读连接。

## 14. 安全与权限

1. 前端不直接发送 V4；网站后端必须重新鉴权、解析账户路由和限制范围。
2. Bridge 再次验证完整账户路由和连接代际，不能信任服务器只传 login。
3. 资源、字段、过滤、排序和新鲜度全部使用白名单。
4. SQL 只能由 Bridge 预定义查询计划生成，并使用参数绑定。
5. describe 不返回内部表名、列名、索引名、路径或安全层结构。
6. diagnostics 只返回脱敏稳定状态，不包含 token、服务器凭据、终端路径或用户文件内容。
7. 查询日志记录资源、范围、行数、字节数、耗时、修订号和错误码，不记录敏感 payload。
8. 观摩源、普通用户和管理员仍使用现有权限边界；Query V4 不能扩大观摩用户写权限或跨账户可见性。
9. 自定义服务器地址不获得额外本机能力；即使服务器已通过现有授权，也只能调用注册资源和同步动作。

## 15. 服务器与前端职责

### 15.1 服务器

- 把前端业务参数转换成 V4 规范请求；
- 解析日期、终端业务日和精确 UTC 范围；
- 验证用户、账户、观摩频道、归属和只读权限；
- 管理 V3/V4 功能开关、影子比对和 fallback；
- 缓存修订号一致的查询结果；
- 计算统计、图表和跨资源业务含义；
- 对前端保持现有响应合同，逐页面迁移。

### 15.2 前端

- 继续调用网站业务接口或现有 WebSocket 业务动作；
- 不出现资源名、SQLite 字段、游标签名或内部错误；
- 明确显示刷新中、数据不完整、统计未就绪和游标过期；
- 图表和表格必须使用同一冻结范围和过滤上下文；
- 过期响应不得覆盖用户已切换的账户、范围或筛选。

### 阶段 0：冻结基线和合同

- 重新确认分支、HEAD、工作区和现有 Bridge 改动归属；
- 记录 V3 资源、响应、错误码、统计公式和时间语义；
- 建立 1 万、10 万、100 万笔历史 SQLite 测试夹具；
- 记录 V3 功能和性能基线；
- 固化 V4 JSON Schema、资源目录和错误码。

验收：没有代码迁移前，V3 行为、性能和已知风险均有可重复基线。

### 阶段 1：能力协商、describe 和查询内核

- 在现有 hello capability 中声明 `bridge_query_v4`；
- 增加 V4 消息解析、严格字段校验和路由校验；
- 在现有 `bridge-contract`、`bridge-transport` 和 `bridge-store` 内增加小型 V4 模块，不先新建独立 crate；
- 实现资源注册表和 `describe`；
- 实现固定两个只读连接和两个查询槽；
- 首批支持 `account.snapshot`、`positions.current`、`orders.current`。

验收：V4 不影响 V3 hello、命令、delta、回执和旧 Bridge 连接。

### 阶段 2：历史资源和游标

- 实现 `history.trades`、`history.deals`、`history.orders`；
- 复用现有历史覆盖、修订号、快照和不透明 cursor；

验收：V3/V4 同一账户、范围和筛选返回相同事实集合，且无跨账户、重复页或漏页。

### 阶段 3：每日汇总、统计和图表迁移

- 实现 `history.performance_daily`；
- Bridge 只返回每日基础事实和汇总修订号；
- 服务器新增纯函数统计与图表组装；
- 服务器同时读取 V3 `chart_data` 与 V4 汇总做影子比对；
- 前端继续使用现有结构，不同步重写 UI。

验收：总交易、胜率、每日盈亏、累计收益、筛选范围和完整性一致；盈亏比与回撤口径差异必须显式记录，不能静默改值。

### 阶段 4：新鲜度与同步

- 实现三种 freshness 模式；
- 实现有界 `sync_request`、稳定 `sync_id` 和任务附着；
- 合并等价刷新，避免页面表格和图表重复唤醒 MT；
- 大范围历史同步异步执行并返回状态。

验收：普通读取无隐藏写入；强制刷新不清库；断线、超时、重启后同步可继续或安全失败。

### 阶段 5：服务器逐资源切换

- 每个读取入口独立配置 `v3`、`shadow`、`v4`、`disabled`；
- 先切账户/持仓/挂单，再切历史分页和图表；
- 记录结果差异、耗时、字节数、fallback 和错误码；
- 只有稳定资源才停止 V3 主读取。

验收：旧 Bridge、V3 Bridge 和 V4 Bridge 可同时服务；回退无需重新安装客户端或修复数据库。

### 阶段 6：收敛旧读取 action

- 经至少一个稳定发布周期后，停止服务器产生已迁移 V3 读取 action；
- 保留旧 Bridge 所需兼容分支，直到安装基数满足退役条件；
- 删除前必须确认服务器、前端、测试、发布包和旧版本兼容引用；
- V3 交易命令、回执和对账不随读取 action 一并删除。

验收：删除范围有调用证据、遥测证据和可恢复发布基线，不凭代码搜索判断“无用”。

## 19. 发布、回滚与停止条件

### 19.1 发布边界

- 网站部署、Bridge 构建、模块更新包、完整安装包、七牛上传和协议启用分别授权；
- 实现完成不等于允许发布；
- 发布 V4 Bridge 前必须通过 `release-liangjian-bridge` 流程和真实双版本演练；
- 服务器先具备能力协商和 V3 fallback，再允许 V4 Bridge 接入。

### 19.2 回滚

1. 服务器按资源关闭 V4 开关，立即恢复 V3 主路径。
2. 停止发送 V4 请求，不需要删除 SQLite 数据或回滚本地历史。
3. 本地迁移必须是追加兼容，旧代码无法安全读取时不得发布。
4. V4 Bridge 二进制问题通过签名模块或完整安装包按既定发布流程回滚。
5. 统计口径异常只回滚服务器计算层，不清库、不重同步历史。

### 19.3 自动停止条件

出现以下任一条件停止扩大 V4 流量：

- 跨账户数据、路由不一致或权限泄漏；
- 交易命令、回执或对账延迟超过门槛；
- V3/V4 事实集合出现无法解释的缺失或重复；
- WebSocket 超大帧、队列持续满或断线率明显上升；
- SQLite 锁等待、损坏、迁移不兼容或汇总 revision 错乱；
- P95、P99、内存或磁盘增长超过验收预算；
- 真实 MT4/MT5 时间语义或资金流口径无法证明。

## 20. 第一轮复审：需求覆盖、业务边界与最小改动

### 20.1 复审结论

- 需求覆盖：方案保留 SQLite，解决“每新增一种查询都改 Bridge action”的核心问题，并允许未来新增 MT 采集能力时更新 Bridge。
- 业务边界：Bridge 只提供数据事实、同步和安全交易执行；统计解释、图表和业务组合留在服务器。
- 现有能力复用：复用 V3 鉴权、路由、交易命令、实时流、历史快照、修订号、物化汇总和 SQLite WAL，不重建一套传输系统。
- 最小改动：V4 第一阶段只处理 describe/query/sync，不同时迁移交易命令和实时订阅。
- 过度设计检查：不开放 SQL，不实现 JOIN、任意聚合、表达式语言、双数据库、外部服务或通用连接池。

### 20.2 第一轮调整

1. 将早期设想中的通用 `execute` 和 `subscribe` 移出 V4 第一阶段，避免把读取精简与交易协议重写绑定。
2. 不新建独立 `bridge-query` crate；先在现有合同、传输和 Store 中按模块隔离，只有代码边界稳定后再评估拆 crate。
3. 不让服务器查询原始 daily summary 表，而是增加稳定资源 `history.performance_daily`。
4. 不把所有统计移到服务器后再拉取全部明细；保留 SQLite 每日物化汇总，服务器只负责公式和图表。
5. 不在首版拆 SQLite；先以 WAL、固定两个只读连接和两个查询槽验证实际瓶颈。
6. 补充“无需更新 Bridge”的精确边界，并要求首版资源公开完整的稳定非敏感字段，而不是按现有页面最小字段集设计；过滤和排序仍受索引与成本白名单限制。

### 20.3 第一轮剩余风险

- 当前工作区有未提交 Bridge 改动，未来实施基线可能变化；
- MT4 与 MT5 历史完整性证据不同，资源能力可能需要平台标记；
- 部分现有 action 可能混有业务语义，迁移前需要逐个冻结合同；
- 服务器拆分复杂 OR 查询可能增加请求数，需要缓存和批次编排控制。

第一轮结论：需求和边界完整，已去除不必要的交易与实时协议重写，可进入第二轮风险复审。

## 21. 第二轮复审：兼容、数据、并发、安全与回滚

### 21.1 兼容性

- 通过 hello capability 协商，旧 Bridge 不接收 V4；
- 每个资源独立 V3 fallback，避免一次性切换；
- 前端先保持现有响应结构，服务器做适配；
- V3 交易命令和回执不随 V4 读取迁移删除。

### 21.2 数据与迁移

- 本地 SQLite 迁移只追加，不修改已发布语义；
- 资源名和字段版本隔离内部表变化；
- summary 不可用时返回未就绪，不扫描 payload JSON 猜结果；
- 本方案不要求网站 MySQL 迁移或生产数据清理。

### 21.3 并发与幂等

- 两个固定只读连接加两个查询槽，防止 32 个待处理请求同时压向 SQLite；
- 大任务进入低优先级队列，交易和回执始终优先；
- query 使用 request ID 做关联，sync 使用稳定 sync ID 和归一化范围做幂等；
- 相同刷新任务 in-flight 去重，避免表格与图表重复唤醒 MT。

### 21.4 异常恢复

- cursor 和 snapshot 过期返回稳定错误，服务器重新从第一页建立快照；
- 刷新超时返回状态，不把未知完成状态伪装为失败或空数据；
- Bridge 重启后通过现有同步任务、覆盖范围和修订号恢复；
- 查询失败不得影响命令账本、Outbox 和 MT 会话。

### 21.5 时间语义

- 传输、游标和精确过滤使用 UTC 毫秒半开区间；
- 每日统计使用目标终端的业务日；
- 响应必须声明 `time_semantics`；
- 精确 UTC 范围切穿业务日边界时，不得用整日汇总猜测边界部分。

### 21.6 安全

- 前后端双重鉴权和 Bridge 路由复核；
- 资源、字段、操作符、范围和成本白名单；
- 参数化 SQL；
- 安全层不可查询；
- 自定义服务器也不能获得脚本、文件或 SQL 能力。

### 21.7 测试与性能

- 增加 100 万笔历史、32 并发和读写并发基准；
- 影子比对事实集合而非只比较 HTTP/WS 成功；
- 把字节数、排队和交易延迟列为发布门槛；
- 真实 MT4/MT5 与网络验证仍是最终验收必需项。

### 21.8 回滚

- 服务器可按资源关闭 V4；
- V3 fallback 保留至少一个稳定发布周期；
- 追加兼容 SQLite 数据无需删除；
- 统计问题回滚服务器公式，不清库；
- 发布和部署继续使用独立授权边界。

### 21.9 第二轮调整

1. 将响应软预算固定为 1 MiB、硬预算保持 4 MiB，并要求软预算超限优先缩页。
2. 将 `include_total` 默认改为 false，避免每页 COUNT；同一快照最多计算一次。
3. 明确 `payoff_ratio` 与传统 `profit_factor` 两种指标，兼容期不静默改变现有展示数值。
4. 最大回撤拆成金额和百分比；缺少可靠起始资金或资金流证据时百分比返回 null。
5. 明确图表与表格必须共享冻结范围和修订号，防止数据看似一致但统计范围漂移。
6. 增加“查询不能延迟交易结果”的停止条件，避免通用查询吞噬单一 WebSocket 发送资源。
7. 为所有 V4 请求增加绝对截止时间和底层可中断查询要求，避免外层超时后 SQLite 扫描继续占用连接。
8. 明确快照必须携带高水位、资源版本和查询哈希，并允许任一只读连接基于同一快照续页，避免双读连接破坏分页一致性。
9. 明确精确 UTC 范围切穿终端业务日时的“整日汇总 + 有界边界原始聚合”语义，禁止用整日数据猜测边界。
10. 将 V3/V4 pending 请求纳入同一个每连接容量预算，并补充实现后的最低验证命令。

### 21.10 第二轮剩余风险

- 尚无 Query V4 原型和真实基准，所有性能数字只是验收目标；
- 真实用户最大历史量、过滤组合和并发档案数仍需采样；
- MT4 历史来源受终端可见范围限制，不能与 MT5 宣称相同完整性；
- 百分比回撤需要可靠区间起始资金和资金流证据，现有数据是否对所有旧账户完整尚未验证；
- V3/V4 影子读取会短期增加 Bridge 查询量，必须控制采样比例；
- 旧安装基数和实际升级成功率会决定 V3 action 的退役时间。

第二轮结论：方案在兼容、数据、并发、幂等、恢复、时间、安全、测试和回滚方面形成闭环，调整后可作为未来实施基线；真实性能、MT 行为和发布兼容仍需在实施阶段验证。

## 22. 最终实施门槛

只有同时满足以下条件才可以开始编码：

1. 用户明确授权实施，而不是仅授权保存方案；
2. 重新检查当前分支、HEAD、工作区和已有 Bridge 改动；
3. 冻结 V4 Schema、第一批资源和错误码；
4. 确认 MT4/MT5 各资源的真实数据来源和完整性边界；
5. 确认性能夹具、影子比对和回滚开关的负责人；
6. 不涉及生产数据库变更；如未来确需网站数据库改动，必须单独说明并获得明确确认；
7. 实现、构建、发布、上传和部署继续逐项授权。

在上述门槛满足前，本方案保持“已完成、尚未实施”。
