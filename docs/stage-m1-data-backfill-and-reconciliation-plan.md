采用“不可变源备份 → 独立恢复源镜像 → 分域字段映射 → 小批次双目标回填 → 逐项对账”的顺序。源库始终不写；不建设长期双写，不引入新的迁移服务或消息队列。

本轮只有只读 MySQL 元数据、聚合计数、源码检查和文档变更。没有读取/输出用户密码、密钥或正文，没有执行源/目标 DDL/DML，没有改 `.env`、GRANT、全局变量、服务或终端。后续每个执行步骤单独说明并获得确认；本方案不是一次性全量执行授权。

## 3. B1：冻结备份与恢复源镜像

### 3.1 执行前检查

- 核对实际 MySQL 实例 UUID、库名、所有表/对象类型、版本、字符集、SQL mode、时区及客户端版本；记录脱敏元数据。
- 备份期间源库不得发生 DDL。InnoDB 一致性导出允许普通事务写入，但不代表整次切换期间可无维护窗口；正式上线另设停写门。
- 不设置全局 read_only、event_scheduler 或全局锁来影响同实例其它项目。若无法保证源 DDL 窗口，停止并协调，不自行停服务。
- 核对受限备份目录、磁盘余量和恢复空间。按实际导出及恢复体积设预算，不能把 682.50 MiB 当成精确空间承诺。
- 当前 A/B 已不是空库，保留现有迁移审计；绝不导入原结构 dump，也不清空重建。

### 3.2 备份产物

首版采用同大版本 `mysqldump`，候选参数为 `--single-transaction --quick --hex-blob --default-character-set=utf8mb4 --tz-utc --no-tablespaces --set-gtid-purged=OFF --routines --events --triggers --skip-lock-tables`，实际命令必须在实施时复核客户端选项和权限。一致性快照只保障事务表；导出期间 DDL 会破坏其假设。[MySQL 8.4 mysqldump](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html)

本项目额外约束：

- 只导出 `dev_vue`，不使用 `--all-databases`，不包含 MySQL 系统账号/权限；凭据不放命令参数、日志或 Git。
- 在 SSH 主机受限路径保存产物，避免经 PowerShell 文本重定向改变字节编码。数据库数据以驱动/工具原始字节处理。
- 原始 dump 包含敏感信息；目录 0700、文件 0600，备份需加密，密钥与包分开保管，使用现成成熟加密工具。工具/密钥保管路径未确认则停止，不临时自写加密协议。
- 产物包括备份文件 hash、大小、工具版本、源标识、导出起止时间、对象清单、退出状态和恢复验证结果。压缩/加密包 hash 与解密后的 SQL 内容 hash 分别记录。
- `--tz-utc` 处理 TIMESTAMP 的时区传输，不会替我们判断旧 DATETIME 的业务时区；原始 DATETIME 墙钟值先完整保留。[MySQL 时区导出说明](https://dev.mysql.com/doc/refman/8.4/en/mysqldump.html#option_mysqldump_tz-utc)
- 不在报告中输出密码哈希、模型密钥、邮箱/手机号清单、提示词或推理正文。备份不得进入 Git、公开下载或当前网站目录。

### 3.3 恢复验证与冻结

建议新建独立源镜像 `dev_vue_m1_source_20260905_01`，**尚未授权/创建**。实施前确认精确名称与路径；名称存在且非空立即拒绝，不能覆盖。

1. 对 dump 做语句级目标审查，禁止活动 SQL 跳回 `dev_vue` 或修改其它 schema/global 状态。不要用全局字符串替换库名破坏用户正文；不把原 dump 交给 V4 结构迁移器。
2. 在新空镜像恢复原结构与原数据，不进行 UTC 转换、JSON 规范化、字段裁剪或主键调整。保留恢复失败现场，不删库重试。
3. 当前源无事件/触发器/例程；若实施时出现，先复审 definer、跨库引用和副作用。不得在共享实例上恢复可能自动执行的任务，也不能为此关闭全局调度器。
4. 恢复完成后镜像只供 SELECT，应用和 Worker 永不连接它。重新生成所有表的精确计数、主键边界、逐行原值摘要和数据异常报告。
5. 将备份内容 hash 绑定为 `source_snapshot_id`，后续 A/B 一律从同一个已恢复且不再变化的镜像读。不能每张表新开一个源库快照冒充一次冻结。
6. 如果原源仍在变化，导出前后的源 COUNT 不要求相等，也不能用它们验证 dump 内数据；以成功的一致性备份及其恢复镜像建立基线。最终上线时再用获批停写快照完成一致性校验。

### 4.3 关键转换约定

- 保留用户 ID/UID、密码哈希、角色、安全版本；邮箱/手机号排序规则变化引发的冲突必须报告，不能合并登录身份。
- BIGINT、金额和价格通过十进制字符串/定点处理。DOUBLE 同时保留原存储表示及转换误差，不用 JS Number 二次四舍五入。
- 每列区分 `utc_epoch_ms / utc_datetime / beijing_wall_clock / terminal_wall_clock / business_date / unknown`。旧写入助手与连接存在 +08:00，但不代表每个 DATETIME 都能统一减 8 小时。
- 新 UUID 由受控命名空间、logical source ID、源表、规范化源 PK、投影角色稳定派生，或使用先冻结再复用的映射。不能把当前时间/随机值或每次 snapshot ID 当成业务 ID 的唯一依据。
- 多个旧账户 ID 可显式映射同一实体；原系统用户的访问与归属区间必须保留，不能让新 owner 看到旧 owner 的私有分析/操作。
- 旧验证挑战、SSO 会话、Bridge 凭据、付费额度各有独立政策。SSO 会话不从旧浏览器 JWT 伪造；Bridge 已批准的 V3→V4 更新/refresh 迁移链不被本次数据库工具撤销。具体有效期/验证列未落实前不得切换认证。

## 5. B3：回填执行机制（待实现）

继续使用独立 Node CLI，不接入应用启动/PM2/Worker。Schema 执行器不承担数据迁移；复用其目标隔离、命名锁、稳定错误码和校验理念，不滥用其文件级 DDL 检查点。

最小持久化实体候选：迁移 run、批次 checkpoint、legacy ID map、逐源行处置 receipt、阻断 issue。只有命名锁/摘要不够，无法证明“一行旧数据去了哪里”。具体 DDL 使用 017 后的追加文件，当前不预占号或执行。

执行规则：

1. run 绑定 source snapshot hash、目标实例/库、目标迁移清单 hash、transform/field-manifest hash；目标不能是源或恢复镜像，禁止默认 `.env` 回退。
2. 读取采用主键稳定游标；组合主键按明确顺序分页。单 worker 首版；默认最多 500 行且有累计字节上限。单条超大载荷独立处理，不能截断。
3. 每批“业务写入 + ID map + row receipt + checkpoint”在同一个短目标事务里提交。网络、压缩、解密等预处理在事务外完成；source 镜像只读。
4. 幂等键存在且全部内容相同则跳过；相同键不同内容失败关闭。禁止 INSERT IGNORE、REPLACE 或不比较内容的 ON DUPLICATE KEY UPDATE。
5. 父表优先，nullable 当前版本指针最后补；不关闭目标外键/CHECK。已执行结构不足时追加迁移，不临时删除约束。
6. 数据批次连接丢失后先按批次 ID/目标 receipt 查询是否提交，再决定是否重做；与不可重放 DDL 恢复明确分开。死锁只重试整段已证明幂等的批次，次数有上限。
7. 冻结镜像 hash、转换版本或字段规则变化后，旧 checkpoint 不能继续使用。保留失败目标，新一轮目标或恢复方案须另行确认，不能清空 A/B。
8. 不写可被 Worker 消费的 queued/running 作业，不恢复历史 outbox/lease，不执行模型、通知、支付激活或 Bridge 指令。原始状态保留在历史证据；活动启用是另一个带审计的切换步骤。

建议波次：身份/模型 → 账户/归属/时区 → 策略/订阅 → 分析/推理/行情历史 → 风控/执行/终端结果 → 复盘/记忆 → 主站/商业/通知。领域没有承接完不能声明全量完成；可先做已具备结构的波次，但必须全部保持未切流。

## 6. B4：对账与恢复质量门

### 6.1 三层证据不能互相替代

- **原值保全**：源记录原字节/类型、NULL/空串/JSON 字符串/二进制区分；备份/受控历史载荷可恢复。
- **业务语义**：按显式转换后的 ID、时间、金额、状态、父子关系逐项核对；不能要求正常转换后的 bytes 与原值相同。
- **用户可用性**：仍存在的功能在新接口/页面可访问，且权限正确；“备份里有”不等于用户没有丢功能。

每张源表都要有逐源主键 receipt。对于一对多拆分和多对一合并，比较源 receipt 覆盖，而不是机械要求目标行数相等。遗漏=0、重复处置=0、未解释冲突=0；空表也须有结构/功能处置记录。

### 6.2 必测不变量

- 逐系统用户：身份/会员、账户归属、订阅、分析历史、交易意图/结果、复盘、记忆、支付与通知数量/权限。
- 逐账户和币种：gross/net/commission/swap/fee、付款/确认/返佣金额；币种、状态、单位不能混加。
- 逐载荷：原 bytes 长度/hash 和转换后 payload hash；不得只比较聚合行数或一个全库 hash。
- 平台信号、孤儿通知、账户合并、未知时区、非法 JSON、历史不确定命令分别有清单与已审核处置。
- A/B 用同一 snapshot/transform/mapping 运行：稳定 ID、业务值、关联和载荷均相同；只排除明确列出的 run ID、执行时刻等运维字段。
- 中断用例：批次提交前、提交后响应丢失、同键内容变化、缺父映射、schema 漂移、大载荷、复合 PK、时区边界。
- 不向任何运行队列发任务；重跑不会重复支付激活、通知、模型调用或交易。MT5 当前实盘账号禁止交易测试。

已有 `trade-history-migration-rehearsal.mjs` 可复用部分精确金额对账，但它只检查传入聚合，不读取数据库，也不证明旧记录已正确写入；不得把其 Mock 通过当作迁移完成。

### 6.3 回滚不是简单切回旧库

切流前失败：源保持不动，保留失败目标/日志，应用继续原库即可。没有理由删除或覆盖目标。

切流后产生新写入：立即切回旧库可能丢失新交易/付款/会员/复盘，必须先停相关写入、冻结新增事实并按逆向清单对账。尤其终端成交不可由数据库回滚撤销。本方案不授权切流，也不承诺一条命令完成无损回滚。

## 7. 两轮复审与调整

### 第一轮：需求覆盖、职责、复杂度

- 发现旧矩阵“表名存在/保留”会掩盖当前合同改变，新增 165 表物理覆盖清单和 13 表字段名差异。
- 纠正重复源条目、早期 JS 目录和反复清空目标的过时说明；迁移历史继续永久保留。
- 不为对齐旧图纸推倒已实现 users/auth；但明确遗漏字段必须承接，不以保留原库推迟功能缺口。
- 不把旧混合提示词自动变成新交易员策略，不制造 V4 模型任务链；历史展示与运行激活分离。
- 不添加迁移常驻服务、队列或复杂通用 ETL 平台，采用模块化 CLI 与少量审计结构。

### 第二轮：数据、安全、并发、异常与回滚

- 源表计数相同不等于快照相同；改为一次备份、恢复镜像、A/B 共用同一 source hash。
- 禁止把新 user 0、默认 UTC+3、空 JSON 或另一账户作为补数据手段。
- 原 JSON bytes 与转换语义使用两种校验，解决目标原生 JSON 重排可能造成证据 hash 混淆。
- 针对已有平台种子和 BIGINT→UUID 的碰撞，要求持久化 ID map；针对归属合并补私有历史隔离验收。
- 备份恢复避免触发共享实例事件，不设置全局 read_only；新恢复源库及受限备份路径需精确授权。
- 新写入后的回滚不能只改连接字符串；财务与终端副作用必须有独立逆向对账，不能用恢复旧 dump 抹除。

剩余风险：逐列时间来源尚未全部证明；历史读取/主站商业结构缺口未实施；备份工具、磁盘与加密保管路径未验收；没有真实备份恢复或数据回填结果。
