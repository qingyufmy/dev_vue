# 手动复盘与策略记忆维护可靠性修复方案

## 1. 文档状态

- 文档类型：生产问题诊断后的整合修复方案
- 编写日期：2026-08-24
- 代码基线：`dev_codex` / `7d7bf627935c9e49cc74b7046f9e92c355a32674`
- 生产核验：虚拟机 `/www/wwwroot/aurum-ai` 为同一提交，工作树干净
- 当前授权：只诊断和编写方案；不修改业务代码、不清理数据库、不重试任务、不重启或部署

本方案整合四类已确认问题：

1. 手动复盘创建稳定返回 `manual_trade_review_history_snapshot_changed`；
2. 策略记忆一致性检查在模型调用前失败，并在重试时产生任务关联冲突；
3. 前端把仍可自动重试的失败状态当成最终失败，页面不继续更新；
4. 已与当前策略、当前记忆库失去绑定的历史冲突仍被展示为当前冲突。

## 2. 结论摘要

这四类现象不是同一个业务错误，但共同暴露出“合同语义与状态展示没有使用同一套判定”的问题。

| 编号 | 结论 | 影响 |
|---|---|---|
| MRS-01 | `history_evidence_v1` 按设计是“固定范围 + 精确交易引用”的点查接口，不接收也不返回历史分页快照 ID；Web 服务却强制要求其返回选择阶段的快照 ID | 正常证据响应被误报为快照变化，创建在事务前终止 |
| MRS-02 | `memory_consistency` 未登记模型容量用途 | 一致性任务在供应商调用前进入 `retry_wait` |
| MRS-03 | 同一一致性 job 的下一次尝试创建新模型任务，但 job 仍绑定旧任务，关联更新拒绝覆盖 | 第二、三次尝试转为 `model_task_link_failed`，留下孤立通用模型任务 |
| MRS-04 | 前端仅按 `status === failed` 判定终态，没有结合 `attempt_count/max_attempts/next_attempt_at` | 后端仍会重试，前端却停止轮询 |
| MRS-05 | 冲突列表把 `location_stale`、零当前绑定的历史记录与当前命中记录混在一起 | 已清空或更新策略后，旧冲突仍看起来正在生效 |

本轮不应通过取消交易来源校验、删除历史冲突记录或粗暴清空模型任务来获得“表面正常”。修复必须保留冻结范围、交易身份哈希、任务幂等和历史审计。

## 3. 当前证据

### 3.1 手动复盘创建

代码链路如下：

1. 候选接口创建签名选择上下文，冻结用户、账户、平台、最近 7 天范围和 `history_snapshot_id`；令牌有效期为 15 分钟。
2. 创建接口在写数据库前调用 `readManualTradeEvidence()`，按所选 `position_id/order_ticket` 二次读取证据。
3. Web 服务把选择快照 ID 传给 `history_evidence`，并要求响应中的快照 ID 与选择快照完全相同。
4. 但 `server/bridge-v3/business-adapter.js` 只对 `history_page` 传递 `snapshot_id`；`history_evidence` 会丢弃该字段。
5. 原生 Bridge 的 `HistoryEvidenceRequest` 允许字段中没有 `snapshot_id`，返回体也没有 `history_snapshot_id`。它用固定时间范围和精确引用读取成交与历史订单。
6. 因此生产正常响应的 `result.history_snapshot_id` 为空，Web 服务把“没有该字段”误判为“字段发生变化”。

生产虚拟机运行的正是上述代码。近 24 小时没有新增 `manual_trade_review_cases`，说明本次请求在证据校验阶段结束，没有创建半成品 case/job，也没有触发模型生成。

现有 `manual-trade-review-history` 测试 20/20 通过，但测试 mock 的 `history_evidence` 响应沿用了带快照 ID 的页面对象，没有模拟原生 Bridge 的真实返回结构；这是明确的测试缺口。

### 3.2 一致性任务失败

- `memory_consistency` 没有出现在 `model-task-capacity.js` 的用途映射中，首次尝试报 `model_capacity_usage_unknown:memory_consistency`。
- 失败后 job 仍保存第一次的 `model_task_id`；下一次尝试按新的幂等键创建新任务，关联 CAS 只允许空值或同一任务 ID，因此报 `model_task_link_failed`。
- 生产最近三个一致性 job 均以 3/3 次失败结束，且 `ai_model_task_attempts` 没有对应供应商尝试，证明失败发生在模型调用前。
- 当前生产还留有 66 条与这些已终止 job 关联不完整的通用模型任务（44 queued、22 retry_wait）。这是待评估的历史数据修复对象，不是本次代码发布时可顺手删除的数据。

### 3.3 页面不自动更新

后端允许 `failed + attempt_count < max_attempts + next_attempt_at` 的任务继续重试；用户端和管理端前端却把所有 `failed` 都视为终态并停止轮询。页面状态因此落后于后端状态机。

### 3.4 历史冲突误展示

- 当前生产策略已是 v25，当前记忆库为 v8；v7 曾被重置为空，v8 是之后的新内容。
- 截图中的旧冲突只有一次历史 occurrence，当前 `matched_bindings=0`、`total_bindings=0`，并标记为 `location_stale`。
- 当前策略和当前记忆正文均未匹配截图中的旧语句，因此它是需要保留的审计记录，不是仍在生效的当前冲突。
- 前端目前将非活动冲突也放进“策略冲突提醒”，并提供“重新打开”，造成语义错误。

## 4. 修复目标与非目标

### 4.1 目标

1. 正常的 `history_evidence_v1` 点查响应可以创建手动复盘；所选交易被修改、缺失或换账户时仍必须失败关闭。
2. 一致性任务能使用通用模型容量、按同一业务 job 正确重试，并保持每次模型任务可审计。
3. 前后端共享统一的“可重试/最终结束”判定，页面持续更新到真实终态。
4. 当前冲突和历史失效冲突分区展示，不删除审计历史。
5. 为四类问题补上贴近真实合同的纵向测试和部署后验收。

### 4.2 非目标

- 不改变手动复盘的最近 7 天、盈利单、人工来源判定、平台策略、最大选择数等业务规则。
- 不减少交易身份、来源哈希、账户、平台、冻结范围和证据完整性校验。
- 不让前端在证据变化后自动替用户确认并创建任务。
- 不自动清空记忆库、删除冲突、删除 case/job/model task。
- 不借本轮重构模型任务框架、Bridge 历史分页协议或策略记忆体系。
- 不把 `history_evidence_v1` 临时改造成分页快照接口；如未来需要快照绑定的点查，应新增版本化能力，而不是悄悄改变 v1。

## 5. 实施批次 A：修复手动复盘创建合同

### 5.1 服务端判定

修改 `server/routes/ai/manual-trade-evidence.js`：

1. 保留签名 `selection_context_token` 的用户、账户、平台、冻结范围和有效期校验。
2. 继续把选择阶段快照作为来源审计信息，但不再要求 `history_evidence_v1` 必须回显该字段。
3. 只有当证据响应**明确返回了非空** `history_snapshot_id` 且与选择快照不同，才返回 `manual_trade_review_history_snapshot_changed`。
4. 响应没有快照 ID时，必须继续完成现有二次核验：
   - 精确 `position_id/order_ticket` 引用；
   - 当前权威账户和唯一 Bridge 路由；
   - 固定选择范围；
   - 完整性与终端时钟状态；
   - `source_identity_hash` 一一匹配；
   - `trade_source_hash` 一一匹配；
   - 权威关闭时间仍位于冻结范围；
   - 当前持仓和系统关联排除规则。
5. 任一所选交易缺失或哈希变化，继续返回 `manual_trade_review_source_changed`，不得自动接受新内容。

这不是“放开快照安全检查”。分页快照负责候选列表的稳定翻页；创建阶段的点查安全边界是签名范围、精确引用和不可变来源哈希。它们与当前 `history_evidence_v1` 的真实协议一致。

### 5.2 前端恢复

修改 `public/ai/app.js`：

- 对 `selection_context_expired/invalid/mismatch`、`history_snapshot_changed`、`source_changed` 使用同一条有界恢复路径：清空当前 cursor、快照、选择令牌和已选交易，保留筛选条件、策略和用户论点，重新读取候选列表。
- 不自动再次提交创建请求；刷新后由用户重新确认交易并点击创建。
- 失败请求的 `client_request_id` 继续保留，维持现有“只在成功响应后轮换”的幂等策略。
- 文案区分“候选已刷新，请重新选择”和普通接口失败，避免用户反复点击同一失效选择。

### 5.3 测试

补充：

1. 原生 Bridge 形状的 `history_evidence`（无快照 ID）+ 交易哈希一致：成功。
2. 响应明确带不同快照 ID：失败关闭。
3. 无快照 ID但所选交易缺失或来源哈希变化：`source_changed`。
4. 适配器合同测试：`history_evidence_v1` 不发送未知 `snapshot_id`，`history_page` 仍发送。
5. 前端恢复测试：只刷新候选，不自动重放 POST，不丢策略和论点。
6. 创建事务测试：证据失败时零 case/job/source 写入；成功时仍只创建一套幂等记录。

## 6. 实施批次 B：修复一致性任务容量与重试关联

### 6.1 容量用途

修改 `server/routes/ai/model-task-capacity.js`：

- 将 `memory_consistency` 明确映射到现有 background 用途。
- 不新增独立容量池，不改变前台分析和交易执行优先级。
- 未知 task type 仍失败关闭，不能用通用默认值掩盖拼写或接线错误。

### 6.2 重试任务身份

修改 `server/routes/ai/strategy-memory-consistency.js`：

- 明确业务 job 与模型 attempt 的一对多关系。
- 每次自动重试可以拥有独立 `ai_model_task`，但必须在领取 attempt 时以事务/CAS 原子更新当前 `model_task_id`；不得用“只能为空或同值”的首次关联条件阻断合法重试。
- 关联条件至少校验 job ID、attempt 编号、租约 owner、当前可重试状态，防止旧 worker 覆盖新 attempt。
- 同一 attempt 重入时复用同一个确定性幂等键和模型任务，不重复调用供应商。
- 只有当前 attempt 明确失败后才推进下一 attempt；供应商状态未知继续失败关闭。
- job 到达最终状态时，不再创建或遗留新的 queued 模型任务。

### 6.3 测试

- `memory_consistency` 容量映射及未知用途拒绝。
- 第一次失败、第二次重试成功的完整链路。
- 同一 attempt 重入只产生一个模型任务。
- 旧租约/旧 attempt 不能覆盖当前模型任务。
- 3/3 失败后没有第四个任务，job 与每次 attempt 都可追踪。
- 并发领取和进程中断恢复测试。

## 7. 实施批次 C：统一重试状态与前端轮询

提取或镜像一个明确的状态判定合同：

```text
terminal = succeeded
        || succeeded_noop
        || stale
        || status_unknown
        || (failed && attempt_count >= max_attempts)
retryable = failed
         && attempt_count < max_attempts
```

`next_attempt_at` 只决定立即领取还是等待，不单独决定任务是否终止；为空或已到期时可立即领取，未来时间则继续等待。这与当前后端 `consistencyJobClaimable()` 的行为保持一致。

用户端与管理端都按该合同处理：

- `retryable` 显示“等待第 N 次重试”和下次时间，继续轮询；
- 正在租约/执行显示当前阶段；
- 只有真正 terminal 才停止轮询并显示“检查失败”；
- 页面重新打开时立即拉取一次，不能依赖旧内存状态；
- 网络错误使用有界退避，不改写服务端业务状态。

后端列表/详情响应应直接返回足够字段；如已有字段齐全，不再新增重复状态列。

## 8. 实施批次 D：区分当前冲突与历史冲突

后端列表结果增加或统一派生展示分类，不修改历史记录：

- `current`：至少有一个当前策略/当前记忆绑定命中，位置验证不是 `location_stale`；
- `observing`：当前仍有有效绑定但证据数未达阈值；
- `historical`：`location_stale`、当前绑定为零，或仅命中过期策略/记忆版本；
- `resolved`：已有明确人工处置结果。

前端：

- “策略冲突提醒”只显示 `current/observing` 的当前有效项；
- `historical/resolved` 放到默认折叠的“历史记录”区域，标明来源版本和失效原因；
- `location_stale` 不提供“重新打开”。若新版本再次真实命中，应由新的扫描 occurrence/binding 推动状态，而不是复活旧位置；
- 保留旧 occurrence、人工处置和版本审计，不删除、不改写旧正文。

## 13. 第一轮复审：安全合同与最小改动

### 13.1 发现

初步思路是给 `history_evidence_v1` 补传分页快照并修改原生 Bridge。复核现有 Bridge 合同后确认，这会把“精确引用点查”扩成新的协议，要求所有已安装 Bridge 同步升级，超出本次 Web 创建失败的必要范围。

另一个过于宽松的思路是直接删除所有快照比较。这样会失去对未来显式回显不同快照的防御，也无法清楚说明安全边界。

### 13.2 调整

- 保持 `history_evidence_v1` 不变，只把服务端比较改为“非空才比较”。
- 明确保留签名范围、精确引用、身份哈希和来源哈希二次核验。
- 给真实的无快照响应补测试，同时保留显式快照不一致的失败测试。
- 将前端自动恢复限定为刷新候选，禁止自动重提创建。

### 13.3 第一轮结论

调整后的批次 A 能修复生产必现错误，不要求 Bridge 客户端发布，也不降低所选交易证据的完整性校验。

## 14. 第二轮复审：状态、并发与历史数据

### 14.1 发现

若只放开 `model_task_id` 覆盖，旧 worker 可能在租约过期后覆盖新 attempt；若只修前端轮询，后端任务关联仍会继续失败。若直接删除 `location_stale` 冲突或 66 条遗留模型任务，又会破坏审计链并扩大本次授权。

### 14.2 调整

- 将重试关联收紧为 job + attempt + lease 的 CAS，而不是无条件替换。
- 批次 B 与 C 必须一起验收：后端能真实重试，前端才有继续轮询的意义。
- 历史冲突只改展示分类，不删除数据。
- 遗留任务清理拆成部署稳定后的独立授权步骤，并要求候选重算、备份和窄条件更新。
- 各问题分提交，手动复盘修复可独立回滚。

### 14.3 第二轮结论

方案已覆盖合同、幂等、并发租约、前端状态、历史审计和回滚边界，没有引入第二套任务或冲突系统，可以进入实施评审。

## 15. 剩余风险

1. 当前服务没有保存本次失败请求的完整 Bridge 响应，不能从日志逐字还原响应体；但部署代码的适配器和原生 v1 合同均确定不提供快照 ID，且错误发生位置与生产现象一致。
2. 已安装 Bridge 可能存在版本差异；批次 A 的验收必须同时覆盖当前真实 MT4/MT5 客户端，不能只依赖 JS mock。
3. `history_evidence_v1` 是当前点查合同。若未来业务要求“证据点查也必须绑定高水位快照”，应新增版本化 capability，并在 Bridge 灰度升级后切换，不能在本轮暗改。
4. 真实供应商超时或状态未知仍需失败关闭，本方案不会为追求自动恢复而重复不确定请求。
5. 前端轮询依赖页面仍在线；重新进入页面必须以服务端详情为准。
6. 历史冲突分类依赖当前绑定数据正确维护；需补“策略升级、记忆重置、新版本再命中”的纵向测试。
7. 66 条遗留模型任务的数量会随生产状态变化，任何处理前都必须重新只读审计并取得数据库写入授权。

## 16. 完成定义

只有同时满足以下条件，才可宣称本轮修复完成：

- MRS-01 至 MRS-05 均有对应代码、测试和问题到修复映射。
- 原生形状的无快照 `history_evidence` 能成功创建复盘；交易变化仍失败关闭。
- 新一致性 job 至少完成一次真实模型 attempt，自动重试不再报容量未知或任务关联失败。
- 用户端和管理端持续轮询到相同终态。
- 当前冲突区不再混入 `location_stale` 零绑定历史记录。
- 专项测试和全量测试通过，未夹带用户未跟踪文件。
- 部署提交、运行进程、静态资源和只读生产证据一致。
- 写入型生产验收、数据库遗留任务处理均在各自授权边界内完成并记录结果。
