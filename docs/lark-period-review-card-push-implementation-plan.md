# AURUM 复盘结果推送 Lark 简化实施方案

> 状态：卡片 v2 已实施并验收；21 个离线测试通过，虚拟机真实数据核对确认总结字段、逐笔评价和周期缠论完整；4 条日复盘共推送 8 张 v2 卡片全部成功，按单卡去重复验通过；Codex 每天 09:00 任务已启用
>
> 运行位置：当前 Windows 本地环境
>
> 运行时间：每天 09:00（Asia/Shanghai）

## 1. 最终方案

只做一个本地 Python 脚本：

```text
Codex 每天 09:00 定时运行
        ↓
本地 Python 脚本
        ↓ HTTPS 登录并读取虚拟机上的现有 AURUM 复盘 API
按策略整理日复盘 / 月复盘
        ↓
Lark 自定义机器人消息卡片
```

不新增服务端接口，不新增数据库表，不直接查询 MySQL，不部署 systemd，不运行常驻进程。

## 2. Python 脚本职责

建议新增一个文件：

```text
scripts/push_period_reviews_to_lark.py
```

脚本每次运行只完成以下步骤：

1. 从本地私有配置读取 AURUM 网站地址、登录邮箱或手机号、密码和 Lark Webhook。
2. 调用现有 AURUM 登录接口取得临时 Token。
3. 调用现有复盘接口读取平台策略的日复盘和月复盘列表。
4. 对有当前版本、证据完整、没有被替代的复盘读取详情。
5. 按策略整理内容，每个策略、每个复盘周期发送一张总结卡和一张明细卡。
6. 每张成功卡片按 `复盘案例 ID + 版本 ID + 卡片结构版本 + 卡片类型` 写入本地状态文件，下一次不重复发送。
7. 输出简短运行结果，供 Codex 定时任务查看。

现有可复用接口：

```text
GET /api/ai/period-reviews
GET /api/ai/period-reviews/:id
```

这些接口已经返回策略名称、策略 ID、周期、状态、证据状态和结构化版本内容，无需为推送功能改 AURUM 后端。

## 3. 推送范围

默认规则：

- 只推送平台策略复盘，不推送普通用户私有策略复盘。
- 日复盘和月复盘都检查。
- 只推送已经生成结果的当前版本。
- 证据不完整、仍在生成、失败、待修订或已被替代的记录不推送。
- 同一复盘版本只发送一次。
- 人工编辑产生新版本时，可再推送一次，并标记“修订版”。

每天 09:00 运行时，不硬编码“只取昨天”，而是读取最近一段时间内尚未推送的结果。这样即使某天电脑关机或 Codex 没有运行，下一次也能补发遗漏，不会丢消息。

默认最多回看 7 天，最多发送 20 张卡片，避免首次运行把全部历史刷进群。首次正式运行前先用预览模式确认范围。

## 4. 按策略整理卡片

不同策略绝不混在同一张卡片中。卡片 v2 将每个复盘拆为两张：

- 总结卡：完整展示核心结论、优势、问题、风控观察和下一步行动；正常复盘数量不再静默截为 3 条。
- 明细卡：日复盘展示全部逐笔交易评价、周期缠论判断和逐笔缠论诊断聚合；月复盘展示全部每日评价以及冲突组、记忆候选数量。

标题：

```text
日复盘总结｜策略名称
日复盘逐笔明细｜策略名称
月复盘总结｜策略名称
月复盘每日明细｜策略名称
```

卡片内容顺序：

1. 复盘周期。
2. 策略名称、策略 ID、策略版本。
3. 当前状态：待人工确认或已确认。
4. 样本数量、证据状态、综合判断、置信度。
5. 核心结论。
6. 做得好的地方，完整展示。
7. 需要关注的问题，完整展示。
8. 风控观察，完整展示。
9. 下一步行动，完整展示。

日复盘字段：

- 核心结论：`period_summary`
- 做得好的地方：`strengths`
- 需要关注：`repeated_issues`
- 风控观察：`risk_observations`
- 下一步：`daily_lessons`

月复盘字段：

- 核心结论：`period_summary`
- 做得好的地方：`strengths`
- 需要关注：`recurring_patterns`
- 风控观察：`risk_observations`
- 下一步：`next_month_actions`

日复盘逐笔评价全部进入明细卡；缠论逐笔诊断按状态和问题来源聚合，只有偏离主要状态的异常项才单列，避免重复七次相同说明。月复盘中的记忆候选只显示数量，不描述成已经生效的经验。

## 5. 数据清理和隐私

卡片不显示：

- 用户姓名、邮箱、手机号和网站用户 ID。
- 完整 MT4/MT5 登录号。
- 余额、权益、绝对手数。
- 订单号、成交号、提示词、模型请求、API Key 和内部错误堆栈。

超长总结和列表会截短；正文不直接输出原始 JSON。内部英文状态转换为自然中文，未知状态显示“未知”，不自行猜测。

## 6. 本地配置

源码只读取环境变量：

```dotenv
AURUM_BASE_URL=https://www.cnfxtrade.com
AURUM_PUSH_EMAIL=<有平台复盘读取权限的邮箱>
# 如使用手机号登录，则改用 AURUM_PUSH_PHONE
AURUM_PUSH_PASSWORD=<密码>
LARK_REVIEW_WEBHOOK_URL=<完整Webhook>
LARK_REVIEW_LOOKBACK_DAYS=7
LARK_REVIEW_MAX_CARDS=20
LARK_REVIEW_STATE_FILE=D:\dev_codex\wall-street-skill-local\.local\lark-review-push-state.json
```

本地可以把完整 Webhook 写入仓库根目录的 `.env.lark-review.local`，脚本用一个很小的本地解析函数读取。当前 `.gitignore` 已忽略 `.env.*`，因此该文件不会进入 Git；Codex 定时任务提示词中也不写任何凭据。

原因是该地址实际是外部 Lark 发送凭据；脚本在本地运行不等于地址不会随源码、Git 或备份泄露。当前地址已经出现在聊天记录中，正式启用前建议在 Lark 中轮换一次。

账号要求：使用能够读取平台策略复盘、但不用于日常操作的账号。脚本只调用登录和 GET 接口，不调用确认、编辑、重试、删除或策略修改接口。

## 7. 本地去重

使用一个简单 JSON 文件，不引入 SQLite：

```json
{
  "sent": {
    "101:205:card-v2:summary": {
      "sent_at": "2026-08-10T01:00:00Z",
      "strategy_id": 12,
      "period_key": "2026-08-09"
    }
  }
}
```

去重键是：

```text
period_case_id:version_id:card-v2:summary
period_case_id:version_id:card-v2:detail
```

总结卡和明细卡独立去重：若总结卡成功而明细卡失败，下一次只补发明细卡。旧版 `case_id:version_id` 记录保留审计，但不会阻止 v2 卡片补发。写文件时先写临时文件，再原子替换，避免运行中断造成半个 JSON。状态文件仅在 Lark 明确返回成功后写入。

如果 Lark 已收到请求但本地没有收到响应，脚本把该条写入 `unknown`，本次不立即重发，并在运行结果中提示人工检查，避免无休止重复刷屏。

## 8. 脚本运行方式

提供两个模式：

```powershell
python -X utf8 scripts/push_period_reviews_to_lark.py --dry-run
python -X utf8 scripts/push_period_reviews_to_lark.py
```

`--dry-run` 会登录和读取复盘，生成脱敏卡片预览，但不会请求 Lark，也不会写已发送状态。

正常成功输出示例：

```text
读取复盘 6 条，符合条件 3 条，发送成功 3 条，跳过 3 条，失败 0 条。
```

没有新复盘时正常退出，输出：

```text
没有新的复盘结果需要推送。
```

退出码：

- `0`：成功，或没有新结果。
- `1`：登录、读取或发送存在失败。
- `2`：本地配置缺失或格式错误。

## 9. Lark 请求处理

- 使用 `msg_type=interactive` 的静态消息卡片。
- 串行发送，每张卡片之间间隔约 1 秒。
- 单次请求超时 10 秒。
- 网络错误、HTTP 429 和 5xx 最多重试 3 次。
- HTTP 2xx 还必须检查 Lark 返回 JSON 中的成功状态，不能只看 HTTP 状态码。
- 400、401、403 或非法卡片直接报错，不盲目重试。
- 日志不打印 Webhook、AURUM 密码、Token 或完整卡片正文。

Lark 官方文档说明消息卡片使用结构化 JSON，并支持 Markdown 文本和彩色标题，适合把复盘结论、风险和下一步分层展示。实现时仍要在测试群实发确认当前客户端效果。

## 10. Codex 每天 09:00 定时任务

Codex 本地 Cron 自动任务已按以下配置创建。脚本通过真实 dry-run 和一次正式手工验收后，再把任务从暂停改为启用：

- 名称：`每天推送 AURUM 复盘到 Lark`
- 类型：Codex 本地项目定时任务
- 项目：`D:\dev_codex\wall-street-skill-local`
- 时间：每天 09:00
- 时区：Asia/Shanghai
- 工作目录：`D:\dev_codex\wall-street-skill-local`
- 动作：运行 Python 脚本，检查退出码，并汇报发送数、跳过数和失败原因。
- 通知：成功且无新复盘时保持简洁；失败时明确提醒。

定时任务的提示词只写运行命令和结果检查，不写 Webhook、账号或密码。敏感配置由该本地项目的环境配置提供。

创建后先执行一次手动运行，确认：

1. 使用的是正确项目和 Python。
2. 能读取私有环境配置。
3. 无新复盘时不会误报失败。
4. 失败会保留在 Codex 任务结果中。
5. 同一版本不会重复推送。

当前任务 ID 为 `aurum-lark`，状态为启用。私有登录配置和 Webhook 保存在 Git 忽略的 `.env.lark-review.local` 中。

## 12. 测试和验收

至少覆盖：

- 登录成功、登录失败。
- 日复盘和月复盘字段映射。
- 两个策略分别生成总结卡和明细卡，四张卡片互不混合。
- 证据不完整或没有当前版本时跳过。
- 同一 `case_id:version_id:card-v2:kind` 不重复发送，单张失败只重试该卡。
- 日复盘全部总结列表、全部逐笔评价和周期缠论判断进入卡片。
- 月复盘全部每日评价进入明细卡，冲突组和记忆候选仅显示数量。
- 新版本可以再次发送并标记修订版。
- 超长内容、空列表、特殊字符和未知枚举。
- Webhook、密码和 Token 不进入日志。
- Lark 200 成功、200 业务失败、429、5xx、超时和非法 JSON。
- 状态文件原子写入和损坏时安全停止。
- `--dry-run` 不发送、不写状态。

验收标准：

- 每张卡片只属于一个策略和一个复盘周期。
- 卡片结论优先、结构清楚，日复盘和月复盘均可读。
- 不外发用户和交易账户敏感信息。
- 每天重复运行不会重复发送同一版本、同一卡片类型。
- 脚本失败不影响 AURUM 网站、复盘生成或数据库。
- Codex 定时任务每天 09:00 能正确运行并留下结果。

## 13. 回滚

回滚只需停用或删除 Codex 定时任务。

Python 脚本没有写 AURUM、没有改数据库、没有修改复盘结果。保留状态文件即可避免未来重新启用时重复发送；不要直接删除状态文件后重跑全部历史。

## 14. 第一轮复审

检查重点：需求覆盖、现有能力复用、最小改动、是否过度设计。

结论：原方案包含内部接口、systemd、SQLite 和服务端配置，超过“本地脚本定时运行”的实际需要。

本轮调整：

1. 删除新服务端接口。
2. 删除 systemd 和常驻进程。
3. 删除 SQLite，改为小型 JSON 去重文件。
4. 直接复用现有登录和复盘 GET API。
5. 将调度交给 Codex，每天 09:00 运行一次。

剩余风险：本地账号需要具备平台复盘读取权限；如果当前账号权限不合适，应创建或选择合适账号，但不扩大脚本为管理员写入工具。

## 15. 第二轮复审

检查重点：兼容性、数据、并发、幂等、异常恢复、时间、安全、测试和回滚。

结论：每天单次串行任务不存在多进程常驻需求；`case_id:version_id` 足以处理日常重复运行和复盘修订。回看最近 7 天可补偿电脑关机或任务错过。

本轮调整：

1. 不再只取“昨天”，避免终端业务日、生成延迟和错过运行导致漏发。
2. 增加首次运行最多 20 张限制，防止历史刷屏。
3. 状态文件改为临时文件后原子替换。
4. Lark 请求结果未知时不立即重发，避免重复消息。
5. 明确定时任务提示词不得包含任何凭据。

剩余风险：

- Codex 本地定时任务依赖本机运行环境可用；创建后必须通过一次手动触发验证。
- Webhook 请求成功但响应丢失时，自定义机器人没有业务幂等键，只能记录未知状态并人工核对。
- 当前 Webhook 已出现在聊天记录中，正式启用前不轮换仍有凭据风险。

方案经两轮调整后可以进入实施。
