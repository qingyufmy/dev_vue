# AI 分析师与账户级 AI 交易员编排方案

> 状态：方案已完成两轮复审；阶段 12A 核心合同、12B 分析调度/Worker、12C 账户级 Trader Worker 已完成实现与离线验证
>
> 建立日期：2026-09-03
>
> 适用范围：AI 交易实验室的自动分析、手动分析、策略订阅、账户级交易判断、持仓管理建议、确定性风控、统一执行状态机和前端状态展示

## 1. 结论

新版不采用三个大模型串行审批，也不依赖模型供应商的连续聊天会话。目标主链路为：

```text
账户级策略订阅到期
  → 按系统用户、策略版本、标准品种和调度时间槽去重
  → AI 分析师生成一份与 MT 交易账户无关的市场分析
  → 仅向“存在市场机会”或“已有持仓/挂单”的账户订阅扇出
  → 每个交易账户独立刷新账户、持仓、挂单、报价和合约规格
  → AI 交易员为该账户生成结构化动作建议
  → 服务端确定性风控与执行前校验
  → 统一 execution intent
  → Bridge V4
  → MT4/MT5 结果与精确对账
```

核心规则：

1. 策略暂分为 `analysis`（分析策略）和 `trader`（交易执行策略）两类。AI 分析师按分析策略订阅统一调度；分析记录归属系统账号，不归属某个 MT4/MT5 账号。
2. AI 交易员不建立独立周期调度器；新的有效分析完成后，仅对存在市场机会或已有持仓/挂单的账户级订阅创建独立任务。无机会且无敞口的账户不消耗第二次模型调用。
3. 同一系统用户、同一分析策略版本、同一标准品种、同一调度时间槽只产生一份分析；同一分析可以供该用户的多个订阅账户分别评估。
4. AI 交易员是账户级动作规划者，不拥有 Bridge 调用权和机械执行权。
5. 风控继续使用服务端确定性配置和计算，不增加第三次常规大模型调用。用户可在自身权限与合同有效范围内修改账户级风险参数；账户归属、幂等、终端身份、状态版本、结果对账等执行安全约束不可关闭。
6. 两次模型调用均为可独立复现的无状态请求。服务端显式组装、版本化并冻结输入上下文，不依赖供应商 `conversation_id`、历史消息或隐式记忆。
7. 任一阶段发现行情、账户、持仓、挂单、订阅或策略版本已变化，旧结果只能留作历史，不得继续执行。
8. 领域命名必须区分：分析师产物是 `market_analysis`，交易员产物是 `trade_decision`，通过风控并进入执行链的才是 `execution_intent`；界面可以使用“最新 AI 分析”等自然语言，但数据库、合同和审计不得继续用一个 `signal` 混指三个阶段。

## 2. 目标与非目标

### 2.1 目标

- 分离“市场是否存在机会”和“某个账户现在应该做什么”。
- 同一份市场分析复用于同一用户的多个账户，避免重复分析和模型成本线性增长。
- 保证每个账户依据自己的资金、持仓、挂单、报价、合约规格和风险配置形成独立决定。
- 通过显式输入、稳定合同、版本和哈希实现重试、审计和复现。
- 避免模型耗时导致旧入场点、旧持仓或旧订阅继续进入交易链路。
- 保持模块化单体、独立 Worker、统一 outbox 和统一 execution 状态机，不增加微服务或新的通用编排框架。

### 2.2 当前实施边界

- 阶段 12C 已实现账户级冻结输入、模型网关端口、同账户租约、任务/attempt、失败重试、结构化决定和迟到结果拦截；真实 provider 适配、风险策略投影写入与执行接线仍未实现。
- 已新增显式迁移文件，但不在研发阶段执行迁移、旧库回填或数据清理。
- 不启动 Bridge，不执行 MT4/MT5 下单、挂单、改单、撤单或平仓。
- 不以提示词代替权限、风控、合约校验、幂等、deadline 和对账。
- 不把完整 K 线、全部宏观历史或完整模型正文复制到每个队列任务中。

## 3. 功能职责

### 3.1 AI 分析师

AI 分析师只回答“市场现在处于什么状态、机会与风险在哪里”。

输入：

- 当前系统用户及其已发布策略版本；
- 标准品种、分析周期和冻结的行情快照；
- K 线、成交量、指标、市场结构和数据完整度；
- 已在宏观模块中形成并带版本的最新宏观研究快照；
- 分析师规则和稳定输出合同。

输出：

- 市场方向：偏多、偏空、中性或不确定；
- 入场机会：无机会、偏多机会或偏空机会；该字段只说明是否值得进入账户级评估，不代表最终下单；
- 市场环境：趋势、震荡、突破、事件风险等；
- 支持证据和反向证据；
- 关键价位、候选入场区域和失效条件；
- 置信度、适用周期和有效期；
- 数据缺口、冲突信息和需要观望的原因；
- 面向用户展示的完整结构化说明。

禁止：

- 读取或推断某个交易账户的余额、持仓或挂单；
- 决定最终手数、账户风险金额或直接发送订单；
- 因某个账户无法交易而改写市场结论；
- 通过连续聊天历史继承未显式提供的市场事实。

### 3.2 AI 交易员

AI 交易员只回答“这份仍然有效的市场分析，对于当前这个账户应该采取什么动作”。

输入：

- 分析师结构化结果及其版本、快照、价格基准和有效期；
- 当前账户余额、净值、可用保证金、杠杆和账户能力；
- 当前持仓、挂单、对应 revision 和完整 expected state；
- 该账户当前经纪商的最新 Bid、Ask、点差、合约规格和交易时段；
- 账户订阅的策略版本、交易员规则和订阅 revision；
- 服务端提供的只读风险摘要。最终风险决定仍由确定性风控产生。

输出：

- `hold`；
- 候选市价单或挂单；
- 修改持仓止盈止损；
- 平仓或部分平仓；
- 修改或撤销挂单；
- 数据不足、分析过期、账户状态冲突或不应操作的明确理由。

一个交易员结果可以包含零个或多个有界动作建议，但每个动作必须拥有独立动作 ID、明确前置状态和独立 execution intent；动作之间不形成跨订单数据库事务。

禁止：

- 直接访问 Bridge 或 MT；
- 覆盖分析师保存的原始市场结论；
- 在账户或行情 revision 已变化后继续使用旧参数；
- 自动追价、放宽止损或扩大用户风险配置；
- 因模型失败而复用上一轮交易结果。

### 3.3 确定性风控与 execution

AI 风控模型不进入首版主链路。服务端继续负责：

- 风险参数读取、计算、预留和拒绝原因；
- 账户归属、会员、订阅、接收时间、交易权限和观摩模式；
- Bridge route、终端实例、连接代次和账户身份；
- 最新报价、最大点差、最大允许偏移和市场状态；
- 仓位、保证金、累计风险、日损失和 kill switch；
- 幂等、expected state、revision、deadline 和结果对账。

风控通过只表示允许进入统一 execution 状态机，不表示 MT 已执行成功。

## 4. 两类策略与提示词结构

首版策略只分为两类，不建立第三类 AI 风控策略，也不把两类提示词塞入一个不可拆分的大文本。

### 4.1 分析策略 `analysis`

分析策略服务于 AI 分析师，定义：

- 适用品种、分析周期和自动分析频率；
- 行情结构、多周期、指标和宏观研究规则；
- 支持证据、反向证据、关键价位、失效条件和置信度要求；
- 分析师稳定输出 Schema；
- 用户可见的分析说明要求。

分析策略可以单独订阅和运行。它只产生 `market_analysis`，不会因为用户没有交易账户、Bridge 离线或没有启用自动交易而停止生成分析。

### 4.2 交易执行策略 `trader`

交易执行策略服务于 AI 交易员，定义：

- 如何消费统一的 `market_analysis`；
- 如何结合目标账户、持仓、挂单、报价和合约规格；
- 开仓、挂单、观望、修改保护、平仓、部分平仓、改单和撤单规则；
- 动作优先级、前置条件和交易员稳定输出 Schema；
- 用户可见的账户决策说明要求。

“交易执行策略”是产品名称，不表示 AI 拥有终端执行权。它只产生 `trade_decision`；服务端确定性风控通过后，才可以建立 `execution_intent`。

### 4.3 两类策略的组合

所有分析策略必须输出同一版本化基础合同，所有交易执行策略必须消费该合同，不允许通过复制另一份提示词或读取聊天历史形成私有接口。

账户级自动执行订阅明确选择：

```text
交易账户
+ 标准品种
+ 分析策略版本
+ 交易执行策略版本
+ 接收时段/时区
+ 自动分析开关
+ 自动交易开关
+ 账户风险配置
```

同一分析策略可以与不同交易执行策略组合，同一交易执行策略也可以消费不同分析策略，只要双方通过统一合同版本校验。这样可以分别升级分析方法和账户动作规则，不必复制整套策略。

固定职责、禁止事项和输出 Schema 由平台系统提示词维护；用户策略只能填写被允许的策略内容，不能覆盖系统合同。风险配置继续作为服务端结构化字段，不编译成第三份自由提示词。

## 5. 两次模型请求的上下文

### 5.1 不使用供应商连续会话

生产自动交易禁止依赖：

- `conversation_id`；
- 供应商保存的历史消息；
- 上一次账户或品种的隐式上下文；
- 不可导出、不可哈希或不可复现的模型记忆。

原因是连续会话会造成跨账户串号、输入不可证明、重试结果污染、上下文无限增长和模型切换困难。

### 5.2 使用服务端显式上下文包

每个模型任务保存：

- `task_id`、`attempt_id` 和 `correlation_id`；
- 模型供应商、模型、用途路由和参数版本；
- 系统提示词版本、策略版本和输出 Schema 版本；
- 冻结输入引用、各资源 revision 和输入哈希；
- 创建时间、deadline、开始时间、结束时间和结果状态；
- 结构化输出、校验结果和用户可见说明。

队列只携带 ID、版本、deadline 和 `payload_ref`，不直接携带完整提示词、K 线、模型密钥或大对象。Worker 从数据库读取已经授权并冻结的上下文包。

### 5.3 分析师向交易员传递什么

交易员不需要重复读取分析师的全部长篇正文。传递内容以稳定结构为主：

```json
{
  "analysis_id": "analysis_10021",
  "system_user_id": "user_18",
  "analysis_strategy_version_id": "analysis_strategy_version_12",
  "symbol": "XAUUSD",
  "market_bias": "bullish",
  "market_regime": "trend",
  "confidence": 76,
  "entry_zone": ["4628.00", "4632.00"],
  "invalidation": {
    "price": "4619.00",
    "conditions": []
  },
  "supporting_evidence": [],
  "counter_evidence": [],
  "market_price_at_analysis": "4630.18",
  "market_snapshot_revision": "market_9821",
  "macro_snapshot_revision": "macro_105",
  "analyzed_at_utc": "2026-09-03T08:02:20.000Z",
  "valid_until_utc": "2026-09-03T08:04:00.000Z"
}
```

完整正文继续保存并供 AI 分析师页面展示；交易员只接收决策所需的结构化结论、关键证据和必要的有界补充说明。这里的“完整推理结果”是可审计的结构化依据和模型说明，不依赖供应商隐藏思维过程。

## 6. 调度、扇出与去重

### 6.1 AI 分析师调度

自动分析任务的逻辑唯一键：

```text
system_user_id
+ analysis_strategy_version_id
+ normalized_symbol
+ schedule_slot_utc
```

自动分析默认每五分钟登记一次到期工作，但 scheduler 只写 outbox/队列，不运行模型正文。手动分析和系统事件触发不能复用自动调度键：手动分析使用 `system_user_id + analysis_strategy_version_id + normalized_symbol + client_request_id`，事件触发使用稳定 `source_event_id`，避免不同触发来源在同一时间槽互相吞并。

分析归属始终是系统账号。行情来源账户、终端或数据供应商只作为数据来源证据保存，不改变分析归属。

### 6.2 AI 交易员触发

分析成功且结果仍有效后，服务端先读取每个订阅账户在该品种上的持仓/挂单投影，再冻结符合条件的目标：

| 市场机会 | 已有持仓或挂单 | 是否创建任务 | `task_mode` |
| --- | --- | --- | --- |
| 无 | 无 | 否 | — |
| 有 | 无 | 是 | `entry` |
| 无 | 有 | 是 | `manage` |
| 有 | 有 | 是 | `both` |

每个入选目标创建独立交易员任务：

```text
analysis_id
+ account_strategy_subscription_id
+ trading_account_id
+ subscription_revision
+ trader_strategy_version_id
+ trader_action_version
```

这避免了交易员在长期没有新入场机会时完全失去持仓管理能力，同时不会让空仓、无机会账户每五分钟重复调用第二个模型。AI 交易员没有独立的五分钟周期调度。不同账户可以受控并行，同一账户使用：

```text
trading_account_id + terminal_instance_id + ownership_epoch
```

进行串行和 fencing，避免开仓、改单、撤单和平仓竞争。

### 6.3 最新结果优先

同一账户、策略和品种出现更新分析时：

- 新自动时间槽只替代旧自动任务，不静默取消用户显式发起的手动分析；
- 尚未开始的旧交易员任务标记 `expired`；
- 正在调用模型的旧任务可以保存结果，但进入执行前必须再次检查最新分析 ID；
- 新分析已经生效时，旧结果只能作为历史，不创建 execution intent；
- 不允许五分钟调度持续堆积旧模型任务；
- 迟到结果不得覆盖用户切换账户、策略或订阅后的页面状态。

### 6.4 多账户

同一系统用户的多个交易账户可以订阅不同策略。同一策略和品种的分析可以复用，但每个账户必须独立：

- 获取最新账户和终端事实；
- 运行交易员模型；
- 进行风控与风险预留；
- 创建 operation 和 execution intent；
- 接收 Bridge/MT 结果；
- 成功、失败或进入 `uncertain`。

批量扇出不是跨账户事务，某个账户失败不得回滚或阻塞其它账户已经完成的结果。

### 6.5 同一账户的多策略冲突

第一版允许一个账户或系统用户订阅多个分析策略，但同一交易账户与标准品种只允许一个活动的自动执行组合，也就是一组“分析策略版本 + 交易执行策略版本”。原因是两个组合可能同时提出相反方向、重复仓位或互相平仓，而当前没有一个经过验证的账户级组合策略仲裁器。

如果未来确需同账户同品种多策略自动执行，必须先增加确定性仲裁设计，至少明确策略优先级、组合风险预算、净敞口、动作冲突、持仓归因和平仓权限。不能临时再增加一个大模型充当仲裁器。

## 7. 行情来源与经纪商差异

分析师使用标准化品种和已选择的市场数据源形成市场结论。数据来源可以是用户的观摩源、授权交易终端或后续独立行情源，但必须保存来源、终端、broker server、时间校准状态和快照 revision。

分析师使用的 XAUUSD 与目标交易账户的经纪商报价、品种后缀、digits、tick size、stop level、交易时段和合约规模可能不同。因此：

1. 分析师输出的是标准价格区域和失效条件，不直接形成最终账户订单参数。
2. 交易员使用目标账户的最新 Bid/Ask 和合约规格重新映射、校验并计算候选动作。
3. 无法可靠映射品种或价格差超过策略允许范围时，返回明确拒绝，不猜测或静默替换品种。
4. 最终 execution 继续使用目标账户的精确定点价格、expected state 和 deadline。

首版不跨不同系统用户共享模型分析结果，因为用户的策略版本、模型配置、宏观输入和权限可能不同。以后只有在数据、策略、模型和合同完全相同且经过隐私评审后，才评估跨用户缓存。

## 8. 时效与延迟控制

模型调用可能占据整条链路的大部分时间，因此分析结果不是执行许可，而是一份有条件、有限期的市场判断。

每个阶段必须检查：

- `valid_until_utc`；
- 当前价格是否仍在候选入场区域；
- 相对分析价格的最大偏移；
- 当前点差和市场交易状态；
- 行情、账户、持仓、挂单、订阅和策略 revision；
- 是否已经存在更新分析或更新交易员决定。

检查点：

1. 分析师输出校验时；
2. 创建账户级交易员任务前；
3. 交易员读取账户上下文后；
4. 确定性风控前；
5. 创建 Bridge 命令前。

超过有效期、行情偏移过大或状态版本变化时，结果进入 `expired` 或 `rejected`，原因使用稳定错误码，例如：

- `analysis_expired`；
- `newer_analysis_available`；
- `market_moved_outside_entry_zone`；
- `spread_above_limit`；
- `account_snapshot_stale`；
- `position_revision_conflict`；
- `subscription_revision_conflict`。

系统不得自动追价。只有策略明确允许相应挂单类型、价格仍满足逻辑且重新通过风控时，才可以生成挂单建议；否则等待下一轮分析。

模型时限、最大总链路时长和价格偏移不能在设计阶段拍脑袋写死。实现后必须以不同模型、波动环境和账户规模测量 p50、p95、p99，再为策略类型配置时效预算。M1 或 Tick 级超短线策略不应依赖两次串行大模型完成实时入场。

## 9. 持仓与挂单管理触发

每次新分析完成后，服务端对该品种已有持仓或挂单的账户创建 `manage`/`both` 任务，因此即使分析师判定没有新入场机会，交易员仍可提出保护修改、平仓、部分平仓、改单或撤单建议。没有持仓、没有挂单且没有新机会时不创建自动交易员任务。

终端 Tick、盈亏或普通持仓 revision 变化本身不直接触发新的大模型请求，避免模型按秒调用。它们用于：

- 更新前端；
- 更新服务器账户投影；
- 触发确定性保护和风险监控；
- 使尚未执行的旧交易员结果失效。

需要临时重新判断时，用户可以显式请求“重新评估当前账户”。如果最近分析已经过期，系统先创建新分析任务，不能直接用旧分析重新下单。

## 10. 自动、手动与观摩模式

### 10.1 自动分析

自动订阅完成分析后，按“有机会或有敞口”的条件触发账户级 AI 交易员。是否最终执行仍由账户的交易发送开关、接收时间、风控和 Bridge 状态决定。

### 10.2 手动分析

手动分析默认只生成分析结果，不自动触发交易员或交易。页面提供独立、明确的“提交给当前账户评估”动作；该动作再次确认账户、订阅、分析有效期和交易权限。

### 10.3 Bridge 离线

Bridge 离线时仍可完成市场分析。如果没有新鲜且完整的账户、持仓和挂单事实，AI 交易员不得生成可执行动作，结果明确为 `account_data_unavailable` 或 `bridge_unavailable`。

### 10.4 观摩模式

观摩模式可以运行分析并展示模拟的账户评估，但不得创建可发送的 execution intent。模拟结果必须明确标记，不得与真实执行结果混合。

## 11. 失败、重试与幂等

| 故障 | 处理 |
| --- | --- |
| 分析师合同校验失败 | 允许同一 attempt 规则下的有界修复；最终失败则不触发交易员 |
| 分析师超时 | 保存失败或超时，不复用上一轮信号 |
| 账户上下文不完整 | 交易员任务拒绝或等待有界刷新，不生成执行意图 |
| 交易员合同校验失败 | 有界修复；最终失败不执行 |
| 模型供应商重试 | 复用冻结输入和同一任务身份，记录新 attempt，不产生第二个业务动作 |
| 订阅或账户切换 | 旧 revision 任务失效，不能写回新账户上下文 |
| 风控拒绝 | 保存独立风险原因，不改写分析师或交易员原始结果 |
| Bridge 可能已收到命令 | 进入 `uncertain` 精确对账，禁止普通重发 |

模型调用必须位于数据库事务外。事务只负责冻结输入引用、状态、outbox、结果和后续任务登记。

## 12. 宏观研究边界

宏观数据通常不是五分钟变化一次。宏观模块独立采集、核验并形成带来源、观察时间、有效期和 revision 的研究快照；分析师只读取最新有效快照。

禁止在每次自动分析的关键路径中临时抓取完整宏观数据或运行长时间宏观研究。重大数据公布、风险等级变化或新宏观快照可以登记一次新的分析触发，但仍需去重和时效校验。

## 13. API、WebSocket 与前端展示

HTTP 负责：

- 分析历史和完整详情；
- 账户级交易员决定和动作详情；
- 手动分析、重新评估和交易命令受理；
- 风控结果、operation 和执行链路恢复。

WebSocket 只推送小型增量：

- 分析任务排队、运行、完成或失败；
- 新分析摘要；
- 账户级交易员任务状态；
- 风控拒绝摘要；
- operation、持仓、挂单和交易结果变化。

完整提示词、完整模型正文、K 线历史和账户历史不进入 WebSocket。

前端按照同一关联链展示：

```text
市场分析
  → 账户交易判断
  → 确定性风控
  → 执行意图
  → Bridge 命令
  → MT 结果/对账
```

每个阶段分别显示时间、模型或规则版本、状态和原因，不能把“分析成功”“风控通过”“Bridge accepted”显示成“交易成功”。

## 14. 可观测性与容量

至少记录以下指标：

- 分析师与交易员各自的排队、首字节、模型、校验和总耗时；
- p50、p95、p99 延迟和超时率；
- 输入大小、输出大小、用量和缓存命中；
- 每轮分析扇出的账户数；
- 被合并、取消、过期和因更新版本失效的任务数；
- `analysis_expired`、市场偏移、点差、账户数据不完整等拒绝原因；
- 从调度时间到 execution intent、Bridge accepted 和 MT 确认的端到端时长；
- 同一账户队列长度和最老任务年龄。

账户扇出必须有用户、模型供应商和 Worker 级有界并发。跨账户允许并行，同账户交易状态变更仍然串行。

## 15. 实施顺序与验收门

本方案纳入阶段 12，但必须在阶段 12 开始前重新向用户介绍并取得确认。

1. 冻结分析策略、交易执行策略、分析师输出和交易员输入/输出合同。
2. 建立任务、attempt、冻结输入引用、结果和关联 ID 的持久模型及迁移；迁移需单独授权。
3. 实现分析师调度去重、outbox 和 analysis Worker。（阶段 12B 已完成离线实现）
4. 实现账户订阅目标冻结、条件扇出和 analysis latest-wins。（阶段 12B 已完成离线实现）
5. 实现 Trader Worker、同账户租约和结构化结果校验，不接 Bridge。（阶段 12C 已完成离线实现）
6. 接入确定性风控与统一 execution 状态机。
7. 接入 HTTP、WebSocket 和前端链路展示。
8. 完成模型延迟、任务积压、账户切换、行情突变、断线、重复投递和多账户容量测试。
9. 通过只读和模拟验证后，再单独申请真实 MT 交易验收授权。

首版验收必须证明：

- 同一用户相同策略/品种/时间槽只调用一次分析师；
- 同一分析按有效订阅为不同账户产生不同交易员上下文和决定；
- 旧分析、旧订阅、旧账户 revision 和迟到模型结果均不能执行；
- 同一账户没有并发交易状态写入；
- 模型失败、超时和合同错误不会复用旧动作；
- 风控拒绝不改写 AI 原始结果；
- Bridge 离线和观摩模式不产生可发送交易命令；
- 所有阶段可通过关联 ID、版本、时间和输入哈希复现。

回滚时可以停止新的 analysis/trader Worker 和任务登记，不删除已有结果、operation、迁移或审计记录；已经进入 execution/Bridge 的命令继续按统一状态机对账，不能通过回滚重复下发。

## 16. 第一轮复审：职责、功能覆盖与最小设计

复审重点：需求覆盖、角色边界、现有能力复用、最少代码和是否设计过度。

发现与调整：

- 原候选方案将 AI 风控师作为第三个串行模型，延迟、费用和不确定性没有对应收益；调整为分析师、交易员两次模型调用，最终使用已有确定性风险域。
- 原表述“分析完成触发交易员”没有说明多账户，会使同一份市场判断错误地复用同一个账户决定；调整为市场分析可复用、交易员任务必须按账户扇出。
- 如果分析师和交易员都独立周期调度，会重复处理旧分析并使时间点错位；调整为分析师拥有周期，交易员只响应新的有效分析事件。
- 用户维护三份完整提示词会产生重复和冲突；调整为分析策略和交易执行策略两类独立版本，通过统一分析合同组合，风控继续使用结构化参数。
- 原有 `signal` 容易同时表示行情分析、账户动作和执行结果；调整为 `market_analysis → trade_decision → execution_intent` 三段稳定领域身份，前端再按用户语言组合展示。
- 未引入工作流引擎、微服务、通用 Agent 框架或第三个模型仲裁器；复用现有 scheduler、outbox、隔离 Worker 和 execution 状态机。

第一轮结论：方案覆盖自动分析、手动分析、多账户、持仓/挂单建议、风控和执行链路，模块边界清晰，没有引入当前需求不需要的基础设施。

## 17. 第二轮复审：并发、时效、异常与连带风险

复审重点：数据与迁移、并发、幂等、异常恢复、时间、安全、测试、回滚和连带 Bug。

发现与调整：

- 两次模型串行仍可能让入场点过期；增加分析有效期、入场区域、最大偏移、多个 revision 检查点、latest-wins 和发送前最终校验。
- 分析数据源与交易账户可能来自不同经纪商；增加标准品种、来源证据和目标账户报价/合约重新映射，禁止直接复制分析价格下单。
- 同一账户同品种的多个自动执行策略可能互相开仓和平仓；首版收敛为一个活动自动执行策略，多个仅分析订阅仍可存在。未来扩展必须先设计确定性仲裁。
- 模型重试可能产生不同结果；任务保持稳定业务身份，每次调用保存独立 attempt，只有仍满足版本与时效条件的一个结果可以推进。
- 账户切换、策略修改和迟到结果可能串号；任务冻结 subscription revision、ownership epoch 和资源 revision，旧结果不能覆盖新上下文。
- 宏观研究放入五分钟关键路径会放大尾延迟；调整为独立形成版本化宏观快照，重大变化只登记新的分析触发。
- 回滚不能撤销已经可能到达 MT 的命令；明确 Worker 停止与 execution 对账分离，`uncertain` 继续保留。

第二轮结论：调整后的方案是阶段 12 AI 分析师、AI 交易员和相关合同实施的权威输入。阶段 12A 已完成静态合同与核心持久模型，阶段 12B 已完成分析调度、冻结上下文、模型任务/attempt、latest-wins 和条件账户扇出，阶段 12C 已完成账户级 Trader Worker、同账户租约、结构化决定和迟到结果拦截的离线实现；真实模型供应商、风险策略投影、Redis/MySQL 联调、Bridge 和 MT4/MT5 行为仍需在后续阶段验证。

## 18. 剩余风险与待确认项

以下内容不能仅靠文档证明：

1. 当前候选模型在不同输入规模下的 p95/p99 延迟和结构化输出稳定性。
2. 五分钟调度在大量账户扇出后的 Worker、供应商限流和数据库容量。
3. 不同经纪商 XAUUSD 报价和合约规格映射的真实差异。
4. 分析有效期、最大价格偏移和最大总链路时间应按策略类型如何配置。
5. 同一账户同品种首版只允许一组活动的“分析策略 + 交易执行策略”自动执行组合，是否作为最终产品规则。
6. 手动分析默认只分析、必须显式提交账户评估是否符合最终交互预期。

这些项目需要在对应后续子阶段开始前逐项确认；未确认时采用本方案的安全默认值，不扩大自动执行范围。
