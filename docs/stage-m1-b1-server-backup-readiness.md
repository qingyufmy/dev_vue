## 1. 结论和证据范围

服务器具备开展加密备份演练的基础工具和当前磁盘余量。**尚未备份、解密验证、建库或恢复；实际执行仍待用户对下列路径、库名和范围确认。**

## 4. 拟采用的加密和保管方式（未执行）

采用现有 GnuPG 对称加密，不自写加密协议。现场版本列出 AES256、SHA256，且具备 symmetric/decrypt、passphrase-fd、pinentry-mode、no-symkey-cache 等选项。

建议使用独立高熵随机口令；只通过文件描述符传给 GPG，不放入命令参数、日志或 Git。批处理口令输入使用 batch 与 loopback；不允许忽略完整性校验错误。[GnuPG 口令输入与完整性选项](https://www.gnupg.org/documentation/manuals/gnupg/GPG-Esoteric-Options.html)

- 先用无敏感小样本测试加密、解密、原字节 hash 和失败退出码，再处理源数据。
- 工具目录/私有 GPG 工作目录仅在新批准目录内建立，不复用用户默认 keyring，不改系统 GPG 配置。是否需要独立临时 agent 以小样本验证为准，不操作其它 agent。
- 导出 SQL 尽量经受控流压缩并加密，不在网站目录落明文；如果恢复审查需要明文临时文件，必须位于同一批准的 `0700` 私有备份目录内，文件 `0600`，不得公开或随日志输出。
- 加密包、原始 SQL、解密还原 SQL 分别做大小/hash 校验，并审查 SQL 的实际作用域；不能边解密边未经完整性验证就导入。
- 同机分目录保管只能隔离误发/一般文件读取，不防 root 被攻破或整机损坏。正式切流前仍需单独批准异机副本与口令保管，不能把本次本机演练当作公网容灾验收。
