## 1. 结论与目标

本次问题由两部分叠加：

1. 首页刷新和完整页面浏览确实会产生短时公网发送突发，主要来自中文 Web 字体、单体前端资源和浏览器行情 WebSocket 响应。
2. 宝塔实时流量把 `eth0`、`lo` 等全部网卡求和；Nginx、Node.js、MySQL、Redis 之间的回环通信会同时记为接收和发送。站点统计还会在 WebSocket 连接关闭时把整个连接生命周期累计发送字节集中记到 HTTP `101` 记录，因此曲线可能表现为虚高且上下行几乎相等。

本方案的目标不是单纯让图表变小，而是同时做到：

- 使用 `eth0` 作为公网带宽验收真值，明确分离 `lo` 内部流量和 WebSocket 关闭记账。
- 降低首次进入和刷新 AI 交易实验室时的真实静态资源传输量。
- 将周期性 K 线刷新从重复返回 200 根改为小窗口增量校准，同时保留断档后的全量恢复能力。
- 在不改变 Bridge、交易、风控、模型推理和行情时间语义的前提下，评估浏览器 WebSocket 压缩。
- 所有实现只进入 `dev_codex`；先本地验证，再部署到内网虚拟机验证。没有用户明确确认，不得合入 `main`，不得部署公网。

## 3. 不可变边界

### 3.1 本方案包含

- 仓库自有的网络采样和聚合工具。
- 浏览器 WebSocket 命令的无敏感内容字节统计。
- AI 前端字体引用精简。
- 首页 K 线周期刷新改为小窗口增量校准。
- 浏览器/管理员 WebSocket 压缩的功能开关和 VM A/B 验证。
- 字体样式的版本化检查；不在本任务顺带重构通用静态缓存代码。
- 仅在上述措施仍不达标时，评估前端单体资源压缩或拆分。

### 3.2 本方案不包含

- 不修改自动分析周期、模型提示词、模型请求体或模型输出。
- 不修改交易、风控、下单、持仓管理、复盘、策略和账户权限逻辑。
- 不修改数据库结构，不运行迁移，不写生产数据。
- 不修改 Bridge V3 协议、Bridge 客户端、MT4/MT5 Worker 或 EA。
- 不修改宝塔面板、宝塔监控插件、Nginx `site_total` 二进制等供应商文件。
- 不为降低曲线而绕过 Nginx、关闭审计日志或减少必要的行情完整性校验。
- 不在本方案执行阶段合并 `main`、部署 `/www1/wwwroot/aurum-ai`、重启公网服务或更改公网 Nginx。

## 4. 总体实施路径

采用五个可独立验收、可独立回滚的批次。每一批必须先在本地通过验收，再形成单一职责提交推送到 `dev_codex`；部署虚拟机后只验证该批效果。上一批未通过，不进入下一批。

```text
批次 A：建立可信观测
    ↓
批次 B：精简字体与缓存合同
    ↓
批次 C：K 线小窗口增量校准
    ↓
批次 D：浏览器 WebSocket 压缩 A/B
    ↓
批次 E：按剩余数据决定是否做前端资源构建/拆分
    ↓
虚拟机综合观察与人工验收
    ↓ 用户明确批准后才可另行规划公网发布
```

## 5. 批次 A：可信观测与回归基线

### 5.1 目标

先准确回答“哪一个浏览器动作发送了多少字节”，避免在缺少 action 级证据时盲目修改行情或业务接口。

### 5.2 拟修改文件

- 新增 `scripts/ops/sample-linux-network.mjs`
  - 从 `/proc/net/dev` 读取指定接口；
  - 默认接口为 `eth0,lo`，默认周期 1 秒；
  - 支持持续时间、输出 JSONL 和最终聚合；
  - 输出总字节、最大值、P50、P95、P99；
  - 不采集 IP、URL、用户、请求内容或凭据。
- 新增 `server/browser-ws-bandwidth-metrics.js`
  - 仅接受 action、请求/响应字节、状态、耗时等低基数字段；
  - 不保存 payload，不保存 token、账号、用户 ID、品种或交易内容；
  - 使用固定 action 白名单/`other`，避免日志基数失控；
  - 按 60 秒窗口聚合，输出次数、总字节、最大响应和 P95 耗时；
  - 每个 action 使用固定桶或有上限的样本，禁止为计算分位数无限保存请求记录；聚合定时器使用 `unref()`，不得阻止进程退出；
  - 仅在 `BROWSER_WS_BANDWIDTH_METRICS=1` 时启用，默认关闭。
- 修改 `server/bridge-ws.js`
  - 在浏览器命令入口计算请求的逻辑 JSON 字节；
  - 在统一 `reply` 发送前计算响应序列化字节；
  - `JSON.stringify` 只执行一次，统计与实际发送复用同一字符串；
  - 统计失败不得改变响应、关闭 socket 或影响命令结果。
- 修改 `server/.env.example`
  - 增加开关说明，明确只建议在开发/VM 观察期开启。
- 新增 `tests/ai/browser-ws-bandwidth-metrics.test.js`
  - 覆盖关闭开关、固定 action、超长/未知 action 归类、窗口聚合、序列化失败和敏感字段不进入输出。

### 5.3 受保护行为

- 浏览器命令协议、`command_id`、响应 JSON 结构和错误码不变。
- WebSocket 发送次数不增加。
- 指标模块异常时 fail-open 到原业务发送，但不得吞掉业务异常。
- 指标日志不得出现 payload、token、用户标识、账户、订单、策略正文或模型内容。

### 5.5 VM 验收

- 部署该批 `dev_codex` 精确提交，开启 `BROWSER_WS_BANDWIDTH_METRICS=1`。
- 连续观察至少 15 分钟，覆盖至少两轮自动分析。
- 执行一次冷缓存登录/首页、一次暖缓存刷新、一次完整页面浏览。
- 确认 action 聚合总响应字节与 OS/Nginx 方向一致，允许协议头和内部代理导致差异，但不得把 `101` 累计值当作同秒流量。
- 确认日志无敏感数据，服务、数据库、Redis、WebSocket 重连正常。

### 5.6 回滚条件

- 响应结构、发送次数或错误处理发生变化。
- 指标输出包含敏感字段。
- 指标模块导致事件循环延迟、内存持续增长或日志量失控。

回滚方式：关闭环境变量即可立即停止指标；代码回滚为单一批次提交，不涉及数据恢复。

## 7. 批次 C：K 线小窗口增量校准

### 7.1 目标

保留首次 200 根完整 K 线和所有数据完整性语义，把周期性重复的 200 根刷新改为最多 3 根尾部校准。

### 7.2 设计

- `loadKlineData()` 继续作为以下场景的权威全量加载：
  - 首次打开首页；
  - 切换品种或周期；
  - WebSocket/Bridge 重连后身份或来源发生变化；
  - 页面从隐藏状态恢复。首版保持当前 `visibilitychange` 的全量校准行为，不在同一批次继续优化短隐藏场景；
  - 增量响应时间戳、品种、来源身份或连续性校验失败；
  - 检测到跨越超过小窗口的 K 线缺口。
- 新增 `refreshKlineTail()`：
  - 默认请求最后 3 根，而不是 200 根；
  - 校验 OHLC、时间戳、时区和来源；
  - 按开盘时间与 `_klineCandles` 合并、去重并限制最多 200 根；
  - 已有 K 线使用 `series.update` 更新，新 K 线顺序追加；
  - 同步 volume 和最后价，但不改变用户当前缩放/滚动范围；
  - 发现不连续时只触发一次全量恢复，使用 flight guard 防止并发重复请求。
- 全量和增量请求共享同一请求代次：开始全量加载时使所有在途增量响应失效；品种、周期、账户上下文或观摩源变化时递增代次；旧响应不得覆盖新来源、新周期或较新的全量结果。
- 周期定时器只调用 `refreshKlineTail()`。不设置固定的周期性全量刷新；只有明确检测到隐藏期、断线、来源变化或数据不连续时才执行一次全量恢复。
- 现有每 5 秒 `count:1` volume 刷新先保留。只有 action 级指标证明它仍是主要流量后，才评估与 3 根尾部刷新合并，避免一次改动同时改变多个时间行为。

### 7.3 受保护行为

- 首次图表仍展示 200 根，切换周期/品种仍立即完整加载。
- 继续使用终端/经纪商时间，不得回退浏览器时间、VM 时间或固定时区。
- 休市时不得凭浏览器时间合成不存在的新 K 线。
- 观摩模式和本人行情的来源隔离不变。
- 数据缺口、重复时间戳、来源身份变化必须 fail closed 到全量重新加载，不得静默拼接。
- 不改变服务端 `platformRates` 的推理、复盘或其他调用者行为；优化只针对首页浏览器刷新策略。

### 7.4 拟修改文件

- `public/ai/app.js`
- 新增或扩展 `tests/ai/frontend-demand-loading.test.js`
- 新增 `tests/ai/frontend-kline-tail-refresh.test.js`（如现有测试结构不适合在原文件覆盖）

### 7.5 必测场景

1. 首次加载返回 200 根。
2. 同一根 K 线价格/成交量变化。
3. 新增一根 K 线。
4. 返回重复时间戳。
5. 返回倒序数据。
6. 小窗口内缺一根。
7. 页面隐藏后恢复。
8. 切换周期/品种时旧响应晚到。
9. 观摩源切换或账户接管。
10. 休市且最后报价陈旧。
11. WebSocket 重连。
12. 增量请求失败后下一轮恢复，且不存在请求风暴。

### 7.6 VM 量化门槛

- 15 分钟连续可见且连接稳定的观察期内，每个品种/周期只允许一次首次 200 根请求；常规定时请求返回不超过 3 根。只有故障注入或明确连续性失败才允许额外全量恢复。
- `rates` action 的总响应字节相对批次 A 同场景基线下降至少 60%。
- 浏览器 WS 总响应字节相对批次 A 同场景下降至少 40%。
- K 线最后价、OHLC、成交量、周期切换、缩放范围和来源标签与基线一致。
- 自动分析的模型行情窗口、K 线数量和调度周期没有变化。

### 7.7 回滚条件

- 图表出现断档、重复、乱序、错误时区或休市合成 K 线。
- 来源切换后残留旧来源数据。
- 网络恢复时出现连续全量请求或请求风暴。
- 自动分析或非首页调用的 `platformRates` 行为发生变化。

回滚方式：定时器恢复调用原 `loadKlineData()`；服务端协议和数据库均未改变。

## 8. 批次 D：浏览器 WebSocket 压缩 A/B

### 8.1 目标

在真实 VM CPU 余量允许时，压缩大于阈值的浏览器/管理员 JSON 响应，进一步降低公网发送量。

### 8.2 设计

- 仅修改 `/aurum-api/bridge/ws?type=browser|admin` 使用的 `WebSocketServer`。
- Bridge V3 使用独立 gateway，不进入本次压缩范围。
- 新增环境开关 `BROWSER_WS_PERMESSAGE_DEFLATE=0|1`，默认关闭。
- 建议初始参数：
  - `threshold: 1024`；
  - `serverNoContextTakeover: true`；
  - `clientNoContextTakeover: true`；
  - 使用明确且有界的 `concurrencyLimit`，避免瞬时 CPU 和内存放大。
- 不对心跳、小通知和小错误响应强制压缩。
- 认证仍通过现有握手/cookie 完成，不把 token 放入消息或指标；禁止为了提高压缩率开启跨消息上下文复用。

### 8.3 拟修改文件

- `server/bridge-ws.js`
- `server/.env.example`
- 新增/扩展 `tests/ai/browser-ws-compression.test.js`

### 8.4 VM A/B 方法

在相同提交、相同账号和相同操作脚本下依次执行：

1. 开关关闭，观察 15 分钟并完成标准浏览动作。
2. 在明确维护窗口内使用 VM 既有 BaoTa Node 项目/受控部署流程重启服务，开关开启。
3. 再观察 15 分钟并完成相同动作。
4. 比较 `eth0` 总发送、1 秒 P95/P99/峰值、WS action 字节、CPU、内存和事件循环延迟。

两轮必须使用同一提交；每轮开始前清空本任务的内存聚合窗口并记录起止时间，重启后预热 5 分钟再采样，避免把启动和冷数据库缓存误算为压缩差异。

### 8.5 启用门槛

- WS 实际公网发送字节相对关闭状态下降至少 25%。
- Node 平均 CPU 增量不超过 5 个百分点，P95 事件循环延迟不增加超过 10 ms。
- 内存无持续增长，15 分钟后回到稳定区间。
- WebSocket 建连、重连、管理员连接和普通用户连接无兼容问题。

未同时满足以上条件则保持关闭，不影响批次 B/C 的上线资格。

### 8.6 回滚条件

- CPU 尖峰、内存增长、事件循环延迟或 WebSocket 断连增加。
- 任一受支持浏览器无法协商或响应解析异常。
- 管理员和普通用户连接行为不一致。

回滚方式：环境变量设为 `0` 并按 VM 明确重启流程恢复；代码无需回滚即可停用。

## 9. 批次 E：条件性前端资源构建/拆分

### 9.1 进入条件

批次 B/C/D 完成后，只有仍满足以下任一条件才进入本批：

- 冷缓存首页 HTTP transferred bytes 仍超过 1 MB；
- 暖缓存首页主线程解析/执行时间明显影响可用性；
- `app.js` 仍占冷启动传输或解析成本的 30% 以上；
- 用户明确批准进行较大前端结构调整。

### 9.2 候选方案顺序

1. 先做无顶层名称混淆的安全压缩，保留内联事件处理器依赖的全局函数。
2. 将只在特定页面使用的大模块改为按需动态加载。
3. 最后才评估引入完整前端构建系统和内容哈希文件名。

不得直接对当前 `app.js` 使用会包裹 IIFE 或修改顶层函数名的默认压缩配置；当前 HTML 和脚本可能依赖全局函数，必须先通过静态引用扫描和真实浏览器全页面验收。

### 9.3 验收与回滚

- 所有导航、按钮、弹窗、表单和图表操作必须通过真实浏览器检查。
- 资源 sourcemap 不部署公网，构建必须可复现。
- 原未构建资源保留到 VM 验收完成；失败时恢复原 script 引用即可。

本批不是前四批上线的阻塞项。

## 14. 剩余风险

- 宝塔总流量图仍会统计回环网卡；即使真实公网带宽下降，图上仍可能出现对称尖峰。该图只能作线索，不能作验收真值。
- HTTP 101 仍会在 WebSocket 关闭时记录生命周期累计字节；不修改供应商统计意味着站点图可能仍在断开时出现尖峰。
- 系统字体在 Windows、macOS、Linux 的字形和字宽存在差异，必须以多平台截图和布局检查控制风险。
- K 线增量刷新最主要风险是隐藏期、断线和来源切换后的数据连续性，必须保留单次全量恢复和并发 flight guard。
- WebSocket 压缩以 CPU、内存和事件循环延迟换带宽，VM A/B 不达标时应保持关闭。
- 当前前端没有独立构建系统；大规模拆包会扩大回归面，因此被明确放在条件性最后批次。
- 当前本地工作区已有用户未跟踪文档和测试，后续提交必须显式只暂存本任务文件。

## 15. 两轮方案复审

### 第一轮：需求覆盖与最小改动复审

状态：已完成并调整。

检查内容与结论：

- 需求边界：方案已明确只在 `dev_codex` 实现、只部署内网 VM 验证，公网必须等待独立人工批准；没有把方案请求扩大为当前实施或部署授权。
- 业务边界：模型、交易、风控、Bridge V3、数据库和公网均排除在修改范围之外，满足最小业务影响要求。
- 现有能力复用：复用现有 `count:1` 尾部读取、tick 增量更新、`platformRates(count)`、HTTP gzip 和 7 天缓存，不新增行情协议或数据库表。
- 最小改动：初稿计划顺带去重 `server/index.js` 两处缓存逻辑，对当前降峰不是必要条件，已移除；缓存仍保持 7 天，仅修复 `fonts.css` 版本引用。
- 避免设计过度：初稿计划每 10 分钟再拉一次 200 根做一致性校准，会持续制造可避免流量，已改为只有隐藏期、断线、来源变化或连续性失败时才单次全量恢复。
- 指标语义：Node action 指标只能证明压缩前的逻辑 JSON 大小，不能代表线上真实字节，已在指标表和实现描述中明确；压缩效果只由 `eth0` A/B 判定。
- 运行方式：纠正了初稿中 VM 使用 PowerShell 重启的表述；本地使用可见 PowerShell，Linux VM 使用既有 BaoTa Node/受控部署流程。

第一轮调整后，核心实施仅剩“观测、字体、K 线尾部刷新、可选压缩”四个单一职责批次；前端构建/拆分保留为有数据才进入的条件项。

### 第二轮：兼容性、恢复与连带风险复审

状态：已完成并调整，最终方案可实施。

检查内容与结论：

- 兼容性：HTTP/API/WS 命令结构均不改变；压缩只作用于独立的 browser/admin WebSocket，Bridge V3 gateway 不在范围内。压缩默认关闭，因此批次 D 不达标不会阻塞字体和 K 线优化。
- 数据与迁移：所有变化均为静态前端、内存指标和传输配置，不新增表、不修改迁移、不写业务数据。部署工具若发现迁移差异必须停止。
- 并发与幂等：增量和全量 K 线原草案只写了 flight guard，仍可能发生“旧增量晚到覆盖新全量/新来源”。最终方案增加统一请求代次，账户、来源、品种和周期变化均使旧响应失效；连续性失败最多触发一个全量恢复。
- 异常恢复：首版继续保留现有“页面从隐藏恢复就全量加载”的保守行为，不把短隐藏优化与周期刷新优化合并。断线、乱序、重复、缺口、来源变化均 fail closed 到单次全量恢复。
- 时间语义：所有 K 线合并仍使用终端/经纪商时间与服务端返回的来源元数据；明确禁止浏览器时间、VM 时间和固定时区生成 K 线，休市行为不变。
- 安全：指标不记录 payload、身份或业务标签，并新增固定 action、样本上限和 `unref()` 要求；压缩关闭跨消息上下文，避免为了压缩率扩大秘密相关侧信道和内存风险。
- 性能：WebSocket 逻辑 JSON 字节与真实公网字节分开；压缩 A/B 增加同一提交、5 分钟预热、窗口清零和 CPU/事件循环门槛，减少错误归因。
- 测试：补充了乱序、旧响应、隐藏恢复、来源切换、休市、断线恢复、请求风暴和敏感日志场景；最终仍以完整 `npm test`、真实浏览器和 VM 15 分钟/24 小时观察共同验收。
- 回滚：A/D 有环境开关，B 保留未删除的字体物理文件，C 保留全量加载函数；每批单独提交，可分别回退，不需要数据库恢复。
- 连带 Bug：确认不在字体批次重构通用静态服务、不把前端构建系统作为必做项、不修改自动分析和服务端 `platformRates` 其他调用者，控制了回归面。

第二轮未发现仍需扩大范围的阻塞问题。剩余风险已在第 14 节列明；方案只有在用户另行授权后才进入批次 A 实施。
