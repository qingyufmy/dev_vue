# M1 中断恢复与 011 显式纠正

日期：2026-09-05。仅处理已授权的 `dev_vue_m1_a`、`dev_vue_m1_b` 隔离演练库，不连接源库、运行服务或终端。

## 实施步骤

1. 冻结 bootstrap 与 001～017 原文。011 第 3 条另存纠正 SQL，唯一语义差异是新建两条外键采用不同约束名，仍在单条原子 ALTER 内保留全部原约束。
2. 纠正清单绑定原文件 SHA-256、原语句 SHA-256、纠正文件 SHA-256；执行器记录纠正的授权与完成事件，不把替代 SQL 伪装成原文执行。
3. 恢复采用本次现场专用清单，绑定服务器 UUID、数据库、完整结构指纹、完整迁移日志指纹、业务表行数指纹和失败 execution ID。任一变化均拒绝，无通用 force/resume 开关。
4. A 核对已经成功的第 3 张基础表后从第 4 条继续；B 原子 ALTER 失败、结构未变化，从纠正后的第 3 条继续。原始失败日志完整写入追加审计事件，再以新 execution ID 继续；不删除失败证据、不重放已确认 DDL。
5. 恢复只完成当前失败文件，后续文件另用普通迁移命令推进。全部完成后比较两个库的结构指纹、原文件 checksum、风控种子，重复运行验证不重放。

## 第一轮复审：范围与复杂度

- 不引入通用 DDL 解析/自动回滚框架。只允许两份已核对现场恢复凭据与一份显式外键纠正。
- 原迁移保持原顺序与校验和，新增纠正文件和审计表不承载业务数据。
- 空库安装不等于 165 张旧表的数据迁移；本轮不回填真实用户，也不开放正式切换。

## 第二轮复审：并发、异常与证据

- 预检、恢复日志和 DDL 全程持有同一数据库迁移命名锁；普通命令遇到 failed/running 仍拒绝。
- 日志与会话分离，保留 008 的 ROW_COUNT/LAST_INSERT_ID 语义；不关闭外键/CHECK，不跳过错误。
- DDL 与日志不能原子提交。恢复或纠正再次中断时立即停机，不自动重试；原现场清单因审计表/日志/结构变化不能再次使用。
- A 第 3 表与 B 中成功建立、后续未修改的同名模型表比对；B 原 ALTER 失败前后外键/列结构结合原 SQL 核对。结构与行数均严格绑定，不仅检查表名存在。
- 不删除两个测试库或临时目录。剩余风险：后续 SQL 可能还有真实 MySQL 兼容错误，必须逐项追加纠正，不能改旧文件。
- 独立代码复核后补强：B 恢复必须携带精确绑定的纠正项；授权事务内对全部迁移日志加锁复核 hash；恢复事件读取同样绑定原服务器和目标库。三项均补负例测试。
- 增加窄范围 `.gitattributes`，仅固定迁移 SQL 的既有 LF 换行，避免 Windows/Linux 检出造成原始字节 checksum 漂移；不改动任何既有 SQL 字节。

### 恢复入口

`scripts/migrate-v4-schema.mjs --recover=<已审查的恢复 ID>` 仅检查；写入还必须带 `--apply --confirm-target=<精确目标库>`。恢复 ID 只适用于上述已冻结现场，现在已消耗，不可作为下一次故障的通用续跑参数。发生新中断必须重新审查，不得删除审计表或重置日志来重复使用。
