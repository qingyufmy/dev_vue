# AURUM 管理通知中心与 AI 实验室提醒设计方案

> 状态：正式方案，本地实现与自动化回归已完成，待受控集成验收与发布授权
> 适用范围：管理后台、用户站内信、AI 交易实验室、账户中心、邮件投递
> 明确不包含：短信、自定义营销邮件、定时发送、自动化营销编排
> 编写日期：2026-08-10

## 1. 目标与结论

本方案为管理员提供一个统一的通知发送与投递审计能力，第一期支持：

- 向指定单个用户发送；
- 按会员类型向用户群发送；
- 向全部有效普通用户发送；
- 发送站内信；
- 可选同步发送邮件；
- 区分普通通知和重要通知；
- 在 AI 交易实验室中提供明显但不阻塞交易工作的提醒；
- 分渠道记录发送、失败、跳过、阅读和确认结果。

核心设计结论：

1. 管理后台新增一级视图“通知中心”，放在“用户与会员”之后、“商业运营”之前。
2. “商业运营 → 到期通知”继续只负责会员到期提醒，不承载通用通知。
3. 用户详情增加“发送通知”快捷操作，但不在用户弹窗中再嵌套编辑弹窗；点击后进入通知中心并预填该用户。
4. AI 交易实验室的“账户”按钮增加未读数字角标；普通通知只使用角标，重要且未确认的通知额外显示靠近账户入口的紧凑悬浮条幅。
5. 重要通知必须由用户点击“我知道了”完成确认，但任何通知都不得用阻塞模态窗口遮挡行情、风控或交易操作。
6. 邮件与站内信是相互独立的投递渠道；邮件失败不得回滚或隐藏已经生成的站内信。
7. 短信第一期完全不进入界面、接口和队列，避免造成“可发送但内容受模板限制”的错误预期。

## 2. 现状证据与复用边界

### 2.1 已有能力

- `server/db.js` 已有 `notifications` 表，字段包括用户、类型、标题、正文、链接、去重键、已读状态和创建时间。
- `server/routes/user.js` 已有用户通知查询和标为已读接口。
- `public/account/` 已有“消息通知”页面，可作为主站与 AI 实验室共用的通知详情容器。
- `public/src/main.js` 已有未读数量、通知列表和账户中心通知入口。
- `server/system-email.js` 和会员到期通知模块已有 SMTP 配置读取、超时控制和 Nodemailer 发送能力。
- `server/bridge-ws.js` 已维护按用户区分的 AI 浏览器 WebSocket，可扩展为用户通知唤醒通道。
- 管理后台已有管理员鉴权、统一导航、确认对话框、实时事件通道和管理审计基础。

### 2.2 不能直接复用的部分

- 现有 `notifications` 表没有通知优先级、要求确认、阅读时间、确认时间和活动归属，无法完整审计管理员群发。
- 现有用户通知接口只返回基础字段，不返回链接、优先级和确认状态，也没有游标分页。
- 现有 `membership_expiry_notifications` 带有会员方案、到期时间和提醒窗口约束，属于专用业务投递表，不能改造成通用通知队列。
- 现有邮件函数偏向系统告警或会员到期邮件，通用用户通知需要独立的安全模板、逐用户投递和渠道结果记录。
- AI 实验室当前只有“账户”按钮，没有通知未读状态，也没有处理账户中心通知更新消息。

## 3. 产品与设计原则

### 3.1 首要用户任务

管理员必须能够在发送前明确回答：

- 发给谁；
- 用户会看到什么；
- 通过哪些渠道发送；
- 预计覆盖多少人；
- 哪些人没有可用邮箱；
- 发送后各渠道成功、失败或跳过了多少。

用户必须能够迅速回答：

- 我有几条未读通知；
- 这条通知是否重要；
- 通知要求我做什么；
- 我是否已经阅读或确认。

### 3.2 视觉方向

- 沿用 AURUM 的产品型工作台设计，不创建独立营销视觉。
- 颜色策略为克制型：普通未读使用信息蓝或中性高亮；重要未确认使用警戒橙；协作金只用于当前入口和主要操作。
- 系统通知颜色不得借用交易上涨红、下跌绿，避免与行情方向混淆。
- 动效只在未读数量首次增加时做一次 150～200ms 的轻微状态变化，不循环闪烁。
- 所有状态必须同时有中文文本或可理解图标，不能只依赖颜色。

## 4. 管理后台信息架构

### 4.1 一级入口

在左侧“运营工作台”分组中按以下顺序排列：

1. 运营总览
2. 用户与会员
3. **通知中心**
4. 商业运营

理由：

- 通知既可能面向单个用户，也可能面向会员群体或全体用户，范围超出商业运营。
- 入口紧邻“用户与会员”，符合“选择受众 → 触达用户”的运营任务顺序。
- 独立入口可以容纳发送编辑、活动记录、渠道状态和失败重试，不会继续扩大会员到期页面。

### 4.2 用户详情快捷入口

在用户详情头部操作区增加“发送通知”。点击后：

1. 关闭用户详情；
2. 切换到“通知中心”；
3. 自动选择“指定用户”；
4. 预填用户 ID、昵称和联系方式摘要；
5. 将焦点放到通知标题字段。

不在用户详情弹窗上再叠加通知编辑弹窗，避免焦点管理、键盘关闭顺序和移动端空间问题。

### 4.3 通知中心页面结构

页面分为两个主视图：

- **发送通知**：编辑、预览、估算接收人和提交发送；
- **发送记录**：查看活动、渠道汇总、单个用户投递结果和失败重试。

桌面端“发送通知”采用主编辑区加右侧发送摘要：

- 左侧约三分之二：接收范围、标题、正文、通知级别、内部链接、渠道；
- 右侧约三分之一：接收人数、邮箱可达人数、不可达原因、用户预览和最终发送按钮；
- 不使用嵌套卡片网格，字段组以分隔线和留白组织。

窄屏下改为单列，发送摘要位于编辑区之后；最终发送按钮不得做遮挡内容的悬浮按钮。

## 5. 发送编辑器

### 5.1 接收范围

提供三个互斥选项：

1. 指定用户；
2. 按会员类型；
3. 全部用户。

规则：

- 指定用户：第一期只允许一个用户，通过可搜索选择器选择；
- 按会员类型：可勾选免费用户、有效 Plus、有效 Pro、已过期会员，至少选一项；
- 有效 Plus/Pro 沿用现有会员口径：对应方案且到期时间为空或不早于当前时间；已过期会员指 Plus/Pro 且到期时间早于当前时间；免费用户只指保存方案为 `free` 的用户，不把已过期会员静默并入免费用户；
- 全部用户：仅包含未匿名化、非管理员的普通用户；
- 管理员确认后固定筛选条件；后台先一次性物化接收人快照，快照完成后才开始任何渠道投递，之后会员变化不改变本次活动的接收人；
- 观摩源专用账号默认排除，防止把业务通知发给平台内部数据源账号；如后续确有需要，应增加独立且明确的内部账号范围。

### 5.2 内容字段

- 标题：必填，1～100 个字符；
- 正文：必填，1～1000 个字符，纯文本输入；
- 级别：普通、重要；
- 内部链接：可选，只允许平台内部相对路径；
- 站内信：默认开启且第一期不可关闭；
- 邮件：可选，默认关闭；
- 短信：不显示。

第一期不允许管理员输入 HTML。服务端把纯文本安全转义后生成邮件 HTML，降低脚本注入、危险链接和不同客户端渲染不一致风险。

### 5.3 内部链接白名单

服务端必须先使用 URL 解析器按站点基准地址解析，再按明确路由判断。允许范围为：

- 站点首页 `/`；
- 账户中心 `/account/` 及其受控查询参数；
- AI 实验室 `/ai/` 及其受控查询参数。

不能把“以 `/` 开头”作为白名单，因为这会同时放行 `/admin/` 等未授权内部页面。

拒绝：

- 完整外部 URL；
- `javascript:`、`data:` 等协议；
- 跨域地址；
- 管理后台地址；
- 包含凭据、令牌或敏感查询参数的链接；
- 路径规范化后落入 `/admin/`、API、静态文件或下载目录的链接；
- `//example.com` 形式的协议相对外部地址。

链接为空时，通知只展示内容，不显示“查看详情”操作。

### 5.4 预览与确认

编辑器内容变化后，以短防抖请求获取接收人估算：

- 预计接收人数；
- 站内信人数；
- 已验证邮箱人数；
- 邮箱未绑定或未验证人数；
- 前 5 位接收人摘要；
- 被排除的账号数量及原因。

预览是发送前估算，不是授权依据。创建活动时服务端必须重新计算并返回本次实际物化人数；如果人数相对管理员最后一次预览发生变化，创建接口返回“范围已变化”，要求重新确认，不得直接发送。

提交前显示最终确认：

- 单用户：显示用户名称和渠道；
- 会员群体：显示会员范围、接收人数和邮件可达人数；
- 全部用户：要求输入确认词“发送给全部用户”。

确认对话框只负责防止管理员误发，不承担内容编辑。

## 6. 用户端体验

### 6.1 AI 交易实验室普通通知

继续保留唯一的“账户”按钮，在按钮右上角增加未读数量角标：

- 1～99 显示准确数字；
- 100 条及以上显示 `99+`；
- 无未读时完全隐藏；
- `aria-label` 动态更新为“账户中心，N 条未读通知”；
- 未读数增加时只做一次轻微高亮，不持续闪烁。

点击规则保持可预测：

- 有未读通知时打开账户中心的“消息通知”页；
- 无未读通知时打开账户中心概览；
- 角标存在时按钮增加可见悬停提示“查看 N 条未读通知”，让入口目的与点击结果一致；
- 账户中心关闭后，按钮恢复焦点。

### 6.2 AI 交易实验室重要通知

当存在“重要且尚未确认”的通知时，在顶栏下方、靠近账户入口的位置显示一条紧凑悬浮通知条幅：

- 图标和“重要通知”文字；
- 最新一条通知标题；
- 简短正文，最多两行；
- “查看通知”按钮；
- 未确认数量，例如“另有 2 条”；
- 不提供临时关闭按钮，直到用户完成确认。

提示条只展示最新一条重要未确认通知，其余用数量说明并在账户中心完整列出。提示条使用 `role="status"` 和 `aria-live="polite"`，不能使用会反复打断屏幕阅读器的强制告警；同一条通知在当前页面会话中只播报一次。

条幅使用固定或绝对定位，不参与 `app-layout`、图表和交易工作区的布局计算，不推挤当前界面。桌面端为右上紧凑横条，窄屏压缩为单行/双行摘要；必须避开账户、退出、交易按钮、风控状态和移动端底部导航。它不能使用全屏弹窗、浏览器通知权限或循环声音。

点击“查看通知”打开账户中心通知页，并定位到对应通知。用户在通知详情中点击“我知道了”后：

- 设置阅读时间和确认时间；
- 更新未读数量；
- 更新 AI 顶部提示条；
- 通过父子页面 `postMessage` 同步账户按钮状态；
- 若还有其他重要未确认通知，展示下一条。

打开消息页、展开通知或点击内部链接只代表“已读”，不得自动完成“已确认”。只有用户主动点击“我知道了”才写入确认时间；确认操作必须幂等，多次点击返回同一结果。

### 6.3 账户中心通知列表

在现有通知列表基础上增加：

- 普通/重要标识；
- 未读、已读、待确认、已确认状态；
- 可选“查看详情”链接；
- 重要通知的“我知道了”按钮；
- 游标分页或“加载更多”；
- 空状态说明“账户、服务与平台的重要动态会显示在这里”。

“全部标为已读”只改变阅读状态，不得替代重要通知的逐条确认。

主站账户中心、AI 内嵌账户中心和 AI 顶层页面共享同一服务端状态。嵌入页与父页面通过 `postMessage` 同步时，双方必须同时校验固定 `origin`、预期 `source`、事件名称和字段类型；不能使用 `'*'` 目标源，也不能把通知正文放进跨窗口消息。

## 7. 邮件体验

### 7.1 发送规则

- 只向 `email_verified = 1` 且邮箱非空的用户发送；
- 每位用户独立投递，不能把所有地址放到 `To` 或 `Cc`；
- 邮件主题使用 `【量见】通知标题`；
- 邮件正文由标题、纯文本正文、安全内部按钮和平台说明组成；
- 邮件不包含 MT 账户、持仓、余额、策略提示词或其他敏感数据；
- 邮件发送失败不影响站内信创建和用户实时提醒。

### 7.2 失败与重试

邮件渠道状态：

- `pending`：等待发送；
- `sending`：已取得任务；
- `sent`：服务商已接受；
- `unknown`：连接超时或中断，无法确认服务商是否已经接受；
- `failed`：本次发送失败，可自动或人工重试；
- `skipped`：用户无已验证邮箱或账号已失效；
- `cancelled`：活动在尚未发送前被取消。

建议最多自动尝试 5 次，采用递增间隔，但只自动重试能够明确判断为“尚未被服务商接受”的失败。SMTP 在提交内容后超时可能已经完成投递，此时标记 `unknown`，不自动重试；管理员人工重试前必须看到“可能造成重复邮件”的提示。为每条邮件生成稳定的 `Message-ID` 并记录服务商响应摘要，但不能把它当作收件服务器一定去重的保证。超过上限后保留失败状态，由管理员在活动详情中“重试失败邮件”。日志和管理界面只展示本地化错误摘要，不展示 SMTP 密码、完整服务响应或其他用户地址。

## 8. 数据模型

### 8.1 扩展 `notifications`

保留现有字段和 `is_read` 兼容行为，新增：

- `campaign_id BIGINT NULL`：管理员通知活动；
- `priority VARCHAR(16) NOT NULL DEFAULT 'normal'`；
- `requires_ack TINYINT NOT NULL DEFAULT 0`；
- `read_at DATETIME NULL`；
- `acknowledged_at DATETIME NULL`。

建议新增索引：

- `(user_id, is_read, created_at)`；
- `(user_id, requires_ack, acknowledged_at, created_at)`；
- `(campaign_id, user_id)`。

兼容规则：

- 原有通知视为普通通知且不要求确认；
- 原有 `PATCH /notifications` 继续可用；
- 新接口写入 `read_at` 时同步设置 `is_read = 1`；
- 重要通知确认时同时确保 `is_read = 1`。

### 8.2 新建 `notification_campaigns`

建议字段：

- `id`；
- `title`、`message`、`priority`、`requires_ack`、`link`；
- `recipient_scope`：`user`、`plans`、`all`；
- `recipient_filter_json`：固定后的筛选条件，不存完整用户隐私；
- `in_app_enabled`、`email_enabled`；
- `status`：`queued`、`materializing`、`sending`、`cancelling`、`completed`、`partial_failed`、`cancelled`；
- `recipient_count`、`in_app_sent_count`、`email_sent_count`、`email_failed_count`、`email_skipped_count`；
- `created_by`、`created_at`、`started_at`、`completed_at`、`cancelled_at`。

活动内容一旦确认发送即不可编辑。需要修正文案时创建新活动，保证审计记录与用户实际收到内容一致。

### 8.3 新建 `notification_deliveries`

每个“活动 × 用户 × 渠道”一条记录：

- `campaign_id`、`user_id`、`notification_id`；
- `channel`：`in_app`、`email`；
- `status`；
- `attempt_count`、`next_attempt_at`；
- `sent_at`、`read_at`、`acknowledged_at`；
- `message_id`、`provider_response_summary`：邮件诊断字段，响应摘要必须脱敏和限长；
- `last_error`；
- `created_at`、`updated_at`。

唯一键：`(campaign_id, user_id, channel)`，防止队列重试产生重复通知或重复邮件。

站内信渠道记录同时承担本次活动的接收人快照：先用一条受筛选条件约束的 `INSERT ... SELECT` 原子写入所有 `in_app` 投递记录，再从这些固定记录派生邮件渠道记录。这样同一活动的站内信与邮件不会因为两次用户查询之间会员状态变化而覆盖不同人群。邮件不可达用户仍保留 `email/skipped` 记录，便于汇总“未绑定或未验证邮箱”。

## 9. 服务与投递流程

### 9.1 创建活动

1. 管理员提交内容和接收范围；
2. 服务端重新校验权限、内容、内部链接和范围；
3. 服务端重新计算接收人数量，不能信任前端预览值；
4. 如果实际人数与管理员确认的人数不一致，返回冲突响应和新摘要，要求重新确认；
5. 写入不可变的通知活动；
6. 记录管理审计；
7. 活动进入 `queued`；
8. 立即返回活动 ID，不让大批量发送阻塞 HTTP 请求。

### 9.2 物化接收人

- 后台任务以固定筛选条件执行幂等的 `INSERT ... SELECT`，先原子物化完整的 `in_app` 接收人快照；
- 快照记录完成后再从 `in_app` 记录派生邮件渠道记录，并把实际人数写回活动；
- 后续按投递记录主键或用户 ID 游标分批生成 `notifications` 和发送邮件，不再重新查询受众条件；
- 使用唯一键和条件状态更新保证崩溃恢复和重复执行安全；
- 单用户活动也走同一服务，避免出现两套业务逻辑；
- 用户在快照完成后被匿名化或失去有效身份时，尚未投递的渠道标记为 `skipped`，但保留快照记录用于审计。

创建接口中的人数复核与后台物化之间仍可能发生极短时间的用户变化；后台物化出的固定人数是最终审计口径。若该人数再次偏离管理员确认值，活动停留在 `materializing` 并进入“待复核”，不得自动开始投递。

### 9.3 站内信实时提醒

站内信写入成功后：

1. 事务提交；
2. 向该用户已连接的 AI 浏览器 WebSocket 发送最小唤醒事件；
3. 事件只包含通知 ID、级别、是否要求确认和新的未读计数；
4. 前端收到后通过受鉴权的 HTTP API读取通知内容；
5. WebSocket 失败不影响通知持久化。

不得通过观摩源转发逻辑把通知发送给其他观摩用户。建议把现有内部 `sendToBrowsers(userId, data)` 封装为专用导出函数，并对 `notification_created` 事件做固定字段白名单。

前端同时保留兜底同步：

- 登录或启动时读取通知摘要；
- 页面重新可见时读取摘要；
- WebSocket 重连成功后读取摘要；
- 不需要高频轮询。

## 10. API 设计

### 10.1 管理员接口

- `POST /api/admin/notifications/preview`：返回接收人估算和排除摘要；
- `POST /api/admin/notifications/campaigns`：创建并排队发送；
- `GET /api/admin/notifications/campaigns`：分页查询发送记录；
- `GET /api/admin/notifications/campaigns/:id`：活动与渠道详情；
- `POST /api/admin/notifications/campaigns/:id/retry-failed-email`：重试失败邮件；
- `POST /api/admin/notifications/campaigns/:id/cancel`：请求停止尚未取得的任务；已经成功的投递保留，活动进入 `cancelling`，待在途任务落定后转为 `cancelled` 并展示已发送/未发送数量。

所有接口必须使用 `authMiddleware + adminOnly`，并设置适当的管理操作频率限制。

创建、取消和人工重试接口必须要求幂等键；同一管理员、同一操作和同一幂等键只能产生一个业务结果。全体用户发送还应设置短时重新鉴权或沿用后台现有高风险操作确认机制，避免长期打开的管理会话被误用。

### 10.2 用户接口

- 扩展 `GET /api/notifications`：支持游标分页并返回优先级、链接、阅读和确认状态；
- 新增 `GET /api/notifications/summary`：返回未读数量、重要未确认数量和最新重要通知摘要；
- 保留 `PATCH /api/notifications` 兼容现有“单条已读/全部已读”；
- 新增 `POST /api/notifications/:id/acknowledge`：仅允许通知所属用户确认。

所有通知查询、阅读和确认操作必须把 `user_id = req.user.id` 写入 SQL 条件，不能先按 ID 查询后在应用层判断。

## 11. 权限、安全与审计

### 11.1 管理权限

- 第一版只允许 `admin` 创建和重试通知；
- 发送给“全部用户”必须二次输入确认词；
- 活动一旦开始不允许修改标题、正文、范围和渠道；
- 取消只停止未来投递，不撤回已经生成的站内信或服务商已接受的邮件；
- 已发送的站内信不提供物理删除功能；确需更正时发送更正通知。

### 11.2 内容安全

- 管理员输入只接受纯文本；
- 服务端控制长度和 Unicode 正常化；
- 邮件 HTML统一转义；
- 内部链接执行前缀和 URL 解析双重校验；
- 用户端使用现有 `escapeHtml` 或 `textContent` 渲染；
- 父子页面消息执行固定源、窗口对象、事件类型和数据结构校验；
- 错误信息不返回 SMTP 凭据、SQL、堆栈或其他接收人信息。

### 11.3 审计事件

至少记录：

- `notification_campaign_created`；
- `notification_campaign_cancelled`；
- `notification_email_retry_requested`。

审计详情包括活动 ID、接收范围、预计人数、通知级别和启用渠道，不保存 SMTP 密码，也不重复保存完整接收人列表。

## 12. 管理后台发送记录

列表字段：

- 创建时间；
- 标题；
- 接收范围；
- 普通/重要；
- 站内信已生成数；
- 邮件成功/失败/跳过；
- 活动状态；
- 创建管理员。

活动详情按渠道展示聚合结果，并允许按状态筛选单用户投递。邮箱在管理界面中默认脱敏；只有具有管理员权限且确有排障需要时才显示完整邮箱，第一期建议始终脱敏。

空状态应说明“发送通知后，可在这里查看站内信、邮件以及用户阅读确认结果”，而不是只显示“暂无数据”。

## 13. 状态与边界场景

必须覆盖：

- 接收范围为空；
- 单个用户不存在、已删除或是观摩源内部账号；
- 全部用户数量变化；
- 用户没有邮箱或邮箱未验证；
- SMTP 未配置；
- 邮件部分成功；
- SMTP 提交后超时导致投递结果未知；
- 站内信已生成但 WebSocket 不在线；
- 用户在主站阅读后 AI 实验室同步更新；
- AI 实验室与账户中心同时打开；
- “全部标为已读”不能确认重要通知；
- 重复提交、任务重启和网络重试不产生重复投递；
- 活动发送过程中管理员取消；
- 99、100 和大量未读角标；
- 长标题、长正文和窄屏换行；
- 深色/浅色主题以及键盘、屏幕阅读器操作。

### 16.1 自动化测试

- 活动内容不可变；
- 站内信与邮件渠道相互独立；
- 唯一键和重复任务幂等；

- 用户只能读取、标记和确认自己的通知；
- 全部标为已读不代替重要确认；
- WebSocket 只唤醒目标用户，不经过观摩转发；
- 管理审计字段和敏感信息过滤；
- 管理后台与 AI 前端契约测试；

### 16.2 浏览器验收

- 管理后台浅色/深色；
- 桌面、平板和手机布局；
- 单用户、会员范围和全体用户发送流程；
- 账户按钮 0、1、99、100 条未读；

## 17. 发布与数据库边界

- 本方案包含新增迁移，实施和测试不等于已获准修改公共生产数据库。
- 公共生产部署前必须单独确认数据库变更授权，并使用受控发布流程。
- 不运行手工 SQL、数据库客户端或直接修复生产数据。
- 发布前要求干净提交、迁移唯一且幂等、全量测试通过和静态资源缓存键更新。
- 发布后验证准确提交、应用健康、迁移记录、通知接口、AI 静态资源版本和近期启动日志。

## 18. 明确不做

第一期不做：

- 短信；
- 管理员自定义 HTML；
- 外部链接；
- 定时发送；
- 多步骤营销自动化；
- 用户标签自由组合；
- 附件、图片或富媒体；
- 浏览器系统通知权限；
- 强制遮挡交易界面的弹窗；
- 发送后编辑或物理删除活动；
- 以邮件成功与否决定站内信是否存在。

## 19. 主要风险

1. **大范围活动造成同步请求过慢**：创建接口只完成复核与排队；后台以集合写入原子物化受众，再按游标分批投递，不在 HTTP 请求中同步遍历全部用户。
2. **重复任务导致重复通知或邮件**：依赖活动、用户、渠道唯一键和条件状态更新。
3. **通知实时事件经过观摩转发泄露**：事件必须只发给目标用户浏览器集合，观摩转换函数对通知类型返回空。
4. **重要提示影响交易工作**：条幅不参与现有布局计算，并通过桌面/窄屏定位验收确认不遮挡关键控件；不使用模态和循环动画。
5. **邮件泄露其他接收人**：必须逐用户投递，禁止群发地址列表进入 `To` 或 `Cc`。
6. **“已读”和“已确认”混淆**：数据、接口和界面必须分别表达；批量已读不能替代确认。
7. **旧通知兼容性**：迁移默认值和现有接口必须保证历史通知仍正常展示。
8. **公共生产迁移风险**：在未单独确认前只允许本地实现和验证，不允许生产数据库操作。
9. **SMTP 超时造成重复邮件**：提交结果不明时标记 `unknown` 并停止自动重试；人工重试必须提示重复风险，稳定 `Message-ID` 只作为追踪辅助。
10. **嵌入账户中心消息伪造**：父子页面必须双向校验 `origin`、`source` 和事件字段，跨窗口事件只传状态，不传正文或敏感数据。

## 20. 两轮复核记录

### 第一轮复核：架构与业务边界

**复核结论：通过，已完成以下调整。**

发现并修正：

1. 初稿用游标边读边投递，同时声称“确认时固定接收人”，两者存在受众漂移矛盾。现改为先原子物化完整站内信渠道接收人快照，再从该快照派生其他渠道；所有投递在快照完成后开始。
2. 初稿只写“免费、Plus、Pro”，没有区分有效会员与已过期会员。现与既有会员口径对齐，明确免费、有效 Plus、有效 Pro 和已过期会员四类，禁止把已过期会员静默归入免费用户。
3. 初稿把 `/` 列为路径前缀，会意外允许管理后台和 API 路径。现改为 URL 解析后按具体路由及受控查询参数校验，并显式拒绝 `/admin/`、API、下载和协议相对地址。
4. 初稿的预览与创建人数变化、发送中取消语义不完整。现增加冲突重确认、物化后二次偏差待复核，以及 `cancelling` 状态和“已发送不可撤回”规则。

本轮保留风险：

- 大批量 `INSERT ... SELECT` 的锁影响和执行时间需要在实施时结合实际用户规模做压测；若单次集合写入超过可接受阈值，再引入独立接收人批次表，但不能退回边查询边投递。
- 观摩源内部账号的识别条件需要实施前以当前账号模型确认，不能仅凭昵称、服务器名称或前端观摩状态推断。
- 既有用户删除语义是匿名化而非简单 `is_deleted`，实现必须沿用 `deletion_status` 契约。

### 第二轮复核：UX、安全与可验证性

**复核结论：通过，已完成以下调整。**

发现并修正：

1. 账户按钮在有无未读时打开不同页，初稿只写了角标，目的提示还不够明确。现增加可见悬停文案和动态无障碍名称，让“账户入口”和“查看未读”两种状态可理解。
2. 重要提示条的屏幕阅读器策略、重复播报和多条通知规则未定义。现明确只展示最新一条、其余显示数量，使用礼貌状态播报，同一会话不重复打断用户。
3. 初稿没有彻底区分“打开、已读、确认”。现明确打开消息页或链接不得自动确认，只有“我知道了”写入确认时间，且确认操作幂等。
4. 父子页面同步只提到 `postMessage`，缺少消息安全契约。现增加固定 `origin`、预期 `source`、事件和字段校验，禁止通配目标源和正文跨窗口传递。
5. 初稿把所有邮件失败都视为可重试，忽略 SMTP 提交后超时可能已投递。现增加 `unknown` 状态、稳定 `Message-ID`、停止自动重试和人工重试重复风险提示。
6. 高风险管理操作缺少请求级重复提交保护。现要求创建、取消、人工重试使用幂等键，并对全体发送采用短时重新鉴权或现有高风险确认机制。

本轮保留风险：

- 是否能对“全体用户发送”复用现有重新鉴权能力，需要实施时核实现有管理员会话机制；若没有，不应为了第一期自行引入另一套登录态，而应保留输入确认词、权限、幂等键和速率限制并单独设计再认证。
- 不同 SMTP 服务商对 `Message-ID` 和超时响应的行为不一致，真实受控邮箱集成测试只能降低风险，不能提供邮件绝对不重复的保证。
- AI 顶栏在极窄屏、系统字体放大和多语言文案下的实际高度需要浏览器实测；方案已禁止覆盖交易区，但最终视觉验收仍不能由静态测试替代。

### 实施前视觉调整：重要通知条幅

用户在进入实现前确认：重要通知直接采用通知条幅样式，但不能影响当前 AI 实验室布局。方案据此由“正常文档流提示条”调整为靠近账户入口的固定悬浮紧凑条幅；未读角标、不可关闭、显式“我知道了”确认及不遮挡交易关键控件等约束保持不变。

## 21. 实施后主审记录

本地实现完成后进行了安全、布局与回归主审，并据此完成以下收口调整：

1. 服务端内部链接在进入 WHATWG URL 规范化前先解码原始路径，拒绝编码路径穿越、编码反斜杠和编码协议相对地址；避免危险路径被规范化成看似安全的账户或 AI 路径。
2. 主站浅色嵌入账户中心为未读标题、重要状态、待确认状态和详情链接增加主题覆盖，暗色账户中心规则保持不变。
3. AI 观摩模式在平板和手机宽度下会增加第三行频道选择器；重要通知条幅仅在该模式下进一步下移，普通模式维持原偏移，仍不进入交易工作区布局。
4. 冻结工作树后完成全量 Vitest、相关 JavaScript 语法检查、通知专项测试和静态布局/排版检测。真实页面浏览器验收因本地管理端需要已有登录会话而未冒用账号，保留为受控集成验收项。

当前仍未执行公共生产数据库迁移、真实 SMTP 投递或真实 Bridge 通知唤醒；这些边界不因本地自动化测试通过而视为已验证。
