# 旧复盘历史承接方案

依据：`architecture/review-transition-inventory-v1-20260911.json`，2026-09-11 对 dev_vue 一致快照只读核对。此方案接续核心重构，不代表迁移已完成。

## 实际范围

183 个案例：155 个系统单笔交易复盘、3 个人工交易复盘、25 个日/月复盘。日/月复盘有 33 个正文版本、11 个已批准案例、2 个仍标记 generating 的旧案例。相关来源、作业、阶段结果、事件、检查点和用户已读状态同时保留。

V4 已有统一案例、版本、证据、来源和作业表，但目前 kind 仅有 daily/monthly/manual，缺少系统单笔类型。25 个周期案例引用的旧策略版本均没有对应的已迁入 trader 版本：策略1的8/15/18/21/25/42版、策略3的10版。当前策略版本不能代替历史版本。

33 个周期正文实际存在三种字段结构，均不是 review.v4.1 的角色评估格式。不得凭空生成 analyst/trader/risk/execution 结论、交易指标或记忆候选。已有批准记录必须保留，不推测批准人及批准时间。

## 实施顺序

1. 补统一历史合同：系统单笔类型使用明确的 trade；区分新生成 review.v4.1 与不可变历史正文 review.legacy.v1。历史正文保留原字段、原文本字节摘要与原批准信息，读取接口明确返回来源格式。禁止用“证据不足”伪装所有旧结论。
2. 追加 schema 承接历史元数据和格式，保持已执行254步不变。同步 HTTP 域合同、生成类型、运行验证器与消费者适配，不直接修改生成文件。历史详情可读；只有完成新格式转换及必要证据校验后，才进入新编辑/确认/记忆派生流程。
3. 从冻结作业/策略快照恢复旧版本身份。能证明原文、摘要、来源一致才建立历史策略版本；证据缺失或冲突时保留明确 legacy 引用，禁止链接当前版本，也不创建伪造的空提示词版本。
4. 分批迁移案例、全部版本和来源，再迁移任务历史、事件、检查点及用户状态。沿用源归档、ID映射、摘要、检查点和事务回执；正文大载荷按单案例限额和游标批次处理，不把约百MiB证据塞进一个事务。
5. 旧 generating/queued/重试作业作为历史承接，不能因迁移启动模型调用；用户发起新任务后使用新job。旧用户29的历史归属保留，当前账户所有者不能继承其私人复盘；通过明确用户归属和历史可见性校验读取。
6. 恢复库先验证整批回滚、独立重跑、逐用户/账户/案例版本对账、原文摘要、当前/批准指针、原表与账本不变，再升级当前dev_vue。最终用真实API读取新旧两种正文和历史所有权拒绝分支。

## 复核一：数据与类型

发现单笔类型缺失以及历史策略版本缺失，因此不能直接把155条案例写成manual，也不能把25条历史周期案例链接当前策略。调整为先扩展类型及历史来源合同，再建立可证明的历史版本映射。旧表和源原文始终保留。

## 复核二：状态与运行影响

旧正文没有新角色评估与指标，强制转换会创造不存在的结论；调整为显式版本化历史正文，后续可追加新的V4修订，历史版本不可变。旧运行中任务不能自动恢复，批准不等于已获新记忆写入授权。不得把归档完成、schema通过或合成端口测试表述为业务承接完成。
