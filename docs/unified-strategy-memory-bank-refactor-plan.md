# 单一策略总记忆库重构方案

> 状态：待实施方案；本文不代表功能已经上线
>
> 审查基线：`dev_codex` @ `00936149cb5b7b0eedf2f477c86322831098be22`
>
> 日期：2026-08-12
>
> 适用范围：个人策略记忆、平台策略记忆、自动/手动推理、日复盘、月复盘、记忆整理、人工维护、冲突提醒及相关审计

## 1. 最终产品定义

每个策略只维护一个总记忆库。最终产品和运行时不再存在以下概念：

- 短期记忆；
- 长期记忆；
- 长期记忆候选；
- 月度摘要作为独立检索层；
- 短期升级长期；
- 短期记忆过期时间；
- 按行情检索若干条记忆；
- 最大命中条数；
- 记忆注入 token 预算；
- 通用记忆最多一条；
- 个人记忆与平台记忆两套不同的运行模型。

每个策略只有：

1. 一个稳定的记忆库身份；
2. 一个当前生效版本；
3. 完整版本历史和来源证据；
4. 一组尚未达到提醒门槛的策略冲突观察；
5. 一个可人工编辑、回滚和整理的界面。

推理、日复盘和月复盘都传入该策略当前冻结的完整记忆库，不再先做条目筛选。

## 2. 目标与边界

### 2.1 必须实现

1. 日复盘确认后，把确认版本产生的记忆变更应用到对应策略总库。
2. 月复盘同时读取完整策略和完整总库，完成月度总结、去重、修正、淘汰和压缩。
3. 每次分析推理传入完整总库，并记录使用的总库版本和内容哈希。
4. 总库允许人工新增、修改、删除、调整适用条件和回滚；任何修改都创建新版本。
5. 记忆与策略冲突时先累计观察；同一冲突多次独立出现后才提醒人工修改策略。
6. 总库达到存储体积阈值时自动整理；每次月复盘无条件执行一次月度整理。
7. 保留全部来源复盘和版本审计，但来源记录不再作为短期/长期记忆向模型检索。
8. 私人策略和平台策略使用同一底层结构，同时保持原权限隔离。

### 2.2 不自动执行

- 不自动修改策略提示词、策略配置或风险规则。
- 不因记忆冲突自动改变交易方向、入场方式或仓位。
- 不删除原始复盘、交易、信号、订单、风险和行情证据。
- 不通过筛选部分记忆来掩盖总库过大。
- 不把复盘生成视为记忆已生效；必须等待复盘确认和总库新版本成功激活。

## 3. 已核实的当前基线

### 3.1 当前个人记忆链路

- 已确认日复盘生成 `experience_memory_items` 短期条目。
- 普通复盘累计至少 3 次、跨度至少 7 天后生成长期候选。
- 已确认月复盘创建月度摘要和长期候选，并强制尝试压缩。
- 推理按策略、品种、周期、方向、入场方式、行情、波动和缠论条件筛选短期、长期和摘要。
- 当前个人运行预算默认 800 tokens，并限制最多 5 条短期、3 条长期、2 条摘要和 1 条通用长期记忆。

### 3.2 当前平台记忆链路

- 平台复盘确认后生成 `platform_strategy_experience_items` candidate。
- 管理员发布后才成为 active。
- 平台运行策略拥有 off/shadow/active、最多命中条数和 token 预算。
- 平台与个人记忆使用不同表、不同检索函数和不同管理动作。

### 3.3 当前复盘与记忆输入

- 日复盘证据包含交易发生时的策略标识和推理系统提示词，但没有当前总记忆库。
- 月复盘包含策略标识、日复盘版本和确定性统计，但没有总记忆库正文。
- 复盘确认通过 `period_review_derivation_jobs` 异步派生个人记忆或平台候选。
- 复盘案例、来源、版本、任务、月度检查点和用户确认状态已经分层持久化，应继续复用。

## 4. 目标架构

```text
交易与行情证据
      ↓
日复盘草稿 ── 人工编辑/确认
      ↓
总记忆库变更补丁
      ↓
策略总记忆库新版本
      ↓
完整传入推理、下一次日复盘和月复盘

月复盘确认
      ↓
全库整理 + 冲突汇总 + 新版本
```

来源证据与总库分开：来源只证明“为什么发生这次修改”，总库版本才是模型实际读取的权威内容。

## 5. 数据模型

### 5.1 `strategy_memory_banks`

每个未删除策略恰好一行：

| 字段 | 语义 |
| --- | --- |
| `id` | 总库 ID |
| `strategy_id` | 唯一绑定策略 |
| `strategy_scope` | `private` 或 `platform` |
| `owner_user_id` | 私人策略所有者；平台策略为 0 |
| `current_version_id` | 当前权威版本 |
| `version_no` | 当前版本号 |
| `status` | `active`、`awaiting_compaction`、`blocked` |
| `content_bytes` | 当前 UTF-8 内容体积，仅用于存储治理 |
| `content_token_observed` | 观测值，不作为记忆预算或截断依据 |
| `updated_at` | 最近变化时间 |

唯一键：`strategy_id`。策略 scope 和 owner 必须与策略表一致，不能由请求体自由指定。

### 5.2 `strategy_memory_bank_versions`

每次日复盘沉淀、月度整理、人工编辑、自动整理和回滚都创建完整版本：

| 字段 | 语义 |
| --- | --- |
| `id`、`bank_id`、`version_no` | 版本身份 |
| `parent_version_id` | 直接父版本 |
| `content_json` | 完整结构化总库 |
| `compiled_text` | 实际传入模型的完整稳定文本 |
| `content_hash` | 完整内容哈希 |
| `strategy_compatibility_hash` | 生成时对应的策略兼容哈希 |
| `change_type` | `daily_review`、`monthly_review`、`manual_edit`、`auto_compaction`、`rollback`、`migration` |
| `source_period_case_id`、`source_period_version_id` | 复盘来源，可为空 |
| `author_user_id` | 人工编辑者或确认者 |
| `status` | `draft`、`active`、`superseded`、`failed`、`awaiting_compaction` |
| `change_summary_json` | 新增、修改、移除和冲突变化 |
| `created_at` | 创建时间 |

每个 bank 同时只有一个 active 版本。`current_version_id` 更新必须与版本插入在同一事务完成。

### 5.3 记忆条目结构

总库不是无结构长文；每项使用稳定 `memory_key`，但没有短期/长期层级：

```json
{
  "memory_key": "mem_018",
  "category": "entry_setup",
  "lesson": "突破后第一次回踩未确认时不要追单",
  "anti_pattern": "把一次快速回踩直接视为确认",
  "applicable_when": {
    "symbols": ["XAUUSD"],
    "timeframes": ["H1"],
    "market_regimes": ["breakout"]
  },
  "avoid_when": {},
  "support_count": 4,
  "confidence": 0.82,
  "source_review_refs": ["period:101", "period:108", "period:116", "period:125"],
  "strategy_conflict_state": "none"
}
```

`support_count`、置信度和来源只表达证据强度，不触发层级升级。

### 5.4 来源与冲突表

新增：

- `strategy_memory_bank_evidence_links`
  - `bank_version_id`、`memory_key`、`source_type`、`source_id`、`source_hash`；
  - 对同一来源幂等去重；
  - 不保存第二份交易或行情正文。
- `strategy_memory_conflicts`
  - `strategy_id`、`conflict_signature`、`strategy_rule_hash`、`memory_key`、`conflict_type`；
  - `status=watching|alerting|acknowledged|resolved|dismissed|revalidation`；
  - `support_count`、首次/最近出现时间、当前策略兼容哈希。
- `strategy_memory_conflict_sources`
  - `conflict_id` + `period_review_case_id` 唯一；
  - 保证同一个日复盘无论有多少交易或被月复盘再次引用，都只计一次。

## 6. 总库正文合同

当前版本的 `content_json` 固定包含：

```json
{
  "schema_version": 1,
  "strategy_id": 12,
  "bank_version": 8,
  "principles": [],
  "memories": [],
  "unresolved_strategy_conflicts": [],
  "generated_from": {
    "parent_version_id": 7,
    "source_period_case_ids": []
  }
}
```

规则：

- `principles` 和 `memories` 全部传入，不做运行时命中筛选。
- 适用条件继续保留，让模型判断何时适用，但不再由检索器删减条目。
- `unresolved_strategy_conflicts` 也随总库传入，并明确标记“只能观察，不能作为违反当前策略的执行依据”。
- 策略、风险、权限、输出格式和仓位边界始终高于记忆。
- 人工文本继续作为不可信数据转义，不能把记忆变成系统指令。

## 7. 推理流程

### 7.1 读取与冻结

每次手动或自动推理：

1. 根据策略 ID 读取唯一总库及 current version。
2. 将 `compiled_text` 完整加入模型输入。
3. 在 inference snapshot 冻结：
   - `memory_bank_id`；
   - `memory_bank_version_id`；
   - `memory_bank_hash`；
   - 实际完整记忆正文或可验证的冻结引用。
4. 同一模型任务重试继续使用冻结版本，即使后台已经产生新总库版本。

删除 `retrievePersonalMemory()`、`retrievePlatformExperience()` 的候选排名职责，替换为单一 `loadStrategyMemoryBankSnapshot()`。

### 7.2 模型采用审计

- `experience_usage.considered_refs` 固定对应该版本内全部可引用 `memory_key`。
- `used_refs` 只能引用总库中实际采用的 key。
- 日志保存 bank/version/hash、模型实际采用 key、信号 ID 和快照 ID。
- 不再记录“未命中原因、最大条数、token 预算、短期/长期选择”。

### 7.3 输入物理容量不足

不允许退回按需选几条记忆。处理顺序固定为：

1. 新总库版本激活前，根据绑定模型的提供商最大输入/上下文能力校验可运行性。
2. 若新版本会使完整策略、完整总库和最小必要业务输入无法放入模型，则版本进入 `awaiting_compaction`，自动排队整理。
3. 整理成功后再激活；期间继续使用上一个可运行的 active 版本。
4. 若模型被换成更小上下文且当前版本也无法运行，推理显式失败并提醒先整理记忆或更换模型；不得静默选择部分记忆。

该流程依赖《模型提供商物理 Token 能力与平台输出硬上限取消方案》的统一能力解析器。

## 8. 日复盘流程

### 8.1 冻结输入

日复盘案例首次创建时冻结：

- 交易发生时的策略版本、策略正文和策略兼容哈希；
- 当前总库 ID、版本、哈希和完整正文；
- 当日交易、行情和缠论证据；
- 终端时区与周期边界。

复盘重试必须保持相同冻结输入，不得在 worker 执行时临时读取更新后的总库。

### 8.2 输出合同

日复盘内容在现有字段外增加：

```json
{
  "memory_bank_patch": {
    "add": [],
    "update": [],
    "remove": [],
    "reinforce": [],
    "no_change_reason": ""
  },
  "strategy_conflict_observations": []
}
```

每项 patch 必须：

- 使用稳定 memory key 或申请新 key；
- 带适用条件和来源证据；
- 区分新增、修正、强化和失效；
- 不修改策略、风控、权限或系统输出合同；
- 不把一次盈利或亏损直接当成稳定规律。

### 8.3 用户确认与应用

用户可以在复盘页面先修改 patch。只有确认复盘版本后，`period_review_derivation_jobs` 才以 `target_type='strategy_memory_bank'` 应用 patch。

应用时：

1. 锁定 bank 和批准的复盘版本。
2. 验证该复盘尚未派生成功。
3. 读取 patch 生成完整下一版本。
4. 更新来源链接和冲突来源。
5. 插入新版本并 compare-and-set `current_version_id`。
6. 激活成功后，派生任务才标记 succeeded。

同一复盘版本重复执行必须返回已经生成的相同 bank version，不得重复增加支持次数。

## 9. 月复盘流程

### 9.1 输入

月复盘每个分块和最终合并都必须带：

- 冻结的当前完整策略；
- 冻结的当前完整总记忆库；
- 该分块的已冻结日复盘来源；
- 当前月涉及的历史策略版本引用。

总库和策略公共上下文不得在分块之间删减；若输入接近提供商最大输入，只减小每日来源分块数量。

### 9.2 月度职责

月复盘不再生成长期候选或独立月度摘要。它生成一个全库 patch：

- 合并明确重复的表达；
- 强化多次出现的经验；
- 修正适用条件；
- 把被反例推翻的经验移除或改写；
- 保留不同市场条件下互相相反但都成立的经验；
- 对达到门槛的策略冲突生成提醒；
- 产出更紧凑但来源可追溯的完整总库版本。

用户确认月复盘后才激活月度整理版本。月复盘引用的日复盘不能再次增加冲突 occurrence。

## 10. 策略冲突累计与人工提醒

### 10.1 冲突签名

同一冲突由以下稳定信息计算：

```text
strategy_id
+ normalized strategy rule hash
+ conflict_type
+ normalized memory proposition
+ applicability signature
```

只比较真正的策略规则。系统权限、仓位、风险和输出格式冲突直接拒绝该记忆修改，不进入“等待多次”的策略优化流程。

### 10.2 occurrence 规则

默认提醒门槛固定为：

- 同一 signature；
- 至少 3 个不同的已确认日复盘案例；
- 来自 3 个不同终端交易日；
- 来源证据完整；
- 被冲突的规则在当前策略中仍存在。

同一日多笔交易只计一次。月复盘只是汇总，不增加次数。模型重复生成相同句子也不增加次数。

### 10.3 策略版本变化

- 策略版本变化但规则哈希不变：保留累计次数。
- 被冲突规则发生实质变化：冲突进入 `revalidation`，保留历史但停止当前提醒。
- 新日复盘确认该冲突仍存在后，使用新规则哈希建立或恢复观察。

### 10.4 人工操作

达到门槛后显示“建议人工检查策略”，提供：

- 修改策略；
- 修改记忆；
- 继续观察；
- 驳回该记忆结论；
- 标记已解决。

所有操作保存操作者、时间、原因和前后版本。系统永不自动改策略。

## 11. 人工维护

### 11.1 私人策略

策略所有者在 AI 复盘师的“策略记忆库”中选择策略并编辑总库。普通用户不能查看或修改其他用户的私人总库。

### 11.2 平台策略

平台总库只在统一 `/admin/` 管理后台维护。观摩源内容管理者只能对其允许维护的平台策略产生复盘候选；发布、人工编辑和策略修改仍按现有平台内容权限执行，不因此获得用户或全局管理权限。

### 11.3 编辑行为

- 前端提供结构化条目编辑，不直接编辑不可验证的数据库 JSON。
- 保存时必须携带 `expected_version_id`。
- 后端验证 memory key 唯一、字段长度、适用条件结构和策略绑定。
- 保存生成新版本和差异预览；不原地覆盖。
- “删除”只表示从新版本移除，历史版本和来源继续保留。
- 回滚通过创建一个以历史内容为正文的新版本完成，不把旧 superseded 行直接改回 active。

## 12. 自动整理与存储上限

不再用记忆 token 预算、命中条数或短期条目数触发压缩。整理触发来源为：

1. 每次已确认月复盘；
2. `content_bytes` 达到系统配置的存储软阈值；
3. 新版本无法适配绑定模型的提供商最大输入；
4. 人工点击“整理记忆库”；
5. 重复、矛盾或失效项累计到需要治理的状态。

存储软阈值以 UTF-8 bytes 表达，不以 token 表达；默认值需要在实施前根据现有真实总库迁移预览确定，本文不武断写死。

整理合同：

- 输入是一个完整 bank version；
- 输出也是一个完整 bank version；
- 必须返回所有保留、合并、移除条目的来源映射；
- 不得合并适用条件相反的经验；
- 不得修改策略、提高风险或创造没有来源的新规则；
- 人工固定的条目只能改写表达，不能静默删除；
- 整理失败时保留当前 active 版本，不产生半版本；
- 整理输出必须通过结构、来源覆盖、内容哈希和物理输入兼容校验后才能激活。

整理模型的输出遵循提供商最大输出能力，不使用 AURUM 自设输出 token 硬上限。

## 13. 并发与重放

### 13.1 compare-and-set

日复盘、月复盘、人工编辑和自动整理都可能同时修改同一总库。所有写入都必须基于 `expected_current_version_id`：

- 当前版本仍等于 expected：创建下一版本并激活；
- 当前版本已变化：不得覆盖，任务进入 `needs_rebase`。

### 13.2 rebase

rebase 使用已批准复盘 patch、原始父版本和新的当前版本做三方处理：

- 修改不同 memory key：确定性合并；
- 同一个 key 只增加不同来源支持：幂等合并来源；
- 同一个 key 内容被双方修改：停止自动应用，进入人工冲突处理；
- remove 与 update 冲突：进入人工处理。

不通过重新调用模型来悄悄改变已经由用户确认的复盘结论。

### 13.3 任务恢复

- 继续复用模型任务、业务任务租约、fencing token 和状态未知机制。
- 总库版本已插入但 derivation job 尚未成功时，恢复逻辑通过 source period version 查到已有结果并收敛为 succeeded。
- worker 丢失租约后不能激活版本。
- 月度检查点和最终合并继续验证全部日复盘来源恰好覆盖一次。

## 15. 旧数据迁移

### 15.1 迁移范围

读取：

- `experience_memory_items`；
- `experience_long_term_memories`；
- `experience_memory_summaries`；
- `platform_strategy_experience_items`；
- 相关来源、压缩和注入日志。

### 15.2 初始版本生成

对每个策略创建一个 migration 版本：

1. 导入所有当前 active 的个人和平台记忆正文及适用条件。
2. exact canonical hash 相同的条目合并来源和支持次数。
3. 不用模型自动判断语义重复，避免迁移时改变含义。
4. active 摘要与其来源条目若不能确定覆盖关系，全部保留并标注迁移来源，交由首次月度整理或人工处理。
5. candidate、duplicate_candidate、revalidation 进入迁移待处理清单，不直接变成有效总库规则。
6. revoked、expired、stale、archival 保留在旧只读归档，不进入当前版本。

迁移必须提供 dry-run 报告：策略数、导入条目数、exact 去重数、待处理数、孤儿来源、总字节和与绑定模型输入能力的兼容结果。

### 15.3 权威切换

1. 先创建新表并生成全部初始版本，不改变现有推理。
2. 对每个策略比较旧 active 内容与迁移版本来源覆盖。
3. 所有策略通过后，一次性切换推理、复盘派生和界面。
4. 切换后旧表只读，不再新增记录。
5. 稳定一个发布周期后再决定是否移除旧代码；旧表不在首个版本删除。

不得长期保留两套运行时同时向模型注入记忆。

## 16. 测试与验收

### 16.1 总库与版本

- 每个策略只能有一个 bank 和一个 active version。
- 私人/平台权限和策略绑定不可跨越。
- 日复盘确认只产生一次新版本；重复任务不重复计数。
- 人工编辑和回滚都创建版本，历史不可变。
- compare-and-set 防止并发覆盖；三方 rebase 冲突不会自动改写人工内容。

### 16.2 完整注入

- 推理消息包含当前总库全部 principles、memories 和 unresolved conflicts。
- 不存在按品种、周期、方向或命中分数删除条目的运行路径。
- 不存在 max_items、runtime_token_budget、短期/长期选择。
- 快照和日志保存 bank/version/hash；任务重试使用冻结版本。
- 记忆正文不能覆盖策略、风险、权限和输出合同。

### 16.3 日/月复盘

- 日复盘输入包含冻结策略和冻结总库。
- 批准前不修改总库；编辑后的批准版本才是派生来源。
- 月度每个分块和合并都带完整策略与总库，来源分块完整无重复。
- 月复盘不创建长期候选或独立摘要。
- 月复盘引用的日复盘不重复增加冲突次数。
- 已批准复盘证据变化不会静默撤销已经生效的总库版本。

### 16.4 冲突提醒

- 同一日多笔只计一次。
- 两个不同日不提醒，第三个不同已确认日才进入 alerting。
- 月复盘不额外计数。
- 策略规则哈希变化后进入 revalidation。
- 风险/权限冲突立即拒绝，不进入三次门槛。
- 人工 resolved/dismissed 操作有审计且不会自动改策略。

### 16.5 整理与迁移

- 存储字节阈值和月度确认会排队整理。
- 整理失败保留旧 active 版本。
- 相反适用条件不会被合并。
- 迁移 dry-run 可证明所有旧 active 来源已覆盖或明确列为阻断。
- 切换后旧检索函数和旧派生目标不再被调用。

定向测试至少覆盖现有 `memory-system`、`platform-experience`、`period-review`、`llm`、`scheduler`、`strategy` 和前端治理测试；随后运行完整 `npm test` 和修改文件的 `node --check`。

## 17. 发布与回滚

### 17.1 发布阻断条件

- 任一 active 旧记忆没有迁移去向；
- 新总库会跨策略或跨用户暴露；
- 正式路径仍同时注入旧检索记忆和新总库；
- 输入物理容量不足时会静默选择部分记忆；
- 日/月复盘重试读取了非冻结总库；
- 冲突次数能被同一复盘或月度汇总重复增加；
- 人工编辑存在覆盖并发新版本的可能；
- 月度整理不能证明来源覆盖或会合并相反经验。

### 17.2 回滚

首个切换版本保留旧表和迁移映射。若必须回滚：

1. 停止新的总库派生 worker；
2. 回退代码并恢复旧读取路径；
3. 不把新总库版本反向拆写为短期/长期记忆，避免制造虚假来源；
4. 回滚窗口内新产生的批准复盘保留 derivation 状态，回滚后不得自动重复派生；
5. 输出新旧系统差异清单，由后续重新切换时处理。

正式切换后不允许两个系统并行向交易推理注入内容。

9. 改造私人策略页面和统一管理后台。

## 19. 第一轮方案复审：需求覆盖、边界与过度设计

### 19.1 检查结论

- 已按最新需求彻底取消短期、长期、长期候选和摘要检索层，不是在旧体系上增加聚合视图。
- 已明确每次推理、日复盘和月复盘传完整总库，不保留按需检索的隐藏后门。
- 已覆盖人工编辑、日复盘增量、月度整理、存储阈值整理和多次冲突提醒。
- 复用了现有复盘案例、版本、派生任务和模型运行时，没有重建交易证据或复盘调度。
- 初稿如果只保存一个可编辑大文本，会丢失来源、冲突计数和并发修改能力，因此保留了版本、来源和冲突三类最小治理表。
- 版本表和冲突表是总库可靠运行所必需，不属于继续保留记忆分层。

### 19.2 根据第一轮作出的调整

1. 删除运行时检索、max_items、token budget 和 off/shadow 产品策略，明确总库非空即随策略使用。
2. 把来源证据从“记忆层级”改成纯审计链接，不参与模型检索。
3. 明确 monthly chunk 和 merge 都携带完整策略及总库，只通过缩小日来源分块解决输入压力。
4. 增加总库结构合同，避免变成无法安全编辑和去重的自由长文。
5. 增加 `AGENTS.md` 旧约束更新项，防止实施后仓库规则仍要求短期/长期检索。

### 19.3 第一轮剩余风险

- 完整总库每次注入会增加输入成本和延迟。
- 不做确定性行情筛选后，模型需要正确理解每项适用条件。
- 旧 active 摘要与原子来源的语义覆盖难以在迁移时完全自动证明。

## 20. 第二轮方案复审：兼容、迁移、并发、恢复与连带 Bug

### 20.1 检查结论

- 新表先建、dry-run、覆盖验证、一次性切换和旧表只读满足可回滚要求；首个版本不破坏旧数据。
- stable memory key、完整版本和 compare-and-set 防止日复盘、月复盘、人工编辑与自动整理互相覆盖。
- 三方 rebase 只自动合并无冲突变化；同 key 内容冲突必须人工处理，不重新调用模型篡改已批准结论。
- 复盘冻结总库版本，重试和检查点保持输入合同；符合现有 period-review 状态机。
- 冲突以唯一日复盘来源计数，月度汇总不会重复计数；策略规则变化会进入 revalidation。
- 平台和私人策略使用同一服务层但仍按 owner/scope 隔离，不扩大观摩源或管理员权限。
- 输入容量不足时不会退回旧按需检索；新版本先整理后激活，当前版本不可运行时显式失败。
- 整理失败、租约丢失、版本已落库但任务未收尾等状态都有恢复路径。

### 20.2 第二轮调整

1. 增加新版本激活前的模型物理输入兼容检查，并与另一份 token 能力方案建立明确依赖。
2. 增加 `awaiting_compaction`，避免超大新版本直接破坏正式推理。
3. 明确回滚通过创建新版本完成，防止直接复活旧行破坏版本单调性。
4. 增加迁移 candidate/revoked/stale 的明确去向，避免它们误入当前总库。
5. 增加“风险/权限冲突立即拒绝”和“策略经验冲突累计三次”的分类，避免安全规则也等待三次。
6. 增加回滚窗口内新批准复盘的派生处理约束，防止旧新系统切换后重复沉淀。

### 20.3 最终剩余风险

- 完整总库的长期规模最终仍受模型提供商最大输入限制；本方案选择整理或显式失败，不允许悄悄恢复部分检索。
- 第一次迁移可能暂时包含摘要与来源表达重复，需要人工或首次月度整理收敛。
- 自动整理需要严格来源覆盖验证，否则可能把“语言更短”误当成“信息无损”。
- 模型即使看到适用条件，也可能错误采用不适用经验；需要通过采用审计和回放评估持续观察。
- 同一策略规则的稳定标识需要在实施时结合当前策略结构确定；纯文本规则只能使用规范化哈希，策略改写可能触发重新验证。

经过两轮复审，本方案已经符合“一个策略只有一个总记忆库”的目标，可进入实施拆分；实施前必须先完成旧数据迁移预览和绑定模型输入能力盘点。
