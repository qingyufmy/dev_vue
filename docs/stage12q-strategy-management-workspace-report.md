# 阶段 12Q：AI 策略师与账户订阅工作区验收记录

> 日期：2026-09-04
>
> 范围：分析/交易执行策略、不可变版本、确定性校验、发布/退役、账户级策略订阅与 Trade 前端工作区
>
> 边界：仅完成源码与离线验证；未执行数据库迁移，未启动 V4 业务进程，未连接真实 MySQL、Redis、模型、Bridge、MT4/MT5，也未触发分析或交易

## 1. 结果

阶段 12Q 将 `/strategist` 从占位页替换为真实策略管理工作区，并补齐对应 V4 HTTP 合同。页面把普通交易者的两项主要任务分开：

1. 在“策略库与版本”中查看平台共享策略、创建个人策略、校验提示词、保存不可变版本、发布或退役；
2. 在“账户订阅”中为不同 MT4/MT5 账户分别选择分析策略和交易执行策略，并独立控制自动分析、AI 交易员和交易发送。

策略继续只有 `analysis` 与 `trader` 两类。分析策略负责行情判断和机会识别；交易执行策略结合分析结论与账户事实提出账户级动作。账户风控、权限、幂等、终端状态和执行安全不进入策略提示词，也不能被策略绕过。

## 2. 策略、版本与编译边界

- 平台策略对普通用户只读；个人策略只能由所有者修改。
- 新建策略先写入草稿与 v1；提示词版本只追加，不允许覆盖历史版本。
- 发布切换 `active_version_id`，并把引用该策略且尚未结束的账户订阅原子推进到新版本；已结束订阅保留原版本，未发布版本不会进入调度。
- 退役不物理删除策略、订阅或历史版本；调度器只接纳活动策略，因此现有订阅停止生成新任务，已有分析、决定和审计引用保持可追溯。退役不会自动平仓或撤单。
- 编译器不执行模型或提示词，只校验输入、配置、数据合同和禁止能力。
- 首版配置禁止声明 script、network、SQL、文件系统、shell、Bridge 或交易工具等执行能力。
- 分析策略的运行时数据范围只接受 M1/M5/M15/M30/H1/H4/D1 和 50～1000 根 K 线；默认 M5/M15/H1/H4、每周期 300 根。

策略 Skill 仍是策略逻辑权威，运行时只绑定所有权、品种、账户、模型和调度。平台合同、权限、schema、风险、执行安全与实时事实始终优先。自然语言引导生成、缺失规则追问、情景验证和高级 ZIP 导入不在本阶段伪造，后续只能建立在本阶段的不可变版本与编译合同上。

## 3. 账户订阅语义

- 分析记录按系统用户归档；AI 交易员与交易发送按交易账户隔离。
- 同一用户可以给不同交易账户订阅不同策略。
- 创建订阅时把已发布策略解析为明确版本；只有显式发布会升级引用该策略的订阅，普通开关、暂停和恢复不能静默漂移版本。
- 自动分析沿用五分钟固定调度；本阶段订阅界面使用 UTC 全天接收，不展示尚未被调度器执行的接收时段设置。
- AI 交易员只在分析存在做单机会，或账户已有持仓/挂单需要管理时触发。
- “允许发送交易”只表示交易员建议可以进入后续确定性风控与执行链，不表示跳过风险评审或直接成交。
- 同账户、同品种只允许一条活动的可执行交易策略；冲突返回稳定 409。
- 结束订阅是终态，不会自动平仓、撤单或删除历史记录。

## 4. shadcn-vue 前端结构

页面只组合共享 `@aurum/ui` 的 shadcn-vue/Reka 组件：

- `Tabs`：分隔策略库与账户订阅，也分隔分析和交易执行策略；
- `Card + ScrollArea + Badge`：策略目录、详情、版本和状态；
- `Sheet + Field + Select + Input + Textarea + Checkbox + Switch`：策略与订阅编辑；
- `Table + Card`：桌面订阅表格与移动端订阅卡片；
- `AlertDialog`：策略退役与订阅结束确认；
- `Alert + Empty`：局部错误、成功反馈、加载和空状态。

页面采用既有语义色、无衬线字体和低动态，不引入新的视觉主题。主要按钮和选择器保持至少 44 px 触控高度；宽屏使用 21rem 策略目录加弹性详情区，窄屏自然堆叠；复杂表单收进可滚动 Sheet。

## 5. API、并发与数据库

V4 新增策略详情、编译、创建、资料修改、版本创建、发布、退役，以及账户订阅列表、创建和 CAS 更新端点。所有浏览器写请求需要当前 Trade 会话 CSRF；资料、版本、发布、退役和订阅更新使用 `If-Match`，过期 revision 返回 412。

实现复用 `20260903_004_ai_strategy_and_inference_core.sql` 中现有 `strategies`、`strategy_versions`、`strategy_subscriptions` 和 `subscription_schedules`，没有新增或执行迁移。交易账户通过活动 owner 关系校验；平台策略和其他用户策略不会因 ID 猜测而泄露。事务采用账户、策略、订阅的固定加锁顺序，唯一键冲突转换为明确领域错误。

## 6. 第一轮复审：版本绑定与权限范围

第一轮复审发现两个会导致业务含义漂移的问题：

1. 更新订阅开关时若总是重新读取策略当前发布版本，会让暂停、恢复或关闭交易发送变成隐式升级；
2. 若把当前观摩上下文当成策略库写权限，用户进入观摩模式后会无故失去个人策略编辑能力。

调整：订阅仅在显式更换策略时解析新活动版本，其他更新保留原版本；结束状态保持终态。策略库权限只看策略所有权，账户订阅权限只看交易账户 owner，不把观摩显示上下文扩展成无关的全局禁写规则。

第一轮结论：平台策略只读、个人策略所有权、账户订阅归属和版本固定边界一致，不会因 UI 上的普通开关导致策略版本静默变化。

## 7. 第二轮复审：前端状态与误操作

第二轮复审发现两个前端状态问题：

1. 合同校验通过后继续修改提示词，旧校验结果仍可能让保存按钮保持可用；
2. 新建策略弹层如果复用当前策略的最新版本，会把旧提示词误带入新策略。

调整：编辑器记录校验时的完整草稿签名，内容变化后必须重新校验；新建策略永远使用空提示词和对应类型的默认运行时配置，只有“新建版本”才继承当前策略最新版本。发布、退役和结束订阅均读取最新 revision，失败后不在浏览器猜测成功。

第二轮结论：创建、版本迭代、发布与账户订阅形成清晰的渐进流程；移动端不依赖横向表格完成编辑和结束操作。

## 9. 剩余风险与下一步

- 当前没有启动旁路 V4 API 或真实数据库，不能把合同测试当作真实数据验收。
- 接收时区和接收窗口虽然存在数据库字段，但当前调度器尚未执行该语义，因此页面没有暴露无效设置。
- 目前是专业提示词编辑与确定性校验，不是最终的普通用户自然语言引导生成；后续需单独设计引导会话、缺失规则追问和情景验证，且不得让模型直接保存或发布策略。
- 策略与订阅变更的统一系统审计展示仍属于后续“系统审计”页面竖切；本阶段不伪造审计 UI。
- 真实长名称、长提示词、焦点回退、Sheet 滚动和 375/768/1024/1440 px 浏览器行为，需在阶段 15～16 启动旁路环境后验收。
