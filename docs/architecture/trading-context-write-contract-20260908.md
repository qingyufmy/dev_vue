# 账户上下文写入与恢复合同

本合同接续全栈模块化方案 B/C，不表示当前幂等持久化已经完成。应用和测试本地运行，现有开发 MySQL 通过追加迁移承接；不删除旧上下文或改写历史 UTC。

## 当前实现与缺口

HTTP 已要求明确目标、规范安全 revision 和 CSRF；同源运行校验覆盖读取与上下文写操作。专用 MysqlTradingContextWriter 已接管原上下文事务，保留同连接权限复核和 CAS。commit 报错返回 trading_context_commit_unknown 并销毁连接；rollback 报错返回 trading_context_rollback_unknown。两者均不自动重试。

当前仍由 MysqlTradingRepository 委托该适配器，TradingReadRepository 尚含 saveContext。专用回执、审计原子性、首次写入的串行锁和前端恢复尚未完成。原 owner 查询使用已存在的 trading_account_ownerships 表，不属于缺表；仍需结合账户根合同复核活动用户、账户删除、所有权区间与锁顺序。

## 目标端口与事务

1. 从只读端口移除 saveContext。独立应用写端口接受 userId、requestId、action、expectedRevision 和明确目标；action 区分选账户、进观摩、退观摩。身份来自认证上下文，不能来自 body。
2. requestId 通过 Idempotency-Key 传输。规范化命令与合同版本形成稳定摘要；同用户同键同摘要复用原回执，同键异摘要返回409。expectedRevision 必须纳入摘要，不能在确认重试时换成最新版本。
3. 新增本域专属变更回执表，唯一键为用户和requestId，保存请求摘要、动作/目标、前后revision、执行结果及UTC记录时间。回执同时承担上下文变更审计，不在成功后另写一笔非原子日志；审计查询通过明确的只读合同接入。
4. 短事务先取得可稳定锁定的用户根，确认用户活动，串行化不存在上下文行时的首次写入；随后检查回执、上下文版本及目标权限。正式锁顺序须与账户归属变更、观摩撤权和用户停用流程逐项核对，不仅依赖文档声明。
5. 新请求在同一连接内复核权限，写上下文和变更回执，再commit。回执写入失败必须回滚上下文。已有回执只提供该请求的历史结果，不再写上下文，不递增revision；读取回执仍需认证和用户作用域检查，返回内容不包含其他账户私有事实。
6. commit异常保留请求键与正文；先确认原请求，禁止换键重放。恢复依赖持久回执，不能用“当前上下文刚好相同”证明原请求已提交，也不能据当前状态不同断言原请求失败。

## 前端恢复

客户端以一个明确操作保存键、动作、目标和expectedRevision，确认阶段沿用这些值。网络失败、提交未知、成功正文解析失败均进入待确认状态；不得自动生成新键或自动改写版本。

原请求历史回执与GET当前上下文分别处理：回执证明原请求结果，GET决定当前展示。即使历史请求成功，若用户已在其它标签页切换，不能把历史回执当作最新上下文再次应用。恢复读取失败时保持待确认提示，不能继续使用不明账户执行后续操作。

所有确认、GET、快照与实时订阅继续受已有请求版本及账户作用域保护；迟到恢复结果不能覆盖后发用户动作。新的主动选择必须有明确的新命令，不能由后台恢复过程隐式发起。

## 交付与验收

先追加表定义和增量注册、验证现有库兼容；再实现独立写端口与同事务回执，接通HTTP和真实前端客户端；最后在恢复副本演练并为当前dev_vue生成专属计划。已执行迁移不可修改。

必要行为包括：首次并发写入、同键同体、同键异体、旧revision、权限撤销、回执失败回滚、commit确认丢失、独立重连恢复、恢复期间另一标签页新写入、前端迟到响应、刷新及重复点击。离线适配器测试、真实MySQL事务和浏览器流程分别记录。

第一轮复审：明确写端口、回执唯一所有者和审计原子性，防止继续向通用repository堆积职责。第二轮复审：区分历史操作与当前上下文，保留未知结果，纳入首次插入串行化和跨域锁顺序。剩余风险是这些持久化与前端恢复尚未实施，当前CAS冲突不等于幂等恢复完成。


## 第七十批：命令与回执结构

新增ContextWriteCommand/ContextWriteReceipt和独立ContextWritePort，暂未替换旧saveContext调用。命令为规范小写UUID请求键、明确动作/目标、正整数用户与安全revision；固定顺序的版本化指纹输入包括全部字段。基础设施负责SHA-256，领域不依赖crypto或MySQL。目标保留原始ASCII opaque ID，拒绝空白归一化带来的同键歧义。

041新增trading_context_changes_v4：用户+请求键主键、用户+结果revision唯一键、请求摘要、动作和目标、前后版本、结果上下文及UTC时间；CHECK约束版本递增、动作/结果对应、观摩只读和目标互斥。历史目标以191字符ASCII精确保存，不建立指向可变账户/频道的外键，避免删除或改名抹去回执；用户外键仍限制硬删除。实际写入时必须验证目标真实性，文本存储不授予任何权限。

新loader只追加165步并绑定原164步注册摘要；尚无执行协调器、MySQL规范DDL采集或持久化适配器接线，不属于已升级数据库。3项命令行为测试与1项历史注册不变测试通过，完整server类型检查通过。

第一轮复核确认回执同时承载原操作历史和审计，未将当前上下文混入历史请求身份；第二轮复核确认字段边界、原步骤不变及NULL分支约束。真实MySQL约束行为、用户停用/归属变更锁序、回执与上下文原子写入及端到端恢复仍待下一批。


## 第七十一批：同事务命令与历史回执适配器

MysqlContextCommands实现ContextWritePort，依赖同连接ContextTargetResolver。新请求锁活动用户根、查询原回执，再锁上下文并核对revision；解析器必须使用传入连接复核当前目标且禁止网络I/O。上下文和回执同事务写入后回读验证，commit之后才返回。相同摘要重放原结果，不解析目标或再次写上下文；不同摘要返回trading_context_idempotency_conflict/409。先检查活动用户，因此历史回执不绕过用户停用。

readContextReceipt逐项验证命令摘要、用户/请求绑定、动作与结果、revision和UTC时间；历史回执读取语句再次限定活动用户。结果字段不含账户登录信息、权限证据或私有数据。解析器收到冻结命令，不能修改已经计算摘要的目标；回读结果按字段比较，不依赖对象属性顺序。

8项事务适配器测试与3项命令测试共11项通过，覆盖成功/重放、同键异体、旧版本、回执插入失败回滚、commit确认丢失后独立连接恢复、后续新写入不被旧回执覆盖、活动用户/目标拒绝、回执损坏及解析器修改命令。完整server类型检查通过。测试是有事务状态的连接fixture，未模拟真实InnoDB并发锁，不作为MySQL演练结果。

第一轮复核确认操作回执与当前上下文职责分离、同连接写入和未知提交禁止自动重试；第二轮补充持久回执内容验证与冻结命令。生产目标解析器、与归属变更/观摩撤权的锁序审计、165步实际建表、组装接线和前端确认仍未完成。旧saveContext尚未移除，不能同时启用两套无统一串行约束的写入口。


## 第七十二批：同连接目标解析与外部route快照

prepareMysqlContextTarget在事务外查询候选账户并采集Redis route，返回绑定完整命令指纹的解析器。事务内重新锁定当前owner grant、ownership interval和账户，核对活动用户、账户未删除、区间起始/结束及ownership revision；退出观摩按原账户读取顺序取最小账户ID。候选变化返回409，原本无账户则保持blocked，不根据变化静默另选目标。

个人账户的readOnly仍取现有MysqlTradingRepository.findOwnedAccount结果。该读取器在同连接上复用完整账户、终端绑定、SQL心跳和投影来源/epoch检查，lease适配器只返回事务前克隆的内存route，不在事务内访问Redis。此route是采样事实，不能证明外部终端与SQL事务原子一致；上下文仍不是交易执行授权，执行链继续独立复核。观摩进入复用authorizeOn，退出不要求旧观摩权限仍有效。

6项新增目标测试和既有账户离线、MySQL观摩、命令事务共30项通过。验证真实repository代码的在线可写、epoch不符只读、外部route对象变化不影响快照、候选/命令变化拒绝、无账户退出以及同连接观摩拒绝。完整server类型检查通过，债务110未扩大；复用本域已有repository租约类型，未新增跨域类型依赖边或修改债务基线。

第一轮复核：避免复制简化终端权限查询，保留所有权和真实投影校验。第二轮复核：外部I/O在事务前、route不可被外部对象修改、候选变化不静默通过。实际InnoDB锁序与并发、165步建表、运行组装和HTTP/前端幂等键接线仍待完成。本批未连接数据库。

## 第七十四批：165步升级状态协调

新增inspectContextChanges/coordinateContextChanges，默认只读。先验证冻结计划与全部165步日志，要求旧164步完成；新表必须匹配规范DDL，未完成时只能为空。未登记但存在的表、completed但缺表、元数据/快照不同步均拒绝。只有独立核验过的新表从旧快照投影中移除，其余未知表继续传递给旧校验；verifyPrior必须运行完整164步及嵌套历史协调器。

写入顺序为持久begin→重新完整检查→DDL→检查真实后置状态→complete→再次检查。begin/DDL/complete确认异常分别标记unknown；独立重入根据实际结构和日志恢复，DDL确认丢失不会盲目再建表。完成后允许新回执行，但依然检查完整表结构和历史验证结果。
