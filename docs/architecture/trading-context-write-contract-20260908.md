# 账户上下文写入与恢复合同

本合同接续全栈模块化方案 B/C，不表示当前幂等持久化已经完成。应用和测试本地运行，现有开发 MySQL 通过追加迁移承接；不删除旧上下文或改写历史 UTC。

## 当前实现与缺口

HTTP 已要求明确目标、规范安全 revision 和 CSRF；同源运行校验覆盖读取与上下文写操作。专用 MysqlTradingContextWriter 已接管原上下文事务，保留同连接权限复核和 CAS。commit 报错返回 trading_context_commit_unknown 并销毁连接；rollback 报错返回 trading_context_rollback_unknown。两者均不自动重试。

当前仍由 MysqlTradingRepository 委托该适配器，TradingReadRepository 尚含 saveContext。专用回执、审计原子性、首次写入的串行锁和前端恢复尚未完成。原 owner 查询使用已存在的 trading_account_ownerships 表，不属于缺表；仍需结合账户根合同复核活动用户、账户删除、所有权区间与锁顺序。

## 目标端口与事务

1. 从只读端口移除 saveContext。独立应用写端口接受 userId、requestId、action、expectedRevision 和明确目标；action 区分选账户、进观摩、退观摩。身份来自认证上下文，不能来自 body。
2. requestId 通过 Idempotency-Key 传输。规范化命令与合同版本形成稳定摘要；同用户同键同摘要复用原回执，同键异摘要返回409。expectedRevision 必须纳入摘要，不能在确认重试时换成最新版本。
3. 新增本域专属变更回执表，唯一键为用户和requestId，保存请求摘要、动作/目标、前后revision、执行结果及UTC记录时间。回执同时承担上下文变更审计，不在成功后另写一笔非原子日志；审计查询通过明确的只读合同接入。
4. 短事务先取得可稳定锁定的用户根，确认用户活动，串行化不存在上下文行时的首次写入；随后检查回执、上下文版本及目标权限。正式锁顺序须与账户归属变更、观摩撤权和用户停用流程逐项核对，不仅依赖文档声明。
5. 新请求在同一连接内复核权限，写上下文和变更回执，再commit。回执写入失败必须回滚上下文。已有回执只提供该请求的历史结果，不再写上下文，不递增revision；读取回执仍需认证和用户作用域检查，返回内容不包含其他账户私有事实。
6. commit异常保留请求键与正文；先确认原请求，禁止换键重放。恢复依赖持久回执，不能用“当前上下文刚好相同”证明原请求已提交，也不能据当前状态不同断言原请求失败。

## 前端恢复

客户端以一个明确操作保存键、动作、目标和expectedRevision，确认阶段沿用这些值。网络失败、提交未知、成功正文解析失败均进入待确认状态；不得自动生成新键或自动改写版本。

原请求历史回执与GET当前上下文分别处理：回执证明原请求结果，GET决定当前展示。即使历史请求成功，若用户已在其它标签页切换，不能把历史回执当作最新上下文再次应用。恢复读取失败时保持待确认提示，不能继续使用不明账户执行后续操作。

所有确认、GET、快照与实时订阅继续受已有请求版本及账户作用域保护；迟到恢复结果不能覆盖后发用户动作。新的主动选择必须有明确的新命令，不能由后台恢复过程隐式发起。

## 第七十一批：同事务命令与历史回执适配器

MysqlContextCommands实现ContextWritePort，依赖同连接ContextTargetResolver。新请求锁活动用户根、查询原回执，再锁上下文并核对revision；解析器必须使用传入连接复核当前目标且禁止网络I/O。上下文和回执同事务写入后回读验证，commit之后才返回。相同摘要重放原结果，不解析目标或再次写上下文；不同摘要返回trading_context_idempotency_conflict/409。先检查活动用户，因此历史回执不绕过用户停用。
