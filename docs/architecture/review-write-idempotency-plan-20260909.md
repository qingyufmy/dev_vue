# 复盘写入持久幂等实施设计

状态：设计复审完成；新增迁移源码待恢复副本验证与升级链登记，应用接线未完成。
对应总计划：full-stack-modularization-plan-20260908.md。核心优先，不扩大到前端或Bridge交互。

## 1. 现有缺口与目标

当前6个复盘写接口已有同源合同、认证/CSRF、CAS（创建除外）、事务内结果读取及提交未知处理。手工创建的scope_key只标识用户和幂等键，不证明请求正文一致；其余5项无持久回执。不能把HTTP校验或CAS冲突当成幂等重放。

目标：用户、幂等键标识一条复盘命令；相同动作、目标、原始正文和预期版本返回原始成功结果，不再次写业务表或outbox。同键任一命令字段改变返回409。每次请求及重放均重新验证当前会话、CSRF和资源访问权限。提交未知只允许保留原请求核对；不自动生成新键。

## 2. 数据与职责

追加`server/db/migrations/inplace/049_review_write_receipts.sql`。不修改已存在的012复盘基础迁移、188步已执行链或其他冻结迁移，不清空/改名/删除旧表。回执表由reviews域拥有，只有reviews基础设施可写，其他域不得导入其内部仓储。

表主键为(actor_user_id,idempotency_key)，动作共6类：create_manual_case、request_generation、create_version、confirm_version、return_case、decide_memory_update。保存request_sha256、resource_id、result_revision、result_json、result_sha256、recorded_at_utc。actor关联现有users主键；resource为review case或memory update的多态ID，不虚构单表外键。无外部请求或后台任务在事务内执行。

应用层负责构建不可变命令，原始正文必须在trim、默认值补齐、内容转换前捕获。请求摘要使用递归排序对象键的规范JSON，保持数组顺序，区分省略字段与显式null，包含动作/目标/预期版本。拒绝非有限数值、非JSON对象及无法序列化值。原始选择token只进入摘要，不存正文或日志；时间now与每次生成的request_id不得进入命令摘要。

回执存领域结果，不存HTTP meta、Cookie或选择token；HTTP每次产生自己的request_id/generated_at并按既有合同验证领域结果映射。回执JSON以同一规范序列化计算摘要，读取后校验形状、摘要、资源ID及版本，损坏时返回review_receipt_invalid/503，不重新执行业务。

## 3. 事务顺序与权限

1. HTTP验证会话/CSRF及请求合同，所有6项要求Idempotency-Key。原有If-Match保持；重放必须使用原版本，不能先拿当前版本覆盖原命令。
2. 开事务，锁定有效actor用户行，序列化同用户回执首次创建与重放；查询该用户/键回执FOR UPDATE。
3. 如有回执，先核对动作与请求摘要；命令一致后根据受信回执resource_id重新核对目标权限。案例仍归该用户且账户当前owner关系有效；记忆更新对应library仍由该用户拥有。手工复盘同样按已创建案例核对账户权限，不要求过期的选择token仍可用于首次创建。未授权不返回冻结结果。
4. 无回执时，按现有用例权限和锁序执行首次写入。案例类锁case并检查当前账户owner；记忆决策锁update/library；手工创建锁当前owner和候选，再检查策略可见性、选择token、有效期及资格。细化SQL时与Worker的既有锁序一起审查，出现死锁回滚返回错误，不增加无边界重试。
5. 业务变化、outbox、事务内结果、回执同一次commit；任何提交前异常全部回滚。提交阶段异常destroy连接，返回review_commit_unknown、retryable=false，不假定已回滚。回执写失败不得放行业务commit。
6. 重放只返回冻结结果，不重新执行fresh CAS、候选有效期、generation活跃状态或新增outbox；当前权限始终检查。result_revision可能旧于当前详情，应保留原ETag语义，另行读取详情取得当前状态。

actor行锁只是并发序列化机制，不能代替权限。当前代码仅凭case.user_id的写权限需要同时接入账户owner检查；必须补权限撤销后的首次写入与重放测试。

## 4. 旧数据兼容与升级

旧scope_key案例没有原始请求摘要和冻结回执，不能事后从当前详情推断首次返回结果。遇到旧键而无回执，返回review_legacy_receipt_unavailable/409并保留案例可读；不重写原案例、不重新排队、不合成回执。使用已有案例详情确认状态。历史数据不丢失，但旧键的精确自动重放不可证明，此边界必须写入合同说明。

新表为空不影响历史案例读取。新写实现不得在表缺失时回落到旧非幂等路径。先在恢复副本验证现有188步journal和数据，再登记后续追加步骤；048策略升级的前置结构仍按独立方案推进，不因049编号而直接向现库批量应用文件。readiness必须明确检测回执表与约束，通过后才能声称对应写接口可运行。

开发升级验收必须包含备份可恢复、原表/案例/版本/来源/金额计数不变、journal前缀一致、重跑no-op。回滚应用不得删除回执表或用户数据；旧应用不识别回执时禁止切回旧写路径继续产生副作用，保留读取用于核对。
