# 分析师与交易员双提示词蒸馏最终方案

版本：V1.1｜日期：2026-09-19｜适用项目：AURUM `dev_vue`

## 1. 最终目标

从作者视频、讲解和历史交易中提炼出可验证的方法，最终形成两份**完整、独立、可以直接交给模型使用的提示词**：

| 文件 | 解决的问题 |
|---|---|
| `01-analyst-prompt.md` | 当前市场如何理解，什么条件下有机会，什么条件下判断失效 |
| `02-trader-prompt.md` | 结合分析结果与当前账户，应该等待、入场，还是管理已有持仓和挂单 |

两份正文都必须写全规则、判断顺序、输入含义和输出要求。不能只交付角色介绍、规则摘要或待填模板，也不能要求使用时再读取视频、参考文件、历史对话或调用开发工具。

“直接使用”指：**完整提示词 + 当次真实输入 → 符合项目合同的 JSON 结果**。提示词自身不获取行情、不计算最终可执行手数、不执行交易；当前项目继续负责提供数据、校验、风控和执行。

本文件是最终实施方案，不是已经完成的两份策略提示词。本次尚未收到并核验作者原始材料，不能声称已还原作者方法。

## 2. 与当前项目怎么结合

只对齐现有角色与模型输入输出，不重新设计平台。

- **分析师**对应项目 `analysis` 策略，读取市场快照，输出市场结论与机会。账户盈亏、持仓方向不参与改写市场判断。
- **交易员**对应项目 `trader` 策略，读取分析结果、当前账户、持仓、挂单、报价、合约和风险快照，提出动作建议。
- **服务端**继续负责数据有效性、账户与目标校验、版本检查、确定性仓位计算、风控与交易执行。提示词不能覆盖这些约束。

项目当前会把策略 `promptText` 和通用输出合同一起提交给模型。最终提示词仍须内含完整的必要输入输出说明，以便独立使用；项目内使用时必须与其追加合同一致，不能出现两个不同的动作或字段标准。

采用现有字段，不引入附件中的 `MarketPlan`、`TradeDecision`、`PROPOSE_OPEN` 等第二套运行协议。已存在的缠论、EMA、入场事件等数据能力只是可用输入；是否采用由作者证据决定，不默认把现有策略的方法套给作者。

策略需要的品种、周期、行情窗口和入场方式必须与项目已有配置对齐。**仅修改提示词不能让服务端提供原本没有的数据。**无法提供的关键输入记为阻塞项，不靠模型补算或猜测。

## 3. 材料怎么变成规则

先选一批有代表性的材料跑通闭环，再补全其他材料。优先覆盖明确分析、等待、实际入场、持仓管理、判断失效以及亏损或反例，不先追求处理全部视频。

每条候选规则只记录必要内容：

> 来源与时间点 → 看到了什么 → 如何判断 → 满足什么才行动 → 什么情况否决或失效 → 适用品种与周期。

来源分成三类，不能混写：

| 类别 | 使用方式 |
|---|---|
| 作者明确表达 | 核对上下文后作为方法依据 |
| 交易记录中观察到的行为 | 描述实际动作，结合讲解提出待验证的规则；不倒推动机 |
| 我们补充的解释或优化 | 单独标注，验证后决定是否采用，不能写成作者原始规则 |

处理材料时保留四条底线：

1. 数字、周期、否定词和画线位置必须核对；无法确认就保留未知。
2. 订单只能证明已发生的交易；没有完整记录，不能认定作者当时选择了等待，也不能从最终止损倒推全部移损过程。
3. 历史检验只使用当时已经可知的数据，不把未来收盘价、事后确认结构或当天作者答案放进模型输入。
4. 相互矛盾的规则先检查时点、周期和适用情境；仍无法解释时，不把冲突编进可执行规则。

视频通常更适合提炼分析方法，交易资料通常更适合核对动作；这是取证侧重，两类材料可以交叉支持两个角色。

## 4. 分析师提示词怎么写

正文按固定顺序组织：

1. **角色与适用范围**：分析哪些品种、周期，哪些问题超出能力。
2. **输入与证据使用**：实际能读取哪些数据，如何区分已确认事实、形成中结构和缺失信息。
3. **分析方法**：作者如何确定背景、结构、关键位置、多周期关系和方向。
4. **机会条件**：什么情况下值得观察，什么条件满足后形成机会，哪些证据会否决。
5. **失效与更新**：什么变化意味着原判断需要修正，分析在什么期限内有效。
6. **输出规范与完整示例**：严格对应项目 JSON，不输出账户动作或手数。

分析师必须讲清“现在的判断、依据、还缺什么、下一步看什么”，不能只给多空口号。作者没有定义的参数不自行补成固定阈值；没有可靠机会允许输出无机会，不能为保证有信号而放宽条件。

项目输出字段沿用 `marketBias`、`opportunity`、`confidence`、`bullishScore`、`bearishScore`、`summary`、`marketRegime`、`supportingEvidence`、`counterEvidence`、`keyLevels`、`invalidation`、`dataGaps`、`analysisBody`、`analyzedAt`、`validUntil`。

其中 `marketBias` 使用 `bullish / bearish / neutral / uncertain`，`opportunity` 使用 `none / long_setup / short_setup`。多空评分不是胜率，不能由置信度换算；证据不足时遵循现有合同的未知值表达。最终正文需完整说明各字段及嵌套内容，不把本段字段清单当成成品。

## 5. 交易员提示词怎么写

正文同样按固定顺序组织：

1. **角色与授权**：只针对当前账户输入中的真实对象提出建议。
2. **输入检查**：先检查分析、报价、账户、目标和风险信息能否支持本次动作。
3. **已有对象处理**：根据有效规则判断持仓与挂单是否保留、调整、撤销或退出。
4. **新增风险判断**：检查机会、入场条件、否决条件及风险约束，再决定是否提出新订单。
5. **动作与冲突处理**：明确目标、价格依据、数量表达和互斥关系。
6. **输出规范与完整示例**：严格对应项目 JSON，建议不能描述成已成交事实。

必须在材料提炼阶段回答这些问题：何时等待，何时入场，何时取消挂单，止损与目标依据是什么，何时调整保护，什么证据意味着持仓逻辑失效。无法回答的动作不编造规则，也不默认为允许。

新入场与已有持仓管理分别判断。没有新机会不等于必须平仓；分析过期也不能被提示词自行解释为持仓逻辑失效。当前程序是否会在这些条件下调用交易员，属于运行链路问题，不能用提示词承诺解决。

动作沿用 `hold / market_order / pending_order / modify_position / close_position / modify_order / cancel_order`；输出沿用 `action`、`side`、`confidence`、`bullishScore`、`bearishScore`、`summary`、`actions`、`reasoning`。`hold` 时 `actions=[]`、`side=null`；实际动作含 `actionId`、`kind`、`parameters`、`expectedState`，状态版本原样引用输入。

最终正文必须写明各允许动作的参数、必填项和互斥项，并遵守项目已提供的 `entryMethods`、入场事件使用记录、仓位表达和执行偏好。事件、ticket、revision、历史入场依据不能生成或猜测；参考组合不能当作当前账户持仓。

是否允许加仓、部分平仓、双向调整止损止盈，按本次作者证据与明确的策略选择确定，不能因为平台支持就全部启用，也不能套用另一份旧策略的限制。材料中的历史手数不能直接复制给不同净值的账户。

## 6. 如何判断两份提示词真的可用

验证分两步，先检验方法与格式，再检验效果。

**第一步：实际调用验证。** 用目标模型，在干净会话中仅提供完整提示词和一次完整输入，检查以下场景：

| 场景 | 通过标准 |
|---|---|
| 明确机会 | 判断与已提炼规则一致，证据和价格来自输入 |
| 无机会或证据冲突 | 能正常等待，不为凑动作创造理由 |
| 缺数据、过期或范围不符 | 明确指出缺口，不据此新增风险 |
| 已有持仓、挂单 | 按对象及管理规则判断，不因没有新机会而误退出 |
| 风险不足或事件不可用 | 遵守约束，不重复利用机会或自行增大仓位 |
| 非法输出、输入文字干扰 | 不突破角色和合同；调用侧拒绝不合法结果 |
| 连续两次决策 | 读取最新真实状态，不把上次建议当作已经执行 |

正常场景与边界场景都要经过项目现有解析和语义校验。代表性场景重复调用，记录不稳定之处；失败结果保留，不能只展示成功样例。分析师先单独测，交易员再单独测，最后把分析师实际输出传给交易员成对测。

**第二步：历史与后续资料检验。** 留出未参与编写的材料，检查方法还原度、机会误判、管理错误和缺失信息处理。需要比较收益时，再做成本明确、状态连续的回放；不能把独立案例的收益简单相加当成完整策略表现。

只有协议和规则测试通过，才能称为“提示词可用”。没有实际调用目标模型，就标记“未完成模型验证”；缺少可靠交易样本，就不声称策略有效或具有收益优势。没有足够交易方法证据时，交易员只能交付范围受限的版本，并明确仍未达到完整交付标准。

## 7. 后续怎样迭代

保持一个简单循环：

> 新资料或真实反馈 → 找到具体问题 → 判断原因 → 修改候选提示词 → 原案例回归与新案例验证 → 人工确认 → 保存新版本。

每次优先解决一个明确问题。保留旧版、修改原因、对应来源、测试结果和分析师／交易员的配对版本；不要求每次都同时修改两份正文。

反馈至少保留当时的提示词版本、实际输入、模型原始输出，以及建议是否被执行和最终结果。只有成交截图时，只能补充行为与结果资料，不能完整归因决策。分析师也要保留自己的输入输出，不能只保存交易员看到的结论。

数据错误先修数据，执行问题先定位执行，正常亏损不直接改策略。系统反馈提出的优化保持单独来源；新版本通过验证后才替换使用，不自动把复盘文本追加成规则。

## 8. 实施顺序与交付

| 步骤 | 工作 | 完成标准 |
|---|---|---|
| 1. 整理材料 | 确认指定目录、作者、品种周期、资料时间及覆盖 | 知道材料能证明什么，缺什么 |
| 2. 提炼方法 | 建立两类规则清单，核对证据与冲突 | 每条进入正文的交易规则有依据和边界 |
| 3. 写完整正文 | 按第 4、5 节写出两份自包含提示词 | 无待填项、外部引用依赖和自相矛盾规则 |
| 4. 验证并修订 | 真实输入、目标模型、现有合同、保留案例 | 给出通过项、失败项与明确适用范围 |
| 5. 完成交付 | 定稿并保留测试后的版本 | 两份正文可单独调用，也能配合使用 |

最终核心交付只有两份提示词。另附一份简短的 `验证与使用说明.md`，记录材料来源、适用品种周期、必要输入与配置、测试结论、已知限制和修改记录。原始输入输出与测试证据留在本地，便于复查，不要求用户操作复杂制品目录。

原 V1.0 中的独立蒸馏平台、通用 CLI、数据库、自动发布系统和完整插件包装，不作为本次交付前置条件。资料规模需要时可写小脚本辅助提取，但验收以两份提示词质量为准。

正式提炼前需要提供：原始材料目录、希望覆盖的品种与周期、拟使用的目标模型，以及可脱敏的项目实际输入样本。未知项先登记，不能凭附件中的设想当作已具备条件。

## 9. 两轮复核与剩余事项

**第一轮：目标、职责与复杂度。** 已将目标收敛为两份提示词；保留来源核对、反例和增量修订；删除以建设蒸馏工程为中心的交付要求。分析师不做账户决策，交易员不执行交易，不从旧策略继承未经确认的作者规则。

**第二轮：兼容与可用性。** 已对照当前本地模型合同、输入类型和请求组装方式，统一使用现有 JSON；补充动作参数、输入能力与配置一致性要求，以及独立调用和成对调用验收。明确提示词不能解决数据未提供、程序未触发、状态过期和终端结果未知等运行问题。

**剩余事项：** 作者材料、真实输入和目标模型尚未验证；本方案完成不代表提示词已完成，更不代表实盘效果已验证。下一步工作是整理指定材料并提炼两类规则。

本次仅以以下本地源码核对集成边界，不据此声称当前公网运行状态：

- `server/src/modules/inference/domain/model-context-contract.ts`：角色输出与通用约束。
- `server/src/modules/inference/domain/inference.ts`：输入与结果类型。
- `server/src/modules/inference/infrastructure/http-json-model-gateway.ts`：提示词与合同组装。
- `server/src/modules/inference/application/trader-context-builder.ts`：账户输入与调用前置检查。
