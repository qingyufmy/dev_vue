## 一、保留的简单规则

管理员维护基础品种目录。公共 K 线、报价和公共指标统一由管理员账户池采集并共享；私有策略行情从策略所有者自己的账户池采集。每个池内首次按稳定账户 ID 升序选定可用来源，选中后保持，不因新账户上线、原账户恢复或浏览器切换而抢占；当前来源持续不可用时自动换源。

来源选择最小作用域为“公共池/私有用户池 + 基础品种”。一个品种的所有周期、报价及其衍生指标共用一份选源结果，不能按 API 请求、浏览用户、周期或进程各选一遍。不同品种可以选择不同账户，因为同一账户可能不提供所有品种；不需要管理员配置品种到账号的映射。

只有公共数据提供者的授权账号进入公共池；私有池只包含策略所有者当前有权访问的账号。继续使用现有账号权限，不提供任意管理员或用户之间的自动借用。前端无需新增选源设置。

## 二、发现与修订

### F1 高：每次排序取一个账户，不能保证固定来源

证据：`server/src/modules/inference/infrastructure/trading-analysis-market-source.ts:16` 每次读取候选；`:17` 逐账户尝试；`:77` 的 candidates 只有首选和在线账户排序，没有共享的当前来源。`server/src/modules/strategies/infrastructure/mysql-analysis-schedule-store.ts:34` 当前用各订阅交易账户填充 marketSourceAccountId。

后果：两个订阅或 Worker 可选择不同账户；重试也可因数据覆盖差异改变来源。置信度高，源码事实；是否在现有运行中触发未检查。

修订：单一服务端选源端口维护 currentAccountId 与单调递增 sourceGeneration。选源通过唯一作用域记录和短事务/CAS 原子更新；采集租约只负责工作者互斥，不能各自决定来源。重启恢复记录后先检查资格与路由，不直接相信旧在线状态。账户 ID 用整数语义比较，不能用字符串排序造成 10 排在 2 前。

验收：并发首次选源只产生一个结果；两个订阅及图表得到同一来源；新增/恢复账号不抢占；进程重启保持来源。

### F2 高：在线只是候选条件，不等于行情可用

证据：`server/src/modules/bridge/application/bridge-gateway-session.ts:43` 使用 45 秒连接租约；`:158` 续租。`server/src/modules/bridge/infrastructure/redis-bridge-gateway-lease-store.ts:94` 检查的是连接身份。它们不能证明某个品种存在、时钟可信或查询成功。现有分析读取器 `:19` 只判断 quote 是否存在，不能把这一检查当新鲜度证明。

修订：入选要通过有效路由、账户权限、基础品种解析及有界只读响应检查。自动交易按钮关闭不排除行情来源；有读权限即可。品种不存在只影响该品种，不排除整个账户。暂时的查询繁忙不能立即判定故障。

确认断开或权限撤销可立即重选；响应超时、持续数据故障按有界失败窗口判定，避免一次失败导致来回跳源。闭市、无新 tick、缺少历史应分别识别，不能单凭“报价时间没变”判断离线。阈值属于内部运行策略，依据现有租约及查询超时确定并测试，不增加客户配置。

验收：覆盖桥接在线但终端不可读、只读账户、闭市、单品种不存在、短暂繁忙、持续超时、权限撤销。

### F3 高：换源不能只换账号字段，旧响应会污染新缓存

证据：`server/src/modules/trading/infrastructure/mysql-trading-repository.ts:365` 当前 K 线按账户、symbol、周期读取；迁成公共逻辑键时若去掉账户而不加入来源代次，会失去原有隔离。`server/src/modules/inference/application/analysis-source-reader.ts:3` 明确历史来源证据不等于当前授权。

修订：采集任务及响应携带池、基础品种、真实品种、来源账户、sourceGeneration、connectionId/epoch。写入前检查当前代次和路由，过时代次只能留作原有证据，不能更新活动缓存。报价、K 线发布同一代次的状态；消费者换代重拉快照，不跨代沿用 revision 或 sequence。

换源后先读取新源报价与所需历史窗口，进入 ready 后供新分析使用；等待期间显示历史与“正在同步”，不声称实时。旧历史保留来源标记；同一分析窗口和指标输入禁止混合旧源/新源，所需窗口缺失时从新源补取。更早历史可以保留用于查看，但跨源分段必须能识别，不能伪装成同源连续数据。未收盘 K 线不能跨源累计成交量。

验收：A 源超时后切 B，A 的迟到响应不覆盖 B；M5/H1 同次分析一致；新源历史不足不触发错误分析；回看旧分析仍可复现原输入。

### F4 高：私有例外要按任务判定，不能按用户全局开关判定

证据：`server/src/modules/strategies/domain/strategy.ts:2` 已区分 platform/user；但 `StrategyVersion` 本身没有 scope，不能仅从版本对象猜测。`AnalysisContextBuilder` 的行情端口当前只有 userId/preferredAccountId，没有明确公共/私有来源类型。

修订：服务端依据经过授权的策略元数据，冻结本次任务的来源模式。公共策略用公共池，私有策略的行情读取用本人私有池。同一用户同时使用公共与私有策略，不互相改变来源；同一用户私有策略在相同品种下复用其私有池，不按执行账号重复采集。

混合流程按阶段保持证据：公共分析已经产出的输入和结论仍属于公共源；用户私有交易策略新读取的行情来自私有源，必须分别标注，不能给既有公共分析改标签。执行目标仍是订阅绑定账号，行情源选成另一账号不转移订单、持仓或操作权限。来源模式、池 ID 不接受浏览器任意指定；私有池不得在失败时回退公共池或其他用户池。

验收：同一用户公共和私有任务并行、两名用户相同品种隔离、私有源离线、策略权限撤销、公共分析加私有交易策略组合、顶栏切换不改变后台任务。

### F5 中：共享采集不能依赖有无浏览器打开

证据：`server/src/modules/trading/infrastructure/redis-market-demand-publisher.ts:9` 每个调用生成独立需求 ID；`:17` 续约 90 秒。这可表达浏览器需求，但单独使用不能证明后台策略需求持续存在或公共任务已去重。

修订：浏览器和策略都是需求来源；Worker 按池、品种、来源代次、周期和窗口合并工作。同一个公共报价流只向来源桥接订阅一次，服务端向消费者分发。收盘历史入 MySQL，最新报价/未收盘 K 线使用内存或 Redis 增量并在收盘时固化，不逐 tick 写 MySQL。所有消费者退出且无策略需求后才释放闲置采集；故障时有界重试，不由每个用户独立重试。

验收：百个公共消费者只产生一份源订阅；关闭网页后后台策略仍有数据；退出私有任务不关闭其他任务依赖的来源。

### F6 中：后缀匹配必须返回真实来源，失败不能拿别的品种凑数

证据：`bridge/native/workers/mt5/worker.py:1808` 已有会话内解析缓存；当前后缀函数仍有长度及字符约束，不能直接宣称 MT4/MT5 任意后缀路径已统一验收。

修订：桥接完整匹配优先，再匹配以基础品种开头的实际名称，不维护 .s/.c 白名单；返回 requestedSymbol 与 resolvedSymbol。正常单候选自动处理；异常多候选采用稳定策略并诊断记录，不新增常规用户配置。品种不支持返回明确原因，尝试池内下一候选；全池不支持显示不可用。账户或终端身份变更时清除解析缓存；黄金别名 GOLD 属于明确别名规则，不用无限前缀猜测不同资产。

验收：无后缀、.s、.c、字母后缀、切换账户、品种不存在、两个终端不同后缀；MT4 与 MT5 分别实测。

## 三、两轮复审结果

需求与复杂度复审：删除手动源选择、管理员逐品种账号配置、私有行情强绑执行账户。保留用户已经确认的粘性自动选源；来源 ID、代次、失败窗口属于内部机制，不展示为客户必须填写的设置。

并发与异常复审：对选源竞争、旧响应、闭市误判、跨源历史、私有越权和无浏览器采集给出明确边界。公共报价仍是公共行情，不恢复“用户图表必须取自己报价”的规则；实际下单的合约规格、权限及价格核验仍针对执行账户，不属于把公共数据重复采集一遍。

## 四、实施与验收顺序

1. 清理未采用的账户目录草稿接线，确定基础品种目录、选源记录、来源代次和公共/私有授权合同；仅追加经过检查的迁移。
2. 实现共享选源、租约与故障切换，先验证并发与重启。
3. 实现桥接解析、Worker 合并采集、按代次缓存及重连补窗。
4. 接入策略来源模式和前端来源状态；报价与 K 线统一切换代次。
5. 完成上述六组验收；数据或代次不一致时暂停新源发布，保留已验证历史，不回滚冻结证据。迁移/重启/部署仍按授权边界执行。
