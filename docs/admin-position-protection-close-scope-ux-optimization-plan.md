# 管理员持仓保护、完整平仓与应用范围明细优化方案

## 1. 背景与目标

管理员当前可在持仓列表中修改 AI 系统持仓的止损、止盈，也具备按原始信号关联关系完整平仓的后端能力。但现有界面存在两个认知断点：

1. 完整平仓区域只有在平仓预览成功后才显示；唯一归因失败、接口失败或安全条件不满足时直接消失，管理员无法判断是“没有功能”还是“当前不可用”。
2. “选择应用范围”只展示目标账户、目标持仓、桥接在线和安全排除四个汇总数字，无法核对本次实际会影响哪些账户和持仓。

本次优化目标是：让管理员在提交前明确知道“能否平仓、为什么”“保护价会应用到谁、为什么纳入或排除”，同时完整保留现有唯一归因、预览哈希、Bridge 实时校验、幂等、执行顺序和审计要求。

## 2. 已核实现状

### 2.1 已有能力

- 持仓列表已有独立“编辑保护”和“平仓”操作。
- 编辑保护弹窗支持当前持仓或同一信号下系统持仓的同步修改。
- 保护价预览已返回 `targets`、`affected_users`、`affected_positions`、`online_users`、`exclusions` 和 `preview_hash`。
- 管理员策略完整平仓已有独立预览、二次确认、任务执行、订阅用户先关、管理员源仓最后、失败目标重试与结果对账流程。

### 2.2 当前问题

- 前端调用完整平仓预览失败后静默吞掉异常，整个危险操作区域保持隐藏。
- 完整平仓入口位于较长弹窗下部，可发现性较差。
- 保护价的四个范围数字是静态统计，没有交互语义和明细视图。
- `targets` 中已有 `login_account`、`ticket`、`bridge_connected` 和合并后的 `user_label`，但没有稳定区分昵称与账户名称/邮箱。
- `multiple_position_sources` 等部分排除项只含 `user_id`、`ticket`、`reason`，不足以直接展示可核验身份。

## 3. 产品与交互原则

1. **职责分离**：保护价修改与完整平仓继续是两条独立流程，不在“保存修改”中增加平仓开关。
2. **危险操作可见但受控**：平仓能力始终可发现；不可用时显示明确原因，不通过隐藏制造误解。
3. **一个范围入口**：不为四个数字分别创建四个弹窗，使用一个统一的“查看范围明细”渐进展开区域。
4. **执行前可核验**：展示账号、昵称、票号、桥接状态、纳入/排除状态及原因，汇总数字必须与明细一致。
5. **安全规则不降级**：UI 优化不得绕过后端唯一归因、Magic、账户归属、实时持仓、预览哈希和幂等校验。
6. **状态可解释**：加载、可用、不可用、失败、数据变化、执行中和完成均提供中文原因与下一步。

## 4. 目标界面结构

### 4.1 弹窗头部与当前持仓

- 标题继续使用“编辑持仓保护价”，说明文字明确该主流程只修改 SL/TP。
- 在“确认当前持仓”摘要右侧增加次级危险入口：`完整平仓…`。
- 入口采用三态：
  - `正在核对平仓范围…`：禁用并显示加载状态；
  - `完整平仓…`：后端确认可唯一归因后可点击；
  - `暂不可完整平仓`：禁用，但可展开查看原因并提供“重新核对”。
- 点击可用入口后，才在当前弹窗内展开现有完整平仓确认区，并自动滚动到该区域；默认不一次性展示长表单。
- 不在列表“平仓”按钮和弹窗入口之间复制业务逻辑，两者统一调用同一预览与执行流程。

### 4.2 完整平仓不可用状态

不得继续静默隐藏。根据后端错误码显示中文说明，例如：

- 无法唯一关联来源信号：当前持仓存在多个或缺失来源记录；
- 持仓已不存在：刷新当前持仓后重新检查；
- 不是系统持仓或 Magic 不匹配：不允许使用批量策略平仓；
- 账户归属已变化：重新获取账户与 Bridge 状态；
- Bridge 离线：连接对应交易终端后重新核对；
- 网络或服务异常：保留当前编辑内容，允许重试平仓预览。

错误详情只用于解释平仓可用性，不得阻断普通 SL/TP 修改。

### 4.3 应用范围汇总与明细

- 保留四个汇总指标，但增加统一的 `查看范围明细` 按钮。
- “目标账户”和“目标持仓”可作为同一明细入口的辅助点击热区。
- “桥接在线”不单独打开弹窗，在统一明细中用状态列解释。
- “安全排除”仅在数量大于 0 时可点击，并打开同一明细后定位到排除项；为 0 时保持静态展示。
- 明细优先在当前 section 内展开，不叠加第二层 modal。桌面端使用紧凑表格，窄屏转换为逐账户列表。

建议字段：

| 字段 | 说明 |
| --- | --- |
| 用户 | 昵称优先，同时保留账户名称或邮箱辅助识别 |
| 交易账户 | 登录号；管理员页面可显示完整值，普通日志仍按既有规则脱敏 |
| 持仓 | 品种、方向、票号 |
| Bridge | 在线、离线或状态未知 |
| 本次处理 | 纳入、排除、仅当前源仓 |
| 说明 | 发起账户、同一信号关联、安全排除原因等 |

列表默认顺序：发起账户第一，其余已纳入目标按用户和票号排序，排除项最后。账户有多笔持仓时保留逐笔记录，避免“账户数”和“持仓数”混淆。

### 4.4 文案调整

- `目标账户`：本次将尝试处理的去重账户数。
- `目标持仓`：预览中可执行的持仓数。
- `桥接在线`：目标账户中当前 Bridge 在线的账户数。
- `安全排除`：发现但未纳入执行的目标数。
- 范围明细顶部说明：`执行前仍会重新核对账户归属、Bridge 和真实持仓；预览不代表已经执行。`

## 5. 后端数据契约优化

### 5.1 保护价预览

在不破坏现有字段的前提下，为每个 `target` 和可识别的 `exclusion` 补充：

- `nickname`
- `account_name` 或 `email`
- `user_label`（保留兼容）
- `login_account`
- `bridge_connected`
- `inclusion_status`: `included | excluded | source_only`
- `reason_code`
- `reason_label`（也可由前端统一映射，但必须覆盖所有错误码）

排除项查询应补齐用户与当前账户快照；如果身份无法安全确定，显示“用户 ID + 票号”，不得猜测账号。

### 5.2 完整平仓预览

- 成功响应保持现有 `preview_hash`、`targets`、`exclusions` 和执行顺序。
- 失败响应必须保留稳定错误码和可用于 UI 映射的安全详情。
- 前端不得把预览失败转换成“功能不存在”；仅记录完整错误到内部日志，用户界面显示中文可行动说明。
- 普通保护价预览和平仓预览互相独立，任何一方失败不得阻断另一方。

### 5.3 汇总一致性

服务端统一计算汇总，前端不从不同来源拼接：

- `affected_users` 等于纳入目标中去重用户数；
- `affected_positions` 等于纳入目标持仓数；
- `online_users` 等于纳入目标中 Bridge 在线的去重用户数；
- `exclusions.length` 等于明细中的排除记录数。

预览哈希继续只包含影响执行身份与目标的稳定字段；纯展示字段变化不得造成无意义的哈希失效。

## 6. 前端状态模型

新增或明确以下独立状态：

- `positionProtectionPreviewState`: `idle | loading | ready | error`
- `scopeDetailsExpanded`: 布尔值
- `adminStrategyClosePreviewState`: `loading | available | unavailable | error`
- `adminStrategyCloseUnavailableReason`
- `adminStrategyCloseExpanded`: 布尔值

切换“同步同一信号”时：

1. 锁定开关并请求最新范围预览；
2. 原明细保留骨架而不是清空整个弹窗；
3. 成功后原子更新汇总和明细；
4. 失败则恢复原开关状态与原预览，并显示中文错误；
5. 请求返回顺序异常时只接受当前 ticket 与当前 scope 对应的最新版本。

## 7. 可访问性与响应式要求

- 所有可点击指标使用原生 `button`，支持键盘、`:focus-visible`、`aria-expanded` 和明确名称。
- 数字本身不依赖颜色表达是否可点；使用“查看明细”文字或箭头建立可发现性。
- 展开区域使用 `aria-controls` 和 `aria-live="polite"`，不强制抢夺焦点。
- 危险操作必须使用文字、图标和危险色共同表达。
- 820px 以下四项汇总改为 2×2；范围表格转换为单列明细，避免横向溢出。
- 展开/收起仅使用 150–200ms 的状态过渡，并支持 `prefers-reduced-motion`。

## 8. 实施步骤

### 阶段一：错误与数据契约

1. 完善保护价预览目标、排除项身份字段和稳定原因码。
2. 明确完整平仓预览的可用/不可用错误映射。
3. 保证两个预览接口失败互不影响。
4. 增加汇总一致性和无信息泄露测试。

### 阶段二：范围明细

1. 在“选择应用范围”加入统一明细入口和展开容器。
2. 实现纳入、离线、排除和仅源仓状态展示。
3. 增加安全排除定位行为、加载态、空态和失败态。
4. 实现键盘操作、焦点样式和窄屏布局。

### 阶段三：完整平仓入口

1. 将平仓预览从“成功才显示整块区域”改为“始终显示入口状态”。
2. 可用时按需展开既有危险确认区。
3. 不可用或失败时展示原因与重新核对按钮。
4. 复用现有预览哈希、二次危险确认、任务进度和失败目标重试。

### 阶段四：联调与回归

1. 校验列表平仓入口和弹窗入口使用同一业务链路。
2. 校验切换同步范围、快速重复请求和持仓实时变化。
3. 校验源仓、订阅目标、离线账户、重复归因和已平仓目标。
4. 在桌面宽屏、820px 和窄屏断点进行视觉与键盘回归。

## 9. 测试方案

### 9.1 后端测试

- 单一来源系统持仓可生成保护价及完整平仓预览。
- 多来源、缺失来源、Magic 不匹配、Bridge 离线和真实持仓不存在返回稳定错误码。
- `targets` 和 `exclusions` 均包含允许展示的身份与原因字段。
- 汇总数字与明细严格一致。
- 展示字段变化不改变预览哈希；执行目标变化必须改变哈希。
- 提交时预览过期仍被后端拒绝，前端要求重新核对。

### 9.2 前端测试

- 平仓预览成功、不可用、网络失败均有可见入口和正确说明。
- 平仓预览失败不影响保护价保存。
- 范围明细只使用一个展开区域，不生成四个独立弹窗。
- 排除数为 0 时不可误导为可点击；大于 0 时可定位到排除明细。
- 快速切换同步范围时旧响应不会覆盖新响应。
- 所有状态可通过键盘访问，焦点顺序合理，Escape 行为不误提交。

### 9.3 浏览器验收

- 管理员能在 3 秒内找到完整平仓入口并判断其当前是否可用。
- 管理员能在提交保护价前确认具体账户、昵称、票号和排除原因。
- 页面不出现嵌套 modal、横向溢出、重复主操作或长内容导致的入口不可见。
- 执行后结果仍按账户/票号展示，并区分成功、失败、跳过和待对账。

## 10. 验收标准

1. AI 系统持仓的编辑弹窗始终可见“完整平仓”能力状态。
2. 平仓不可用时至少提供一个明确中文原因和下一步，不再静默隐藏。
3. 四个范围数字对应同一个可核验明细视图，不增加四个重复弹窗。
4. 明细至少显示用户昵称或账号标识、交易账户、票号、Bridge 状态、纳入/排除状态和原因。
5. 汇总、明细、提交目标和最终执行结果可以按用户与票号相互核对。
6. 现有唯一归因、Magic、账户归属、实时持仓、预览哈希、幂等和审计保护全部保留。
7. 普通保护价修改不因完整平仓预览失败而不可用。
8. 自动化测试、桌面及窄屏浏览器回归通过，无新增控制台错误。

## 11. 非目标

- 不修改 AI 模型持仓管理或退出判断逻辑。
- 不改变订阅用户与观摩源的执行顺序和归属规则。
- 不允许通过 UI 绕过后端安全校验。
- 不把保护价修改和平仓合并为一次提交。
- 不新增四个独立统计弹窗，也不重写已有任务执行框架。

## 12. 风险与控制

- **身份信息过度暴露**：仅管理员接口返回所需字段，审计日志与普通用户页面继续按现有脱敏规则处理。
- **预览与提交间状态变化**：保留预览哈希并在执行前再次查询实时账户和持仓。
- **弹窗进一步变长**：完整平仓和范围明细默认折叠，按需展开；危险操作展开时收敛无关内容。
- **双入口行为分叉**：列表入口与弹窗入口复用同一函数、接口和状态机。
- **错误码遗漏**：建立集中中文映射与未知错误兜底，同时保留内部可追踪码但不直接暴露给用户。

## 13. 方案复审记录

### 第一次复审：业务与安全边界

- 确认方案没有把完整平仓混入保护价保存，也没有放宽唯一归因、Magic、账户归属、实时持仓、哈希和幂等要求。
- 将“直接显示完整平仓表单”调整为“始终显示能力入口、按需展开危险确认区”，降低误触并提高可发现性。
- 明确完整平仓预览失败不得阻断普通保护价流程。

### 第二次复审：信息架构与过度设计

- 否决四个统计数字分别打开四个弹窗，收敛为一个范围明细展开区。
- 将“桥接在线”保留为状态列而非独立入口；仅安全排除大于 0 时提供定位动作。
- 复用现有目标预览和执行任务，不新增第二套目标解析或平仓执行系统。
- 剩余实施风险主要是排除项身份字段补齐、旧错误码覆盖率和窄屏长列表表现，已纳入测试与验收。
