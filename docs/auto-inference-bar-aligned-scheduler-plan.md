>
> 目标分支：`dev_codex`
>
> 方案基线：`7c53d88343038262a50d11df6a4143176712d742`

## 1. 结论

建议将自动推理从当前的“本轮完成后再等待完整配置间隔”，调整为“按可信 MT4/MT5 终端服务器时间的固定时间槽运行”。

最终目标语义如下：

- 策略配置为 5 分钟时，在终端时间 `xx:00、xx:05、xx:10……` 的边界之后运行。
- 策略配置为 10 分钟时，在终端时间 `xx:00、xx:10、xx:20……` 的边界之后运行。
- 默认在边界后等待 3 秒再准入，避免在第 0 秒读取到尚未推进的报价或当前柱状态。
- 上一轮跨过下一个时间槽时，错过的时间槽直接丢弃，不补跑、不排队、不连续追赶。
- 同一“策略 + 标准品种 + 时间槽”最多产生一次模型任务；进程重启、Redis 丢失或多实例竞争均不得重复请求模型。
- 失败退避、市场休市、Bridge 离线、可信时钟缺失等安全条件继续优先于时间槽。

这是一项调度基础设施调整，不修改策略提示词、缠论算法、模型输出合同、风控规则、订单逻辑或 Bridge 交易语义。

## 2. 当前问题与证据

### 2.1 当前行为

当前调度器在每轮推理、持久化和分发全部结束后，调用 `completionIntervalCooldownSeconds()`，从完成时刻起再等待完整的 `interval_minutes`。

当前行为同时由以下三层保证：

1. `server/routes/ai/scheduler.js` 的运行时完成后冷却。
2. Redis `auto:scheduler:cooldown:*` 冷却键。
3. `checkAutoModelTaskGate()` 根据上一任务 `completed_at_utc_msc + interval` 实施的持久化门禁。

因此只修改 `setTimeout()` 或下一次运行时间不足以改变系统语义；Redis 或服务重启后仍会被旧的任务门禁挡住。

### 2.2 虚拟机近期样本

2026-08-28 对虚拟机最近 9 次成功推理的只读抽样结果：

- 平均请求大小：约 130.2 KiB。
- 平均响应大小：约 368.1 KiB。
- 每轮模型流量合计：约 498.3 KiB。
- 平均启动间隔：392.3 秒，即约 6 分 32 秒。
- 每轮完成后到下一轮启动：约 300.5～300.7 秒。
- 实际频率：约 9.18 次/小时，而严格 M5 对齐应为 12 次/小时。

样本启动时刻包括：

`16:50:07、16:56:35、17:03:03、17:09:16、17:16:45、17:23:14、17:29:37、17:36:08、17:42:25`

这些时刻持续漂移，不对应 M5 收盘边界。若一轮在 `17:29:37` 冻结行情，它仍看不到 `17:30` 才结束的 M5 K线；下一轮到 `17:36:08` 才会处理该结构，触发证据可能延迟超过 6 分钟。

### 2.3 与当前策略的关系

当前 H1 主判策略的入场链路最终依赖“已收盘 M5 触发”，M1 EMA34 是候选方向确定后的过滤条件。自动推理虽然以 H1 作为主要行情周期之一，但日内决策节拍需要跟随 M5 已收盘证据。

因此，M5 边界对齐能改善的是：

- 每根新 M5 收盘后的分析及时性。
- 不同推理样本之间的决策点一致性。
- 历史复测与实时推理的时间点可比性。
- 避免因模型耗时变化而随机跳过某些 M5 收盘点。

它不能直接修复或替代：

- 缠论结构计算正确性。
- 策略门槛是否合理。
- 模型推理耗时过长。
- 请求体和响应体过大。
- 模型是否一定给出买卖结论。

## 3. 目标、非目标与约束

### 3.1 实施目标

1. `interval_minutes=N` 表示相邻计划时间槽相隔 N 分钟，而不是“上一轮完成后休眠 N 分钟”。
2. 5、10、15、30、60 分钟等常用值必须落在用户直观理解的终端时间边界。
3. 运行时间不得由 VM 本地时间、北京时间或固定 UTC 偏移代替终端服务器时间。
4. 慢推理期间不并发启动同一策略和品种的新一轮模型请求。
5. 错过的时间槽不得补跑。
6. Redis 故障、服务重启、多进程竞争后，同一时间槽不得重复推理。
7. 行情尚未推进到应有的已收盘K线时，不得向模型提交本时间槽请求。
8. 前端继续使用现有 `interval_minutes` 配置，不要求用户再配置额外的 M5 专用选项。

### 3.2 非目标

- 不修改任何策略提示词。
- 不把 M5 写死为所有策略的固定周期。
- 不调整 DeepSeek 模型配置、思考模式、输出预算或流式协议。
- 不做提示词/K线数据瘦身。
- 不调整自动下单、独立风控、仓位档位或订单幂等。
- 不增加失败后的模型重试次数。
- 不在本方案阶段部署、重启或修改线上数据库。

### 3.3 必须保留的安全合同

- 一个策略和标准品种同一时刻最多一轮在途推理。
- 活跃或状态未知的模型任务继续阻止新的服务商请求。
- 模型结果超过有效期时继续只保留历史，不允许进入下单链路。
- 市场休市、报价停滞、Bridge 离线、部署排空和维护围栏继续阻止新一轮准入。
- 失败退避长于正常间隔时，使用更长的失败退避。
- 尚未提交服务商请求的行情/Bridge前置失败可以短周期复查，但只能在有效时间槽准入窗口内提交模型。

## 4. 时间语义定义

### 4.1 时间源

调度边界使用当前策略实际行情来源对应的：

`terminal_instance_id + broker_server + login + timezone_offset_minutes + clock_status`

要求：

- 必须通过现有 `trustedTerminalClock()` 判断。
- 时钟来源、偏移、状态和采样时间进入调度审计字段。
- 终端时钟不可用时，调度器保持暂停状态 `terminal_clock_unverified`，不得回退到 VM 时间或固定 UTC+3。
- 首次连接阶段如果现有系统允许同经纪商观摩源引导时钟，只沿用现有 `observer_bootstrap` 边界，不新增更宽松的回退。

### 4.2 时间槽

定义：

- `interval_ms = interval_minutes × 60,000`
- `terminal_now = utc_now + timezone_offset_minutes`
- 时间槽边界按终端时间对 `interval_ms` 取整。
- `slot_boundary_utc_msc` 为边界换算回 UTC 的时间。
- `slot_eligible_at_utc_msc = slot_boundary_utc_msc + boundary_grace_ms`

默认参数：

- `boundary_grace_ms = 3,000`
- `admission_window_ms = 30,000`
- 行情就绪复查间隔：1～2 秒，最多持续到准入窗口结束。

示例：

| 间隔 | K线/时间槽边界 | 允许开始准入 |
|---|---|---|
| 5 分钟 | 12:05:00 | 12:05:03 起 |
| 10 分钟 | 12:10:00 | 12:10:03 起 |
| 15 分钟 | 12:15:00 | 12:15:03 起 |

### 4.3 准入窗口

一个时间槽仅在以下窗口允许开始：

`[slot_eligible_at, slot_eligible_at + admission_window_ms]`

规则：

- 调度器正常唤醒延迟数秒时，仍可进入当前时间槽。
- 服务在时间槽中段才启动、策略中途启用或上一轮刚结束时，不追赶已经过期的时间槽。
- 超过准入窗口后，直接计算下一个未来时间槽。
- 一旦在准入窗口内成功取得调度锁，本轮后续行情计算和模型推理可以继续执行，不因窗口随后结束而中止。

### 4.4 非常用间隔

所有正整数分钟仍可保持兼容；5、10、15、20、30、60 等可整除小时的值具有最直观的“整点”表现。

对于 7 分钟等不能整除小时的配置：

- 仍按终端时间连续 7 分钟时间槽计算，不静默改成 5 或 10 分钟。
- 前端显示实际“下次运行时间”，避免用户误认为它会落在每小时固定分钟数。
- 后续可单独评估是否将前端改为常用间隔选项，本次不限制已有策略配置。

## 5. 目标调度状态机

```text
启动/重建调度器
  ↓
读取订阅、策略、行情来源与可信终端时钟
  ├─ 不可用 → 短周期检查，但不创建模型任务
  ↓
计算当前/下一个时间槽
  ├─ 未到准入时间 → 等待到 slot_eligible_at
  ├─ 已超过准入窗口 → 标记 slot_missed，等待下一槽
  ↓
检查部署排空、维护、市场、Bridge、Redis
  ├─ 前置条件失败 → 在窗口内短查；窗口结束则跳过
  ↓
检查活动模型任务与当前槽幂等记录
  ├─ 上一任务仍活动 → 标记 slot_skipped_in_flight，等待下一槽
  ├─ 当前槽已消费 → 标记 slot_already_consumed，等待下一槽
  ↓
取得 Redis 分布式锁
  ↓
获取并验证已收盘行情
  ├─ 最新闭合K线未就绪 → 窗口内短查，超时跳过
  ↓
以确定性时间槽键创建 ai_model_task
  ↓
调用模型 → 校验 → 保存信号 → 分发
  ↓
完成后计算“完成时刻之后的第一个未来时间槽”
  ↓
释放锁并等待该未来时间槽，不补跑中间槽
```

## 6. 核心算法设计

### 6.1 新增纯函数

建议在 `server/routes/ai/scheduler.js` 先实现并导出测试接口：

```js
normalizeScheduleIntervalMinutes(value)
scheduleSlotAtOrBefore({ nowUtcMs, timezoneOffsetMinutes, intervalMinutes })
nextScheduleSlotAfter({ afterUtcMs, timezoneOffsetMinutes, intervalMinutes })
scheduleSlotAdmission({ nowUtcMs, timezoneOffsetMinutes, intervalMinutes,
  graceMs, admissionWindowMs })
autoInferenceSlotKey({ promptTypeId, symbol, slotBoundaryUtcMs })
nextAlignedRetryDeadline({ notBeforeUtcMs, timezoneOffsetMinutes,
  intervalMinutes, graceMs })
```

返回对象至少包括：

```json
{
  "mode": "bar_aligned_v1",
  "slot_boundary_utc_msc": 0,
  "slot_boundary_terminal_msc": 0,
  "eligible_at_utc_msc": 0,
  "window_expires_at_utc_msc": 0,
  "next_eligible_at_utc_msc": 0,
  "status": "before_slot|admissible|missed"
}
```

纯函数不得读取系统全局状态，便于覆盖 UTC、终端偏移、DST变化、秒和毫秒边界测试。

### 6.2 确定性时间槽键

当前 `cycleId` 使用 `${strategy:symbol}:${Date.now()}`，相同时间槽重启后会生成不同键。

调整为：

```text
auto-slot-v1:{promptTypeId}:{canonicalSymbol}:{slotBoundaryUtcMsc}
```

该值同时作为：

- `cycleId`
- `ai_model_tasks.idempotency_key`
- 模型任务冻结上下文中的 `schedule_slot_id`

现有数据库已具备唯一键：

`UNIQUE (task_kind, idempotency_key)`

因此本方案不新增调度时间槽表，也不需要数据库迁移。

### 6.3 持久化模型任务字段

复用现有字段：

- `scheduled_at_utc_msc`：写入 `slot_eligible_at_utc_msc`，表示计划准入时刻。
- `created_at_utc_msc`：保留实际创建时间。
- `completed_at_utc_msc`：保留实际终态时间。
- `idempotency_key`：写入确定性时间槽键。
- `domain_id`：继续使用 `strategyId:canonicalSymbol`。

在 `frozen_context_json` 增加：

```json
{
  "schedule_mode": "bar_aligned_v1",
  "schedule_slot_id": "auto-slot-v1:1:XAUUSD:...",
  "schedule_interval_minutes": 5,
  "slot_boundary_utc_msc": 0,
  "slot_boundary_terminal_msc": 0,
  "slot_eligible_at_utc_msc": 0,
  "cycle_started_at_utc_msc": 0,
  "slot_start_lag_ms": 0,
  "terminal_timezone_offset_minutes": 0,
  "terminal_clock_status": "",
  "terminal_clock_source": ""
}
```

这些字段只用于审计与恢复，不向策略提示词注入额外交易规则。

模型任务截止时间与结果有效期继续按实际冻结快照/本轮启动时间计算，不因计划槽边界而被无意延长；计划时间只负责调度身份和审计。

### 6.4 持久化任务门禁调整

`checkAutoModelTaskGate()` 从“上一终态任务完成时间 + 间隔”改为两类检查：

1. 域级在途检查：同一 `strategy + symbol` 只要存在活动或状态未知任务，就禁止当前槽启动。
2. 槽级幂等检查：当前 `idempotency_key` 已存在任何任务时，当前槽视为已消费，不再创建第二个任务。

终态任务不再产生“完成后完整 N 分钟”的通用冷却。

并发竞争的最后一道处理：

- 正常情况下 Redis 锁会使同槽只有一个创建者。
- 若发生进程切换或极端竞争，数据库唯一键仍可能让后到者得到 `ER_DUP_ENTRY`，随后触发现有冻结信封一致性检查。
- 对带 `auto-slot-v1:` 前缀且能查询到完全相同 `task_kind + idempotency_key` 的冲突，调度器将其归类为 `schedule_slot_consumed`，不记为模型失败，也不发起第二次请求。
- 不得在通用 `model-task-runtime` 中放宽冻结信封校验；该归类只能位于自动调度调用层，并且只能针对完全相同的确定性槽键。

兼容旧任务：

- 没有 `schedule_mode` 或槽字段的旧任务保持历史事实不变。
- 新调度器只在下一个有效自然时间槽启动，不将旧任务回写成新槽。
- 旧任务仍为活动/状态未知时，继续阻止新请求。
- 旧终态任务不再从部署时刻重新制造一段漂移冷却。

### 6.5 Redis锁与冷却

保留现有分布式锁和续租机制。

成功或已提交服务商请求的失败任务结束后：

1. 计算“当前完成时刻之后第一个未来时间槽”的 `eligible_at`。
2. 将 Redis cooldown TTL 设置到该时间点。
3. `next_run_at_utc` 保存同一个绝对时间。
4. TTL 秒数只用于唤醒优化，最终能否准入仍由绝对槽计算与数据库幂等共同决定。

如果 Redis finalize 失败：

- 恢复流程不再重建“完成后 N 分钟”的截止时间。
- 恢复目标改为原先已经计算并保存在内存状态中的 `next_slot_eligible_at_utc_msc`。
- Redis恢复后补写到该绝对截止时间；截止已过则重新计算下一个未来槽。

### 6.6 调度器启动、重启和策略启用

- 在准入窗口之前启动：等待当前即将到来的时间槽。
- 在准入窗口内启动：若当前槽未消费，可运行一次。
- 在准入窗口之后启动：不立即分析，等待下一槽。
- 策略在任意时刻开启时使用相同规则，不额外立即触发一轮。
- Reconciler 重建运行时状态时，必须从可信终端时钟和数据库当前槽记录恢复，不得仅依赖 Redis 剩余 TTL。

## 7. K线与报价就绪校验

### 7.1 为什么不能在边界第 0 秒直接请求模型

MT4/MT5 的新当前柱通常随边界后的第一笔报价形成。若调度器在 `12:05:00.000` 抢先读取，Bridge可能仍返回 `12:00` 作为当前柱，或者报价尚未推进。

因此采用“3秒缓冲 + 客观数据校验”，而不是仅依靠固定延迟。

### 7.2 通用锚定周期

不得在调度器中写死 M5。应复用策略的市场数据计划与 `resolveStrategyEvaluationTimeframe()`，得到本策略当前配置的客观评估周期。

当前策略配置为 5 分钟且注入 M1/M5/M15/H1/H4 时，评估周期为 M5；配置为 10 分钟时，仍以最新已收盘 M5 作为本时间槽的日内触发证据。

### 7.3 就绪条件

模型请求前至少核对：

- 终端时钟可信且来源身份未变化。
- 最新报价已经推进，不是 `market_stale_tick`。
- 评估周期的 `last_bar_closed` 状态明确。
- 最新已收盘K线开盘时间不早于该时间槽应能看到的最后一根已收盘K线。
- 缓存缺口仍按现有缺口复核逻辑处理，不因边界调度放宽。
- 同一轮所有周期继续冻结在同一个推理快照中。

未就绪时：

- 尚未创建模型任务、尚未发起服务商请求：在准入窗口内按 1～2 秒复查。
- 到达窗口上限仍未就绪：记录 `slot_skipped_market_not_ready`，等待下一槽。
- 不允许先发送旧数据给模型，再以新数据补算或自动重试。

## 8. 慢推理、失败和特殊场景

### 8.1 慢推理跨槽

示例：

- 12:05:03 启动。
- 12:10:03 时仍在运行。
- 12:10 槽记录 `slot_skipped_in_flight`，不排队。
- 12:11:20 完成。
- 下一次为 12:15:03，而不是立即运行，也不是 12:16:20。

### 8.2 成功任务

成功完成后直接等待完成时刻之后的下一个自然时间槽。

### 8.3 服务商请求已开始后失败

- 不在同一时间槽重试模型。
- 计算现有失败退避 `retry_not_before`。
- 选择不早于该退避截止时间的第一个自然时间槽。
- 连续失败指数退避可跳过多个槽。

### 8.4 服务商请求尚未开始的前置失败

- Bridge、市场状态、Redis、部署排空等检查可以保持现有短周期复查。
- 只有仍处于当前准入窗口且当前槽未消费时才可继续本槽。
- 窗口结束后转到下一槽，不以“条件刚恢复”为由立即推理。

### 8.5 `status_unknown`

- 继续禁止任何重复服务商请求。
- 即使状态确认时已经跨入后续时间槽，也不补跑被阻塞的槽。
- 状态最终恢复后，选择下一个未来自然时间槽。

### 8.6 市场休市和周末

- 休市期间不创建“空时间槽任务”。
- 继续按现有市场状态短查，以便开市后恢复。
- 开市恢复时若不在准入窗口，等待下一个自然槽。
- 周五强平窗口、维护窗口和部署排空继续高于时间槽准入。

### 8.7 系统时间跳变与DST

- 时间槽基于“UTC当前时间 + 当前可信终端偏移”计算。
- 槽任务冻结当时的终端偏移与时钟来源。
- 已创建槽的幂等身份使用 UTC 边界，不因后续偏移变化被重写。
- 偏移变化后，新槽使用新可信偏移；若时钟暂时处于校准状态则暂停准入。

## 11. 测试方案

### 11.1 纯函数边界测试

至少覆盖：

1. 5分钟：12:04:59.999 → 下次 12:05:03。
2. 5分钟：12:05:03.000 → 当前槽可准入。
3. 5分钟：12:05:33.001 → 当前槽过期，等待 12:10:03。
4. 10分钟：仅在 `:00、:10、:20……` 准入。
5. 终端偏移为 UTC+2、UTC+3、UTC+8 时，终端分钟边界一致。
6. 秒和毫秒取整无提前 1 毫秒准入。
7. DST偏移变化后，新槽可计算且旧槽ID不变。
8. 非常用间隔不被静默改值。

### 11.2 状态机测试

1. 正常成功后等待下一个自然槽，不等待“完成+N”。
2. 12:05任务运行到12:11，跳过12:10，下一次12:15。
3. 同一槽重复 tick 只启动一次。
4. 两个进程竞争时只有一个取得锁并创建任务。
5. Redis 冷却丢失后，数据库槽幂等仍阻止重复模型请求。
6. 服务重启后，当前槽已完成则不重复；当前槽未消费且仍在准入窗口可运行。
7. 活动旧任务跨槽时阻止新任务，不排队补跑。
8. `status_unknown` 恢复后进入未来槽，不立即重试。
9. provider已开始后失败，退避截止时间量化到未来自然槽。
10. provider未开始的行情失败只在准入窗口内短查。
11. finalize失败恢复到既定下一槽，不重新添加完整间隔。
12. 调度停止/部署排空期间不启动新槽。

### 11.3 行情就绪测试

1. 边界后新当前柱已出现，上一柱被识别为 closed。
2. 边界后报价尚未推进，在窗口内复查。
3. 窗口结束仍未推进，跳过而不请求模型。
4. `last_bar_closed=false` 时指标和缠论继续只使用已闭合数据。
5. M5最新闭合柱时间与槽预期一致。
6. 缺口复核、已验证源缺口和缓存回填逻辑不回归。

## 12. 观测指标与验收标准

### 12.1 功能验收

以连续至少 6 小时市场开放时段为第一阶段样本：

- 5分钟配置的计划槽为每小时12个。
- 在上一轮已完成、市场开放、Bridge在线、时钟可信的情况下，槽准入成功率 ≥ 99%。
- 实际 cycle start 相对 `slot_eligible_at` 的 p95 延迟 ≤ 5 秒，最大值 ≤ 15 秒。
- 同一槽重复模型任务数为 0。
- 跨槽慢推理产生明确跳过记录，补跑数为 0。
- 行情未就绪时发送模型请求数为 0。
- Redis重启或服务重启演练后，同槽重复请求数为 0。

### 12.2 交易数据验收

每个冻结快照应能追溯：

- 槽边界UTC与终端时间。
- 实际启动滞后。
- 最新 M5 已收盘K线时间。
- 终端时钟状态与来源。
- 策略版本、提示词哈希和行情快照哈希。

本次验收只证明调度与数据时间点正确，不以“必须产生买卖单”作为调度代码通过标准。买卖结果仍需按策略、缠论证据和完整订单链单独审计。

### 12.3 性能与带宽门槛

当前样本约 9.18 次/小时；5分钟对齐后理论为 12 次/小时，模型调用频率预计增加约 30.8%。按当前约 498.3 KiB/轮估算：

- 当前约 4.47 MiB/小时/策略品种。
- 对齐后约 5.84 MiB/小时/策略品种。
- 增量约 1.37 MiB/小时/策略品种。

灰度期间必须记录：

- 每小时模型任务数。
- 请求/响应字节。
- p50/p95/p99 推理耗时。
- 槽启动滞后。
- 跳过槽数量与原因。
- provider 429、5xx、fetch failed、status_unknown。
- CPU、内存、Redis和公网带宽变化。

若带宽或模型成本超出接受范围，应单独实施提示词/证据数据瘦身，不能通过恢复漂移调度来隐式降频。

## 14. 回滚方案

触发条件：

- 出现同一时间槽重复模型请求。
- 时间槽计算与终端K线边界不一致。
- Redis/重启后产生补跑或请求风暴。
- 行情未闭合却进入模型。
- 调用量、带宽或服务商错误率超过运营承受范围。

回滚动作：

1. 设置 `AUTO_INFERENCE_SCHEDULE_MODE=completion_interval`。
2. 按正常部署排空流程等待在途模型任务终态。
3. 停止旧进程并确认3000端口释放后重启。
4. 验证运行时恢复为完成后冷却。
5. 不删除已经生成的槽任务、信号或审计数据。

由于方案不修改数据库结构，回滚不需要逆向迁移；已写入的冻结槽字段作为历史审计信息保留。

## 15. 风险清单

### 中风险：调用频率和带宽增加

严格5分钟对齐会比当前漂移调度增加约30.8%的推理次数。需要以真实 `ai_model_usage_logs` 验证，而不是仅依靠理论值。

### 中风险：边界行情尚未推进

仅靠固定3秒不能覆盖所有流动性、网络或Bridge延迟，必须同时验证报价和最新闭合柱。

### 中风险：旧任务门禁与新时间槽冲突

若只修改完成回调而不修改 `checkAutoModelTaskGate()`，Redis恢复后仍会执行旧冷却。本方案要求两者同批修改和测试。

### 中风险：多进程/重启重复槽

Redis锁不足以独立证明不重复；必须使用现有数据库唯一幂等键和确定性槽ID双重保护。

### 低风险：前端时间理解偏差

管理端需要明确显示终端时间，并说明慢任务错过不补跑，避免用户把倒计时理解为完成后休眠。

### 剩余风险

- 模型本身仍可能耗时超过5分钟。
- 供应商可能在固定边界形成瞬时请求高峰。
- 当前大响应会放大对齐后的带宽增量。
- 无真实开放市场运行证据前，不能宣称生产验收完成。

## 16. 两轮方案复审

### 第一轮复审：需求覆盖、业务边界、复用与最小改动

检查结论：

- 已覆盖5分钟、10分钟自然边界、慢任务跳槽、不补跑和策略配置间隔语义。
- 初稿曾考虑新增独立 `auto_inference_slots` 数据表；复核后判定设计过度。现有 `ai_model_tasks` 已有 `(task_kind, idempotency_key)` 唯一键、计划时间和冻结上下文，可直接承担槽幂等与审计，因此移除新表和数据库迁移。
- 初稿曾考虑写死M5行情就绪校验；复核后改为复用策略市场计划与通用评估周期，避免服务端引入当前策略专属规则。
- 保持提示词、缠论、模型合同、风控、订单和Bridge不变，修改范围集中在调度器、测试、状态展示和长期规范。
- 增加30秒准入窗口，避免服务事件循环或Bridge出现数秒抖动就整槽漏跑，同时仍禁止中途追赶。

第一轮调整后结论：范围符合需求，未引入不必要的策略专用逻辑或数据库结构。

### 第二轮复审：兼容、并发、时间、异常、测试与回滚

检查结论：

- 仅依赖Redis锁无法覆盖Redis丢失与进程重启，已增加确定性数据库槽幂等键。
- 数据库唯一键竞争可能触发现有冻结信封冲突；已明确只在自动调度调用层把“完全相同确定性槽键已存在”归类为槽已消费，不放宽通用模型任务幂等校验。
- 仅调整成功路径会在失败、`status_unknown` 和 finalize恢复路径重新产生漂移，已统一要求所有下一次模型准入时间量化到未来自然槽。
- 终端偏移可能变化，已要求每槽冻结UTC边界、终端边界、偏移、状态和来源；时钟未验证时失败关闭。
- 慢任务不能在完成后立即追赶，已明确“跨槽跳过，下一未来槽运行”。
- 模型请求尚未开始的短查若不限制准入窗口，可能在12:07恢复后错误启动12:05槽；已限制前置短查只能发生在槽窗口内。
- 灰度若直接全量切换，约30.8%的调用增长可能放大带宽问题；已增加环境开关、影子阶段、虚拟机单策略验收和完整回滚步骤。
- 初稿要求首次提交就替换旧默认测试并更新 `AGENTS.md`，与阶段 A 仍以旧模式为默认相矛盾；已调整为双模式测试，阶段 C 正式切换默认值时再更新最终合同。
- 无数据库迁移降低回滚风险；切换阶段必须确保代码默认值、测试默认断言、前端说明和 `AGENTS.md` 在同一发布批次保持一致。

第二轮调整后结论：方案可实施；未发现仍需先解决的架构阻塞。剩余主要风险为真实供应商耗时、边界行情推进速度和调用/带宽增量，必须通过虚拟机开放市场灰度验证。
