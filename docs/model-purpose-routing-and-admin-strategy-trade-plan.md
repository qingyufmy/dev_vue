## 1. 结论

本需求应拆成 **2 个正式功能方案、4 个实施批次**，不建议合并成一次大改：

1. **方案 A：按业务用途选择模型**
   - A1：统一模型用途路由与兼容迁移；
   - A2：模型管理用途选择、继承来源与运行时可观测性。
2. **方案 B：管理员策略交易全生命周期**
   - B1：管理员选择策略并创建、预览、确认、分发下单；
   - B2：按本次策略指令批量修改止盈止损、完整平仓、重试与对账。

方案 A 与方案 B 没有业务依赖，可分别实施和验收。管理员手动策略下单本身不调用模型，不应等待模型用途路由完成。

## 2. 需求整理

### 2.1 模型管理

用户期望“每个需要用模型的地方，都可以选择不同模型”。落到当前系统，应定义为：

- 平台和个人模型管理可按业务用途配置不同默认模型；
- 每个策略现有的模型绑定继续作为该策略的分析模型，不在首期扩展为“每策略 × 每用途”的复杂矩阵；
- 用户私有策略只能绑定该用户拥有且已验证的模型；
- 任务创建后冻结实际使用的模型，重试、输出修复和结果落库不得中途切换；
- 显式绑定失效时失败关闭，不得静默改用其他模型产生费用或改变交易结论；
- 管理端必须展示“配置模型、继承来源、最终生效模型、最近运行结果”。

### 2.2 管理员策略下单

管理员需要：

- 选择一个已启用的平台策略；
- 填写方向、入场方式、品种、止损、止盈、交易手数、有效期和下单原因；
- 下单前看到准确的目标用户预览及排除原因；
- 确认后向该策略的有效执行订阅用户创建分发记录；
- 每个用户仍使用自己的账户、报价、合约规格、风险限额和 Bridge；
- 查看每个用户的成功、拒绝、离线、过期、状态未知和对账结果；
- 后续按这次策略指令的精确成交归因批量修改止盈止损或完整平仓；
- 对失败目标进行重新预览后重试，不重复执行已成功目标。

“编辑持仓”在 MT4/MT5 中不能表示修改开仓价或方向。首期明确限定为：

- 修改止损；
- 修改止盈；
- 完整平仓。

部分减仓、加仓、改变持仓方向和净持仓拆分均不纳入首期，避免把不同来源的成交量误当作一笔可编辑持仓。

## 3. 当前系统核对结果

### 3.1 已确认可复用能力

1. 模型档案已经统一保存在 `ai_model_profiles`，带所有权、平台/用户范围、加密凭据、能力确认、默认模型和使用日志。
2. `resolveAiTaskModel({ userId, strategyId, usage })` 已支持手动分析、自动推理、复盘、记忆压缩、一致性检查和模型评测等用途。
3. 平台策略和私有策略已有 `model_profile_id`，管理端和用户策略编辑器已经能让不同策略绑定不同模型。
4. 显式绑定模型不可用时，现有解析器会失败关闭，不会静默回退到另一模型。
5. 自动共享推理已有成熟的“冻结订阅者集合 → 写入共享信号和逐用户交付 → 逐用户校验订阅、时段、Bridge、交易发送权限、报价和风控 → 订单意图 → Bridge → 成交归因”链路。
6. `order_intents` 已提供幂等、发送前状态、状态未知对账和风险决策关联。
7. `signal_outcomes` 已能将系统持仓关联到信号、交付、用户账户和精确 position/ticket。
8. 管理员已经可以从一个系统持仓出发，按相同 `signal_id` 批量修改所有关联持仓的止盈止损；已有预览哈希、持久化任务、逐目标状态、失败重试和管理员审计。
9. Bridge 已支持开仓、修改保护价和关闭持仓所需的底层交易命令；周末系统清仓也已有完整平仓与对账的可复用执行经验。

### 3.2 当前缺口

1. 一个策略只有一个 `model_profile_id`，手动分析、自动分析、日/月复盘、手动交易复盘、记忆整理和一致性检查会共同继承同一模型，不能按用途分别配置。
2. 当前 `usage` 同时承担路由、配额和日志分类，若直接把日复盘、月复盘等继续拆成更多 `usage`，会连带改变共享政策、配额和容量控制合同。
3. 模型评测已由每次任务显式选择 2–5 个模型，不需要再增加默认绑定；连接测试也天然使用正在编辑的模型。
4. 输出修复、服务商重试和任务恢复必须沿用父任务冻结模型，不属于可单独选择的业务用途。
5. 持仓管理目前是自动分析同一次模型输出的一部分，不是独立模型调用位置；本需求不应为了增加一个下拉框而拆成第二次模型调用。
6. 当前没有“管理员策略指令”这一业务实体。普通手动下单是用户本人直接下单，不能表示平台策略分发。
7. 当前自动分发由模型信号触发，不能安全地把管理员表单伪装成模型结果。
8. 现有管理员止盈止损批量任务依赖一个管理员源账户中的真实持仓作为入口；本需求已确认管理员手动分发前本人必定先形成这笔系统源持仓，因此可继续复用该入口，无需新增独立持仓管理入口。
9. 当前没有管理员按同一策略指令批量完整平仓的任务、预览和逐目标对账界面。
10. 当前周末清仓按 `Magic = 234000` 获取并关闭全部系统持仓，不区分自动信号与管理员手动分发；如果管理员分发仓继续使用系统 Magic，会被现有周末任务误平。

## 4. 方案 A：按业务用途选择模型

### 4.1 三种可选设计

| 设计 | 做法 | 优点 | 问题 | 结论 |
| --- | --- | --- | --- | --- |
| A-轻量列扩展 | 在策略表持续增加 `review_model_id`、`memory_model_id` 等列 | 初期代码少 | 字段持续膨胀；平台默认、用户默认和新用途难扩展；无法清楚表达继承 | 不推荐 |
| A-用途默认表 | 按模型所有者和用途保存一个默认模型，现有策略模型保留 | 改动小、可审计、能表达功能差异 | 不支持每策略每用途的细粒度覆盖 | **推荐** |
| A-工作流编排 | 每类 AI 任务做完整工作流节点和多模型链 | 能实现多模型复核、投票和降级 | 远超当前需求，交易结论归因复杂，实施风险高 | 暂不采用 |

### 4.2 推荐数据模型

新增最小用途默认表（最终表名在实现前与现有迁移命名复核）：

```text
ai_model_purpose_defaults
  id
  owner_user_id          平台用途默认使用 0；个人用途默认使用实际用户 ID
  purpose_key            枚举模型用途
  model_profile_id
  updated_by
  created_at / updated_at
  UNIQUE(owner_user_id, purpose_key)
```

首期 `purpose_key`：

- `manual_analysis`：用户主动行情分析；
- `auto_inference`：策略自动分析及共享信号；
- `daily_review`：日复盘；
- `monthly_review`：月复盘；
- `manual_trade_review`：手动交易复盘；
- `memory_compression`：统一策略记忆库整理压缩；
- `memory_consistency`：记忆一致性检查；

以下不建立用途绑定：

- `model_compare`：继续由每个评测任务显式选择多个模型；
- `connection_test`：继续使用当前待保存模型；
- `response_repair`、网络重试、任务恢复：强制继承父任务冻结模型。

### 4.3 兼容解析规则

保留现有 `usage` 作为配额、共享政策、容量控制和日志大类；新增 `modelPurpose` 只负责精确模型路由：

```js
resolveAiTaskModel({ userId, strategyId, usage, modelPurpose })
```

不得直接把现有 `ai_model_tasks.task_kind` 当作模型用途。当前任务运行时已经使用 `task_kind` 控制期限、队列、幂等和恢复，而且手动交易复盘当前仍使用 `manual_analysis` task kind；复用它会把执行策略与模型选择错误耦合。`modelPurpose` 是解析器语义，任务继续冻结最终 `frozen_model_profile_id`、provider、model、protocol 和 credential source。

解析优先级：

1. 当前任务允许的一次性显式模型（目前仅模型评测）；
2. 所有者对应 `modelPurpose` 的用途默认；
3. 未配置该用途时，完整调用现有解析规则，包括策略 `model_profile_id`、用户/平台通用默认和当前共享政策；
4. 无可用模型则失败关闭。

关键约束：

- 一旦命中用途默认，模型删除、停用、能力未确认或凭据不可用时直接失败，不继续调用旧回退规则；
- 模型任务创建时继续冻结 profile、provider、model、协议和凭据来源，不新增重复的任务用途字段；
- 同一任务的重试、输出修复和恢复只使用冻结模型；
- 使用日志若需要细分统计，可追加可空 `model_purpose`；旧报表仍按 `usage` 工作，容量政策不按 purpose 拆分；
- 平台策略只能绑定平台模型，私有策略只能绑定所属用户模型，沿用现有越权校验；
- 删除模型前的影响预览必须统计用途默认表，不能只检查策略单模型字段和通用默认模型；
- 用途默认未配置时直接进入完整旧解析器，保证数据库空表时行为逐字节兼容当前结果。

### 4.4 管理端交互

模型管理新增“用途分配”区域，不在首期修改策略编辑器的数据结构：

- 行：手动分析、自动分析、日复盘、月复盘、手动交易复盘、记忆整理、一致性检查；
- 每行只选择该所有者的用途默认模型，并显示未配置时会进入的现有策略/通用默认规则；
- 每个选择项显示模型名、服务商、能力状态和最近验证时间；
- “继承”必须显示具体继承来源，不能只写“默认模型”；
- 绑定失效显示阻断状态，不自动选择其他模型；
- 策略编辑器保留现有单一模型绑定，界面文案明确它是策略分析模型；
- 运行任务详情显示最终 profile、model purpose 和解析原因即可，不另建工作流编排页面。

### 4.5 明确非目标：独立持仓管理模型

当前持仓管理与自动推理共享同一次模型调用和结构化合同，因此由 `auto_inference` 模型负责。将其拆成独立模型会增加调用成本、延迟、调度竞争和结论冲突，属于新的持仓管理架构需求，不在本方案内。只有用户以后明确要求“开仓分析和持仓管理必须由不同模型分别调用”，才另写独立方案。

## 5. 方案 B：管理员策略交易全生命周期

### 5.1 业务身份

新增“管理员策略指令”实体，不使用普通 `manual` 订单来源，也不伪装成模型自动信号：

```text
admin_strategy_trade_dispatches
  id / idempotency_key
  actor_user_id
  strategy_id / frozen_strategy_version
  signal_id
  symbol / direction / entry_method
  entry prices / stop_loss / take_profit tiers
  requested_volume
  valid_until_utc_msc
  reason
  preview_hash
  status / counters
  created_at / confirmed_at / completed_at
```

管理员指令使用独立逐用户目标表，不复用 `auto_signal_deliveries`：

- 一条 `ai_signals`：`source = 'admin_strategy_dispatch'`，仅作为统一策略指令、订单结果和持仓归因的根记录；不创建 `inference_snapshot`，不进入模型质量、AI 交易复盘或模型评测样本；
- 一条管理员指令：保存人工输入、确认人、冻结策略和预览；
- 管理员本人一条源目标：`target_role = 'source'`，承载管理员源仓的订单意图、成交和后续批量操作入口；
- 每个订阅用户一条 `admin_strategy_trade_targets`：`target_role = 'subscriber'`，承载冻结订阅、账户身份、分发与执行状态；
- 每次实际下单一条 `order_intents`：管理员源仓使用 `source_type = 'admin_strategy_source'`，订阅用户使用 `source_type = 'admin_strategy_delivery'`；两者的 `source_id` 均以同一数值 `signal_id` 开头；
- 成交后写入 `signal_outcomes`，继续支持保护修改、平仓、复盘和策略归因。

`auto_signal_deliveries` 与自动推理 scheduler、离线恢复、挂单恢复、Bridge 信号列表和自动持仓管理高度耦合，而且现有信号列表会把所有含 delivery_id 的记录强制标记为 `auto_shared`。复用该表会让管理员指令被误认为模型自动信号，并可能进入自动恢复路径。新目标表只复用更底层的资格校验、风控、`order_intents`、Bridge 命令和结果归因。

不能使用 `source_type = 'manual'`，因为现有业务规则明确将普通人工订单排除在 AI/策略持仓保护和系统成交结果链之外。

### 5.2 管理员下单字段

首期支持：

- 平台策略；
- 策略允许的品种；
- 买入或卖出；
- 市价单；
- 止损；
- 一至三档止盈及默认执行档位；
- 交易手数；
- 指令有效期；
- 选填中文原因；填写时限制为 2–500 字。

管理员输入本次分发统一请求的交易手数，管理员源账户和订阅目标均使用同一请求值。每个目标仍必须经过账户归属、经纪商规格和平台风控校验；安全门可以拒绝或下调请求手数，但不能改用仓位档位重新计算。

挂单可作为 B1.1 后续子批次开放，必须额外复用挂单有效期、取消竞态和成交对账，不与首期市价单同时上线。

### 5.3 目标用户定义

“所有订阅此策略的用户”在执行层必须解释为“所有在确认时满足执行授权的有效订阅目标”，不能绕过用户配置。预览分组显示：

- 管理员本人源账户及预计源订单；

- 策略订阅总数；
- 有效执行订阅数；
- 品种不匹配；
- 套餐失效；
- 订阅停用；
- 不在交易时段；
- 自动交易关闭；
- Bridge 交易发送关闭；
- 账户归属无效或只读；
- Bridge 离线；
- 报价或合约规格不可用；
- 风控拒绝；
- 可执行目标。

管理员确认后冻结目标集合和 `preview_hash`。确认前订阅、账户归属或关键配置变化必须要求重新预览。确认后每个目标在发送 Bridge 命令前仍要重新校验；变化的目标记为跳过或拒绝，不扩大目标集合。

执行顺序固定为：先创建同一管理员指令根记录，再执行管理员本人源订单；只有源订单已确认形成带系统 Magic、唯一 `signal_id` 和 `signal_outcome` 的真实持仓后，才开始向冻结的订阅用户分发。源订单失败或状态未知时不得向订阅用户发送新订单；状态未知必须先完成对账。

管理员不能通过本功能覆盖：

- `execution_enabled`；
- 用户自动交易开关；
- Bridge `trade_send_enabled`；
- 订阅交易时段；
- 会员资格；
- 周末新增风险保护窗口；
- 当前账户归属和 Bridge generation；
- 平台、账户及订单级风控；
- 经纪商最小距离、手数、报价和市场状态限制。

### 5.4 分发状态机

```text
draft
  -> previewed
  -> confirmed
  -> delivering
  -> succeeded | partial | failed | expired | cancelled_before_send
```

逐目标状态：

```text
pending
  -> validating
  -> executing
  -> succeeded | rejected | skipped | expired | uncertain
  -> reconciling
  -> succeeded | failed_manual_review
```

要求：

- 指令、目标、订单意图和 Bridge 命令均有稳定幂等键；
- 不持有数据库事务等待 Bridge 网络返回；
- 同一账户、同一 broker symbol 使用现有库存锁或等价跨进程租约串行化；
- 状态未知不得自动重发订单，先按订单意图和终端历史对账；
- 离线用户保留一条目标记录和可见指令历史，但首期不在恢复上线后补执行；
- 过有效期的目标终态为 `expired`；
- 已成功目标永不进入“重试失败目标”；
- 用户端清楚标记“管理员策略指令”，不能显示成模型自动结论。

### 5.5 修改止盈止损

复用现有管理员源持仓行中的“编辑保护”按钮，以及保护价任务的预览、哈希、逐目标 worker、失败重试、实时进度和审计。管理员源仓必须唯一归因到本次 `admin_strategy_dispatch` 信号，打开现有弹窗后直接启用“同步同信号关联持仓”：

1. 从 `signal_outcomes` 查询仍为 `open/closing` 的目标；
2. 校验系统 Magic、策略、原指令、当前账户归属、broker symbol 和精确 position/ticket；
3. 读取每个用户 MT4/MT5 实时持仓；
4. 对净持仓混合来源、多来源 position、人工仓和归属不明目标失败关闭；
5. 预览影响用户、持仓、在线状态和排除项；
6. 使用预览哈希确认后执行；
7. 每个目标独立记录旧值、新值、Bridge 返回和最终对账状态。

不新增独立“管理持仓”页面或入口，不扩大现有按钮到 Magic 0 普通人工仓位。后端继续从管理员本人源 ticket 和唯一 `signal_id` 出发，沿 `signal_outcomes` 解析订阅用户目标；源仓身份校验失败时整批失败关闭，各订阅用户目标仍独立校验、执行和落审计。

### 5.6 批量平仓

新增管理员批量完整平仓任务，目标解析与保护价修改共用同一个只读服务：

- 批量平仓入口放在现有“编辑保护”弹窗内，不新增独立持仓管理中心；普通“平仓”按钮继续只关闭当前普通持仓；
- 对可唯一归因到 `admin_strategy_dispatch` 的管理员源仓，关闭源仓前必须先展示“平仓本次分发关联持仓”预览，避免先关闭唯一入口后遗留订阅用户持仓；

- 只关闭本次管理员策略指令对应、归因明确且仍存续的系统持仓；
- 首期只允许完整平仓，不允许输入统一减仓手数；
- 发命令前重新读取实时持仓并校验 ticket、symbol、volume、Magic、账户归属和 Bridge generation；
- 套期保值账户按精确 ticket 关闭；
- 净持仓账户若同一 position 混有人工或其他策略来源，排除并转人工处理；
- 使用稳定 `operation_id`，超时进入 `uncertain`，按终端持仓和历史成交对账；
- 部分成功时任务为 `partial`，不重开已关闭仓位；
- 平仓成功后由既有结果归因更新 `signal_outcomes`，不得只依赖 Bridge 即时返回；
- 每次任务必须有必填原因、影响预览、二次确认和管理员审计。

### 5.7 周末强制平仓豁免

管理员本人源仓和本次分发给订阅用户的持仓都必须继续使用系统 Magic，以复用现有按钮、Bridge 安全前置校验和结果归因；不新增第二套 Magic。周末任务不能再把“系统 Magic”直接等同于“必须周末平仓”，而应先做来源分区：

1. 获取现有 `system_trade_inventory` 后，以当前用户、当前交易账户、仍为 `open/closing` 的 `signal_outcomes` 和其关联 `ai_signals.source = 'admin_strategy_dispatch'` 解析豁免 ticket；同时读取仍在执行、成功或待对账的 `admin_strategy_trade_targets/order_intents`，覆盖成交已返回但 outcome 尚未落稳的短暂窗口；
2. 同时校验 position/ticket、broker symbol、方向、系统 Magic、当前账户归属和 Bridge generation，不能只凭 comment、历史 ticket 或前端标记豁免；
3. 将库存拆成 `weekly_flatten_targets` 与 `admin_dispatch_exemptions`，周末任务只取消/关闭前者；
4. 清理后的完成判定同样只检查非豁免目标；豁免仓仍存在时任务可以正常完成，并在审计中记录豁免数量和 ticket；
5. 豁免解析所需数据库查询、账户身份或归因不可用，或者存在活跃管理员分发目标却无法唯一对应实时持仓时，对该账户失败关闭：不发送任何周末平仓命令并报警，不能把“暂时未查到 outcome”误判为普通自动仓；
6. 豁免只针对周末自动取消/平仓，不绕过周末新增风险门禁。周末保护窗口内仍禁止创建新的管理员源仓和订阅用户分发订单；
7. 首期只有市价单。以后开放管理员分发挂单时，同来源挂单也必须从周末自动取消中排除后才能上线。

此豁免不改变管理员主动批量平仓、止损止盈触发、保证金止损或经纪商强平；它只约束平台自己的 `weekly-system-flatten` 自动任务。

## 11. 第二轮方案复审：兼容性、安全与连带风险

### 11.1 检查结论

- **兼容性**：空用途默认表保持旧解析；现有策略通用绑定继续有效；`/api` 与 `/aurum-api` 兼容路径不得改变。
- **数据与迁移**：使用追加迁移和新唯一键；不回填虚构用途绑定；删除模型影响检查必须扩展，否则会留下悬空显式绑定。
- **并发与幂等**：预览哈希只解决确认前变化，执行前还必须逐目标重新校验；指令、目标、订单意图和 Bridge operation 均需稳定幂等键。
- **异常恢复**：Bridge 超时属于状态未知，不得重发；应用重启后 worker 只能认领未完成目标并尊重 fencing/lease。
- **时间语义**：指令 TTL 使用 UTC；订阅时段仍使用目标交易账户已校准的终端服务器时间；未校准时钟失败关闭。
- **安全**：管理员权限不能替代用户执行授权、账户归属和风控；用户端必须区分管理员策略指令与 AI 模型结论。
- **净持仓风险**：按 signal/outcome 归因仍可能在净持仓账户混合人工或多策略成交，必须排除而不是按估算手数修改或平仓。
- **测试**：mock 可证明状态机，但不能证明真实 MT4/MT5 命令、经纪商限制和重连对账；需测试账户验收。
- **回滚**：不能删除已创建交易任务；关闭新入口后仍需完成对账。

### 11.2 第二轮调整

1. 保持模型任务冻结最终模型身份，不让绑定变化影响已创建任务；
2. 增加确认后“不扩大目标集合”规则，避免执行期间新订阅用户被意外加入；
3. 明确离线用户只保留信号历史，管理员订单过期后不恢复执行；
4. 增加账户 Bridge generation、当前 ownership history 和 broker symbol 的发送前复核；
5. 将批量平仓限定为完整平仓，净持仓混合来源转人工；
6. 增加 `uncertain` 对账与回滚后的继续处理要求；
7. 增加后端 feature flag、测试账户灰度和前端缓存键验证。

## 12. 第三轮方案复审：需求符合度、过度设计与现有功能影响

### 12.1 审查发现

1. **高风险兼容问题：不应复用 `auto_signal_deliveries`。** 该表被 scheduler 恢复、Bridge 信号列表、挂单对账和自动持仓管理广泛使用，且现有列表会把带 delivery 的信号统一改写为 `auto_shared`。已改为管理员目标独立表，只复用底层交易网关。
2. **中风险过度设计：不应新增独立持仓管理模型批次。** 当前持仓管理属于自动推理同一次调用，不是独立模型位置；拆分会引入第二次模型调用和结论冲突。已从实施范围删除。
3. **中风险过度设计：不应首期实现“每个策略 × 每种用途”矩阵。** 当前已有每策略分析模型；新增矩阵会显著扩大权限、删除影响、迁移和 UI 复杂度。已收缩为模型所有者级用途默认，未配置时调用完整旧解析器。
4. **中风险数据模型问题：原复合唯一键含可空 `strategy_id`。** MySQL 对 NULL 的唯一性不会阻止重复平台/用户默认行。已改为 `UNIQUE(owner_user_id, purpose_key)`，不再使用可空唯一键。
5. **中风险语义冲突：现有 `ai_model_tasks.task_kind` 不能直接承担模型用途。** task kind 已用于期限、队列、幂等和恢复，且手动交易复盘仍标记为 `manual_analysis`。已改为独立 resolver 参数 `modelPurpose`，不改变任务运行策略。
6. **低风险过度约束：用途绑定不应保存 `expected_profile_updated_at`。** 管理员正常编辑模型会使所有用途绑定变成陈旧配置。已删除该字段，任务创建时继续冻结最终模型即可。
7. **低风险不必要依赖：模型用途路由与管理员下单互不依赖。** 已取消 A 先于 B 的强制顺序，两者可独立实施。

### 12.2 对正常功能的保护结论

- 新用途默认表为空时，模型解析直接进入完整旧逻辑，现有策略绑定、用户默认、平台默认和共享政策不变；
- 不改变 `usage`、共享额度、容量队列和 task kind，避免影响现有模型配额、并发与恢复；
- 不改 `auto_signal_deliveries` 的表义和 scheduler 状态机，避免管理员订单进入自动推理恢复；
- 普通手动订单仍为 `source_type = 'manual'`，不会被纳入系统策略持仓；
- 管理员策略指令使用新 source type 和独立目标表，不污染模型评测样本；
- 只有带完整 `inference_snapshot` 的现有 AI 信号才进入 AI 交易复盘资格，管理员人工指令不能伪造模型证据；
- 所有把 `ai_signals` 视为模型结论的统计、自动持仓管理和样本查询必须显式排除 `admin_strategy_dispatch`；账号风险和系统 Magic 保护仍应包含它，但平台周末自动清仓必须按可靠归因排除它；
- 现有管理员从自身系统持仓发起的保护价修改入口保留不变；
- B2 只在现有管理员源持仓入口扩展关联完整平仓，不新增独立持仓中心，不改变普通用户持仓操作；
- 管理员指令仍经过用户执行授权、风险、账户归属、Bridge generation 和订单意图，不能绕过现有安全门。

### 12.3 本轮结论

修订后的方案符合用户提出的两项核心需求，并已去除非必要的独立持仓模型、策略用途矩阵和自动交付表复用。剩余改造仍涉及真实交易，实施时必须以“新增旁路、旧路径不变”为验收原则，并为自动推理、普通手动下单、复盘与 Bridge 信号列表建立回归测试。

## 13. 第四轮方案复审：持仓按钮与无管理员源仓场景

### 13.1 代码事实校正

用户所述“只有存在信号的持仓才显示编辑持仓按钮”与当前前端源码的精确条件略有差异，但指出的实际产品问题成立：

- 当前按钮文案是“编辑保护”，只在登录用户为管理员且持仓 `magic === 234000` 时显示；前端并不先查询该持仓是否存在信号；
- 后端同样先要求管理员本人账户中的持仓带系统 Magic；若不能唯一归因到一个 `signal_outcome/signal_id`，仍可修改当前源持仓，但不能启用同信号跨账户同步；
- 普通手动下单使用 Magic 0，因此实际界面上“系统 Magic 持仓”通常与“有系统信号归因的持仓”高度重合，容易表现为用户观察到的规则。

### 13.2 后续前提校正

第四轮曾基于“管理员可能没有源仓”的假设提出独立持仓管理入口。第五轮需求已明确：管理员手动分发时本人必定先持有该笔仓位，因此该假设不成立，第四轮提出的独立入口已撤销。保留本节是为了记录审查轨迹，不再作为实施要求。

## 14. 第五轮方案复审：复用源仓入口与周末清仓豁免

### 14.1 独立入口属于过度设计

管理员本人源仓是本次分发的强制前置条件，并且现有保护价任务已经能从管理员源 ticket 的唯一 `signal_id` 解析同信号持仓。因此再增加一套按 dispatch 管理的页面、接口和权限链没有必要，会形成两个入口、两套预览身份和状态一致性成本。

修订后只保留现有持仓行“编辑保护”入口：管理员源订单先成交并写入唯一结果归因，订阅用户随后共享同一 `signal_id`。保护修改继续使用现有同步范围；关联完整平仓作为同一弹窗的新动作，不改变普通“平仓”按钮的 source-only 语义。

该收缩依赖一个明确业务约束：管理员源仓必须在关联保护修改或批量平仓前保持存续。如果管理员绕过平台直接在 MT4/MT5 关闭源仓，现有页面将失去入口；本方案不为这个违背前提的场景重新增加独立管理中心。

### 14.2 周末清仓存在确定性冲突

当前 `system_trade_inventory` 只按 `Magic = 234000` 返回系统仓，`weekly-system-flatten` 随后遍历全部返回持仓调用 `close_system_position`，没有查询信号来源。因此只要管理员分发仓复用系统 Magic，现状下周末一定会进入清仓候选；原方案“周末系统清仓仍应包含它”的结论错误，现已纠正。

### 14.3 最小兼容修订

1. 不新增第二套 Magic，避免扩大 Bridge、持仓保护、归因和自动管理协议改造；
2. 只在周末任务内新增可靠来源分区，按当前账户、存续结果归因以及未落稳结果的目标/订单意图排除 `admin_strategy_dispatch`；
3. 管理员源仓和所有订阅用户分发仓使用同一豁免规则；
4. 周末任务的前置库存、发送目标和事后完成判定都使用同一分区器，避免豁免仓被反复判定为“清仓未完成”；
5. 归因服务异常，或存在活跃分发目标但无法唯一映射实时 ticket 时，整账户不发周末平仓命令并报警，以“不误平管理员分发仓”优先；
6. 普通自动系统仓、周末新增风险门禁、管理员主动平仓、止损止盈和经纪商风控保持原样。

### 14.4 本轮结论

独立管理持仓入口已从方案中删除，属于有效的去过度设计。周末豁免则不是界面选项，而是交易安全硬约束，必须与 B1/B2 同批实现和验收；否则管理员分发仓虽然能成功建立，仍会被现有周末任务自动平掉，不能上线。

## 15. 剩余产品决策与风险

实施前仍需管理员确认以下产品取舍：

1. 日复盘与月复盘是否必须选择不同模型；本方案已支持分开，但也可以在界面默认继承同一“周期复盘模型”。
2. 管理员策略指令是否严格遵守用户订阅交易时段；本方案建议严格遵守。
3. 离线用户是否只接收信号历史；本方案建议不在上线后补执行，以避免陈旧行情下单。
4. B1 首期是否只做市价单；本方案建议是，挂单在对账和取消竞态测试完成后单独开放。
5. 是否需要部分减仓；本方案首期不支持，完整平仓稳定后再单独设计。
6. 管理员策略指令是否出现在现有“信号历史”中；本方案建议显示，但必须明确标记为人工策略指令且排除 AI 评测/复盘。

## 17. 实施结果与最终复审

### 17.1 已完成范围

- 模型用途路由已实现七个独立用途，并保留空绑定时的完整旧解析路径；显式失效绑定失败关闭。
- 管理员策略指令已在现有手动交易卡片中实现，首期仅支持市价单；管理员源订单确认形成真实系统持仓后才向冻结订阅目标分发。
- 管理员策略分发直接使用手动下单区的交易手数，不再引入仓位档位；源账户和订阅目标使用同一请求手数并分别经过现有安全校验。
- 关联完整平仓只出现在现有“编辑保护”弹窗内，且仅在后端确认源仓唯一归因到 `admin_strategy_dispatch` 时显示；未新增独立持仓管理入口或任务列表接口。
- 保护价原有接口和 source-only/同信号同步行为保持不变；完整平仓使用独立 job/target 台账和 worker。
- 周末强平已排除管理员源仓及订阅分发仓；普通同 Magic 系统仓仍正常平仓。归因歧义或查询失败时保留原挂单取消流程，但对该账户发送零条持仓平仓命令。
- 管理员策略指令由现有登录鉴权和 `adminOnly` 管理员权限控制；管理员直接可用，普通用户不可见且不能访问相关接口。

### 17.2 最终审查移除的过度设计

1. 未建立独立持仓中心，也未保留未约定的平仓任务列表 API；
2. 未把管理员分发写入 `auto_signal_deliveries`，避免进入自动推理恢复和 `auto_shared` 语义；
3. 未增加第二套 Magic、策略用途矩阵、独立持仓模型或首期挂单；
4. 保护价模块没有为形式复用而引入新依赖，普通路径保持原实现；
5. 完整平仓只新增预览、创建、详情和失败目标重试四个接口。

### 17.3 最终安全修正

- source/subscriber 下单和完整平仓均使用稳定幂等键、目标租约与 job fencing；多实例下订阅目标阶段完成后才允许处理管理员源仓。
- Bridge ACK 不直接视为平仓成功，只有后续 `system_trade_inventory` 确认持仓消失才记为成功；`uncertain` 只对账、不重发。
- 目标发送前重新校验当前账户归属、Bridge generation、ticket、Magic、品种、方向和手数。
- B1/B2 租约统一使用北京时间 DATETIME，并以显式北京时间解析比较，避免 UTC 字符串与数据库 `NOW()` 混用导致租约提前失效。
- 周末豁免的无 outcome 回退仅覆盖活动意图或短归因窗口；已关闭历史目标和陈旧 succeeded 意图不会永久阻断账户。

### 17.4 本地验证结果

最终独立定向回归覆盖模型用途、管理员分发、订单意图、scheduler、保护价、完整平仓、周末强平、前端缓存和租约时区，共 19 个测试文件、214 项测试通过；全部变更 JavaScript 通过 `node --check`，`git diff --check` 通过。

本地验证未连接生产数据库、未执行 migration、未发送 Bridge 命令或真实订单、未启动或部署生产服务。真实 MT4/MT5、经纪商约束、生产数据量和多实例竞争仍需在 feature flag 关闭状态下完成测试账户验收。

## 18. 实施后产品纠正：分发使用直接交易手数

管理员策略分发复用了现有手动下单界面，继续增加“仓位档位”会让同一操作出现两套互斥的仓位输入，并改变管理员人工指令的直观含义。实施后复审确认该设计过度，最终规则调整如下：

1. 分发模式与普通手动下单共用“交易手数”输入，不再显示或提交仓位档位；
2. API 新请求使用 `volume`，分发台账以 `requested_volume` 冻结确认值；
3. 管理员源账户和所有订阅目标使用同一个请求手数，但仍分别通过现有账户、Bridge、经纪商和风险安全门；
4. 新根信号以 `recommended_volume` 保存人工请求手数，不写入 `position_size_tier` 或 `position_size_factor`；
5. migration 189 只新增兼容字段并将旧 tier 列改为可空，不修改已发布的 migration 187；worker 仅对 migration 189 之前已经创建且缺少 `requested_volume` 的在途记录保留旧 tier 恢复路径；
6. 普通 AI 推理信号的仓位档位设计保持不变，本次纠正只作用于管理员人工策略分发。

管理员策略分发原因最终调整为选填：空值以空字符串保存并允许提交；填写时仍限制为 2–500 字。完整平仓和保护价修改的原因要求不在本次调整范围内。
