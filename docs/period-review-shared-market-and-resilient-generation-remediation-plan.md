# 周期复盘共享行情与可靠生成优化修复方案

> 文档状态：已实施，但虚拟机真实验证未通过；后续修复见 `period-review-post-deployment-second-remediation-plan.md`
> 基线分支：`dev_codex`
> 基线提交：`6e711fa4076ade7ee37a9dfced2f5baf3f8e4`
> 编制日期：2026-08-19

## 1. 目标与边界

本方案解决以下已经在公网服务器和虚拟机复现的问题：

1. 周期复盘错误地把 K 线来源账号与策略观摩源账号强绑定，导致已有完整市场行情仍被判定为 `period_market_source_unauthorized`。
2. 日复盘分块重复携带完整行情与完整优化上下文，单个分块输入约 48.5 万至 49.5 万 token，虽然未超过模型上下文上限，但显著放大调用成本和配额消耗。
3. 模型对 `missing_evidence` 字段的偶发格式错误会触发额外修复调用，随后遇到 HTTP 429，最终把可恢复问题固化为 `model_quota_exhausted`。
4. 证据重建、模型配额恢复和失败任务续跑的状态边界不清晰，造成“证据缺失不自动恢复”和“完整证据仍生成失败”。
5. 前端只显示泛化失败文案，无法区分行情证据、模型输出契约、配额等待和永久失败。

本方案只调整周期复盘的行情证据、模型输入、校验、重试和展示链路，不改变：

- 交易、订单、成交、持仓、挂单的真实账号归属；
- 平台策略与观摩源的关联关系；
- 复盘确认后才写入策略记忆库的规则；
- 日复盘 v3 的逐笔分析、归因、行动建议和经验规则业务目标；
- 已有版本唯一性、幂等键和审核状态语义。

本文档不授权修改生产数据、手工重试任务、部署或重启服务。

### 2.3 根因结论

当前系统存在两个互相冲突的契约：

- 实时推理把平台行情源作为共享行情服务使用；
- 周期复盘却要求行情来源账号必须与策略观摩源账号完全一致。

K 线本质上是按品种、周期和时间窗口定义的市场证据。账号身份可以作为来源审计信息，但不应作为平台策略周期行情的授权条件。真正需要严格账号身份约束的是订单、成交、持仓和挂单。

## 3. 最终业务规则

### 3.1 数据身份分层

| 数据类型 | 归属规则 | 是否允许共享 |
|---|---|---|
| 订单、成交、持仓、挂单 | 必须严格绑定策略观摩源及真实账号 | 否 |
| 入场、出场、止损、止盈执行事实 | 必须来自真实订单/成交记录 | 否 |
| K 线、市场结构、通用技术指标 | 按标准品种、周期、UTC 窗口选择可信行情源 | 是 |
| 行情来源账号、服务器、source key | 只用于溯源、质量审计和故障诊断 | 不作为账号授权条件 |

### 3.2 共享行情约束

“共享”不等于任意拼接。每个 `symbol + timeframe + review_window` 必须满足：

1. 由服务器端行情解析器选择来源，前端和模型不能指定任意账号。
2. 一个时间窗口只使用一个可信来源，不把多个来源的蜡烛混合为同一序列。
3. 优先使用该批交易冻结推理快照的行情源；不可用或不完整时，回退到平台规范行情源。
4. 优先让所有周期使用同一来源；确需按周期回退时，逐周期记录来源，仍禁止单周期内混源。
5. 校验标准品种映射、UTC 时间边界、K 线顺序、重复时间戳、缺口比例、首尾覆盖和终端时钟可信度。
6. 来源发生变化只记录 `market_source_changed` 审计提示；只要质量合格，不再将复盘判为证据缺失。
7. 所有交易事实继续取自真实订单和成交，不允许用共享 K 线反推或覆盖交易事实。

## 4. 总体改造设计

### 4.1 拆分“归属授权”和“行情质量校验”

将现有 `periodMarketSourceAuthorization()` 的职责拆为两类：

- `authorizeTradeEvidenceSource()`：用于订单、成交、持仓、挂单，继续执行严格的用户、账号、策略和观摩源校验。
- `validateCanonicalMarketSource()`：用于 K 线，只校验品种、周期、时间窗口、来源可信度和数据完整性，不比较观摩源账号身份。

新增统一的 `resolveCanonicalPeriodMarketSource()`：

1. 查找冻结推理快照中已使用且覆盖完整的行情源；
2. 若不满足质量要求，查找当前平台规范行情源；
3. 如缓存缺失，通过现有 Bridge 行情请求补齐后再次校验；
4. 只返回通过质量门禁的单一序列；
5. 所有候选源都不合格时，才返回真正的 `period_market_incomplete`。

建议在证据 JSON 中增加，无需立即新增数据库列：

```json
{
  "market_policy_version": "canonical-market-v2",
  "source_selection_reason": "frozen_inference_source|platform_canonical_fallback",
  "source_changed": false,
  "source_key": "audit-only",
  "coverage": {
    "expected_start_utc": "...",
    "expected_end_utc": "...",
    "actual_start_utc": "...",
    "actual_end_utc": "...",
    "gap_count": 0
  }
}
```

`source_key` 只用于后台审计，不进入模型决策字段，也不向普通用户暴露账号隐私。

### 4.2 重建证据时保持来源集合稳定

行情政策变化只允许重建周期行情部分：

- 不重新选择交易记录；
- 不改变 source/outcome 集合；
- 不改变订单归属；
- 仅更新周期行情证据、证据哈希和政策版本；
- 重建成功后按既有唯一键创建或唤醒一个生成任务，禁止产生重复 case 或重复 review version。

case 292 仅作为回归样本，代码中不得硬编码 case、用户、账号或策略 ID。

## 5. 模型输入优化

### 5.1 当前问题

`dailyReviewModelEvidenceForChunk()` 虽然按交易拆分 chunk，但每个 chunk 仍重复携带完整 `period_market` 和完整 `current_optimization_context`。交易越多，重复输入和调用次数越多，导致一次日复盘消耗数百万累计输入 token，并增加触发供应商配额限制的概率。

### 5.2 新的三层输入结构

1. **服务端完整证据层**
   保留原始 K 线、快照、订单事实和策略文本，供审计、确定性计算和回放使用，不直接完整复制到每个模型请求。

2. **共享市场摘要层**
   在分块前只计算一次：各周期趋势、波动、关键结构、关键价位、时段状态、数据覆盖及哈希。摘要必须由确定性代码生成，并保留到原始证据的引用。

3. **交易局部证据层**
   每个 chunk 只携带该组交易的入场前窗口、持仓路径、出场后必要窗口、订单事实及与共享市场摘要的关联。

模型合并阶段只接收：

- 各 chunk 的结构化逐笔结论；
- 一份共享市场摘要；
- 一份受长度约束的策略与当前优化上下文；
- 服务端确定的统计结果。

### 5.3 输入预算

新增发送前预算器，以配置项控制并提供保守默认值：

- 单 chunk 预计输入不超过 120,000 token；
- 单 chunk 序列化正文建议不超过 500 KB；
- chunk 大小同时受交易数量和实际字节数约束；
- 超预算时优先缩短重复行情数组和历史上下文，不删除订单事实与关键局部行情；
- 仍超预算时继续细分 chunk，禁止把供应商“输入过长”作为常规重试处理。

预算值必须通过测试验证，并可按模型能力配置，不在业务代码中散落硬编码。

### 5.4 检查点复用

- 每个成功 chunk 持久化输入哈希、输出和契约版本。
- 供应商 429、进程重启或单 chunk 校验失败后，只续跑未成功 chunk。
- 输入哈希或契约版本变化才使旧检查点失效。
- 合并任务保持幂等，同一个 case/revision 只允许生成一个有效版本。

## 6. 输出契约与确定性校验优化

### 6.1 `missing_evidence` 改为服务端所有

证据是否缺失是系统事实，不应让模型自由创造。调整为：

- 服务端为每条交易提供 `evidence_limitations` 和允许的证据不足原因；
- 最终保存的 `missing_evidence` 由服务端根据模型状态和确定性证据归一化；
- 模型仍可说明“哪些分析无法确认”，但不能改变系统的证据完整状态。

### 6.2 安全归一化规则

| 场景 | 处理方式 | 是否追加模型调用 |
|---|---|---|
| 确定性证据完整，模型额外返回 `missing_evidence` | 清空该字段，记录契约警告 | 否 |
| 确定性证据存在缺口，模型漏填 | 使用服务端已有 `evidence_limitations` 补齐 | 否 |
| 模型声明证据不足，但服务端无任何允许缺口 | 拒绝该 chunk，最多进行一次定向修复 | 最多 1 次 |
| JSON/枚举等结构损坏 | 使用现有结构修复；仍失败则终止当前 chunk | 最多 1 次 |

严禁根据模型文本伪造不存在的行情或订单证据。归一化前后的差异要写入 job event，供后台审计。

## 7. 配额与重试状态机

### 7.1 分离三类计数

- **业务生成尝试**：冻结证据或业务契约发生变化后的一次完整生成流程。
- **供应商调用尝试**：HTTP 请求、超时、429、5xx 等真实调用次数。
- **契约修复尝试**：针对某个 chunk 输出的结构化修复次数。

HTTP 429 和可恢复 5xx 不应消耗业务生成 3/3；契约修复也不得伪装为新的业务生成尝试。

### 7.2 429 处理

1. 首次 429 后对对应模型配置开启短时容量熔断，暂停继续启动同一复盘的其他新 chunk。
2. 优先读取 `Retry-After`；没有时使用带抖动的指数退避。
3. job 进入明确的 `waiting_provider_capacity`/`retry_wait`，保留 `next_attempt_at`。
4. 到期后从第一个未完成 chunk 恢复，不重复已成功调用。
5. 只有鉴权、配置错误等不可重试错误，或超过可配置的总恢复期限，才进入终态失败。
6. 自动恢复必须受全局并发和批量上限保护，避免服务重启后形成重试风暴。

### 7.3 证据恢复

- `period_market_source_unauthorized` 在新政策下不再是有效的行情缺失原因。
- 维护任务发现旧 `market_policy_version` 或该旧错误时，执行一次幂等行情重建。
- 重建成功后由正常状态机创建/唤醒 job；失败时保留精确的质量缺口，不循环无效请求。
- 证据仍在采集窗口内时保持 preparing；周期已结束且真实行情仍缺失时显示具体缺失周期和时间段。

## 8. 前端状态与运维可观测性

前端至少区分：

- `行情证据补齐中`：显示缺失周期和下一次检查时间；
- `模型容量等待中`：显示预计重试时间，不显示为永久失败；
- `模型输出校验中`：说明正在修复结构，不暴露内部 JSON；
- `生成失败`：只用于不可恢复或超过恢复期限的终态；
- `行情来源已切换`：信息级审计提示，不标红、不判证据缺失。

管理员详情增加：

- 业务尝试次数；
- 供应商调用/429 次数；
- 契约修复次数；
- 已完成 chunk / 总 chunk；
- 当前阶段、精确错误码、`next_attempt_at`；
- 行情政策版本和来源选择原因。

普通用户只显示可理解的中文状态及是否需要人工操作。手动“重试生成”只在终态失败或管理员明确允许时出现，点击后仍使用幂等键，不能生成重复版本。

## 10. 测试与验收标准

### 10.1 单元与集成测试

1. 策略观摩源账号与行情源账号不同，但行情覆盖完整时，周期证据应为完整。
2. 同一周期存在多个候选源时只选择一个，不混合蜡烛。
3. 品种、时间窗口、时钟或缺口不合格时仍应 fail closed。
4. 订单、成交、持仓、挂单的跨账号证据继续被拒绝。
5. 冻结推理来源不可用时可回退平台规范源，并记录 `source_changed`。
6. 等价 case 292 的夹具可从旧错误恢复并创建唯一 job。
7. `missing_evidence` 多填和漏填可本地归一化，不产生额外供应商调用。
8. 不允许的“证据不足”最多修复一次，仍错误时只失败当前 chunk。
9. 429 不增加业务尝试，进入等待后可从失败 chunk 继续。
10. 进程重启、lease 过期和重复维护轮询不产生重复 chunk、job 或 review version。
11. 9 笔和 12 笔回归样本中，单 chunk 输入均低于配置预算，完整日复盘不再重复发送完整行情。
12. 前端能正确区分证据补齐、容量等待、校验修复和终态失败。

### 10.2 业务验收

- 每条交易仍能回答：当时信号分析是否正确、是否符合行情、为何盈利或亏损、如何避免同类亏损。
- `next_day_actions` 和 `experience_rules` 必须是明确条件、明确动作、可验证结果，不允许泛化口号。
- 交易事实与共享行情不会串账号；共享 K 线只用于行情判断。
- 来源账号变化不再单独造成“证据缺失”。
- 暂时性模型配额不足能够自动恢复，不要求用户反复点击重试。
- 任何恢复流程不生成重复版本，也不绕过复盘确认与记忆写入审核。

### 10.3 建议验证命令

实施时按仓库实际脚本补齐，至少执行：

```powershell
npm test -- --runInBand
npm run lint
```

并单独运行周期复盘、模型任务状态机、前端静态缓存版本和迁移相关测试。若仓库没有统一 lint 命令，应记录实际替代命令，不允许把不存在的命令当作通过证据。

## 11. 兼容、迁移与回滚

- 优先把政策版本和来源信息写入现有证据 JSON/job event，避免为展示字段引入不必要的新表。
- 如确需新增可查询列，只能追加新迁移，不修改已发布迁移。
- 新旧任务通过 `market_policy_version` 和模型契约版本隔离。
- 回滚代码时，停止新政策重建任务；已生成的 review version 保持可读，不删除历史。
- 不通过 SQL 强行把证据标为完整，不直接补造模型结果。

## 12. 与既有方案的关系

本方案仅替代 `docs/daily-period-review-business-optimization-plan.md` 中“平台策略周期行情必须与策略观摩源账号完全一致”的行情授权设计。以下既有设计继续有效：

- 交易来源和账号归属严格校验；
- 短持仓行情不可观测时的诚实降级；
- 日复盘 v3 的逐笔证据、归因和经验规则结构；
- 确认后才更新策略记忆库；
- job、case、version 的幂等与唯一性约束。

## 13. 两轮方案复审

### 第一轮：数据安全与业务边界

发现风险：直接取消来源账号校验，可能被误解为允许任意行情或多源拼接。

调整：增加服务器端规范行情源解析、单周期单源、质量门禁和完整来源审计；只放宽 K 线账号身份，不放宽订单及交易事实归属。

### 第二轮：状态机与配额风险

发现风险：简单增加自动重试可能形成重试风暴，也可能重复消耗已成功 chunk 的配额。

调整：增加模型配置级熔断、`Retry-After`/退避、全局并发上限、检查点续跑，以及业务尝试和供应商尝试分离；现存生产任务恢复仍需受控授权。

## 14. 剩余风险

- 不同经纪商的 OHLC、点差和交易时段可能有小幅差异；因此共享行情适合趋势和技术分析，不得替代订单成交事实。
- 模型供应商配额属于外部约束，状态机只能降低浪费并自动续跑，不能保证供应商始终可用。
- 历史窗口若所有可信来源都缺少 K 线，系统仍应诚实保持证据不完整。
- 行情政策版本变化会改变证据哈希，必须验证旧检查点失效和版本唯一性逻辑。
- 输入压缩必须保留局部关键行情；实施后需用已知盈亏样本对比压缩前后的分析质量。

## 15. 实施记录

本次实现采用以下落地版本：

- 行情来源政策：`shared-canonical-v1`；
- 模型行情摘要：`daily-market-digest-v1`；
- 旧配额终态一次性恢复键：`quota-recovery-v1`；
- 前端运行契约：`period-review-shared-market1`。

已完成两轮代码复审调整：

1. 共享行情仍限定为可信时钟、服务端选择、单周期单来源；私有交易证据继续执行原账号授权。
2. 原始 K 线保留在冻结证据中，只从模型分块输入移除；逐笔成交、持仓路径和确定性日行情摘要继续提供给模型。
3. `missing_evidence` 改为服务端根据冻结限制生成；确定性证据完整时忽略模型多填内容，无服务端限制却声明证据不足时仍最多进行一次契约修复。
4. HTTP 429 使用模型容量熔断时间安排续跑、返还本轮业务尝试，并复用已经成功的分块检查点。
5. 历史 `model_quota_exhausted` 终态仅在证据完整、没有版本时执行一次幂等恢复；不修改原始交易和复盘版本。

虚拟机部署后的真实验证已完成，结果未通过：旧证据没有及时进入政策升级通道；case 291 虽完成配额恢复和分片断点续跑，但最终因 v3 输出误落旧版 `daily_lessons` 验证路径而失败；单分片仍约 1.27 MB、约 47 万输入 token；case 292 仍保留旧来源身份冲突。详细第二轮修复设计与验收门槛见 `docs/period-review-post-deployment-second-remediation-plan.md`。
