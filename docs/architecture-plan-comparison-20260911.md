# 当前 V4 重构与 Workbuddy 架构方案对比

日期：2026-09-11。性质：方案比较与当前实现抽查；重构实施已按用户要求暂停。本次没有修改业务代码、配置或数据库，没有启动服务、运行迁移或部署。本文不替换任何已批准方案。

## 1. 结论

针对本轮已经明确的目标——前后端全面模块化、数据库规范化、现有 dev_vue 可直接升级且数据保留、四应用独立、开发阶段不涉及公网——**建议保留当前 V4 总体架构，吸收 Workbuddy 的交付组织、事故回归和运维验收方法，不整体换用其技术方案。**

这不是因为当前代码已经投入很多，而是两份方案解决的问题不同：

- 当前 V4：重新建立业务、身份、协议、数据和运行边界，最终切换新版；保留迁移历史与数据，不长期兼容旧业务 API。
- Workbuddy：在旧系统持续在线的条件下，保持旧协议、旧 API 和旧前端形态，渐进拆分原有实现，然后替换页面。

如果目标改为“尽快整理正在运行的旧系统，尽量不改变用户行为”，Workbuddy 的路线改动面较小。如果目标仍是本轮的完整 V4，当前路线更合适。**设计更适合不代表实施已经完成；当前最大的短板是交付节奏和业务闭环收口。**

## 2. 依据与证据等级

Workbuddy 的资料摘要明确基于 `D:\dev_workbuddy`、`dev_mimo@57052a64`，不是当前 dev_vue 工作树。其旧单文件行数、245 个测试、16 份 schema，不能用来判断 V4 当前进度。

本次读取其主概览，按议题核对高层设计、系统设计、UserStory、部署、安全及两份调研文档的相关章节。当前侧读取 AGENTS、需求基线、全项目功能矩阵、主路线图、后端/数据库/模块化方案和最新状态记录，并抽查源码与配置。

当前源码可直接确认：

- `server/src/modules` 有 14 个目录；业务入口与 composition 入口分离已有明确规则。
- `frontend/apps` 已有 www、trade、admin、auth 四应用；trade 有多个业务页面，admin 仍主要为 auth、overview、settings、shell，存在占位页。
- HTTP runtime 清单为 104 项。它是接入清单，不是全功能完成率。
- 服务端、前端 boundary debt 文件的 entries 均为空；本次未重跑检查，不能把空清单独立视为全源码无越界证明。
- `ecosystem.v4.config.cjs` 实际配置 12 个角色；部分文档仍写 11 个，存在文档漂移。角色配置不等于进程已运行。
- 人工复盘候选持久任务 runner 已存在，但 task queues 尚无候选队列，最新状态也明确自动触发、Worker 和恢复扫描未接通。

数据库 262 步/311 表、历史数据承接等数字来自本次读取的既有验收记录；本次没有重新连接数据库复核。不使用迁移步数、表数或测试数推导完成百分比。

## 3. 主要架构差异与选择

| 比较项 | 当前 V4 | Workbuddy | 判断 |
| --- | --- | --- | --- |
| 重构边界 | 全面重建目标边界，旧系统只作迁移输入 | 旧系统不停机渐进改造 | 本轮保留 V4；其在线兼容成本不是当前开发阶段的必要前置 |
| 模块化 | domain/application/infrastructure/transport；唯一业务入口、受限组装入口、数据所有权和依赖门禁 | 8 业务域 + 2 平台模块，源文件拆分映射清楚 | 两者都选模块化单体。V4 的跨域访问约束更具体；借鉴对方的全景映射，不能以文件小于 2000 行代替模块化 |
| 服务端框架 | Fastify + 严格 TypeScript | 沿用 Express，并逐步领域分层 | 没有框架天然胜负；V4 已形成合同和组装体系，换回 Express 不解决剩余业务断点 |
| 后台任务 | API、浏览器实时、Bridge、调度、outbox、Worker 分角色；MySQL 权威，BullMQ 唤醒 | 现有调度/Redis 锁基础上拆分；Redis 被列为可选降级依赖 | V4 对耗时隔离、提交后投递、重启恢复描述更完整；仍需实测总资源预算，不无限增加角色 |
| HTTP 契约 | `/api/v4`，按域合同生成 OpenAPI、类型及运行校验 | `/api`、`/aurum-api` 兼容，新增 `/api/v1`；六位错误码 | 本轮保留 V4 单一新业务契约，避免新增第三种路径和错误体系 |
| 设备/实时协议 | HTTP、浏览器实时、Bridge 三类独立版本化合同 | 优先保留 V3 JSON Schema 并工具化 | JSON Schema 与 OpenAPI 服务不同契约范围，不是必须二选一；其加权得分不能证明 HTTP 不该使用 OpenAPI |
| 身份与会话 | auth 中心 + Code/PKCE；应用 Host-only HttpOnly 会话；明确退出范围 | 同源 shared/session.js、JWT 与兼容令牌退出广播，完整版再子域化 | 四应用目标下 V4 更完整。独立登录页面不等于独立会话隔离；不恢复跨应用令牌共享 |
| 前端 | Nuxt www + Vue/Vite trade/admin/auth；shadcn-vue 唯一共享 UI | Vite/TS 三应用，PrimeVue；旧形态先保留 | 两套组件库都能做业务，不能凭名称判优。当前方案对公开页面渲染和独立会话更具体，保留已选栈 |
| 数据库 | 实际库审计、根实体/历史归属/版本/载荷规范化、追加迁移和回填对账 | 核心是拆分旧 migrations.js、校验和及少量新表；强调不改表结构语义 | 对“全面规范化 + 现库升级不丢数据”，V4 覆盖更深；仅拆迁移文件无法完成结构与业务语义治理 |
| 价格精度 | 精确数值合同、合约规格和执行检查分属明确业务域 | 唯一 normalize 入口、Decimal、tick 网格和事故回归独立列项 | 吸收其事故驱动验收；统一规则，不建设同时拥有所有行情、时钟和业务判断的万能 normalize 模块 |
| 时间 | UTC 存储；实验室终端时间，其它北京时间；休市 UTC+3 仅显示默认 | UTC + 可信终端业务时间，禁止固定 UTC+3 回退 | 可信业务时间原则一致；对方缺少本轮“展示默认值与执行证据分开”的明确要求，不能覆盖用户决定 |
| Bridge | .NET Framework 4.8 Win7 候选主客户端；MT5 固定 Python Worker；V4 升级链 | 保留 Rust，明确不支持 Win7，维持 V3 | 属产品支持范围冲突。Win7 必须保留时对方不满足；若放弃 Win7，保留 Rust 可减少旧客户端改写。不能仅因该文件写“已裁决”就变更本轮支持范围 |
| 交易与风控 | 分析师/交易员/确定性风控分责，统一 execution 状态链，所有来源操作入同一入口 | 信号→意图→静态/账户风控→桥接；保留既有策略与仓位语义 | V4 的统一执行、未知结果和历史授权设计更细；对方也有 uncertain 不重放，不能说它没有幂等保护 |
| 策略与记忆 | 分析/执行策略版本与角色记忆明确，人工确认；旧记忆暂处 shadow/revalidating | 每策略一个统一权威记忆库 | 都禁止自动改策略，但存储语义不同，不能直接把旧统一正文当作所有角色可立即注入的内容；V4 尚未完整运行验收 |
| 部署与安全 | 当前本地应用 + VM MySQL/Redis；后续单 PM2 项目分角色验收 | 多网络分区、主从、观测栈、WAF、保留期和成本表 | 对方运维清单更成体系，适合后续上线准备；当前照搬主机拓扑与成本会扩大范围，必须按实测定规模 |
| 交付治理 | 全功能矩阵细，但状态散落、过细阶段过多 | F/US/验收条件/依赖切片更易读 | 应借鉴其交付组织；周数和绿色测试数量都不直接证明功能可交付 |

## 6. Workbuddy 方案需要先修正的具体问题

1. **全库范围不闭合。** 系统设计 §4.2.1 将 db.js 的 33 张既有表称为“全库表清单”，但 §4.5 又记录 migrations.js 有 137 个 CREATE TABLE。33 并不因此等于完整数据库，更不能替代当前实际库逐表映射。这里是覆盖证据不足，不是用 311 张表证明 V4 更好。
2. **兼容与结构变更缺少桥梁。** 一方面强调迁移拆分“不改表结构语义”，另一方面规定统一时间、价格、软删除、身份等结构；哪些只是目标约定、哪些实际改变旧列、旧代码如何继续读写，尚需形成逐表方案。
3. **新错误协议仍把失败标为 200。** 系统设计 §3.5.1 的 problem 示例以 status=200 表示策略不存在，还把 A01001 用在示例，而注册表将该码用于账号密码错误。会影响通用客户端/监控区分成功与失败，应在新 API 纠正；旧兼容层另行隔离。
4. **账户调度修订未贯穿。** 高层主链和 US-26 改为用户+账户+策略+品种，但系统设计 §3.2.M2 仍有 `ai:sched:{strategy}:{symbol}:{slot}`。不能直接据此编码，需要区分可共享分析与账户级执行，并统一持久键/锁/缓存键。
5. **品种规格作用域偏粗。** §4.2.9 唯一键是 symbol+broker_server，没有显式 platform/account/terminal route/version。对于本轮多平台、账户换号和派发前复核目标，该结构不能单独证明规格属于当前命令路由；历史版本依赖审计但未展开完整绑定机制。
6. **Redis 降级语义需逐功能定义。** “不可用不阻断主链路”不能直接套给额度领取、分布式任务和命令派发。数据库唯一键防重复，不自动解决锁过期旧 Worker、丢失唤醒和当前路由有效性。V4 也必须分别验收这些机制。
7. **上线无损不能只靠入口回滚。** 旧/新写语义一旦不同，切回旧页面或恢复旧备份不保证新数据可用；需要证明旧代码兼容新写入，或明确停止写入、前向修复与增量恢复方式。
8. **汇总存在版本漂移。** 概览仍写 7 个 Dashboard/14 告警，系统设计修订记录已增加多账户大盘和 AL-15～17；概览日期为 09-11，部署正式稿记录 09-13。文档中的“已冻结/已确认”应追溯对应基线，不能视为当前会话已接受的变更。

另外，Win7 调研评估的是保持原 Rust 技术基线的代价，不构成对当前 .NET 候选路线的直接否定。本次不重新核验第三方平台支持矩阵，也不作兼容性实机结论。

## 7. 当前方案自身需要修正的问题

1. **交付单位过碎。** 同一人工复盘链分成许多独立表、端口、脚本和小批次，虽然积累了证据，但用户可运行的自然流程迟迟没有闭合。应保留必要正确性要求，把实施与验证组织成完整用户流程。
2. **现状文档相互漂移。** 路线图顶部仍有 240 步，当前状态为 262；进程说明 11 与实际 12 不一致；功能总矩阵还保留较早阶段状态。需要一个当前验收清单，历史流水从“当前状态”中移出。
3. **方案范围广，优先级未充分落实到交付。** 主站、后台、Bridge 和自动复盘尚未完成，不能再用结构升级步数掩盖业务缺口。
4. **曾出现不必要的约束扩张。** 人工单笔复盘曾要求完整历史时区区间，后因它只需精确交易 ID 与 UTC 生命周期而撤回。后续必须区分展示、单笔事实和自然日/月分组要求。
5. **可观测性与容量的交付组织不如对方清楚。** 已有日志、角色和审计不等于仪表盘、告警、延迟目标与连接池预算已经验收。
6. **部分真实依赖测试仍是参考链。** 实际 MySQL/Redis 加合成终端/最小父表，只证明对应调用与事务；不是所有真实用户前置条件、模型响应和终端结果的完整集成。

## 8. 建议采用的合并原则（仅建议，未执行）

- 保留 V4 的模块公开入口、数据所有权、独立运行角色、outbox、统一 execution、四应用/SSO、V4 合同及现库追加升级路线。
- 借鉴 Workbuddy：给每项功能建立一条“需求→实现入口→数据→合同→用户流程验收→剩余项”的记录；按可运行闭环交付，不按内部表/端口宣布阶段完成。
- 将价格事故回归、版本双轴、trace 关联、告警、容量与恢复预算加入明确验收项；不把固定工期、全量日志采样或多机拓扑直接当作必要配置。
- 不恢复旧前端、旧浏览器令牌共享或旧 API；不改成 PrimeVue/Rust，不删除/重写已执行迁移。除非用户重新选择产品范围，否则这些都不是本次比较的自动结论。
- 恢复实施前，先将现有功能矩阵的“设计覆盖”与“已可运行”分开，收敛一份当前剩余交付清单；保留所有尚未完成需求，不以缩小目标来宣布重构完成。
