# 手动交易对照策略复盘与经验沉淀实施方案（历史设计）

> 本文档保留早期设计过程，不再代表当前生产合同。当前权威合同见
> [`manual-trade-review-v2-contract.md`](./manual-trade-review-v2-contract.md)：每次一笔盈利且未绑定平台信号的完整平仓交易，采用两阶段冻结，只形成待验证假设，不创建平台经验候选，也不写入策略记忆或策略。

> 文档状态：三轮复审通过，已按管理员/观摩源权限边界修订，可进入实施
> 编制日期：2026-08-08
> 最近复审：2026-08-10
> 适用项目：AURUM / AI 交易实验室
> 目标入口：AI复盘师 → 手动交易复盘

## 1. 背景与决策

当前日复盘、月复盘以 `signal_outcomes`、`inference_snapshots` 和完整成交证据为基础，适合分析系统产生并管理的 AI 交易。直接在网站或 MT4/MT5 终端完成的手动交易被明确排除在系统管理结果之外，因此不会进入现有周期复盘，也无法自然获得策略 ID、策略版本和推理快照。

本需求不应把手动交易强行混入现有 AI 信号结果，而应在 AI复盘师中增加独立的“手动交易复盘”子页面：用户从已完全平仓且可确认是手动来源的交易中选择记录，再选择一个有权查看和编辑的策略，系统冻结所选交易、策略版本与历史行情证据，分析手动交易逻辑是否符合当时行情、是否符合所选策略，并产生两类人工可控结果：

1. 平台经验候选：仅在操作者单独确认后进入平台经验候选区，仍需通过现有发布动作才会成为可检索的平台记忆。
2. 策略优化候选：只提供差异、证据、风险和建议，不自动修改策略；用户最终在策略编辑器中人工修改并保存新版本。

最终产品决策是：**以“对照平台策略并生成优化方案”为主流程，以“人工确认后生成平台经验候选”为附属结果；只增加一个手动交易复盘 Tab，不拆成两个重复页面。该入口仅管理员和 `plan_source = observer_source` 的观摩源专用账号可见、可用。**

## 2. 需求目标

### 2.1 必须实现

- 在 AI复盘师现有“待处理复盘、策略记忆”旁增加“手动交易复盘”子 Tab。
- 前端仅向管理员和观摩源专用账号显示该 Tab；所有后端接口同时使用 `canManagePlatformAiContent()` 强制授权，禁止只依赖前端隐藏。
- 交易选择器只展示当前登录用户、当前实际交易账户下的手动做单记录。
- 只允许选择已完全平仓、成交链完整、账户归属和终端时间可信的交易。
- 支持按账户、日期、品种、方向和盈亏筛选，并采用服务端分页和按需加载。
- 部分平仓、分批退出按同一持仓身份合并为一笔完整交易，不把每个成交拆成独立样本。
- 操作者必须选择一个有权管理的平台策略；分析时冻结策略内容和版本，不提供私有策略选项。
- 用户可选填真实下单思路，明确补充成交数据无法证明的主观意图。
- 模型分别判断行情合理性、策略符合度、决策质量和结果偶然性。
- 模型输出结构化策略优化候选，显示现有规则、观察到的手动逻辑、建议、证据、反例、适用场景、风险和置信度。
- 系统不提供自动应用策略修改的接口，不直接改写策略提示词或策略配置。
- 操作者确认复盘后，可单独选择合格经验候选生成平台经验候选；不默认生成、不自动发布。
- 全流程保留证据哈希、策略快照、版本、模型任务、用户修订、确认动作和审计记录。

### 2.2 明确不做

- 不分析仍在持仓中的交易或未成交挂单。
- 不把系统 Magic、AI 信号、自动交付或其他 EA 的交易伪装为手动交易。
- 不自动扫描全部历史并批量生成复盘。
- 不根据单笔盈利自动修改策略。
- 不把手动交易自动写入平台经验或平台策略；只有显式确认的候选可进入平台经验候选区，发布仍走现有人工治理。
- 不新建第二套策略编辑器、回测引擎或记忆检索系统。
- 不要求 Bridge 将无界历史一次性上传到服务器。
- 不从盈亏反推“交易逻辑正确”，也不把模型推测的入场理由当作用户事实。

## 3. 现有能力与复用边界

| 现有能力 | 当前行为 | 本方案处理 |
| --- | --- | --- |
| Bridge 历史交易 | `history` 命令按页读取，页大小有界 | 复用读取与强制刷新，不增加全量历史接口 |
| 手动订单隔离 | `source_type = manual` 不创建系统管理 outcome | 保持不变，新增独立手动复盘证据 |
| 平台内容权限 | `canManagePlatformAiContent()` 只允许管理员和观摩源专用账号 | Tab、接口、case 读取和结果动作全部复用该能力，不新增角色 |
| 策略权限 | 管理员和观摩源专用账号维护平台策略 | 选择器只返回平台策略，不扩大到私有策略或其他用户数据 |
| 策略版本 | 内容变化时版本递增 | 创建复盘时冻结当前版本和配置快照 |
| 模型选择 | 已有 `usage = review` 和后台容量队列 | 复用复盘模型与容量治理 |
| 周期复盘任务 | 具备队列、租约、重试、版本和确认 | 复用设计模式，不复用其周期聚合数据表 |
| 平台经验 | 已有 candidate、active、revoked 状态及人工发布治理 | 只增加手动复盘来源引用，先生成 candidate，不另建记忆系统 |
| 策略编辑器 | 用户人工编辑并保存新版本 | 仅提供“打开策略编辑器”和建议摘要，不自动填充保存 |

### 3.1 为什么不直接复用 `trade_review_cases`

现有 `trade_review_cases` 强绑定非空 `outcome_id`，其证据语义是“AI 信号 → 系统订单 → 成交结果”。手动复盘允许一次选择一笔或多笔完整持仓，并需要额外保存策略快照、用户下单说明、手动来源判定和策略优化候选。修改旧表会扩大现有证据合同并影响周期复盘，因此采用独立表和独立模块更安全。

### 3.2 为什么不新建策略优化执行器

本需求的最终动作是人工修改策略。策略优化候选保存在复盘版本的结构化内容中即可，无需新增“自动打补丁、自动回测、自动发布”系统，也无需新增独立 proposal 表。这样可以保留审计和展示能力，同时避免过度设计及自动修改策略的风险。

## 4. 用户流程与页面设计

### 4.1 信息架构

AI复盘师保留现有页面，只在现有子 Tab 中增加：

- 待处理复盘
- 手动交易复盘（新增）
- 策略记忆

可见性规则：

- 管理员：显示并允许进入。
- `role = user` 且 `plan_source = observer_source`：显示并允许进入。
- 其他普通用户、Plus/Pro 用户和观摩频道订阅用户：不渲染 Tab；即使手工调用接口也返回 403。
- 权限以服务端 `canManagePlatformAiContent()` 为唯一判定源；前端只消费登录态中的能力结果，不自行推导第二套规则。

“手动交易复盘”内部使用同一页面的三阶段工作流，不再增加第二层 Tab：

1. 选择交易
2. 选择策略与补充思路
3. 查看并确认分析

### 4.2 阶段一：选择手动交易

页面首次进入时才请求数据，离开后不持续刷新。筛选项包括：

- 交易账户
- 平仓日期范围
- 品种
- 买入/卖出
- 盈利/亏损

交易数据范围固定为当前登录身份自己连接且归属有效的交易账户。观摩源账号只能读取其自身 Bridge 数据账户；管理员也只读取管理员本人明确连接的账户，不能借此入口浏览任意观摩源或普通用户交易。后续若确需管理员代选观摩源账户，应单独设计授权、审计和隐私边界，不在首期暗中扩大范围。

管理员未连接本人交易账户时显示明确空状态“当前管理员账号未连接可复盘的交易账户”，不回退读取默认观摩源，也不建议切换身份规避权限。

列表每页默认 20 笔，最大 100 笔；前端不自动翻完全部分页。每行显示：

- 复选框
- 品种、方向、完整持仓标识
- 入场时间、平仓时间
- 入场均价、平仓均价
- 初始止损、初始止盈
- 总交易量、分批成交数量
- 净盈亏
- “手动来源已确认”状态

允许一次选择 1–10 笔交易。选择超过 10 笔时前端阻止并解释“请按同类行情分批复盘，避免不同逻辑相互污染”。

同一次复盘选择的交易必须属于同一交易账户；跨账户记录需要分别创建复盘，避免账户规格、终端时钟和归属期不同导致证据混合。

创建任务前，服务端必须对所选记录执行一次强制刷新并重新校验，防止用户根据陈旧列表提交已经变化或证据不完整的交易。

### 4.3 阶段二：选择策略与补充思路

策略选择器只返回当前操作者有权管理且未删除的平台策略。不得返回私有策略，也不得把“可订阅平台策略”等同于“可管理平台策略”。管理员和观摩源专用账号继续复用现有平台策略读取、编辑和版本权限；其他账号无权进入该功能。

选择策略后显示：

- 策略名称、范围、当前版本
- 品种和周期计划
- 入场方式
- 是否使用缠论、EMA 等声明能力
- “本次分析将冻结 vN，不会跟随之后的策略修改”提示

用户可以填写最多 2,000 字的“当时下单思路”，包括入场原因、观察到的行情结构、止损依据和退出原因。该内容在模型上下文中作为不可信参考数据处理，不得覆盖系统规则、策略配置或输出合同。

### 4.4 阶段三：结果与人工决策

结果页面按结论优先展示：

1. 证据完整度：完整、部分缺失、不可分析。
2. 行情合理性：符合、部分符合、不符合、证据不足。
3. 策略符合度：符合、部分符合、冲突、无法判断。
4. 决策质量：良好、有得有失、需要改进、证据不足。
5. 交易逐笔评价。
6. 策略规则逐项对照。
7. 经验候选。
8. 策略优化候选。

操作按钮分开治理：

- 保存修订：保存用户对模型结论的修改，生成复盘新版本。
- 标记有问题：阻止平台经验候选生成，等待重新修改或重新生成。
- 确认复盘：锁定本次复盘版本，但不自动生成或发布平台经验。
- 确认所选经验：仅把操作者勾选且服务端判定合格的内容创建为 `candidate` 状态的平台经验；本 Tab 不新增发布按钮，发布为 `active` 仍使用现有平台经验人工治理流程。
- 打开策略编辑器：跳转到 AI策略师并选中同一策略，只展示优化建议摘要；不自动修改表单、不自动保存。

当策略当前版本已经高于复盘冻结版本时，结果页显示“策略已更新，本建议基于旧版本”，仍可查看和复制，但不得把建议描述成针对当前版本的直接差异。

## 5. 手动交易识别与证据合同

### 5.1 手动交易判定

一笔交易只有同时满足以下条件，才进入可选列表：

- 属于当前登录用户当前有效账户归属期。
- 已完全平仓，当前持仓中不存在同一持仓身份的剩余数量。
- 入场与出场成交可以按 `position_id` 关联；MT4 缺少该字段时才允许使用稳定的开仓订单票号回退。
- 组成该交易的订单和成交 `magic = 0`。
- 终端提供 reason 时，不得标记为 Expert/EA 来源。
- 未与 `ai_signals`、`auto_signal_deliveries`、`order_intents`、`signal_outcomes` 的票号或持仓身份匹配。
- 历史同步状态完整，没有游标缺口或分页截断。

任一条件无法确定时，服务端返回排除原因，不进入可选择集合。前端不得仅凭 `magic = 0` 自行判断。

### 5.2 交易身份

稳定身份由以下字段组成：

`terminal_instance_id + broker_server + login_account + position_id`

MT4 回退身份为：

`terminal_instance_id + broker_server + login_account + entry_order_ticket`

禁止只用 ticket 在不同账户或终端之间关联。账户身份、归属期和终端实例必须同时校验。

### 5.3 冻结的标准化证据

每笔来源交易保存标准化快照，而不是保存整个账户历史：

- 交易身份和来源判定结果
- 品种、方向、交易量
- 所有入场和出场成交
- 加仓、减仓、部分平仓顺序
- 入场均价、平仓均价
- 开仓时可验证的止损、止盈
- 手续费、佣金、库存费和净盈亏
- 入场、平仓 UTC 毫秒时间
- 对应终端服务器时间、时差和时钟状态
- 原始记录的最小必要引用与内容哈希
- 历史同步完成状态和快照生成时间

服务端生成 `trade_source_hash`。创建复盘时再次读取并比较；记录变化则拒绝提交并要求用户刷新。

### 5.4 历史行情证据

按冻结策略的 `market_data_plan` 和每笔交易的决策/入场时间构建历史行情窗口，优先复用现有行情缓存、历史 K 线和缠论构建能力。证据至少包含：

- 策略要求的各周期 K 线窗口
- 入场前完整闭合 K 线，不使用未来 K 线
- 入场到退出的价格路径
- 当时可计算的趋势、震荡、波动和缠论结构
- 行情数据来源、时间范围、完整状态和哈希

行情证据不完整时可以生成“证据不足”的人工可读复盘，但不得生成可进入平台经验候选区的内容，也不得把策略优化建议标为“可修改”。

### 5.5 用户说明的事实边界

成交数据证明“实际做了什么”，用户说明描述“当时为什么做”，模型只能将其标记为 `user_stated_thesis`。如果用户说明与成交、行情或策略冲突，结果必须明确指出冲突，不能用用户说明覆盖终端事实。

## 6. 策略快照与比较规则

创建复盘时冻结以下内容：

- `strategy_id`
- `strategy_version`
- 策略范围和所有者
- 系统提示词
- `strategy_policy_json`
- `market_data_plan`
- `entry_methods`
- 缠论、EMA 和持仓上下文开关
- 支持品种及其他会影响判断的声明配置
- 快照内容哈希

比较必须基于冻结快照，不在任务执行时重新读取“最新策略”。共享代码只负责通用解析和比较；具体周期、指标参数、入场规则和行情条件全部来自策略快照，禁止在手动复盘模块中硬编码某个策略的 M5/M15/H1、EMA 或形态规则。

策略符合度按规则逐项输出：

- `aligned`：证据支持符合该规则。
- `partial`：部分符合或执行存在偏差。
- `conflict`：明确违反该规则。
- `unknown`：缺少证据，不能判断。
- `not_applicable`：该规则在当前行情不适用。

盈亏不参与“是否符合策略”的直接判定。盈利但违反规则仍是 `conflict`；亏损但按策略和行情合理执行可以是 `aligned`。

## 7. 模型输入与结构化输出

### 7.1 模型输入

模型任务复用复盘用途的模型选择、配额和后台容量队列。输入只包含：

- 冻结策略快照
- 1–10 笔所选交易的标准化证据
- 对应历史行情证据
- 用户可选说明
- 系统定义的输出结构与安全边界

不发送账户密码、真实登录账号、API 密钥、完整账户历史或与所选交易无关的个人数据。

### 7.2 输出合同

建议的顶层结构：

```json
{
  "evidence_quality": "complete|partial|insufficient",
  "review_summary": "string",
  "market_alignment": "aligned|partial|misaligned|unknown",
  "strategy_alignment": "aligned|partial|conflict|unknown",
  "decision_quality": "good|mixed|poor|insufficient_evidence",
  "outcome_independence_note": "string",
  "trade_assessments": [],
  "rule_comparisons": [],
  "strengths": [],
  "issues": [],
  "experience_candidates": [],
  "strategy_optimization_candidates": [],
  "confidence": 0.0
}
```

`trade_assessments` 每项必须引用来源交易身份和证据引用；`rule_comparisons` 必须引用冻结策略中的规则或配置路径。不能定位到具体规则时只能写一般观察，不能伪造规则 ID。

每个 `experience_candidate` 包含：

- `candidate_id`
- `lesson`
- `anti_pattern`
- `applicability`
- `avoid_when`
- `supporting_trade_refs`
- `evidence_refs`
- `confidence`
- `eligibility`：`eligible|needs_more_evidence|rejected`
- `eligibility_reason`

每个 `strategy_optimization_candidate` 包含：

- `candidate_id`
- `target_path`：指向策略快照的合法配置路径；不能定位时为 `null`
- `current_rule_summary`
- `observed_manual_logic`
- `proposed_change`
- `supporting_trade_refs`
- `counter_evidence`
- `applicable_when`
- `risk_if_applied`
- `confidence`
- `recommendation_state`：`observe|candidate|ready_for_human_review`
- `required_more_samples`

服务端必须进行字段、枚举、长度、引用闭包、策略路径白名单和交易引用校验。模型输出不能引用未选交易，也不能把单笔样本标记为确定性的长期策略结论。

### 7.3 防止单笔过拟合

- 1 笔交易：优化建议最高只能是 `observe`。
- 2 笔同类交易：最高只能是 `candidate`。
- 至少 3 笔同类交易且没有直接反例：才允许 `ready_for_human_review`。
- 以上状态只决定文案和排序，不授权自动修改策略。
- 不按盈利笔数计算支持度；必须比较行情条件、策略规则和决策逻辑是否同类。

### 9.3 权限规则

- 所有新接口进入时先调用 `canManagePlatformAiContent(req.user)`；不满足时统一返回 `manual_trade_review_forbidden`，不能只靠 Tab 隐藏。
- 所有 case、source、version 和 job 查询都必须再带 `user_id = req.user.id` 所有权条件；具有平台内容能力不代表可以读取其他管理员或观摩源创建的复盘。
- 交易账户必须属于当前登录身份的有效归属期。观摩源账号只读自己的 Bridge 数据账户；管理员也不得通过本入口读取任意观摩源或普通用户账户。
- 策略必须为未删除的平台策略，并通过现有平台策略管理权限校验；私有策略不进入候选列表。
- 普通用户不能通过猜测 ID 读取复盘、平台策略快照或经验候选；资源不存在与无权读取都按现有防枚举约定处理。
- 平台经验创建只允许 `candidate` 状态；后续发布、撤销和删除复用现有平台经验权限与审计接口。
- 套餐、模型和配额继续复用现有复盘能力判定。

## 10. 平台经验候选生成规则

确认复盘和生成平台经验候选是两个动作。服务端创建候选前再次校验：

- case 状态为 `approved`。
- 请求的版本等于 `approved_version_id`。
- 版本中的候选确实存在且 ID 唯一。
- 候选 `eligibility = eligible`。
- 证据状态为完整。
- 策略仍是当前操作者有权管理的未删除平台策略。
- 候选有非空适用条件或明确标记为通用原则。
- 候选引用仅来自本 case 的所选交易。

单次手动复盘只生成短期平台经验候选，绑定平台策略、策略来源版本和适用条件，并保留 `source = approved_manual_strategy_review`，便于评估和撤销。候选只有在操作者通过现有平台经验治理界面显式发布为 `active` 后才可参与后续精确检索；“确认复盘”和“确认候选”都不能绕过发布步骤。

长期平台经验不在本功能中直接创建。单次手动经验不得直接升级为长期规则；未来如需合并多个手动复盘，只能复用既有跨样本治理或另行评审，首期不增加自动压缩链路。

## 11. 策略优化方案治理

策略优化候选只保存在手动复盘版本中，不写入策略表。前端“打开策略编辑器”只完成以下操作：

- 切换到 AI策略师。
- 选中同一策略。
- 在只读提示区域显示来源复盘、冻结版本、优化建议和风险。

禁止：

- 自动替换系统提示词。
- 自动修改 `strategy_policy_json`。
- 自动勾选指标、周期或执行开关。
- 自动调用策略保存接口。
- 绕过现有策略权限。

操作者人工修改并保存后，继续由现有 `updateStrategy()` 递增策略版本。审计记录只记录实际保存的策略变更；手动复盘 ID 可作为可选 `change_reason` 引用，但不得将“打开建议”记为策略已经修改。

## 12. 并发、幂等与异常恢复

### 12.1 创建并发

- 客户端提供一次性 `client_request_id`。
- 服务端按用户、请求 ID 和最终幂等键防止双击创建重复任务。
- 创建事务保存 case、sources 和 job；任一步失败全部回滚。
- Bridge 读取和行情准备在事务外完成，事务内只保存已验证快照，避免长事务持锁。

### 12.2 模型任务

- 使用租约和 `lease_token`，重启后恢复超时任务。
- 只有持有当前租约的 Worker 能写入结果。
- 模型成功但数据库写入前进程退出时，任务可重试；内容哈希和版本唯一约束防止重复版本。
- 策略在任务期间更新不改变冻结快照；结果标记为基于旧版本。

### 12.3 来源变化

- 创建前来源哈希变化：拒绝并要求刷新。
- 创建后历史费用晚到：不静默重写已确认复盘。未确认 case 设置 `status = needs_revision`、`evidence_status = incomplete`、`evidence_reason = source_changed` 后允许用户重新生成；已确认 case 保留原证据并提示“来源后续发生变化”，需要用户显式发起新复盘。
- Bridge 离线：列表可以显示前端已有缓存的占位，但不能创建任务；服务端返回明确的来源不可用状态。

### 12.4 平台经验候选并发

- 锁定 case 和 approved version 后创建 candidate。
- 同一 `manual_review_version_id + candidate_id` 只能成功一次。
- 策略已删除或权限变化时拒绝创建，不产生无归属平台经验。

## 13. 时间与数据新鲜度

- 数据库存储和跨系统关联使用 UTC 毫秒时间。
- 页面显示和交易业务日使用对应终端实例、经纪商服务器和登录账号的终端服务器时间。
- 保存证据时同时记录 UTC、终端时间、时差、时钟状态和校准来源。
- 时钟未校准或来源不可信时，允许查看交易事实，但禁止生成依赖历史 K 线对齐的复盘和平台经验候选。
- 进入手动复盘 Tab 才加载第一页；筛选、翻页和查看详情按需请求。
- 创建任务只刷新用户已选择的交易及其所需行情窗口，不刷新整个历史账户。

## 14. 安全与隐私

- 操作者下单说明、交易备注、策略提示词和既有经验内容都作为数据传给模型，不允许其中的文字改变系统指令、工具权限和输出合同。
- 所有文本做长度限制、Unicode 正常化和控制字符清理。
- 日志只记录 case、job、策略、账户内部 ID、哈希、阶段和错误码；不记录模型完整正文、交易账号、凭据或用户下单说明。
- 错误响应使用稳定内部错误码，前端转换为自然中文。
- 模型输入不包含无关账户资产、其他用户交易、观摩源隐私和完整历史。
- 所有写操作记录审计：创建、重试、人工编辑、确认、平台经验候选创建、发布/撤销和最终策略保存。

功能完成必须同时满足：

1. 只有管理员和观摩源专用账号可看到并调用手动交易复盘；其他账号前端无入口、后端返回 403。
2. 获准操作者只能选择自己当前有效账户中的高置信度手动已平仓交易，不能跨观摩源或跨用户读取。
3. 系统单、自动交付单、其他 EA 单和证据不完整交易不会进入列表。
4. 只能选择有权管理的平台策略，私有策略不出现在接口或页面中。
5. 分批成交正确聚合，交易数据和历史行情均有来源哈希。
6. 模型使用冻结策略版本，不受任务期间策略更新影响。
7. 结果明确区分行情合理性、策略符合度、决策质量和最终盈亏。
8. 单笔交易不能输出“可直接修改”的策略结论。
9. 确认复盘不会自动修改策略，也不会自动生成或发布平台经验。
10. 只有操作者单独确认的合格内容创建平台经验 candidate；只有再次显式发布为 active 后才参与检索。
11. 打开策略编辑器不会自动改变表单或调用保存接口。
12. 现有周期复盘、平台经验、策略保存、交易记录和 Bridge 历史分页无回归。
13. 服务重启后任务可恢复，重复请求和重复回调不会产生重复版本或经验候选。
14. 页面按需加载，不增加首页或其他 Tab 的历史数据请求。

## 19. 回滚方案

- 前端回滚：移除或隐藏“手动交易复盘”子 Tab，现有待处理复盘和策略记忆不受影响。
- 后端回滚：停止注册新接口和 Worker；保留新增表作为审计数据，不删除用户已确认内容。
- 平台经验回滚：未发布 candidate 可保留审计或按既有治理处理；已发布内容按现有机制标记为 revoked，不物理删除复盘证据。
- 策略无需数据回滚，因为本功能从不自动写策略。
- 迁移采用追加式建表、加空列和加索引，不修改现有交易、周期复盘和策略数据。
- 如果发现手动来源误判，立即停止新任务创建；已生成 case 保留证据并标记 `source_classification_invalid`，阻止确认、候选创建和发布。

## 20. 第一轮复审：需求覆盖、复用与过度设计

### 20.1 检查结论

- 覆盖了用户提出的核心路径：手动选择交易、选择策略、复盘逻辑、对照策略、生成优化方案、人工修改策略。
- 保留了方案一有价值的经验沉淀，但改为独立人工确认动作，不偏离“方案二为主”的产品决策。
- 现有 `trade_review_cases` 与 AI outcome 强绑定，独立表是必要隔离，不是重复建设。
- 复用了 Bridge 分页历史、策略权限、策略版本、模型复盘用途、任务租约和既有经验体系，没有另建历史同步、模型配置或记忆检索系统。
- 原始设想中单独建立“策略优化 proposal 表”和“自动策略补丁预览器”超过当前需求，已删除；优化候选保存在复盘版本中，用户人工修改现有策略编辑器。
- 原始设想中为手动复盘增加独立平台开关和用户开关会增加治理复杂度，已删除；复用现有复盘生成、模型配额和平台内容能力。
- 将选择上限收敛为 1–10 笔，既支持模式比较，又控制模型输入和不同交易逻辑混合风险。
- 自动沉淀经验不属于本需求，已排除；经验必须经过候选确认与现有平台经验发布治理。

### 20.2 第一轮调整

1. 从两个页面收敛为一个 Tab、三阶段工作流。
2. 从“确认后自动写经验”改为“确认复盘”“确认经验候选”“发布平台经验”三个独立动作。
3. 删除自动策略补丁、自动回测和 proposal 独立表。
4. 明确只处理已完全平仓且高置信度手动来源交易。
5. 明确单笔样本只能输出观察项，至少三笔同类证据才可进入人工修改建议等级。
6. 明确按需分页和选中交易强制复验，避免前端全量加载。

第一轮结论：方案满足核心需求，已删除自动修改和额外治理开关等过度设计，可以进入第二轮技术复审。

## 21. 第二轮复审：兼容性、数据、并发、安全、测试与回滚

### 21.1 兼容性与迁移

- 新表、新空列和新索引均为追加式，不修改历史迁移，不改变 `signal_outcomes` 和现有周期复盘语义。
- 新增模块和接口命名独立，不替换现有 `/period-reviews`、`history` 和策略更新接口。
- 平台经验表只增加手动来源引用，现有旧复盘与周期复盘记录仍使用原字段。
- 迁移编号实施前必须重新读取最新序列，防止与并行开发冲突。

### 21.2 数据与时间

- 已补充终端实例、经纪商服务器、登录账号和账户归属期组合身份，避免跨账户 ticket 碰撞。
- 已明确 UTC 用于存储和关联，终端服务器时间用于展示与交易业务语义。
- 已增加时钟不可信时禁止行情对齐复盘和平台经验候选生成的 fail-closed 规则。
- 已增加部分平仓聚合、费用晚到和来源哈希变化处理，避免把未稳定结果当成最终证据。

### 21.3 并发、幂等与恢复

- Bridge 和行情读取放在事务外，最终保存使用短事务，避免远程等待期间持有数据库锁。
- case、sources 和 job 同事务创建；job 使用租约、重试和内容哈希，服务重启可恢复。
- 已确认复盘不会因来源后续变化被静默重写；必须显式创建新复盘。
- 平台经验候选创建锁定 approved version，并对来源版本与候选建立唯一约束。

### 21.4 安全与权限

- 所有接口先校验平台内容能力，再按操作者和账户归属校验；管理员与观摩源专用账号也不能猜测 ID 读取其他操作者的复盘或交易。
- 手动来源必须在服务端判断并强制复验，前端不能决定来源类别。
- 用户说明、策略文本和交易备注均按不可信数据处理，不能改变系统提示与输出合同。
- 策略优化没有写接口，人工保存仍经过现有策略权限和版本递增。

### 21.5 测试与回滚

- 测试覆盖了来源识别、部分平仓、权限、时钟、策略版本、模型输出、任务恢复、经验候选幂等和前端过期响应。
- 真实供应商和真实终端验证与自动测试分开，不把 mock 通过当作生产证明。
- 回滚不删表、不删复盘、不物理删除平台经验；隐藏入口和停止 Worker 即可停止新行为。
- 策略没有自动写入，因此不存在本功能导致的策略数据回滚。

### 21.6 第二轮发现与调整

第二轮发现并修正了以下实质问题：

1. 用户选择列表时的来源哈希可能在创建任务前因历史同步、手续费或部分平仓状态变化而过期，因此新增服务端强制刷新、最终哈希比较和明确的 `source_changed` 状态组合。
2. 同一复盘可以选择多个经验候选，仅按 `manual_review_version_id` 唯一会误伤第二个候选，因此改为 `manual_review_version_id + manual_review_candidate_id` 唯一。
3. 仅靠应用层处理双击不足以保证创建幂等，因此补充 `user_id + client_request_id` 数据库唯一约束。
4. 跨账户交易的合约规格、终端时钟和归属期不同，因此明确同一 case 只能选择同一账户的交易。
5. 策略可能在模型运行期间更新，因此补充冻结版本、快照哈希和结果过期提示，防止建议错误套用到当前版本。

调整后未发现阻止实施的兼容性、数据、并发、安全或回滚问题。

第二轮结论：方案符合现有架构和用户需求，实施边界明确，没有自动改策略、单笔直接升级长期经验或全量历史加载等过度设计。方案可实施。

## 22. 第三轮复审：管理员/观摩源可见性与平台经验边界

### 22.1 发现的问题

新增“只有管理员和观摩源账号可以看到”后，原方案不能只增加前端隐藏规则。复审发现原方案仍以普通用户、私有策略和个人记忆为主，这与现有权限架构冲突：

1. `canManagePlatformAiContent()` 已将管理员与 `role = user, plan_source = observer_source` 统一定义为平台 AI 内容管理者；若另写角色判断会产生两套权限逻辑。
2. 观摩源专用账号只能维护平台策略，复盘结论也只能沉淀为平台记忆；个人记忆接口会明确拒绝平台内容管理者。
3. 仅隐藏 Tab 无法防止普通用户直接调用接口，也无法防止有平台内容能力的账号横向读取其他账号 case。
4. “管理员可见”不等于“管理员可浏览全部观摩源交易”。若默认开放跨账号交易，会扩大敏感交易数据权限且超出本需求。
5. 将确认动作直接写为 active 平台经验，会绕过现有 candidate → active 的人工发布治理。

### 22.2 本轮修订

- Tab 与全部 API 统一复用 `canManagePlatformAiContent()`；普通用户和观摩订阅用户前端无入口，后端仍强制 403。
- case、source、version、job 继续按 `user_id = req.user.id` 隔离；管理员与观摩源账号之间也不能互读复盘。
- 交易范围收敛为当前登录身份自己连接且归属有效的账户，不增加管理员跨观摩源选择器。
- 策略选择从“私有或平台策略”收敛为“当前操作者有权管理的平台策略”。
- 经验归属从个人记忆改为平台经验；确认所选内容只创建 `candidate`，显式发布为 `active` 后才可检索。
- 数据扩展从 `experience_memory_items` 改为 `platform_strategy_experience_items`，保留手动复盘版本和候选的唯一引用。
- 增加身份矩阵、伪造接口请求、跨账号 case、跨账户交易、私有策略排除和 candidate 不得直达 active 的测试。

### 22.3 过度设计复查

- 未新增新的角色、权限表或独立发布系统，直接复用平台内容能力与平台经验状态机。
- 未为管理员增加跨观摩源交易浏览器；该能力涉及额外隐私和审计要求，当前需求没有授权。
- 未增加自动经验合并、自动发布、自动策略修改或自动回测。
- 保留独立手动复盘 case/source/version/job 是证据合同隔离所必需，不属于重复建设。

第三轮结论：修订后的可见性、数据归属、策略范围和经验生命周期与现有架构一致；没有发现阻止实施的问题，也没有保留为满足权限要求而不必要的额外系统。方案可实施。

## 23. 剩余风险

- 某些老 MT4 历史可能缺少稳定 `position_id`、reason 或完整成交字段，只能安全排除，不能为了覆盖率猜测。
- `magic = 0` 是重要证据但不是绝对证明；必须结合系统票号反查和终端 reason，仍可能存在第三方工具使用 0 Magic 的极少数情况。
- 历史行情缓存不足时只能得到证据不足结论，不能补用未来行情或当前行情。
- 用户未填写真实下单思路时，模型只能重建“可能的逻辑”，不能把推测写成事实。
- 用户主动挑选成功交易可能造成样本偏差；页面需要提示同时选择亏损或反例，模型输出也必须披露样本限制。
- 当前策略表只保留当前配置及递增版本号，本方案通过 case 内冻结完整快照解决复盘可重现性，但不会反向建设完整策略版本仓库。
- 平台经验来源虽然只允许当前登录身份自己的交易，但一旦发布会影响绑定该平台策略的后续检索；发布界面必须清楚显示来源是单次手动复盘、样本数量、冻结策略版本和适用/避用条件。
- 当前不支持管理员代替观摩源选择其交易。如果未来需要该能力，必须单独补充明确授权、来源选择、审计、脱敏与撤权后的数据处理方案，不能只放开查询条件。
