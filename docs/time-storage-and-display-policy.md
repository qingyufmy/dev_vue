# 时间存储与显示规则

2026-09-07 用户明确决定：数据库时间统一 UTC，AI 交易实验室显示终端时间，其它页面显示北京时间。本规则细化现有数据库规范，适用于后续全部迁移和前端开发。

## 存储与传输

- 表示一个时刻的字段统一存 UTC，V4 SQL 使用 UTC 会话与 `DATETIME(3)`；Unix 时间戳仍表示 UTC 时刻。HTTP、实时事件使用带 `Z` 的 ISO 时间，前端不改写其原值。
- MySQL 驱动的 `timezone: 'Z'` 与 SQL 会话的 `SET SESSION time_zone = '+00:00'` 同时设置。SQL 会话初始化失败则销毁连接。
- 时长、业务日期、交易时段不是时间戳，不做机械偏移。终端时区、采样时间与校准状态是独立证据，仍需保存；“只存 UTC”不表示删除时区元数据。
- 用户于 2026-09-07 明确接受旧时间可能存在偏差：后续旧表 DATETIME 统一按 UTC 原值迁移，offsetMinutes=0，不再校正历史北京时间或等待历史部署时区证明。已有 UTC 时间戳保持原值；保留原始值和用户决定证据，不把约定写成历史时区已验证。不重写已执行迁移或擅自修改已完成批次。

## 显示与输入

- `trade` 整个应用属于 AI 交易实验室。普通记录使用当前账户的终端时区；历史交易和复盘优先使用记录冻结的终端偏移，复盘业务日期先转换再截取日期。
- 当前快照必须与当前账户 ID 匹配。缺少时区时只在显示层使用 UTC+3，并明确标识待校准；休市仍沿用该账户最近有效偏移。
- `www`、`auth`、`admin` 使用北京时间 UTC+8；通用入口为 `@aurum/ui/lib/time` 的 `formatBeijingTime`。当前这三个应用未发现已有日期格式化显示入口，后续新增页面须使用该入口。
- 不依赖浏览器、Windows 或 SSR 进程的本地时区。无时区的时间字符串不能作为 API 时刻直接解析。
- 挂单到期输入使用终端时间，提交前转回 UTC。输入时冻结账户与偏移，账户或偏移变化须重新打开表单。缺少有效偏移不能使用显示默认值生成交易有效期；未改到期时间不重复写入。
- UTC+3 显示默认值不进入数据库校准证据、风控、交易时段或复盘边界判断。

## 实施与历史迁移边界

本次实现统一前端格式化及 V4 连接池 UTC 初始化。当前 `dev_vue` 旧表尚未全部回填；本政策是目标规范，不是全部历史数据已迁移的证明。课程/进度已按用户确认的零偏移清单完成回填，见阶段 185；其它域继续逐批迁移，使用同一 UTC 原值口径。
