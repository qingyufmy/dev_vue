# 统一策略记忆库实施方案

## 1. 结论

本次改造将彻底停止运行时的“短期记忆、长期记忆、月度摘要、按需检索”分层模型，改为：

- 每个策略只有一个当前有效的总记忆库。
- 总记忆库是完整、可人工编辑、带版本历史的文本资产。
- 手动分析、自动分析、日复盘、月复盘均直接传入当前策略全文和总记忆库全文，不再检索若干记忆条目。
- 已人工确认的日复盘才可向记忆库沉淀内容；月复盘确认后执行总结压缩。
- 达到存储容量时自动压缩；默认容量为 120,000 个 UTF-8 字符，目标压缩至容量的约 60%。容量限制是记忆资产的存储治理，不是模型输出 Token 硬上限。
- 记忆经验与策略冲突只记录证据，不自动修改策略。至少 3 个不同、已人工确认的日/月复盘指向同一冲突后，才显示“需要人工评估修改策略”的提醒。

该方案采用切换式迁移：旧记忆表只读保留用于历史审计，新代码不再双写或读取旧的短期、长期、摘要数据。

## 2. 当前实现与问题

### 2.1 已核实的现状

当前个人记忆由以下资产共同组成：

- `experience_memory_items`：短期记忆及重复候选。
- `experience_long_term_memories`：长期候选、确认、撤销。
- `experience_memory_summaries`：自动压缩或月度摘要。
- `memory_compression_jobs`：旧分层条目压缩任务。
- `memory_injection_logs`：按环境检索后注入若干条目的日志。
- `user_memory_settings.runtime_token_budget`：按需检索的运行时预算。

平台策略另有一套 `platform_strategy_experience_items` 与策略级检索政策。分析运行时分别调用个人检索或平台检索；日/月复盘确认后也分别写入两套资产。

本地数据库当前个人三类记忆均为 0 条，平台策略经验共 6 条，其中 3 条有效、3 条已撤销。因此本地迁移可以验证平台有效数据归并，但迁移仍必须支持其他环境已有的个人数据。

### 2.2 必须解决的问题

- “每个策略一个总库”与现有“用户级多层条目 + 平台另一套条目”模型冲突。
- 运行时只选择少量匹配条目，不能满足每次完整传入总库的要求。
- 用户当前无法直接编辑一份完整、权威的策略记忆文本。
- 月复盘压缩和达到容量压缩是两条不同路径，缺少统一的版本、并发和失败恢复合同。
- 现有月复盘的 `conflict_groups` 表示经验之间的冲突，不等于“经验与策略规则冲突”，不能直接复用为修改策略提醒。

## 3. 目标数据模型

### 3.1 当前总库

新增 `strategy_memory_libraries`，每个 `strategy_id` 仅一行：

- `strategy_id`：主键，严格绑定策略，不按策略版本拆库。
- `strategy_scope`、`owner_user_id`：权限与迁移快照；读取时仍以策略表为权威校验。
- `content_text`：当前唯一参与分析与复盘的完整记忆库文本。
- `version_no`、`content_hash`：乐观并发与注入快照标识。
- `char_count`、`estimated_token_count`：展示和预检统计；不作为模型输出硬上限。
- `capacity_chars`：默认 120,000，可由有权管理策略记忆的用户调整。
- `compression_target_ratio`：默认 0.60。
- `conflict_alert_threshold`：默认 3。
- `pending_update_count`、`compression_status`、`last_compacted_at`：运行状态。
- `created_at`、`updated_at`、`updated_by_user_id`。

总库内容采用可读 Markdown，按“通用原则、行情环境、入场、缠论、风控执行、来源说明”组织。条件标签保留在正文中，但运行时不再据此筛选条目。

### 3.2 不可变版本与待合并更新

新增：

- `strategy_memory_library_revisions`：保存每次人工编辑、日复盘追加、月度压缩、容量压缩和旧数据导入的完整快照。历史版本只用于审计与人工回滚，不参与运行时注入。
- `strategy_memory_pending_updates`：保存已确认复盘产生、但尚未成功合并的更新；以来源复盘版本作为唯一幂等键。
- `strategy_memory_compression_jobs`：统一承载容量压缩和月度压缩，冻结源库版本、待合并更新集合和模型任务 ID。
- `strategy_memory_injection_logs`：记录分析或复盘实际注入的库版本、哈希、字符数、信号/快照/复盘任务关联。

待更新表和版本表是审计/恢复设施，不是第二个运行时记忆库。任何时刻只有 `strategy_memory_libraries.content_text` 是权威运行时内容。

### 3.3 策略冲突证据

新增：

- `strategy_memory_conflicts`：策略级冲突候选，包含稳定冲突键、冲突说明、策略原文摘要、建议修改方向、累计不同复盘数、状态和提醒阈值。
- `strategy_memory_conflict_occurrences`：每个已确认复盘对某个冲突的一次证据，唯一键防止重试或重复确认重复计数。

状态语义：

- `observing`：证据少于阈值，不显示修改策略提醒。
- `attention_required`：不同已确认复盘数达到阈值，显示独立提醒。
- `resolved`：人工确认已修改策略或问题已处理；保留历史。
- `dismissed`：人工判定不构成冲突；后续新证据不自动重新打开，除非人工恢复。

系统不得自动修改策略提示词、策略政策或交易规则。

## 4. 权限与归属

- 私有策略：只有策略所有者可查看、编辑、调整容量和处理冲突。
- 平台策略：只有具备平台 AI 内容管理权限的身份可编辑和处理冲突；普通订阅用户只能在推理中使用，不能读取管理全文或修改。
- 服务端每次读取或修改都重新查询 `auto_prompt_types` 的 scope、owner、删除和启用状态，不能仅信任记忆库冗余字段。
- 人工保存必须携带 `expected_version_no`；版本已变化时返回稳定错误 `strategy_memory_version_conflict`，不覆盖他人或后台压缩的新版本。
- 文本经过控制字符清理，但保留 Markdown；前端只以文本方式编辑和展示，禁止把记忆内容作为 HTML 注入。

## 5. 业务流程

### 5.1 手动与自动分析

1. 解析并校验策略。
2. 读取该策略唯一总库及版本。
3. 将策略全文和记忆库全文明确分区后传给模型；空库也传递“当前无已确认记忆”。
4. 不执行关键词、品种、周期、方向或层级筛选，不使用 `runtime_token_budget`。
5. 模型物理输入预检仍使用已确认的模型最大输入和上下文窗口；记忆过大导致物理输入不足时返回明确错误并排队压缩，不静默截断总库。
6. 持久化注入日志，记录库版本和哈希。

### 5.2 日复盘

1. 模型输入必须包含冻结交易证据、当前策略全文、当前记忆库全文及库版本。
2. 输出继续产生日复盘结论，并新增结构化 `memory_updates` 与 `strategy_conflicts`。
3. 只有人工确认日复盘后，派生任务才创建幂等待更新记录并累计冲突证据。
4. 若当前库加更新后低于容量，事务内追加并生成新版本。
5. 若将达到或超过容量，不写入超限当前库；创建容量压缩任务，把当前库和待更新一起压缩合并。失败时待更新保留并重试，当前稳定版本继续服务。

### 5.3 月复盘

1. 月度分块和最终汇总均传入当前策略与记忆库快照，所有分块使用同一版本。
2. 继续保留经验之间的 `conflict_groups`，另输出经验与策略之间的 `strategy_conflicts`。
3. 人工确认月复盘后，无论是否达到容量，都创建 `monthly_review` 压缩任务。
4. 压缩输入包含当前总库、当月已确认结论和未合并更新；输出是一份完整的新总库，不是摘要旁路。
5. 成功后以版本 CAS 原子切换当前内容，保存完整前后版本；源版本变化则任务重新冻结，不覆盖较新人工编辑。

### 5.4 人工编辑

- 页面按策略选择记忆库，显示完整文本、字符容量、当前版本、更新时间、待合并/压缩状态。
- 用户可直接修改全文并保存；保存创建 `manual_edit` 版本。
- 保存内容超过容量时拒绝并提示缩减或先压缩，不自动截断。
- 提供版本历史和人工回滚；回滚本身生成新版本，历史不可变。
- 冲突达到阈值后在同一策略下显示独立提醒，可标记已处理或忽略。

## 6. 压缩合同

- 触发：预计写入达到 `capacity_chars`，或月复盘确认。
- 默认目标：不超过 `floor(capacity_chars * 0.60)`；若模型输出仍超出目标，验证失败并在同一模型任务期限内按既有修复机制重试。
- 必须保留：仍有效的策略经验、适用/避用条件、相互矛盾经验的分区、重要风控边界、来源周期概述。
- 必须删除或合并：重复表述、已被更完整结论覆盖的旧表述、无证据的推测、流水账。
- 禁止：修改策略本身、把冲突经验强行合并、增加绝对手数或绕过风控、生成未提供的新事实。
- 模型请求的最大输出继续取供应商已确认物理上限；字符目标仅验证业务资产大小。

## 7. 迁移与切换

新增幂等迁移 `181_unified_strategy_memory_library`：

1. 创建新表、索引、唯一键和必要的策略记忆功能标志。
2. 按策略归并旧的有效个人短期记忆、已确认长期记忆、有效摘要，以及有效平台策略经验。
3. 每个策略生成一个 `legacy_import` 初始版本；保留原记录 ID、类型和条件为可读来源说明。
4. 已撤销、过期、候选未确认、失效摘要不进入当前总库，但旧表原样保留。
5. 无 `strategy_id` 的旧个人记忆不猜测归属，不导入当前库，并在迁移审计统计中报告。
6. 应用切换后不再写入或读取旧表；旧 API 返回 410 和新端点提示。

迁移不删除旧表、不修改旧记录状态，回滚可让旧版本应用继续读取原数据。新应用不提供退回旧分层运行时的开关，避免双系统漂移。

## 8. API 与界面

新增统一端点：

- `GET /api/ai/strategy-memories`：列出当前身份可管理的策略及库概览。
- `GET /api/ai/strategy-memories/:strategyId`：返回当前全文、设置、状态、提醒和版本摘要。
- `PUT /api/ai/strategy-memories/:strategyId`：人工保存全文和库级设置，必须带期望版本。
- `POST /api/ai/strategy-memories/:strategyId/compress`：人工请求压缩，仅排队，不同步占用 HTTP。
- `POST /api/ai/strategy-memories/:strategyId/revisions/:revisionId/restore`：以旧内容创建新版本。
- `POST /api/ai/strategy-memory-conflicts/:id/:action`：`resolve`、`dismiss`、`reopen`。

个人和平台界面都只显示“策略记忆库”，移除短期、长期、摘要、候选发布、按需检索预算等控件和文案。来源、版本和压缩状态通过渐进披露展示。

## 9. 旧能力退役范围

- 退役 `retrievePersonalMemory`、`retrievePlatformExperience` 的运行时调用。
- 退役短期过期、长期候选、长期确认、摘要回滚、按类别检索和旧压缩工作流。
- 停止 `memory_compression_jobs` 旧 worker；已排队旧任务在切换时标记为退休/不再执行，但不删除。
- `memory_injection_logs` 与平台经验日志只保留历史查询，不再新增。
- `user_memory_settings.runtime_token_budget`、`retrieval_mode` 和平台 `max_items` 不再参与运行时。
- 原 `experience_memory_enabled`、`memory_compression_enabled` 与平台分层策略仅作旧版本兼容审计；新运行时使用统一策略记忆状态。

## 10. 并发、幂等与失败恢复

- 复盘派生唯一键：`period_review_version_id + strategy_id + update_kind`。
- 冲突发生唯一键：`conflict_id + period_review_version_id`。
- 当前库更新：事务锁定库行并比较 `version_no/content_hash`。
- 压缩任务：唯一冻结 `strategy_id + source_version + trigger + source_set_hash`。
- 人工编辑优先：压缩完成时若源版本已变化，结果不得应用；重新排队使用新版本。
- 分析始终读取最近一次成功版本；待更新或压缩失败不让总库变为半成品。
- worker 重启后回收过期 lease，并通过模型任务状态判断重试、未知状态或终态，不能重复调用供应商。

## 11. 实施批次与验收门槛

### 批次 A：迁移与核心服务

- 新表、旧数据归并、权限、版本、人工编辑、待更新、冲突累计。
- 门槛：迁移重复执行幂等；本地 3 条有效平台记忆可归并；旧表行数和内容不变。

### 批次 B：推理与复盘接入

- 手动/自动分析完整注入；日/月复盘传入策略和库；批准后统一沉淀。
- 门槛：私有/平台策略各覆盖；空库、非空库、未授权、策略删除、模型输入不足均有回归测试。

### 批次 C：统一压缩与冲突提醒

- 容量/月度压缩 worker、CAS、恢复、阈值提醒。
- 门槛：重复审批不重复累计；第 1、2 次不提醒，第 3 个不同批准复盘才提醒；压缩失败保留当前库和待更新。

### 批次 D：界面与旧入口退役

- 单一全文编辑器、容量/版本/状态、冲突处理、历史回滚；移除所有层级文案与操作。
- 门槛：浏览器实测个人和平台权限，键盘操作、冲突保存、版本冲突、压缩中/失败状态。

### 批次 E：全量验证

- 对所有修改的 JavaScript 运行 `node --check`。
- 运行记忆、策略、调度、复盘、前端、迁移定向测试，再运行 `npm test`。
- 重启本地 3000 端口可见 PowerShell，检查 `/health`、首页和 `/ai`，执行一次手动分析、自动分析、日复盘确认与月度压缩的非交易验证。

## 12. 回滚与数据安全

- 新表为追加式迁移，旧表不删除，数据库结构回滚不依赖恢复备份。
- 应用回滚到旧版本前，应停止新记忆 worker；旧版本仍可读取迁移前旧表，但看不到切换后新库更新。
- 不提供双写回滚，因为双写会产生无法判定的权威冲突；若必须长期回滚，需单独授权把新库版本导出为旧格式。
- 不删除历史记忆、复盘、信号、模型任务或注入日志。

## 13. 第一轮方案复审：需求与设计边界

### 检查结论

- 需求覆盖：已覆盖单库、完整传入、人工修改、日/月复盘携带、冲突多次提醒、容量压缩、月度压缩和取消短/长期记忆。
- 业务边界：明确只有确认复盘可沉淀，冲突不自动改策略，避免模型直接改变交易规则。
- 现有能力复用：复用复盘批准派生任务、模型任务追踪、供应商物理限制、租约恢复和权限函数；不重建调度基础设施。
- 最小改动：不能只在旧表上改名，因为旧个人/平台数据模型、检索和状态语义不同；新增单库和修订表是必要改动。
- 设计过度检查：移除条目级检索、向量化、短长期晋升和多摘要；仅保留版本、待更新、压缩和冲突证据这四类必要治理数据。

### 第一轮调整

- 原设想允许容量触发后短暂写入超限库，复审后改为“待更新 + 压缩成功后原子切换”，避免分析收到超容量或被截断的库。
- 原设想按生成复盘立即累计冲突，复审后改为只对人工批准版本累计，减少模型单次误判造成提醒。
- 原设想复用旧 `memory_injection_logs`，复审后改为新库版本日志，避免继续携带 selected short/long IDs 的旧合同。
- 明确容量以字符计量且与供应商 Token 上限分离，避免重新引入用户刚取消的输出 Token 硬限制。

### 第一轮剩余风险

- 大型总库每次完整注入会增加请求字节、成本和延迟，这是需求本身的权衡；通过容量和压缩治理，不做按需检索回退。
- 语义相同但措辞不同的策略冲突可能被分成多个候选；稳定冲突键、类别和文本相似度只能降低，不能完全消除该风险。

## 14. 第二轮方案复审：兼容性与运行安全

### 检查结论

- 兼容性：旧表与数据只读保留；旧 API 明确 410；`/api` 与 `/aurum-api` 路由兼容由现有挂载方式继续保障。
- 数据迁移：只导入有效且可确定策略归属的数据；不猜测无策略记录，不导入撤销/过期/未确认候选；迁移可重复且用哈希去重。
- 并发与幂等：批准重试、worker 重启、人工编辑与压缩竞态均有唯一键和版本 CAS；压缩不得覆盖较新版本。
- 异常恢复：当前成功库与待更新分离；模型失败、未知终态或 lease 丢失不会污染当前库。
- 时间语义：复盘周期仍使用可信终端时间；记忆更新时间只作审计，不参与交易周期判断。
- 安全：权限以策略表实时校验；人工文本不作为 HTML；提示词明确记忆是经验资料而非越权指令，现有策略和风控优先级不变。
- 测试：迁移、权限、注入、批准派生、阈值、压缩 CAS、恢复、旧入口退役和浏览器状态均有明确门槛。
- 回滚：不删除旧表、不双写；应用回滚时新数据不可见但不会损坏旧数据。

### 第二轮发现与调整

- 发现月度分块可能跨多次模型调用。最终方案要求同一月复盘的所有分块和汇总冻结同一个库版本，防止月中人工编辑导致各分块依据不一致。
- 发现平台与个人当前是两套权限。最终方案以策略为唯一归属，同时保留平台内容管理权限与私有所有者权限，普通订阅用户不能借分析权限读取平台记忆全文。
- 发现模型物理输入可能小于库容量。最终方案禁止静默截断：先做物理输入预检，必要时排队压缩并返回可解释状态。
- 发现旧压缩任务可能在切换后继续运行。最终方案要求停止旧 worker，并让旧任务只保留审计状态，防止切换后继续写旧摘要。

### 第二轮剩余风险与实施判定

- 旧应用回滚后无法看见切换后新库内容；这是避免双写漂移的有意取舍，长期回滚需另行导出。
- 真实供应商对接的超大文本压缩仍需本地真实模型验证，单元测试只能证明合同和状态机。
- 前端目前集中在大型静态文件，修改需严格做静态资产缓存键与浏览器实测。

在上述风险可接受且验证门槛不降低的前提下，方案判定为可实施。
